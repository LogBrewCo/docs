تعرض هذه الصفحة مثالًا واحدًا لكل عائلة استجابات في [Telemetry API](/ar/reference/telemetry-api). كل القيم مصطنعة. لرموز الأخطاء وطرق التعافي، راجع [أخطاء API](/ar/reference/api-errors).

## <span id="read-a-response">اقرأ الاستجابة</span>

اقرأ كل استجابة بهذا الترتيب:

1. اقرأ حالة HTTP.
2. تأكد أن للنص الشكل الذي يحدده المسار.
3. تأكد أن كل `project_id` يقع داخل نطاق المشروع المطلوب.
4. أبقِ قيم التعداد (enum) المعيارية والمعرّفات دون تغيير.
5. اتبع `next_action` فقط عندما يدعم العميل قيمتي `code` و`target` الخاصتين به.
6. تعامل مع `null` والحقل المحذوف والقائمة الفارغة على أنها حالات مختلفة.

قد تحتوي الاستجابة `200 OK` على قائمة فارغة. قائمة السجلات الفارغة تعني أنه لم يطابق أي سجل الطلب. ولا تعني أن المشكلات أو التتبّعات أو الإجراءات فارغة أيضًا. لا تربط الإشارات لأن طوابعها الزمنية متقاربة. اتبع تتبّعًا فقط عندما تحتوي الاستجابة على `trace_id` الخاص به تمامًا.

الاستجابة `404` والقائمة الفارغة نتيجتان مختلفتان. يعيد مسار القائمة `[]` عندما لا يطابق أي قيد. ويعيد مسار التفاصيل `404` مع `code: not_found` عندما لا يجد قيدًا يمكن قراءته. لا تثبت أي من النتيجتين أن الاستيعاب فشل.

## <span id="what-to-send">ما يجب إرساله</span>

فائدة الاستجابات بقدر فائدة بيانات القياس عن بُعد التي ترسلها. أرسل هذه القيم في كل غلاف أو إعداد SDK:

- `release` و`environment`.
- أسماء ثابتة للخدمات والإجراءات والمقاييس.
- سياق التتبّع عندما تنتمي السجلات والـ Spans والإجراءات والمشكلات إلى الطلب نفسه.
- قيم الخطورة المعيارية: `info` و`warning` و`error` و`critical`.
- سمات تساعد في تصحيح الأخطاء، دون أسرار أو بيانات شخصية غير ضرورية.

راجع [دمج SDK](/ar/guides/sdk-ingestion) و[التحكم في البيانات الملتقطة](/ar/guides/safe-capture).

## <span id="ingestion-response">استجابة الاستيعاب</span>

تقرأ حزم SDK العامة استجابة `POST /v1/events` نيابةً عنك. لا تحتاج شيفرة التطبيق إلى معالجتها.

### <span id="sdk-batch-response">استجابة دفعة SDK</span>

تعيد دفعة SDK الناجحة `200 OK` مع الأعداد المقبولة لكل تدفق:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| الحقل | المعنى |
| --- | --- |
| `issues`، `logs`، `trace_spans`، `actions`، `metrics` | الأحداث التي قبلها LogBrew من هذه الدفعة. |
| `already_accepted` | الأحداث التي قبل LogBrew معرّفاتها سابقًا. لا يخزّنها LogBrew مرة أخرى. |
| `context_updated` | `true` عندما تحدّث الدفعة سياق الإصدار أو البيئة. |

تغطي الأعداد هذه الدفعة فقط. إعادة محاولة دفعة قبلها LogBrew سابقًا تعيد `0` لكل تدفق، وعدد الأحداث في `already_accepted`. أبقِ معرّفات الأحداث الأصلية عندما تعيد المحاولة.

### <span id="native-envelope-response">استجابة الغلاف الأصلي</span>

يعيد `POST /api/telemetry/ingest` الاستجابة `200 OK` مع أعداد العناصر المقبولة لكل تدفق:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

ليس في الاستجابة الأصلية حقل `metrics` أو `context_updated`. لا تضفهما. يعدّ `already_accepted` العناصر التي قبل LogBrew قيمة `id` الخاصة بها سابقًا لهذا المشروع. راجع [الغلاف الأصلي المباشر](/ar/guides/sdk-ingestion#required-envelope-fields).

### <span id="ingestion-errors">أخطاء الاستيعاب</span>

الاستجابة `401` مع `code: ingest_key_invalid` تعني أن رمز Bearer للاستيعاب مُبطَل أو منتهي الصلاحية أو غير صالح للمشروع. في `POST /v1/events`، يعيد الطلب `401` مع `code: unauthorized` عندما يغيب رمز Bearer أو لا يكون مفتاح استيعاب. استخدم رمز Bearer الحالي للاستيعاب الخاص بالمشروع. لا تُعد المحاولة باستخدام رمز Bearer للحساب.

تعيد دفعة SDK المرفوضة `422` مع `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

من قيم `error` الأخرى `SDK event batch requires at least one event` و`SDK event type is not supported by this ingest route`. افحص إصدار الـ SDK وإعدادات النقل. لا ترسل دفعة فارغة. لا تغيّر أنواع الأحداث أو معرّفاتها لمجرد أن تجتاز الدفعة التحقق.

الطلب بطريقة غير `POST` يعيد `405` مع `code: method_not_allowed`. ونص JSON غير المقروء يعيد `code: invalid_json`.

## <span id="telemetry-list-response-format">تنسيق استجابة قوائم بيانات القياس عن بُعد</span>

تعيد مسارات القوائم افتراضيًا مصفوفة JSON مجردة. القائمة الفارغة الناجحة هي `[]`.

مع `pagination=cursor`، يعيد المسار غلافًا. يطابق مفتاح المجموعة نوع الإشارة:

| المسار | مفتاح المجموعة |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`، مع `issue_id` في المستوى الأعلى |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`، مع `naming_quality` في المستوى الأعلى |

`next_cursor` كائن فيه حقول المتابعة، أو `null` في الصفحة الأخيرة. الصفوف مرتبة من الأحدث إلى الأقدم. راجع [ترقيم الصفحات بالمؤشر](/ar/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">استجابة السجل</span>

صفحة مؤشر للسجلات مع `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

تتضمن السجلات `level` للتوافق و`severity` للعرض. يحمل الحقلان كلاهما القيمة المعيارية. ويحمل `triage` نتيجة قاعدة الخطورة. راجع [استجابات قواعد الخطورة](#severity-rule-responses).

يكون `trace_id` و`span_id` بالقيمة `null` عندما لا يكون للسجل رابط تتبّع. عندها تكون قيمة `next_action` هي `inspect_related_logs` والهدف `telemetry_logs`. تستخدم السجلات والمشكلات والإجراءات زوجَي `next_action` نفسيهما.

يعيد `GET /api/logs/{log_id}` سجلًا واحدًا بالشكل نفسه.

### <span id="issue-response">استجابة المشكلة</span>

يعيد `GET /api/telemetry/issues/{issue_id}` مشكلة مجمّعة واحدة. وتعيد القائمة الكائنات نفسها. يستخدم هذا المثال نسخة الاستجابة الافتراضية 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

في النسخة 1، قيمة `status` هي `unresolved` أو `resolved` أو `ignored`. للمشكلة المؤرشفة، تكون قيمة `triage.ignored` هي `true`. لأزواج `next_action` والقراءات التي تليها، راجع [التحقيق في مشكلة](/ar/guides/investigate-an-issue).

`first_seen_at` و`last_seen_at` هما وقتا أول حدوث وأحدث حدوث. لا يتغيران عندما تتغير الحالة.

تظهر بعض الحقول فقط عندما تتوفر البيانات لدى LogBrew:

| الحقل | متى يظهر |
| --- | --- |
| `span_id` | للمشكلة رابط Span. وإلا يُحذف الحقل. |
| `diagnostics` | لأحدث حدوث نوع استثناء أو Breadcrumbs (أحداث قصيرة مسجَّلة قبل وقوع المشكلة). راجع [تاريخ مرات حدوث المشكلة](#issue-occurrence-history). |
| `symbolication` | في `GET /api/telemetry/issues/{issue_id}` فقط، عندما تكون للمشكلة هوية ملف بناء خاصة بالإصدار. راجع [خرائط المصدر لـ JavaScript](/ar/guides/source-maps). |

قيمة `symbolication.status` هي `resolved` أو `invalid_metadata` أو `artifact_not_found` أو `source_not_resolved` أو `unavailable`. لا تعيد القائمة ولا تغييرات الحالة ولا تغييرات القواعد الحقل `symbolication`.

مع `response_version=2`، للمشكلة الحقول نفسها، مع هذه التغييرات:

| الحقل | القيمة في النسخة 2 |
| --- | --- |
| `status` | `unresolved` أو `resolved` أو `archived`. تعرض النسخة 1 القيمة `archived` على أنها `ignored`. |
| `priority` | `high` أو `medium` أو `low`. |
| `priority_source` | `manual` عندما يضبط شخص الأولوية. `derived` عندما تتبع الأولوية الخطورة الفعلية. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

يعرض هذا المثال بعض الحقول فقط. الأولوية المشتقة هي `high` لـ `error` و`critical`، و`medium` لـ `warning`، و`low` لـ `info`. وهي تستخدم `triage.effective_severity`، لذلك يمكن لقاعدة خطورة المشكلة أن تغيّرها.

مع `response_version=3`، للمشكلة كل حقول النسخة 2 بالإضافة إلى `assignee`. تكون قيمة `assignee` هي `null` عندما لا يكون للمشكلة مسؤول:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| الحقل | المعنى |
| --- | --- |
| `assignee.user_id` | معرّف المستخدم المسؤول. أرسله في `assignee` ضمن عامل تصفية أو تغيير. |
| `assignee.name` | اسم المسؤول، أو `null` عندما لا يكون للحساب اسم. |
| `assignee.email` | عنوان البريد الإلكتروني للمسؤول. |

لا تعرض المشكلة أي مسؤول عندما يفقد العضو المُسند إليه صلاحية قراءة المشروع.

مع `response_version=4`، يحمل `assignee` أيضًا الحقل `type`. المسؤول من نوع `user` له `user_id` و`name` و`email` كما في النسخة 3. والمسؤول من نوع `team` له `team_id` و`slug` و`name`. تعرض النسخة 3 الفريق المسؤول على أنه `null`. يطلب CLI النسخة 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

أي قيمة أخرى لـ `response_version` تعيد `422` مع `code: validation_failed`. وتستخدم صفحة المؤشر النسخة نفسها لكل مشكلة في `issues`.

### <span id="assignee-list-response">استجابة قائمة المسؤولين</span>

يعيد `GET /api/telemetry/issues/assignees?project_id=<project_id>` كل حساب يمكن إسناد المشكلات إليه في المشروع:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

أضف `response_version=2` لتحصل أيضًا على `teams`: كل فرق مؤسسة المشروع، مع `team_id` و`slug` و`name`.

إذا لم يستطع الحساب قراءة المشروع، يعيد المسار `404` مع `code: not_found`.

### <span id="action-response">استجابة الإجراء</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

يتبع `distinct_id` جهة فاعلة واحدة أو جلسة واحدة. تعامل مع `distinct_id` و`session_id` على أنهما معرّفان مبهمان. يكون `session_id` و`trace_id` بالقيمة `null` عندما يكونان مفقودين. ويُحذف `span_id` عندما يكون مفقودًا. ليس للإجراء خطورة. راجع [التقاط أحداث المنتج](/ar/guides/product-events).

### <span id="release-response">استجابة الإصدار</span>

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

يغطي الصف الواحد مشروعًا واحدًا وإصدارًا واحدًا وبيئة واحدة وخدمة واحدة. وتصف أعداده هذا الصف فقط.

قيمة `trace_health.status` هي `unknown` عندما لا تكون للصف تتبّعات، وإلا فهي `no_errors_observed` أو `errors_observed`. و`error_rate_basis_points` هي نسبة التتبّعات التي فيها Span خطأ، من `0` إلى `10000`. وهي ليست معدل أخطاء لكل الطلبات.

يشير `next_action` إلى أول نوع إشارة له بيانات، بهذا الترتيب:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

راجع [الإصدارات](/ar/concepts/releases).

### <span id="trace-discovery-response">استجابة اكتشاف التتبّعات</span>

يعيد `GET /api/telemetry/traces?pagination=cursor` صفًا واحدًا لكل تتبّع، بالإضافة إلى إيصال `naming_quality` للصفحة المُعادة:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

يغطي `naming_quality` الصفحة المُعادة فقط. وهو ليس درجة على مستوى الحساب كله. `truncated: true` تعني أن هناك صفحة أخرى. عندما يكون في الصفحة اسم عام أو مسار غير مطابق أو عملية عامة، تكون قيمة `next_action` هي `improve_trace_naming` والهدف `sdk_configuration`. ودون `pagination=cursor`، يعيد المسار مصفوفة مجردة من التتبّعات دون `naming_quality`.

يحمل `next_cursor` الحقلين `time` و`trace_id`. أرسلهما في `cursor_time` و`cursor_trace_id`.

مع `response_version=2` يحمل كل تتبّع أيضًا `capture_span_count` و`capture_error_count`. عندها لا تحسب `span_count` و`error_span_count` [Spans الالتقاط](/ar/concepts/distributed-tracing#capture-spans). أما الإصدار 1 فيحسبها. ويطابق `status=error` التتبّع عندما تكون `error_span_count` أو `capture_error_count` أكبر من `0`.

يعيد `GET /api/telemetry/traces/{trace_id}` الـ Spans لتتبّع واحد. ويعيد `GET /api/telemetry/traces/{trace_id}/summary` الـ Span الجذري وSpans الأخطاء والخدمات والمدة وأبطأ مسار، دون سمات الـ Spans الخام. الاستجابة `404` للملخص تعني أنه لم يطابق أي تتبّع النطاق الكامل. لا تُعد المحاولة دون عوامل التصفية. راجع [استجابات Spans التتبّع وملخصه](#trace-spans-and-summary-responses).

### <span id="empty-lists-and-missing-records">القوائم الفارغة والقيود المفقودة</span>

قد لا تكون لقراءة القائمة نتائج مطابقة. أما قراءة التفاصيل فلها عقد مختلف:

| الطلب | النجاح | لا يوجد قيد يمكن قراءته |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` مع [سجل](#log-response) واحد | `404` مع `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` مع [مشكلة](#issue-response) واحدة | `404` مع `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` مع مرات الحدوث | `404` مع `code: not_found` في الصفحة الأولى |
| `GET /api/telemetry/traces/{trace_id}` | `200` مع الـ Spans | `200` مع `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` مع ملخص واحد | `404` مع `code: not_found` |

يعيد السجل المفقود هذه الاستجابة `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

تستخدم المشكلة المفقودة `"error": "issue not found"`. ويستخدم ملخص التتبّع المفقود `"error": "trace not found"`. المعرّف غير المعروف والمعرّف الذي لا يستطيع الحساب قراءته يعيدان الاستجابة نفسها.

القائمة التي فيها `project_id` واحد لا يستطيع الحساب قراءته تعيد `404` مع `"error": "project selection not found"`. ويعيد معرّف المشروع غير المعروف الاستجابة نفسها. راجع [تحديدات المشاريع المرفوضة](#rejected-project-selections).

### <span id="rejected-project-selections">تحديدات المشاريع المرفوضة</span>

تقبل قوائم السجلات والمشكلات والإجراءات والمقاييس والإصدارات والتتبّعات مشروعًا واحدًا عبر `project_id`، أو من 2 إلى 50 مشروعًا عبر `project_ids`. ويقبل فهرس سمات السجلات المُحدِّدات نفسها. أما تاريخ مرات حدوث المشكلة فلا يقبلها.

الطلب الذي فيه `project_id` و`project_ids` معًا يعيد `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

يعيد `project_ids` أيضًا `422` مع `code: validation_failed` عندما يحتوي على UUID غير صالح، أو معرّف مكرر، أو أقل من 2 أو أكثر من 50 معرّفًا.

إذا لم يستطع الحساب قراءة مشروع `project_id` أو مشروع واحد في مجموعة `project_ids`، يعيد الطلب كله `404`. ولا يعيد المشاريع الأخرى نتيجةً جزئية:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

اعرض الخطأ، لا قائمة فارغة ولا عددًا صفريًا. اقرأ قائمة المشاريع مرة أخرى. لا تحذف مشروعًا بصمت، ولا تُعد المحاولة عبر كل المشاريع. بيانات الاعتماد المفوَّضة، مثل اتصال MCP (grant)، تعيد `403` مع `code: forbidden` لمشروع خارج نطاق اتصالها. راجع [نطاق المشروع](/ar/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">أخطاء المؤشر</span>

تستخدم السجلات والمشكلات والإجراءات والمقاييس ومرات حدوث المشكلات `cursor_time` و`cursor_id`. يعيد المؤشر المرفوض `422` مع `code: validation_failed`. ولا تعني هذه الأخطاء أن القائمة فارغة.

| الطلب | `error` |
| --- | --- |
| `pagination=cursor` مع حقل واحد فقط من حقلي المؤشر | `cursor_time and cursor_id must be sent together` |
| `cursor_time` ليس طابعًا زمنيًا بتنسيق RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| حقول المؤشر دون `pagination=cursor`، أو بقيمة أخرى لـ `pagination` | `pagination must be cursor when cursor pagination is requested` |

مثلًا:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

انسخ `next_cursor` كاملًا من الصفحة السابقة. لا تضع الوقت الحالي مكان `cursor_time`. إذا فقدت المؤشر، فابدأ من جديد مع `pagination=cursor` وعوامل التصفية الأصلية. مفتاح الاستعلام غير المعروف أو القيمة من نوع خاطئ يعيدان `422` مع `"error": "invalid query parameters"`.

### <span id="release-cursor-responses">استجابات مؤشر الإصدارات</span>

لمؤشر الإصدارات 5 حقول. الطلب الناجح الذي ليس له نتائج مطابقة يعيد `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

عندما لا تكون قيمة `next_cursor` هي `null`، أرسل القيم الخمس كلها في الطلب التالي:

| حقل `next_cursor` | معامل الاستعلام |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

يحدد `cursor_project_id` موضعًا. ولا يحل محل `project_id` أو `project_ids`. أبقِ معاملات المشروع والتصفية الأصلية. رمّز كل قيمة لعنوان URL.

مع `pagination=cursor`، يعيد المؤشر الجزئي أو قيمة الإصدار أو البيئة أو الخدمة الفارغة `422` مع `"error": "all release cursor fields must be sent together"`. وتعيد قيمة `cursor_time` غير الصالحة وغياب `pagination=cursor` الأخطاء نفسها التي تعيدها [المؤشرات الأخرى](#cursor-errors).

### <span id="trace-discovery-errors">أخطاء اكتشاف التتبّعات</span>

تنطبق هذه الأخطاء على `GET /api/telemetry/traces`. يعيد كل منها `422` مع `code: validation_failed`. الطلب المرفوض ليس نتيجة فارغة.

| الطلب | `error` |
| --- | --- |
| `status` بقيمة غير `error` أو `ok` | `trace status must be error or ok` |
| `min_duration_ms` أقل من `0` | `minimum trace duration must not be negative` |
| حقل مؤشر واحد فقط، أو `cursor_trace_id` فارغ | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` ليس طابعًا زمنيًا بتنسيق RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| حقول المؤشر دون `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |
| `response_version` غير `1` و`2` | `trace response_version must be 1 or 2` |

لتضمين حالتي التتبّع كلتيهما، احذف `status`. للصفحة التالية، انسخ `next_cursor.time` إلى `cursor_time` و`next_cursor.trace_id` إلى `cursor_trace_id`. لا ترسل `cursor_id` لصفحة تتبّعات. راجع [عوامل تصفية التتبّعات](/ar/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">تاريخ مرات حدوث المشكلة</span>

يقرأ `GET /api/telemetry/issues/{issue_id}/events` مرات حدوث مشكلة مجمّعة واحدة. استخدم رمز Bearer للحساب ومعرّف المشكلة المجمّعة. يقبل المسار فقط `pagination` و`cursor_time` و`cursor_id` و`limit`. ولا يقبل عوامل التصفية حسب المشروع أو الوقت أو الإصدار أو البيئة أو الخطورة.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

صفحة أولى فيها حدوث واحد ومؤشر متابعة:

```json

      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {

          "type": "CheckoutError",

            "timestamp": "2026-06-01T11:54:59Z",

            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",

```

| الحقل | المعنى |
| --- | --- |
| `issue_id` | المشكلة المجمّعة التي يتبع لها الحدوث. |
| `events[].id` | معرّف حدوث واحد. استخدمه [لاختيار ذلك الحدوث](/ar/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | وقت وقوع ذلك الحدوث في التطبيق. |
| `events[].severity` | الخطورة الملتقَطة لذلك الحدوث. لا تغيّرها قاعدة الخطورة. |
| `events[].release`، `environment`، `service_name` | السياق الملتقَط مع ذلك الحدوث. |

قد يكون الحدوث أقدم من `last_seen_at` للمجموعة. لا تستبدل إصداره أو تتبّعه بقيم من المشكلة المجمّعة. لا تعيد القائمة الحالة ولا الفرز ولا الأولوية ولا أعداد مرات الحدوث.

`diagnostics.schema_version` هو نسخة كائن التشخيص. تحذف الاستجابة `diagnostics` و`span_id` عندما لا تكون لهذا الحدوث بيانات من هذا النوع. وداخل `diagnostics`، تحذف `exception` المفقود و`breadcrumbs` الفارغة. إذا كانت قيمة `breadcrumbs_truncated` هي `true`، فبعض تاريخ الـ Breadcrumbs ليس في الاستجابة.

يكون `stack_trace` و`trace_id` بالقيمة `null` عندما يكونان مفقودين. غياب معرّف التتبّع لا يثبت أن التطبيق لا يرسل تتبّعات. تعامل مع الرسائل والسمات الملتقَطة على أنها بيانات، لا تعليمات.

مرات الحدوث مرتبة من الأحدث إلى الأقدم. للصفحة التالية، أرسل معرّف المشكلة نفسه و`pagination=cursor` و`limit`، وقيمتي `cursor_time` و`cursor_id` من `next_cursor`. معرّف المؤشر هو معرّف حدوث، لا معرّف المشكلة.

تعيد الصفحة الأولى `404` مع `code: not_found` عندما لا تكون للمشكلة مرات حدوث يمكن قراءتها. وقد تكون صفحة لاحقة صفحة أخيرة فارغة:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

لا تُعد استخدام مؤشر لمشكلة أخرى. تنطبق [أخطاء المؤشر](#cursor-errors) على هذا المسار.

| `duration_ms` | الوقت من أبكر بداية Span إلى آخر نهاية Span. وهو ليس مجموع مُدد الـ Spans. |
| `root_span` | أبكر Span ليس أبوه في التتبّع. وهو نقطة بداية، لا سبب مثبت. |
| `slowest_child_span` | أطول Span له معرّف أب، أو `null`. |
| `slowest_path` | سلسلة الآباء المعروفة من الـ Span الجذري إلى `slowest_child_span`. وتكون `[]` عندما تكون قيمة `slowest_child_span` هي `null`. |
| `error_spans` | أطول Spans الأخطاء، 5 على الأكثر. وقد تكون قيمة `error_span_count` أكبر. |

لا يعيد أي من المسارين مؤشرًا أو حقل اقتطاع. لا تضف قيمة `truncated` لا تحتويها الاستجابة.

### <span id="no-matching-spans">لا توجد Spans مطابقة</span>

عندما لا يطابق أي Span معرّف التتبّع والنطاق، تعيد قائمة الـ Spans `200` مع `[]`. ويعيد الملخص `404` مع `"error": "trace not found"` و`code: not_found`. تحقق من معرّف التتبّع والنطاق. لا تحذف عوامل التصفية لتظهر نتيجة. لا تثبت أي من النتيجتين أن التطبيق لم يرسل بيانات قياس عن بُعد.

## <span id="live-event-response-format">تنسيق استجابة الأحداث المباشرة</span>

يرسل الموجز المباشر الأحداث الجديدة. ولا يعيد إرسال الأحداث التي فاتت العميل أثناء انقطاع الاتصال. استخدم مسارات القوائم لقراءة القيود الموجودة.

### <span id="create-a-ticket">أنشئ تذكرة</span>

أرسل `POST /api/feed/ticket` مع رمز Bearer للحساب. ليس للطلب نص.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

تحتوي الاستجابة `200 OK` على التذكرة في الحقل `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

التذكرة بيانات اعتماد قصيرة العمر. لا تكتبها في السجلات ولا تضعها في موجّه (prompt) وكيل. افتح الاتصال قبل انتهاء `expires_in_seconds`. تحدد مدة الصلاحية متى يمكن أن يبدأ الاتصال، لا المدة التي يبقى فيها مفتوحًا.

تبقى التذكرة صالحة 60 ثانية وتعمل مرة واحدة فقط. تفتح التذكرة الواحدة اتصالًا واحدًا. اطلب تذكرة جديدة لكل اتصال، بما في ذلك عند إعادة الاتصال.

الاستجابة `401` تعني أن تسجيل الدخول إلى الحساب غير صالح. سجّل الدخول مرة أخرى قبل أن تطلب تذكرة. والطلب بطريقة غير `POST` يعيد `405` مع `code: method_not_allowed`.

### <span id="open-the-connection">افتح الاتصال</span>

اربط عميل WebSocket بالعنوان `wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. رمّز التذكرة لعنوان URL. لا تضع رمز Bearer للحساب ولا رمز Bearer للاستيعاب في عنوان URL. الاستجابة `401` تعني أن التذكرة أو تسجيل الدخول إلى الحساب غير صالح. أنشئ تذكرة جديدة بعد أن تسجّل الدخول مرة أخرى.

يمكن أن يملك الحساب الواحد 10 اتصالات مفتوحة بالموجز المباشر كحد أقصى. ويمكن لعنوان IP واحد أن يملك 20 اتصالًا كحد أقصى. يتلقى أي اتصال يتجاوز أحد الحدين استجابة `429`.

| الاستجابة | السبب | الخطوة التالية |
| --- | --- | --- |
| `422` مع `"error": "feed ticket is required"` | قيمة الاستعلام `ticket` مفقودة أو فارغة. | أنشئ تذكرة واتصل بها. |
| `401` مع `code: unauthorized` | التذكرة منتهية الصلاحية أو سبق استخدامها أو غير صالحة. | أنشئ تذكرة جديدة. لا تُعد المحاولة بالتذكرة نفسها. |
| `429` مع `code: rate_limited` | لدى الحساب 10 اتصالات مفتوحة، أو لدى عنوان IP عشرون اتصالًا. | أغلق الاتصالات التي لا تستخدمها. انتظر `retry_after_seconds` أو `Retry-After` (`5` ثوانٍ). ثم اتصل بتذكرة جديدة. |
| `code: invalid_websocket_upgrade` | الطلب ليس ترقية WebSocket صالحة. | استخدم عميل WebSocket. |
| `405` مع `code: method_not_allowed` | الطلب لا يستخدم `GET`. | استخدم `GET` للاتصال. |

انتظر قبل أن تعيد الاتصال بعد خطأ. لا تُعد الاتصال في حلقة متقاربة.

### <span id="read-the-messages">اقرأ الرسائل</span>

كل رسالة غلاف بالشكل `{ "type": "...", "data": ... }`. اقرأ `type` قبل أن تحلّل `data`. تجاوز الأنواع التي لا يدعمها العميل.

| نوع الحدث | البيانات المحمولة |
| --- | --- |
| `native_log` | بيانات سجل، بشكل [استجابة السجل](#log-response). |
| `native_issue` | بيانات مشكلة مجمّعة، بشكل [استجابة المشكلة](#issue-response) في النسخة 1. |
| `native_trace_span` | Span واحد، بشكل عنصر [قائمة الـ Spans](#span-list). |
| `native_action` | بيانات إجراء منتج، بشكل [استجابة الإجراء](#action-response). |
| `project_created`، `project_updated`، `project_catalog_changed` | بيانات المشروع. اقرأ قائمة المشاريع مرة أخرى عندما تتغير. |
| `usage_updated`، `usage_limit_warning`، `usage_limit_blocked` | استخدام الحساب، بشكل [استخدام الحساب](/ar/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

يستخدم الحدث `native_issue` النسخة 1 من استجابة المشكلة: تظهر المشكلة المؤرشفة بالقيمة `ignored`، وليس للحدث أولوية. المقاييس والإصدارات ليست من أنواع الأحداث المباشرة. اقرأها بمسارات قوائمها. لا تختار التذكرة مشروعًا. تحقق من `project_id` لكل حدث قبل أن تعرضه في عرض مشروع. يستخدم `logbrew watch --json` هذا الموجز. راجع [مرجع CLI](/ar/reference/cli).

### <span id="handle-a-closed-connection">تعامل مع الاتصال المغلق</span>

| رمز الإغلاق | السبب | الخطوة التالية |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | انتظر، ثم أعد الاتصال بتذكرة جديدة. اقرأ مسارات القوائم مرة أخرى لتحصل على القيود التي فاتتك. |
| `1008` | `live feed access changed; sign in again` | أوقف إعادة الاتصال. سجّل الدخول مرة أخرى قبل أن تنشئ تذكرة جديدة. |

قد لا يكون لحالات الانقطاع الأخرى سبب من LogBrew. بعد أن تعيد الاتصال، اقرأ مسارات القوائم مرة أخرى وطابق القيود حسب المعرّف.

## <span id="issue-status-response-examples">أمثلة استجابات حالة المشكلة</span>

يعيد `PATCH /api/telemetry/issues/{issue_id}` مع `{ "status": "resolved" }` الاستجابة `200 OK` مع المشكلة المجمّعة المحدَّثة، بشكل [استجابة المشكلة](#issue-response) نفسه. يختار مفتاح الاستعلام `response_version` النسخة. ولا يعيد المسار علامة نجاح.

يضبط النص حقلًا واحدًا أو أكثر من `status` و`priority` و`assignee`. يقبل `status` القيم `unresolved` أو `resolved` أو `archived`. و`ignored` اسم أقدم لـ `archived`. راجع [حدّث مشكلة واحدة](/ar/reference/telemetry-api#update-one-issue).

تحقق من `id` و`status` و`priority` في الاستجابة قبل أن تعرض النجاح. لا تبنِ النتيجة من القيم المرسلة. تغيير الحالة لا يحذف مرات الحدوث، ولا يغيّر `first_seen_at` و`last_seen_at`. ولا يغيّر `severity` أو قاعدة الخطورة.

يعيد التغيير المرفوض `422` مع `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| النتيجة | السبب |
| --- | --- |
| `422`، `issue update requires status, priority, or assignee` | ليس في النص أي من الحقول الثلاثة. |
| `422`، `issue priority must be high, medium, or low` | قيمة الأولوية غير مدعومة. |
| `422`، `issue assignee must be me, none, a user ID, or team:<team_id>` | قيمة المسؤول غير مدعومة. |
| `422`، `issue assignee cannot read this project` | ليس للمسؤول صلاحية وصول إلى المشروع. لا يغيّر LogBrew شيئًا. |
| `422`، `issue assignee team is not a team of this project's organization` | الفريق لا يتبع مؤسسة المشروع. لا يغيّر LogBrew شيئًا. |
| `403` مع `code: forbidden` | لا يستطيع الحساب إدارة المشكلات في المشروع. |
| `404` مع `code: not_found` | لا يستطيع الحساب قراءة المشكلة، أو المشكلة غير موجودة. |

الحقل الذي له القيمة المطلوبة بالفعل لا يتغير. بعد انتهاء المهلة أو ضياع الاستجابة، أرسل الطلب نفسه مرة أخرى، أو اقرأ المشكلة أولًا. لا ترسل تغييرًا مختلفًا قبل أن تقرأ الحالة الحالية. راجع [عمليات الكتابة](/ar/reference/api-errors#writes).

يعيد `POST /api/telemetry/issues/bulk` الاستجابة `200 OK` مع نتيجة واحدة لكل معرّف مشكلة مطلوب، بترتيب الطلب. تستخدم كل مشكلة موجودة شكل النسخة 3. أضف `"response_version": 2` إلى النص لتحصل على كل مشكلة بشكل النسخة 4. ولنتيجة `not_found` القيمة `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

يعرض هذا المثال بعض حقول المشكلة فقط. قيمة `outcome` هي `updated` أو `unchanged` أو `not_found`. الطلب المكرر يعيد `unchanged` ولا يغيّر شيئًا. راجع [حدّث المشكلات دفعة واحدة](/ar/reference/telemetry-api#update-issues-in-bulk).

يفشل الطلب الجماعي كله في هذه الحالات:

| النتيجة | السبب |
| --- | --- |
| `422`، `issue_ids must name 1 to 100 issues` | القائمة فارغة أو فيها أكثر من 100 معرّف. |
| `422`، `issue_ids must not contain duplicates` | يتكرر معرّف أكثر من مرة. |
| `422` مع `code: invalid_json` | في النص حقل غير معروف. |
| `403` مع `code: forbidden` | لا يستطيع الحساب إدارة المشكلات في المشروع. |
| `404`، `project not found` | لا يستطيع الحساب قراءة المشروع. |

## <span id="analytics-request-scope">نطاق طلبات التحليلات</span>

تقرأ مسارات التحليلات ومسار سلسلة المقياس ومسار حجم الإشارات مشروعًا واحدًا ونطاقًا زمنيًا واحدًا. يحتاج كل طلب إلى `project_id` و`since`. يقبل `since` مدة مختصرة مثل `24h` أو `7d`، أو طابعًا زمنيًا بتنسيق RFC3339. ويقبل `until` طابعًا زمنيًا بتنسيق RFC3339، وقيمته الافتراضية وقت الطلب. يشمل النطاق `since` ولا يشمل `until`، ولا يمكن أن يزيد على 31 يومًا.

`service_name` و`release` و`environment` عوامل تصفية اختيارية بالمطابقة التامة. يجب أن تكون كل قيمة من 1 إلى 256 حرفًا بعد أن يزيل LogBrew المسافات من طرفيها. يضع مسار مقارنة الشرائح عوامل التصفية هذه داخل كل شريحة، لا في المستوى الأعلى.

إذا لم يستطع الحساب قراءة المشروع، تعيد هذه المسارات `200 OK` مع أعداد صفرية. ولا تعيد `404`. النتيجة الفارغة لا تؤكد صلاحية الوصول إلى المشروع. قارن `project_id` بالمشاريع التي يستطيع الحساب قراءتها. والطلب عبر اتصال MCP (grant) لا يشمل المشروع يعيد `403` و`forbidden`.

| المسار | قيم `response_version` | القيمة الافتراضية |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1` أو `2` أو `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` أو `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` أو `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` أو `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` أو `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | غير مقبول | المخطط `1` |
| `POST /api/telemetry/analytics/paths` | غير مقبول | المخطط `1` |
| `GET /api/telemetry/metrics/series` | غير مقبول | المخطط `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

تبدأ كل استجابة بالحقول `schema_version` و`query` و`purpose`. يعيد `query` النطاق الفعلي. ويحذف أي عامل تصفية لم ترسله. و`purpose` نص عادي يشرح السؤال الذي يجيب عنه المسار.

يُحذف المعدّل عندما يكون مقامه صفرًا. المعدّل المحذوف ليس `0` وليس `null`. اقرأ `coverage` قبل أن تثق بمعدّل.

### <span id="shared-scope-errors">أخطاء النطاق المشتركة</span>

تستخدم هذه الأخطاء HTTP `422` و`validation_failed`:

| السبب | `error` |
| --- | --- |
| لا يوجد `project_id` | `product analytics project_id is required` |
| لا يوجد `since` | `product analytics since is required` |
| `since` ليس مدة ولا طابعًا زمنيًا بتنسيق RFC3339 | `invalid since value` |
| `until` ليس طابعًا زمنيًا بتنسيق RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` ليس أبكر من `until` | `product analytics since must be earlier than until` |
| النطاق أطول من 31 يومًا | `product analytics range must not exceed 31 days` |
| عامل تصفية فارغ، أو عامل تصفية أطول من 256 حرفًا | `product analytics context filters must be non-empty and at most 256 characters` |

مثلًا، الطلب الذي ليس فيه `project_id` يعيد:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

يستخدم مسارا سلسلة المقياس وحجم الإشارات قواعد النطاق نفسها، مع نص `error` خاص بكل منهما. تسرد أقسامهما أدناه تلك الأخطاء.

يعيد مفتاح الاستعلام غير المعروف `422` مع استجابة [معاملات الاستعلام غير الصالحة](/ar/reference/api-errors#invalid-query-parameters). ويعيد حقل JSON غير المعروف، أو حقل JSON المطلوب المفقود، أو قيمة التعداد غير المدعومة `invalid_json`. راجع [JSON غير صالح](/ar/reference/api-errors#invalid-json). والطلب بطريقة HTTP خاطئة يعيد `405` و`method_not_allowed`. ويسمّي نص `next` فيه الطريقة والحقول المدعومة. راجع [طريقة غير مدعومة](/ar/reference/api-errors#unsupported-method).

## <span id="product-analytics-overview-response">استجابة النظرة العامة لتحليلات المنتج</span>

يعرض `GET /api/telemetry/analytics/overview` النشاط في مشروع واحد: حجم الإجراءات، والمستخدمين، والجلسات، وسلسلة زمنية، وأبرز الإجراءات، ومشاهدات الصفحات ومشاهدات الشاشات والتفاعلات المصنَّفة. استخدمه لتجد أسماء الأحداث الدقيقة لمسارات التحليلات الأخرى.

أرسل `response_version=3`. تعيد النسختان 1 و2 الأعداد نفسها، لكن قيمة `estimation.method` فيهما رمز أقدم. لا تتحقق النسخة 1 من نوع الكيان عندما تعدّ المستخدمين معروفي الهوية. وتعدّ النسختان 2 و3 فقط الكيانات من النوع `user`، وتضيفان أعداد الكيانات مجهولة الهوية و`subject_coverage`.

يقرأ هذا الطلب ساعة واحدة في فواصل زمنية مدة كل منها خمس دقائق، ويعيد صفين في كل قائمة من القوائم الأبرز:

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/overview" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T11:00:00Z" \
  --data-urlencode "until=2026-06-01T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "top_limit=2" \
  --data-urlencode "response_version=3"
```

### <span id="overview-success">نجاح النظرة العامة</span>

في هذه النتيجة المصطنعة، للمشروع 120 إجراءً في فاصلين زمنيين من الفواصل الاثني عشر. يأتي عشرون إجراءً من كيانات مجهولة الهوية. لكل إجراء معرّف جلسة. ولنصف الإجراءات معرّف تتبّع.

```json
{
  "schema_version": 3,
  "query": {
    "project_id": "11111111-1111-4111-8111-111111111111",
    "since": "2026-06-01T11:00:00Z",
    "until": "2026-06-01T12:00:00Z",
    "interval": "5m",
    "interval_seconds": 300,
```

### <span id="read-the-overview">اقرأ النظرة العامة</span>

مجموع أعداد `subject_coverage` الخمسة يساوي إجمالي الأحداث في قسمها. وحده `identified_user_events` يُحسب ضمن المستخدمين. و`anonymous_actions` يساوي `summary.actions` ناقص `identified_actions`.

يحتوي `series` فقط على الفواصل الزمنية التي فيها نشاط. و`expected_buckets` هو عدد الفواصل الزمنية الممكنة في النطاق. لا ترسم الفاصل الزمني المفقود صفرًا مقيسًا إلا إذا ذكر مخططك هذه القاعدة. تتوافق الفواصل الزمنية مع حدود الفواصل بتوقيت UTC. والنطاق الذي يبدأ داخل فاصل زمني يشمل ذلك الفاصل الجزئي.

يعدّ `classified_activity` مشاهدات الصفحات ومشاهدات الشاشات والتفاعلات. مشاهدات الشاشات والتفاعلات إجراءات أيضًا. أما مشاهدات الصفحات فليست إجراءات. لا تجمع `summary.actions` مع `classified_activity.summary.events`.

انسخ `kind` و`event_name` من `classified_activity.top_events` إلى خطوات قمع التحويل، ومُحدِّدات الاحتفاظ بالمستخدمين، ومُحدِّدات دورة الحياة، والأحداث المرجعية للمسارات، وأهداف الشرائح. القيمة `true` في `top_events_truncated` تعني وجود أسماء أقل حجمًا. زِد `top_limit` حتى 20 لترى المزيد.

قيمة `analysis_level` هي `no_data` أو `event_only` أو `user_level` أو `user_and_session`. إذا لم تكن للمشروع إجراءات ولا أحداث مصنَّفة، فقيمة `next_action.code` هي `capture_product_activity`. راجع [تحليلات المنتج](/ar/concepts/product-analytics#use-the-analytics-api).

### <span id="overview-errors">أخطاء النظرة العامة</span>

بالإضافة إلى [أخطاء النطاق المشتركة](#shared-scope-errors)، تعيد النظرة العامة `422` و`validation_failed` لهذه القيم:

| القيمة | `error` |
| --- | --- |
| `response_version` بقيمة غير `1` أو `2` أو `3` | `product analytics response_version must be 1, 2, or 3` |
| `top_limit` خارج النطاق من `1` إلى `20` | `product analytics top_limit must be between 1 and 20` |
| `interval` بقيمة غير `auto` أو `1m` أو `5m` أو `15m` أو `1h` أو `6h` أو `1d` | `product analytics interval is not supported` |
| `interval` صريح يحتاج إلى أكثر من 500 فاصل زمني | `product analytics interval would exceed 500 buckets` |

القيمة الافتراضية لـ `interval` هي `auto`. وهي تختار أصغر فاصل زمني يحتاج إلى 300 فاصل على الأكثر. والقيمة الافتراضية لـ `top_limit` هي `10`.

### <span id="read-conversion-and-coverage">اقرأ التحويل والتغطية</span>

`entry_rate` يساوي `entered_units` مقسومًا على `candidate_units`: 50 من 60. و`overall_conversion_rate` يساوي `completed_units` مقسومًا على `entered_units`: 15 من 50، أي 30%. وهو ليس 15 مقسومًا على كل الوحدات المرشّحة. لا توضح هذه الأعداد سبب توقف الوحدات.

تعدّ التغطية الأحداث، لا الجلسات. هنا يطابق 120 حدثًا خطوةً ما، و20 منها ليس لها معرّف جلسة. تستبعد النتيجة هذه الأحداث العشرين من أعداد الجلسات. لا تتعامل معها على أنها 20 جلسة فاشلة.

ليس للخطوة الأولى `conversion_from_previous`. وليس للخطوة الأخيرة `drop_off_to_next_units` ولا `drop_off_to_next_rate`.

تصل الوحدة إلى خطوة لاحقة فقط عندما تتزايد أوقات الخطوات تزايدًا صارمًا. لا يمكن للأحداث ذات الطابع الزمني نفسه أن تحقق خطوتين متتاليتين. ويجب أن تقع الخطوة الأخيرة خلال `conversion_window_seconds` من الخطوة الأولى.

وضع الجلسات يعدّ الجلسات، لا الأشخاص. استخدم `identified_user` فقط للأحداث التي تحمل معرّف كيان مبهمًا من النوع `user`. يمكن لهذا الوضع أن يربط أحداثًا من جلسات مختلفة داخل فترة التحويل. أبقِ الوحدة نفسها والخطوات نفسها عندما تقارن النتائج.

القيمة الافتراضية لـ `conversion_window_seconds` هي 24 ساعة أو طول النطاق، أيهما أقصر. والحد الأقصى هو طول النطاق بالثواني الكاملة، مقرَّبًا إلى الأعلى.

### <span id="empty-funnel-results">نتائج قمع التحويل الفارغة</span>

الاستجابة الفارغة الناجحة تسرد مع ذلك الخطوات المطلوبة مع `units` صفرية. إذا لم تكن هناك وحدات مرشّحة، يحذف `summary` الحقلين `entry_rate` و`overall_conversion_rate`. لا يعيد المسار `404` لأن أي حدث لم يطابق.

اقرأ `coverage` و`next_action` لتجد السبب:

| `next_action.code` | السبب |
| --- | --- |
| `capture_product_activity` | لا توجد أحداث مصنَّفة في النطاق. |
| `choose_captured_funnel_steps` | لا يطابق أي حدث خطوة مطلوبة. |
| `sessionize_product_activity` | توجد أحداث للخطوات، لكن ليس لأي منها معرّف جلسة. |
| `identify_product_users` | توجد أحداث للخطوات، لكن ليس لأي منها كيان من النوع `user`. |
| `verify_funnel_entry` | لم تدخل أي وحدة عند الخطوة 1. |
| `investigate_funnel_drop_off` | دخلت وحدات، لكن لم تكمل أي وحدة كل الخطوات. |
| `compare_funnel_contexts` | أكملت وحدة واحدة على الأقل قمع التحويل. |

### <span id="rejected-funnel-requests">طلبات قمع التحويل المرفوضة</span>

بالإضافة إلى [أخطاء النطاق المشتركة](#shared-scope-errors)، تعيد هذه الطلبات `422` و`validation_failed`. أقل من خطوتين أو أكثر من 8 خطوات:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

قيمة `conversion_window_seconds` تساوي `0`، أو قيمة أكبر من طول النطاق:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

قيمة `event_name` الفارغة، أو الأطول من 256 حرفًا، أو التي تحتوي على حرف تحكم تعيد `product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`. ويجب أن تكون خطوة `interaction` أيضًا اسم إجراء صالحًا. وإلا فالخطأ هو `product analytics interaction event_name must be a bounded stable action name`.

صحّح الطلب قبل أن ترسله مرة أخرى. لا تحذف خطوات ولا تغيّر وحدة التحليل لمجرد أن تحصل على نتيجة غير فارغة.

## <span id="exact-event-and-automatic-analysis">التحليل بأحداث محددة والتحليل التلقائي</span>

يقبل الاحتفاظ بالمستخدمين ودورة الحياة شكلين للطلب. استخدم `response_version` لتختار الشكل الذي يجيب عن سؤالك:

| التحليل | `response_version` | مُحدِّدات الأحداث |
| --- | --- | --- |
| الاحتفاظ بالمستخدمين لأحداث محددة | `1`، أو محذوف | أرسل `start_event` و`return_event` كليهما. |
| دورة الحياة لحدث محدد واحد | `1`، أو محذوف | أرسل `event`. |
| الاحتفاظ بالمستخدمين أو دورة الحياة تلقائيًا | `2` | لا ترسل أي مُحدِّد أحداث. |

يحتوي المُحدِّد الدقيق على `kind` و`event_name`. قيمة `kind` هي `page_view` أو `screen_view` أو `interaction`. انسخ `event_name` من `classified_activity.top_events`. لا تخمّن اسم الحدث من نص زر.

يعدّ الشكلان كلاهما المستخدمين فقط: معرّفات الكيانات المبهمة من النوع `user`. لا تُحسب الكيانات مجهولة الهوية ولا الأحداث التي ليس لها معرّف كيان صالح للاستخدام مستخدمين. لا تعيد الاستجابات معرّفات الكيانات أبدًا.

الفواصل الزمنية الثابتة هي `hour` و`day` و`week` و`thirty_day`. وهي مُدد ثابتة. `thirty_day` تعني 30 يومًا، لا شهرًا تقويميًا. إذا حذفت `interval`، يستخدم API القيمة `hour` للنطاق الذي مدته 48 ساعة أو أقل، و`day` للنطاق الأطول.

### <span id="exact-event-retention-request">طلب الاحتفاظ بالمستخدمين لأحداث محددة</span>

أرسل هذا النص إلى `POST /api/telemetry/analytics/retention`. وهو يسأل هل يكمل المستخدمون عملية إتمام شراء أخرى بعد أول عملية إتمام شراء لهم في النطاق:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T00:00:00Z",
  "until": "2026-06-03T00:00:00Z",
  "response_version": 1,
  "interval": "day",
  "interval_count": 1,
  "mode": "return_on",
  "cohort_mode": "first_in_range",
  "start_event": { "kind": "interaction", "event_name": "checkout_completed" },
  "return_event": { "kind": "interaction", "event_name": "checkout_completed" }
}
```

أول حدث بداية مطابق في النطاق هو نقطة البداية لكل مستخدم. يجب أن تقع العودة بعد نقطة البداية هذه تمامًا وقبل `until`. ويمكن أن يكون المُحدِّدان الحدث نفسه.

| الحقل | القيم | القيمة الافتراضية |
| --- | --- | --- |
| `interval_count` | من `1` إلى `31` فترة | `10` |
| `mode` | `return_on` يعدّ العودة داخل كل فترة بعينها. و`return_on_or_after` يعدّ العودة عند بداية كل فترة أو بعدها. | `return_on` |

### <span id="read-retention">اقرأ الاحتفاظ بالمستخدمين</span>

تعدّ التغطية الأحداث المصنَّفة الأربعة كلها، لكن ثلاثة منها فقط تطابق كل مُحدِّد لإتمام الشراء. مشاهدة الصفحة لا تُحسب عودة. يكرر أحد المستخدمَين إتمام الشراء، لذلك قيمة `return_rate_after_start` هي `0.5`.

### <span id="read-lifecycle">اقرأ دورة الحياة</span>

لا تجمع الأعداد اليومية للنشطين لتحصل على المستخدمين الفريدين. هنا مجموع الأعداد اليومية 5، لكن قيمة `analysis_active_subjects` هي 3. يظهر أربعة مستخدمين فريدين عبر التاريخ المرصود والتحليل.

| --- | --- |
| النسخة 1 دون `event`، أو النسخة 2 مع `event`، أو نسخة أخرى | `product analytics lifecycle activity selection is contradictory` |
| `history_period_count` خارج النطاق من `2` إلى `31` | `product analytics lifecycle history_period_count must be between 2 and 31` |
| فترات التاريخ المرصود أطول من 62 يومًا إجمالًا | `product analytics lifecycle history must not exceed 62 days` |
| أكثر من 100 فاصل زمني للتحليل | `product analytics lifecycle interval would exceed 100 analysis buckets` |

مثلًا، عشر فترات `week` للتاريخ المرصود تحتاج إلى 70 يومًا:

```json
{
  "error": "product analytics lifecycle history must not exceed 62 days",
  "code": "validation_failed",
  "next": "use fewer history periods or a narrower fixed interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

### <span id="read-the-selected-analysis-scope">اقرأ نطاق التحليل المختار</span>

لاستجابات الأحداث المحددة `schema_version: 1`. ويعيد `query` فيها المُحدِّدات ويحذف `activity_scope`. أما الاستجابات التلقائية فلها `schema_version: 2` و`query.activity_scope: "all_classified_activity"`. وتحذف المُحدِّدات. قد يغيّر مُحدِّد مختلف النتيجة دون أي تغيير في النشاط الملتقَط.

### <span id="read-a-metric-series">اقرأ سلسلة المقياس</span>

تسجّل النقطة الأولى 10 مهام مكتملة، لا 10 عيّنات. يقسم `rate_per_second` هذا التغير على الفاصل الزمني الذي مدته 300 ثانية. و`last` هو آخر تغير مُدوَّن، لا المجموع. راجع [معاني تجميع المقاييس](/ar/concepts/telemetry#read-the-metric-value).

يحدد نوع السلسلة وطبيعتها الزمنية (temporality) قيمة `aggregation.code` والإحصاءات في كل نقطة. تحذف النقطة الإحصاء الذي لا ينطبق. الإحصاء المفقود ليس صفرًا.

| النوع والطبيعة الزمنية | `status` | `aggregation.code` | `value` | إحصاءات أخرى |
| --- | --- | --- | --- | --- |
| `gauge`، `instant` | `ready` | `gauge_last` | آخر عيّنة | `last`، `min`، `max`، `average` |
| `counter`، `delta` | `ready` | `delta_sum` | مجموع التغيرات | `last`، `min`، `max`، `average`، `sum`، `rate_per_second` |
| `histogram`، `delta` | `ready` | `distribution_p95` | قيمة p95 تقريبية | `min`، `max`، `average`، `sum`، `p50`، `p95`، `p99` |
| أي نوع، `cumulative` | `limited` | `raw_cumulative_last` | آخر عيّنة خام | `last`، `min`، `max` |
| أي زوج آخر | `limited` | `raw_last` | آخر عيّنة خام | `last`، `min`، `max` |

`limited` استجابة ناجحة، لا خطأ. وهي تضيف `aggregation.limitation` الذي يشرح سبب عرض LogBrew للقيم الخام فقط. و`ready` لا تثبت أن الالتقاط كامل.

اقرأ `coverage` قبل أن ترسم مخططًا:

- يعدّ `samples` عيّنات كل السلاسل المطابقة، ومنها السلاسل التي لا تعيدها الاستجابة.
- يعدّ `series` السلاسل المطابقة. ويعدّ `returned_series` و`points` البيانات المُعادة.
- تكون قيمة `truncated` هي `true` عندما يحذف `series_limit` السلاسل الأقل حجمًا.
- `expected_buckets_per_series` هو عدد الفواصل الزمنية الممكنة في النطاق.

لا تضف نقطة لفاصل زمني ليس فيه عيّنات. لا تُدرج صفرًا ولا تنسخ القيمة السابقة. تعيد كل نقطة حتى 3 قيم في `trace_exemplars`. تربط العيّنة النموذجية للتتبّع (trace exemplar) عيّنة واحدة بتتبّع. ولا تشرح كل عيّنة في الفاصل الزمني. إذا لم تكن لأي نقطة عيّنة نموذجية للتتبّع، فقيمة `next_action.target` هي `metric_samples`.

### <span id="metric-series-scope-and-errors">نطاق سلسلة المقياس وأخطاؤها</span>

`project_id` و`name` و`since` مطلوبة. يمكن أن يحتوي `name` على 200 حرف على الأكثر. قيمة `interval` هي `auto` أو `1m` أو `5m` أو `15m` أو `1h` أو `6h` أو `1d`. القيمة الافتراضية `auto`، وهي تختار أصغر فاصل زمني يحتاج إلى 300 فاصل على الأكثر. ولا يمكن أن يحتاج الفاصل الصريح إلى أكثر من 500 فاصل.

قيمة `group_by` هي `none` أو `service_name` أو `release` أو `environment`. القيمة الافتراضية `none`. دون تجميع، تبقى الأنواع والوحدات والطبائع الزمنية المختلفة في سلاسل منفصلة. يقبل `series_limit` من `1` إلى `20`. القيمة الافتراضية `10`.

النتيجة الفارغة تعيد `200` مع `series: []` و`samples` صفرية. ويحذف الكائن `coverage` الحقلين `first_seen_at` و`last_seen_at`. وهذا لا يثبت أن التطبيق لم يرسل المقياس قط. تحقق من المشروع واسم المقياس والنطاق الزمني.

حذف `name` يعيد `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

الفواصل الزمنية التي مدتها دقيقة واحدة عبر سبعة أيام تعيد `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

أخطاء `422` الأخرى هي `metric series group_by is not supported` و`metric series interval is not supported` و`metric series_limit must be between 1 and 20`.

### <span id="read-paths">اقرأ المسارات</span>

يقسم `share_of_anchored_sessions` جلسات المسار على الجلسات الأربع كلها التي فيها الحدث المرجعي. النسبتان 50% و25%، لا 67% و33%. يعدّ `unrepresented_sessions` الجلسات التي فيها الحدث المرجعي ولا يمثّلها أي مسار مُعاد. و`paths_truncated: true` تعني أن النتيجة غير مكتملة.

تعدّ التغطية الأحداث، لا الجلسات. هنا تطابق خمسة أحداث الحدث المرجعي، لكن أحدها ليس له معرّف جلسة. لا يمكن لهذا الحدث أن يدخل في مسار. يعيد كل مسار حتى 3 عيّنات نموذجية للتتبّع. استخدم معرّف تتبّع من استجابتك أنت. رابط التتبّع لا يبيّن سبب إجراء المستخدم أو سبب الفشل.

| الحقل | المعنى |
| --- | --- |
| `following` | يبدأ عند أبكر حدث مرجعي مطابق في كل جلسة. موضع الحدث المرجعي `0`. وللعقد اللاحقة مواضع موجبة. |
| `preceding` | ينتهي عند آخر حدث مرجعي مطابق في كل جلسة. للعقد السابقة مواضع سالبة. وموضع الحدث المرجعي `0`. |
| `depth` | عدد العقد المجاورة للحدث المرجعي، دون احتساب الحدث المرجعي. من `1` إلى `8`. القيمة الافتراضية `4`. قد يكون للمسار عقد أقل. |
| `collapse_repeated` | يدمج العقد المتتالية التي لها النوع والاسم نفسيهما. القيمة الافتراضية `true`. |
| `path_limit` | الحد الأقصى للمسارات المُعادة، مرتبة حسب عدد الجلسات. من `1` إلى `20`. القيمة الافتراضية `10`. |

العقد مرتبة زمنيًا في الاتجاهين كليهما. المسار ليس إعادة تشغيل كاملة للجلسة. يقرأ LogBrew 1024 حدثًا مسمى على الأكثر لكل جلسة قبل أن يختار الحدث المرجعي: أبكر الأحداث لـ `following`، وأحدث الأحداث لـ `preceding`. وقد يُحذف الحدث المرجعي الذي يقع خارج هذا الحد.

### <span id="filter-the-anchor-by-property">صفِّ الحدث المرجعي حسب خاصية</span>

أرسل حتى أربعة عناصر في `property_filters`، لكل منها `key` و`value` محددان تمامًا. انسخ المفتاح من [فهرس الخصائص](#analytics-property-catalog). تنطبق عوامل التصفية على الحدث المرجعي فقط، لا على الأحداث المحيطة به. القيم حساسة لحالة الأحرف. عندما توجد عوامل تصفية، يعيدها `query`، ويبلّغ `coverage.anchor_property_filters` بما يلي:

| الحقل | المعنى |
| --- | --- |
| `context_events` | الأحداث المرجعية في النطاق قبل عوامل تصفية الخصائص. |
| `property_ready_events` | الأحداث المرجعية التي فيها كل مفتاح مطلوب. |
| `missing_property_events` | الأحداث المرجعية التي ينقصها مفتاح مطلوب واحد أو أكثر. |
| `matching_events` | الأحداث المرجعية التي تطابق قيمها كل عامل تصفية. |
| `nonmatching_value_events` | الأحداث المرجعية التي فيها كل مفتاح لكن بقيمة مختلفة. |
| `property_ready_rate` | `property_ready_events` مقسومًا على `context_events`. |
| `match_rate` | `matching_events` مقسومًا على `property_ready_events`. |

المفاتيح المفقودة والقيم المختلفة تحتاج إلى إصلاحات مختلفة. لا تجمعها معًا. يُحذف الكائن عندما لا يكون في الطلب عامل تصفية للخصائص.

### <span id="empty-paths-and-rejected-requests">المسارات الفارغة والطلبات المرفوضة</span>

قد تكون مصفوفة `paths` الفارغة استجابة `200` ناجحة. اقرأ `summary` و`coverage` و`next_action`. تميّز هذه الرموز بين الأسباب: `capture_product_activity` و`choose_captured_path_anchor` و`capture_anchor_properties` و`improve_anchor_property_coverage` و`verify_anchor_property_values` و`sessionize_product_activity` و`narrow_or_move_path_anchor`.

بالإضافة إلى [أخطاء النطاق المشتركة](#shared-scope-errors)، تعيد هذه الطلبات `422` و`validation_failed`:

| السبب | `error` |
| --- | --- |
| `depth` خارج النطاق من `1` إلى `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` خارج النطاق من `1` إلى `20` | `product analytics path_limit must be between 1 and 20` |
| أكثر من أربعة عوامل تصفية للخصائص | `product analytics paths accept at most four exact anchor property filters` |
| مفتاح ليس في فهرس الخصائص | `product analytics path property keys must be supported privacy-safe keys` |
| المفتاح نفسه مرتين | `product analytics path property keys must be unique` |
| قيمة فارغة، أو قيمة أطول من 256 حرفًا، أو حرف تحكم | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

مثلًا، `depth: 0` يعيد:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">فهرس خصائص التحليلات</span>

يسرد `GET /api/telemetry/analytics/properties` مفاتيح الخصائص في أحداث المنتج المصنَّفة في مشروع واحد. استخدم المفاتيح في [مقارنات الشرائح](#analytics-segment-comparison) وفي عوامل تصفية الحدث المرجعي للمسارات. يعيد الفهرس المفاتيح والأعداد. ولا يعيد قيم الخصائص أو الهويات أبدًا.

### <span id="read-available-property-keys">اقرأ مفاتيح الخصائص المتاحة</span>

أرسل `project_id` و`since`. يمكنك أيضًا إرسال `until` و`service_name` و`release` و`environment` و`limit` و`response_version`. يقبل `limit` من `1` إلى `50` مفتاحًا. القيمة الافتراضية `20`. أرسل `response_version=2` لتحصل على قيمة `estimation.method` العامة.

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/properties" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T00:00:00Z" \
  --data-urlencode "until=2026-06-02T00:00:00Z" \
  --data-urlencode "limit=20" \
  --data-urlencode "response_version=2"
```

### <span id="interpret-the-catalog">فسّر الفهرس</span>

قيمة `source` هي `standard_context` لمفتاح سياق قياسي، مثل `resource.runtime.name`، أو `custom_tag` لمفتاح يبدأ بـ `tag.`. وقيمة `value_type` هي دائمًا `string`. و`properties` مرتبة حسب `events`، من الأعلى إلى الأدنى.

| --- | --- |
| `summary.classified_events` | الأحداث المصنَّفة في النطاق. وهذا هو المقام لكل `coverage_rate`. |
| `summary.available_property_keys` | العدد التقديري للمفاتيح المختلفة، لا عدد الصفوف المُعادة. |
| `coverage.unindexed_events` | الأحداث الملتقَطة قبل فهرس الخصائص الحالي. لا يمكنها أن تضيف مفاتيح. |
| `coverage.incomplete_index_events` | الأحداث التي فيها بعض السياق المشوَّه أو المقتطَع. وتبقى مفاتيحها الصالحة محسوبة. |
| `coverage.privacy_filtered_events` | الأحداث التي أزال LogBrew منها مفاتيح وسوم مخصصة حساسة. وهذا ليس عددًا للمفاتيح. |

| `coverage.values_returned` | دائمًا `false`. |

مصفوفة `properties` الفارغة لا تثبت أن المشروع ليس فيه أحداث منتج. اقرأ `summary` و`coverage` و`next_action`.

تحتاج كل شريحة إلى `key` فريد و`label` ومجموعة عوامل تصفية مختلفة:

- `key`: من 1 إلى 32 بايت. ابدأ بحرف ASCII صغير أو رقم. استخدم فقط أحرف ASCII الصغيرة والأرقام و`_` و`-`.

الشريحة التي ليس فيها عوامل تصفية تختار كل النشاط المصنَّف في المشروع والنطاق الزمني. يمكن أن تتداخل الشرائح. اختلاف الاسم أو المفتاح لا يجعل مجموعتي عوامل تصفية متطابقتين صالحتين.

## <span id="signal-volume-response">استجابة حجم الإشارات</span>

يعدّ `GET /api/telemetry/summary/volume` الإشارات المحتفَظ بها لمشروع واحد ونطاق زمني واحد. ويتطلب `project_id` و`since`. ولا يقبل `project_ids`.

لعدّ من 1 إلى 50 مشروعًا معًا، أرسل `project_ids` و`since` إلى `GET /api/telemetry/summary/volume/combined`. للاستجابة الشكل نفسه. ويحتوي `query` فيها على `project_ids` بدل `project_id`. ويُحسب التتبّع الذي له Spans في عدة مشاريع محددة مرة واحدة. وإذا لم يستطع الحساب قراءة أحد المشاريع، يعيد هذا المسار `404` مع `"error": "project selection not found"`.

### <span id="read-each-count-in-its-own-unit">اقرأ كل عدد بوحدته</span>

| الإشارة | ما يعدّه `total` | لا تقرأه على أنه |
| --- | --- | --- |
| `issues` | مرات حدوث المشكلات المحتفَظ بها | مشكلات مجمّعة أو مستخدمون متأثرون |
| `logs` | أحداث السجلات المحتفَظ بها | طلبات |
| `traces` | معرّفات التتبّع الفريدة، محسوبة عند أول Span محتفَظ به لها في هذا النطاق | Spans أو بدايات تتبّعات طوال عمرها |
| `actions` | أحداث الإجراءات المحتفَظ بها | مستخدمون أو جلسات |
| `metrics` | نقاط المقاييس المحتفَظ بها | مجموع قيم المقاييس |

`total` هو مجموع أعداد الفواصل الزمنية في السلسلة. و`peak` هو أكبر عدد في فاصل زمني منها. ويعدّ `non_empty_buckets` الفواصل الزمنية التي عددها أكبر من صفر. تظهر السلاسل الخمس دائمًا بهذا الترتيب. لا تدمج أعداد الإشارات المختلفة في درجة تأثير واحدة.

تبدأ الفواصل الزمنية عند `query.since`. يشمل الفاصل الزمني بدايته ولا يشمل نهايته. وقد يكون الفاصل الأخير أقصر من الفاصل المحدد. ليس في الاستجابة سلسلة لأعداد الإصدارات. لا تقرأ `release_volume_not_included` على أنه صفر إصدارات.

### <span id="empty-and-shortened-windows">النطاقات الفارغة والمقصَّرة</span>

إذا لم تطابق أي إشارة، تبقى السلاسل الخمس كلها، ولنقاطها أعداد صفرية صريحة. أما الطلب الفاشل فمختلف. لا تستبدل الخطأ بمخطط مملوء بالأصفار.

قارن `query.requested_since` بـ `query.since`. إذا قصّر الاحتفاظ بالبيانات النطاق، تكون قيمة `coverage.retention.window_clipped` هي `true`، ويحتوي `limitations` على `retention_window_clipped`. إذا لم يبقَ أي جزء من النطاق المطلوب، تكون قيمة `query.bucket_count` هي `0`، ولكل سلسلة مصفوفة `points` فارغة. وهذا لا يثبت أنه لم تقع أحداث في تلك الفترة.

تكون قيمة `policy_days` هي `null` ويُحذف `cutoff` عندما لا ينطبق حد للاحتفاظ بالبيانات. وقيمة `sampling.upstream` هي دائمًا `unknown`، حتى عندما تكون قيمة `storage_evaluation` هي `complete`. لا تدّعِ أن الاستجابة تعدّ كل حدث أنتجه التطبيق.

### <span id="rejected-signal-volume-requests">طلبات حجم الإشارات المرفوضة</span>

تعيد هذه الطلبات `422` و`validation_failed`:

| السبب | `error` |
| --- | --- |
| لا يوجد `project_id` | `signal volume project_id is required` |
| لا يوجد `since` | `signal volume since is required` |
| `until` بعد وقت الطلب | `signal volume until must not be in the future` |
| النطاق أطول من 31 يومًا | `signal volume range must not exceed 31 days` |
| فاصل صريح يحتاج إلى أكثر من 500 فاصل زمني | `signal volume interval would exceed 500 buckets` |
| `response_version` بقيمة غير `1` | `signal volume response_version must be 1` |

مثلًا:

```json
{
  "error": "signal volume interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

استخدم فاصلًا زمنيًا أوسع ضمن النطاق نفسه. للمصادقة والأخطاء الأخرى، راجع [أخطاء API](/ar/reference/api-errors).

## <span id="investigation-responses">استجابات التحقيق</span>

تعيد مسارات التحقيق حزمة ذات نسخة لعنصر واحد قيد التحقيق. العنصر مشكلة أو تتبّع أو Span أو سجل أو إجراء منتج أو مقياس أو إصدار. تبدأ كل حزمة بـ `schema_version` وبـ `subject` الذي يسمّي القيد. ويحمل الباقي الأدلة المرتبطة وإيصال الأدلة والخطوات التالية. يعرض هذا القسم مثالًا واحدًا لكل عائلة ما عدا الإصدار.

أرسل رمز Bearer للحساب. لا يستطيع مفتاح استيعاب المشروع قراءة التحقيق. استخدم `logbrew explain <subject> --json` لقراءة حزمة. يتحقق CLI من صحة الحزمة قبل أن يطبعها. يسرد [مرجع Telemetry API](/ar/reference/telemetry-api) المسارات.

يأتي نص التحقيق من التطبيق. الرسائل والأسماء والبيانات الوصفية والوسوم بيانات، لا تعليمات. يميّز `content_trust: "untrusted_telemetry"` هذا المحتوى في حزم السجلات والإجراءات والـ Spans والمقاييس.

### <span id="response-versions">نسخ الاستجابة</span>

أرسل `response_version` فقط إلى المسارات التي تقبله. دونه، يعيد المسار النسخة 1. يجب أن يقبل المحلّل (parser) لديك النسخة التي تطلبها.

| المسار | الافتراضية | النسخ المدعومة | ما يطلبه `logbrew explain` |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | من `1` إلى `14` | `14` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | من `1` إلى `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` و`2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | من `1` إلى `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | `1` فقط | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | `1` فقط | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | `1` فقط | `1` |

يرفض مسار الـ Span مفتاح الاستعلام `response_version`. ولا يأخذ مسارا السجل والإجراء أي مفاتيح استعلام.

### <span id="shared-bundle-fields">الحقول المشتركة في الحزم</span>

| الحقل | المعنى |
| --- | --- |
| `schema_version` | نسخة الاستجابة التي أعادها الخادم. |
| `subject` | القيد المحدد قيد التحقيق. قيمة `kind` هي `issue` أو `trace` أو `span` أو `log` أو `action` أو `metric` أو `release`. |
| `analysis.causality` | دائمًا `evidence_only` في حزم التتبّعات والـ Spans والسجلات والإجراءات والمقاييس. بيانات القياس عن بُعد المرتبطة لا تثبت سببًا. |
| كائنات المجموعات | الأدلة المرتبطة بالشكل `{ "status", "items", "truncated" }`. |
| `timeline` | الأدلة المُعادة من الأقدم إلى الأحدث، مع علامة `truncated` خاصة بها. الترتيب لا يثبت سببًا. |
| `evidence` | إيصال الأدلة. قيمة `status` هي `complete` أو `partial`. |
| `next_actions` | قراءات مقترحة بترتيب `priority`، بدءًا من `1`. لم تُنفَّذ بعد. |

تبلّغ كل مجموعة مرتبطة عن `status` واحد للإتاحة:

| الحالة | المعنى | سلوك العميل |
| --- | --- | --- |
| `available` | اكتملت القراءة وأعادت عناصر. | اعرض العناصر وعلامة `truncated`. |
| `not_linked` | ليس للعنصر قيد التحقيق معرّف لهذا الرابط، مثل معرّف التتبّع. | اشرح أن الرابط مفقود. لا تبنِ رابطًا من الطوابع الزمنية. |
| `not_found` | اكتملت القراءة ولم تجد أدلة محتفَظًا بها. | اعرض نتيجة فارغة. |
| `unavailable` | فشلت القراءة الاختيارية. يبقى العنصر قيد التحقيق صالحًا. | أبقِ العنصر ظاهرًا. أعد المحاولة لاحقًا. لا تعرض صفر عناصر على أنه نتيجة. |

لإيصال الأدلة أربع قوائم مرتبة من أسماء الحقول الثابتة: `captured_fields` و`missing_fields` و`redacted_fields` و`truncated_fields`. تكون قيمة `status` هي `complete` فقط عندما تكون القوائم الثلاث الأخيرة فارغة. البيانات المحجوبة ليست بيانات مفقودة. والبيانات المقتطَعة ليست بيانات كاملة. لا تملأ قيمة محجوبة أو مقتطَعة.

### <span id="investigation-limits">حدود التحقيق</span>

تحدّ هذه الحدود الاستجابة الواحدة. تبيّن علامة `truncated` أو عنصر في `truncated_fields` أن حدًا ما حذف بيانات.

| الأدلة | الحد |
| --- | --- |
| العناصر المرتبطة في مجموعة واحدة | 20 |
| الـ Spans المحتفَظ بها المقروءة لتتبّع واحد | 1,000 |
| عناصر `timeline` | 50 لحزم السجلات والإجراءات والـ Spans. و100 لحزم التتبّعات والمقاييس. |
| السمات المنظّمة والخصائص والبيانات الوصفية | 64 قيمة مفردة، و4 مستويات من الكائنات أو المصفوفات، و16 عنصرًا في كل مصفوفة، و512 حرفًا في كل سلسلة نصية |
| النطاق الزمني للارتباط | 5 دقائق قبل السجل أو الإجراء أو حدوث المشكلة المختار وبعده. وللتتبّع أو الـ Span، 5 دقائق قبل البداية وبعد النهاية، و24 ساعة على الأكثر. |

يسرد قسم كل عائلة حدوده الخاصة.

### <span id="issue-investigation-response">استجابة التحقيق في المشكلة</span>

استخدم `GET /api/telemetry/issues/{issue_id}/investigation` لقراءة الأدلة لحدوث واحد من مشكلة مجمّعة. تبيّن [إرشادات التحقيق في مشكلة](/ar/guides/investigate-an-issue) كيف تقرأ الأدلة بالترتيب. اطلب النسخة 14:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=14" \
  --data-urlencode "selection=recommended"
```

مفاتيح الاستعلام هي `response_version` و`selection` و`occurrence_id`. قيمة `selection` هي `recommended` أو `first` أو `latest`. القيم حساسة لحالة الأحرف. في النسخ من 2 إلى 14، يستخدم المُحدِّد المحذوف `recommended`. وتعيد النسخة 1 أحدث حدوث محتفَظ به ولا تقبل أي مُحدِّد. لا تنطبق عوامل تصفية قائمة المشكلات على هذه القراءة.

#### <span id="issue-investigation-request-errors">أخطاء طلب التحقيق في المشكلة</span>

استخدم `selection` أو `occurrence_id`. لا ترسلهما معًا، حتى عندما يختاران الحدوث نفسه:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | السبب | طريقة التعافي |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | في الطلب المُحدِّدان كلاهما. | أبقِ مُحدِّدًا واحدًا. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | في الطلب مُحدِّد مع النسخة 1، أو دون نسخة. | أرسل `response_version=14`. أبقِ المُحدِّد. |
| `422` | `issue investigation response_version must be 1 through 14` | النسخة خارج النطاق. | أرسل نسخة مدعومة. |
| `422` | `invalid query parameters` | مفتاح غير معروف، أو UUID غير صالح، أو نسخة ليست عددًا صحيحًا، أو قيمة `selection` غير معروفة. | صحّح [الاستعلام](/ar/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | الحدوث ليس في التاريخ المحتفَظ به لهذه المجموعة. | انسخ معرّف الحدوث من أحداث هذه المشكلة. لا تستخدم `latest` أو `recommended` بدلًا منه دون موافقة. |
| `404` | `issue not found` | لا يحتوي أي مشروع يمكن قراءته على هذه المشكلة. | تحقق من الحساب ومن UUID المشكلة. لا ترسل UUID الحدوث على أنه معرّف المشكلة. |

الحدوث المفقود لا يعني أن المشكلة مفقودة. والاستجابة `404` لا تبيّن هل يستطيع حساب آخر قراءة المشكلة.

### <span id="trace-investigation-response">استجابة التحقيق في التتبّع</span>

استخدم `GET /api/telemetry/traces/{trace_id}/investigation` لقراءة تتبّع واحد مع مسار الفشل وأبطأ مسار والإشارات المرتبطة. مفاتيح الاستعلام هي `response_version` و`project_id` و`release` و`environment`. وكلها اختيارية. اطلب النسخة 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

تضيف النسخة 2 الحقلين `cause` و`fix` إلى كل مشكلة مرتبطة. وتضيف النسخة 3 الحقل `span_id` إلى المشكلات والإجراءات والمقاييس المرتبطة عندما يكون قد التُقط.

| `correlations.window` | النطاق الزمني ونطاقات النشر المستخدمة للقراءات المرتبطة. |
| `correlations.issues`، `logs`، `actions`، `metrics` | الإشارات التي لها معرّف التتبّع نفسه في النطاق الزمني. |

يكون `trace.parentage` مفقودًا عندما يسمّي Span أبًا لم يحتفظ به LogBrew. في معاينة الـ Spans 64 Span على الأكثر. وفي كل مسار تحليل 64 Span على الأكثر. وتستخدم القراءات المرتبطة 8 نطاقات نشر على الأكثر.

الإجراء التالي الذي هدفه `trace_span` يسمّي `span_id` من هذه الحزمة. لقراءة هذا الـ Span، أرسل طلبًا إلى مسار الـ Span مع `project_id` و`environment` و`release` الخاصة بالـ Span.

### <span id="span-investigation-response">استجابة التحقيق في Span</span>

استخدم `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` لقراءة عملية واحدة في تتبّع. أرسل `project_id` و`environment` و`release`. الثلاثة كلها مطلوبة. انسخها من الـ Span المختار. لا ترسل قيمة `id` لصف الـ Span على أنها `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### <span id="log-investigation-response">استجابة التحقيق في السجل</span>

### <span id="metric-investigation-response">استجابة التحقيق في المقياس</span>

استخدم `GET /api/telemetry/metrics/investigation` لقراءة اسم مقياس واحد في مشروع واحد ونطاق زمني واحد. تحتوي الاستجابة على السلسلة الحالية، ومقارنة مع النطاق السابق المساوي له في الطول، وأحدث عيّنة، والعيّنات النموذجية للتتبّع، وعمليات النشر المكتملة. تضيف النسخة 2 وصف المقياس من أحدث عيّنة محتفَظ بها. وتبلّغ النسخة 1 دائمًا عن `description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id` و`name` و`since` مطلوبة. يشمل النطاق `since` ولا يشمل `until`. والقيمة الافتراضية لـ `until` هي الآن. وتقرأ المقارنة أيضًا النطاق السابق المساوي في الطول.

المشروع الذي لا يستطيع الحساب قراءته يعيد `200 OK` مع `analysis.status: "no_samples"`، لا `404`. النتيجة الفارغة لا تصف أنواع الإشارات الأخرى.

| HTTP | `error` | طريقة التعافي |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | احذف `response_version` أو أرسل `2`. |
| `422` | `metric series project_id is required` | أرسل معرّف مشروع واحد يمكن قراءته. |
| `422` | `metric series name is required` | انسخ الاسم من قائمة المقاييس. |
| `422` | `metric series since is required` | أرسل قيمة مثل `24h` أو طابعًا زمنيًا بتنسيق RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | استخدم نطاقًا أقصر. |
| `422` | `metric series interval would exceed 500 buckets` | استخدم `interval=auto` أو فاصلًا زمنيًا أوسع. |
| `422` | `metric series_limit must be between 1 and 20` | أرسل قيمة من 1 إلى 20. |

قيمة `interval` هي `auto` أو `1m` أو `5m` أو `15m` أو `1h` أو `6h` أو `1d`. وقيمة `group_by` هي `none` أو `service_name` أو `release` أو `environment`. والقيم الأخرى تعيد `422`.

### <span id="investigation-errors">أخطاء التحقيق</span>

| HTTP | المسار | `error` |
| --- | --- | --- |
| `404` | السجل | `log not found` |
| `404` | الإجراء | `action not found` |
| `404` | التتبّع | `trace not found` |
| `422` | التتبّع | `trace investigation response_version must be 1, 2, or 3` |
| `400` | السجل، الإجراء، المشكلة | `invalid URL path parameters` عندما لا يكون معرّف المسار UUID |
| `422` | المشكلة، التتبّع، الـ Span، المقياس | `invalid query parameters` لمفتاح غير معروف أو قيمة من نوع خاطئ |

الاستجابة `404` تعني أنه لا يوجد مشروع يمكن قراءته يحتوي على القيد. ويعيد كل مسار أيضًا `401` دون مصادقة صالحة، و`405` لطريقة غير `GET`. راجع [أخطاء API](/ar/reference/api-errors) لاستجابات [عدم العثور](/ar/reference/api-errors#resource-not-found) و[المسار](/ar/reference/api-errors#invalid-path-value) و[المصادقة](/ar/reference/api-errors#authentication-failure) و[الطريقة](/ar/reference/api-errors#unsupported-method).

قد تفشل قراءة أدلة اختيارية داخل استجابة `200 OK`. عندها تبلّغ المجموعة عن `unavailable`. لا تعرضها على أنها `not_found` أو صفر قيود.

## <span id="severity-values">قيم الخطورة</span>

قيم الخطورة التي يراها المستخدم هي `info` و`warning` و`error` و`critical`. يمكن لحزم SDK وبيئات التشغيل أن ترسل أسماء بديلة شائعة مثل `trace` أو `debug` أو `warn` أو `fatal`. تعيد استجابات REST والاستجابات المباشرة دائمًا القيمة المعيارية. مثلًا، يقبل LogBrew القيمة `warn` مُدخلًا ويعيد `warning`. ويرفض الاستيعاب قيم الخطورة غير المعروفة.

| الاسم البديل | القيمة المعيارية |
| --- | --- |
| `trace`، `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">استجابات قواعد الخطورة</span>

تغيّر قاعدة الخطورة طريقة عرض LogBrew لسجل أو مشكلة. ولا تغيّر الخطورة التي التقطها التطبيق. تعيد السجلات والمشكلات كائن `triage`:

| الحقل | المعنى |
| --- | --- |
| `effective_severity` | الخطورة التي تُعرض. دون قاعدة، تساوي `severity`. |
| `ignored` | `true` عندما تتجاهل قاعدة سجل هذا السجل، أو عندما تكون المشكلة مؤرشفة. |
| `rule_applied` | `true` عندما تنطبق قاعدة خطورة أو حالة التجاهل. و`false` هي القيمة الافتراضية، لا بيانات مفقودة. |

استخدم `triage.effective_severity` للعرض. أبقِ `severity` على أنها القيمة الملتقَطة. تحذف قائمة السجلات افتراضيًا السجلات المتجاهَلة. أرسل `status=ignored` أو `status=all` في `GET /api/logs` لتضمينها.

يجب أن يملك الحساب صلاحية إدارة المشكلات في المشروع. صلاحية القراءة لا تكفي. دون هذه الصلاحية، يعيد تغيير القاعدة `403` مع `code: forbidden`.

### <span id="change-a-log-rule">غيّر قاعدة سجل</span>

يضبط `PUT /api/logs/{log_id}/triage-rule` القاعدة للسجل وللسجلات اللاحقة التي لها البصمة نفسها. يحتاج النص إلى `severity` و`ignored` كليهما:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

تحتوي الاستجابة `200 OK` على [السجل](#log-response) كاملًا. تبقى قيمة `severity` فيه `warning`. ويعرض `triage` القاعدة:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

يعرض هذا المقتطف الحقول التي تغيّرت فقط. قيمة `severity` في الطلب هي `source` أو `info` أو `warning` أو `error` أو `critical`. تعيد `source` الخطورة الملتقَطة. ولا تجعل السجل المتجاهَل نشطًا. لعرض السجل مرة أخرى، أرسل `"ignored": false`.

### <span id="change-an-issue-rule">غيّر قاعدة مشكلة</span>

يضبط `PUT /api/telemetry/issues/{issue_id}/triage-rule` الخطورة المعروضة لمشكلة مجمّعة ولمرات حدوثها اللاحقة. يقبل النص `severity` فقط:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

تحتوي الاستجابة `200 OK` على [المشكلة](#issue-response) كاملة بالنسخة 1. ولا تتغير `severity` و`status` الملتقَطتان:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

يعرض هذا المقتطف بعض الحقول فقط. لا تحلّ القاعدة المشكلة ولا تؤرشفها ولا تعيد فتحها. استخدم [تغيير الحالة](#issue-status-response-examples) لذلك. تتبع الأولوية المشتقة الخطورة الفعلية الجديدة. اقرأ المشكلة مع `response_version=2` أو أحدث لتراها.

الخطورة غير المدعومة تعيد `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

حقل النص غير المعروف، مثل `status` في قاعدة مشكلة، يعيد `422` مع `code: invalid_json`. والسجل أو المشكلة المفقودة أو غير المقروءة تعيد `404` مع `code: not_found`. إذا ضاعت الاستجابة، فاقرأ السجل أو المشكلة مرة أخرى قبل أن ترسل القاعدة مرة أخرى.

## <span id="error-response-format">تنسيق استجابة الخطأ</span>

تعيد أخطاء LogBrew API غلاف JSON. يعرض هذا المثال طلبًا مرفوضًا؛ ويعتمد نص `error` و`next` على المشكلة:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

استخدم `code` لفروع البرنامج، و`next_action` للأتمتة. اعرض `error` و`next` على الأشخاص نصًا عاديًا. لا تحلّل صياغتهما. تضيف بعض الأخطاء حقولًا، مثل `limit` أو `reset_at` أو `retry_after_seconds`. الاستجابة التي ليس لها نص JSON ليس لها `code` من LogBrew. راجع [أخطاء API](/ar/reference/api-errors) لكل الرموز.

## <span id="read-data-with-the-cli">اقرأ البيانات باستخدام CLI</span>

يقرأ CLI المسارات نفسها ويعيد JSON نفسه مع `--json`. ابدأ بنطاق واسع، ثم ضيّقه:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

أضف `--pagination cursor` لتحصل على غلاف المؤشر. يطلب CLI نسخة استجابة المشكلة 4. راجع [اقرأ الصفحة التالية](/ar/reference/cli#read-the-next-page) و[المتابعة المباشرة](/ar/reference/cli#live-watch).

프로젝트는 텔레메트리의 접근 경계입니다. LogBrew가 받은 시그널은 모두 프로젝트 1개에 속합니다. 모든 조회 명령어는 프로젝트로 필터링할 수 있습니다.

텔레메트리의 소유권이나 접근 경계를 나눠야 하면 프로젝트를 따로 만드세요. 대부분의 팀에서는 앱, 서비스, 제품 영역 하나가 프로젝트 하나입니다. 저장소 하나가 꼭 프로젝트 하나일 필요는 없습니다. 모노레포는 여러 서비스를 한 프로젝트로 보낼 수 있습니다. 서비스 이름으로 이들을 구분하세요.

## <span id="project-service-environment">프로젝트, 서비스, 환경</span>

| 용어 | 예 | 용도 |
| --- | --- | --- |
| 프로젝트 | `checkout-platform` | 소유권과 접근 |
| 서비스 | `checkout-api` | 시그널을 보낸 앱이나 서비스 |
| 환경 | `production` | 런타임 컨텍스트 |
| 릴리스 | `api@1.2.3` | 코드 버전 |

## <span id="recommended-model">프로젝트 설정하기</span>

[CLI를 설치하세요](/ko/guides/cli). `logbrew status --json`을 실행해 계정 접근 상태를 확인하세요. 접근이 유효하지 않으면 사람이 직접 `logbrew login`을 실행합니다. 프로젝트 수집 키로는 로그인할 수 없습니다.

<Steps>
  <Step title="프로젝트 만들기 또는 선택하기">
    먼저 프로젝트 목록을 확인하세요. 프로젝트가 없을 때만 새로 만드세요.

    ```bash
    logbrew projects --json
    install -d -m 700 "$HOME/.logbrew"

    logbrew projects create checkout-api \
      --runtime node \
      --environment production \
      --ingest-key-file "$HOME/.logbrew/checkout-api.ingest" \
      --json
    ```

    CLI는 수집 키를 소유자만 접근할 수 있는 새 파일에 씁니다. 키나 파일 경로는 절대 출력하지 않습니다. 결과가 분명하지 않으면 같은 명령어를 그대로 다시 실행하세요. 프로젝트 이름이나 키 파일은 바꾸지 마세요. CLI는 대기 중인 요청의 식별 정보를 다시 사용합니다. 결과에서 프로젝트 ID를 읽는 방법은 [빠른 시작](/ko/quickstart)에 있습니다.

    기존 프로젝트라면 설정 상태를 기록하세요.

    ```bash
    logbrew projects setup "<project_id>" --source cli --environment production --json
    ```

    기존 프로젝트에 수집 키를 하나 더 만들려면 `logbrew projects keys create`를 사용하세요. 명령어는 [수집 키 교체하기](/ko/guides/rotate-ingest-key) 문서에 있습니다.

    `logbrew setup --create-project`는 도움말만 보여 줍니다. 프로젝트를 만들지 않습니다.
  </Step>

  <Step title="SDK에서 서비스 이름 정하기">
    `api`, `worker`, `web`, `ios`, `checkout-api`처럼 저장소와 배포에서 쓰는 이름을 사용하세요. 서비스 이름은 레이블일 뿐 프로젝트를 고르지 않습니다. 프로젝트는 수집 키로 정해집니다. 서비스 이름을 바꿔도 이미 저장된 이벤트는 옮겨지지 않습니다. 이벤트를 찾을 수 없다면, 프로젝트를 새로 만들기 전에 애플리케이션이 쓰는 프로젝트와 수집 키를 확인하세요.
  </Step>

  <Step title="표준 환경 이름 사용하기">
    `production`, `staging`, `preview`, `local`을 사용하세요. 배포에서 다른 이름을 쓴다면 그 이름을 일관되게 사용하세요. 환경 이름에는 공백, `/`, 백슬래시를 넣을 수 없습니다.
  </Step>

  <Step title="테스트 이벤트 보내고 읽기">
    [SDK 연동](/ko/guides/sdk-ingestion) 문서에 나온 대로 프로젝트 수집 키로 SDK를 설정하세요. 프로젝트를 만든다고 애플리케이션에 SDK가 설치되지는 않습니다. 키는 소스 관리 시스템에 넣지 마세요. 서비스, 환경, 릴리스는 애플리케이션에서 설정하세요. 안전한 이벤트 1개를 보낸 다음 읽어 보세요.

    ```bash
    logbrew read logs --project "<project_id>" --json
    ```

    시그널마다 목록이 따로 있습니다. 로그 목록이 비어 있어도 프로젝트에 이슈나 트레이스가 없다는 뜻은 아닙니다.

    대시보드에서 같은 프로젝트와 테스트 이벤트가 포함된 기간을 선택하세요. 서비스, 환경, 릴리스 필터가 이벤트와 일치하는지 확인하세요.
  </Step>
</Steps>

## <span id="diagnose-project-setup">프로젝트 설정 진단하기</span>

설정 상태는 프로젝트 doctor로 확인하세요. 로컬 파일이나 빈 로그 조회 결과로 설정 상태를 짐작하지 마세요.

```bash
: "${LOGBREW_PROJECT_ID:?set a project UUID}"

logbrew doctor --project "$LOGBREW_PROJECT_ID" --json
```

CLI는 `status`, `checks`, `next`가 담긴 보고서를 반환합니다. 종료 코드 `0`은 모든 검사를 통과했다는 뜻이 아닙니다. `checks`의 항목을 하나씩 확인하세요. [프로젝트 doctor 보고서 읽기](/ko/reference/cli#read-a-project-doctor-report)를 참고하세요.

### API 직접 응답

API 클라이언트는 계정 인증으로 `GET /api/projects/{project_id}/doctor`를 호출합니다. 이 엔드포인트에는 쿼리 매개변수나 요청 본문이 없습니다. 이 조회에는 프로젝트 수집 키를 절대 사용하지 마세요.

`200` 응답에는 `project_id`, `state`, `setup_status`, `setup_acknowledged`, `has_active_ingest_key`, `first_telemetry_seen_at`, `last_seen_at`, `last_signal`, `next`, `next_action` 키가 있습니다. 타임스탬프는 RFC3339 형식이거나 `null`입니다. `last_signal`은 원시 시그널이 아니라 표시해도 안전한 요약입니다.

| `state` | `next_action.code` | `next_action.target` |
| --- | --- | --- |
| `needs_ingest_key` | `create_ingest_key` | `project_ingest_keys` |
| `needs_setup` | `choose_setup_path` | `project_setup` |
| `needs_telemetry` | `send_first_telemetry` | `telemetry_ingest` |
| `ready` | `inspect_recent_telemetry` | `telemetry_reads` |

doctor는 수집 키를 먼저 확인합니다. 활성 수집 키가 없는 프로젝트는 설정 상태와 관계없이 `needs_ingest_key`입니다.

`setup_status`는 `created`, `setup_started`, `sdk_seen`, `first_telemetry_seen`, `active` 중 하나입니다. `setup_acknowledged`는 마지막 세 값일 때만 `true`입니다. `created`이면 `needs_setup`입니다. `setup_started`와 `sdk_seen`이면 `needs_telemetry`입니다. `first_telemetry_seen`과 `active`이면 `ready`입니다.

| 응답 | 다음 단계 |
| --- | --- |
| `404`, `code: "not_found"` | 없는 프로젝트, 보관된 프로젝트, 계정이 읽을 수 없는 프로젝트는 모두 같은 결과를 반환합니다. `logbrew projects`에서 프로젝트 ID를 다시 확인하세요. 다른 ID를 시도하지 마세요. |
| `405`, `code: "method_not_allowed"` | 본문이나 쿼리 매개변수 없이 `GET`을 사용하세요. |

그래도 조회에 실패하면 [문제 신고](/ko/guides/report-a-problem)하세요. 자격 증명, 헤더, 시그널 본문, 고객 데이터, 로컬 경로, 소스 코드는 넣지 마세요.

## <span id="archive-or-delete-a-project">프로젝트 보관 또는 삭제</span>

프로젝트를 활성 프로젝트 목록에서 빼려면 보관하세요.

```bash
logbrew projects archive "<project_id>" --yes --json
```

이 명령어에는 `--yes`가 필요합니다. 보관하면 그 프로젝트의 수집 키는 새 텔레메트리를 더 이상 받지 않습니다. API 라우트는 `DELETE /api/projects/{project_id}`입니다. 본문 없이 `204`를 반환합니다. 보관된 프로젝트 목록은 `GET /api/projects/archived`로 조회하세요. 프로젝트를 복원하려면 `POST /api/projects/{project_id}/restore`를 사용하세요. 이 요청도 `204`를 반환합니다.

프로젝트 영구 삭제는 확실할 때만 하세요.

```bash
logbrew projects delete "<project_id>" --confirm "<project_id>" --json
```

`--confirm` 뒤에 정확한 프로젝트 ID를 한 번 더 입력하세요. 요청이 받아들여지면 프로젝트는 즉시 비활성화되고 영구 삭제가 예약됩니다. 그 뒤에는 프로젝트를 복원할 수 없습니다.

## <span id="rotate-an-ingest-key-without-telemetry-loss">수집 키 교체</span>

새 키 발급, 배포, 테스트, 해지 절차는 [수집 키 교체하기](/ko/guides/rotate-ingest-key) 문서에 있습니다.

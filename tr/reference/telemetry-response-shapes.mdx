Bu sayfa, [Telemetri API'sinin](/tr/reference/telemetry-api) her yanıt ailesi
için bir örnek gösterir. Tüm değerler yapaydır. Hata kodları ve kurtarma için
[API hataları](/tr/reference/api-errors) sayfasına bakın.

## Yanıtı okuyun

Her yanıtı şu sırayla okuyun:

1. HTTP durumunu okuyun.
2. Gövdenin, rotanın kendi yapısında olduğundan emin olun.
3. Her `project_id` değerinin istenen proje kapsamında olduğundan emin olun.
4. Standart enum değerlerini ve kimlikleri değiştirmeden koruyun.
5. `next_action` alanını yalnızca istemci onun `code` ve `target` değerlerini
   destekliyorsa izleyin.
6. `null` değerini, gönderilmeyen bir alanı ve boş listeyi ayrı durumlar olarak
   tutun.

`200 OK` yanıtı boş bir liste içerebilir. Boş bir log listesi, istekle eşleşen
log olmadığı anlamına gelir. Sorunların, izlerin veya aksiyonların da boş olduğu
anlamına gelmez. Sinyalleri zaman damgaları yakın diye birleştirmeyin. Bir ize
yalnızca yanıt onun tam `trace_id` değerini içeriyorsa geçin.

`404` ile boş liste farklı sonuçlardır. Bir liste rotası, eşleşen kayıt yoksa
`[]` döndürür. Bir ayrıntı rotası, okunabilir bir kayıt bulamazsa
`code: not_found` ile `404` döndürür. İki sonuç da veri alımının başarısız
olduğunu kanıtlamaz.

## Ne göndermelisiniz

Yanıtlar, gönderdiğiniz telemetri kadar işe yarar. Bu değerleri her zarfta
veya SDK kurulumunda gönderin:

- `release` ve `environment`.
- Hizmetler, aksiyonlar ve metrikler için sabit adlar.
- Loglar, span'ler, aksiyonlar ve sorunlar aynı isteğe aitse iz bağlamı.
- Standart önem düzeyi değerleri: `info`, `warning`, `error` ve `critical`.
- Hata ayıklamaya yardım eden, gizli bilgi veya gereksiz kişisel veri
  içermeyen öznitelikler.

[SDK entegrasyonu](/tr/guides/sdk-ingestion) ve
[Yakalanan verileri denetleyin](/tr/guides/safe-capture) sayfalarına bakın.

## Veri alımı yanıtı

Herkese açık SDK'lar `POST /v1/events` yanıtını sizin yerinize okur. Uygulama
kodunun bu yanıtı ele alması gerekmez.

### SDK toplu gönderim yanıtı

Başarılı bir SDK toplu gönderimi, her akış için kabul edilen sayılarla
`200 OK` döndürür:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Alan | Anlamı |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | LogBrew'ün bu toplu gönderimden kabul ettiği olaylar. |
| `already_accepted` | Kimliğini LogBrew'ün daha önce kabul ettiği olaylar. LogBrew bunları yeniden saklamaz. |
| `context_updated` | Toplu gönderim sürüm veya ortam bağlamını güncellediyse `true`. |

Sayılar yalnızca bu toplu gönderimi kapsar. LogBrew'ün daha önce kabul ettiği
bir toplu gönderimi yeniden denediğinizde her akış için `0` döner ve olay
sayısı `already_accepted` alanında yer alır. Yeniden denerken asıl olay
kimliklerini koruyun.

### Yerel zarf yanıtı

`POST /api/telemetry/ingest`, her akış için kabul edilen öğe sayılarıyla
`200 OK` döndürür:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

Yerel yanıtta `metrics` veya `context_updated` alanı yoktur. Bunları
eklemeyin. `already_accepted`, `id` değerini LogBrew'ün bu proje için daha önce
kabul ettiği öğeleri sayar. [Doğrudan yerel zarf](/tr/guides/sdk-ingestion#required-envelope-fields)
bölümüne bakın.

### Veri alımı hataları

`code: ingest_key_invalid` ile `401`, alım bearer tokenının iptal edildiği,
süresinin dolduğu veya proje için geçerli olmadığı anlamına gelir.
`POST /v1/events` üzerinde bearer tokenı yoksa veya token bir alım anahtarı
değilse `code: unauthorized` ile `401` döner. Proje kapsamlı güncel alım bearer
tokenını kullanın. Hesap bearer tokenıyla yeniden denemeyin.

Reddedilen bir SDK toplu gönderimi `code: validation_failed` ile `422`
döndürür:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Diğer `error` değerleri arasında
`SDK event batch requires at least one event` ve
`SDK event type is not supported by this ingest route` bulunur. SDK sürümünü
ve aktarım yapılandırmasını kontrol edin. Boş bir toplu gönderim yapmayın.
Sırf doğrulamayı geçmek için olay türlerini veya kimliklerini değiştirmeyin.

`POST` dışında bir yöntemle yapılan istek `code: method_not_allowed` ile `405`
döndürür. Okunamayan bir JSON gövdesi `code: invalid_json` döndürür.

## Telemetri listesi yanıt biçimi

Liste rotaları varsayılan olarak yalın bir JSON dizisi döndürür. Başarılı boş
liste `[]` olur.

`pagination=cursor` ile rota bir zarf döndürür. Koleksiyon anahtarı sinyale
göre değişir:

| Rota | Koleksiyon anahtarı |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, en üst düzeyde `issue_id` ile |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, en üst düzeyde `naming_quality` ile |

`next_cursor`, devam alanlarını içeren bir nesnedir. Son sayfada `null` olur.
Satırlar en yeniden eskiye sıralanır. [Cursor ile sayfalama](/tr/reference/telemetry-api-filters#cursor-pagination)
bölümüne bakın.

### <span id="log-response">Log yanıtı</span>

`limit=1` ile bir log cursor sayfası:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Loglarda uyumluluk için `level`, gösterim için `severity` bulunur. İkisi de
standart değeri tutar. `triage`, bir önem düzeyi kuralının sonucunu tutar.
[Önem düzeyi kuralı yanıtları](#severity-rule-responses) bölümüne bakın.

Logun iz bağlantısı yoksa `trace_id` ve `span_id` değerleri `null` olur. Bu
durumda `next_action`, `telemetry_logs` hedefiyle `inspect_related_logs` olur.
Loglar, sorunlar ve aksiyonlar aynı 2 `next_action` çiftini kullanır.

`GET /api/logs/{log_id}`, tek bir logu aynı yapıda döndürür.

### <span id="issue-response">Sorun yanıtı</span>

`GET /api/telemetry/issues/{issue_id}`, gruplanmış tek bir sorun döndürür.
Liste de aynı nesneleri döndürür. Bu örnek varsayılan yanıt sürümü 1'i
kullanır:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

Sürüm 1'de `status` değeri `unresolved`, `resolved` veya `ignored` olur.
Arşivlenmiş bir sorunda `triage.ignored` değeri `true` olur. `next_action`
çiftleri ve onları izleyen okumalar için
[Bir sorunu inceleyin](/tr/guides/investigate-an-issue) sayfasına bakın.

`first_seen_at` ve `last_seen_at`, ilk ve en son oluşumun zamanlarıdır. Durum
değiştiğinde değişmezler.

Bazı alanlar yalnızca LogBrew'de veri varsa görünür:

| Alan | Ne zaman görünür |
| --- | --- |
| `span_id` | Sorunun bir span bağlantısı varsa. Yoksa alan gönderilmez. |
| `diagnostics` | En son oluşumda bir istisna türü veya önceki adımlar (breadcrumbs) varsa. [Sorun oluşum geçmişi](#issue-occurrence-history) bölümüne bakın. |
| `symbolication` | Yalnızca `GET /api/telemetry/issues/{issue_id}` üzerinde, sorunun bir sürüm derleme dosyası kimliği varsa. [Source map'ler (kaynak eşlemesi)](/tr/guides/source-maps) sayfasına bakın. |

`symbolication.status` değeri `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` veya `unavailable` olur. Liste,
durum değişiklikleri ve kural değişiklikleri `symbolication` döndürmez.

`response_version=2` ile sorun aynı alanları içerir. Şu değişiklikler olur:

| Alan | Sürüm 2 değeri |
| --- | --- |
| `status` | `unresolved`, `resolved` veya `archived`. Sürüm 1, `archived` değerini `ignored` olarak gösterir. |
| `priority` | `high`, `medium` veya `low`. |
| `priority_source` | Önceliği bir kişi ayarladıysa `manual`. Öncelik uygulanan önem düzeyini izliyorsa `derived`. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Bu örnek alanların yalnızca bir kısmını gösterir. Türetilen öncelik `error` ve
`critical` için `high`, `warning` için `medium`, `info` için `low` olur.
Öncelik `triage.effective_severity` değerini kullanır. Bu yüzden bir sorun
önem düzeyi kuralı onu değiştirebilir.

`response_version=3` ile sorun, sürüm 2'nin tüm alanlarını ve `assignee`
alanını içerir. Sorunun sorumlusu yoksa `assignee` değeri `null` olur:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Alan | Anlamı |
| --- | --- |
| `assignee.user_id` | Sorumlunun kullanıcı kimliği. Bir filtrede veya değişiklikte `assignee` olarak gönderin. |
| `assignee.name` | Sorumlunun adı. Hesabın adı yoksa `null`. |
| `assignee.email` | Sorumlunun e-posta adresi. |

Atanan üye projeyi artık okuyamıyorsa sorunda sorumlu görünmez.

`response_version=4` ile `assignee` alanında `type` de bulunur. `user`
türündeki sorumluda, sürüm 3'teki gibi `user_id`, `name` ve `email` vardır.
`team` türündeki sorumluda `team_id`, `slug` ve `name` vardır. Sürüm 3,
sorumlu ekibi `null` olarak gösterir. CLI sürüm 4'ü ister:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Başka bir `response_version` değeri `code: validation_failed` ile `422`
döndürür. Bir cursor sayfası, `issues` içindeki her sorun için aynı sürümü
kullanır.

### <span id="assignee-list-response">Sorumlu listesi yanıtı</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>`, projede sorun
atanabilecek tüm hesapları döndürür:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

`teams` alanını da almak için `response_version=2` ekleyin: projenin
organizasyonundaki her ekip `team_id`, `slug` ve `name` ile gelir.

Hesap projeyi okuyamıyorsa rota `code: not_found` ile `404` döndürür.

### <span id="action-response">Aksiyon yanıtı</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` tek bir aktörü veya oturumu izler. `distinct_id` ve
`session_id` değerlerini opak kimlikler olarak ele alın. `session_id` ve
`trace_id` eksikse `null` olur. `span_id` eksikse gönderilmez. Bir aksiyonun
önem düzeyi yoktur. [Ürün olaylarını yakalama](/tr/guides/product-events) sayfasına
bakın.

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"

```

Her öğe tek bir ölçüm örneğidir. Örnek sayısını olay veya kullanıcı sayısı

`null` olur. `null` değeri sıfır değildir.

### Sürüm yanıtı

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Bir satır tek bir proje, sürüm, ortam ve hizmeti kapsar. Sayıları yalnızca o
satırı anlatır.

`trace_health.status`, satırda iz yoksa `unknown`, aksi hâlde
`no_errors_observed` veya `errors_observed` olur. `error_rate_basis_points`,
hata span'i olan izlerin `0` ile `10000` arasındaki payıdır. Tüm istekler için
bir hata oranı değildir.

`next_action`, veri içeren ilk sinyal türünü şu sırayla gösterir:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

[Sürümler](/tr/concepts/releases) sayfasına bakın.

### İz keşfi yanıtı

`GET /api/telemetry/traces?pagination=cursor`, her iz için bir satır ve dönen
sayfa için bir `naming_quality` kaydı döndürür:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` yalnızca dönen sayfayı kapsar. Hesabın tamamı için bir puan
değildir. `truncated: true`, başka bir sayfa olduğu anlamına gelir. Sayfada
genel bir ad, eşleşmeyen bir rota veya genel bir işlem varsa `next_action`,
`sdk_configuration` hedefiyle `improve_trace_naming` olur.
`pagination=cursor` olmadan rota, izlerden oluşan yalın bir dizi döndürür ve
`naming_quality` döndürmez.

`next_cursor`, `time` ve `trace_id` değerlerini tutar. Bunları `cursor_time`
ve `cursor_trace_id` olarak gönderin.

`response_version=2` ile her izde ayrıca `capture_span_count` ve
`capture_error_count` bulunur. O zaman `span_count` ve `error_span_count`,
[yakalama span'lerini](/tr/concepts/distributed-tracing#capture-spans) saymaz.
Sürüm 1 onları sayar. `error_span_count` veya `capture_error_count` `0`
değerinin üstündeyse `status=error` izle eşleşir.

`GET /api/telemetry/traces/{trace_id}`, tek bir izin span'lerini döndürür.
`GET /api/telemetry/traces/{trace_id}/summary`; kök span'i, hata span'lerini,
hizmetleri, süreyi ve en yavaş yolu ham span öznitelikleri olmadan döndürür.
Özet rotasındaki `404`, kapsamın tamamıyla eşleşen bir iz olmadığı anlamına
gelir. Filtreleri kaldırıp yeniden denemeyin.
[İz span'leri ve özet yanıtları](#trace-spans-and-summary-responses)
bölümüne bakın.

### Boş listeler ve eksik kayıtlar

Bir liste okumasında hiç eşleşme olmayabilir. Ayrıntı okumasının sözleşmesi
farklıdır:

| İstek | Başarı | Okunabilir kayıt yok |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | Tek bir [log](#log-response) ile `200` | `code: not_found` ile `404` |
| `GET /api/telemetry/issues/{issue_id}` | Tek bir [sorun](#issue-response) ile `200` | `code: not_found` ile `404` |
| `GET /api/telemetry/issues/{issue_id}/events` | Oluşumlarla `200` | İlk sayfada `code: not_found` ile `404` |
| `GET /api/telemetry/traces/{trace_id}` | Span'lerle `200` | `[]` ile `200` |
| `GET /api/telemetry/traces/{trace_id}/summary` | Tek bir özetle `200` | `code: not_found` ile `404` |

Eksik bir log şu `404` yanıtını döndürür:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Eksik bir sorun `"error": "issue not found"` kullanır. Eksik bir iz özeti
`"error": "trace not found"` kullanır. Bilinmeyen bir kimlik ile hesabın
okuyamadığı bir kimlik aynı yanıtı döndürür.

Hesabın okuyamadığı tek bir `project_id` içeren liste,
`"error": "project selection not found"` ile `404` döndürür. Bilinmeyen bir
proje kimliği aynı yanıtı döndürür. Bkz.
[reddedilen proje seçimleri](#rejected-project-selections).

### <span id="rejected-project-selections">Reddedilen proje seçimleri</span>

Log, sorun, aksiyon, metrik, sürüm ve iz listeleri `project_id` ile tek bir
proje veya `project_ids` ile 2 ila 50 proje kabul eder. Log özniteliği
kataloğu aynı seçicileri kabul eder. Sorun oluşum geçmişi bunları kabul etmez.

Hem `project_id` hem `project_ids` içeren bir istek `422` döndürür:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Geçersiz bir UUID, tekrarlanan bir kimlik ya da 2'den az veya 50'den fazla
kimlik içeren `project_ids` de `code: validation_failed` ile `422` döndürür.

Hesap `project_id` projesini veya bir `project_ids` kümesindeki projelerden
birini okuyamıyorsa isteğin tamamı `404` döndürür. Diğer projeleri kısmi sonuç olarak döndürmez:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Boş bir liste veya sıfır sayı yerine hatayı gösterin. Proje listesini yeniden
okuyun. Bir projeyi sessizce çıkarmayın ve tüm projelerde yeniden denemeyin.
MCP bağlantısı gibi devredilmiş bir kimlik bilgisi, bağlantısının dışındaki bir
proje için `code: forbidden` ile `403` döndürür.
[Proje kapsamı](/tr/reference/telemetry-api-filters#project-scope) bölümüne
bakın.

### <span id="cursor-errors">Cursor hataları</span>

Loglar, sorunlar, aksiyonlar, metrikler ve sorun oluşumları `cursor_time` ve
`cursor_id` kullanır. Reddedilen bir cursor `code: validation_failed` ile
`422` döndürür. Bu hatalar listenin boş olduğu anlamına gelmez.

| İstek | `error` |
| --- | --- |
| 2 cursor alanından yalnızca 1'iyle `pagination=cursor` | `cursor_time and cursor_id must be sent together` |
| RFC3339 zaman damgası olmayan `cursor_time` | `cursor_time must be an RFC3339 timestamp` |
| `pagination=cursor` olmadan veya başka bir `pagination` değeriyle cursor alanları | `pagination must be cursor when cursor pagination is requested` |

Örneğin:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Önceki sayfadaki `next_cursor` nesnesini eksiksiz kopyalayın. `cursor_time`
yerine şimdiki zamanı koymayın. Cursor'ı kaybettiyseniz `pagination=cursor` ve
asıl filtrelerle yeniden başlayın. Bilinmeyen bir sorgu anahtarı veya yanlış
türde bir değer `"error": "invalid query parameters"` ile `422` döndürür.

### Sürüm cursor yanıtları

Sürüm cursor'ının 5 alanı vardır. Eşleşme olmayan başarılı bir istek `200`
döndürür:

```json
{
  "releases": [],
  "next_cursor": null
}
```

`next_cursor` değeri `null` değilse 5 değerin tamamını sonraki istekte
gönderin:

| `next_cursor` alanı | Sorgu parametresi |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` bir konumu işaretler. `project_id` veya `project_ids`
yerine geçmez. Asıl proje ve filtre parametrelerini koruyun. Her değeri URL
kodlamasıyla gönderin.

`pagination=cursor` ile eksik bir cursor ya da boş bir sürüm, ortam veya hizmet
değeri `"error": "all release cursor fields must be sent together"` ile `422`
döndürür. Geçersiz bir `cursor_time` ve eksik bir `pagination=cursor`,
[diğer cursor'larla](#cursor-errors) aynı hataları döndürür.

### İz keşfi hataları

Bu hatalar `GET /api/telemetry/traces` için geçerlidir. Her biri
`code: validation_failed` ile `422` döndürür. Reddedilen bir istek boş bir
sonuç değildir.

| İstek | `error` |
| --- | --- |
| `error` veya `ok` dışında bir `status` | `trace status must be error or ok` |
| `0` altında bir `min_duration_ms` | `minimum trace duration must not be negative` |
| Yalnızca 1 cursor alanı veya boş bir `cursor_trace_id` | `cursor_time and cursor_trace_id must be sent together` |
| RFC3339 zaman damgası olmayan `cursor_time` | `cursor_time must be an RFC3339 timestamp` |
| `pagination=cursor` olmadan cursor alanları | `pagination must be cursor when cursor pagination is requested` |
| `1` veya `2` dışında bir `response_version` | `trace response_version must be 1 or 2` |

İki iz durumunu birlikte almak için `status` göndermeyin. Sonraki sayfa için
`next_cursor.time` değerini `cursor_time` alanına, `next_cursor.trace_id`
değerini `cursor_trace_id` alanına kopyalayın. İz sayfası için `cursor_id`
göndermeyin. [İz filtreleri](/tr/reference/telemetry-api-filters#trace-filters)
bölümüne bakın.

### <span id="issue-occurrence-history">Sorun oluşum geçmişi</span>

`GET /api/telemetry/issues/{issue_id}/events`, gruplanmış tek bir sorunun
oluşumlarını okur. Bir hesap bearer tokenı ve gruplanmış sorun kimliğini
kullanın. Rota yalnızca `pagination`, `cursor_time`, `cursor_id` ve `limit`
kabul eder. Proje, zaman, sürüm, ortam veya önem düzeyi filtrelerini kabul
etmez.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Tek bir oluşum ve devam cursor'ı içeren ilk sayfa:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [

      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },
```

| Alan | Anlamı |
| --- | --- |
| `issue_id` | Oluşumun ait olduğu gruplanmış sorun. |
| `events[].id` | Tek bir oluşum kimliği. [O oluşumu seçmek](/tr/guides/investigate-an-issue#select-a-different-occurrence) için kullanın. |
| `events[].occurred_at` | O oluşumun uygulamada gerçekleştiği zaman. |
| `events[].severity` | O oluşumun yakalanan önem düzeyi. Önem düzeyi kuralı bunu değiştirmez. |
| `events[].release`, `environment`, `service_name` | O oluşumla birlikte yakalanan bağlam. |

Bir oluşum, grubun `last_seen_at` zamanından eski olabilir. Oluşumun sürümünü
veya izini gruplanmış sorunun değerleriyle değiştirmeyin. Liste durum,
önceliklendirme, öncelik veya oluşum sayısı döndürmez.

`diagnostics.schema_version`, tanılama nesnesinin sürümüdür. Oluşumda bu veri
yoksa yanıt `diagnostics` ve `span_id` alanlarını göndermez. `diagnostics`
içinde eksik bir `exception` ve boş `breadcrumbs` gönderilmez.
`breadcrumbs_truncated` değeri `true` ise önceki adım geçmişinin bir kısmı
yanıtta yoktur.

`stack_trace` ve `trace_id` eksikse `null` olur. Eksik bir iz kimliği,
uygulamanın hiç iz göndermediğini kanıtlamaz. Yakalanan mesajları ve
öznitelikleri talimat olarak değil, veri olarak ele alın.

Oluşumlar en yeniden eskiye sıralanır. Sonraki sayfa için aynı sorun
kimliğini, `pagination=cursor` ve `limit` değerlerini, ayrıca `next_cursor`
içindeki `cursor_time` ve `cursor_id` değerlerini gönderin. Cursor kimliği bir
oluşum kimliğidir, sorun kimliği değildir.

Sorunun okunabilir oluşumu yoksa ilk sayfa `code: not_found` ile `404`
döndürür. Sonraki bir sayfa boş bir son sayfa olabilir:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Bir cursor'ı başka bir sorun için yeniden kullanmayın.
[Cursor hataları](#cursor-errors) bu rota için de geçerlidir.

## <span id="live-event-response-format">Canlı olay yanıt biçimi</span>

Canlı akış yeni olayları gönderir. İstemcinin bağlantısı kopukken kaçırdığı
olayları yeniden göndermez. Mevcut kayıtları okumak için liste rotalarını
kullanın.

### Bilet oluşturun

Bir hesap bearer tokenıyla `POST /api/feed/ticket` gönderin. İsteğin gövdesi
yoktur.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

`200 OK` yanıtı bileti `ticket` alanında içerir:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Bilet kısa ömürlü bir kimlik bilgisidir. Onu loglamayın veya bir agent
promptuna koymayın. Bağlantıyı `expires_in_seconds` dolmadan açın. Bu süre,
bağlantının ne zamana kadar başlayabileceğini sınırlar. Bağlantının ne kadar
açık kalacağını sınırlamaz.

Bir bilet 60 saniye geçerlidir ve yalnızca bir kez kullanılır. Bir bilet tek bir bağlantı açar. Yeniden bağlanırken de dahil olmak üzere her bağlantı için yeni bir bilet isteyin.

`401`, hesap girişinin geçerli olmadığı anlamına gelir. Bilet istemeden önce
yeniden giriş yapın. `POST` dışında bir yöntem `code: method_not_allowed` ile
`405` döndürür.

### Bağlantıyı açın

Bir WebSocket istemcisini
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>` adresine bağlayın.
Bileti URL kodlamasıyla gönderin. URL'ye hesap bearer tokenı veya alım bearer
tokenı koymayın. `401`, biletin veya hesap girişinin geçerli olmadığı anlamına
gelir. Yeniden giriş yaptıktan sonra yeni bir bilet oluşturun.

Bir hesapta en fazla 10 açık canlı akış bağlantısı olabilir. Tek bir IP adresinde en fazla 20 olabilir. Bu sınırlardan birini aşan bağlantı `429` yanıtı alır.

| Yanıt | Neden | Sonraki adım |
| --- | --- | --- |
| `"error": "feed ticket is required"` ile `422` | `ticket` sorgu değeri eksik veya boş. | Bir bilet oluşturun ve onunla bağlanın. |
| `code: unauthorized` ile `401` | Biletin süresi dolmuş, bilet daha önce kullanılmış veya geçerli değil. | Yeni bir bilet oluşturun. Aynı biletle yeniden denemeyin. |
| `code: rate_limited` ile `429` | Hesabın 10 açık bağlantısı var veya IP adresinin 20 açık bağlantısı var. | Kullanmadığınız bağlantıları kapatın. `retry_after_seconds` (`5` sn) kadar bekleyin. Sonra yeni bir bilet ile bağlanın. |
| `code: invalid_websocket_upgrade` | İstek geçerli bir WebSocket yükseltmesi değil. | Bir WebSocket istemcisi kullanın. |
| `code: method_not_allowed` ile `405` | İstek `GET` kullanmıyor. | Bağlantı için `GET` kullanın. |

Bir hatadan sonra yeniden bağlanmadan önce bekleyin. Ara vermeden döngü
içinde yeniden bağlanmayın.

### Mesajları okuyun

Her mesaj bir `{ "type": "...", "data": ... }` zarfıdır. `data` alanını
ayrıştırmadan önce `type` alanını okuyun. İstemcinin desteklemediği türleri
atlayın.

| Olay türü | Veri yükü |
| --- | --- |
| `native_log` | [Log yanıtı](#log-response) yapısında log verisi. |
| `native_issue` | Sürüm 1 [sorun yanıtı](#issue-response) yapısında gruplanmış sorun verisi. |
| `native_trace_span` | [Span listesi](#span-list) öğesi yapısında tek bir span. |
| `native_action` | [Aksiyon yanıtı](#action-response) yapısında ürün aksiyonu verisi. |
| `project_created`, `project_updated`, `project_catalog_changed` | Proje verisi. Değiştiğinde proje listesini yeniden okuyun. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | [Hesap kullanımı](/tr/reference/account-api#account-usage) yapısında hesap kullanımı. |

```json
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
```

## <span id="issue-status-response-examples">Sorun durumu yanıt örnekleri</span>

`{ "status": "resolved" }` ile `PATCH /api/telemetry/issues/{issue_id}`,
güncellenen gruplanmış sorunla birlikte `200 OK` döndürür. Yapı
[sorun yanıtı](#issue-response) ile aynıdır. Sürümü `response_version` sorgu
anahtarı seçer. Yanıt bir başarı işareti döndürmez.

Gövde `status`, `priority` ve `assignee` alanlarından en az 1'ini ayarlar.
`status`; `unresolved`, `resolved` veya `archived` kabul eder. `ignored`,
`archived` için eski bir addır.
[Tek bir sorunu güncelleyin](/tr/reference/telemetry-api#update-one-issue)
bölümüne bakın.

Başarıyı göstermeden önce dönen `id`, `status` ve `priority` değerlerini
kontrol edin. Sonucu gönderdiğiniz değerlerden oluşturmayın. Durum
değişikliği oluşumları silmez, `first_seen_at` ve `last_seen_at` değerlerini
değiştirmez. `severity` değerini veya bir önem düzeyi kuralını da değiştirmez.

Reddedilen bir değişiklik `code: validation_failed` ile `422` döndürür:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Sonuç | Neden |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Gövdede 3 alandan hiçbiri yok. |
| `422`, `issue priority must be high, medium, or low` | Öncelik değeri desteklenmiyor. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | Sorumlu değeri desteklenmiyor. |
| `422`, `issue assignee cannot read this project` | Sorumlunun projeye erişimi yok. LogBrew hiçbir şeyi değiştirmez. |
| `422`, `issue assignee team is not a team of this project's organization` | Ekip, projenin organizasyonunda değil. LogBrew hiçbir şeyi değiştirmez. |
| `code: forbidden` ile `403` | Hesap projedeki sorunları yönetemiyor. |
| `code: not_found` ile `404` | Hesap sorunu okuyamıyor veya sorun yok. |

İstenen değere zaten sahip olan bir alan değişmez. Zaman aşımından veya
kaybolan bir yanıttan sonra aynı isteği yeniden gönderin ya da önce sorunu
okuyun. Güncel durumu okumadan farklı bir değişiklik göndermeyin.
[Yazma işlemleri](/tr/reference/api-errors#writes) bölümüne bakın.

`POST /api/telemetry/issues/bulk`, istenen her sorun kimliği için 1 sonuçla
`200 OK` döndürür. Sonuçlar istekteki sırayla gelir. Bulunan her sorun sürüm
3 yapısını kullanır. Her sorunu sürüm 4 yapısında almak için gövdeye
`"response_version": 2` ekleyin. `not_found` sonucunda `issue: null` olur:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

Bu örnek sorun alanlarının yalnızca bir kısmını gösterir. `outcome` değeri
`updated`, `unchanged` veya `not_found` olur. Tekrarlanan bir istek
`unchanged` döndürür ve hiçbir şeyi değiştirmez.
[Sorunları toplu güncelleyin](/tr/reference/telemetry-api#update-issues-in-bulk)
bölümüne bakın.

Toplu istek şu durumlarda bütünüyle başarısız olur:

| Sonuç | Neden |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | Liste boş veya 100'den fazla kimlik içeriyor. |
| `422`, `issue_ids must not contain duplicates` | Bir kimlik birden fazla kez geçiyor. |
| `code: invalid_json` ile `422` | Gövdede bilinmeyen bir alan var. |
| `code: forbidden` ile `403` | Hesap projedeki sorunları yönetemiyor. |
| `404`, `project not found` | Hesap projeyi okuyamıyor. |

## Analiz isteği kapsamı

Analiz rotaları, metrik serisi rotası ve sinyal hacmi rotası tek bir projeyi
ve tek bir zaman aralığını okur. Her istek `project_id` ve `since` gerektirir.
`since`, `24h` veya `7d` gibi kısa bir süre ya da bir RFC3339 zaman damgası
kabul eder. `until` bir RFC3339 zaman damgası kabul eder. Varsayılan değeri
istek zamanıdır. Aralık `since` değerini içerir, `until` değerini içermez ve
31 günü aşamaz.

`service_name`, `release` ve `environment` isteğe bağlı tam eşleşme
filtreleridir. LogBrew boşlukları kırptıktan sonra her değer 1 ile 256
karakter arasında olmalıdır. Segment karşılaştırma rotası bu filtreleri en üst
düzeye değil, her segmentin içine koyar.

Hesap projeyi okuyamıyorsa bu rotalar sıfır sayılarla `200 OK` döndürür.
`404` döndürmezler. Boş bir sonuç proje erişimini doğrulamaz. `project_id`
değerini hesabın okuyabildiği projelerle karşılaştırın. Projeyi içermeyen bir
MCP bağlantısı üzerinden yapılan istek `403` ve `forbidden` döndürür.

| Rota | `response_version` değerleri | Varsayılan |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` veya `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` veya `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` veya `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` veya `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` veya `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Kabul edilmez | Şema `1` |
| `POST /api/telemetry/analytics/paths` | Kabul edilmez | Şema `1` |
| `GET /api/telemetry/metrics/series` | Kabul edilmez | Şema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Her yanıt `schema_version`, `query` ve `purpose` ile başlar. `query`, uygulanan
kapsamı geri yansıtır. Göndermediğiniz bir filtreyi içermez. `purpose`,
rotanın neyi yanıtladığını anlatan düz metindir.

Paydası sıfır olan bir oran gönderilmez. Gönderilmeyen oran `0` veya `null`
değildir. Bir orana güvenmeden önce `coverage` alanını okuyun.

### <span id="shared-scope-errors">Ortak kapsam hataları</span>

Bu hatalar HTTP `422` ve `validation_failed` kullanır:

| Neden | `error` |
| --- | --- |
| `project_id` yok | `product analytics project_id is required` |
| `since` yok | `product analytics since is required` |
| `since` bir süre veya RFC3339 zaman damgası değil | `invalid since value` |
| `until` bir RFC3339 zaman damgası değil | `product analytics until must be an RFC3339 timestamp` |
| `since`, `until` değerinden önce değil | `product analytics since must be earlier than until` |
| Aralık 31 günden uzun | `product analytics range must not exceed 31 days` |
| Boş bir filtre veya 256 karakterden uzun bir filtre | `product analytics context filters must be non-empty and at most 256 characters` |

Örneğin `project_id` içermeyen bir istek şunu döndürür:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Metrik serisi ve sinyal hacmi rotaları aynı kapsam kurallarını kendi `error`
metinleriyle kullanır. Bu hatalar aşağıda kendi bölümlerinde listelenir.

Bilinmeyen bir sorgu anahtarı
[geçersiz sorgu parametreleri](/tr/reference/api-errors#invalid-query-parameters)
yanıtıyla `422` döndürür. Bilinmeyen bir JSON alanı, eksik bir zorunlu JSON
alanı veya desteklenmeyen bir enum değeri `invalid_json` döndürür.
[Geçersiz JSON](/tr/reference/api-errors#invalid-json) bölümüne bakın. Yanlış
HTTP yöntemiyle yapılan istek `405` ve `method_not_allowed` döndürür. `next`
metni desteklenen yöntemi ve alanları adlandırır.
[Desteklenmeyen yöntem](/tr/reference/api-errors#unsupported-method)
bölümüne bakın.

## Ürün analizleri genel bakış yanıtı

`GET /api/telemetry/analytics/overview`, tek bir projedeki etkinliği gösterir:
aksiyon hacmi, kullanıcılar, oturumlar, bir zaman serisi, en sık aksiyonlar ve
sınıflandırılmış sayfa görüntülemeleri, ekran görüntülemeleri ve etkileşimler.
Diğer analiz rotaları için tam olay adlarını bulmak üzere bu rotayı kullanın.

`response_version=3` gönderin. Sürüm 1 ve 2 aynı sayıları döndürür, ancak
`estimation.method` alanında eski bir değer döndürür. Sürüm 1, tanımlı kullanıcıları

özneleri sayar. Anonim özne sayılarını ve `subject_coverage` alanını da

### Genel bakışı okuyun

Beş `subject_coverage` sayısının toplamı, bulundukları bölümün olay toplamına
eşittir. Yalnızca `identified_user_events` kullanıcılara sayılır.
`anonymous_actions`, `summary.actions` eksi `identified_actions` değeridir.

`series` yalnızca etkinlik olan zaman dilimlerini içerir. `expected_buckets`,
aralıktaki olası zaman dilimi sayısıdır. Grafiğiniz bu kuralı belirtmiyorsa
eksik bir zaman dilimini ölçülmüş sıfır olarak çizmeyin. Zaman dilimleri UTC
aralık sınırlarına hizalanır. Bir zaman diliminin içinde başlayan aralık, o
kısmi zaman dilimini de içerir.

`classified_activity`; sayfa görüntülemelerini, ekran görüntülemelerini ve
etkileşimleri sayar. Ekran görüntülemeleri ve etkileşimler aynı zamanda
aksiyondur. Sayfa görüntülemeleri aksiyon değildir. `summary.actions` değerini
`classified_activity.summary.events` değerine eklemeyin.

`classified_activity.top_events` içindeki `kind` ve `event_name` değerlerini
dönüşüm hunisi adımlarına, elde tutma seçicilerine, yaşam döngüsü
seçicilerine, yol çapalarına ve segment hedeflerine kopyalayın.
`top_events_truncated` alanındaki `true` değeri, daha az görülen adlar olduğu
anlamına gelir. Daha fazlasını görmek için `top_limit` değerini en fazla 20'ye
kadar artırın.

`analysis_level` değeri `no_data`, `event_only`, `user_level` veya
`user_and_session` olur. Projede aksiyon ve sınıflandırılmış olay yoksa
`next_action.code` değeri `capture_product_activity` olur.
[Ürün analizleri](/tr/concepts/product-analytics#use-the-analytics-api)
sayfasına bakın.

### <span id="overview-errors">Genel bakış hataları</span>

Genel bakış, [ortak kapsam hatalarına](#shared-scope-errors) ek olarak şu
değerler için `422` ve `validation_failed` döndürür:

| Değer | `error` |
| --- | --- |
| `1`, `2` veya `3` dışında bir `response_version` | `product analytics response_version must be 1, 2, or 3` |
| `1` ile `20` dışında bir `top_limit` | `product analytics top_limit must be between 1 and 20` |
| `auto`, `1m`, `5m`, `15m`, `1h`, `6h` veya `1d` dışında bir `interval` | `product analytics interval is not supported` |
| 500'den fazla zaman dilimi gerektiren açık bir `interval` | `product analytics interval would exceed 500 buckets` |

Varsayılan `interval` değeri `auto` olur. En fazla 300 zaman dilimi gerektiren
en küçük aralığı seçer. Varsayılan `top_limit` değeri `10` olur.

`POST /api/telemetry/analytics/funnel`, 2 ila 8 adım boyunca sıralı
tamamlanmayı ölçer. Her `kind` ve `event_name` değerini genel bakıştaki
`classified_activity.top_events` içinden tam olarak kopyalayın. Benzer bir
aksiyon adı eşleşme sayılmaz. Bu istek gövdesi, `/pricing` sayfasını
görüntüleyip ardından bir saat içinde kaydı tamamlayan oturumları sayar:

```json

  "since": "2026-08-01T00:00:00Z",
  "until": "2026-08-02T00:00:00Z",
  "environment": "production",
  "analysis_unit": "session",
  "conversion_window_seconds": 3600,
  "steps": [
    { "kind": "page_view", "event_name": "/pricing" },
```

`analysis_unit` değeri `session` veya `identified_user` olur. Varsayılan
`session` olur. Adım `kind` değeri `page_view`, `screen_view` veya
`interaction` olur. Dönüşüm hunisi rotası `response_version` kabul etmez.

### Dönüşümü ve kapsama oranını okuyun

`entry_rate`, `entered_units` bölü `candidate_units` değeridir: 60'ta 50.
`overall_conversion_rate`, `completed_units` bölü `entered_units` değeridir:
50'de 15, yani %30. 15'in tüm adaylara bölümü değildir. Bu sayılar birimlerin
neden durduğunu açıklamaz.

Kapsama oranı oturumları değil, olayları sayar. Burada 120 olay bir adımla
eşleşir ve bunların 20'sinde oturum kimliği yoktur. Sonuç bu 20 olayı oturum
sayılarının dışında tutar. Bunları başarısız 20 oturum olarak ele almayın.

İlk adımda `conversion_from_previous` yoktur. Son adımda
`drop_off_to_next_units` ve `drop_off_to_next_rate` yoktur.

Bir birim sonraki bir adıma yalnızca adım zamanları kesin olarak artıyorsa
ulaşır. Aynı zaman damgasına sahip olaylar art arda iki adımı karşılayamaz.
Son adım, ilk adımdan sonraki `conversion_window_seconds` içinde
gerçekleşmelidir.

Oturum modu kişileri değil, oturumları sayar. `identified_user` modunu
yalnızca `user` türünde opak bir özne kimliği taşıyan olaylar için kullanın.
Bu mod, dönüşüm süresi içindeki farklı oturumlardan gelen olayları
birleştirebilir. Sonuçları karşılaştırırken aynı birimi ve aynı adımları
koruyun.

Varsayılan `conversion_window_seconds` değeri 24 saat veya aralığın
uzunluğudur; hangisi daha kısaysa o geçerlidir. En büyük değer, tam saniyeye
yukarı yuvarlanmış aralık uzunluğudur.

içermez. Rota, olay eşleşmedi diye `404` döndürmez.

| `next_action.code` | Neden |
| --- | --- |

| `choose_captured_funnel_steps` | İstenen bir adımla eşleşen olay yok. |
| `sessionize_product_activity` | Adım olayları var, ancak hiçbirinde oturum kimliği yok. |
| `identify_product_users` | Adım olayları var, ancak hiçbirinde `user` türünde özne yok. |

### Reddedilen dönüşüm hunisi istekleri

[Ortak kapsam hatalarına](#shared-scope-errors) ek olarak şu istekler `422`
ve `validation_failed` döndürür. 2'den az veya 8'den fazla adım:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`0` olan veya aralık uzunluğunu aşan bir `conversion_window_seconds`:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }

```

Boş, 256 karakterden uzun veya kontrol karakteri içeren bir `event_name`
şunu döndürür:
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Bir `interaction` adımı geçerli bir aksiyon adı da olmalıdır. Değilse hata
`product analytics interaction event_name must be a bounded stable action name`
olur.

İsteği yeniden göndermeden önce düzeltin. Sırf boş olmayan bir sonuç almak
için adımları kaldırmayın veya analiz birimini değiştirmeyin.

## Tam olay ve otomatik analiz

Elde tutma ve yaşam döngüsü iki istek yapısı kabul eder. Sorunuza yanıt veren
yapıyı seçmek için `response_version` kullanın:

| Analiz | `response_version` | Olay seçicileri |
| --- | --- | --- |
| Tam olaylar için elde tutma | `1` veya gönderilmez | Hem `start_event` hem `return_event` gönderin. |
| Tek bir tam olay için yaşam döngüsü | `1` veya gönderilmez | `event` gönderin. |
| Otomatik elde tutma veya yaşam döngüsü | `2` | Olay seçicisi göndermeyin. |

Tam seçici `kind` ve `event_name` içerir. `kind` değeri `page_view`,
`screen_view` veya `interaction` olur. `event_name` değerini
`classified_activity.top_events` içinden kopyalayın. Olay adını bir düğme
etiketinden tahmin etmeyin.

İki yapı da yalnızca kullanıcıları sayar: `user` türündeki opak özne
kimlikleri. Anonim özneler ve kullanılabilir özne kimliği olmayan olaylar
kullanıcı olarak sayılmaz. Yanıtlar hiçbir zaman özne kimliği döndürmez.

Sabit aralıklar `hour`, `day`, `week` ve `thirty_day` olur. Bunlar sabit
sürelerdir. `thirty_day` takvim ayı değil, 30 gündür. `interval`
göndermezseniz API 48 saat veya daha kısa bir aralık için `hour`, daha uzun
bir aralık için `day` kullanır.

`interval: "hour"` ile 30 günlük bir aralıkta 720 kohort zaman dilimi olur.
`interval_count: 1` ile bu 720 hücre eder. Bu da 500'den fazladır:

```json

  "next_action": { "code": "fix_request", "target": "request" }

```

Otomatik elde tutmayı kullanmak için iki seçiciyi de kaldırın. Bu okuma
isteğini düzeltmek için SDK'yı değiştirmeyin.

### Metrik serisini okuyun

İlk nokta 10 ölçüm örneğini değil, tamamlanan 10 işi kaydeder.
`rate_per_second`, bu değişimi 300 saniyelik zaman dilimine böler. `last`
toplam değil, kaydedilen son değişimdir.
[Metrik toplama anlamları](/tr/concepts/telemetry#read-the-metric-value)
bölümüne bakın.

Bir serinin türü ve zamansallığı, onun `aggregation.code` değerini ve her
noktadaki istatistikleri seçer. Nokta, o seriye uygulanamayan bir istatistiği
içermez. Eksik bir istatistik sıfır değildir.

| Tür ve zamansallık | `status` | `aggregation.code` | `value` | Diğer istatistikler |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Son ölçüm örneği | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Değişimlerin toplamı | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | Yaklaşık p95 | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Herhangi bir tür, `cumulative` | `limited` | `raw_cumulative_last` | Son ham ölçüm örneği | `last`, `min`, `max` |
| Diğer tüm çiftler | `limited` | `raw_last` | Son ham ölçüm örneği | `last`, `min`, `max` |

`limited` bir hata değil, başarılı bir yanıttır. LogBrew'ün neden yalnızca ham
değerleri gösterdiğini açıklayan `aggregation.limitation` alanını ekler.
`ready`, yakalamanın eksiksiz olduğunu kanıtlamaz.

Grafik çizmeden önce `coverage` alanını okuyun:

- `samples`, yanıtın döndürmediği seriler dâhil eşleşen tüm serilerin ölçüm
  örneklerini sayar.
- `series` eşleşen serileri sayar. `returned_series` ve `points` dönen veriyi
  sayar.
- `series_limit` daha düşük hacimli serileri çıkardıysa `truncated` değeri
  `true` olur.
- `expected_buckets_per_series`, aralıktaki olası zaman dilimi sayısıdır.

Ölçüm örneği olmayan bir zaman dilimi için nokta eklemeyin. Sıfır eklemeyin
veya önceki değeri kopyalamayın. Her nokta en fazla 3 `trace_exemplars`
döndürür. İz örneği (trace exemplar), tek bir ölçüm örneğini bir ize bağlar.
Zaman dilimindeki her ölçüm örneğini açıklamaz. Hiçbir noktada iz örneği
yoksa `next_action.target` değeri `metric_samples` olur.

### Metrik serisi kapsamı ve hataları

`project_id`, `name` ve `since` zorunludur. `name` en fazla 200 karakter
olabilir. `interval` değeri `auto`, `1m`, `5m`, `15m`, `1h`, `6h` veya `1d`
olur. Varsayılan `auto` olur. Bu değer, en fazla 300 zaman dilimi gerektiren
en küçük aralığı seçer. Açıkça verilen bir aralık 500'den fazla zaman dilimi
gerektiremez.

`group_by` değeri `none`, `service_name`, `release` veya `environment` olur.
Varsayılan `none` olur. Gruplama olmadan farklı türler, birimler ve
zamansallıklar ayrı serilerde kalır. `series_limit`, `1` ile `20` arasında bir
değer kabul eder. Varsayılan `10` olur.

Boş bir sonuç `series: []` ve sıfır `samples` ile `200` döndürür. `coverage`
nesnesi `first_seen_at` ve `last_seen_at` içermez. Bu, uygulamanın metriği hiç
göndermediğini kanıtlamaz. Projeyi, metrik adını ve zaman aralığını kontrol
edin.

`name` gönderilmezse `422` döner:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Yedi gün boyunca bir dakikalık zaman dilimleri `422` döndürür:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Diğer `422` hataları `metric series group_by is not supported`,
`metric series interval is not supported` ve
`metric series_limit must be between 1 and 20` olur.

### Yolları okuyun

`share_of_anchored_sessions`, bir yolun oturumlarını çapalı dört oturumun
tamamına böler. Paylar %67 ve %33 değil, %50 ve %25 olur.
`unrepresented_sessions`, dönen hiçbir yolun temsil etmediği çapalı oturumları
sayar. `paths_truncated: true`, sonucun eksik olduğu anlamına gelir.

Kapsama oranı oturumları değil, olayları sayar. Burada beş olay çapayla
eşleşir, ancak birinde oturum kimliği yoktur. Bu olay bir yola giremez. Her
yol en fazla 3 iz örneği döndürür. Kendi yanıtınızdaki bir iz kimliğini
kullanın. Bir iz bağlantısı, bir kullanıcı aksiyonuna veya bir hataya neyin
yol açtığını göstermez.

| Alan | Anlamı |
| --- | --- |
| `following` | Her oturumdaki en erken eşleşen çapada başlar. Çapanın konumu `0` olur. Sonraki düğümlerin konumları pozitiftir. |
| `preceding` | Her oturumdaki en geç eşleşen çapada biter. Önceki düğümlerin konumları negatiftir. Çapanın konumu `0` olur. |
| `depth` | Çapa sayılmadan, çapanın yanındaki düğüm sayısı. `1` ile `8` arası. Varsayılan `4` olur. Bir yolda daha az düğüm olabilir. |
| `collapse_repeated` | Aynı tür ve ada sahip art arda gelen düğümleri birleştirir. Varsayılan `true` olur. |
| `path_limit` | Oturum sayısına göre sıralanan en fazla dönen yol sayısı. `1` ile `20` arası. Varsayılan `10` olur. |

Düğümler iki yönde de zaman sırasındadır. Yol, oturumun tam bir yeniden
oynatması değildir. LogBrew çapayı seçmeden önce oturum başına en fazla 1024
adlandırılmış olay okur: `following` için en erken olayları, `preceding` için
en geç olayları. Bu sınırın dışındaki bir çapa sonuca girmeyebilir.

### <span id="filter-the-anchor-by-property">Çapayı özelliğe göre filtreleyin</span>

Her biri tek bir tam `key` ve `value` içeren en fazla dört `property_filters`
gönderin. Anahtarı [özellik kataloğundan](#analytics-property-catalog)
kopyalayın. Filtreler yalnızca çapaya uygulanır, çevresindeki olaylara
uygulanmaz. Değerler büyük/küçük harfe duyarlıdır. Filtreler varsa `query`
onları geri yansıtır ve `coverage.anchor_property_filters` şunları bildirir:

| Alan | Anlamı |
| --- | --- |
| `context_events` | Özellik filtrelerinden önce kapsamdaki çapa olayları. |
| `property_ready_events` | İstenen her anahtarı içeren çapa olayları. |
| `missing_property_events` | İstenen anahtarlardan bir veya daha fazlası eksik olan çapa olayları. |
| `matching_events` | Değerleri her filtreyle eşleşen çapa olayları. |
| `nonmatching_value_events` | Her anahtarı içeren ama farklı bir değere sahip çapa olayları. |
| `property_ready_rate` | `property_ready_events` bölü `context_events`. |
| `match_rate` | `matching_events` bölü `property_ready_events`. |

Eksik anahtarlar ve farklı değerler farklı düzeltmeler gerektirir. Bunları
toplamayın. İstekte özellik filtresi yoksa nesne gönderilmez.

### Boş yollar ve reddedilen istekler

Boş bir `paths` dizisi başarılı bir `200` yanıtı olabilir. `summary`,
`coverage` ve `next_action` alanlarını okuyun. Şu kodlar nedenleri ayırır:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` ve
`narrow_or_move_path_anchor`.

[Ortak kapsam hatalarına](#shared-scope-errors) ek olarak şu istekler `422`
ve `validation_failed` döndürür:

| Neden | `error` |
| --- | --- |
| `1` ile `8` dışında bir `depth` | `product analytics path depth must be between 1 and 8` |
| `1` ile `20` dışında bir `path_limit` | `product analytics path_limit must be between 1 and 20` |
| Dörtten fazla özellik filtresi | `product analytics paths accept at most four exact anchor property filters` |
| Özellik kataloğunda olmayan bir anahtar | `product analytics path property keys must be supported privacy-safe keys` |
| Aynı anahtar iki kez | `product analytics path property keys must be unique` |
| Boş bir değer, 256 karakterden uzun bir değer veya kontrol karakteri | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

Örneğin `depth: 0` şunu döndürür:


## <span id="analytics-segment-comparison">Analiz segment karşılaştırması</span>

`POST /api/telemetry/analytics/segments/compare`, tek bir projedeki 2 ila 4
segmentte oturumların veya kullanıcıların tek bir tam olaya ne sıklıkla
ulaştığını karşılaştırır. Bir segment olayları hizmete, sürüme, ortama ve
özellik değerlerine göre seçer. İlk segment temel segmenttir.

### Karşılaştırmayı tanımlayın

Bu JSON gövdesini hesap kimlik doğrulamasıyla ve
`Content-Type: application/json` ile gönderin. Buradaki `basic` ve `premium`,
LogBrew planları değil, örnek uygulamanın plan değerleridir:

```json

  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }
  ]
}
```

`target` ve `segments` zorunludur. `analysis_unit` değeri `session` veya
`identified_user` olur. Varsayılan `session` olur. Bu değer kişileri değil,
oturumları sayar. `interval`, genel bakışla aynı değerleri kabul eder.
Varsayılan `auto` olur.

Her segmentin benzersiz bir `key`, bir `label` ve farklı bir filtre kümesi
olmalıdır:

- `key`: 1 ile 32 bayt arası. Küçük bir ASCII harfiyle veya bir rakamla
  başlayın. Yalnızca küçük ASCII harfleri, rakamlar, `_` ve `-` kullanın.
- `label`: Kontrol karakteri içermeyen 1 ile 80 karakter arası.
- `service_name`, `release`, `environment`: İsteğe bağlı. Her değer kontrol
  karakteri içermeyen 1 ile 256 karakter arasındadır.
- `property_filters`: 0 ile 4 arası filtre. Her anahtar bir segmentte bir kez
  geçebilir. Bir olay segmentin tüm filtreleriyle eşleşmelidir. Değerler
  büyük/küçük harfe duyarlıdır ve 1 ile 256 karakter arasındadır. LogBrew
  baştaki ve sondaki boşlukları kırpar.

Filtresi olmayan bir segment, projedeki ve zaman aralığındaki tüm
sınıflandırılmış etkinliği seçer. Segmentler örtüşebilir. Farklı bir etiket
veya anahtar, birbirinin aynısı iki filtre kümesini geçerli yapmaz.

[yol çapası filtresi kapsama oranı](#filter-the-anchor-by-property) ile aynı
alanlara sahiptir. Burada `matching_events`, `classified_events` değerine
eşittir. Eksik anahtarları ve farklı değerleri ayrı tutun. Segmentler
örtüşebilir ve bir oturum birden fazla zaman diliminde yer alabilir. Birim
sayılarını segmentler veya zaman dilimleri arasında toplamayın.

Karşılaştırma betimleyicidir. `confidence.causal_inference` değeri
`not_established`, `confidence.statistical_significance` değeri `not_tested`
olur. %20'ye karşı %30'luk bir oran, bir planın daha fazla ödemeye yol
açtığını göstermez.

### Segment karşılaştırma hataları

[Ortak kapsam hatalarına](#shared-scope-errors) ek olarak şu istekler `422`
ve `validation_failed` döndürür:

| Neden | `error` |
| --- | --- |
| 2'den az veya 4'ten fazla segment | `product analytics segment comparison requires two through four segments` |
| Aynı anahtara sahip iki segment | `product analytics segment keys must be unique` |
| Aynı filtrelere sahip iki segment | `product analytics segment filters must be unique` |
| İzin verilen 1 ile 32 bayt arasında olmayan bir anahtar | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| Boş, çok uzun veya kontrol karakteri içeren bir etiket | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| Kontrol karakteri içeren bir filtre değeri | `product analytics segment filters must be control-free` |

| Özellik kataloğunda olmayan bir anahtar | `product analytics segment property keys must be supported privacy-safe keys` |

Farklı bir etiket veya özellik filtrelerinin farklı sırası seçilen olayları
değiştirmez. Doğrulama hatası, hiçbir olayın eşleşmediğine dair kanıt

## Sinyal hacmi yanıtı

`GET /api/telemetry/summary/volume`, tek bir proje ve zaman aralığı için
saklanan sinyalleri sayar. `project_id` ve `since` gerektirir. `project_ids`
kabul etmez.

1 ila 50 projeyi birlikte saymak için `GET /api/telemetry/summary/volume/combined`
rotasına `project_ids` ve `since` gönderin. Yanıt aynı yapıdadır. `query`
alanında `project_id` yerine `project_ids` bulunur. Birden fazla seçili projede
span'i olan bir iz bir kez sayılır. Hesap projelerden birini okuyamıyorsa bu rota
`"error": "project selection not found"` ile `404` döndürür.

`until` gelecekte olamaz. Göndermezseniz bitiş, istek zamanı olur. `24h` gibi
kısa bir `since`, `until` zamanından geriye doğru sayar. `interval` değeri
`auto`, `1m`, `5m`, `15m`, `1h`, `6h` veya `1d` olur. Varsayılan `auto`, en
fazla 120 zaman dilimi gerektiren en küçük aralığı seçer. Bir istek 500'den
fazla zaman dilimi gerektiremez. Tek `response_version` değeri `1` olur.

### Boş ve kısalmış aralıklar

Hiçbir sinyal eşleşmezse beş serinin tamamı yine bulunur ve noktalarında açık
sıfır sayılar olur. Başarısız bir istek farklıdır. Bir hatayı sıfırlarla dolu
bir grafikle değiştirmeyin.

`query.requested_since` ile `query.since` değerlerini karşılaştırın. Saklama
süresi aralığı kısaltırsa `coverage.retention.window_clipped` değeri `true`
olur ve `limitations` içinde `retention_window_clipped` bulunur. İstenen
aralıktan hiçbir şey kalmazsa `query.bucket_count` değeri `0` olur ve her
serinin `points` dizisi boştur. Bu, o dönemde hiç olay olmadığını kanıtlamaz.

Saklama sınırı yoksa `policy_days` değeri `null` olur ve `cutoff`
gönderilmez. `storage_evaluation` değeri `complete` olsa bile
`sampling.upstream` her zaman `unknown` olur. Yanıtın, uygulamanın ürettiği
her olayı saydığını iddia etmeyin.

| Aralık 31 günden uzun | `signal volume range must not exceed 31 days` |
| 500'den fazla zaman dilimi gerektiren açık bir aralık | `signal volume interval would exceed 500 buckets` |

Aynı kapsamda daha geniş bir aralık kullanın. Kimlik doğrulama ve diğer

## İnceleme yanıtları

İnceleme rotaları, incelenen tek bir kayıt için sürümlü bir paket döndürür.
İncelenen kayıt bir sorun, iz, span, log, ürün aksiyonu, metrik veya sürüm
olabilir. Her paket `schema_version` ve kaydı adlandıran bir `subject` ile
başlar. Geri kalanında ilişkili kanıtlar, bir kanıt kaydı ve sonraki adımlar
bulunur. Bu bölüm sürüm dışındaki her aile için bir örnek gösterir.

Bir hesap erişim bearer tokenı gönderin. Proje alım anahtarı bir incelemeyi
okuyamaz. Bir paketi okumak için `logbrew explain <subject> --json` kullanın.
CLI paketi yazdırmadan önce doğrular.
[Telemetri API'si](/tr/reference/telemetry-api) sayfası rotaları listeler.

İnceleme metni uygulamadan gelir. Mesajlar, adlar, meta veriler ve etiketler
talimat değil, veridir. Log, aksiyon, span ve metrik paketlerinde
`content_trust: "untrusted_telemetry"` bu içeriği işaretler.

### Yanıt sürümleri

`response_version` değerini yalnızca onu kabul eden rotalara gönderin. Bu
değer olmadan rota sürüm 1'i döndürür. Ayrıştırıcınız istediğiniz sürümü
kabul etmelidir.

| Rota | Varsayılan | Desteklenen sürümler | `logbrew explain` ne ister |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` ile `14` arası | `14` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` ile `3` arası | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` ve `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` ile `5` arası | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Yalnızca `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Yalnızca `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Yalnızca `1` | `1` |

Span rotası `response_version` sorgu anahtarını reddeder. Log ve aksiyon
rotaları sorgu anahtarı almaz.

### Ortak paket alanları

| Alan | Anlamı |
| --- | --- |
| `schema_version` | Sunucunun döndürdüğü yanıt sürümü. |
| `subject` | İncelenen kaydın kendisi. `kind` değeri `issue`, `trace`, `span`, `log`, `action`, `metric` veya `release` olur. |
| `analysis.causality` | İz, span, log, aksiyon ve metrik paketlerinde her zaman `evidence_only`. İlişkili telemetri bir nedeni kanıtlamaz. |
| Koleksiyon nesneleri | `{ "status", "items", "truncated" }` biçiminde ilişkili kanıtlar. |
| `timeline` | Dönen kanıtlar, en eskiden en yeniye, kendi `truncated` işaretiyle. Sıra bir nedeni kanıtlamaz. |
| `evidence` | Kanıt kaydı. `status` değeri `complete` veya `partial` olur. |
| `next_actions` | `1` ile başlayan `priority` sırasında önerilen okumalar. Henüz çalıştırılmamışlardır. |

Her ilişkili koleksiyon tek bir erişilebilirlik `status` değeri bildirir:

| Durum | Anlamı | İstemci davranışı |
| --- | --- | --- |
| `available` | Okuma tamamlandı ve öğeler döndü. | Öğeleri ve `truncated` işaretini gösterin. |
| `not_linked` | Kayıtta bu bağlantı için iz kimliği gibi bir tanımlayıcı yok. | Eksik bağlantıyı açıklayın. Zaman damgalarından bağlantı oluşturmayın. |
| `not_found` | Okuma tamamlandı ve saklanan kanıt bulamadı. | Boş bir sonuç gösterin. |
| `unavailable` | İsteğe bağlı okuma başarısız oldu. Kayıt yine geçerlidir. | Kaydı görünür tutun. Daha sonra yeniden deneyin. Sonuç olarak sıfır öğe göstermeyin. |

Kanıt kaydında sabit alan adlarından oluşan dört sıralı liste vardır:
`captured_fields`, `missing_fields`, `redacted_fields` ve
`truncated_fields`. `status` yalnızca son üç liste boşsa `complete` olur.
Gizlenmiş veri eksik veri değildir. Kısaltılmış veri eksiksiz veri değildir.
Gizlenmiş veya kısaltılmış bir değeri doldurmayın.

### İnceleme sınırları

Bu sınırlar tek bir yanıtı sınırlar. Bir `truncated` işareti veya bir
`truncated_fields` girdisi, bir sınırın veriyi dışarıda bıraktığını gösterir.

| Kanıt | Sınır |
| --- | --- |
| Tek bir koleksiyondaki ilişkili öğeler | 20 |
| Tek bir iz için okunan saklanmış span'ler | 1,000 |
| Zaman çizelgesi öğeleri | Log, aksiyon ve span paketleri için 50. İz ve metrik paketleri için 100. |
| Yapılandırılmış öznitelikler, özellikler ve meta veriler | 64 skaler değer, 4 düzey nesne veya dizi, her dizide 16 öğe, her dizede 512 karakter |
| İlişki zaman aralığı | Bir logdan, aksiyondan veya seçilen sorun oluşumundan 5 dakika önce ve sonra. Bir iz veya span için başlangıçtan 5 dakika önce ve bitişten 5 dakika sonra, en fazla 24 saat. |

Her ailenin bölümü kendi sınırlarını listeler.

### Sorun incelemesi yanıtı

Gruplanmış bir sorunun tek bir oluşumuna ait kanıtları okumak için

`null` olarak okumayın.

`subject.status` ve `lifecycle` durumları, arşivlenmiş bir sorunu `ignored`
olarak bildirir. Sorun listesi ve ayrıntı yanıtları, yanıt sürümü 2 ve
sonrasında `archived` kullanır.

Sorun sınırları: Öneri en fazla 50 saklanmış oluşum okur. Eğilimde en fazla
30 zaman dilimi olur. Her dağılım en fazla 10 değer döndürür. Bir yığında en
fazla 32 çerçeve olur.

#### Sorun incelemesi istek hataları

`selection` veya `occurrence_id` değerlerinden yalnızca birini kullanın. Aynı
oluşumu seçseler bile ikisini birlikte göndermeyin:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Neden | Kurtarma |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | İstekte iki seçici de var. | Tek bir seçici bırakın. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | İstekte seçiciyle birlikte sürüm 1 var veya sürüm yok. | `response_version=14` gönderin. Seçiciyi koruyun. |
| `422` | `issue investigation response_version must be 1 through 14` | Sürüm aralığın dışında. | Desteklenen bir sürüm gönderin. |
| `422` | `invalid query parameters` | Bilinmeyen bir anahtar, geçersiz bir UUID, tam sayı olmayan bir sürüm veya bilinmeyen bir `selection` değeri. | [Sorguyu](/tr/reference/api-errors#invalid-query-parameters) düzeltin. |
| `404` | `issue occurrence not found` | Oluşum bu grubun saklanan geçmişinde yok. | Oluşum kimliğini bu sorunun olaylarından kopyalayın. Onay almadan yerine `latest` veya `recommended` kullanmayın. |
| `404` | `issue not found` | Okunabilir hiçbir projede bu sorun yok. | Hesabı ve sorun UUID'sini kontrol edin. Sorun kimliği olarak bir oluşum UUID'si göndermeyin. |

Eksik bir oluşum, sorunun eksik olduğu anlamına gelmez. `404`, başka bir
hesabın sorunu okuyup okuyamadığını göstermez.

### İz incelemesi yanıtı

Tek bir izi hata yolu, en yavaş yolu ve ilişkili sinyalleriyle okumak için
`GET /api/telemetry/traces/{trace_id}/investigation` kullanın. Sorgu
anahtarları `response_version`, `project_id`, `release` ve `environment`
olur. Hepsi isteğe bağlıdır. Sürüm 3'ü isteyin:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

Sürüm 2, ilişkili her soruna `cause` ve `fix` ekler. Sürüm 3, yakalandıysa
ilişkili sorunlara, aksiyonlara ve metriklere `span_id` ekler.

`environment` ve `release` değerleriyle gönderin.

### Span incelemesi yanıtı

Bir izdeki tek bir işlemi okumak için
`GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation`
kullanın. `project_id`, `environment` ve `release` gönderin. Üçü de
zorunludur. Bunları seçilen span'den kopyalayın. Span satırının `id` değerini
`span_id` olarak göndermeyin.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### Log incelemesi yanıtı

Tek bir logu ve ilişkili kanıtlarını okumak için
`GET /api/logs/{log_id}/investigation` kullanın. Bu rotanın sorgu anahtarı
yoktur. Log kimliğini bir log listesinden kopyalayın.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

Okuma, log listesinin filtreleri dışında kalan kanıtları da döndürebilir.
İlişkili okumalar logun projesini, ortamını ve sürümünü ve logdan 5 dakika
önce ve sonrasını kullanır. Yakındaki loglar aynı hizmeti de kullanır. Bunlar
için iz kimliği gerekmez. Tam iz okumaları logun iz kimliğini gerektirir ve
başka hizmetleri de içerebilir. İz özeti aynı iz kimliğini ve kapsamı, zaman
aralığı olmadan kullanır.

### Metrik incelemesi yanıtı

Tek bir projede ve zaman aralığında tek bir metrik adını okumak için
`GET /api/telemetry/metrics/investigation` kullanın. Yanıtta güncel seri, eşit

```bash
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
```

### İnceleme hataları

| HTTP | Rota | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Aksiyon | `action not found` |
| `404` | İz | `trace not found` |
| `422` | İz | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, aksiyon, sorun | Yol kimliği bir UUID değilse `invalid URL path parameters` |
| `422` | Sorun, iz, span, metrik | Bilinmeyen bir anahtar veya yanlış türde bir değer için `invalid query parameters` |

`404`, okunabilir hiçbir projede kaydın olmadığı anlamına gelir. Her rota
geçerli kimlik doğrulama olmadan `401`, `GET` dışındaki bir yöntem için `405`
de döndürür.
[Bulunamadı](/tr/reference/api-errors#resource-not-found),
[yol](/tr/reference/api-errors#invalid-path-value),
[kimlik doğrulama](/tr/reference/api-errors#authentication-failure) ve
[yöntem](/tr/reference/api-errors#unsupported-method) yanıtları için
[API hataları](/tr/reference/api-errors) sayfasına bakın.

İsteğe bağlı bir kanıt okuması `200 OK` yanıtının içinde başarısız olabilir.
Bu durumda koleksiyon `unavailable` bildirir. Bunu `not_found` veya sıfır
kayıt olarak göstermeyin.

## <span id="severity-values">Önem düzeyi değerleri</span>

Kullanıcıya gösterilen önem düzeyi değerleri `info`, `warning`, `error` ve
`critical` olur. SDK'lar ve çalışma ortamları `trace`, `debug`, `warn` veya
`fatal` gibi yaygın eş adlar gönderebilir. REST ve canlı yanıtlar her zaman
standart değeri döndürür. Örneğin LogBrew girdi olarak `warn` kabul eder ve
`warning` döndürür. Veri alımı bilinmeyen önem düzeyi değerlerini reddeder.

| Eş ad | Standart değer |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Önem düzeyi kuralı yanıtları</span>

Önem düzeyi kuralı, LogBrew'ün bir logu veya sorunu nasıl gösterdiğini
değiştirir. Uygulamanın yakaladığı önem düzeyini değiştirmez. Loglar ve
sorunlar bir `triage` nesnesi döndürür:

| Alan | Anlamı |
| --- | --- |
| `effective_severity` | Gösterilecek önem düzeyi. Kural yoksa `severity` değerine eşittir. |
| `ignored` | Bir log kuralı logu yok sayıyorsa veya sorun arşivlenmişse `true`. |
| `rule_applied` | Bir önem düzeyi kuralı veya yok sayılma durumu uygulanıyorsa `true`. `false` varsayılandır, eksik veri değildir. |

Gösterim için `triage.effective_severity` kullanın. `severity` değerini
yakalanan değer olarak koruyun. Log listesi varsayılan olarak yok sayılan
logları içermez. Onları da almak için `GET /api/logs` üzerinde
`status=ignored` veya `status=all` gönderin.

Hesabın projedeki sorunları yönetme izni olmalıdır. Okuma erişimi yeterli
değildir. Bu izin olmadan kural değişikliği `code: forbidden` ile `403`
döndürür.

### Log kuralını değiştirin

`PUT /api/logs/{log_id}/triage-rule`, kuralı bu log ve aynı imzaya sahip
sonraki loglar için ayarlar. Gövdede hem `severity` hem `ignored`
bulunmalıdır:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

`200 OK` yanıtı [logun](#log-response) tamamını içerir. Logun `severity`
değeri `warning` olarak kalır. `triage` alanı kuralı gösterir:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Bu alıntı yalnızca değişen alanları gösterir. İstekteki `severity` değeri
`source`, `info`, `warning`, `error` veya `critical` olur. `source`,
yakalanan önem düzeyini geri getirir. Yok sayılan bir logu etkin yapmaz. Logu
yeniden göstermek için `"ignored": false` gönderin.

### Sorun kuralını değiştirin

`PUT /api/telemetry/issues/{issue_id}/triage-rule`, gruplanmış bir sorunun ve
sonraki oluşumlarının gösterilen önem düzeyini ayarlar. Gövde yalnızca
`severity` kabul eder:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

`200 OK` yanıtı, sürüm 1'deki [sorunun](#issue-response) tamamını içerir.
Yakalanan `severity` ve `status` değerleri değişmez:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Bu alıntı alanların yalnızca bir kısmını gösterir. Kural bir sorunu çözmez,
arşivlemez veya yeniden açmaz. Bunun için
[durum değişikliğini](#issue-status-response-examples) kullanın. Türetilen
öncelik yeni uygulanan önem düzeyini izler. Görmek için sorunu
`response_version=2` veya sonrasıyla okuyun.

Desteklenmeyen bir önem düzeyi `422` döndürür:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Bir sorun kuralındaki `status` gibi bilinmeyen bir gövde alanı
`code: invalid_json` ile `422` döndürür. Eksik veya okunamayan bir log ya da
sorun `code: not_found` ile `404` döndürür. Yanıt kaybolursa kuralı yeniden
göndermeden önce logu veya sorunu yeniden okuyun.

## Hata yanıt biçimi

LogBrew API hataları bir JSON zarfı döndürür. Bu örnek reddedilen bir isteği
gösterir. `error` ve `next` metni soruna göre değişir:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Program dalları için `code`, otomasyon için `next_action` kullanın. `error` ve
`next` değerlerini kişilere düz metin olarak gösterin. İfadelerini
ayrıştırmayın. Bazı hatalar `limit`, `reset_at` veya `retry_after_seconds`
gibi alanlar ekler. JSON gövdesi olmayan bir yanıtta LogBrew `code` değeri
yoktur. Tüm kodlar için [API hataları](/tr/reference/api-errors) sayfasına
bakın.

## CLI ile veri okuyun

CLI aynı rotaları okur ve `--json` ile aynı JSON'u döndürür. Geniş başlayın,
ardından daraltın:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Cursor zarfını almak için `--pagination cursor` ekleyin. CLI sorun yanıtı
sürüm 4'ü ister. [Sonraki sayfayı okuyun](/tr/reference/cli#read-the-next-page)
ve [Canlı izleme](/tr/reference/cli#live-watch) bölümlerine bakın.

Questa pagina mostra un esempio per ogni famiglia di risposte della
[API di telemetria](/it/reference/telemetry-api). Tutti i valori sono fittizi. Per i
codici di errore e il ripristino, vedi [Errori API](/it/reference/api-errors).

## Leggi una risposta

Leggi ogni risposta in questo ordine:

1. Leggi lo stato HTTP.
2. Verifica che il corpo abbia la forma prevista dalla route.
3. Verifica che ogni `project_id` rientri nell'ambito di progetti richiesto.
4. Lascia invariati i valori enum canonici e gli identificatori.
5. Segui `next_action` solo se il client supporta il suo `code` e il suo
   `target`.
6. Tratta `null`, un campo omesso e una lista vuota come stati diversi.

Un `200 OK` può contenere una lista vuota. Una lista di log vuota significa
che nessun log corrisponde alla richiesta. Non significa che anche problemi,
tracce o azioni siano vuoti. Non collegare segnali solo perché i loro
timestamp sono vicini. Segui una traccia solo quando la risposta contiene il
suo `trace_id` esatto.

Un `404` e una lista vuota sono risultati diversi. Una route di lista
restituisce `[]` quando nessun record corrisponde. Una route di dettaglio
restituisce `404` con `code: not_found` quando non trova un record leggibile.
Nessuno dei due risultati dimostra che l'ingestione non è riuscita.

## Cosa inviare

Le risposte sono utili quanto la telemetria che invii. Invia questi valori in
ogni envelope o configurazione dell'SDK:

- `release` e `environment`.
- Nomi stabili per servizi, azioni e metriche.
- Il contesto di traccia quando log, span, azioni e problemi appartengono alla
  stessa richiesta.
- Valori di gravità canonici: `info`, `warning`, `error` e `critical`.
- Attributi utili al debug, senza segreti né dati personali superflui.

Vedi [Invia telemetria con l'SDK](/it/guides/sdk-ingestion) e
[Controlla i dati acquisiti](/it/guides/safe-capture).

## Risposta di ingestione

Gli SDK pubblici leggono la risposta di `POST /v1/events` al posto tuo. Il
codice dell'applicazione non deve gestirla.

### Risposta a un batch dell'SDK

Un batch dell'SDK riuscito restituisce `200 OK` con il numero di elementi
accettati per ogni flusso:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Campo | Significato |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Eventi di questo batch accettati da LogBrew. |
| `already_accepted` | Eventi con un ID che LogBrew ha già accettato in precedenza. LogBrew non li memorizza di nuovo. |
| `context_updated` | `true` quando il batch ha aggiornato il contesto di release o di ambiente. |

I conteggi riguardano solo questo batch. Un nuovo tentativo con un batch che
LogBrew ha già accettato restituisce `0` per ogni flusso e il numero di eventi
in `already_accepted`. Mantieni gli ID originali degli eventi quando riprovi.

### Risposta all'envelope nativo

`POST /api/telemetry/ingest` restituisce `200 OK` con il numero di elementi
accettati per ogni flusso:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

La risposta nativa non ha i campi `metrics` e `context_updated`. Non
aggiungerli. `already_accepted` conta gli elementi il cui `id` LogBrew ha già
accettato in precedenza per il progetto. Vedi l'[envelope nativo diretto](/it/guides/sdk-ingestion#required-envelope-fields).

### Errori di ingestione

Un `401` con `code: ingest_key_invalid` significa che il token bearer di
ingestione è revocato, scaduto o non valido per il progetto. Su
`POST /v1/events`, un token bearer mancante o che non è una chiave di
ingestione restituisce `401` con `code: unauthorized`. Usa il token bearer di
ingestione attuale, limitato al progetto. Non riprovare con un token bearer
dell'account.

Un batch dell'SDK rifiutato restituisce `422` con `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Altri valori di `error` sono `SDK event batch requires at least one event` e
`SDK event type is not supported by this ingest route`. Controlla la versione
dell'SDK e la configurazione del trasporto. Non inviare un batch vuoto. Non
cambiare tipi o ID degli eventi solo per far superare la validazione al batch.

Una richiesta con un metodo diverso da `POST` restituisce `405` con
`code: method_not_allowed`. Un corpo JSON illeggibile restituisce
`code: invalid_json`.

## Formato delle risposte di lista della telemetria

Per impostazione predefinita, le route di lista restituiscono un array JSON
semplice. Una lista vuota riuscita è `[]`.

Con `pagination=cursor`, la route restituisce un envelope. La chiave della
collezione corrisponde al segnale:

| Route | Chiave della collezione |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, con un `issue_id` di primo livello |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, con un `naming_quality` di primo livello |

`next_cursor` è un oggetto con i campi per continuare, oppure `null`
sull'ultima pagina. Le righe vanno dalla più recente alla meno recente. Vedi
[paginazione con cursore](/it/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Risposta dei log</span>

Una pagina con cursore di log con `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

I log includono `level` per compatibilità e `severity` per la
visualizzazione. Entrambi contengono il valore canonico. `triage` contiene il
risultato di una regola di gravità. Vedi
[risposte delle regole di gravità](#severity-rule-responses).

`trace_id` e `span_id` sono `null` quando il log non ha un collegamento a una
traccia. In quel caso `next_action` è `inspect_related_logs` con target
`telemetry_logs`. Log, problemi e azioni usano le stesse 2 coppie di
`next_action`.

`GET /api/logs/{log_id}` restituisce un log con la stessa forma.

### <span id="issue-response">Risposta dei problemi</span>

`GET /api/telemetry/issues/{issue_id}` restituisce un problema raggruppato. La
lista restituisce gli stessi oggetti. Questo esempio usa la versione di
risposta predefinita 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

Nella versione 1, `status` è `unresolved`, `resolved` o `ignored`. Per un
problema archiviato, `triage.ignored` è `true`. Per le coppie di `next_action`
e le letture che seguono, vedi
[Indaga su un problema](/it/guides/investigate-an-issue).

`first_seen_at` e `last_seen_at` sono gli orari della prima e dell'ultima
occorrenza. Non cambiano quando cambia lo stato.

Alcuni campi compaiono solo quando LogBrew ha i dati:

| Campo | Quando compare |
| --- | --- |
| `span_id` | Il problema ha un collegamento a uno span. Altrimenti il campo è omesso. |
| `diagnostics` | L'ultima occorrenza ha un tipo di eccezione o dei breadcrumb. Vedi [cronologia delle occorrenze di un problema](#issue-occurrence-history). |
| `symbolication` | Solo su `GET /api/telemetry/issues/{issue_id}`, quando il problema ha un'identità di artefatto di release. Vedi [Source map](/it/guides/source-maps). |

`symbolication.status` è `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` o `unavailable`. La lista, i
cambi di stato e le modifiche alle regole non restituiscono `symbolication`.

Con `response_version=2`, il problema ha gli stessi campi, con queste
modifiche:

| Campo | Valore nella versione 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` o `archived`. La versione 1 mostra `archived` come `ignored`. |
| `priority` | `high`, `medium` o `low`. |
| `priority_source` | `manual` quando una persona ha impostato la priorità. `derived` quando la priorità segue la gravità effettiva. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Questo esempio mostra solo alcuni campi. Una priorità derivata è `high` per
`error` e `critical`, `medium` per `warning` e `low` per `info`. Usa
`triage.effective_severity`, quindi una regola di gravità per i problemi può
cambiarla.

Con `response_version=3`, il problema ha tutti i campi della versione 2 e
`assignee`. `assignee` è `null` quando il problema non ha un assegnatario:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Campo | Significato |
| --- | --- |
| `assignee.user_id` | ID utente dell'assegnatario. Invialo come `assignee` in un filtro o in una modifica. |
| `assignee.name` | Nome dell'assegnatario, oppure `null` quando l'account non ha un nome. |
| `assignee.email` | Indirizzo email dell'assegnatario. |

Un problema non mostra alcun assegnatario quando il membro assegnato non può
più leggere il progetto.

Con `response_version=4`, `assignee` ha anche `type`. Un assegnatario `user`
ha `user_id`, `name` ed `email`, come nella versione 3. Un assegnatario `team`
ha `team_id`, `slug` e `name`. La versione 3 mostra un team assegnatario come
`null`. La CLI richiede la versione 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Qualsiasi altro `response_version` restituisce `422` con
`code: validation_failed`. Una pagina con cursore usa la stessa versione per
ogni problema in `issues`.

### <span id="assignee-list-response">Risposta della lista degli assegnatari</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` restituisce ogni
account a cui si possono assegnare problemi nel progetto:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Aggiungi `response_version=2` per ottenere anche `teams`: ogni team
dell'organizzazione del progetto, con `team_id`, `slug` e `name`.

Se l'account non può leggere il progetto, la route restituisce `404` con
`code: not_found`.

### <span id="action-response">Risposta delle azioni</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` segue un attore o una sessione. Tratta `distinct_id` e
`session_id` come identificatori opachi. `session_id` e `trace_id` sono `null`
quando mancano. `span_id` è omesso quando manca. Un'azione non ha gravità.
Vedi [Eventi di prodotto](/it/guides/product-events).

### Risposta delle metriche

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Ogni elemento è un campione. Non usare il numero di campioni come conteggio di
eventi o di utenti. `unit`, `temporality`, `trace_id` e `span_id` sono `null`
quando mancano. Un valore `null` non è zero.

### Risposta delle release

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Una riga copre un progetto, una release, un ambiente e un servizio. I suoi
conteggi descrivono solo quella riga.

`trace_health.status` è `unknown` quando la riga non ha tracce, altrimenti
`no_errors_observed` o `errors_observed`. `error_rate_basis_points` è la quota
di tracce con uno span di errore, da `0` a `10000`. Non è un tasso di errore
su tutte le richieste.

`next_action` punta al primo tipo di segnale che ha dati, in questo ordine:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Vedi [Release](/it/concepts/releases).

### Risposta della ricerca di tracce

`GET /api/telemetry/traces?pagination=cursor` restituisce una riga per ogni
traccia, più un resoconto `naming_quality` per la pagina restituita:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` copre solo la pagina restituita. Non è un punteggio
dell'intero account. `truncated: true` significa che esiste un'altra pagina.
Quando la pagina ha un nome generico, una route non riconosciuta o
un'operazione generica, `next_action` è `improve_trace_naming` con target
`sdk_configuration`. Senza `pagination=cursor`, la route restituisce un array
semplice di tracce, senza `naming_quality`.

`next_cursor` contiene `time` e `trace_id`. Inviali come `cursor_time` e
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` restituisce gli span di una traccia.
`GET /api/telemetry/traces/{trace_id}/summary` restituisce lo span radice, gli
span di errore, i servizi, la durata e il percorso più lento, senza gli
attributi grezzi degli span. Un `404` sul riepilogo significa che nessuna
traccia corrisponde all'ambito completo. Non riprovare senza i filtri. Vedi
[risposte degli span e del riepilogo di una traccia](#trace-spans-and-summary-responses).

### Liste vuote e record mancanti

Una lettura di lista può non avere corrispondenze. Una lettura di dettaglio
segue un contratto diverso:

| Richiesta | Successo | Nessun record leggibile |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` con un [log](#log-response) | `404` con `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` con un [problema](#issue-response) | `404` con `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` con le occorrenze | `404` con `code: not_found` sulla prima pagina |
| `GET /api/telemetry/traces/{trace_id}` | `200` con gli span | `200` con `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` con un riepilogo | `404` con `code: not_found` |

Un log mancante restituisce questo `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Un problema mancante usa `"error": "issue not found"`. Un riepilogo di traccia
mancante usa `"error": "trace not found"`. Un ID sconosciuto e un ID che
l'account non può leggere restituiscono la stessa risposta.

Una lista con un `project_id` che l'account non può leggere restituisce `200`
con una lista vuota. Controlla l'ID del progetto prima di segnalare che non
esistono dati.

### Selezioni di progetti rifiutate

Le liste di log, problemi, azioni, metriche, release e tracce accettano un
progetto con `project_id` oppure da 2 a 50 progetti con `project_ids`. Il
catalogo degli attributi dei log accetta gli stessi selettori. La cronologia
delle occorrenze di un problema non li accetta.

Una richiesta con sia `project_id` sia `project_ids` restituisce `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Anche `project_ids` con un UUID non valido, un ID ripetuto, meno di 2 o più di
50 ID restituisce `422` con `code: validation_failed`.

Se l'account non può leggere uno dei progetti di un insieme `project_ids`,
l'intera richiesta restituisce `404`. Non restituisce gli altri progetti come
risultato parziale:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Mostra l'errore, non una lista vuota o un conteggio pari a zero. Leggi di
nuovo la lista dei progetti. Non rimuovere un progetto in silenzio e non
riprovare su tutti i progetti. Una credenziale delegata, come una connessione
MCP, restituisce `403` con `code: forbidden` per un progetto fuori dalla sua
connessione. Vedi
[ambito del progetto](/it/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Errori del cursore</span>

Log, problemi, azioni, metriche e occorrenze dei problemi usano `cursor_time` e
`cursor_id`. Un cursore rifiutato restituisce `422` con
`code: validation_failed`. Questi errori non significano che la lista sia
vuota.

| Richiesta | `error` |
| --- | --- |
| `pagination=cursor` con solo 1 dei 2 campi del cursore | `cursor_time and cursor_id must be sent together` |
| `cursor_time` che non è un timestamp RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Campi del cursore senza `pagination=cursor`, oppure con un altro valore di `pagination` | `pagination must be cursor when cursor pagination is requested` |

Per esempio:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Copia l'intero `next_cursor` dalla pagina precedente. Non sostituire
`cursor_time` con l'ora attuale. Se hai perso il cursore, ricomincia con
`pagination=cursor` e i filtri originali. Una chiave di query sconosciuta o un
valore del tipo sbagliato restituisce `422` con
`"error": "invalid query parameters"`.

### Risposte del cursore delle release

Un cursore delle release ha 5 campi. Una richiesta riuscita senza
corrispondenze restituisce `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Quando `next_cursor` non è `null`, invia tutti e 5 i valori nella richiesta
successiva:

| Campo di `next_cursor` | Parametro di query |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` indica una posizione. Non sostituisce `project_id` o
`project_ids`. Mantieni i parametri originali di progetto e di filtro. Codifica
ogni valore per l'URL.

Con `pagination=cursor`, un cursore parziale o un valore vuoto per release,
ambiente o servizio restituisce `422` con
`"error": "all release cursor fields must be sent together"`. Un
`cursor_time` non valido e un `pagination=cursor` mancante restituiscono gli
stessi errori degli [altri cursori](#cursor-errors).

### Errori della ricerca di tracce

Questi errori riguardano `GET /api/telemetry/traces`. Ognuno restituisce `422`
con `code: validation_failed`. Una richiesta rifiutata non è un risultato
vuoto.

| Richiesta | `error` |
| --- | --- |
| `status` diverso da `error` o `ok` | `trace status must be error or ok` |
| `min_duration_ms` sotto `0` | `minimum trace duration must not be negative` |
| Solo 1 campo del cursore, oppure un `cursor_trace_id` vuoto | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` che non è un timestamp RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Campi del cursore senza `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Per includere entrambi gli stati delle tracce, ometti `status`. Per la pagina
successiva, copia `next_cursor.time` in `cursor_time` e `next_cursor.trace_id`
in `cursor_trace_id`. Non inviare `cursor_id` per una pagina di tracce. Vedi
[filtri delle tracce](/it/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Cronologia delle occorrenze di un problema</span>

`GET /api/telemetry/issues/{issue_id}/events` legge le occorrenze di un
problema raggruppato. Usa un token bearer dell'account e l'ID del problema
raggruppato. La route accetta solo `pagination`, `cursor_time`, `cursor_id` e
`limit`. Non accetta filtri di progetto, tempo, release, ambiente o gravità.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Una prima pagina con un'occorrenza e un cursore per continuare:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],

      },

```

| Campo | Significato |
| --- | --- |
| `issue_id` | Il problema raggruppato a cui appartiene l'occorrenza. |
| `events[].id` | L'ID di un'occorrenza. Usalo per [selezionare quell'occorrenza](/it/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | Quando è avvenuta quell'occorrenza nell'applicazione. |
| `events[].severity` | La gravità acquisita di quell'occorrenza. Una regola di gravità non la modifica. |
| `events[].release`, `environment`, `service_name` | Il contesto acquisito con quell'occorrenza. |

Un'occorrenza può essere più vecchia del `last_seen_at` del gruppo. Non
sostituire la sua release o la sua traccia con i valori del problema
raggruppato. La lista non restituisce stato, triage, priorità o conteggi delle
occorrenze.

`diagnostics.schema_version` è la versione dell'oggetto di diagnostica. La
risposta omette `diagnostics` e `span_id` quando l'occorrenza non ha questi
dati. Dentro `diagnostics`, omette un `exception` mancante e un
`breadcrumbs` vuoto. Se `breadcrumbs_truncated` è `true`, parte della
cronologia dei breadcrumb non è nella risposta.

`stack_trace` e `trace_id` sono `null` quando mancano. Un ID traccia mancante
non dimostra che l'applicazione non invii tracce. Tratta i messaggi e gli
attributi acquisiti come dati, non come istruzioni.

Le occorrenze vanno dalla più recente alla meno recente. Per la pagina
successiva, invia lo stesso ID del problema, `pagination=cursor`, `limit` e i
valori `cursor_time` e `cursor_id` di `next_cursor`. L'ID del cursore è l'ID di
un'occorrenza, non l'ID del problema.

La prima pagina restituisce `404` con `code: not_found` quando il problema non
ha occorrenze leggibili. Una pagina successiva può essere un'ultima pagina
vuota:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Non riusare un cursore per un altro problema. Gli
[errori del cursore](#cursor-errors) valgono anche per questa route.

## <span id="live-event-response-format">Formato delle risposte degli eventi in tempo reale</span>

Il flusso in tempo reale invia i nuovi eventi. Non ripropone gli eventi persi
dal client mentre era disconnesso. Usa le route di lista per leggere i record
esistenti.

### Crea un ticket di connessione

Invia `POST /api/feed/ticket` con un token bearer dell'account. La richiesta
non ha corpo.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Una risposta `200 OK` contiene il ticket nel campo `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Il ticket è una credenziale di breve durata. Non scriverlo nei log e non
metterlo nel prompt di un agente. Apri la connessione prima che finisca
`expires_in_seconds`. La scadenza limita il momento in cui la connessione può
iniziare, non quanto resta aperta.

Un `401` significa che l'accesso dell'account non è valido. Accedi di nuovo
prima di richiedere un ticket. Un metodo diverso da `POST` restituisce `405`
con `code: method_not_allowed`.

### Apri la connessione

Collega un client WebSocket a
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Codifica il ticket
per l'URL. Non mettere nell'URL un token bearer dell'account o un token bearer
di ingestione. Un `401` significa che il ticket o l'accesso dell'account non
è valido. Crea un nuovo ticket dopo aver eseguito di nuovo l'accesso.

| Risposta | Causa | Passo successivo |
| --- | --- | --- |
| `422` con `"error": "feed ticket is required"` | Il valore di query `ticket` manca o è vuoto. | Crea un ticket e connettiti con quello. |
| `401` con `code: unauthorized` | Il ticket è scaduto o non è valido. | Crea un nuovo ticket. Non riprovare con lo stesso ticket. |
| `code: invalid_websocket_upgrade` | La richiesta non è un upgrade WebSocket valido. | Usa un client WebSocket. |
| `405` con `code: method_not_allowed` | La richiesta non usa `GET`. | Usa `GET` per la connessione. |

Attendi prima di riconnetterti dopo un errore. Non riconnetterti in un ciclo
stretto.

### Leggi i messaggi

Ogni messaggio è un envelope `{ "type": "...", "data": ... }`. Leggi `type`
prima di analizzare `data`. Salta i tipi che il client non supporta.

| Tipo di evento | Payload dei dati |
| --- | --- |
| `native_log` | Dati del log, con la forma della [risposta dei log](#log-response). |
| `native_issue` | Dati del problema raggruppato, con la forma della [risposta dei problemi](#issue-response) nella versione 1. |
| `native_trace_span` | Uno span, con la forma di un elemento della [lista degli span](#span-list). |
| `native_action` | Dati dell'azione di prodotto, con la forma della [risposta delle azioni](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Dati del progetto. Leggi di nuovo la lista dei progetti quando cambia. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Utilizzo dell'account, con la forma di [utilizzo dell'account](/it/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Un evento `native_issue` usa la versione 1 della risposta dei problemi: un
problema archiviato mostra `ignored` e l'evento non ha priorità. Metriche e
release non sono tipi di eventi in tempo reale. Leggile con le loro route di lista. Il
ticket non seleziona un progetto. Controlla il `project_id` di ogni evento
prima di mostrarlo nella vista di un progetto. `logbrew watch --json` usa
questo flusso. Vedi il [riferimento della CLI](/it/reference/cli).

### Gestisci una connessione chiusa

| Codice di chiusura | Motivo | Passo successivo |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Attendi, poi riconnettiti con un nuovo ticket. Leggi di nuovo le route di lista per recuperare i record persi. |
| `1008` | `live feed access changed; sign in again` | Smetti di riconnetterti. Accedi di nuovo prima di creare un nuovo ticket. |

Altre disconnessioni possono non avere un motivo LogBrew. Dopo esserti
riconnesso, leggi di nuovo le route di lista e abbina i record per ID.

## <span id="issue-status-response-examples">Esempi di risposte sullo stato dei problemi</span>

`PATCH /api/telemetry/issues/{issue_id}` con `{ "status": "resolved" }`
restituisce `200 OK` con il problema raggruppato aggiornato, con la stessa
forma della [risposta dei problemi](#issue-response). La chiave di query
`response_version` seleziona la versione. Non restituisce un flag di successo.

Il corpo imposta 1 o più campi tra `status`, `priority` e `assignee`. `status`
accetta `unresolved`, `resolved` o `archived`. `ignored` è un vecchio nome di
`archived`. Vedi [Aggiorna un problema](/it/reference/telemetry-api#update-one-issue).

Controlla `id`, `status` e `priority` restituiti prima di mostrare il
successo. Non costruire il risultato dai valori inviati. Un cambio di stato
non elimina occorrenze e non cambia `first_seen_at` e `last_seen_at`. Non
cambia `severity` né una regola di gravità.

Una modifica rifiutata restituisce `422` con `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Risultato | Causa |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Il corpo non ha nessuno dei 3 campi. |
| `422`, `issue priority must be high, medium, or low` | Il valore della priorità non è supportato. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | Il valore dell'assegnatario non è supportato. |
| `422`, `issue assignee cannot read this project` | L'assegnatario non ha accesso al progetto. LogBrew non cambia nulla. |
| `422`, `issue assignee team is not a team of this project's organization` | Il team non appartiene all'organizzazione del progetto. LogBrew non cambia nulla. |
| `403` con `code: forbidden` | L'account non può gestire i problemi del progetto. |
| `404` con `code: not_found` | L'account non può leggere il problema, oppure il problema non esiste. |

Un campo che ha già il valore richiesto non cambia. Dopo un timeout o una
risposta persa, invia di nuovo la stessa richiesta oppure leggi prima il
problema. Non inviare una modifica diversa prima di aver letto lo stato
attuale. Vedi [Scritture](/it/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` restituisce `200 OK` con 1 risultato per
ogni ID di problema richiesto, nell'ordine della richiesta. Ogni problema
trovato usa la forma della versione 3. Un risultato `not_found` ha
`issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
```

## Ambito delle richieste di analisi

Le route di analisi, la route delle serie di metriche e la route del volume
dei segnali leggono un progetto e un intervallo di tempo. Ogni richiesta
richiede `project_id` e `since`. `since` accetta una durata compatta come
`24h` o `7d`, oppure un timestamp RFC3339. `until` accetta un timestamp
RFC3339 e per impostazione predefinita è l'ora della richiesta. L'intervallo
include `since`, esclude `until` e non può superare 31 giorni.

`service_name`, `release` e `environment` sono filtri esatti facoltativi. Ogni
valore deve avere da 1 a 256 caratteri dopo che LogBrew ha rimosso gli spazi
iniziali e finali. La route di confronto dei segmenti mette questi filtri
dentro ogni segmento, non al primo livello.

Se l'account non può leggere il progetto, queste route restituiscono `200 OK`
con conteggi a zero. Non restituiscono `404`. Un risultato vuoto non conferma
l'accesso al progetto. Confronta `project_id` con i progetti che l'account può
leggere. Una richiesta tramite una connessione MCP che non include il progetto
restituisce `403` e `forbidden`.

| Route | Valori di `response_version` | Predefinito |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` o `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Non accettato | Schema `1` |
| `POST /api/telemetry/analytics/paths` | Non accettato | Schema `1` |
| `GET /api/telemetry/metrics/series` | Non accettato | Schema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Ogni risposta inizia con `schema_version`, `query` e `purpose`. `query` riporta
l'ambito effettivo. Omette i filtri che non hai inviato. `purpose` è un testo
semplice che spiega a quale domanda risponde la route.

Un tasso è omesso quando il suo denominatore è zero. Un tasso omesso non è `0`
e non è `null`. Leggi `coverage` prima di fidarti di un tasso.

### <span id="shared-scope-errors">Errori comuni dell'ambito</span>

Questi errori usano HTTP `422` e `validation_failed`:

| Causa | `error` |
| --- | --- |
| Nessun `project_id` | `product analytics project_id is required` |
| Nessun `since` | `product analytics since is required` |
| `since` non è una durata o un timestamp RFC3339 | `invalid since value` |
| `until` non è un timestamp RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` non è precedente a `until` | `product analytics since must be earlier than until` |
| L'intervallo supera i 31 giorni | `product analytics range must not exceed 31 days` |
| Un filtro vuoto o più lungo di 256 caratteri | `product analytics context filters must be non-empty and at most 256 characters` |

Per esempio, una richiesta senza `project_id` restituisce:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Le route delle serie di metriche e del volume dei segnali usano le stesse
regole di ambito, con un proprio testo di `error`. Le loro sezioni più sotto
elencano questi errori.

Una chiave di query sconosciuta restituisce `422` come descritto in [Parametri di query non validi](/it/reference/api-errors#invalid-query-parameters).
Un campo JSON sconosciuto, un campo JSON obbligatorio mancante o un valore
enum non supportato restituisce `invalid_json`. Vedi
[JSON non valido](/it/reference/api-errors#invalid-json). Una richiesta con il
metodo HTTP sbagliato restituisce `405` e `method_not_allowed`. Il suo testo
`next` indica il metodo e i campi supportati. Vedi
[Metodo non supportato](/it/reference/api-errors#unsupported-method).

## Risposta della panoramica di analisi di prodotto

`GET /api/telemetry/analytics/overview` mostra l'attività di un progetto:
volume delle azioni, utenti, sessioni, una serie temporale, le azioni
principali e le visualizzazioni di pagina, le visualizzazioni di schermata e
le interazioni classificate. Usala per trovare i nomi esatti degli eventi da
usare nelle altre route di analisi.

conteggi, ma il loro valore `estimation.method` è un token più vecchio. La

identificati. Le versioni 2 e 3 contano solo i soggetti di tipo `user` e

### Leggi conversione e copertura

`entry_rate` è `entered_units` diviso `candidate_units`: 50 su 60.
`overall_conversion_rate` è `completed_units` diviso `entered_units`: 15 su
50, cioè il 30%. Non è 15 diviso tutti i candidati. Questi conteggi non
spiegano perché le unità si sono fermate.

La copertura conta eventi, non sessioni. Qui 120 eventi corrispondono a un
passaggio e 20 di questi non hanno un ID di sessione. Il risultato esclude
quei 20 eventi dai conteggi delle sessioni. Non trattarli come 20 sessioni
fallite.

Il primo passaggio non ha `conversion_from_previous`. L'ultimo passaggio non
ha `drop_off_to_next_units` né `drop_off_to_next_rate`.

Un'unità raggiunge un passaggio successivo solo quando gli orari dei passaggi
sono strettamente crescenti. Eventi con lo stesso timestamp non
possono soddisfare due passaggi consecutivi. L'ultimo passaggio deve avvenire
entro `conversion_window_seconds` dal primo.

La modalità per sessione conta sessioni, non persone. Usa `identified_user`
solo per eventi che portano un ID soggetto opaco di tipo `user`. Questa
modalità può unire eventi di sessioni diverse dentro la finestra di
conversione. Mantieni la stessa unità e gli stessi passaggi quando confronti i
risultati.

Il `conversion_window_seconds` predefinito è 24 ore oppure la durata
dell'intervallo, se più breve. Il massimo è la durata dell'intervallo in
secondi interi, arrotondata per eccesso.

### Risultati vuoti del funnel

Una risposta vuota riuscita elenca comunque i passaggi richiesti con `units`
a zero. Se non ci sono unità candidate, `summary` omette `entry_rate` e
`overall_conversion_rate`. La route non restituisce `404` perché nessun
evento corrisponde.

Leggi `coverage` e `next_action` per trovare la causa:

| `next_action.code` | Causa |
| --- | --- |
| `capture_product_activity` | Non esistono eventi classificati nell'ambito. |
| `choose_captured_funnel_steps` | Nessun evento corrisponde a un passaggio richiesto. |
| `sessionize_product_activity` | Esistono eventi dei passaggi, ma nessuno ha un ID di sessione. |
| `identify_product_users` | Esistono eventi dei passaggi, ma nessuno ha un soggetto di tipo `user`. |
| `verify_funnel_entry` | Nessuna unità è entrata al passaggio 1. |
| `investigate_funnel_drop_off` | Alcune unità sono entrate, ma nessuna ha completato tutti i passaggi. |
| `compare_funnel_contexts` | Almeno un'unità ha completato il funnel. |

Oltre agli [errori comuni dell'ambito](#shared-scope-errors), queste richieste
restituiscono `422` e `validation_failed`. Meno di 2 o più di 8 passaggi:

```json
  "code": "validation_failed",
```

di controllo restituisce
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Un passaggio `interaction` deve anche essere un nome di azione valido.
Altrimenti l'errore è `product analytics interaction event_name must be a bounded stable action name`.

Correggi la richiesta prima di inviarla di nuovo. Non rimuovere passaggi e non
cambiare l'unità di analisi solo per ottenere un risultato non vuoto.

## Analisi per eventi esatti e automatica

Fidelizzazione e ciclo di vita accettano due forme di richiesta. Usa
`response_version` per scegliere la forma che risponde alla tua domanda:

| Analisi | `response_version` | Selettori di eventi |
| --- | --- | --- |
| Fidelizzazione per eventi esatti | `1`, oppure omesso | Invia sia `start_event` sia `return_event`. |
| Ciclo di vita per un evento esatto | `1`, oppure omesso | Invia `event`. |
| Fidelizzazione o ciclo di vita automatici | `2` | Non inviare selettori di eventi. |

Un selettore esatto contiene `kind` e `event_name`. `kind` è `page_view`,
`screen_view` o `interaction`. Copia `event_name` da
`classified_activity.top_events`. Non indovinare il nome di un evento
dall'etichetta di un pulsante.

Entrambe le forme contano solo gli utenti: ID soggetto opachi di tipo `user`.
I soggetti anonimi e gli eventi senza un ID soggetto utilizzabile non contano
come utenti. Le risposte non restituiscono mai ID soggetto.

Gli intervalli fissi sono `hour`, `day`, `week` e `thirty_day`. Sono durate
fisse. `thirty_day` è 30 giorni, non un mese di calendario. Se ometti
`interval`, l'API usa `hour` per un intervallo di 48 ore o meno e `day` per un
intervallo più lungo.

### Errori di fidelizzazione

Oltre agli [errori comuni dell'ambito](#shared-scope-errors), queste richieste
restituiscono `422` e `validation_failed`:

| Causa | `error` |
| --- | --- |
| Versione 1 senza entrambi i selettori, versione 2 con un selettore o un'altra versione | `product analytics retention activity selection is contradictory` |
| `interval_count` non compreso tra `1` e `31` | `product analytics retention interval_count must be between 1 and 31` |
| Le fasce temporali delle coorti moltiplicate per `interval_count` superano 500 | `product analytics retention interval and interval_count would exceed 500 cohort matrix cells` |

Il limite di celle dipende dall'intervallo e dai periodi, non dal numero di
utenti. Un intervallo di 30 giorni con `interval: "hour"` ha 720 fasce
temporali di coorte. Con `interval_count: 1`, sono 720 celle, cioè più di 500:

```json

  "code": "validation_failed",
  "next": "choose a wider interval, a shorter time range, or fewer retention periods",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Per usare la fidelizzazione automatica, rimuovi entrambi i selettori. Non
modificare l'SDK per correggere questa richiesta di lettura.

utenti in base a un evento, non a tutta l'attività del progetto:

utente può essere inattivo per questo evento mentre svolge altre attività.

Le risposte per eventi esatti hanno `schema_version: 1`. Il loro `query`
riporta i selettori e omette `activity_scope`. Le risposte automatiche hanno
`schema_version: 2` e `query.activity_scope: "all_classified_activity"`.
Omettono i selettori. Un selettore diverso può cambiare il risultato anche se
l'attività acquisita non cambia.

Il primo punto registra 10 job completati, non 10 campioni. `rate_per_second`
divide quella variazione per la fascia temporale di 300 secondi. `last` è
l'ultima variazione registrata, non la somma. Vedi
[significato delle aggregazioni delle metriche](/it/concepts/telemetry#read-the-metric-value).

Il tipo e la temporalità di una serie determinano il suo `aggregation.code` e
le statistiche di ogni punto. Un punto omette le statistiche che non si
applicano. Una statistica mancante non è zero.

| Tipo e temporalità | `status` | `aggregation.code` | `value` | Altre statistiche |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Ultimo campione | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Somma delle variazioni | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 approssimativo | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Qualsiasi tipo, `cumulative` | `limited` | `raw_cumulative_last` | Ultimo campione grezzo | `last`, `min`, `max` |
| Qualsiasi altra coppia | `limited` | `raw_last` | Ultimo campione grezzo | `last`, `min`, `max` |

`limited` è una risposta riuscita, non un errore. Aggiunge
`aggregation.limitation`, che spiega perché LogBrew mostra solo valori grezzi.
`ready` non dimostra un'acquisizione completa.

Leggi `coverage` prima di disegnare un grafico:

- `samples` conta i campioni di tutte le serie corrispondenti, incluse le serie
  che la risposta non restituisce.
- `series` conta le serie corrispondenti. `returned_series` e `points` contano
  i dati restituiti.
- `truncated` è `true` quando `series_limit` ha rimosso serie con volume più
  basso.
- `expected_buckets_per_series` è il numero di fasce temporali possibili
  nell'intervallo.

Non aggiungere un punto per una fascia temporale senza campioni. Non inserire
uno zero e non copiare il valore precedente. Ogni punto restituisce fino a 3
`trace_exemplars`. Un esemplare di traccia collega un campione a una traccia.
Non spiega tutti i campioni della fascia temporale. Se nessun punto ha un
esemplare di traccia, `next_action.target` è `metric_samples`.

### Ambito ed errori delle serie di metriche

`project_id`, `name` e `since` sono obbligatori. `name` può avere al massimo
200 caratteri. `interval` è `auto`, `1m`, `5m`, `15m`, `1h`, `6h` o `1d`. Il
valore predefinito è `auto`, che seleziona l'intervallo più piccolo con al
massimo 300 fasce temporali. Un intervallo esplicito non può richiedere più di
500 fasce temporali.

`group_by` è `none`, `service_name`, `release` o `environment`. Il valore
predefinito è `none`. Senza raggruppamento, tipi, unità e temporalità diversi
restano in serie separate. `series_limit` accetta da `1` a `20`. Il valore
predefinito è `10`.

Un risultato vuoto restituisce `200` con `series: []` e `samples` a zero.
L'oggetto `coverage` omette `first_seen_at` e `last_seen_at`. Questo non
dimostra che l'applicazione non abbia mai inviato la metrica. Controlla il
progetto, il nome della metrica e l'intervallo di tempo.

Se ometti `name`, la richiesta restituisce `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Fasce temporali di un minuto su sette giorni restituiscono `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Altri errori `422` sono `metric series group_by is not supported`,
`metric series interval is not supported` e
`metric series_limit must be between 1 and 20`.

La copertura conta eventi, non sessioni. Qui cinque eventi corrispondono

riproduzione completa di una sessione. LogBrew legge al massimo 1024 eventi
con nome per sessione prima di selezionare l'ancoraggio: i primi eventi per
`following` e gli ultimi per `preceding`. Un ancoraggio fuori da questo limite
può essere omesso.

### <span id="filter-the-anchor-by-property">Filtra l'ancoraggio per proprietà</span>

Invia fino a quattro `property_filters`, ognuno con una `key` e un `value`
esatti. Copia la chiave dal [catalogo delle proprietà](#analytics-property-catalog).
I filtri si applicano solo all'ancoraggio, non agli eventi intorno. I valori
distinguono tra maiuscole e minuscole. Quando ci sono filtri, `query` li
riporta e `coverage.anchor_property_filters` indica:

| Campo | Significato |
| --- | --- |
| `context_events` | Eventi di ancoraggio nell'ambito prima dei filtri sulle proprietà. |
| `property_ready_events` | Eventi di ancoraggio che hanno tutte le chiavi richieste. |
| `missing_property_events` | Eventi di ancoraggio senza una o più chiavi richieste. |
| `matching_events` | Eventi di ancoraggio i cui valori corrispondono a tutti i filtri. |
| `nonmatching_value_events` | Eventi di ancoraggio che hanno tutte le chiavi ma un valore diverso. |
| `property_ready_rate` | `property_ready_events` diviso `context_events`. |
| `match_rate` | `matching_events` diviso `property_ready_events`. |

Chiavi mancanti e valori diversi richiedono correzioni diverse. Non sommarli.
L'oggetto è omesso quando la richiesta non ha filtri sulle proprietà.

### Percorsi vuoti e richieste rifiutate

Un array `paths` vuoto può essere una risposta `200` riuscita. Leggi
`summary`, `coverage` e `next_action`. Questi codici distinguono le cause:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` e
`narrow_or_move_path_anchor`.

Oltre agli [errori comuni dell'ambito](#shared-scope-errors), queste richieste
restituiscono `422` e `validation_failed`:

| Causa | `error` |
| --- | --- |
| `depth` non compreso tra `1` e `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` non compreso tra `1` e `20` | `product analytics path_limit must be between 1 and 20` |
| Più di quattro filtri sulle proprietà | `product analytics paths accept at most four exact anchor property filters` |
| Una chiave che non è nel catalogo delle proprietà | `product analytics path property keys must be supported privacy-safe keys` |
| La stessa chiave due volte | `product analytics path property keys must be unique` |
| Un valore vuoto, più lungo di 256 caratteri o con un carattere di controllo | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

Per esempio, `depth: 0` restituisce:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

presenti negli eventi di prodotto classificati di un progetto. Usa le chiavi
nei [confronti tra segmenti](#analytics-segment-comparison) e nei filtri
sull'ancoraggio dei percorsi. Il catalogo restituisce chiavi e conteggi. Non

### Leggi le chiavi delle proprietà disponibili

## <span id="analytics-segment-comparison">Confronto tra segmenti di analisi</span>

`POST /api/telemetry/analytics/segments/compare` confronta con quale frequenza
sessioni o utenti raggiungono un evento esatto in 2-4 segmenti di un progetto.
Un segmento seleziona gli eventi per servizio, release, ambiente e valori
delle proprietà. Il primo segmento è il riferimento.

### Definisci il confronto

Invia questo corpo JSON con l'autenticazione dell'account e
`Content-Type: application/json`. Qui `basic` e `premium` sono valori di piano
dell'applicazione di esempio, non piani LogBrew:

```json

  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",

  "response_version": 2,

      "label": "Basic plan",

      "environment": "production",

      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]

```

`target` e `segments` sono obbligatori. `analysis_unit` è `session` o
`identified_user`. Il valore predefinito è `session`, che conta sessioni, non
persone. `interval` accetta gli stessi valori della panoramica. Il valore
predefinito è `auto`.

Ogni segmento richiede una `key` univoca, una `label` e un insieme di filtri
diverso:

- `key`: da 1 a 32 byte. Inizia con una lettera ASCII minuscola o con una
  cifra. Usa solo lettere ASCII minuscole, cifre, `_` e `-`.
- `label`: da 1 a 80 caratteri, senza caratteri di controllo.
- `service_name`, `release`, `environment`: facoltativi. Ogni valore ha da 1 a
  256 caratteri, senza caratteri di controllo.
- `property_filters`: da 0 a 4 filtri. Ogni chiave può comparire una sola
  volta in un segmento. Un evento deve corrispondere a tutti i filtri del
  segmento. I valori distinguono tra maiuscole e minuscole, hanno da 1 a 256
  caratteri e LogBrew rimuove gli spazi iniziali e finali.

Un segmento senza filtri seleziona tutta l'attività classificata del progetto
nell'intervallo di tempo. I segmenti possono sovrapporsi. Un'etichetta o una
chiave diversa non rende validi due insiemi di filtri identici.

### Leggi tassi e differenze

`eligible_units` stima le sessioni o gli utenti con attività classificata nel
segmento. `reached_units` stima quanti di loro hanno raggiunto il target.
`reach_rate` è `reached_units` diviso `eligible_units`. Gli eventi senza l'ID
dell'unità selezionata non contano per queste unità.

Il tasso del riferimento è 20%. Il tasso premium è 30%. La differenza è di 10
punti percentuali. L'incremento relativo è 50%, non 10%. I piccoli errori
decimali derivano dall'aritmetica in virgola mobile. Arrotonda i tassi per la
visualizzazione, ma calcola con i valori restituiti. Il segmento di
riferimento non ha `comparison_to_baseline`. L'incremento relativo è omesso
quando il tasso di raggiungimento del riferimento è zero.

In `query`, un filtro di segmento che non hai inviato è `null`. Una lista
`property_filters` vuota è omessa.

`coverage.property_filters` ha gli stessi campi della
[copertura dei filtri sull'ancoraggio dei percorsi](#filter-the-anchor-by-property).
Qui `matching_events` è uguale a `classified_events`. Tieni separati chiavi
mancanti e valori diversi. I segmenti possono sovrapporsi e una sessione può
comparire in più fasce temporali. Non sommare i conteggi delle unità tra
segmenti o fasce temporali.

Il confronto è descrittivo. `confidence.causal_inference` è
`not_established` e `confidence.statistical_significance` è `not_tested`. Un
tasso del 30% contro il 20% non dimostra che un piano abbia causato più
checkout.

Oltre agli [errori comuni dell'ambito](#shared-scope-errors), queste richieste

## Risposta del volume dei segnali

e un intervallo di tempo. Richiede `project_id` e `since`. Non accetta
`project_ids`.

`until` non può essere nel futuro. Se lo ometti, la fine è l'ora della
richiesta. Un `since` compatto come `24h` conta all'indietro da `until`.
`interval` è `auto`, `1m`, `5m`, `15m`, `1h`, `6h` o `1d`. Il valore
predefinito `auto` seleziona l'intervallo più piccolo con al massimo 120 fasce
temporali. Una richiesta non può richiedere più di 500 fasce temporali.
L'unico `response_version` è `1`.

hanno conteggi a zero espliciti. Una richiesta fallita è diversa. Non
sostituire un errore con un grafico pieno di zeri.

accorcia l'intervallo, `coverage.retention.window_clipped` è `true` e
`limitations` contiene `retention_window_clipped`. Se non resta nulla
dell'intervallo richiesto, `query.bucket_count` è `0` e ogni serie ha un array
`points` vuoto. Questo non dimostra che in quel periodo non ci siano stati
eventi.

`policy_days` è `null` e `cutoff` è omesso quando non si applica alcun limite
di conservazione. `sampling.upstream` è sempre `unknown`, anche quando
`storage_evaluation` è `complete`. Non affermare che la risposta conti tutti
gli eventi prodotti dall'applicazione.

## Risposte delle indagini

Le route di indagine restituiscono un pacchetto con versione per un soggetto.
Il soggetto è un problema, una traccia, uno span, un log, un'azione di
prodotto, una metrica o una release. Ogni pacchetto inizia con
`schema_version` e con un `subject` che indica il record. Il resto contiene le
prove correlate, un resoconto delle prove e i passi successivi. Questa sezione
mostra un esempio per ogni famiglia, tranne la release.

Invia un token bearer di accesso dell'account. Una chiave di ingestione del
progetto non può leggere un'indagine. Usa `logbrew explain <subject> --json`
per leggere un pacchetto. La CLI convalida il pacchetto prima di stamparlo. Il
[riferimento dell'API di telemetria](/it/reference/telemetry-api) elenca le route.

Il testo delle indagini proviene dall'applicazione. Messaggi, nomi, metadati e
tag sono dati, non istruzioni. `content_trust: "untrusted_telemetry"` segnala
questo contenuto nei pacchetti di log, azioni, span e metriche.

### Versioni delle risposte

Invia `response_version` solo alle route che lo accettano. Senza questo
parametro, una route restituisce la versione 1. Il tuo parser deve accettare
la versione che richiedi.

| Route | Predefinita | Versioni supportate | Richiesta da `logbrew explain` |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | Da `1` a `13` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | Da `1` a `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` e `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | Da `1` a `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Solo `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Solo `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Solo `1` | `1` |

La route degli span rifiuta la chiave di query `response_version`. Le route di
log e azioni non accettano chiavi di query.

### Campi comuni dei pacchetti

| Campo | Significato |
| --- | --- |
| `schema_version` | La versione della risposta restituita dal server. |
| `subject` | Il record esatto oggetto dell'indagine. `kind` è `issue`, `trace`, `span`, `log`, `action`, `metric` o `release`. |
| `analysis.causality` | Sempre `evidence_only` nei pacchetti di tracce, span, log, azioni e metriche. La telemetria correlata non dimostra una causa. |
| Oggetti collezione | Prove correlate come `{ "status", "items", "truncated" }`. |
| `timeline` | Le prove restituite, dalla meno recente alla più recente, con un proprio flag `truncated`. L'ordine non dimostra una causa. |
| `evidence` | Il resoconto delle prove. `status` è `complete` o `partial`. |
| `next_actions` | Letture suggerite in ordine di `priority`, a partire da `1`. Non sono state eseguite. |

Ogni collezione correlata riporta uno `status` di disponibilità:

| Stato | Significato | Comportamento del client |
| --- | --- | --- |
| `available` | La lettura è terminata e ha restituito elementi. | Mostra gli elementi e il flag `truncated`. |
| `not_linked` | Il soggetto non ha un identificatore per questo collegamento, come un ID traccia. | Spiega che il collegamento manca. Non ricostruirlo dai timestamp. |
| `not_found` | La lettura è terminata e non ha trovato prove conservate. | Mostra un risultato vuoto. |
| `unavailable` | La lettura facoltativa non è riuscita. Il soggetto resta valido. | Lascia visibile il soggetto. Riprova più tardi. Non mostrare zero elementi come risultato. |

Il resoconto delle prove ha quattro liste ordinate di nomi di campo stabili:
`captured_fields`, `missing_fields`, `redacted_fields` e `truncated_fields`.
`status` è `complete` solo quando le ultime tre liste sono vuote. I dati
oscurati non sono dati mancanti. I dati troncati non sono dati completi. Non
completare un valore oscurato o troncato.

### Limiti delle indagini

Questi limiti valgono per una singola risposta. Un flag `truncated` o una voce
in `truncated_fields` indica che un limite ha omesso dei dati.

| Prove | Limite |
| --- | --- |
| Elementi correlati in una collezione | 20 |
| Span conservati letti per una traccia | 1.000 |
| Elementi della timeline | 50 per i pacchetti di log, azioni e span. 100 per i pacchetti di tracce e metriche. |
| Attributi strutturati, proprietà e metadati | 64 valori scalari, 4 livelli di oggetti o array, 16 elementi per array, 512 caratteri per stringa |
| Intervallo di tempo di correlazione | 5 minuti prima e dopo un log, un'azione o l'occorrenza del problema selezionata. Per una traccia o uno span, 5 minuti prima dell'inizio e dopo la fine, al massimo 24 ore. |

Ogni sezione di famiglia elenca i propri limiti.

### Risposta dell'indagine su un problema

Usa `GET /api/telemetry/issues/{issue_id}/investigation` per leggere le prove
di un'occorrenza di un problema raggruppato. La
[guida all'indagine sui problemi](/it/guides/investigate-an-issue) mostra in che
ordine leggere le prove. Richiedi la versione 13:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

Le chiavi di query sono `response_version`, `selection` e `occurrence_id`.
`selection` è `recommended`, `first` o `latest`. I valori distinguono tra
maiuscole e minuscole. Nelle versioni da 2 a 13, se ometti il selettore viene
usato `recommended`. La versione 1 restituisce l'ultima occorrenza conservata
e non accetta selettori. I filtri della lista dei problemi non si applicano a
questa lettura.

#### Errori delle richieste di indagine su un problema

Usa `selection` oppure `occurrence_id`. Non inviarli entrambi, nemmeno quando
selezionano la stessa occorrenza:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 13 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Causa | Ripristino |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | La richiesta ha entrambi i selettori. | Mantieni un solo selettore. |
| `422` | `issue occurrence selection requires response_version=2 through 13` | La richiesta ha un selettore e la versione 1, oppure nessuna versione. | Invia `response_version=13`. Mantieni il selettore. |
| `422` | `issue investigation response_version must be 1 through 13` | La versione è fuori intervallo. | Invia una versione supportata. |
| `422` | `invalid query parameters` | Una chiave sconosciuta, un UUID non valido, una versione non intera o un valore di `selection` sconosciuto. | Correggi la [query](/it/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | L'occorrenza non è nella cronologia conservata di questo gruppo. | Copia l'ID dell'occorrenza dagli eventi di questo problema. Non usare al suo posto `latest` o `recommended` senza approvazione. |
| `404` | `issue not found` | Nessun progetto leggibile ha questo problema. | Controlla l'account e l'UUID del problema. Non inviare l'UUID di un'occorrenza come ID del problema. |

Un'occorrenza mancante non significa che manchi il problema. Un `404` non
indica se un altro account può leggere il problema.

### Risposta dell'indagine su una traccia

Usa `GET /api/telemetry/traces/{trace_id}/investigation` per leggere una
traccia con il suo percorso di errore, il percorso più lento e i segnali
correlati. Le chiavi di query sono `response_version`, `project_id`, `release`
e `environment`. Sono tutte facoltative. Richiedi la versione 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

La versione 2 aggiunge `cause` e `fix` a ogni problema correlato. La versione 3
aggiunge `span_id` a problemi, azioni e metriche correlati, quando è stato
acquisito.

### Risposta dell'indagine su uno span

Usa `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` per
leggere un'operazione in una traccia. Invia `project_id`, `environment` e
`release`. Sono obbligatori tutti e tre. Copiali dallo span selezionato. Non
inviare l'`id` della riga dello span come `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### Risposta dell'indagine su un log

Usa `GET /api/logs/{log_id}/investigation` per leggere un log e le prove
correlate. Questa route non ha chiavi di query. Copia l'ID del log da una lista
di log.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

La lettura può restituire prove fuori dai filtri della lista dei log. Le
letture correlate usano progetto, ambiente e release del log, e i 5 minuti
prima e dopo il log. Anche i log vicini usano lo stesso servizio. Non
richiedono un ID traccia. Le letture sulla traccia esatta richiedono l'ID
traccia del log e possono includere altri servizi. Il riepilogo della traccia
usa lo stesso ID traccia e lo stesso ambito, senza l'intervallo di tempo.

### Risposta dell'indagine su un'azione

Usa `GET /api/telemetry/actions/{action_id}/investigation` per leggere
un'azione di prodotto, il suo stato riportato e le prove correlate. Questa
route non ha chiavi di query. Le letture correlate usano lo stesso intervallo e
gli stessi ambiti di un'indagine su un log.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/telemetry/actions/$ACTION_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

`correlations`, `timeline` e `next_actions` usano le forme dell'indagine su un
log. Le azioni correlate escludono l'azione oggetto dell'indagine.

### Risposta dell'indagine su una metrica

Usa `GET /api/telemetry/metrics/investigation` per leggere un nome di metrica
in un progetto e in un intervallo di tempo. La risposta contiene la serie
attuale, un confronto con l'intervallo precedente di pari durata, l'ultimo
campione, gli esemplari di traccia e i deploy completati. La versione 2
aggiunge la descrizione della metrica presa dall'ultimo campione conservato.
La versione 1 riporta sempre `description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` e `since` sono obbligatori. `since` è incluso e `until`
è escluso. Per impostazione predefinita `until` è l'ora attuale. Il confronto
legge anche l'intervallo precedente di pari durata.

`relative_change_percent` è `(current - previous) / abs(previous) * 100`.
È `null` quando il valore precedente è zero o mancante.
`expected_buckets_per_series` conta le fasce temporali possibili, non quelle
con dati. Non disegnare le fasce vuote come zero. Un deploy vicino a una
variazione non dimostra di averla causata.

Un progetto che l'account non può leggere restituisce `200 OK` con
`analysis.status: "no_samples"`, non `404`. Un risultato vuoto non descrive
gli altri tipi di segnale.

al massimo 500 fasce temporali. `series_limit` va da 1 a 20, con 10 come
valore predefinito. La risposta restituisce al massimo 20 esemplari e 20
deploy.

| HTTP | `error` | Ripristino |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Ometti `response_version` oppure invia `2`. |
| `422` | `metric series project_id is required` | Invia l'ID di un progetto leggibile. |
| `422` | `metric series name is required` | Copia il nome dalla lista delle metriche. |
| `422` | `metric series since is required` | Invia un valore come `24h` o un timestamp RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | Usa un intervallo più breve. |
| `422` | `metric series interval would exceed 500 buckets` | Usa `interval=auto` o un intervallo più ampio. |
| `422` | `metric series_limit must be between 1 and 20` | Invia un valore da 1 a 20. |

`interval` è `auto`, `1m`, `5m`, `15m`, `1h`, `6h` o `1d`. `group_by` è
`none`, `service_name`, `release` o `environment`. Altri valori restituiscono
`422`.

### Errori delle indagini

| HTTP | Route | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Azione | `action not found` |
| `404` | Traccia | `trace not found` |
| `422` | Traccia | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, azione, problema | `invalid URL path parameters` quando l'ID nel percorso non è un UUID |
| `422` | Problema, traccia, span, metrica | `invalid query parameters` per una chiave sconosciuta o un valore del tipo sbagliato |

Un `404` significa che nessun progetto leggibile contiene il record. Ogni
route restituisce anche `401` senza un'autenticazione valida e `405` per un
metodo diverso da `GET`. Vedi [Errori API](/it/reference/api-errors) per le
risposte di
[risorsa non trovata](/it/reference/api-errors#resource-not-found),
[percorso](/it/reference/api-errors#invalid-path-value),
[autenticazione](/it/reference/api-errors#authentication-failure) e
[metodo](/it/reference/api-errors#unsupported-method).

Una lettura facoltativa delle prove può fallire dentro una risposta `200 OK`.
In quel caso la collezione riporta `unavailable`. Non mostrarla come
`not_found` o come zero record.

## <span id="severity-values">Valori di gravità</span>

I valori di gravità mostrati agli utenti sono `info`, `warning`, `error` e
`critical`. SDK e runtime possono inviare alias comuni come `trace`, `debug`,
`warn` o `fatal`. Le risposte REST e in tempo reale restituiscono sempre il valore
canonico. Per esempio, LogBrew accetta `warn` in ingresso e restituisce
`warning`. L'ingestione rifiuta i valori di gravità sconosciuti.

| Alias | Valore canonico |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Risposte delle regole di gravità</span>

Una regola di gravità cambia il modo in cui LogBrew mostra un log o un
problema. Non cambia la gravità acquisita dall'applicazione. Log e problemi
restituiscono un oggetto `triage`:

| Campo | Significato |
| --- | --- |
| `effective_severity` | La gravità da mostrare. Senza una regola, è uguale a `severity`. |
| `ignored` | `true` quando una regola dei log ignora il log, oppure quando il problema è archiviato. |
| `rule_applied` | `true` quando si applica una regola di gravità o lo stato ignorato. `false` è il valore predefinito, non un dato mancante. |

Usa `triage.effective_severity` per la visualizzazione. Mantieni `severity`
come valore acquisito. Per impostazione predefinita, la lista dei log omette i
log ignorati. Invia `status=ignored` o `status=all` su `GET /api/logs` per
includerli.

L'account deve avere il permesso di gestire i problemi nel progetto. L'accesso
in lettura non basta. Senza questo permesso, una modifica alla regola
restituisce `403` con `code: forbidden`.

### Modifica una regola dei log

`PUT /api/logs/{log_id}/triage-rule` imposta la regola per il log e per i log
successivi con la stessa firma. Il corpo richiede sia `severity` sia
`ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Una risposta `200 OK` contiene il [log](#log-response) completo. Il suo
`severity` resta `warning`. Il suo `triage` mostra la regola:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Questo estratto mostra solo i campi modificati. Nella richiesta, `severity` è
`source`, `info`, `warning`, `error` o `critical`. `source` ripristina la
gravità acquisita. Non riattiva un log ignorato. Per mostrare di nuovo il log,
invia `"ignored": false`.

### Modifica una regola dei problemi

`PUT /api/telemetry/issues/{issue_id}/triage-rule` imposta la gravità mostrata
per un problema raggruppato e per le sue occorrenze successive. Il corpo
accetta solo `severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Una risposta `200 OK` contiene il [problema](#issue-response) completo nella
versione 1. Il `severity` acquisito e lo `status` non cambiano:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Questo estratto mostra solo alcuni campi. Una regola non risolve, non archivia
e non riapre un problema. Per questo usa il
[cambio di stato](#issue-status-response-examples). Una priorità derivata
segue la nuova gravità effettiva. Leggi il problema con `response_version=2` o
`3` per vederla.

Una gravità non supportata restituisce `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Un campo sconosciuto nel corpo, come `status` in una regola dei problemi,
restituisce `422` con `code: invalid_json`. Un log o un problema mancante o
illeggibile restituisce `404` con `code: not_found`. Se la risposta va persa,
leggi di nuovo il log o il problema prima di inviare di nuovo la regola.

## Formato delle risposte di errore

Gli errori dell'applicazione restituiscono un envelope JSON. Questo esempio
mostra una richiesta rifiutata; il testo di `error` e di `next` dipende
dall'errore:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Usa `code` per le diramazioni del programma e `next_action` per
l'automazione. Mostra `error` e `next` alle persone come testo semplice. Non
analizzarne la formulazione. Alcuni errori aggiungono campi, come `limit`,
`reset_at` o `retry_after_seconds`. Una risposta senza corpo JSON non ha un
`code` LogBrew. Vedi [Errori API](/it/reference/api-errors) per tutti i
codici.

## Leggi i dati con la CLI

La CLI legge le stesse route e restituisce lo stesso JSON con `--json`. Inizia
con una ricerca ampia, poi restringi:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Aggiungi `--pagination cursor` per ottenere l'envelope con cursore. La CLI
richiede la versione 4 della risposta dei problemi. Vedi
[Leggi la pagina successiva](/it/reference/cli#read-the-next-page) e
[Monitoraggio in tempo reale](/it/reference/cli#live-watch).

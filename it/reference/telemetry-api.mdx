L'API di telemetria è JSON su HTTP all'indirizzo `https://api.logbrew.co`. Gli
SDK pubblici inviano i loro batch gestiti a `POST /v1/events`. I client
nativi personalizzati inviano envelope nativi a `POST /api/telemetry/ingest`.
Entrambe le route di ingestione richiedono un token bearer di ingestione
limitato al progetto.

Le letture e le modifiche di proprietà dell'account usano un token bearer
dell'account. Non usare mai un token bearer dell'account o una sessione del
browser nella configurazione dell'SDK o dell'ingestione. Non inviare mai un
token bearer di ingestione a una route di lettura.

## Invia una richiesta ben delimitata

Usa questa checklist prima che un client invii una richiesta:

1. Scegli la route e il metodo HTTP dalla tabella degli endpoint.
2. Usa il token bearer corretto: un token bearer di ingestione per
   l'ingestione, un token bearer dell'account per tutto il resto.
3. Seleziona l'ambito di progetto supportato dalla route. Non allargare
   l'ambito dopo una risposta vuota.
4. Aggiungi solo le chiavi di query che la route accetta. Consulta
   [Filtri di query dell'API di telemetria](/it/reference/telemetry-api-filters).
5. Invia `Content-Type: application/json` quando la route ha un corpo JSON.
6. Leggi lo stato HTTP e il corpo della risposta prima di riprovare.
7. Tieni token bearer, ticket di connessione e corpi completi delle risposte
   fuori dai log e dai prompt degli agenti.

## Endpoint

### Ingestione

| Metodo | Percorso | Scopo |
| --- | --- | --- |
| `POST` | `/v1/events` | Ingestione dei batch che gli SDK pubblici di LogBrew costruiscono e inviano. |
| `POST` | `/api/telemetry/ingest` | Ingestione degli envelope di telemetria nativi da un client personalizzato. |

Lascia che sia l'SDK a costruire i batch per `/v1/events`. Non costruirli a
mano. Per l'envelope nativo, consulta
[Invia telemetria con l'SDK](/it/guides/sdk-ingestion).

### Deploy

| Metodo | Percorso | Comando CLI |
| --- | --- | --- |
| `PUT` | `/api/telemetry/deployments/{deployment_id}` | `logbrew deploy` |
| `GET` | `/api/telemetry/deployments/{deployment_id}?project_id=<project-uuid>` | Nessuno |
| `GET` | `/api/telemetry/deployments?project_id=<project-uuid>` | Nessuno |

Registra un deploy dalla tua automazione delle release dopo che è riuscito o
non è riuscito. Il corpo del `PUT` contiene `project_id`, `release`,
`environment`, `service_name`, `status` (`succeeded` o `failed`),
`started_at`, `finished_at` e un `commit_sha` facoltativo. Usa gli stessi
valori di `release`, `environment` e `service_name` che invia il tuo SDK.
L'account deve possedere il progetto.

`deployment_id` è un tuo ID per il deploy. Un nuovo tentativo con lo stesso ID
e lo stesso corpo restituisce il deploy salvato. Lo stesso ID con un corpo
diverso non riesce con `409` e `idempotency_conflict`. Usa un nuovo ID per un
deploy diverso.

### Indagini

Ogni route di indagine restituisce un pacchetto limitato di prove per un
singolo elemento. Il comando `logbrew explain` della [CLI](/it/reference/cli)
legge queste route e convalida la risposta.

| Metodo | Percorso | Comando CLI |
| --- | --- | --- |
| `GET` | `/api/logs/{log_id}/investigation` | `logbrew explain log` |
| `GET` | `/api/telemetry/issues/{issue_id}/investigation` | `logbrew explain issue` |
| `GET` | `/api/telemetry/issues/{issue_id}/correction-verification` | `logbrew investigate issue <issue_id> verify` |
| `GET` | `/api/telemetry/traces/{trace_id}/investigation` | `logbrew explain trace` |
| `GET` | `/api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `logbrew explain span` |
| `GET` | `/api/telemetry/actions/{action_id}/investigation` | `logbrew explain action` |
| `GET` | `/api/telemetry/metrics/investigation` | `logbrew explain metric` |
| `GET` | `/api/telemetry/releases/investigation` | `logbrew explain release` |

## Codici di stato di successo

| Operazione | Stato di successo |
| --- | --- |
| Ingestione, letture, aggiornamenti dei problemi, regole, deploy, analisi e ticket di connessione | `200 OK` |
| Connessione al flusso in tempo reale | `101 Switching Protocols`, poi messaggi WebSocket |

Una risposta `200` non dimostra che le prove siano complete. Leggi i campi di
copertura, troncamento e stato nella risposta.

## Filtri di query e paginazione

Ogni route di lettura accetta le proprie chiavi di query. Gli alias comodi
come `project`, `trace` e `user` non sono chiavi di query. Le route di elenco
restituiscono per impostazione predefinita un array semplice e, con
`pagination=cursor`, un envelope con cursore. L'elenco dei deploy restituisce
sempre un oggetto pagina. Consulta
[Filtri di query dell'API di telemetria](/it/reference/telemetry-api-filters).

## Risposte ed errori

- [Formati delle risposte di telemetria](/it/reference/telemetry-response-shapes)
  mostra un esempio per ogni famiglia di risposte.
- [Errori API](/it/reference/api-errors) elenca i codici di errore e le
  azioni di ripristino.

Leggi `code` prima del messaggio per le persone. Usa `next_action` per il
comportamento del programma e `next` per le indicazioni alle persone. Non
analizzare la formulazione di `error` o `next`.

## Aggiorna i problemi

Queste richieste usano un token bearer dell'account. È volutamente diverso da
`LOGBREW_INGEST_BEARER`. L'account deve avere il permesso di gestire i
problemi nel progetto del problema. In caso contrario, la richiesta non riesce
con `403` e `forbidden`. Lo stesso permesso copre le modifiche di stato,
priorità e assegnatario, e le regole per problemi e log.

Ogni richiesta imposta 1 o più di questi campi:

| Campo | Valori |
| --- | --- |
| `status` | `unresolved`, `resolved` o `archived`. `ignored` è un nome precedente di `archived`. |
| `priority` | `high`, `medium` o `low`. |
| `assignee` | Un ID utente, `me` per l'account con cui hai eseguito l'accesso, `team:<team_id>` per un team, oppure `none` per rimuovere l'assegnatario. |

Una richiesta senza nessuno di questi campi non riesce con `422` e
`validation_failed`.

Un problema ha 0 o 1 assegnatario: un account o un team. Un account deve poter
leggere il progetto e un team deve appartenere all'organizzazione del
progetto. In caso contrario, la richiesta non riesce con `422` e
`validation_failed` e LogBrew non modifica nulla. Ottieni gli account che puoi
assegnare da [Elenca gli assegnatari](#list-assignees). Anche qualsiasi altro
valore di `assignee` non riesce con `422` e `validation_failed`.

Una priorità impostata da te resta fissa. Senza una priorità impostata da te,
la priorità segue la gravità del problema: `error` e `critical` corrispondono
a `high`, `warning` a `medium` e `info` a `low`.

Un campo che ha già il valore richiesto non cambia. Puoi inviare di nuovo la
stessa richiesta dopo un timeout. Un timeout non dimostra che la modifica non
sia avvenuta. Leggi di nuovo il problema prima di inviare una modifica
diversa.

### <span id="update-one-issue">Aggiorna un problema</span>

Aggiungi `response_version=4` per ricevere nella risposta `archived`, la
priorità e l'assegnatario. Nella versione 4, `assignee` vale
`{ "type": "user", "user_id", "name", "email" }`,
`{ "type": "team", "team_id", "slug", "name" }` oppure `null`. La versione 3
mostra un team assegnatario come `null`.

```bash
curl -X PATCH "$LOGBREW_API_URL/api/telemetry/issues/$ISSUE_ID?response_version=4" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{ "status": "archived", "priority": "low", "assignee": "me" }'
```

La risposta è il problema aggiornato. Consulta gli
[esempi di risposta sullo stato dei problemi](/it/reference/telemetry-response-shapes#issue-status-response-examples).

### <span id="update-issues-in-bulk">Aggiorna più problemi insieme</span>

Invia `project_id` e da 1 a 100 ID di problemi diversi di quel progetto:

```bash
curl -X POST "$LOGBREW_API_URL/api/telemetry/issues/bulk" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{
    "project_id": "<project-uuid>",
    "issue_ids": ["<issue-uuid-1>", "<issue-uuid-2>"],
    "assignee": "<user-uuid>"
  }'
```

La richiesta applica la stessa modifica a ogni problema. La risposta contiene
`project_id` e `results`, con 1 risultato per ogni ID problema, nell'ordine
della richiesta. Ogni risultato contiene `issue_id`, `outcome` e `issue`.
`issue` è il problema attuale nella versione 3 della risposta, oppure `null`
per `not_found`. Aggiungi `"response_version": 2` al corpo per ricevere ogni
problema nella versione 4 della risposta.

| `outcome` | Significato |
| --- | --- |
| `updated` | LogBrew ha applicato la modifica. |
| `unchanged` | Il problema aveva già i valori richiesti. |
| `not_found` | Il progetto non ha un problema con questo ID. LogBrew non ha modificato nulla per questo ID. |

Un elenco vuoto, più di 100 ID o un ID ripetuto non riescono con `422` e
`validation_failed`. Dividi un insieme più grande in più richieste. Se
l'account non può leggere il progetto, la richiesta non riesce con `404` e
`not_found`.

### <span id="list-assignees">Elenca gli assegnatari</span>

Invia l'ID del progetto per ottenere tutti gli account a cui puoi assegnare
problemi in quel progetto:

```bash
curl "$LOGBREW_API_URL/api/telemetry/issues/assignees?project_id=$PROJECT_ID" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

L'elenco contiene ogni account che può leggere il progetto. Ogni voce contiene
`user_id`, `name` e `email`. `name` vale `null` quando l'account non ha un
nome. Aggiungi `response_version=2` per ricevere anche `teams`: ogni team
dell'organizzazione del progetto, con `team_id`, `slug` e `name`. Consulta la
[risposta della lista degli assegnatari](/it/reference/telemetry-response-shapes#assignee-list-response).
Qualsiasi account che può leggere il progetto può ottenere questo elenco. Se
l'account non può leggere il progetto, la richiesta non riesce con `404` e
`not_found`.

Quando un membro perde l'accesso al progetto, i problemi assegnati a quel
membro non mostrano alcun assegnatario. Se il membro ottiene di nuovo
l'accesso, i problemi mostrano di nuovo quel membro, a meno che nel frattempo
qualcuno non abbia cambiato o rimosso l'assegnatario.

### Regole dei referenti e referenti suggeriti

`GET /api/telemetry/issues/ownership?project_id=<project-uuid>` restituisce
`rules`, `codeowners`, `updated_at` e `unresolved_owners`. Qualsiasi account
che può leggere il progetto può leggerli. `PUT` con `project_id` e `rules`,
`codeowners` o entrambi sostituisce quel testo e richiede il permesso di
gestire i problemi. Un campo che non invii mantiene il suo testo, e una
stringa vuota lo cancella. Ogni testo è di massimo 128 KiB. Un testo non
valido non riesce con `422` e indica la riga.

`GET /api/telemetry/issues/{issue_id}/owners?response_version=2` restituisce
`suggested_assignee`, `owners` e `inputs`. Ogni referente ha `type` (`user`
o `team`), `source` (`ownership_rule`, `codeowners` o `recent_activity`),
`rule`, `line` e `matched`. La versione 1, quella predefinita, elenca solo gli
account.

### Cronologia del problema

`GET /api/telemetry/issues/{issue_id}/activity?response_version=2` restituisce
`activity`, dalla voce più recente, e `next_cursor`. Ogni voce ha `type`
(`status`, `priority`, `assigned`, `unassigned`, `severity_rule` o
`first_seen`), `value`, `actor_id`, `actor`, `assignee_id`, `assignee`,
`team` e `at`. `limit` va da 1 a 200, 50 per impostazione predefinita. Invia
`cursor_time` e `cursor_id` presi da `next_cursor` per la pagina successiva.

### Notifiche

`GET /api/telemetry/issues/notifications` restituisce `notifications`,
`unread`, `read_at` e `next_cursor`. Ogni notifica è l'assegnazione di un
problema a te o al tuo team da parte di un altro account. `POST
/api/telemetry/issues/notifications/read` con un oggetto JSON vuoto, oppure
con `read_at`, sposta il tuo segno di lettura. Il segno non torna mai
indietro.

### Imposta le regole per problemi e log

Una regola cambia il modo in cui LogBrew mostra i segnali corrispondenti. Non
elimina dati. La `severity` acquisita resta invariata e la risposta mostra la
regola in `triage`.

| Richiesta | Corpo JSON |
| --- | --- |
| `PUT /api/telemetry/issues/{issue_id}/triage-rule` | `{ "severity": "<value>" }` |
| `PUT /api/logs/{log_id}/triage-rule` | `{ "severity": "<value>", "ignored": true }` |

`severity` vale `info`, `warning`, `error`, `critical` o `source`. `source`
rimuove la sostituzione e mostra di nuovo la gravità acquisita. Per una regola
sui log, `ignored: true` nasconde i log corrispondenti dall'elenco predefinito
dei log. Leggili con `status=ignored` o `status=all`. La regola si applica ai
segnali corrispondenti conservati e futuri. Un altro valore non riesce con
`422` e `validation_failed`.

  Non inviare release vuote. LogBrew le rifiuta per mantenere affidabile il
  tracciamento delle release.
</Warning>

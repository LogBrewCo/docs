Esta página muestra un ejemplo de cada familia de respuestas de la
[API de telemetría](/es/reference/telemetry-api). Todos los valores son
ficticios. Para los códigos de error y cómo recuperarte, consulta
[Errores de la API](/es/reference/api-errors).

## Lee una respuesta

Lee cada respuesta en este orden:

1. Lee el estado HTTP.
2. Comprueba que el cuerpo tiene la estructura propia de la ruta.
3. Comprueba que cada `project_id` está dentro del alcance de proyecto
   solicitado.
4. Conserva sin cambios los valores canónicos de los enums y los
   identificadores.
5. Sigue `next_action` solo cuando el cliente admita su `code` y su
   `target`.
6. Trata `null`, un campo omitido y una lista vacía como estados distintos.

Un `200 OK` puede contener una lista vacía. Una lista de logs vacía significa
que ningún log coincidió con la solicitud. No significa que las incidencias,
las trazas o las acciones también estén vacías. No relaciones señales porque
sus marcas de tiempo estén próximas. Sigue una traza solo cuando la respuesta
contenga su `trace_id` exacto.

Un `404` y una lista vacía son resultados distintos. Una ruta de lista
devuelve `[]` cuando ningún registro coincide. Una ruta de detalle devuelve
`404` con `code: not_found` cuando no encuentra un registro legible. Ninguno de
los dos resultados demuestra que la ingesta haya fallado.

## Qué enviar

Las respuestas solo son tan útiles como la telemetría que envías. Envía estos
valores en cada sobre o configuración del SDK:

- `release` y `environment`.
- Nombres estables para servicios, acciones y métricas.
- Contexto de la traza cuando los logs, los spans, las acciones y las
  incidencias pertenecen a la misma solicitud.
- Valores canónicos de severidad: `info`, `warning`, `error` y `critical`.
- Atributos que ayuden a depurar, sin secretos ni datos personales
  innecesarios.

Consulta [Integración del SDK](/es/guides/sdk-ingestion) y
[Controlar los datos capturados](/es/guides/safe-capture).

## Respuesta de ingesta

Los SDK públicos leen la respuesta de `POST /v1/events` por ti. El código de tu
aplicación no tiene que gestionarla.

### Respuesta de lote del SDK

Un lote del SDK aceptado devuelve `200 OK` con el número de eventos aceptados
de cada flujo:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Campo | Significado |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Eventos de este lote que LogBrew aceptó. |
| `already_accepted` | Eventos cuyo ID LogBrew ya había aceptado. LogBrew no los vuelve a guardar. |
| `context_updated` | `true` cuando el lote actualizó el contexto de release o de entorno. |

Los recuentos cubren solo este lote. Si reintentas un lote que LogBrew ya
aceptó, la respuesta devuelve `0` en cada flujo y el número de eventos en
`already_accepted`. Conserva los ID de evento originales al reintentar.

### Respuesta del sobre nativo

`POST /api/telemetry/ingest` devuelve `200 OK` con el número de elementos
aceptados de cada flujo:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

La respuesta nativa no tiene los campos `metrics` ni `context_updated`. No los
añadas. `already_accepted` cuenta los elementos cuyo `id` LogBrew ya había
aceptado para el proyecto. Consulta el
[sobre nativo directo](/es/guides/sdk-ingestion#required-envelope-fields).

### Errores de ingesta

Un `401` con `code: ingest_key_invalid` significa que el token bearer de ingesta
está revocado, ha caducado o no es válido para el proyecto. En
`POST /v1/events`, si falta el token bearer o no es una clave de ingesta,
la respuesta es `401` con `code: unauthorized`. Usa el token bearer de ingesta
actual del proyecto. No reintentes con un token bearer de cuenta.

Un lote del SDK rechazado devuelve `422` con `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Otros valores de `error` son `SDK event batch requires at least one event` y
`SDK event type is not supported by this ingest route`. Comprueba la versión
del SDK y la configuración del transporte. No envíes un lote vacío. No cambies
los tipos ni los ID de los eventos solo para que un lote pase la validación.

Una solicitud con un método distinto de `POST` devuelve `405` con
`code: method_not_allowed`. Un cuerpo JSON ilegible devuelve
`code: invalid_json`.

## Formato de respuesta de las listas de telemetría

Las rutas de lista devuelven un array JSON simple de forma predeterminada. Una
lista vacía correcta es `[]`.

Con `pagination=cursor`, la ruta devuelve un sobre. La clave de la colección
corresponde a la señal:

| Ruta | Clave de la colección |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, con un `issue_id` en el nivel superior |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, con un `naming_quality` en el nivel superior |

`next_cursor` es un objeto con los campos para continuar, o `null` en la última
página. Las filas van de la más reciente a la más antigua. Consulta
[paginación por cursor](/es/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Respuesta de logs</span>

Una página por cursor de logs con `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Los logs incluyen `level` por compatibilidad y `severity` para mostrar. Los
dos tienen el valor canónico. `triage` guarda el resultado de una regla de
severidad. Consulta
[respuestas de las reglas de severidad](#severity-rule-responses).

`trace_id` y `span_id` son `null` cuando el log no tiene enlace a una traza. En
ese caso, `next_action` es `inspect_related_logs` con el destino
`telemetry_logs`. Los logs, las incidencias y las acciones usan los mismos 2
pares de `next_action`.

`GET /api/logs/{log_id}` devuelve un log con la misma estructura.

### <span id="issue-response">Respuesta de incidencias</span>

`GET /api/telemetry/issues/{issue_id}` devuelve una incidencia agrupada. La
lista devuelve los mismos objetos. Este ejemplo usa la versión de respuesta
predeterminada, la 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

En la versión 1, `status` es `unresolved`, `resolved` o `ignored`. En una
incidencia archivada, `triage.ignored` es `true`. Para ver los pares de
`next_action` y las lecturas que siguen, consulta
[Investigar una incidencia](/es/guides/investigate-an-issue).

`first_seen_at` y `last_seen_at` son las horas de la primera ocurrencia y de la
más reciente. No cambian cuando cambia el estado.

Algunos campos aparecen solo cuando LogBrew tiene los datos:

| Campo | Cuándo aparece |
| --- | --- |
| `span_id` | La incidencia tiene un enlace a un span. Si no, el campo se omite. |
| `diagnostics` | La última ocurrencia tiene un tipo de excepción o pasos anteriores. Consulta [historial de ocurrencias de una incidencia](#issue-occurrence-history). |
| `symbolication` | Solo en `GET /api/telemetry/issues/{issue_id}`, cuando la incidencia tiene una identidad de artefacto de release. Consulta [Mapas de origen de JavaScript](/es/guides/source-maps). |

`symbolication.status` es `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` o `unavailable`. La lista, los
cambios de estado y los cambios de reglas no devuelven `symbolication`.

Con `response_version=2`, la incidencia tiene los mismos campos, con estos
cambios:

| Campo | Valor en la versión 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` o `archived`. La versión 1 muestra `archived` como `ignored`. |
| `priority` | `high`, `medium` o `low`. |
| `priority_source` | `manual` cuando una persona fijó la prioridad. `derived` cuando la prioridad sigue la severidad efectiva. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Este ejemplo muestra solo algunos campos. Una prioridad derivada es `high` para
`error` y `critical`, `medium` para `warning` y `low` para `info`. Usa
`triage.effective_severity`, así que una regla de severidad de la incidencia
puede cambiarla.

Con `response_version=3`, la incidencia tiene todos los campos de la versión 2
y `assignee`. `assignee` es `null` cuando la incidencia no tiene responsable:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Campo | Significado |
| --- | --- |
| `assignee.user_id` | ID de usuario del responsable. Envíalo como `assignee` en un filtro o en un cambio. |
| `assignee.name` | Nombre del responsable, o `null` cuando la cuenta no tiene nombre. |
| `assignee.email` | Dirección de correo electrónico del responsable. |

Una incidencia aparece sin responsable cuando el miembro asignado ya no puede
leer el proyecto.

Con `response_version=4`, `assignee` también tiene `type`. Un responsable
`user` tiene `user_id`, `name` y `email`, como en la versión 3. Un responsable
`team` tiene `team_id`, `slug` y `name`. La versión 3 muestra un equipo
responsable como `null`. La CLI solicita la versión 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Cualquier otro `response_version` devuelve `422` con
`code: validation_failed`. Una página por cursor usa la misma versión para
todas las incidencias de `issues`.

### <span id="assignee-list-response">Respuesta de la lista de responsables</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` devuelve todas
las cuentas a las que se pueden asignar incidencias en el proyecto:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Añade `response_version=2` para obtener también `teams`: todos los equipos de
la organización del proyecto, con `team_id`, `slug` y `name`.

Si la cuenta no puede leer el proyecto, la ruta devuelve `404` con
`code: not_found`.

### <span id="action-response">Respuesta de acciones</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` sigue a un actor o a una sesión. Trata `distinct_id` y
`session_id` como identificadores opacos. `session_id` y `trace_id` son `null`
cuando faltan. `span_id` se omite cuando falta. Una acción no tiene severidad.
Consulta [Captura de eventos de producto](/es/guides/product-events).

### Respuesta de métricas

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Cada elemento es una muestra. No uses el número de muestras como recuento de
eventos o de usuarios. `unit`, `temporality`, `trace_id` y `span_id` son
`null` cuando faltan. Un valor `null` no es cero.

### Respuesta de releases

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Una fila cubre un proyecto, un release, un entorno y un servicio. Sus
recuentos describen solo esa fila.

`trace_health.status` es `unknown` cuando la fila no tiene trazas,
`no_errors_observed` o `errors_observed`. `error_rate_basis_points` es la
proporción de trazas con un span de error, de `0` a `10000`. No es una tasa de
error de todas las solicitudes.

`next_action` apunta al primer tipo de señal que tiene datos, en este orden:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Consulta [Releases](/es/concepts/releases).

### Respuesta de la búsqueda de trazas

`GET /api/telemetry/traces?pagination=cursor` devuelve una fila por traza y un
comprobante `naming_quality` de la página devuelta:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` cubre solo la página devuelta. No es una puntuación de toda la
cuenta. `truncated: true` significa que existe otra página. Cuando la página
tiene un nombre genérico, una ruta sin coincidencia o una operación genérica,
`next_action` es `improve_trace_naming` con el destino `sdk_configuration`. Sin
`pagination=cursor`, la ruta devuelve un array simple de trazas y ningún
`naming_quality`.

`next_cursor` contiene `time` y `trace_id`. Envíalos como `cursor_time` y
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` devuelve los spans de una traza.
`GET /api/telemetry/traces/{trace_id}/summary` devuelve el span raíz, los spans
de error, los servicios, la duración y la ruta más lenta, sin los atributos
sin procesar de los spans. Un `404` del resumen significa que ninguna traza
coincidió con el alcance completo. No reintentes sin los filtros. Consulta
[respuestas de spans y del resumen de una traza](#trace-spans-and-summary-responses).

### Listas vacías y registros ausentes

Una lectura de lista puede no tener coincidencias. Una lectura de detalle tiene
otro contrato:

| Solicitud | Éxito | Ningún registro legible |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` con un [log](#log-response) | `404` con `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` con una [incidencia](#issue-response) | `404` con `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` con ocurrencias | `404` con `code: not_found` en la primera página |
| `GET /api/telemetry/traces/{trace_id}` | `200` con spans | `200` con `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` con un resumen | `404` con `code: not_found` |

Un log ausente devuelve este `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Una incidencia ausente usa `"error": "issue not found"`. Un resumen de traza
ausente usa `"error": "trace not found"`. Un ID desconocido y un ID que la
cuenta no puede leer devuelven la misma respuesta.

Una lista con un `project_id` que la cuenta no puede leer devuelve `200` con
una lista vacía. Comprueba el ID del proyecto antes de informar de que no hay
datos.

### Selecciones de proyectos rechazadas

Las listas de logs, incidencias, acciones, métricas, releases y trazas aceptan
un proyecto con `project_id` o de 2 a 50 proyectos con `project_ids`. El
catálogo de atributos de logs acepta los mismos selectores. El historial de
ocurrencias de una incidencia no los acepta.

Una solicitud con `project_id` y `project_ids` a la vez devuelve `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` con un UUID no válido, un ID repetido, o menos de 2 o más de 50
ID también devuelve `422` con `code: validation_failed`.

Si la cuenta no puede leer uno de los proyectos de `project_ids`, toda la
solicitud devuelve `404`. No devuelve los demás proyectos como resultado
parcial:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Muestra el error, no una lista vacía ni un recuento de cero. Vuelve a leer la
lista de proyectos. No quites un proyecto sin avisar y no reintentes con todos
los proyectos. Una credencial delegada, como un grant de MCP, devuelve `403`
con `code: forbidden` para un proyecto fuera de su grant. Consulta
[alcance del proyecto](/es/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Errores de cursor</span>

Los logs, las incidencias, las acciones, las métricas y las ocurrencias de
incidencias usan `cursor_time` y `cursor_id`. Un cursor rechazado devuelve
`422` con `code: validation_failed`. Estos errores no significan que la lista
esté vacía.

| Solicitud | `error` |
| --- | --- |
| `pagination=cursor` con solo 1 de los 2 campos de cursor | `cursor_time and cursor_id must be sent together` |
| `cursor_time` que no es una marca de tiempo RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Campos de cursor sin `pagination=cursor`, o con otro valor de `pagination` | `pagination must be cursor when cursor pagination is requested` |

Por ejemplo:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Copia el `next_cursor` completo de la página anterior. No sustituyas
`cursor_time` por la hora actual. Si perdiste el cursor, empieza de nuevo con
`pagination=cursor` y los filtros originales. Una clave de consulta
desconocida o un valor de tipo incorrecto devuelve `422` con
`"error": "invalid query parameters"`.

### Respuestas con cursor de releases

Un cursor de releases tiene 5 campos. Una solicitud correcta sin coincidencias
devuelve `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Cuando `next_cursor` no es `null`, envía los 5 valores en la siguiente
solicitud:

| Campo de `next_cursor` | Parámetro de consulta |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` marca una posición. No sustituye a `project_id` ni a
`project_ids`. Conserva los parámetros de proyecto y de filtro originales.
Codifica cada valor para URL.

Con `pagination=cursor`, un cursor parcial o un valor vacío de release,
entorno o servicio devuelve `422` con
`"error": "all release cursor fields must be sent together"`. Un `cursor_time`
no válido y la falta de `pagination=cursor` devuelven los mismos errores que
los [demás cursores](#cursor-errors).

### Errores de la búsqueda de trazas

Estos errores se aplican a `GET /api/telemetry/traces`. Cada uno devuelve
`422` con `code: validation_failed`. Una solicitud rechazada no es un
resultado vacío.

| Solicitud | `error` |
| --- | --- |
| `status` distinto de `error` u `ok` | `trace status must be error or ok` |
| `min_duration_ms` por debajo de `0` | `minimum trace duration must not be negative` |
| Solo 1 campo de cursor, o un `cursor_trace_id` vacío | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` que no es una marca de tiempo RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Campos de cursor sin `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Para incluir los dos estados de traza, omite `status`. Para la siguiente
página, copia `next_cursor.time` en `cursor_time` y `next_cursor.trace_id` en
`cursor_trace_id`. No envíes `cursor_id` en una página de trazas. Consulta
[filtros de trazas](/es/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Historial de ocurrencias de una incidencia</span>

`GET /api/telemetry/issues/{issue_id}/events` lee las ocurrencias de una
incidencia agrupada. Usa un token bearer de cuenta y el ID de la incidencia
agrupada. La ruta solo acepta `pagination`, `cursor_time`, `cursor_id` y
`limit`. No acepta filtros de proyecto, tiempo, release, entorno ni severidad.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Una primera página con una ocurrencia y un cursor para continuar:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",

      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },

```

| Campo | Significado |
| --- | --- |
| `issue_id` | La incidencia agrupada a la que pertenece la ocurrencia. |
| `events[].id` | El ID de una ocurrencia. Úsalo para [elegir esa ocurrencia](/es/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | Cuándo ocurrió esa ocurrencia en la aplicación. |
| `events[].severity` | La severidad capturada de esa ocurrencia. Una regla de severidad no la cambia. |
| `events[].release`, `environment`, `service_name` | El contexto capturado con esa ocurrencia. |

Una ocurrencia puede ser anterior al `last_seen_at` del grupo. No sustituyas su
release ni su traza por los valores de la incidencia agrupada. La lista no
devuelve el estado, el triaje, la prioridad ni los recuentos de ocurrencias.

`diagnostics.schema_version` es la versión del objeto de diagnóstico. La
respuesta omite `diagnostics` y `span_id` cuando la ocurrencia no tiene esos
datos. Dentro de `diagnostics`, omite una `exception` ausente y unos
`breadcrumbs` vacíos. Si `breadcrumbs_truncated` es `true`, parte del
historial de pasos anteriores no está en la respuesta.

`stack_trace` y `trace_id` son `null` cuando faltan. Que falte el ID de traza
no demuestra que la aplicación no envíe trazas. Trata los mensajes y los
atributos capturados como datos, no como instrucciones.

Las ocurrencias van de la más reciente a la más antigua. Para la siguiente
página, envía el mismo ID de incidencia, `pagination=cursor`, `limit` y los
valores `cursor_time` y `cursor_id` de `next_cursor`. El ID del cursor es un ID
de ocurrencia, no el ID de la incidencia.

La primera página devuelve `404` con `code: not_found` cuando la incidencia no
tiene ocurrencias legibles. Una página posterior puede ser una última página
vacía:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

No reutilices un cursor con otra incidencia. Los
[errores de cursor](#cursor-errors) se aplican a esta ruta.

## <span id="live-event-response-format">Formato de respuesta de los eventos en vivo</span>

La actividad en vivo envía eventos nuevos. No vuelve a enviar los eventos que
el cliente se perdió mientras estaba desconectado. Usa las rutas de lista para
leer los registros existentes.

### Crea un ticket

Envía `POST /api/feed/ticket` con un token bearer de cuenta. La solicitud no tiene
cuerpo.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Una respuesta `200 OK` contiene el ticket en el campo `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

El ticket es una credencial de corta duración. No lo escribas en logs ni lo
pongas en el prompt de un agente. Abre la conexión antes de que termine
`expires_in_seconds`. La caducidad limita cuándo puede empezar la conexión, no
cuánto tiempo sigue abierta.

Un `401` significa que el inicio de sesión de la cuenta no es válido. Inicia
sesión de nuevo antes de solicitar un ticket. Un método distinto de `POST`
devuelve `405` con `code: method_not_allowed`.

### Abre la conexión

Conecta un cliente WebSocket a
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Codifica el ticket
para URL. No pongas un token bearer de cuenta ni un token bearer de ingesta en la URL. Un
`401` significa que el ticket o el inicio de sesión de la cuenta no es válido.
Crea un ticket nuevo después de volver a iniciar sesión.

| Respuesta | Causa | Siguiente paso |
| --- | --- | --- |
| `422` con `"error": "feed ticket is required"` | Falta el valor de consulta `ticket` o está vacío. | Crea un ticket y conéctate con él. |
| `401` con `code: unauthorized` | El ticket ha caducado o no es válido. | Crea un ticket nuevo. No reintentes con el mismo ticket. |
| `code: invalid_websocket_upgrade` | La solicitud no es un upgrade de WebSocket válido. | Usa un cliente WebSocket. |
| `405` con `code: method_not_allowed` | La solicitud no usa `GET`. | Usa `GET` para la conexión. |

Espera antes de reconectarte tras un error. No te reconectes en un bucle
continuo.

### Lee los mensajes

Cada mensaje es un sobre `{ "type": "...", "data": ... }`. Lee `type` antes de
analizar `data`. Omite los tipos que el cliente no admita.

| Tipo de evento | Contenido de `data` |
| --- | --- |
| `native_log` | Datos del log, con la estructura de la [respuesta de logs](#log-response). |
| `native_issue` | Datos de la incidencia agrupada, con la estructura de la [respuesta de incidencias](#issue-response) de la versión 1. |
| `native_trace_span` | Un span, con la estructura de un elemento de la [lista de spans](#span-list). |
| `native_action` | Datos de la acción de producto, con la estructura de la [respuesta de acciones](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Datos del proyecto. Vuelve a leer la lista de proyectos cuando cambie. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Uso de la cuenta, con la estructura de [uso de la cuenta](/es/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Un evento `native_issue` usa la versión 1 de la respuesta de incidencias: una
incidencia archivada aparece como `ignored` y el evento no tiene prioridad. Las
métricas y los releases no son tipos de eventos en vivo. Léelos con sus rutas
de lista. El ticket no selecciona un proyecto. Comprueba el `project_id` de
cada evento antes de mostrarlo en la vista de un proyecto.
`logbrew watch --json` usa esta actividad. Consulta [Referencia de la CLI](/es/reference/cli).

### Gestiona una conexión cerrada

| Código de cierre | Motivo | Siguiente paso |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Espera y reconéctate con un ticket nuevo. Vuelve a leer las rutas de lista para obtener los registros que te perdiste. |
| `1008` | `live feed access changed; sign in again` | Deja de reconectarte. Inicia sesión de nuevo antes de crear un ticket nuevo. |

Otras desconexiones pueden no tener un motivo de LogBrew. Después de
reconectarte, vuelve a leer las rutas de lista y relaciona los registros por
ID.

## <span id="issue-status-response-examples">Ejemplos de respuestas de estado de incidencias</span>

`PATCH /api/telemetry/issues/{issue_id}` con `{ "status": "resolved" }`
devuelve `200 OK` con la incidencia agrupada actualizada, con la misma
estructura que la [respuesta de incidencias](#issue-response). La clave de
consulta `response_version` selecciona la versión. No devuelve un indicador de
éxito.

El cuerpo define 1 o más de estos campos: `status`, `priority` y `assignee`.
`status` acepta `unresolved`, `resolved` o `archived`. `ignored` es un nombre
antiguo de `archived`. Consulta
[Actualiza una incidencia](/es/reference/telemetry-api#update-one-issue).

Comprueba los valores devueltos de `id`, `status` y `priority` antes de
mostrar que el cambio se hizo. No construyas el resultado a partir de los
valores enviados. Un cambio de estado no elimina ocurrencias ni cambia
`first_seen_at` ni `last_seen_at`. Tampoco cambia `severity` ni una regla de
severidad.

Un cambio rechazado devuelve `422` con `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Resultado | Causa |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | El cuerpo no tiene ninguno de los 3 campos. |
| `422`, `issue priority must be high, medium, or low` | El valor de prioridad no es compatible. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | El valor del responsable no es compatible. |
| `422`, `issue assignee cannot read this project` | El responsable no tiene acceso al proyecto. LogBrew no cambia nada. |
| `422`, `issue assignee team is not a team of this project's organization` | El equipo no pertenece a la organización del proyecto. LogBrew no cambia nada. |
| `403` con `code: forbidden` | La cuenta no puede gestionar incidencias en el proyecto. |
| `404` con `code: not_found` | La cuenta no puede leer la incidencia o la incidencia no existe. |

Un campo que ya tiene el valor solicitado no cambia. Tras un tiempo de espera
agotado o una respuesta perdida, vuelve a enviar la misma solicitud o lee
antes la incidencia. No envíes otro cambio antes de leer el estado actual.
Consulta [Escrituras](/es/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` devuelve `200 OK` con 1 resultado por cada
ID de incidencia solicitado, en el orden de la solicitud. Cada incidencia
encontrada usa la estructura de la versión 3. Un resultado `not_found` tiene
`issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
```

Una solicitud en bloque falla por completo en estos casos:

| Resultado | Causa |
| --- | --- |

| `422`, `issue_ids must not contain duplicates` | Un ID aparece más de una vez. |
| `422` con `code: invalid_json` | El cuerpo tiene un campo desconocido. |
| `403` con `code: forbidden` | La cuenta no puede gestionar incidencias en el proyecto. |
| `404`, `project not found` | La cuenta no puede leer el proyecto. |

## Alcance de las solicitudes de analíticas

Las rutas de analíticas, la ruta de series de métricas y la ruta de volumen de
señales leen un proyecto y un intervalo de tiempo. Cada solicitud necesita
`project_id` y `since`. `since` acepta una duración compacta como `24h` o `7d`,
o una marca de tiempo RFC3339. `until` acepta una marca de tiempo RFC3339 y,
de forma predeterminada, es la hora de la solicitud. El intervalo de tiempo
incluye `since`, excluye `until` y no puede superar 31 días.

`service_name`, `release` y `environment` son filtros exactos opcionales. Cada
valor debe tener de 1 a 256 caracteres después de que LogBrew quite los
espacios de los extremos. La ruta de comparación de segmentos pone estos
filtros dentro de cada segmento, no en el nivel superior.

Si la cuenta no puede leer el proyecto, estas rutas devuelven `200 OK` con
recuentos a cero. No devuelven `404`. Un resultado vacío no confirma el acceso
al proyecto. Compara `project_id` con los proyectos que la cuenta puede leer.
Una solicitud a través de un grant de MCP que no incluye el proyecto devuelve
`403` y `forbidden`.

| Ruta | Valores de `response_version` | Valor predeterminado |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` o `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` o `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | No se acepta | Esquema `1` |
| `POST /api/telemetry/analytics/paths` | No se acepta | Esquema `1` |
| `GET /api/telemetry/metrics/series` | No se acepta | Esquema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Cada respuesta empieza con `schema_version`, `query` y `purpose`. `query`
repite el alcance efectivo. Omite los filtros que no enviaste. `purpose` es un
texto simple que explica qué responde la ruta.

Una tasa se omite cuando su denominador es cero. Una tasa omitida no es `0` ni
`null`. Lee `coverage` antes de fiarte de una tasa.

### <span id="shared-scope-errors">Errores de alcance compartidos</span>

Estos errores usan HTTP `422` y `validation_failed`:

| Causa | `error` |
| --- | --- |
| Falta `project_id` | `product analytics project_id is required` |
| Falta `since` | `product analytics since is required` |
| `since` no es una duración ni una marca de tiempo RFC3339 | `invalid since value` |
| `until` no es una marca de tiempo RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` no es anterior a `until` | `product analytics since must be earlier than until` |
| El intervalo de tiempo supera 31 días | `product analytics range must not exceed 31 days` |
| Un filtro vacío o de más de 256 caracteres | `product analytics context filters must be non-empty and at most 256 characters` |

Por ejemplo, una solicitud sin `project_id` devuelve:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Las rutas de series de métricas y de volumen de señales usan las mismas reglas
de alcance, con su propio texto de `error`. Sus secciones, más abajo, enumeran
esos errores.

Una clave de consulta desconocida devuelve `422` con la respuesta de
[parámetros de consulta no válidos](/es/reference/api-errors#invalid-query-parameters).
Un campo JSON desconocido, la falta de un campo JSON obligatorio o un valor de
enum no admitido devuelve `invalid_json`. Consulta
[JSON no válido](/es/reference/api-errors#invalid-json). Una solicitud con un
método HTTP incorrecto devuelve `405` y `method_not_allowed`. Su texto `next`
indica el método y los campos admitidos. Consulta
[Método no admitido](/es/reference/api-errors#unsupported-method).

### Lee la conversión y la cobertura

`entry_rate` es `entered_units` dividido entre `candidate_units`: 50 de 60.
`overall_conversion_rate` es `completed_units` dividido entre
`entered_units`: 15 de 50, es decir, un 30 %. No es 15 dividido entre todos
los candidatos. Estos recuentos no explican por qué se detuvieron las
unidades.

La cobertura cuenta eventos, no sesiones. Aquí, 120 eventos coinciden con un
paso y 20 de ellos no tienen ID de sesión. El resultado excluye esos 20
eventos de los recuentos de sesiones. No los trates como 20 sesiones
fallidas.

El primer paso no tiene `conversion_from_previous`. El último paso no tiene
`drop_off_to_next_units` ni `drop_off_to_next_rate`.

Una unidad llega a un paso posterior solo cuando las horas de los pasos
aumentan estrictamente. Los eventos con la misma marca de tiempo no pueden
cumplir dos pasos consecutivos. El último paso debe ocurrir dentro de
`conversion_window_seconds` desde el primero.

El modo de sesión cuenta sesiones, no personas. Usa `identified_user` solo con
eventos que lleven un ID de sujeto opaco de tipo `user`. Ese modo puede unir
eventos de sesiones distintas dentro de la ventana de conversión. Mantén la
misma unidad y los mismos pasos cuando compares resultados.

El valor predeterminado de `conversion_window_seconds` es 24 horas o la
duración del intervalo de tiempo, lo que sea menor. El máximo es la duración
del intervalo de tiempo en segundos completos, redondeada hacia arriba.

### Resultados de embudo vacíos

Una respuesta vacía correcta sigue mostrando los pasos solicitados con
`units` a cero. Si no hay unidades candidatas, `summary` omite `entry_rate` y
`overall_conversion_rate`. La ruta no devuelve `404` porque ningún evento
coincida.

Lee `coverage` y `next_action` para encontrar la causa:

| `next_action.code` | Causa |
| --- | --- |
| `capture_product_activity` | No hay eventos clasificados en el alcance. |
| `choose_captured_funnel_steps` | Ningún evento coincide con un paso solicitado. |
| `sessionize_product_activity` | Hay eventos de los pasos, pero ninguno tiene ID de sesión. |
| `identify_product_users` | Hay eventos de los pasos, pero ninguno tiene un sujeto de tipo `user`. |
| `verify_funnel_entry` | Ninguna unidad entró en el paso 1. |
| `investigate_funnel_drop_off` | Entraron unidades, pero ninguna completó todos los pasos. |
| `compare_funnel_contexts` | Al menos una unidad completó el embudo. |

### Solicitudes de embudo rechazadas

Además de los [errores de alcance compartidos](#shared-scope-errors), estas
solicitudes devuelven `422` y `validation_failed`. Menos de 2 pasos o más de
8:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Un `conversion_window_seconds` de `0`, o un valor mayor que la duración del
intervalo de tiempo:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Un `event_name` vacío, de más de 256 caracteres o con un carácter de control
devuelve
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Un paso `interaction` también debe ser un nombre de acción válido. Si no, el
error es `product analytics interaction event_name must be a bounded stable action name`.

Corrige la solicitud antes de volver a enviarla. No quites pasos ni cambies la
unidad de análisis solo para obtener un resultado que no esté vacío.

La retención y el ciclo de vida aceptan dos estructuras de solicitud. Usa

| Análisis | `response_version` | Selectores de evento |
| --- | --- | --- |
| Retención de eventos exactos | `1`, u omitido | Envía `start_event` y `return_event`. |
| Ciclo de vida de un evento exacto | `1`, u omitido | Envía `event`. |
| Retención o ciclo de vida automáticos | `2` | No envíes ningún selector de evento. |

Un selector exacto contiene `kind` y `event_name`. `kind` es `page_view`,
`screen_view` o `interaction`. Copia `event_name` de
`classified_activity.top_events`. No adivines el nombre de un evento a partir
de la etiqueta de un botón.

Las dos estructuras cuentan solo usuarios: ID de sujeto opacos de tipo
`user`. Los sujetos anónimos y los eventos sin un ID de sujeto utilizable no
cuentan como usuarios. Las respuestas nunca devuelven ID de sujeto.

Los periodos fijos son `hour`, `day`, `week` y `thirty_day`. Son duraciones
fijas. `thirty_day` son 30 días, no un mes del calendario. Si omites
`interval`, la API usa `hour` para un intervalo de tiempo de 48 horas o menos,
y `day` para uno más largo.

cambie la actividad capturada.

### Lee una serie de métricas

El primer punto registra 10 tareas completadas, no 10 muestras.
`rate_per_second` divide ese cambio entre los 300 segundos del intervalo.
`last` es el último cambio registrado, no la suma. Consulta
[qué significa cada agregación de métricas](/es/concepts/telemetry#read-the-metric-value).

El tipo y la temporalidad de una serie determinan su `aggregation.code` y las
estadísticas de cada punto. Un punto omite las estadísticas que no se
aplican. Una estadística ausente no es cero.

| Tipo y temporalidad | `status` | `aggregation.code` | `value` | Otras estadísticas |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Última muestra | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Suma de los cambios | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 aproximado | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Cualquier tipo, `cumulative` | `limited` | `raw_cumulative_last` | Última muestra sin procesar | `last`, `min`, `max` |
| Cualquier otra combinación | `limited` | `raw_last` | Última muestra sin procesar | `last`, `min`, `max` |

`limited` es una respuesta correcta, no un error. Añade
`aggregation.limitation`, que explica por qué LogBrew muestra solo valores sin
procesar. `ready` no demuestra que la captura esté completa.

Lee `coverage` antes de dibujar un gráfico:

- `samples` cuenta las muestras de todas las series que coinciden, incluidas
  las series que la respuesta no devuelve.
- `series` cuenta las series que coinciden. `returned_series` y `points`
  cuentan los datos devueltos.
- `truncated` es `true` cuando `series_limit` quitó series con menos volumen.
- `expected_buckets_per_series` es el número de intervalos posibles en el
  intervalo de tiempo.

No añadas un punto para un intervalo sin muestras. No insertes un cero ni
copies el valor anterior. Cada punto devuelve hasta 3 `trace_exemplars`. Un
ejemplar de traza enlaza una muestra con una traza. No explica todas las
muestras del intervalo. Si ningún punto tiene un ejemplar de traza,
`next_action.target` es `metric_samples`.

### Alcance y errores de las series de métricas

`project_id`, `name` y `since` son obligatorios. `name` puede tener como
máximo 200 caracteres. `interval` es `auto`, `1m`, `5m`, `15m`, `1h`, `6h` o
`1d`. El valor predeterminado es `auto`, que selecciona el intervalo más
pequeño con 300 intervalos como máximo. Un intervalo explícito no puede
necesitar más de 500 intervalos.

`group_by` es `none`, `service_name`, `release` o `environment`. El valor
predeterminado es `none`. Sin agrupación, los distintos tipos, unidades y
temporalidades siguen en series separadas. `series_limit` acepta de `1` a
`20`. El valor predeterminado es `10`.

Un resultado vacío devuelve `200` con `series: []` y `samples` a cero. El
objeto `coverage` omite `first_seen_at` y `last_seen_at`. Esto no demuestra
que la aplicación nunca haya enviado la métrica. Comprueba el proyecto, el
nombre de la métrica y el intervalo de tiempo.

Si omites `name`, la respuesta es `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Intervalos de un minuto a lo largo de siete días devuelven `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Otros errores `422` son `metric series group_by is not supported`,
`metric series interval is not supported` y
`metric series_limit must be between 1 and 20`.

`following` y los más recientes para `preceding`. Un ancla fuera de ese límite
puede omitirse.

solo al ancla, no a los eventos que la rodean. Los valores distinguen entre
mayúsculas y minúsculas. Cuando hay filtros, `query` los repite y
`coverage.anchor_property_filters` informa de esto:

| Campo | Significado |
| --- | --- |
| `context_events` | Eventos ancla del alcance antes de aplicar los filtros de propiedades. |
| `property_ready_events` | Eventos ancla que tienen todas las claves solicitadas. |
| `missing_property_events` | Eventos ancla a los que les falta una o más de las claves solicitadas. |
| `matching_events` | Eventos ancla cuyos valores coinciden con todos los filtros. |
| `nonmatching_value_events` | Eventos ancla que tienen todas las claves, pero un valor distinto. |
| `property_ready_rate` | `property_ready_events` dividido entre `context_events`. |
| `match_rate` | `matching_events` dividido entre `property_ready_events`. |

Las claves ausentes y los valores distintos necesitan correcciones distintas.
No los sumes. El objeto se omite cuando la solicitud no tiene ningún filtro de
propiedades.

## <span id="analytics-segment-comparison">Comparación de segmentos de analíticas</span>

`POST /api/telemetry/analytics/segments/compare` compara con qué frecuencia
las sesiones o los usuarios llegan a un evento exacto en 2 a 4 segmentos de un
proyecto. Un segmento selecciona eventos por servicio, release, entorno y
valores de propiedades. El primer segmento es la referencia.

### Define la comparación

Envía este cuerpo JSON con autenticación de cuenta y
`Content-Type: application/json`. Aquí, `basic` y `premium` son valores de
plan de la aplicación de ejemplo, no planes de LogBrew:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }
  ]
}
```

`target` y `segments` son obligatorios. `analysis_unit` es `session` o
`identified_user`. El valor predeterminado es `session`, que cuenta sesiones,
no personas. `interval` acepta los mismos valores que el resumen. El valor
predeterminado es `auto`.

Cada segmento necesita una `key` única, una `label` y un conjunto de filtros
distinto:

- `key`: de 1 a 32 bytes. Empieza por una letra ASCII minúscula o un dígito.
  Usa solo letras ASCII minúsculas, dígitos, `_` y `-`.
- `label`: de 1 a 80 caracteres, sin caracteres de control.
- `service_name`, `release`, `environment`: opcionales. Cada valor tiene de 1
  a 256 caracteres, sin caracteres de control.
- `property_filters`: de 0 a 4 filtros. Cada clave puede aparecer una vez en
  un segmento. Un evento debe coincidir con todos los filtros del segmento.
  Los valores distinguen entre mayúsculas y minúsculas, tienen de 1 a 256
  caracteres y LogBrew quita los espacios del principio y del final.

Un segmento sin filtros selecciona toda la actividad clasificada del proyecto
y del intervalo de tiempo. Los segmentos pueden solaparse. Una etiqueta o una
clave distinta no hace válidos dos conjuntos de filtros idénticos.

### Lee las tasas y las diferencias

`eligible_units` estima las sesiones o los usuarios con actividad clasificada
en el segmento. `reached_units` estima cuántos de ellos llegaron al objetivo.
`reach_rate` es `reached_units` dividido entre `eligible_units`. Los eventos
sin el ID de la unidad seleccionada no cuentan para estas unidades.

La tasa de la referencia es del 20 %. La tasa del segmento premium es del
30 %. La diferencia es de 10 puntos porcentuales. La mejora relativa es del
50 %, no del 10 %. Los pequeños errores decimales vienen de la aritmética de
coma flotante. Redondea las tasas para mostrarlas, pero calcula con los
valores devueltos. El segmento de referencia no tiene
`comparison_to_baseline`. La mejora relativa se omite cuando la tasa de
alcance de la referencia es cero.

En `query`, un filtro de segmento que no enviaste es `null`. Una lista
`property_filters` vacía se omite.

`coverage.property_filters` tiene los mismos campos que la
[cobertura de los filtros del ancla de las rutas](#filter-the-anchor-by-property).
Aquí, `matching_events` es igual a `classified_events`. Mantén separadas las
claves ausentes y los valores distintos. Los segmentos pueden solaparse, y una
sesión puede aparecer en varios intervalos. No sumes los recuentos de unidades
de distintos segmentos o intervalos.

La comparación es descriptiva. `confidence.causal_inference` es
`not_established` y `confidence.statistical_significance` es `not_tested`.
Una tasa del 30 % frente a una del 20 % no demuestra que un plan haya causado
más pagos.

### Errores de la comparación de segmentos

Además de los [errores de alcance compartidos](#shared-scope-errors), estas
solicitudes devuelven `422` y `validation_failed`:

| Causa | `error` |
| --- | --- |
| Menos de 2 segmentos o más de 4 | `product analytics segment comparison requires two through four segments` |
| Dos segmentos con la misma clave | `product analytics segment keys must be unique` |
| Dos segmentos con los mismos filtros | `product analytics segment filters must be unique` |
| Una clave que no tiene de 1 a 32 bytes permitidos | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| Una etiqueta vacía, demasiado larga o con un carácter de control | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| Un valor de filtro con un carácter de control | `product analytics segment filters must be control-free` |
| Más de cuatro filtros de propiedades en un segmento | `product analytics segments accept at most four exact property filters` |
| Una clave que no está en el catálogo de propiedades | `product analytics segment property keys must be supported privacy-safe keys` |
| La misma clave de propiedad dos veces en un segmento | `product analytics segment property keys must be unique within each segment` |
| Un valor de propiedad vacío, demasiado largo o con un carácter de control | `product analytics segment property values must be non-empty, control-free, and at most 256 characters` |
| Un `response_version` distinto de `1` o `2` | `product analytics response_version must be 1 or 2` |

Los errores de `interval` son los mismos que los
[errores del resumen](#overview-errors).

Por ejemplo, dos segmentos con claves distintas y filtros idénticos devuelven:

```json

```

Una etiqueta distinta o un orden distinto de los filtros de propiedades no
cambia los eventos seleccionados. Un error de validación no es evidencia de
que ningún evento coincida.

## Respuesta del volumen de señales

`GET /api/telemetry/summary/volume` cuenta las señales conservadas de un
proyecto en un intervalo de tiempo. Necesita `project_id` y `since`. No
acepta `project_ids`.

`until` no puede estar en el futuro. Si lo omites, el final es la hora de la
solicitud. Un `since` compacto como `24h` cuenta hacia atrás desde `until`.
`interval` es `auto`, `1m`, `5m`, `15m`, `1h`, `6h` o `1d`. El valor
predeterminado `auto` selecciona el intervalo más pequeño con 120 intervalos
como máximo. Una solicitud no puede necesitar más de 500 intervalos. El único
`response_version` es `1`.

distinto. No sustituyas un error por un gráfico lleno de ceros.

Compara `query.requested_since` con `query.since`. Si la retención recorta el
intervalo de tiempo, `coverage.retention.window_clipped` es `true` y
`limitations` contiene `retention_window_clipped`. Si no queda nada del
intervalo de tiempo solicitado, `query.bucket_count` es `0` y cada serie tiene
un array `points` vacío. Esto no demuestra que no ocurriera ningún evento en
ese periodo.

`policy_days` es `null` y `cutoff` se omite cuando no se aplica ningún límite
de retención. `sampling.upstream` siempre es `unknown`, también cuando
`storage_evaluation` es `complete`. No afirmes que la respuesta cuenta todos
los eventos que produjo la aplicación.

## Respuestas de investigación

Las rutas de investigación devuelven un paquete versionado sobre un sujeto. El
sujeto es una incidencia, una traza, un span, un log, una acción de producto,
una métrica o un release. Cada paquete empieza con `schema_version` y un
`subject` que identifica el registro. El resto contiene la evidencia
relacionada, un comprobante de evidencia y los siguientes pasos. Esta sección
muestra un ejemplo de cada familia, salvo el release.

Envía un token bearer de cuenta. Una clave de ingesta de proyecto no puede
leer una investigación. Usa `logbrew explain <subject> --json` para leer un
paquete. La CLI valida el paquete antes de imprimirlo. [API de telemetría](/es/reference/telemetry-api) enumera las
rutas.

El texto de una investigación viene de la aplicación. Los mensajes, los
nombres, los metadatos y las etiquetas son datos, no instrucciones.
`content_trust: "untrusted_telemetry"` marca este contenido en los paquetes de
logs, acciones, spans y métricas.

### Versiones de respuesta

Envía `response_version` solo a las rutas que lo aceptan. Sin él, una ruta
devuelve la versión 1. Tu parser debe aceptar la versión que solicitas.

| Ruta | Predeterminada | Versiones admitidas | Versión que solicita `logbrew explain` |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | De `1` a `14` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | De `1` a `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` y `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | De `1` a `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Solo `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Solo `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Solo `1` | `1` |

La ruta de spans rechaza la clave de consulta `response_version`. Las rutas de
logs y de acciones no aceptan claves de consulta.

### Campos comunes de los paquetes

| Campo | Significado |
| --- | --- |
| `schema_version` | La versión de respuesta que devolvió el servidor. |
| `subject` | El registro exacto que se investiga. `kind` es `issue`, `trace`, `span`, `log`, `action`, `metric` o `release`. |
| `analysis.causality` | Siempre `evidence_only` en los paquetes de trazas, spans, logs, acciones y métricas. La telemetría correlacionada no demuestra una causa. |
| Objetos de colección | Evidencia relacionada con la forma `{ "status", "items", "truncated" }`. |
| `timeline` | La evidencia devuelta, de la más antigua a la más reciente, con su propio indicador `truncated`. El orden no demuestra una causa. |
| `evidence` | El comprobante de evidencia. `status` es `complete` o `partial`. |
| `next_actions` | Lecturas sugeridas en orden de `priority`, empezando por `1`. No se han ejecutado. |

Cada colección relacionada informa de un `status` de disponibilidad:

| Estado | Significado | Comportamiento del cliente |
| --- | --- | --- |
| `available` | La lectura terminó y devolvió elementos. | Muestra los elementos y el indicador `truncated`. |
| `not_linked` | El sujeto no tiene un identificador para este enlace, como un ID de traza. | Explica que falta el enlace. No lo construyas a partir de marcas de tiempo. |
| `not_found` | La lectura terminó y no encontró evidencia conservada. | Muestra un resultado vacío. |
| `unavailable` | La lectura opcional falló. El sujeto sigue siendo válido. | Mantén visible el sujeto. Reintenta más tarde. No muestres cero elementos como resultado. |

El comprobante de evidencia tiene cuatro listas ordenadas de nombres de campo
estables: `captured_fields`, `missing_fields`, `redacted_fields` y
`truncated_fields`. `status` es `complete` solo cuando las tres últimas listas
están vacías. Los datos ocultos no son datos ausentes. Los datos truncados no
son datos completos. No rellenes un valor oculto o truncado.

### Límites de la investigación

Estos límites acotan una respuesta. Un indicador `truncated` o una entrada en
`truncated_fields` indica que un límite omitió datos.

| Evidencia | Límite |
| --- | --- |
| Elementos relacionados en una colección | 20 |
| Spans conservados leídos para una traza | 1.000 |
| Elementos de la línea de tiempo | 50 en los paquetes de logs, acciones y spans. 100 en los paquetes de trazas y métricas. |
| Atributos estructurados, propiedades y metadatos | 64 valores escalares, 4 niveles de objetos o arrays, 16 elementos en cada array, 512 caracteres en cada cadena |
| Intervalo de tiempo de correlación | 5 minutos antes y después de un log, una acción o la ocurrencia de incidencia seleccionada. En una traza o un span, 5 minutos antes del inicio y después del final, 24 horas como máximo. |

La sección de cada familia enumera sus propios límites.

### Respuesta de la investigación de una incidencia

evidencia de una ocurrencia de una incidencia agrupada. [Investigar una incidencia](/es/guides/investigate-an-issue) muestra
cómo leer la evidencia en orden. Solicita la versión 13:

Las claves de consulta son `response_version`, `selection` y
`occurrence_id`. `selection` es `recommended`, `first` o `latest`. Los valores
distinguen entre mayúsculas y minúsculas. En las versiones 2 a 14, si omites
el selector, se usa `recommended`. La versión 1 devuelve la última ocurrencia
conservada y no acepta ningún selector. Los filtros de la lista de incidencias
no se aplican a esta lectura.

| `event` | 1 | La ocurrencia seleccionada: SDK, `context`, `exception`, `stack_frames` y `breadcrumbs`. En la versión 1, es `null` cuando no se puede leer ninguna ocurrencia reciente. |
| `cause` | 1 | `status` es `reported_hypothesis`, `evidence_only` o `unknown`. `signals` enumera las señales observadas. |
| `fix` | 1 | Una ubicación en el código. `status` es `reported_location`, `observed_application_frame`, `observed_frame`, `observed_underlying_exception_frame` o `unknown`. |
| `impact` | 1 | Recuentos de ocurrencias y `user_impact`. `reported` contiene el impacto informado por la aplicación o `null`. |
| `correlations` | 1 | `trace`, `logs`, `actions`, `metrics` y `release`. |
| `occurrence_selection` | 2 | El selector solicitado, el motivo y resúmenes de las ocurrencias seleccionada, primera, última y recomendada. |
| `lifecycle` | 3 | `persisted_status`, `effective_status`, la actividad de estado y `regression`. `effective_status` puede ser `regressed`. |

devuelve como máximo 10 valores. Una pila tiene como máximo 32 marcos.

#### Errores de solicitud de la investigación de una incidencia

Usa `selection` o `occurrence_id`, no los dos. No los envíes juntos, aunque
seleccionen la misma ocurrencia:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Causa | Recuperación |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | La solicitud tiene los dos selectores. | Deja un solo selector. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | La solicitud tiene un selector y la versión 1, o ninguna versión. | Envía `response_version=13`. Conserva el selector. |
| `422` | `issue investigation response_version must be 1 through 14` | La versión está fuera del rango. | Envía una versión admitida. |
| `422` | `invalid query parameters` | Una clave desconocida, un UUID no válido, una versión que no es un número entero o un valor de `selection` desconocido. | Corrige la [consulta](/es/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | La ocurrencia no está en el historial conservado de este grupo. | Copia el ID de la ocurrencia de los eventos de esta incidencia. No uses `latest` ni `recommended` en su lugar sin aprobación. |
| `404` | `issue not found` | Ningún proyecto legible tiene esta incidencia. | Comprueba la cuenta y el UUID de la incidencia. No envíes el UUID de una ocurrencia como ID de la incidencia. |

Que falte una ocurrencia no significa que falte la incidencia. Un `404` no
indica si otra cuenta puede leer la incidencia.

### Respuesta de la investigación de una traza

Usa `GET /api/telemetry/traces/{trace_id}/investigation` para leer una traza
con su ruta de fallo, su ruta más lenta y las señales relacionadas. Las claves
de consulta son `response_version`, `project_id`, `release` y `environment`.
Todas son opcionales. Solicita la versión 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

La versión 2 añade `cause` y `fix` a cada incidencia relacionada. La versión 3
añade `span_id` a las incidencias, acciones y métricas relacionadas cuando se
capturó.

### Respuesta de la investigación de un span

Usa `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` para
leer una operación de una traza. Envía `project_id`, `environment` y
`release`. Los tres son obligatorios. Cópialos del span seleccionado. No
envíes el `id` de la fila del span como `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### Respuesta de la investigación de un log

Usa `GET /api/logs/{log_id}/investigation` para leer un log y su evidencia
relacionada. Esta ruta no tiene claves de consulta. Copia el ID del log de una
lista de logs.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

La lectura puede devolver evidencia fuera de los filtros de la lista de logs.
Las lecturas relacionadas usan el proyecto, el entorno y el release del log, y
los 5 minutos anteriores y posteriores al log. Los logs cercanos también usan
el mismo servicio. No necesitan un ID de traza. Las lecturas de la traza
exacta necesitan el ID de traza del log y pueden incluir otros servicios. El
resumen de la traza usa el mismo ID de traza y el mismo alcance, sin el
intervalo de tiempo.

### Respuesta de la investigación de una acción

Usa `GET /api/telemetry/actions/{action_id}/investigation` para leer una
acción de producto, su estado informado y la evidencia relacionada. Esta ruta
no tiene claves de consulta. Las lecturas relacionadas usan el mismo
intervalo de tiempo y los mismos alcances que la investigación de un log.

`correlations`, `timeline` y `next_actions` usan las estructuras de la
investigación de un log. Las acciones relacionadas excluyen la acción del
sujeto.

### Respuesta de la investigación de una métrica

Usa `GET /api/telemetry/metrics/investigation` para leer un nombre de métrica

otros tipos de señales.

| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Omite `response_version` o envía `2`. |
| `422` | `metric series project_id is required` | Envía un ID de proyecto legible. |
| `422` | `metric series name is required` | Copia el nombre de la lista de métricas. |
| `422` | `metric series since is required` | Envía un valor como `24h` o una marca de tiempo RFC 3339. |

| `422` | `metric series interval would exceed 500 buckets` | Usa `interval=auto` o un intervalo más amplio. |

`none`, `service_name`, `release` o `environment`. Otros valores devuelven
`422`.

### Errores de investigación

| HTTP | Ruta | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Acción | `action not found` |
| `404` | Traza | `trace not found` |
| `422` | Traza | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, acción, incidencia | `invalid URL path parameters` cuando el ID de la ruta no es un UUID |
| `422` | Incidencia, traza, span, métrica | `invalid query parameters` para una clave desconocida o un valor de tipo incorrecto |

Un `404` significa que ningún proyecto legible tiene el registro. Cada ruta
también devuelve `401` sin una autenticación válida y `405` con un método
distinto de `GET`. Consulta [Errores de la API](/es/reference/api-errors) para
ver las respuestas de
[recurso no encontrado](/es/reference/api-errors#resource-not-found),
[ruta](/es/reference/api-errors#invalid-path-value),
[autenticación](/es/reference/api-errors#authentication-failure) y
[método](/es/reference/api-errors#unsupported-method).

Una lectura de evidencia opcional puede fallar dentro de una respuesta
`200 OK`. En ese caso, la colección informa de `unavailable`. No lo muestres
como `not_found` ni como cero registros.

## <span id="severity-values">Valores de severidad</span>

Los valores de severidad que ven los usuarios son `info`, `warning`, `error` y
`critical`. Los SDK y los runtimes pueden enviar alias comunes como `trace`,
`debug`, `warn` o `fatal`. Las respuestas REST y en vivo siempre devuelven el
valor canónico. Por ejemplo, LogBrew acepta `warn` como entrada y devuelve
`warning`. La ingesta rechaza los valores de severidad desconocidos.

| Alias | Valor canónico |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Respuestas de las reglas de severidad</span>

Una regla de severidad cambia cómo muestra LogBrew un log o una incidencia. No
cambia la severidad que capturó la aplicación. Los logs y las incidencias
devuelven un objeto `triage`:

| Campo | Significado |
| --- | --- |
| `effective_severity` | La severidad que se muestra. Sin una regla, es igual a `severity`. |
| `ignored` | `true` cuando una regla de logs ignora el log o cuando la incidencia está archivada. |
| `rule_applied` | `true` cuando se aplica una regla de severidad o el estado ignorado. `false` es el valor predeterminado, no un dato ausente. |

Usa `triage.effective_severity` para mostrar la severidad. Conserva
`severity` como valor capturado. De forma predeterminada, la lista de logs
omite los logs ignorados. Envía `status=ignored` o `status=all` en
`GET /api/logs` para incluirlos.

La cuenta debe tener permiso para gestionar incidencias en el proyecto. El
acceso de lectura no basta. Sin ese permiso, un cambio de regla devuelve `403`
con `code: forbidden`.

### Cambia una regla de logs

`PUT /api/logs/{log_id}/triage-rule` define la regla del log y de los logs
posteriores con la misma firma. El cuerpo necesita `severity` e `ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Una respuesta `200 OK` contiene el [log](#log-response) completo. Su
`severity` sigue siendo `warning`. Su `triage` muestra la regla:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Este extracto muestra solo los campos que cambian. En la solicitud,
`severity` es `source`, `info`, `warning`, `error` o `critical`. `source`
restaura la severidad capturada. No vuelve activo un log ignorado. Para volver
a mostrar el log, envía `"ignored": false`.

### Cambia una regla de incidencias

`PUT /api/telemetry/issues/{issue_id}/triage-rule` define la severidad que se
muestra para una incidencia agrupada y sus ocurrencias posteriores. El cuerpo
solo acepta `severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Una respuesta `200 OK` contiene la [incidencia](#issue-response) completa en
la versión 1. Los valores capturados de `severity` y `status` no cambian:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Este extracto muestra solo algunos campos. Una regla no resuelve, archiva ni
reabre una incidencia. Para eso, usa el
[cambio de estado](#issue-status-response-examples). Una prioridad derivada
sigue la nueva severidad efectiva. Lee la incidencia con
`response_version=2` o `3` para verla.

Una severidad no admitida devuelve `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Un campo desconocido en el cuerpo, como `status` en una regla de incidencias,
devuelve `422` con `code: invalid_json`. Un log o una incidencia ausente o
ilegible devuelve `404` con `code: not_found`. Si se pierde la respuesta,
vuelve a leer el log o la incidencia antes de enviar de nuevo la regla.

## Formato de respuesta de error

Los errores de la aplicación devuelven un sobre JSON. Este ejemplo muestra una
solicitud rechazada. El texto de `error` y de `next` depende del problema:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Usa `code` para las ramas del programa y `next_action` para la automatización.
Muestra `error` y `next` a las personas como texto simple. No analices su
redacción. Algunos errores añaden campos, como `limit`, `reset_at` o
`retry_after_seconds`. Una respuesta sin cuerpo JSON no tiene `code` de
LogBrew. Consulta [Errores de la API](/es/reference/api-errors) para ver todos
los códigos.

## Lee datos con la CLI

La CLI lee las mismas rutas y devuelve el mismo JSON con `--json`. Empieza con
una consulta amplia y luego acótala:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Añade `--pagination cursor` para obtener el sobre con cursor. La CLI solicita
la versión 4 de la respuesta de incidencias. Consulta
[Lee la página siguiente](/es/reference/cli#read-the-next-page) y
[Observación en vivo](/es/reference/cli#live-watch).

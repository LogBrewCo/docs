Deze pagina toont één voorbeeld voor elk type response van de
[Telemetrie-API](/nl/reference/telemetry-api). Alle waarden zijn fictief. Zie
[API-fouten](/nl/reference/api-errors) voor foutcodes en herstel.

## Een response lezen

Lees elke response in deze volgorde:

1. Lees de HTTP-status.
2. Controleer of de body de vorm heeft die bij de route hoort.
3. Controleer of elk `project_id` binnen de gevraagde projectscope valt.
4. Laat canonieke enumwaarden en ID's ongewijzigd.
5. Volg `next_action` alleen als de client de bijbehorende `code` en
   `target` ondersteunt.
6. Behandel `null`, een weggelaten veld en een lege lijst als verschillende
   toestanden.

Een `200 OK` kan een lege lijst bevatten. Een lege loglijst betekent dat geen
enkele log bij het request paste. Dat betekent niet dat issues, traces of
acties ook leeg zijn. Koppel signalen niet omdat hun tijdstempels dicht bij
elkaar liggen. Volg een trace alleen als de response het exacte `trace_id`
ervan bevat.

Een `404` en een lege lijst zijn verschillende resultaten. Een lijstroute geeft
`[]` terug als geen enkel record overeenkomt. Een detailroute geeft `404` met
`code: not_found` terug als die geen leesbaar record vindt. Geen van beide
resultaten bewijst dat de opname is mislukt.

## Wat je verstuurt

Een response is maar zo nuttig als de telemetrie die je verstuurt. Stuur deze
waarden mee in elke envelop of SDK-installatie:

- `release` en `environment`.
- Vaste namen voor services, acties en metrics.
- Tracecontext als logs, spans, acties en issues bij hetzelfde request horen.
- Canonieke ernstwaarden: `info`, `warning`, `error` en `critical`.
- Attributen die helpen bij debuggen, zonder geheimen of onnodige
  persoonsgegevens.

Zie [SDK-integratie](/nl/guides/sdk-ingestion) en
[Vastgelegde gegevens beheren](/nl/guides/safe-capture).

## Response van de ingest-API

De openbare SDK's lezen de response van `POST /v1/events` voor je. Je
applicatiecode hoeft die niet af te handelen.

### Response op een SDK-batch

Een geslaagde SDK-batch geeft `200 OK` terug met de geaccepteerde aantallen per
stroom:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Veld | Betekenis |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Events uit deze batch die LogBrew heeft geaccepteerd. |
| `already_accepted` | Events waarvan LogBrew het ID eerder al accepteerde. LogBrew slaat ze niet opnieuw op. |
| `context_updated` | `true` als de batch de release- of omgevingscontext heeft bijgewerkt. |

De aantallen gelden alleen voor deze batch. Stuur je een batch opnieuw die
LogBrew al accepteerde, dan krijg je `0` voor elke stroom en het aantal events
in `already_accepted`. Houd de oorspronkelijke event-ID's aan als je het
opnieuw probeert.

### Response op een native envelop

`POST /api/telemetry/ingest` geeft `200 OK` terug met het aantal geaccepteerde
items per stroom:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

De native response heeft geen veld `metrics` of `context_updated`. Voeg ze niet
toe. `already_accepted` telt items waarvan LogBrew de `id` eerder al voor het
project accepteerde. Zie de [directe native envelop](/nl/guides/sdk-ingestion#required-envelope-fields).

### Opnamefouten

Een `401` met `code: ingest_key_invalid` betekent dat de ingest-bearer is
ingetrokken, verlopen of niet geldig is voor het project. Op
`POST /v1/events` geeft een ontbrekende bearer, of een bearer die geen
ingest-sleutel is, `401` met `code: unauthorized`. Gebruik de huidige
projectgebonden ingest-bearer. Probeer het niet opnieuw met een
account-bearer.

Een geweigerde SDK-batch geeft `422` met `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Andere waarden van `error` zijn onder meer
`SDK event batch requires at least one event` en
`SDK event type is not supported by this ingest route`. Controleer de
SDK-versie en de transportconfiguratie. Stuur geen lege batch. Wijzig geen
eventtypes of ID's alleen om een batch door de validatie te krijgen.

Een request met een andere methode dan `POST` geeft `405` met
`code: method_not_allowed`. Een onleesbare JSON-body geeft `code: invalid_json`.

## Responseformaat van telemetrielijsten

Lijstroutes geven standaard een gewone JSON-array terug. Een geslaagde lege lijst
is `[]`.

Met `pagination=cursor` geeft de route een envelop terug. De collectiesleutel
hoort bij het signaal:

| Route | Collectiesleutel |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, met een `issue_id` op het hoogste niveau |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, met een `naming_quality` op het hoogste niveau |

`next_cursor` is een object met de velden om verder te lezen, of `null` op de
laatste pagina. Rijen staan van nieuw naar oud. Zie [cursorpaginering](/nl/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Logresponse</span>

Een cursorpagina met logs en `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Logs bevatten `level` voor compatibiliteit en `severity` voor weergave. Beide
bevatten de canonieke waarde. `triage` bevat het resultaat van een ernstregel.
Zie [responses van ernstregels](#severity-rule-responses).

`trace_id` en `span_id` zijn `null` als de log geen tracekoppeling heeft. Dan
is `next_action` gelijk aan `inspect_related_logs` met als doel
`telemetry_logs`. Logs, issues en acties gebruiken dezelfde 2 paren voor
`next_action`.

`GET /api/logs/{log_id}` geeft één log terug in dezelfde vorm.

### <span id="issue-response">Issueresponse</span>

`GET /api/telemetry/issues/{issue_id}` geeft één gegroepeerd issue terug. De
lijst geeft dezelfde objecten terug. Dit voorbeeld gebruikt de
standaardversie 1 van de response:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

In versie 1 is `status` gelijk aan `unresolved`, `resolved` of `ignored`. Voor
een gearchiveerd issue is `triage.ignored` gelijk aan `true`. Zie
[Een issue onderzoeken](/nl/guides/investigate-an-issue) voor de paren van
`next_action` en de leesacties die erop volgen.

`first_seen_at` en `last_seen_at` zijn de tijdstippen van het eerste en het
meest recente voorval. Ze veranderen niet als de status verandert.

Sommige velden verschijnen alleen als LogBrew de gegevens heeft:

| Veld | Wanneer het verschijnt |
| --- | --- |
| `span_id` | Het issue heeft een spankoppeling. Anders laat de response het veld weg. |
| `diagnostics` | Het laatste voorval heeft een exceptiontype of breadcrumbs. Zie [voorvalgeschiedenis van een issue](#issue-occurrence-history). |
| `symbolication` | Alleen op `GET /api/telemetry/issues/{issue_id}`, als het issue de identiteit van een release-artefact heeft. Zie [Source maps voor JavaScript](/nl/guides/source-maps). |

`symbolication.status` is `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` of `unavailable`. De lijst,
statuswijzigingen en regelwijzigingen geven geen `symbolication` terug.

Met `response_version=2` heeft het issue dezelfde velden, met deze wijzigingen:

| Veld | Waarde in versie 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` of `archived`. Versie 1 toont `archived` als `ignored`. |
| `priority` | `high`, `medium` of `low`. |
| `priority_source` | `manual` als iemand de prioriteit heeft ingesteld. `derived` als de prioriteit de effectieve ernst volgt. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Dit voorbeeld toont maar een deel van de velden. Een afgeleide prioriteit is
`high` voor `error` en `critical`, `medium` voor `warning` en `low` voor
`info`. Die prioriteit gebruikt `triage.effective_severity`, dus een ernstregel
voor het issue kan die veranderen.

Met `response_version=3` heeft het issue alle velden van versie 2 en
`assignee`. `assignee` is `null` als het issue aan niemand is toegewezen:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Veld | Betekenis |
| --- | --- |
| `assignee.user_id` | Gebruikers-ID van het toegewezen account. Stuur het als `assignee` in een filter of een wijziging. |
| `assignee.name` | Naam van dat account, of `null` als het account geen naam heeft. |
| `assignee.email` | E-mailadres van dat account. |

Een issue toont geen toewijzing als het toegewezen lid het project niet meer
kan lezen.

Met `response_version=4` heeft `assignee` ook `type`. Een toewijzing aan een
account (`user`) heeft `user_id`, `name` en `email`, zoals in versie 3. Een
toewijzing aan een team (`team`) heeft `team_id`, `slug` en `name`. Versie 3
toont een toewijzing aan een team als `null`. De CLI vraagt versie 4 op:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Elke andere `response_version` geeft `422` met `code: validation_failed`. Een
cursorpagina gebruikt dezelfde versie voor elk issue in `issues`.

### <span id="assignee-list-response">Response met toewijsbare accounts en teams</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` geeft elk account
terug waaraan je issues in het project kunt toewijzen:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Voeg `response_version=2` toe om ook `teams` te krijgen: elk team van de
organisatie van het project, met `team_id`, `slug` en `name`.

Als het account het project niet kan lezen, geeft de route `404` met
`code: not_found`.

### <span id="action-response">Actieresponse</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` volgt één actor of sessie. Behandel `distinct_id` en
`session_id` als ondoorzichtige ID's. `session_id` en `trace_id` zijn `null`
als ze ontbreken. `span_id` ontbreekt als er geen waarde is. Een actie heeft
geen ernst. Zie [Productevents vastleggen](/nl/guides/product-events).

```json
{

  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
```

### Releaseresponse

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Eén rij gaat over één project, release, omgeving en service. De aantallen
beschrijven alleen die rij.

`trace_health.status` is `unknown` als de rij geen traces heeft, en anders
`no_errors_observed` of `errors_observed`. `error_rate_basis_points` is het
aandeel traces met een foutspan, van `0` tot `10000`. Het is geen
foutpercentage voor alle requests.

`next_action` wijst naar het eerste signaaltype met gegevens, in deze volgorde:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Zie [Releases](/nl/concepts/releases).

### Response bij het zoeken naar traces

`GET /api/telemetry/traces?pagination=cursor` geeft één rij per trace terug,
plus een overzicht in `naming_quality` voor de teruggegeven pagina:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` gaat alleen over de teruggegeven pagina. Het is geen score
voor het hele account. `truncated: true` betekent dat er nog een pagina is. Als
de pagina een generieke naam, een niet-herkende route of een generieke bewerking
bevat, is `next_action` gelijk aan `improve_trace_naming` met als doel
`sdk_configuration`. Zonder `pagination=cursor` geeft de route een gewone array
van traces terug, zonder `naming_quality`.

`next_cursor` bevat `time` en `trace_id`. Stuur ze als `cursor_time` en
`cursor_trace_id`.

Met `response_version=2` heeft elke trace ook `capture_span_count` en
`capture_error_count`. Dan tellen `span_count` en `error_span_count` de
[vastleggingsspans](/nl/concepts/distributed-tracing#capture-spans) niet mee.
Versie 1 telt ze wel mee. `status=error` komt overeen met een trace als
`error_span_count` of `capture_error_count` groter is dan `0`.

`GET /api/telemetry/traces/{trace_id}` geeft de spans van één trace terug.
`GET /api/telemetry/traces/{trace_id}/summary` geeft de rootspan, de foutspans,
de services, de duur en het traagste pad terug, zonder ruwe spanattributen.
Een `404` op de samenvatting betekent dat geen enkele trace bij de volledige
scope paste. Probeer het niet opnieuw zonder de filters. Zie [responses voor trace-spans en samenvattingen](#trace-spans-and-summary-responses).

### Lege lijsten en ontbrekende records

Een lijst lezen kan nul resultaten opleveren. Voor het lezen van één record
geldt een ander contract:

| Request | Gelukt | Geen leesbaar record |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` met één [log](#log-response) | `404` met `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` met één [issue](#issue-response) | `404` met `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` met voorvallen | `404` met `code: not_found` op de eerste pagina |
| `GET /api/telemetry/traces/{trace_id}` | `200` met spans | `200` met `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` met één samenvatting | `404` met `code: not_found` |

Een ontbrekende log geeft deze `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Een ontbrekend issue gebruikt `"error": "issue not found"`. Een ontbrekende
tracesamenvatting gebruikt `"error": "trace not found"`. Een onbekend ID en een
ID dat het account niet kan lezen, geven dezelfde response.

Een lijstrequest met één `project_id` dat het account niet kan lezen, geeft
`404` met `"error": "project selection not found"`. Een onbekend project-ID geeft
dezelfde response. Zie
[geweigerde projectselecties](#rejected-project-selections).

### <span id="rejected-project-selections">Geweigerde projectselecties</span>

De lijsten voor logs, issues, acties, metrics, releases en traces accepteren
één project met `project_id` of 2 tot 50 projecten met `project_ids`. De
catalogus met logattributen accepteert dezelfde selectors. De
voorvalgeschiedenis van een issue accepteert ze niet.

Een request met zowel `project_id` als `project_ids` geeft `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` met een ongeldige UUID, een dubbel ID, of minder dan 2 of meer
dan 50 ID's geeft ook `422` met `code: validation_failed`.

Als het account het project van `project_id` of één project in een set
`project_ids` niet kan lezen, geeft het hele request `404`. Het geeft de andere projecten niet terug als gedeeltelijk
resultaat:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Toon de fout, geen lege lijst of een aantal van nul. Lees de projectlijst
opnieuw. Verwijder niet stilletjes een project en probeer het niet opnieuw over
alle projecten. Gedelegeerde toegangsgegevens, zoals een MCP-verbinding, geven
`403` met `code: forbidden` voor een project buiten die verbinding. Zie
[projectscope](/nl/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Cursorfouten</span>

Logs, issues, acties, metrics en voorvallen van issues gebruiken `cursor_time`
en `cursor_id`. Een geweigerde cursor geeft `422` met
`code: validation_failed`. Deze fouten betekenen niet dat de lijst leeg is.

| Request | `error` |
| --- | --- |
| `pagination=cursor` met maar 1 van de 2 cursorvelden | `cursor_time and cursor_id must be sent together` |
| `cursor_time` dat geen RFC3339-tijdstempel is | `cursor_time must be an RFC3339 timestamp` |
| Cursorvelden zonder `pagination=cursor`, of een andere waarde voor `pagination` | `pagination must be cursor when cursor pagination is requested` |

Bijvoorbeeld:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Kopieer de volledige `next_cursor` van de vorige pagina. Vervang `cursor_time`
niet door de huidige tijd. Ben je de cursor kwijt? Begin dan opnieuw met
`pagination=cursor` en de oorspronkelijke filters. Een onbekende queryparameter
of een waarde van het verkeerde type geeft `422` met
`"error": "invalid query parameters"`.

### Responses van de releasecursor

Een releasecursor heeft 5 velden. Een geslaagd request zonder resultaten geeft
`200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Als `next_cursor` niet `null` is, stuur je alle 5 waarden mee met het volgende
request:

| Veld in `next_cursor` | Queryparameter |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` markeert een positie. Het vervangt `project_id` of
`project_ids` niet. Houd de oorspronkelijke project- en filterparameters aan.
URL-codeer elke waarde.

Met `pagination=cursor` geeft een onvolledige cursor, of een lege waarde voor
release, omgeving of service, `422` met
`"error": "all release cursor fields must be sent together"`. Een ongeldige
`cursor_time` en een ontbrekende `pagination=cursor` geven dezelfde fouten als
de [andere cursors](#cursor-errors).

### Fouten bij het zoeken naar traces

Deze fouten gelden voor `GET /api/telemetry/traces`. Elke fout geeft `422` met
`code: validation_failed`. Een geweigerd request is geen leeg resultaat.

| Request | `error` |
| --- | --- |
| `status` anders dan `error` of `ok` | `trace status must be error or ok` |
| `min_duration_ms` onder `0` | `minimum trace duration must not be negative` |
| Maar 1 cursorveld, of een lege `cursor_trace_id` | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` dat geen RFC3339-tijdstempel is | `cursor_time must be an RFC3339 timestamp` |
| Cursorvelden zonder `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |
| `response_version` anders dan `1` of `2` | `trace response_version must be 1 or 2` |

Laat `status` weg om beide tracestatussen mee te nemen. Kopieer voor de
volgende pagina `next_cursor.time` naar `cursor_time` en `next_cursor.trace_id`
naar `cursor_trace_id`. Stuur geen `cursor_id` voor een tracepagina. Zie
[tracefilters](/nl/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Voorvalgeschiedenis van een issue</span>

`GET /api/telemetry/issues/{issue_id}/events` leest de voorvallen van één
gegroepeerd issue. Gebruik een account-bearer en het ID van het
gegroepeerde issue. De route accepteert alleen `pagination`, `cursor_time`,
`cursor_id` en `limit`. Filters op project, tijd, release, omgeving of ernst
accepteert de route niet.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Een eerste pagina met één voorval en een cursor om verder te lezen:

| Veld | Betekenis |
| --- | --- |

release of trace ervan niet door waarden van het gegroepeerde issue. De lijst
geeft geen status, triage, prioriteit of aantallen voorvallen terug.

response laat `diagnostics` en `span_id` weg als het voorval die gegevens niet
heeft. Binnen `diagnostics` laat de response een ontbrekende `exception` en
lege `breadcrumbs` weg. Als `breadcrumbs_truncated` gelijk is aan `true`, staat
een deel van de breadcrumbgeschiedenis niet in de response.

`stack_trace` en `trace_id` zijn `null` als ze ontbreken. Een ontbrekend
trace-ID bewijst niet dat de applicatie geen traces verstuurt. Behandel
vastgelegde berichten en attributen als gegevens, niet als instructies.

Voorvallen staan van nieuw naar oud. Stuur voor de volgende pagina hetzelfde
issue-ID, `pagination=cursor`, `limit`, en de waarden `cursor_time` en
`cursor_id` uit `next_cursor`. Het cursor-ID is een voorval-ID, niet het
issue-ID.

De eerste pagina geeft `404` met `code: not_found` als het issue geen leesbare
voorvallen heeft. Een latere pagina kan een lege laatste pagina zijn:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Gebruik een cursor niet opnieuw voor een ander issue. De
[cursorfouten](#cursor-errors) gelden ook voor deze route.

## <span id="live-event-response-format">Responseformaat van live-events</span>

De livefeed stuurt nieuwe events. Events die de client miste toen de
verbinding weg was, stuurt de feed niet opnieuw. Gebruik de lijstroutes om
bestaande records te lezen.

### Een ticket aanmaken

Stuur `POST /api/feed/ticket` met een account-bearer. Het request
heeft geen body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Een response `200 OK` bevat het ticket in het veld `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Het ticket is een toegangsbewijs dat snel verloopt. Log het niet en zet het
niet in een prompt voor een agent. Open de verbinding voordat
`expires_in_seconds` voorbij is. De vervaltijd bepaalt wanneer de verbinding
kan starten, niet hoe lang die openblijft.

Een `401` betekent dat de inlogsessie van het account niet geldig is. Log
opnieuw in voordat je een ticket aanvraagt. Een andere methode dan `POST` geeft
`405` met `code: method_not_allowed`.

### De verbinding openen

Verbind een WebSocket-client met
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. URL-codeer het
ticket. Zet geen account-bearer en geen ingest-bearer in de URL. Een `401`
betekent dat het ticket of de inlogsessie van het account niet geldig is. Maak een nieuw ticket aan nadat je opnieuw bent ingelogd.

| Response | Oorzaak | Volgende stap |
| --- | --- | --- |
| `422` met `"error": "feed ticket is required"` | De querywaarde `ticket` ontbreekt of is leeg. | Maak een ticket aan en verbind daarmee. |
| `401` met `code: unauthorized` | Het ticket is verlopen of niet geldig. | Maak een nieuw ticket aan. Probeer hetzelfde ticket niet opnieuw. |
| `code: invalid_websocket_upgrade` | Het request is geen geldige WebSocket-upgrade. | Gebruik een WebSocket-client. |
| `405` met `code: method_not_allowed` | Het request gebruikt geen `GET`. | Gebruik `GET` voor de verbinding. |

Wacht na een fout voordat je opnieuw verbindt. Verbind niet opnieuw in een
snelle lus.

### De berichten lezen

Elk bericht is een envelop `{ "type": "...", "data": ... }`. Lees `type`
voordat je `data` parset. Sla types over die de client niet ondersteunt.

| Eventtype | Payload |
| --- | --- |
| `native_log` | Loggegevens, in de vorm van de [logresponse](#log-response). |
| `native_issue` | Gegevens van een gegroepeerd issue, in de vorm van versie 1 van de [issueresponse](#issue-response). |
| `native_trace_span` | Eén span, in de vorm van een item uit de [spanlijst](#span-list). |
| `native_action` | Gegevens van een productactie, in de vorm van de [actieresponse](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Projectgegevens. Lees de projectlijst opnieuw als die verandert. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Accountgebruik, in de vorm van [accountgebruik](/nl/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Een event `native_issue` gebruikt versie 1 van de issueresponse: een
gearchiveerd issue toont `ignored`, en het event heeft geen prioriteit. Metrics
en releases zijn geen live-eventtypes. Lees ze via hun lijstroutes. Het ticket
selecteert geen project. Controleer de `project_id` van elk event voordat je
het in een projectweergave toont. `logbrew watch --json` gebruikt deze feed.
Zie de [CLI-referentie](/nl/reference/cli).

### Een gesloten verbinding afhandelen

| Sluitcode | Reden | Volgende stap |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Wacht en verbind daarna opnieuw met een nieuw ticket. Lees de lijstroutes opnieuw om de gemiste records op te halen. |
| `1008` | `live feed access changed; sign in again` | Stop met opnieuw verbinden. Log opnieuw in voordat je een nieuw ticket aanmaakt. |

Bij andere verbroken verbindingen geeft LogBrew soms geen reden. Lees na het
opnieuw verbinden de lijstroutes opnieuw en koppel records op ID.

## <span id="issue-status-response-examples">Responsevoorbeelden voor de issuestatus</span>

`PATCH /api/telemetry/issues/{issue_id}` met `{ "status": "resolved" }` geeft
`200 OK` terug met het bijgewerkte gegroepeerde issue, in dezelfde vorm
als de [issueresponse](#issue-response). De queryparameter `response_version`
kiest de versie. De route geeft geen succesvlag terug.

De body stelt 1 of meer van `status`, `priority` en `assignee` in. `status`
accepteert `unresolved`, `resolved` of `archived`. `ignored` is een oudere naam
voor `archived`. Zie [Eén issue bijwerken](/nl/reference/telemetry-api#update-one-issue).

Controleer de teruggegeven `id`, `status` en `priority` voordat je toont dat
het gelukt is. Bouw het resultaat niet op uit de verstuurde waarden. Een
statuswijziging verwijdert geen voorvallen en verandert `first_seen_at` en
`last_seen_at` niet. Ze verandert ook `severity` of een ernstregel niet.

Een geweigerde wijziging geeft `422` met `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Resultaat | Oorzaak |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | De body heeft geen van de 3 velden. |
| `422`, `issue priority must be high, medium, or low` | De waarde voor de prioriteit wordt niet ondersteund. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | De waarde voor `assignee` wordt niet ondersteund. |
| `422`, `issue assignee cannot read this project` | Het toegewezen account heeft geen toegang tot het project. LogBrew wijzigt niets. |
| `422`, `issue assignee team is not a team of this project's organization` | Het team hoort niet bij de organisatie van het project. LogBrew wijzigt niets. |
| `403` met `code: forbidden` | Het account kan geen issues beheren in het project. |
| `404` met `code: not_found` | Het account kan het issue niet lezen, of het issue bestaat niet. |

Een veld dat al de gevraagde waarde heeft, verandert niet. Stuur na een
time-out of een verloren response hetzelfde request opnieuw, of lees eerst het
issue. Stuur geen andere wijziging voordat je de huidige toestand hebt gelezen.
Zie [Schrijfacties](/nl/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` geeft `200 OK` terug met 1 resultaat per
gevraagd issue-ID, in de volgorde van het request. Elk gevonden issue gebruikt
de vorm van versie 3. Voeg `"response_version": 2` toe aan de body om elk issue in de
vorm van versie 4 te krijgen. Een resultaat `not_found` heeft `issue: null`:

```json
{
```

## Scope van analyserequests

De analyseroutes, de route voor metric-tijdreeksen en de route voor
signaalvolume lezen één project en één tijdsbereik. Elk request heeft
`project_id` en `since` nodig. `since` accepteert een korte duur zoals `24h` of
`7d`, of een RFC3339-tijdstempel. `until` accepteert een RFC3339-tijdstempel en
is standaard het tijdstip van het request. Het bereik bevat `since`, bevat
`until` niet en mag niet langer zijn dan 31 dagen.

`service_name`, `release` en `environment` zijn optionele exacte filters. Elke
waarde moet 1 tot 256 tekens hebben nadat LogBrew de spaties aan begin en eind
heeft verwijderd. De route voor segmentvergelijking zet deze filters in elk
segment, niet op het hoogste niveau.

Als het account het project niet kan lezen, geven deze routes `200 OK` met
aantallen van nul. Ze geven geen `404`. Een leeg resultaat bevestigt dus niet
dat je toegang hebt tot het project. Vergelijk `project_id` met de projecten
die het account kan lezen. Een request via een MCP-verbinding die het project
niet bevat, geeft `403` en `forbidden`.

| Route | Waarden voor `response_version` | Standaard |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` of `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` of `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` of `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` of `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` of `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Niet geaccepteerd | Schema `1` |
| `POST /api/telemetry/analytics/paths` | Niet geaccepteerd | Schema `1` |
| `GET /api/telemetry/metrics/series` | Niet geaccepteerd | Schema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Elke response begint met `schema_version`, `query` en `purpose`. `query`
herhaalt de effectieve scope. Een filter dat je niet hebt gestuurd, staat er
niet in. `purpose` is platte tekst die uitlegt op welke vraag de route antwoord
geeft.

Een ratio ontbreekt als de noemer nul is. Een weggelaten ratio is niet `0` en
niet `null`. Lees `coverage` voordat je op een ratio vertrouwt.

### <span id="shared-scope-errors">Gedeelde scopefouten</span>

Deze fouten gebruiken HTTP `422` en `validation_failed`:

| Oorzaak | `error` |
| --- | --- |
| Geen `project_id` | `product analytics project_id is required` |
| Geen `since` | `product analytics since is required` |
| `since` is geen duur of RFC3339-tijdstempel | `invalid since value` |
| `until` is geen RFC3339-tijdstempel | `product analytics until must be an RFC3339 timestamp` |
| `since` ligt niet vóór `until` | `product analytics since must be earlier than until` |
| Het bereik is langer dan 31 dagen | `product analytics range must not exceed 31 days` |
| Een leeg filter, of een filter langer dan 256 tekens | `product analytics context filters must be non-empty and at most 256 characters` |

Een request zonder `project_id` geeft bijvoorbeeld:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

De routes voor metric-tijdreeksen en signaalvolume gebruiken dezelfde
scoperegels, met hun eigen tekst in `error`. Hun secties hieronder noemen die
fouten.

Een onbekende queryparameter geeft `422` met de response voor
[ongeldige queryparameters](/nl/reference/api-errors#invalid-query-parameters).
Een onbekend JSON-veld, een ontbrekend verplicht JSON-veld of een
niet-ondersteunde enumwaarde geeft `invalid_json`. Zie
[Ongeldige JSON](/nl/reference/api-errors#invalid-json). Een request met de
verkeerde HTTP-methode geeft `405` en `method_not_allowed`. De tekst in `next`
noemt de ondersteunde methode en velden. Zie
[Niet-ondersteunde methode](/nl/reference/api-errors#unsupported-method).

## Response van het overzicht voor productanalyse

`GET /api/telemetry/analytics/overview` toont de activiteit in één project:
actievolume, gebruikers, sessies, een tijdreeks, topacties, en geclassificeerde

exacte eventnamen voor de andere analyseroutes te vinden.

Stuur `response_version=3`. Versies 1 en 2 geven dezelfde aantallen, maar hun
waarde voor `estimation.method` is een ouder token. Versie 1 controleert het
soort subject niet als ze geïdentificeerde gebruikers telt. Versies 2 en 3
tellen alleen subjecten van het soort `user`, en voegen aantallen voor anonieme
subjecten en `subject_coverage` toe.

Dit request leest één uur in tijdsintervallen van vijf minuten en geeft twee

### Conversie en dekking lezen

`entry_rate` is `entered_units` gedeeld door `candidate_units`: 50 van 60.
`overall_conversion_rate` is `completed_units` gedeeld door `entered_units`:
15 van 50, dus 30%. Het is niet 15 gedeeld door alle kandidaten. Deze aantallen
verklaren niet waarom eenheden stopten.

Dekking telt events, geen sessies. Hier passen 120 events bij een stap, en 20
daarvan hebben geen sessie-ID. Het resultaat laat die 20 events buiten de
sessieaantallen. Behandel ze niet als 20 mislukte sessies.

De eerste stap heeft geen `conversion_from_previous`. De laatste stap heeft
geen `drop_off_to_next_units` en geen `drop_off_to_next_rate`.

Een eenheid bereikt een latere stap alleen als de tijden van de stappen strikt
oplopen. Events met dezelfde tijdstempel kunnen niet aan twee opeenvolgende
stappen voldoen. De laatste stap moet binnen `conversion_window_seconds` na de
eerste stap plaatsvinden.

De sessiemodus telt sessies, geen mensen. Gebruik `identified_user` alleen
voor events met een ondoorzichtig subject-ID van het soort `user`. Die modus
kan events uit verschillende sessies binnen het conversievenster samenvoegen.
Houd dezelfde eenheid en dezelfde stappen aan als je resultaten vergelijkt.

Standaard is `conversion_window_seconds` 24 uur of de lengte van het bereik,
als die korter is. Het maximum is de lengte van het bereik in hele seconden,
naar boven afgerond.

Een geslaagde lege response toont nog steeds de gevraagde stappen, met nul
`units`. Zijn er geen kandidaateenheden, dan laat `summary` `entry_rate` en
`overall_conversion_rate` weg. De route geeft geen `404` alleen omdat er geen
events overeenkomen.

| `next_action.code` | Oorzaak |
| --- | --- |
| `capture_product_activity` | Er zijn geen geclassificeerde events in de scope. |
| `choose_captured_funnel_steps` | Geen enkel event past bij een gevraagde stap. |
| `sessionize_product_activity` | Er zijn stapevents, maar geen ervan heeft een sessie-ID. |
| `identify_product_users` | Er zijn stapevents, maar geen ervan heeft een subject van het soort `user`. |
| `verify_funnel_entry` | Geen enkele eenheid is bij stap 1 binnengekomen. |
| `investigate_funnel_drop_off` | Er kwamen eenheden binnen, maar geen enkele eenheid voltooide alle stappen. |
| `compare_funnel_contexts` | Minstens één eenheid voltooide de trechter. |

`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Een stap `interaction` moet ook een geldige actienaam zijn. Anders is de fout
`product analytics interaction event_name must be a bounded stable action name`.

Corrigeer het request voordat je het opnieuw stuurt. Verwijder geen stappen en
wijzig de analyse-eenheid niet alleen om een niet-leeg resultaat te krijgen.

## Analyse op exacte events en automatische analyse

Retentie en levenscyclus accepteren twee vormen van requests. Kies met
`response_version` de vorm die je vraag beantwoordt:

| Analyse | `response_version` | Eventselectors |
| --- | --- | --- |
| Retentie voor exacte events | `1`, of weggelaten | Stuur zowel `start_event` als `return_event`. |
| Levenscyclus voor één exact event | `1`, of weggelaten | Stuur `event`. |
| Automatische retentie of levenscyclus | `2` | Stuur geen eventselector. |

Een exacte selector bevat `kind` en `event_name`. `kind` is `page_view`,
`screen_view` of `interaction`. Kopieer `event_name` uit
`classified_activity.top_events`. Raad geen eventnaam op basis van een
knoplabel.

Beide vormen tellen alleen gebruikers: ondoorzichtige subject-ID's van het
soort `user`. Anonieme subjecten en events zonder bruikbaar subject-ID tellen
niet als gebruikers. Responses geven nooit subject-ID's terug.

De vaste intervallen zijn `hour`, `day`, `week` en `thirty_day`. Het zijn vaste
tijdsduren. `thirty_day` is 30 dagen, geen kalendermaand. Laat je `interval`
weg, dan gebruikt de API `hour` voor een bereik van 48 uur of korter, en `day`
voor een langer bereik.

### Retentiefouten

Naast de [gedeelde scopefouten](#shared-scope-errors) geven deze requests
`422` en `validation_failed`:

| Oorzaak | `error` |
| --- | --- |
| Versie 1 zonder beide selectors, versie 2 met een selector, of een andere versie | `product analytics retention activity selection is contradictory` |
| `interval_count` buiten `1` tot `31` | `product analytics retention interval_count must be between 1 and 31` |
| Tijdsintervallen voor cohorten maal `interval_count` is meer dan 500 | `product analytics retention interval and interval_count would exceed 500 cohort matrix cells` |

De limiet op cellen gebruikt het bereik en de perioden, niet het aantal
gebruikers. Een bereik van 30 dagen met `interval: "hour"` heeft 720
tijdsintervallen voor cohorten. Met `interval_count: 1` zijn dat 720 cellen,
meer dan 500:

```json

  "code": "validation_failed",
  "next": "choose a wider interval, a shorter time range, or fewer retention periods",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Verwijder beide selectors om automatische retentie te gebruiken. Wijzig de SDK
niet om dit leesrequest te corrigeren.

`GET /api/telemetry/metrics/series` leest één exacte metricnaam in één project.
Kopieer de naam uit `GET /api/telemetry/metrics`. Dit request groepeert een
delta-counter per service:

```bash
curl --get "https://api.logbrew.co/api/telemetry/metrics/series" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "name=jobs.completed" \
  --data-urlencode "since=2026-06-01T12:00:00Z" \
  --data-urlencode "until=2026-06-01T12:15:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name"
```

### Een metric-tijdreeks lezen

Het eerste datapunt registreert 10 voltooide jobs, niet 10 metingen.
`rate_per_second` deelt die verandering door het tijdsinterval van 300
seconden. `last` is de laatst geregistreerde verandering, niet de som. Zie
[betekenissen van metric-aggregaties](/nl/concepts/telemetry#read-the-metric-value).

Het soort en de temporaliteit van een tijdreeks bepalen de `aggregation.code`
en de statistieken in elk datapunt. Een datapunt laat een statistiek weg die
niet van toepassing is. Een ontbrekende statistiek is geen nul.

| Soort en temporaliteit | `status` | `aggregation.code` | `value` | Andere statistieken |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Laatste meting | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Som van de veranderingen | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 bij benadering | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Elk soort, `cumulative` | `limited` | `raw_cumulative_last` | Laatste ruwe meting | `last`, `min`, `max` |
| Elk ander paar | `limited` | `raw_last` | Laatste ruwe meting | `last`, `min`, `max` |

`limited` is een geslaagde response, geen fout. Het voegt
`aggregation.limitation` toe, dat uitlegt waarom LogBrew alleen ruwe waarden
toont. `ready` bewijst niet dat alles is vastgelegd.

Lees `coverage` voordat je een grafiek tekent:

- `samples` telt de metingen van alle overeenkomende tijdreeksen, ook
  tijdreeksen die de response niet teruggeeft.
- `series` telt overeenkomende tijdreeksen. `returned_series` en `points` tellen
  de teruggegeven gegevens.
- `truncated` is `true` als `series_limit` tijdreeksen met minder volume heeft
  weggelaten.
- `expected_buckets_per_series` is het aantal mogelijke tijdsintervallen in het
  bereik.

Voeg geen datapunt toe voor een tijdsinterval zonder metingen. Vul geen nul in
en kopieer de vorige waarde niet. Elk datapunt geeft maximaal 3
`trace_exemplars` terug. Een trace-exemplar koppelt één meting aan een trace.
Het verklaart niet elke meting in het tijdsinterval. Als geen enkel datapunt
een trace-exemplar heeft, is `next_action.target` gelijk aan `metric_samples`.

### Scope en fouten van metric-tijdreeksen

`project_id`, `name` en `since` zijn verplicht. `name` mag hoogstens 200 tekens
hebben. `interval` is `auto`, `1m`, `5m`, `15m`, `1h`, `6h` of `1d`. Standaard
is dat `auto`. Die waarde kiest het kleinste interval met hoogstens 300
tijdsintervallen. Een expliciet interval mag niet meer dan 500 tijdsintervallen
nodig hebben.

`group_by` is `none`, `service_name`, `release` of `environment`. Standaard is
dat `none`. Zonder groepering blijven verschillende soorten, eenheden en
temporaliteiten in aparte tijdreeksen. `series_limit` accepteert `1` tot `20`.
Standaard is dat `10`.

Een leeg resultaat geeft `200` met `series: []` en nul `samples`. Het object
`coverage` laat `first_seen_at` en `last_seen_at` weg. Dat bewijst niet dat de
applicatie de metric nooit heeft verstuurd. Controleer het project, de
metricnaam en het tijdsbereik.

Zonder `name` krijg je `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Tijdsintervallen van één minuut over zeven dagen geven `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Andere fouten met `422` zijn `metric series group_by is not supported`,
`metric series interval is not supported` en
`metric series_limit must be between 1 and 20`.

## Response van padanalyse

`POST /api/telemetry/analytics/paths` vindt de benoemde events vóór of na één
gekozen event in dezelfde sessie. Het gekozen event is het anker. Kopieer de
`kind` en `event_name` ervan uit `classified_activity.top_events`. De route
geeft `schema_version: 1` terug. Ze accepteert geen `response_version` of
`analysis_unit`.

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "direction": "following",
  "anchor": { "kind": "page_view", "event_name": "/checkout" },
  "depth": 2,
  "collapse_repeated": true,
  "path_limit": 2
}
```

`direction` en `anchor` zijn verplicht.

sessies met het anker. De aandelen zijn 50% en 25%, niet 67% en 33%.

pad vertegenwoordigt. `paths_truncated: true` betekent dat het resultaat
onvolledig is.

Dekking telt events, geen sessies. Hier passen vijf events bij het anker, maar
één heeft geen sessie-ID. Dat event kan niet in een pad komen. Elk pad geeft
maximaal 3 trace-exemplars terug. Gebruik een trace-ID uit je eigen response.
Een tracekoppeling toont niet wat een gebruikersactie of een fout veroorzaakte.

| Veld | Betekenis |
| --- | --- |
| `following` | Begint bij het vroegste overeenkomende anker in elke sessie. Het anker heeft positie `0`. Latere knooppunten hebben positieve posities. |

| `depth` | Aantal knooppunten naast het anker, het anker zelf niet meegeteld. `1` tot `8`. Standaard is dat `4`. Een pad kan minder knooppunten hebben. |
| `collapse_repeated` | Voegt opeenvolgende knooppunten met hetzelfde soort en dezelfde naam samen. Standaard is dat `true`. |
| `path_limit` | Maximaal aantal teruggegeven paden, gerangschikt op aantal sessies. `1` tot `20`. Standaard is dat `10`. |

Knooppunten staan in beide richtingen op tijdsvolgorde. Een pad is geen
volledige herhaling van de sessie. LogBrew leest hoogstens 1024 benoemde events
per sessie voordat het het anker kiest: de vroegste events voor `following` en
de laatste events voor `preceding`. Een anker buiten die limiet kan ontbreken.

### <span id="filter-the-anchor-by-property">Het anker filteren op eigenschap</span>

Stuur maximaal vier `property_filters`, elk met één exacte `key` en `value`.
Kopieer de sleutel uit de [eigenschappencatalogus](#analytics-property-catalog).
De filters gelden alleen voor het anker, niet voor de events eromheen. Waarden
zijn hoofdlettergevoelig. Als er filters zijn, herhaalt `query` ze en meldt
`coverage.anchor_property_filters`:

| Veld | Betekenis |
| --- | --- |
| `context_events` | Ankerevents in de scope vóór de eigenschapsfilters. |
| `property_ready_events` | Ankerevents die elke gevraagde sleutel hebben. |
| `missing_property_events` | Ankerevents zonder een of meer gevraagde sleutels. |
| `matching_events` | Ankerevents waarvan de waarden bij elk filter passen. |
| `nonmatching_value_events` | Ankerevents die elke sleutel hebben, maar een andere waarde. |
| `property_ready_rate` | `property_ready_events` gedeeld door `context_events`. |
| `match_rate` | `matching_events` gedeeld door `property_ready_events`. |

Ontbrekende sleutels en afwijkende waarden vragen om verschillende oplossingen.
Tel ze niet bij elkaar op. Het object ontbreekt als het request geen
eigenschapsfilter heeft.

### Lege paden en geweigerde requests

Een lege array `paths` kan een geslaagde response `200` zijn. Lees `summary`,
`coverage` en `next_action`. Deze codes onderscheiden de oorzaken:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` en
`narrow_or_move_path_anchor`.

Naast de [gedeelde scopefouten](#shared-scope-errors) geven deze requests
`422` en `validation_failed`:

| Oorzaak | `error` |
| --- | --- |
| `depth` buiten `1` tot `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` buiten `1` tot `20` | `product analytics path_limit must be between 1 and 20` |
| Meer dan vier eigenschapsfilters | `product analytics paths accept at most four exact anchor property filters` |
| Een sleutel die niet in de eigenschappencatalogus staat | `product analytics path property keys must be supported privacy-safe keys` |
| Dezelfde sleutel twee keer | `product analytics path property keys must be unique` |
| Een lege waarde, een waarde langer dan 256 tekens, of een stuurteken | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

`depth: 0` geeft bijvoorbeeld:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">Eigenschappencatalogus voor productanalyse</span>

`GET /api/telemetry/analytics/properties` toont de eigenschapssleutels op
geclassificeerde productevents in één project. Gebruik de sleutels in
[segmentvergelijkingen](#analytics-segment-comparison) en in filters voor
padankers. De catalogus geeft sleutels en aantallen terug. Hij geeft nooit
eigenschapswaarden of identiteiten terug.

### Beschikbare eigenschapssleutels lezen

Stuur `project_id` en `since`. Je kunt ook `until`, `service_name`, `release`,
`environment`, `limit` en `response_version` sturen. `limit` accepteert `1`
tot `50` sleutels. Standaard is dat `20`. Stuur `response_version=2` voor de
openbare waarde van `estimation.method`.

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/properties" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T00:00:00Z" \
  --data-urlencode "until=2026-06-02T00:00:00Z" \
  --data-urlencode "limit=20" \
  --data-urlencode "response_version=2"
```

`events`, de hoogste eerst.

`tag.plan` staat op 60 van de 100 geclassificeerde events. De sleutel heeft
ongeveer 3 unieke waarden. De beschrijving toont die waarden niet. Gebruik
waarden die je uit je applicatie kent. Raad geen waarde op basis van een
aantal. Eén event kan meerdere sleutels hebben, dus tel de aantallen in
`events` per sleutel niet bij elkaar op.

| `coverage.properties_truncated` | `true` als er meer sleutels zijn dan `limit`. Maak de scope kleiner, of verhoog `limit` tot maximaal 50. |
| `coverage.values_returned` | Altijd `false`. |

Een lege array `properties` bewijst niet dat het project geen productevents
heeft. Lees `summary`, `coverage` en `next_action`.

Naast de [gedeelde scopefouten](#shared-scope-errors) geeft `limit=0` of
`limit=51` een `422`:

```json

  "code": "validation_failed",
  "next": "use limit=1 through limit=50",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Een `response_version` anders dan `1` of `2` geeft
`product analytics response_version must be 1 or 2`. LogBrew controleert
`response_version` vóór de andere waarden.

Een `POST`-request geeft `405`:

```json
{
  "error": "Method not allowed",
  "code": "method_not_allowed",
  "next": "send GET /api/telemetry/analytics/properties with required project_id and since plus optional until, service_name, release, environment, limit, or response_version query parameters",
  "next_action": { "code": "use_supported_method", "target": "api_method" }
}
```

## <span id="analytics-segment-comparison">Segmentvergelijking in productanalyse</span>

`POST /api/telemetry/analytics/segments/compare` vergelijkt hoe vaak sessies
of gebruikers één exact event bereiken in 2 tot 4 segmenten binnen één
project. Een segment selecteert events op service, release, omgeving en
eigenschapswaarden. Het eerste segment is het referentiesegment.

### De vergelijking definiëren

Stuur deze JSON-body met accountauthenticatie en
`Content-Type: application/json`. Hier zijn `basic` en `premium`
abonnementswaarden van de voorbeeldapplicatie, geen abonnementen van LogBrew:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
```

`target` en `segments` zijn verplicht. `analysis_unit` is `session` of
`identified_user`. Standaard is dat `session`. Die waarde telt sessies, geen
mensen.
`interval` accepteert dezelfde waarden als het overzicht. Standaard is dat
`auto`.

Elk segment heeft een unieke `key`, een `label` en een eigen set filters nodig:

- `key`: 1 tot 32 bytes. Begin met een kleine ASCII-letter of een cijfer.
  Gebruik alleen kleine ASCII-letters, cijfers, `_` en `-`.
- `label`: 1 tot 80 tekens, zonder stuurtekens.
- `service_name`, `release`, `environment`: optioneel. Elke waarde heeft 1 tot
  256 tekens, zonder stuurtekens.
- `property_filters`: 0 tot 4 filters. Elke sleutel mag één keer in een
  segment voorkomen. Een event moet bij alle filters van het segment passen.
  Waarden zijn hoofdlettergevoelig en hebben 1 tot 256 tekens. LogBrew
  verwijdert spaties aan het begin en het eind.

Een segment zonder filters selecteert alle geclassificeerde activiteit in het
project en het tijdsbereik. Segmenten mogen overlappen. Een ander label of een
andere sleutel maakt twee identieke sets filters niet geldig.

### Ratio's en verschillen lezen

`eligible_units` schat de sessies of gebruikers met geclassificeerde activiteit
in het segment. `reached_units` schat hoeveel daarvan het doel bereikten.
`reach_rate` is `reached_units` gedeeld door `eligible_units`. Events zonder ID
van de gekozen eenheid tellen niet mee voor deze eenheden.

De ratio van het referentiesegment is 20%. De ratio van premium is 30%. Het
verschil is 10 procentpunten. De relatieve stijging is 50%, niet 10%. Kleine
decimale afwijkingen komen door rekenen met drijvendekommagetallen. Rond
ratio's af voor weergave, maar reken met de teruggegeven waarden. Het
referentiesegment heeft geen `comparison_to_baseline`. De relatieve stijging
ontbreekt als de bereikratio van het referentiesegment nul is.

In `query` is een segmentfilter dat je niet hebt gestuurd `null`. Een lege
lijst `property_filters` wordt weggelaten.

`coverage.property_filters` heeft dezelfde velden als de
[dekking van padankerfilters](#filter-the-anchor-by-property). Hier is
`matching_events` gelijk aan `classified_events`. Houd ontbrekende sleutels en
afwijkende waarden apart. Segmenten kunnen overlappen, en één sessie kan in
meerdere tijdsintervallen voorkomen. Tel aantallen eenheden niet op over
segmenten of tijdsintervallen heen.

De vergelijking is beschrijvend. `confidence.causal_inference` is
`not_established` en `confidence.statistical_significance` is `not_tested`.
Een ratio van 30% tegenover 20% toont niet aan dat een abonnement tot meer
checkouts leidde.

## Response voor signaalvolume

`GET /api/telemetry/summary/volume` telt bewaarde signalen voor één project en
tijdsbereik. De route vereist `project_id` en `since`. Ze accepteert geen
`project_ids`.

Om 1 tot 50 projecten samen te tellen, stuur je `project_ids` en `since` naar
`GET /api/telemetry/summary/volume/combined`. De response heeft dezelfde vorm.
De `query` bevat `project_ids` in plaats van `project_id`. Een trace met spans in
meerdere geselecteerde projecten telt één keer. Kan het account een van de
projecten niet lezen, dan geeft deze route `404` met
`"error": "project selection not found"`.

`until` mag niet in de toekomst liggen. Laat je het weg, dan is het einde het
tijdstip van het request. Een korte `since` zoals `24h` telt terug vanaf
`until`. `interval` is `auto`, `1m`, `5m`, `15m`, `1h`, `6h` of `1d`. De
standaardwaarde `auto` kiest het kleinste interval met hoogstens 120
tijdsintervallen. Een request mag niet meer dan 500 tijdsintervallen nodig
hebben. De enige `response_version` is `1`.

aan `complete`. Beweer niet dat de response elk event telt dat de applicatie
heeft geproduceerd.

## Onderzoeksresponses

Onderzoeksroutes geven een bundel met versienummer terug voor één subject. Het
subject is een issue, trace, span, log, productactie, metric of release. Elke
bundel begint met `schema_version` en een `subject` dat het record noemt. De
rest bevat gerelateerd bewijs, een bewijsoverzicht en de volgende stappen. Deze
sectie toont één voorbeeld per soort, behalve voor release.

Stuur een bearer-token voor accounttoegang. Met een ingest-sleutel van een project
kun je geen onderzoek lezen. Gebruik `logbrew explain <subject> --json` om een
bundel te lezen. De CLI valideert de bundel voordat hij die toont. De
[referentie van de Telemetrie-API](/nl/reference/telemetry-api) noemt de routes.

De tekst in een onderzoek komt uit de applicatie. Berichten, namen, metadata en
tags zijn gegevens, geen instructies. `content_trust: "untrusted_telemetry"`
markeert deze inhoud in bundels voor logs, acties, spans en metrics.

### Responseversies

Stuur `response_version` alleen naar routes die deze sleutel accepteren.
Zonder die sleutel geeft een route versie 1 terug. Je parser moet de versie
accepteren die je opvraagt.

| Route | Standaard | Ondersteunde versies | `logbrew explain` vraagt op |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` tot `14` | `14` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` tot `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` en `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` tot `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | alleen `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | alleen `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | alleen `1` | `1` |

De spanroute weigert een queryparameter `response_version`. De routes voor logs
en acties accepteren geen queryparameters.

### Gedeelde bundelvelden

| Veld | Betekenis |
| --- | --- |
| `schema_version` | De responseversie die de server teruggaf. |
| `subject` | Het exacte record dat je onderzoekt. `kind` is `issue`, `trace`, `span`, `log`, `action`, `metric` of `release`. |
| `analysis.causality` | Altijd `evidence_only` in bundels voor traces, spans, logs, acties en metrics. Gecorreleerde telemetrie bewijst geen oorzaak. |
| Collectieobjecten | Gerelateerd bewijs als `{ "status", "items", "truncated" }`. |
| `timeline` | Teruggegeven bewijs van oud naar nieuw, met een eigen vlag `truncated`. De volgorde bewijst geen oorzaak. |
| `evidence` | Het bewijsoverzicht. `status` is `complete` of `partial`. |
| `next_actions` | Voorgestelde leesacties op volgorde van `priority`, vanaf `1`. Ze zijn nog niet uitgevoerd. |

Elke gerelateerde collectie meldt één `status` voor beschikbaarheid:

| Status | Betekenis | Gedrag van de client |
| --- | --- | --- |
| `available` | De leesactie is voltooid en gaf items terug. | Toon de items en de vlag `truncated`. |
| `not_linked` | Het subject heeft geen ID voor deze koppeling, zoals een trace-ID. | Leg uit dat de koppeling ontbreekt. Bouw er geen op basis van tijdstempels. |
| `not_found` | De leesactie is voltooid en vond geen bewaard bewijs. | Toon een leeg resultaat. |
| `unavailable` | De optionele leesactie is mislukt. Het subject is nog steeds geldig. | Houd het subject zichtbaar. Probeer het later opnieuw. Toon geen nul items als resultaat. |

Het bewijsoverzicht heeft vier gesorteerde lijsten met vaste veldnamen:
`captured_fields`, `missing_fields`, `redacted_fields` en `truncated_fields`.
`status` is alleen `complete` als de laatste drie lijsten leeg zijn.
Afgeschermde gegevens zijn geen ontbrekende gegevens. Afgekapte gegevens zijn
geen volledige gegevens. Vul geen afgeschermde of afgekapte waarde in.

### Limieten van een onderzoek

Deze limieten begrenzen één response. Een vlag `truncated` of een regel in
`truncated_fields` laat zien dat een limiet gegevens heeft weggelaten.

| Bewijs | Limiet |
| --- | --- |
| Gerelateerde items in één collectie | 20 |
| Gelezen bewaarde spans voor één trace | 1.000 |
| Items in de tijdlijn | 50 voor bundels van logs, acties en spans. 100 voor bundels van traces en metrics. |
| Gestructureerde attributen, eigenschappen en metadata | 64 scalaire waarden, 4 niveaus van objecten of arrays, 16 items per array, 512 tekens per string |
| Tijdvenster voor correlatie | 5 minuten vóór en na een log, actie of geselecteerd issuevoorval. Voor een trace of span 5 minuten vóór de start en na het einde, hoogstens 24 uur. |

Elke sectie per soort noemt haar eigen limieten.

### Response van een issueonderzoek

Gebruik `GET /api/telemetry/issues/{issue_id}/investigation` om het bewijs voor
één voorval van een gegroepeerd issue te lezen. De
[handleiding voor issueonderzoek](/nl/guides/investigate-an-issue) laat zien in
welke volgorde je het bewijs leest. Vraag versie 14 op:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=14" \
  --data-urlencode "selection=recommended"
```

De queryparameters zijn `response_version`, `selection` en `occurrence_id`.
`selection` is `recommended`, `first` of `latest`. De waarden zijn
hoofdlettergevoelig. In versies 2 tot 14 gebruikt een weggelaten selector
`recommended`. Versie 1 geeft het laatste bewaarde voorval terug en accepteert
geen selector. Filters van de issuelijst gelden niet voor deze leesactie.

#### Requestfouten bij een issueonderzoek

Gebruik `selection` of `occurrence_id`. Stuur ze niet allebei, ook niet als ze
hetzelfde voorval selecteren:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Oorzaak | Herstel |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | Het request heeft beide selectors. | Houd één selector. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | Het request heeft een selector en versie 1, of geen versie. | Stuur `response_version=14`. Houd de selector. |
| `422` | `issue investigation response_version must be 1 through 14` | De versie valt buiten het bereik. | Stuur een ondersteunde versie. |
| `422` | `invalid query parameters` | Een onbekende sleutel, een ongeldige UUID, een versie die geen geheel getal is, of een onbekende waarde voor `selection`. | Corrigeer de [query](/nl/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | Het voorval zit niet in de bewaarde geschiedenis van deze groep. | Kopieer het voorval-ID uit de events van dit issue. Gebruik niet zonder goedkeuring `latest` of `recommended` in plaats daarvan. |
| `404` | `issue not found` | Geen enkel leesbaar project heeft dit issue. | Controleer het account en de UUID van het issue. Stuur geen UUID van een voorval als issue-ID. |

Een ontbrekend voorval betekent niet dat het issue ontbreekt. Een `404` laat
niet zien of een ander account het issue kan lezen.

### Response van een spanonderzoek

Gebruik `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` om
één bewerking in een trace te lezen. Stuur `project_id`, `environment` en
`release`. Alle drie zijn verplicht. Kopieer ze van de geselecteerde span.
Stuur de `id` van de spanrij niet als `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### Response van een logonderzoek

Gebruik `GET /api/logs/{log_id}/investigation` om één log en het gerelateerde
bewijs te lezen. Deze route heeft geen queryparameters. Kopieer het log-ID uit een
loglijst.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

De leesactie kan bewijs teruggeven buiten de filters van de loglijst.
Gerelateerde leesacties gebruiken het project, de omgeving en de release van de
log, en 5 minuten vóór en na de log. Logs in de buurt gebruiken ook dezelfde
service. Die hebben geen trace-ID nodig. Leesacties op de exacte trace hebben
het trace-ID van de log nodig en kunnen andere services bevatten. De
tracesamenvatting gebruikt hetzelfde trace-ID en dezelfde scope, zonder het
tijdvenster.

### Response van een actieonderzoek

Gebruik `GET /api/telemetry/actions/{action_id}/investigation` om één
productactie te lezen, met de gemelde status en gerelateerd bewijs. Deze route
heeft geen queryparameters. Gerelateerde leesacties gebruiken hetzelfde
tijdvenster en dezelfde scopes als een logonderzoek.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/telemetry/actions/$ACTION_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

`correlations`, `timeline` en `next_actions` gebruiken de vormen van een
logonderzoek. Gerelateerde acties bevatten de onderzochte actie zelf niet.

### Response van een metriconderzoek

Gebruik `GET /api/telemetry/metrics/investigation` om één metricnaam in één
project en tijdsbereik te lezen. De response bevat de huidige tijdreeks, een
vergelijking met het voorgaande tijdvenster van dezelfde lengte, de laatste
meting, trace-exemplars en voltooide deployments. Versie 2 voegt de beschrijving
van de metric uit de laatste bewaarde meting toe. Versie 1 meldt altijd
`description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` en `since` zijn verplicht. `since` telt mee en `until`
niet. Standaard is `until` gelijk aan nu. De vergelijking leest ook het
voorgaande tijdvenster van dezelfde lengte.

deployment vlak bij een verandering bewijst niet dat die de verandering
veroorzaakte.

andere signaaltypen.

hoogstens 500 tijdsintervallen. `series_limit` is 1 tot 20, standaard 10. De
response geeft hoogstens 20 exemplars en 20 deployments terug.

| HTTP | `error` | Herstel |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Laat `response_version` weg of stuur `2`. |
| `422` | `metric series project_id is required` | Stuur één leesbaar project-ID. |
| `422` | `metric series name is required` | Kopieer de naam uit de metriclijst. |
| `422` | `metric series since is required` | Stuur een waarde zoals `24h` of een RFC 3339-tijdstempel. |
| `422` | `metric series range must not exceed 31 days` | Gebruik een korter bereik. |
| `422` | `metric series interval would exceed 500 buckets` | Gebruik `interval=auto` of een groter interval. |
| `422` | `metric series_limit must be between 1 and 20` | Stuur een waarde van 1 tot 20. |

`interval` is `auto`, `1m`, `5m`, `15m`, `1h`, `6h` of `1d`. `group_by` is
`none`, `service_name`, `release` of `environment`. Andere waarden geven
`422`.

### Onderzoeksfouten

| HTTP | Route | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Actie | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, actie, issue | `invalid URL path parameters` als het ID in het pad geen UUID is |
| `422` | Issue, trace, span, metric | `invalid query parameters` bij een onbekende sleutel of een waarde van het verkeerde type |

Een `404` betekent dat geen enkel leesbaar project het record heeft. Elke route
geeft ook `401` zonder geldige authenticatie en `405` voor een andere methode
dan `GET`. Zie [API-fouten](/nl/reference/api-errors) voor de responses bij
[niet gevonden](/nl/reference/api-errors#resource-not-found),
[pad](/nl/reference/api-errors#invalid-path-value),
[authenticatie](/nl/reference/api-errors#authentication-failure) en
[methode](/nl/reference/api-errors#unsupported-method).

Een optionele leesactie voor bewijs kan mislukken binnen een response
`200 OK`. De collectie meldt dan `unavailable`. Toon dat niet als `not_found`
of als nul records.

## <span id="severity-values">Ernstwaarden</span>

De ernstwaarden die gebruikers zien, zijn `info`, `warning`, `error` en
`critical`. SDK's en runtimes kunnen gangbare aliassen sturen, zoals `trace`,
`debug`, `warn` of `fatal`. REST- en live-responses geven altijd de canonieke
waarde terug. LogBrew accepteert bijvoorbeeld `warn` als invoer en geeft
`warning` terug. De ingest-API weigert onbekende ernstwaarden.

| Alias | Canonieke waarde |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Responses van ernstregels</span>

Een ernstregel verandert hoe LogBrew een log of issue toont. De regel verandert
niet de ernst die de applicatie heeft vastgelegd. Logs en issues geven een
object `triage` terug:

| Veld | Betekenis |
| --- | --- |
| `effective_severity` | De ernst om te tonen. Zonder regel is die gelijk aan `severity`. |
| `ignored` | `true` als een logregel de log negeert, of als het issue is gearchiveerd. |
| `rule_applied` | `true` als een ernstregel of de genegeerde toestand geldt. `false` is de standaardwaarde, geen ontbrekende gegevens. |

Gebruik `triage.effective_severity` voor weergave. Houd `severity` als de
vastgelegde waarde. Standaard laat de loglijst genegeerde logs weg. Stuur
`status=ignored` of `status=all` op `GET /api/logs` om ze mee te nemen.

Het account moet issues in het project mogen beheren. Leestoegang is niet
genoeg. Zonder die toestemming geeft een regelwijziging `403` met
`code: forbidden`.

### Een logregel wijzigen

`PUT /api/logs/{log_id}/triage-rule` stelt de regel in voor de log en voor
latere logs met dezelfde signatuur. De body heeft zowel `severity` als
`ignored` nodig:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Een response `200 OK` bevat de volledige [log](#log-response). De `severity`
blijft `warning`. De `triage` toont de regel:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Dit fragment toont alleen de gewijzigde velden. `severity` in het request is
`source`, `info`, `warning`, `error` of `critical`. `source` zet de vastgelegde
ernst terug. Een genegeerde log wordt daardoor niet weer actief. Stuur
`"ignored": false` om de log weer te tonen.

### Een issueregel wijzigen

`PUT /api/telemetry/issues/{issue_id}/triage-rule` stelt de getoonde ernst in
van een gegroepeerd issue en de latere voorvallen ervan. De body accepteert
alleen `severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Een response `200 OK` bevat het volledige [issue](#issue-response) in versie 1.
De vastgelegde `severity` en `status` veranderen niet:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Dit fragment toont maar een deel van de velden. Een regel lost een issue niet
op, archiveert het niet en heropent het niet. Gebruik daarvoor de
[statuswijziging](#issue-status-response-examples). Een afgeleide prioriteit
volgt de nieuwe effectieve ernst. Lees het issue met `response_version=2` of
later om die te zien.

Een niet-ondersteunde ernst geeft `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Een onbekend veld in de body, zoals `status` bij een issueregel, geeft `422`
met `code: invalid_json`. Een log of issue dat ontbreekt of niet leesbaar is,
geeft `404` met `code: not_found`. Is de response verloren gegaan? Lees dan de
log of het issue opnieuw voordat je de regel opnieuw stuurt.

## Formaat van foutresponses

Applicatiefouten geven een JSON-envelop terug. Dit voorbeeld toont een
geweigerd request. De tekst in `error` en `next` hangt af van het probleem:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Gebruik `code` voor vertakkingen in je programma en `next_action` voor
automatisering. Toon `error` en `next` als platte tekst aan mensen. Parse hun
formulering niet. Sommige fouten voegen velden toe, zoals `limit`, `reset_at`
of `retry_after_seconds`. Een response zonder JSON-body heeft geen `code` van
LogBrew. Zie [API-fouten](/nl/reference/api-errors) voor alle codes.

## Gegevens lezen met de CLI

De CLI leest dezelfde routes en geeft met `--json` dezelfde JSON terug. Begin
breed en verfijn daarna:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Voeg `--pagination cursor` toe voor de cursorenvelop. De CLI vraagt versie 4
van de issueresponse op. Zie [De volgende pagina lezen](/nl/reference/cli#read-the-next-page)
en [Live volgen](/nl/reference/cli#live-watch).

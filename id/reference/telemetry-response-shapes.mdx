Halaman ini memberi satu contoh untuk setiap jenis respons
[API Telemetri](/id/reference/telemetry-api). Semua nilai adalah contoh
sintetis. Untuk kode error dan cara pemulihannya, lihat
[Error API](/id/reference/api-errors).

## Baca respons

Baca setiap respons dengan urutan ini:

1. Baca status HTTP.
2. Pastikan body punya bentuk yang sesuai dengan rutenya.
3. Pastikan setiap `project_id` ada di dalam lingkup proyek yang diminta.
4. Biarkan nilai enum kanonis dan ID tetap seperti aslinya.
5. Ikuti `next_action` hanya jika klien mendukung `code` dan
   `target`-nya.
6. Perlakukan `null`, kolom yang tidak disertakan, dan daftar kosong sebagai
   status yang berbeda.

`200 OK` bisa berisi daftar kosong. Daftar log yang kosong berarti tidak ada
log yang cocok dengan permintaan. Itu tidak berarti masalah, trace, atau aksi
juga kosong. Jangan gabungkan sinyal hanya karena stempel waktunya berdekatan.
Ikuti trace hanya jika respons berisi `trace_id`-nya yang persis.

`404` dan daftar kosong adalah dua hasil yang berbeda. Rute daftar
mengembalikan `[]` jika tidak ada record yang cocok. Rute detail mengembalikan
`404` dengan `code: not_found` jika tidak menemukan record yang bisa dibaca.
Kedua hasil itu tidak membuktikan bahwa ingest gagal.

## Data yang perlu dikirim

Kegunaan respons bergantung pada telemetri yang Anda kirim. Kirim nilai
berikut di setiap envelope atau penyiapan SDK:

- `release` dan `environment`.
- Nama yang stabil untuk layanan, aksi, dan metrik.
- Konteks trace jika log, span, aksi, dan masalah berasal dari permintaan yang
  sama.
- Nilai tingkat keparahan kanonis: `info`, `warning`, `error`, dan `critical`.
- Atribut yang membantu debugging, tanpa rahasia atau data pribadi yang tidak
  perlu.

Lihat [Integrasi SDK](/id/guides/sdk-ingestion) dan
[Kendalikan data yang direkam](/id/guides/safe-capture).

## Respons ingest

SDK publik membaca respons `POST /v1/events` untuk Anda. Kode aplikasi tidak
perlu menanganinya.

### Respons batch SDK

Batch SDK yang berhasil mengembalikan `200 OK` beserta jumlah yang diterima
untuk setiap stream:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Kolom | Arti |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Peristiwa dari batch ini yang diterima LogBrew. |
| `already_accepted` | Peristiwa yang ID-nya sudah diterima LogBrew sebelumnya. LogBrew tidak menyimpannya lagi. |
| `context_updated` | `true` jika batch ini memperbarui konteks rilis atau lingkungan. |

Jumlah ini hanya mencakup batch ini. Percobaan ulang untuk batch yang sudah
diterima LogBrew mengembalikan `0` untuk setiap stream, dan jumlah
peristiwanya ada di `already_accepted`. Pertahankan ID peristiwa asli saat
Anda mencoba lagi.

### Respons envelope native

`POST /api/telemetry/ingest` mengembalikan `200 OK` beserta jumlah item yang
diterima untuk setiap stream:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

Respons native tidak punya kolom `metrics` atau `context_updated`. Jangan
tambahkan kolom itu. `already_accepted` menghitung item yang `id`-nya sudah
diterima LogBrew sebelumnya untuk proyek itu. Lihat [envelope native langsung](/id/guides/sdk-ingestion#required-envelope-fields).

### Error ingest

`401` dengan `code: ingest_key_invalid` berarti bearer ingest sudah dicabut,
kedaluwarsa, atau tidak valid untuk proyek itu. Di `POST /v1/events`,
permintaan tanpa bearer atau dengan bearer yang bukan kunci ingest
mengembalikan `401` dengan `code: unauthorized`. Gunakan bearer ingest khusus
proyek yang berlaku saat ini. Jangan mencoba lagi dengan bearer akun.

Batch SDK yang ditolak mengembalikan `422` dengan `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Nilai `error` lain antara lain `SDK event batch requires at least one event` dan
`SDK event type is not supported by this ingest route`. Periksa versi SDK dan
konfigurasi transport. Jangan kirim batch kosong. Jangan ubah tipe peristiwa
atau ID hanya agar batch lolos validasi.

Permintaan dengan metode selain `POST` mengembalikan `405` dengan
`code: method_not_allowed`. Body JSON yang tidak bisa dibaca mengembalikan
`code: invalid_json`.

## Format respons daftar telemetri

Secara default, rute daftar mengembalikan array JSON polos. Daftar kosong yang
berhasil adalah `[]`.

Dengan `pagination=cursor`, rute mengembalikan envelope. Kunci koleksinya
sesuai dengan sinyal:

| Rute | Kunci koleksi |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, dengan `issue_id` di tingkat atas |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, dengan `naming_quality` di tingkat atas |

`next_cursor` adalah objek berisi kolom lanjutan, atau `null` di halaman
terakhir. Baris diurutkan dari yang terbaru. Lihat [paginasi berbasis kursor](/id/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Respons log</span>

Halaman kursor berisi log dengan `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Log berisi `level` untuk kompatibilitas dan `severity` untuk tampilan. Keduanya
menyimpan nilai kanonis. `triage` menyimpan hasil aturan tingkat keparahan.
Lihat [respons aturan tingkat keparahan](#severity-rule-responses).

`trace_id` dan `span_id` bernilai `null` jika log tidak punya tautan trace.
Dalam kasus itu, `next_action` adalah `inspect_related_logs` dengan target
`telemetry_logs`. Log, masalah, dan aksi memakai 2 pasangan `next_action` yang
sama.

`GET /api/logs/{log_id}` mengembalikan satu log dengan bentuk yang sama.

### <span id="issue-response">Respons masalah</span>

`GET /api/telemetry/issues/{issue_id}` mengembalikan satu masalah terkelompok.
Daftarnya mengembalikan objek yang sama. Contoh ini memakai versi respons
default, yaitu versi 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

Di versi 1, `status` bernilai `unresolved`, `resolved`, atau `ignored`. Untuk
masalah yang diarsipkan, `triage.ignored` bernilai `true`. Untuk pasangan
`next_action` dan pembacaan yang mengikutinya, lihat
[Investigasi masalah](/id/guides/investigate-an-issue).

`first_seen_at` dan `last_seen_at` adalah waktu kemunculan pertama dan
kemunculan terbaru. Keduanya tidak berubah saat status berubah.

Beberapa kolom hanya muncul jika LogBrew punya datanya:

| Kolom | Kapan muncul |
| --- | --- |
| `span_id` | Masalah punya tautan span. Jika tidak, kolom ini tidak disertakan. |
| `diagnostics` | Kemunculan terbaru punya tipe exception atau breadcrumb. Lihat [riwayat kemunculan masalah](#issue-occurrence-history). |
| `symbolication` | Hanya di `GET /api/telemetry/issues/{issue_id}`, jika masalah punya identitas artefak rilis. Lihat [Source map JavaScript](/id/guides/source-maps). |

`symbolication.status` bernilai `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved`, atau `unavailable`. Daftar,
perubahan status, dan perubahan aturan tidak mengembalikan `symbolication`.

Dengan `response_version=2`, masalah punya kolom yang sama, dengan perubahan
berikut:

| Kolom | Nilai versi 2 |
| --- | --- |
| `status` | `unresolved`, `resolved`, atau `archived`. Versi 1 menampilkan `archived` sebagai `ignored`. |
| `priority` | `high`, `medium`, atau `low`. |
| `priority_source` | `manual` jika seseorang menetapkan prioritas. `derived` jika prioritas mengikuti tingkat keparahan efektif. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Contoh ini hanya menampilkan sebagian kolom. Prioritas turunan bernilai `high`
untuk `error` dan `critical`, `medium` untuk `warning`, dan `low` untuk `info`.
Prioritas ini memakai `triage.effective_severity`, jadi aturan tingkat
keparahan masalah bisa mengubahnya.

Dengan `response_version=3`, masalah punya semua kolom versi 2 ditambah
`assignee`. `assignee` bernilai `null` jika masalah belum punya penanggung
jawab:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Kolom | Arti |
| --- | --- |
| `assignee.user_id` | ID pengguna penanggung jawab. Kirim sebagai `assignee` di filter atau perubahan. |
| `assignee.name` | Nama penanggung jawab, atau `null` jika akun tidak punya nama. |
| `assignee.email` | Alamat email penanggung jawab. |

Masalah tidak menampilkan penanggung jawab jika anggota yang ditugaskan tidak
bisa membaca proyek itu lagi.

Dengan `response_version=4`, `assignee` juga punya `type`. Penanggung jawab
`user` punya `user_id`, `name`, dan `email`, seperti di versi 3. Penanggung
jawab `team` punya `team_id`, `slug`, dan `name`. Versi 3 menampilkan tim
penanggung jawab sebagai `null`. CLI meminta versi 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

`response_version` lain mengembalikan `422` dengan `code: validation_failed`.
Halaman kursor memakai versi yang sama untuk setiap masalah di `issues`.

### <span id="assignee-list-response">Respons daftar penanggung jawab</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` mengembalikan
setiap akun yang bisa ditugaskan masalah di proyek itu:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Tambahkan `response_version=2` untuk juga mendapatkan `teams`: setiap tim di
organisasi proyek, dengan `team_id`, `slug`, dan `name`.

Jika akun tidak bisa membaca proyek itu, rute mengembalikan `404` dengan
`code: not_found`.

### <span id="action-response">Respons aksi</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` mengikuti satu pelaku atau sesi. Perlakukan `distinct_id` dan
`session_id` sebagai ID buram: jangan mengurai atau menafsirkan isinya. `session_id` dan `trace_id` bernilai `null`
jika tidak terekam. `span_id` tidak disertakan jika tidak terekam. Aksi tidak
punya tingkat keparahan. Lihat [Perekaman peristiwa produk](/id/guides/product-events).

### Respons metrik

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Setiap item adalah satu sampel. Jangan pakai jumlah sampel sebagai jumlah
peristiwa atau jumlah pengguna. `unit`, `temporality`, `trace_id`, dan
`span_id` bernilai `null` jika tidak terekam. Nilai `null` bukan nol.

### Respons rilis

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Satu baris mencakup satu proyek, rilis, lingkungan, dan layanan. Jumlah di
dalamnya hanya menggambarkan baris itu.

`trace_health.status` bernilai `unknown` jika baris tidak punya trace,
`no_errors_observed`, atau `errors_observed`. `error_rate_basis_points` adalah
porsi trace yang punya span error, dari `0` sampai `10000`. Nilai ini bukan
tingkat error untuk semua permintaan.

`next_action` menunjuk ke tipe sinyal pertama yang punya data, dengan urutan
ini:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Lihat [Rilis](/id/concepts/releases).

### Respons pencarian trace

`GET /api/telemetry/traces?pagination=cursor` mengembalikan satu baris untuk
setiap trace, ditambah catatan `naming_quality` untuk halaman yang
dikembalikan:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` hanya mencakup halaman yang dikembalikan. Nilai ini bukan
skor untuk seluruh akun. `truncated: true` berarti masih ada halaman lain. Jika
halaman itu punya nama generik, rute yang tidak cocok, atau operasi generik,
`next_action` adalah `improve_trace_naming` dengan target
`sdk_configuration`. Tanpa `pagination=cursor`, rute mengembalikan array trace
polos tanpa `naming_quality`.

`next_cursor` berisi `time` dan `trace_id`. Kirim keduanya sebagai
`cursor_time` dan `cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` mengembalikan span dari satu trace.
`GET /api/telemetry/traces/{trace_id}/summary` mengembalikan root span, span
error, layanan, durasi, dan jalur paling lambat tanpa atribut span mentah. `404`
dari ringkasan berarti tidak ada trace yang cocok dengan lingkup lengkapnya.
Jangan mencoba lagi tanpa filter. Lihat [respons span dan ringkasan trace](#trace-spans-and-summary-responses).

### Daftar kosong dan record yang tidak ada

Pembacaan daftar bisa tidak punya hasil yang cocok. Pembacaan detail punya
kontrak yang berbeda:

| Permintaan | Berhasil | Tidak ada record yang bisa dibaca |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` dengan satu [log](#log-response) | `404` dengan `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` dengan satu [masalah](#issue-response) | `404` dengan `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` dengan kemunculan | `404` dengan `code: not_found` di halaman pertama |
| `GET /api/telemetry/traces/{trace_id}` | `200` dengan span | `200` dengan `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` dengan satu ringkasan | `404` dengan `code: not_found` |

Log yang tidak ada mengembalikan `404` ini:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Masalah yang tidak ada memakai `"error": "issue not found"`. Ringkasan trace
yang tidak ada memakai `"error": "trace not found"`. ID yang tidak dikenal dan
ID yang tidak bisa dibaca akun mengembalikan respons yang sama.

Daftar dengan satu `project_id` yang tidak bisa dibaca akun mengembalikan
`200` dengan daftar kosong. Periksa ID proyek sebelum Anda melaporkan bahwa
tidak ada data.

### Pilihan proyek yang ditolak

Daftar log, masalah, aksi, metrik, rilis, dan trace menerima satu proyek
dengan `project_id` atau 2 sampai 50 proyek dengan `project_ids`. Katalog
atribut log menerima pemilih yang sama. Riwayat kemunculan masalah tidak
menerimanya.

Permintaan yang berisi `project_id` dan `project_ids` sekaligus mengembalikan
`422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` dengan UUID yang tidak valid, ID yang berulang, atau kurang dari
2 atau lebih dari 50 ID juga mengembalikan `422` dengan `code: validation_failed`.

Jika akun tidak bisa membaca salah satu proyek di kumpulan `project_ids`,
seluruh permintaan mengembalikan `404`. Respons tidak mengembalikan proyek
lainnya sebagai hasil sebagian:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Tampilkan error-nya, bukan daftar kosong atau jumlah nol. Baca lagi daftar
proyek. Jangan hapus proyek diam-diam, dan jangan mencoba lagi di semua
proyek. Kredensial yang didelegasikan, seperti koneksi MCP, mengembalikan
`403` dengan `code: forbidden` untuk proyek di luar koneksinya. Lihat
[lingkup proyek](/id/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Error kursor</span>

Log, masalah, aksi, metrik, dan kemunculan masalah memakai `cursor_time` dan
`cursor_id`. Kursor yang ditolak mengembalikan `422` dengan
`code: validation_failed`. Error ini tidak berarti daftarnya kosong.

| Permintaan | `error` |
| --- | --- |
| `pagination=cursor` dengan hanya 1 dari 2 kolom kursor | `cursor_time and cursor_id must be sent together` |
| `cursor_time` yang bukan stempel waktu RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Kolom kursor tanpa `pagination=cursor`, atau dengan nilai `pagination` lain | `pagination must be cursor when cursor pagination is requested` |

Contoh:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Salin `next_cursor` lengkap dari halaman sebelumnya. Jangan ganti
`cursor_time` dengan waktu saat ini. Jika kursor hilang, mulai lagi dengan
`pagination=cursor` dan filter aslinya. Kunci kueri yang tidak dikenal atau
nilai dengan tipe yang salah mengembalikan `422` dengan
`"error": "invalid query parameters"`.

### Respons kursor rilis

Kursor rilis punya 5 kolom. Permintaan berhasil yang tidak punya hasil cocok
mengembalikan `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Jika `next_cursor` bukan `null`, kirim kelima nilainya di permintaan
berikutnya:

| Kolom `next_cursor` | Parameter kueri |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` menandai posisi. Kolom ini tidak menggantikan `project_id`
atau `project_ids`. Pertahankan parameter proyek dan filter aslinya.
Lakukan URL-encode pada setiap nilai.

Dengan `pagination=cursor`, kursor yang tidak lengkap atau nilai rilis,
lingkungan, atau layanan yang kosong mengembalikan `422` dengan
`"error": "all release cursor fields must be sent together"`. `cursor_time`
yang tidak valid dan permintaan tanpa `pagination=cursor` mengembalikan error
yang sama dengan [kursor lainnya](#cursor-errors).

### Error pencarian trace

Error ini berlaku untuk `GET /api/telemetry/traces`. Masing-masing
mengembalikan `422` dengan `code: validation_failed`. Permintaan yang ditolak
bukan hasil kosong.

| Permintaan | `error` |
| --- | --- |
| `status` selain `error` atau `ok` | `trace status must be error or ok` |
| `min_duration_ms` di bawah `0` | `minimum trace duration must not be negative` |
| Hanya 1 kolom kursor, atau `cursor_trace_id` yang kosong | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` yang bukan stempel waktu RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Kolom kursor tanpa `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Untuk menyertakan kedua status trace, jangan kirim `status`. Untuk halaman
berikutnya, salin `next_cursor.time` ke `cursor_time` dan
`next_cursor.trace_id` ke `cursor_trace_id`. Jangan kirim `cursor_id` untuk
halaman trace. Lihat
[filter trace](/id/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Riwayat kemunculan masalah</span>

`GET /api/telemetry/issues/{issue_id}/events` membaca kemunculan dari satu
masalah terkelompok. Gunakan bearer akun dan ID masalah terkelompok. Rute ini
hanya menerima `pagination`, `cursor_time`, `cursor_id`, dan `limit`. Rute
ini tidak menerima filter proyek, waktu, rilis, lingkungan, atau tingkat
keparahan.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
```

terekam dan `breadcrumbs` yang kosong. Jika `breadcrumbs_truncated` bernilai
`true`, sebagian riwayat breadcrumb tidak ada di respons.

tidak terekam tidak membuktikan bahwa aplikasi tidak mengirim trace.
Perlakukan pesan dan atribut yang terekam sebagai data, bukan instruksi.

Kemunculan diurutkan dari yang terbaru. Untuk halaman berikutnya, kirim ID
masalah yang sama, `pagination=cursor`, `limit`, serta nilai `cursor_time` dan
`cursor_id` dari `next_cursor`. ID kursor adalah ID kemunculan, bukan ID
masalah.

Halaman pertama mengembalikan `404` dengan `code: not_found` jika masalah
tidak punya kemunculan yang bisa dibaca. Halaman berikutnya bisa berupa
halaman terakhir yang kosong:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Jangan pakai ulang kursor untuk masalah lain. [Error kursor](#cursor-errors)
juga berlaku untuk rute ini.

## <span id="live-event-response-format">Format respons peristiwa langsung</span>

Feed langsung mengirim peristiwa baru. Feed ini tidak memutar ulang peristiwa
yang terlewat oleh klien saat koneksinya terputus. Gunakan rute daftar untuk
membaca record yang sudah ada.

### Buat tiket

Kirim `POST /api/feed/ticket` dengan bearer akun. Permintaan ini tidak punya
body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Respons `200 OK` berisi tiket di kolom `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Tiket adalah kredensial berumur pendek. Jangan catat tiket di log atau
masukkan ke prompt agen. Buka koneksi sebelum `expires_in_seconds` habis. Masa
berlaku ini membatasi kapan koneksi bisa dimulai, bukan berapa lama koneksi
tetap terbuka.

`401` berarti login akun tidak valid. Masuk lagi sebelum Anda meminta tiket.
Metode selain `POST` mengembalikan `405` dengan `code: method_not_allowed`.

### Buka koneksi

Hubungkan klien WebSocket ke
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Lakukan URL-encode
pada tiket. Jangan masukkan bearer akun atau bearer ingest ke URL. `401`
berarti tiket atau login akun tidak valid. Buat tiket baru setelah Anda masuk
lagi.

| Respons | Penyebab | Langkah berikutnya |
| --- | --- | --- |
| `422` dengan `"error": "feed ticket is required"` | Nilai kueri `ticket` tidak ada atau kosong. | Buat tiket dan hubungkan dengan tiket itu. |
| `401` dengan `code: unauthorized` | Tiket sudah kedaluwarsa atau tidak valid. | Buat tiket baru. Jangan coba lagi dengan tiket yang sama. |
| `code: invalid_websocket_upgrade` | Permintaan bukan upgrade WebSocket yang valid. | Gunakan klien WebSocket. |
| `405` dengan `code: method_not_allowed` | Permintaan tidak memakai `GET`. | Gunakan `GET` untuk koneksi. |

Tunggu sebelum Anda menyambung ulang setelah error. Jangan menyambung ulang
terus-menerus dalam loop tanpa jeda.

### Baca pesan

Setiap pesan adalah envelope `{ "type": "...", "data": ... }`. Baca `type`
sebelum Anda mem-parse `data`. Lewati tipe yang tidak didukung klien.

| Tipe peristiwa | Payload data |
| --- | --- |
| `native_log` | Data log, dalam bentuk [respons log](#log-response). |
| `native_issue` | Data masalah terkelompok, dalam bentuk [respons masalah](#issue-response) versi 1. |
| `native_trace_span` | Satu span, dalam bentuk item [daftar span](#span-list). |
| `native_action` | Data aksi produk, dalam bentuk [respons aksi](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Data proyek. Baca lagi daftar proyek saat data ini berubah. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Penggunaan akun, dalam bentuk [penggunaan akun](/id/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Peristiwa `native_issue` memakai respons masalah versi 1: masalah yang
diarsipkan tampil sebagai `ignored`, dan peristiwa ini tidak punya prioritas.
Metrik dan rilis bukan tipe peristiwa langsung. Baca keduanya dengan rute
daftarnya. Tiket tidak memilih proyek. Periksa `project_id` setiap peristiwa
sebelum Anda menampilkannya di tampilan proyek. `logbrew watch --json` memakai
feed ini. Lihat [Referensi CLI](/id/reference/cli).

### Tangani koneksi yang tertutup

| Kode penutupan | Alasan | Langkah berikutnya |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Tunggu, lalu sambung ulang dengan tiket baru. Baca lagi rute daftar untuk mendapatkan record yang terlewat. |
| `1008` | `live feed access changed; sign in again` | Berhenti menyambung ulang. Masuk lagi sebelum Anda membuat tiket baru. |

Koneksi yang terputus karena hal lain bisa tidak punya alasan dari LogBrew.
Setelah Anda menyambung ulang, baca lagi rute daftar dan cocokkan record
berdasarkan ID.

## <span id="issue-status-response-examples">Contoh respons status masalah</span>

`PATCH /api/telemetry/issues/{issue_id}` dengan `{ "status": "resolved" }`
mengembalikan `200 OK` beserta masalah terkelompok yang sudah diperbarui,
dalam bentuk yang sama dengan [respons masalah](#issue-response). Kunci kueri
`response_version` memilih versinya. Respons ini tidak mengembalikan flag
keberhasilan.

Body menetapkan 1 atau lebih dari `status`, `priority`, dan `assignee`.
`status` menerima `unresolved`, `resolved`, atau `archived`. `ignored` adalah
nama lama untuk `archived`. Lihat [Perbarui satu masalah](/id/reference/telemetry-api#update-one-issue).

Periksa `id`, `status`, dan `priority` yang dikembalikan sebelum Anda
menampilkan keberhasilan. Jangan susun hasil dari nilai yang dikirim.
Perubahan status tidak menghapus kemunculan atau mengubah `first_seen_at` dan
`last_seen_at`. Perubahan ini juga tidak mengubah `severity` atau aturan
tingkat keparahan.

Perubahan yang ditolak mengembalikan `422` dengan `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Hasil | Penyebab |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Body tidak berisi satu pun dari 3 kolom itu. |
| `422`, `issue priority must be high, medium, or low` | Nilai prioritas tidak didukung. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | Nilai penanggung jawab tidak didukung. |
| `422`, `issue assignee cannot read this project` | Penanggung jawab tidak punya akses ke proyek. LogBrew tidak mengubah apa pun. |
| `422`, `issue assignee team is not a team of this project's organization` | Tim tidak termasuk dalam organisasi proyek. LogBrew tidak mengubah apa pun. |
| `403` dengan `code: forbidden` | Akun tidak bisa mengelola masalah di proyek itu. |
| `404` dengan `code: not_found` | Akun tidak bisa membaca masalah itu, atau masalahnya tidak ada. |

Kolom yang sudah punya nilai yang diminta tidak berubah. Setelah timeout atau
respons yang hilang, kirim lagi permintaan yang sama, atau baca masalahnya
dulu. Jangan kirim perubahan lain sebelum Anda membaca status saat ini. Lihat
[Operasi tulis](/id/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` mengembalikan `200 OK` dengan 1 hasil untuk
setiap ID masalah yang diminta, sesuai urutan permintaan. Setiap masalah yang
ditemukan memakai bentuk versi 3. Hasil `not_found` berisi `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",

      }
    },

      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

Contoh ini hanya menampilkan sebagian kolom masalah. `outcome` bernilai
`updated`, `unchanged`, atau `not_found`. Permintaan yang diulang mengembalikan
`unchanged` dan tidak mengubah apa pun. Lihat
[Perbarui masalah secara massal](/id/reference/telemetry-api#update-issues-in-bulk).

Permintaan massal gagal seluruhnya dalam kasus berikut:

| Hasil | Penyebab |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | Daftarnya kosong atau berisi lebih dari 100 ID. |
| `422`, `issue_ids must not contain duplicates` | Ada ID yang muncul lebih dari sekali. |
| `422` dengan `code: invalid_json` | Body berisi kolom yang tidak dikenal. |
| `403` dengan `code: forbidden` | Akun tidak bisa mengelola masalah di proyek itu. |
| `404`, `project not found` | Akun tidak bisa membaca proyek itu. |

## Lingkup permintaan analitik

Rute analitik, rute deret metrik, dan rute volume sinyal membaca satu proyek
dan satu rentang waktu. Setiap permintaan memerlukan `project_id` dan `since`.
`since` menerima durasi ringkas seperti `24h` atau `7d`, atau stempel waktu
RFC3339. `until` menerima stempel waktu RFC3339 dan default-nya adalah waktu
permintaan. Rentang ini mencakup `since`, tidak mencakup `until`, dan tidak
boleh lebih dari 31 hari.

`service_name`, `release`, dan `environment` adalah filter persis yang
opsional. Setiap nilai harus berisi 1 sampai 256 karakter setelah LogBrew
memangkas spasi. Rute perbandingan segmen menaruh filter ini di dalam setiap
segmen, bukan di tingkat atas.

Jika akun tidak bisa membaca proyek itu, rute ini mengembalikan `200 OK`
dengan jumlah nol. Rute ini tidak mengembalikan `404`. Hasil kosong tidak
memastikan akses ke proyek. Bandingkan `project_id` dengan proyek yang bisa
dibaca akun. Permintaan lewat koneksi MCP yang tidak mencakup proyek itu
mengembalikan `403` dan `forbidden`.

| Rute | Nilai `response_version` | Default |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2`, atau `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` atau `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` atau `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` atau `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` atau `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Tidak diterima | Skema `1` |
| `POST /api/telemetry/analytics/paths` | Tidak diterima | Skema `1` |
| `GET /api/telemetry/metrics/series` | Tidak diterima | Skema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Setiap respons diawali dengan `schema_version`, `query`, dan `purpose`.
`query` mengulang lingkup yang berlaku. Kolom ini tidak menyertakan filter yang
tidak Anda kirim. `purpose` adalah teks biasa yang menjelaskan pertanyaan yang
dijawab rute itu.

Nilai tingkat tidak disertakan jika penyebutnya nol. Tingkat yang tidak
disertakan bukan `0` dan bukan `null`. Baca `coverage` sebelum Anda memercayai
suatu tingkat.

### <span id="shared-scope-errors">Error lingkup bersama</span>

Error ini memakai HTTP `422` dan `validation_failed`:

| Penyebab | `error` |
| --- | --- |
| Tidak ada `project_id` | `product analytics project_id is required` |
| Tidak ada `since` | `product analytics since is required` |
| `since` bukan durasi atau stempel waktu RFC3339 | `invalid since value` |
| `until` bukan stempel waktu RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` tidak lebih awal daripada `until` | `product analytics since must be earlier than until` |
| Rentangnya lebih dari 31 hari | `product analytics range must not exceed 31 days` |
| Filter kosong, atau filter yang lebih dari 256 karakter | `product analytics context filters must be non-empty and at most 256 characters` |

Misalnya, permintaan tanpa `project_id` mengembalikan:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Rute deret metrik dan rute volume sinyal memakai aturan lingkup yang sama,
dengan teks `error` masing-masing. Bagian setiap rute di bawah mencantumkan
error tersebut.

Kunci kueri yang tidak dikenal mengembalikan `422` dengan respons
[parameter kueri tidak valid](/id/reference/api-errors#invalid-query-parameters).
Kolom JSON yang tidak dikenal, kolom JSON wajib yang tidak ada, atau nilai enum
yang tidak didukung mengembalikan `invalid_json`. Lihat
[JSON tidak valid](/id/reference/api-errors#invalid-json). Permintaan dengan
metode HTTP yang salah mengembalikan `405` dan `method_not_allowed`. Teks
`next`-nya menyebutkan metode dan kolom yang didukung. Lihat
[Metode tidak didukung](/id/reference/api-errors#unsupported-method).

`GET /api/telemetry/analytics/overview` menampilkan aktivitas di satu proyek:

menemukan nama peristiwa yang persis bagi rute analitik lainnya.

Kirim `response_version=3`. Versi 1 dan 2 mengembalikan jumlah yang sama,

### Baca konversi dan cakupan

`entry_rate` adalah `entered_units` dibagi `candidate_units`: 50 dari 60.
`overall_conversion_rate` adalah `completed_units` dibagi `entered_units`:
15 dari 50, atau 30%. Nilai ini bukan 15 dibagi semua kandidat. Jumlah ini
tidak menjelaskan mengapa unit berhenti.

Cakupan menghitung peristiwa, bukan sesi. Di sini, 120 peristiwa cocok dengan
satu langkah, dan 20 di antaranya tidak punya ID sesi. Hasilnya mengecualikan
20 peristiwa itu dari jumlah sesi. Jangan anggap peristiwa itu sebagai 20 sesi
yang gagal.

Langkah pertama tidak punya `conversion_from_previous`. Langkah terakhir tidak
punya `drop_off_to_next_units` dan `drop_off_to_next_rate`.

Unit mencapai langkah berikutnya hanya jika waktu setiap langkah lebih akhir
daripada langkah sebelumnya. Peristiwa dengan stempel waktu yang sama tidak
bisa memenuhi 2 langkah yang berurutan. Langkah terakhir harus terjadi dalam
`conversion_window_seconds` sejak langkah pertama.

Mode sesi menghitung sesi, bukan orang. Gunakan `identified_user` hanya untuk
peristiwa yang membawa ID subjek buram dengan jenis `user`. Mode itu bisa
menggabungkan peristiwa dari sesi yang berbeda di dalam periode konversi.
Gunakan unit dan langkah yang sama saat Anda membandingkan hasil.

`conversion_window_seconds` default-nya 24 jam atau panjang rentang, mana pun
yang lebih pendek. Nilai maksimumnya adalah panjang rentang dalam detik penuh,
dibulatkan ke atas.

### Hasil funnel kosong

Respons kosong yang berhasil tetap mencantumkan langkah yang diminta dengan
`units` nol. Jika tidak ada unit kandidat, `summary` tidak menyertakan
`entry_rate` dan `overall_conversion_rate`. Rute ini tidak mengembalikan `404`
karena tidak ada peristiwa yang cocok.

Baca `coverage` dan `next_action` untuk menemukan penyebabnya:

| `next_action.code` | Penyebab |
| --- | --- |
| `capture_product_activity` | Tidak ada peristiwa terklasifikasi di lingkup itu. |
| `choose_captured_funnel_steps` | Tidak ada peristiwa yang cocok dengan langkah yang diminta. |
| `sessionize_product_activity` | Ada peristiwa langkah, tetapi tidak satu pun punya ID sesi. |
| `identify_product_users` | Ada peristiwa langkah, tetapi tidak satu pun punya subjek dengan jenis `user`. |
| `verify_funnel_entry` | Tidak ada unit yang masuk di langkah 1. |
| `investigate_funnel_drop_off` | Ada unit yang masuk, tetapi tidak ada unit yang menyelesaikan semua langkah. |
| `compare_funnel_contexts` | Setidaknya 1 unit menyelesaikan funnel. |

### Permintaan funnel yang ditolak

Selain [error lingkup bersama](#shared-scope-errors), permintaan berikut
mengembalikan `422` dan `validation_failed`. Kurang dari 2 atau lebih dari 8
langkah:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`conversion_window_seconds` bernilai `0`, atau nilai yang melebihi panjang
rentang:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`event_name` yang kosong, lebih dari 256 karakter, atau berisi karakter
kontrol mengembalikan
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Langkah `interaction` juga harus berupa nama aksi yang valid. Jika tidak,
error-nya adalah `product analytics interaction event_name must be a bounded stable action name`.

Perbaiki permintaan sebelum Anda mengirimnya lagi. Jangan hapus langkah atau
ubah unit analisis hanya agar hasilnya tidak kosong.

## Analisis peristiwa persis dan analisis otomatis

Retensi dan siklus hidup menerima 2 bentuk permintaan. Gunakan
`response_version` untuk memilih bentuk yang menjawab pertanyaan Anda:

| Analisis | `response_version` | Pemilih peristiwa |
| --- | --- | --- |
| Retensi untuk peristiwa persis | `1`, atau tidak dikirim | Kirim `start_event` dan `return_event` sekaligus. |
| Siklus hidup untuk satu peristiwa persis | `1`, atau tidak dikirim | Kirim `event`. |
| Retensi atau siklus hidup otomatis | `2` | Jangan kirim pemilih peristiwa. |

Pemilih persis berisi `kind` dan `event_name`. `kind` bernilai `page_view`,
`screen_view`, atau `interaction`. Salin `event_name` dari
`classified_activity.top_events`. Jangan menebak nama peristiwa dari label
tombol.

Kedua bentuk hanya menghitung pengguna: ID subjek buram dengan jenis `user`.
Subjek anonim dan peristiwa tanpa ID subjek yang bisa dipakai tidak dihitung
sebagai pengguna. Respons tidak pernah mengembalikan ID subjek.

Interval tetap adalah `hour`, `day`, `week`, dan `thirty_day`. Semuanya
berupa durasi tetap. `thirty_day` berarti 30 hari, bukan 1 bulan kalender.
Jika Anda tidak mengirim `interval`, API memakai `hour` untuk rentang 48 jam
atau kurang, dan `day` untuk rentang yang lebih panjang.

Respons peristiwa persis punya `schema_version: 1`. `query`-nya mengulang
pemilih dan tidak menyertakan `activity_scope`. Respons otomatis punya
`schema_version: 2` dan `query.activity_scope: "all_classified_activity"`.
Respons ini tidak menyertakan pemilih. Pemilih yang berbeda bisa mengubah
hasil tanpa perubahan apa pun pada aktivitas yang terekam.

Jenis dan temporalitas sebuah deret menentukan `aggregation.code`-nya dan
statistik di setiap titik data. Titik data tidak menyertakan statistik yang
tidak berlaku. Statistik yang tidak ada bukan nol.

| Jenis dan temporalitas | `status` | `aggregation.code` | `value` | Statistik lain |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Sampel terakhir | `last`, `min`, `max`, `average` |

`limited` adalah respons yang berhasil, bukan error. Status ini menambahkan
`aggregation.limitation`, yang menjelaskan mengapa LogBrew hanya menampilkan
nilai mentah. `ready` tidak membuktikan perekaman yang lengkap.

Baca `coverage` sebelum Anda menggambar grafik:

- `samples` menghitung sampel dari semua deret yang cocok, termasuk deret yang
  tidak dikembalikan respons.
- `series` menghitung deret yang cocok. `returned_series` dan `points`
  menghitung data yang dikembalikan.
- `truncated` bernilai `true` jika `series_limit` membuang deret bervolume
  lebih rendah.
- `expected_buckets_per_series` adalah jumlah interval waktu yang mungkin ada
  dalam rentang.

nol atau salin nilai sebelumnya. Setiap titik data mengembalikan paling banyak
3 `trace_exemplars`. Exemplar trace menautkan satu sampel ke satu trace.
Exemplar itu tidak menjelaskan setiap sampel di interval waktu tersebut. Jika
tidak ada titik data yang punya exemplar trace, `next_action.target` adalah
`metric_samples`.

### Lingkup dan error deret metrik

`project_id`, `name`, dan `since` wajib dikirim. `name` paling banyak berisi
200 karakter. `interval` bernilai `auto`, `1m`, `5m`, `15m`, `1h`, `6h`, atau
`1d`. Default-nya `auto`, yang memilih interval terkecil dengan paling banyak
300 interval waktu. Interval eksplisit tidak boleh memerlukan lebih dari 500
interval waktu.

`group_by` bernilai `none`, `service_name`, `release`, atau `environment`.
Default-nya `none`. Tanpa pengelompokan, jenis, unit, dan temporalitas yang
berbeda tetap berada di deret terpisah. `series_limit` menerima `1` sampai
`20`. Default-nya `10`.

Hasil kosong mengembalikan `200` dengan `series: []` dan `samples` nol. Objek
`coverage` tidak menyertakan `first_seen_at` dan `last_seen_at`. Ini tidak
membuktikan bahwa aplikasi tidak pernah mengirim metrik itu. Periksa proyek,
nama metrik, dan rentang waktunya.

Permintaan tanpa `name` mengembalikan `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Interval waktu 1 menit selama 7 hari mengembalikan `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Error `422` lainnya adalah `metric series group_by is not supported`,
`metric series interval is not supported`, dan
`metric series_limit must be between 1 and 20`.

Node diurutkan menurut waktu di kedua arah. Jalur bukan pemutaran ulang sesi
secara lengkap. LogBrew membaca paling banyak 1.024 peristiwa bernama per sesi
sebelum memilih jangkar: peristiwa paling awal untuk `following` dan peristiwa paling akhir
untuk `preceding`. Jangkar di luar batas itu bisa tidak disertakan.

### <span id="filter-the-anchor-by-property">Filter jangkar berdasarkan properti</span>

Kirim paling banyak 4 `property_filters`, masing-masing dengan satu `key` dan
`value` yang persis. Salin kuncinya dari [katalog properti](#analytics-property-catalog).
Filter hanya berlaku untuk jangkar, bukan untuk peristiwa di sekitarnya. Nilai
peka huruf besar-kecil. Jika ada filter, `query` mengulangnya, dan
`coverage.anchor_property_filters` melaporkan:

| Kolom | Arti |
| --- | --- |
| `context_events` | Peristiwa jangkar dalam lingkup sebelum filter properti diterapkan. |
| `property_ready_events` | Peristiwa jangkar yang punya semua kunci yang diminta. |
| `missing_property_events` | Peristiwa jangkar yang tidak punya 1 atau lebih kunci yang diminta. |
| `matching_events` | Peristiwa jangkar yang nilainya cocok dengan semua filter. |
| `nonmatching_value_events` | Peristiwa jangkar yang punya semua kunci, tetapi dengan nilai yang berbeda. |
| `property_ready_rate` | `property_ready_events` dibagi `context_events`. |
| `match_rate` | `matching_events` dibagi `property_ready_events`. |

Kunci yang tidak ada dan nilai yang berbeda memerlukan perbaikan yang berbeda.
Jangan jumlahkan keduanya. Objek ini tidak disertakan jika permintaan tidak
punya filter properti.

sekitar 3 nilai yang berbeda. Deskriptornya tidak menampilkan nilai itu.

| `coverage.properties_truncated` | `true` jika jumlah kunci melebihi `limit`. Persempit lingkupnya, atau naikkan `limit` sampai 50. |
| `coverage.values_returned` | Selalu `false`. |

Array `properties` yang kosong tidak membuktikan bahwa proyek tidak punya
peristiwa produk. Baca `summary`, `coverage`, dan `next_action`.

## <span id="analytics-segment-comparison">Perbandingan segmen analitik</span>

`POST /api/telemetry/analytics/segments/compare` membandingkan seberapa sering
sesi atau pengguna mencapai satu peristiwa persis di 2 sampai 4 segmen dalam
satu proyek. Segmen memilih peristiwa berdasarkan layanan, rilis, lingkungan,
dan nilai properti. Segmen pertama menjadi acuan.

### Tentukan perbandingan

Kirim body JSON ini dengan autentikasi akun dan
`Content-Type: application/json`. Di sini, `basic` dan `premium` adalah nilai
paket dari aplikasi contoh, bukan paket LogBrew:

```json

      "key": "premium",

      "environment": "production",
```

`target` dan `segments` wajib dikirim. `analysis_unit` bernilai `session` atau
`identified_user`. Default-nya `session`, yang menghitung sesi, bukan orang.
`interval` menerima nilai yang sama dengan ikhtisar. Default-nya `auto`.

Setiap segmen memerlukan `key` yang unik, `label`, dan kumpulan filter yang
berbeda:

- `key`: 1 sampai 32 byte. Awali dengan huruf ASCII kecil atau angka. Gunakan
  hanya huruf ASCII kecil, angka, `_`, dan `-`.
- `label`: 1 sampai 80 karakter, tanpa karakter kontrol.
- `service_name`, `release`, `environment`: opsional. Setiap nilai berisi 1
  sampai 256 karakter, tanpa karakter kontrol.
- `property_filters`: 0 sampai 4 filter. Setiap kunci hanya boleh muncul
  sekali dalam satu segmen. Peristiwa harus cocok dengan semua filter segmen.
  Nilai peka huruf besar-kecil, berisi 1 sampai 256 karakter, dan LogBrew
  memangkas spasi di awal dan akhir.

Segmen tanpa filter memilih semua aktivitas terklasifikasi di proyek dan
rentang waktu itu. Segmen bisa saling tumpang-tindih. Label atau kunci yang
berbeda tidak membuat 2 kumpulan filter yang identik menjadi valid.

`release_volume_not_included` sebagai nol rilis.

### Rentang waktu kosong dan dipersingkat

Jika tidak ada sinyal yang cocok, kelima deret tetap ada, dan titik datanya
berisi angka nol yang eksplisit. Permintaan yang gagal berbeda. Jangan ganti
error dengan grafik berisi nol.

Bandingkan `query.requested_since` dengan `query.since`. Jika retensi data
mempersingkat rentang waktu, `coverage.retention.window_clipped` bernilai
`true` dan `limitations` berisi `retention_window_clipped`. Jika tidak ada
bagian rentang waktu yang diminta yang tersisa, `query.bucket_count` bernilai
`0` dan setiap deret punya array `points` yang kosong. Ini tidak membuktikan
bahwa tidak ada peristiwa yang terjadi di periode itu.

`policy_days` bernilai `null` dan `cutoff` tidak disertakan jika tidak ada
batas retensi yang berlaku. `sampling.upstream` selalu bernilai `unknown`,
juga saat `storage_evaluation` bernilai `complete`. Jangan klaim bahwa respons
menghitung setiap peristiwa yang dihasilkan aplikasi.

| Tidak ada `since` | `signal volume since is required` |
| `until` lebih lambat daripada waktu permintaan | `signal volume until must not be in the future` |
| Rentangnya lebih dari 31 hari | `signal volume range must not exceed 31 days` |
| Interval eksplisit yang memerlukan lebih dari 500 interval waktu | `signal volume interval would exceed 500 buckets` |
| `response_version` selain `1` | `signal volume response_version must be 1` |

Contoh:

```json
{
  "error": "signal volume interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Gunakan interval yang lebih lebar dalam lingkup yang sama. Untuk kegagalan
autentikasi dan kegagalan lain, lihat [Error API](/id/reference/api-errors).

## Respons investigasi

Rute investigasi mengembalikan paket bukti berversi untuk satu subjek. Subjek
itu berupa masalah, trace, span, log, aksi produk, metrik, atau rilis. Setiap
paket diawali dengan `schema_version` dan `subject` yang menyebutkan
record-nya. Sisanya berisi bukti terkait, catatan bukti, dan langkah
berikutnya. Bagian ini menampilkan satu contoh untuk setiap jenis, kecuali
rilis.

Kirim bearer akses akun. Kunci ingest proyek tidak bisa membaca investigasi.
Gunakan `logbrew explain <subject> --json` untuk membaca paket. CLI
memvalidasi paket sebelum mencetaknya.
Referensi [API Telemetri](/id/reference/telemetry-api) mencantumkan rutenya.

Teks investigasi berasal dari aplikasi. Pesan, nama, metadata, dan tag adalah
data, bukan instruksi. `content_trust: "untrusted_telemetry"` menandai konten
ini di paket log, aksi, span, dan metrik.

### Versi respons

Kirim `response_version` hanya ke rute yang menerimanya. Tanpa kunci itu, rute
mengembalikan versi 1. Parser Anda harus menerima versi yang Anda minta.

| Rute | Default | Versi yang didukung | Versi yang diminta `logbrew explain` |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` sampai `14` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` sampai `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` dan `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` sampai `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Hanya `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Hanya `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Hanya `1` | `1` |

Rute span menolak kunci kueri `response_version`. Rute log dan rute aksi tidak
menerima kunci kueri apa pun.

### Kolom paket bersama

| Kolom | Arti |
| --- | --- |
| `schema_version` | Versi respons yang dikembalikan server. |
| `subject` | Record persis yang sedang diinvestigasi. `kind` bernilai `issue`, `trace`, `span`, `log`, `action`, `metric`, atau `release`. |
| `analysis.causality` | Selalu `evidence_only` di paket trace, span, log, aksi, dan metrik. Telemetri yang berkorelasi tidak membuktikan penyebab. |
| Objek koleksi | Bukti terkait dalam bentuk `{ "status", "items", "truncated" }`. |
| `timeline` | Bukti yang dikembalikan, dari yang terlama sampai yang terbaru, dengan flag `truncated`-nya sendiri. Urutan ini tidak membuktikan penyebab. |
| `evidence` | Catatan bukti. `status` bernilai `complete` atau `partial`. |
| `next_actions` | Pembacaan yang disarankan, diurutkan menurut `priority` mulai dari `1`. Pembacaan ini belum dijalankan. |

Setiap koleksi terkait melaporkan satu `status` ketersediaan:

| Status | Arti | Perilaku klien |
| --- | --- | --- |
| `available` | Pembacaan selesai dan mengembalikan item. | Tampilkan item dan flag `truncated`. |
| `not_linked` | Subjek tidak punya ID untuk tautan ini, misalnya ID trace. | Jelaskan tautan yang tidak ada. Jangan bangun tautan dari stempel waktu. |
| `not_found` | Pembacaan selesai dan tidak menemukan bukti yang tersimpan. | Tampilkan hasil kosong. |
| `unavailable` | Pembacaan opsional gagal. Subjeknya tetap valid. | Tetap tampilkan subjek. Coba lagi nanti. Jangan tampilkan nol item sebagai hasil. |

Catatan bukti punya 4 daftar terurut berisi nama kolom yang stabil:
`captured_fields`, `missing_fields`, `redacted_fields`, dan
`truncated_fields`. `status` bernilai `complete` hanya jika 3 daftar terakhir
kosong. Data yang disamarkan bukan data yang tidak terekam. Data yang dipotong
bukan data yang lengkap. Jangan isi nilai yang disamarkan atau dipotong.

### Batas investigasi

Batas berikut membatasi satu respons. Flag `truncated` atau entri
`truncated_fields` menunjukkan bahwa sebuah batas membuang sebagian data.

| Bukti | Batas |
| --- | --- |
| Item terkait dalam satu koleksi | 20 |
| Span tersimpan yang dibaca untuk satu trace | 1.000 |
| Item timeline | 50 untuk paket log, aksi, dan span. 100 untuk paket trace dan metrik. |
| Atribut terstruktur, properti, dan metadata | 64 nilai skalar, 4 tingkat objek atau array, 16 item di setiap array, 512 karakter di setiap string |
| Rentang waktu korelasi | 5 menit sebelum dan sesudah log, aksi, atau kemunculan masalah yang dipilih. Untuk trace atau span, 5 menit sebelum awal dan sesudah akhir, paling lama 24 jam. |

Setiap bagian jenis paket mencantumkan batasnya sendiri.

### Respons investigasi masalah

Gunakan `GET /api/telemetry/issues/{issue_id}/investigation` untuk membaca
bukti dari satu kemunculan masalah terkelompok.
Panduan [Investigasi masalah](/id/guides/investigate-an-issue) menunjukkan cara
membaca bukti secara berurutan. Minta versi 13:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

Kunci kuerinya adalah `response_version`, `selection`, dan `occurrence_id`.
`selection` bernilai `recommended`, `first`, atau `latest`. Nilainya peka
huruf besar-kecil. Di versi 2 sampai 14, pemilih yang tidak dikirim memakai
`recommended`. Versi 1 mengembalikan kemunculan tersimpan terbaru dan tidak
menerima pemilih. Filter daftar masalah tidak berlaku untuk pembacaan ini.

baca kunci yang tidak ada sebagai `null`.

`subject.status` dan status di `lifecycle` melaporkan masalah yang diarsipkan
sebagai `ignored`. Respons daftar dan detail masalah memakai `archived` di
versi respons 2 dan yang lebih baru.

Batas masalah: rekomendasi membaca paling banyak 50 kemunculan yang tersimpan.
Tren punya paling banyak 30 interval waktu. Setiap distribusi mengembalikan
paling banyak 10 nilai. Stack punya paling banyak 32 frame.

#### Error permintaan investigasi masalah

Gunakan `selection` atau `occurrence_id`, salah satunya saja. Jangan kirim
keduanya, meskipun keduanya memilih kemunculan yang sama:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Penyebab | Pemulihan |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | Permintaan berisi kedua pemilih. | Pertahankan satu pemilih. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | Permintaan berisi pemilih dan versi 1, atau tanpa versi. | Kirim `response_version=13`. Pertahankan pemilihnya. |
| `422` | `issue investigation response_version must be 1 through 14` | Versinya di luar rentang. | Kirim versi yang didukung. |
| `422` | `invalid query parameters` | Kunci yang tidak dikenal, UUID yang tidak valid, versi yang bukan bilangan bulat, atau nilai `selection` yang tidak dikenal. | Perbaiki [kueri](/id/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | Kemunculan itu tidak ada di riwayat tersimpan kelompok ini. | Salin ID kemunculan dari peristiwa masalah ini. Jangan memakai `latest` atau `recommended` sebagai gantinya tanpa persetujuan. |
| `404` | `issue not found` | Tidak ada proyek yang bisa dibaca yang punya masalah ini. | Periksa akun dan UUID masalah. Jangan kirim UUID kemunculan sebagai ID masalah. |

Kemunculan yang tidak ada tidak berarti masalahnya juga tidak ada. `404` tidak
menunjukkan apakah akun lain bisa membaca masalah itu.

### Respons investigasi trace

Gunakan `GET /api/telemetry/traces/{trace_id}/investigation` untuk membaca satu
trace beserta jalur kegagalannya, jalur paling lambatnya, dan sinyal terkait.
Kunci kuerinya adalah `response_version`, `project_id`, `release`, dan
`environment`. Semuanya opsional. Minta versi 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

Versi 2 menambahkan `cause` dan `fix` ke setiap masalah terkait. Versi 3
menambahkan `span_id` ke masalah, aksi, dan metrik terkait jika `span_id`
terekam.

| Kolom | Arti |
| --- | --- |
| `subject` | Total trace dari span yang dianalisis. |
| `analysis.status` | `errors_observed`, `latency_focus`, atau `no_error_observed`. |
| `analysis.first_error_path` | Rantai parent yang diketahui dari root sampai span error paling awal. |
| `analysis.bottleneck_path` | Rantai parent yang diketahui sampai child span paling lambat. |
| `spans.items[].roles` | Alasan span ada di pratinjau: `root`, `first_error`, `error_path`, `bottleneck`, `bottleneck_path`, `error`, atau `slow`. |
| `correlations.window` | Rentang waktu dan lingkup deployment yang dipakai untuk pembacaan terkait. |
| `correlations.issues`, `logs`, `actions`, `metrics` | Sinyal dengan ID trace yang sama dalam rentang waktu itu. |

`trace.parentage` tidak terekam jika span menyebut parent yang tidak disimpan
LogBrew. Pratinjau span berisi paling banyak 64 span. Setiap jalur analisis
berisi paling banyak 64 span. Pembacaan terkait memakai paling banyak 8
lingkup deployment.

Langkah berikutnya dengan target `trace_span` menyebutkan `span_id` dari paket
ini. Untuk membaca span itu, kirim rute span dengan `project_id`,
`environment`, dan `release` milik span tersebut.

### Respons investigasi span

Gunakan `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation`
untuk membaca satu operasi dalam trace. Kirim `project_id`, `environment`, dan
`release`. Ketiganya wajib dikirim. Salin nilainya dari span yang dipilih.
Jangan kirim `id` baris span sebagai `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

| Kolom | Arti |
| --- | --- |
| `subject.description_status` | `captured`, `not_captured`, atau `unavailable`. |

| `analysis.focus` | Item perbandingan dengan perubahan relatif terbesar, atau perubahan absolut terbesar jika tidak ada perubahan relatif. Bernilai `null` jika tidak ada item yang bisa dibandingkan. |
| `series[].aggregation.code` | `gauge_last`, `delta_sum`, `distribution_p95`, `raw_cumulative_last`, atau `raw_last`. |

| `next_actions[]` | `code`, `target`, `reason` berupa teks biasa, dan lingkup `context` untuk pembacaan berikutnya. |

`relative_change_percent` adalah `(current - previous) / abs(previous) * 100`.
Nilainya `null` jika nilai sebelumnya nol atau tidak ada.
`expected_buckets_per_series` menghitung interval waktu yang mungkin ada, bukan interval waktu yang punya
data. Jangan gambar interval waktu kosong sebagai nol. Deployment yang terjadi
di dekat suatu perubahan tidak membuktikan bahwa deployment itu menyebabkan
perubahan tersebut.

Proyek yang tidak bisa dibaca akun mengembalikan `200 OK` dengan
`analysis.status: "no_samples"`, bukan `404`. Hasil kosong tidak
menggambarkan tipe sinyal lain.

Batas metrik: rentang paling lama 31 hari. Setiap deret punya paling banyak
500 interval waktu. `series_limit` bernilai 1 sampai 20, dengan default 10.
Respons mengembalikan paling banyak 20 exemplar dan 20 deployment.

| HTTP | `error` | Pemulihan |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Jangan kirim `response_version`, atau kirim `2`. |
| `422` | `metric series project_id is required` | Kirim satu ID proyek yang bisa dibaca. |
| `422` | `metric series name is required` | Salin nama dari daftar metrik. |
| `422` | `metric series since is required` | Kirim nilai seperti `24h` atau stempel waktu RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | Gunakan rentang yang lebih pendek. |
| `422` | `metric series interval would exceed 500 buckets` | Gunakan `interval=auto` atau interval yang lebih lebar. |
| `422` | `metric series_limit must be between 1 and 20` | Kirim nilai dari 1 sampai 20. |

`interval` bernilai `auto`, `1m`, `5m`, `15m`, `1h`, `6h`, atau `1d`.
`group_by` bernilai `none`, `service_name`, `release`, atau `environment`.
Nilai lain mengembalikan `422`.

### Error investigasi

| HTTP | Rute | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Aksi | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, aksi, masalah | `invalid URL path parameters` jika ID di path bukan UUID |
| `422` | Masalah, trace, span, metrik | `invalid query parameters` untuk kunci yang tidak dikenal atau nilai dengan tipe yang salah |

`404` berarti tidak ada proyek yang bisa dibaca yang punya record itu. Setiap
rute juga mengembalikan `401` tanpa autentikasi yang valid dan `405` untuk
metode selain `GET`. Lihat [Error API](/id/reference/api-errors) untuk respons
[tidak ditemukan](/id/reference/api-errors#resource-not-found),
[path](/id/reference/api-errors#invalid-path-value),
[autentikasi](/id/reference/api-errors#authentication-failure), dan
[metode](/id/reference/api-errors#unsupported-method).

Pembacaan bukti opsional bisa gagal di dalam respons `200 OK`. Dalam kasus
itu, koleksinya melaporkan `unavailable`. Jangan tampilkan sebagai
`not_found` atau sebagai nol record.

## <span id="severity-values">Nilai tingkat keparahan</span>

Nilai tingkat keparahan yang tampil ke pengguna adalah `info`, `warning`,
`error`, dan `critical`. SDK dan runtime bisa mengirim alias umum seperti
`trace`, `debug`, `warn`, atau `fatal`. Respons REST dan respons langsung
selalu mengembalikan nilai kanonis. Misalnya, LogBrew menerima `warn` sebagai
input dan mengembalikan `warning`. Ingest menolak nilai tingkat keparahan yang
tidak dikenal.

| Alias | Nilai kanonis |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Respons aturan tingkat keparahan</span>

Aturan tingkat keparahan mengubah cara LogBrew menampilkan log atau masalah.
Aturan ini tidak mengubah tingkat keparahan yang direkam aplikasi. Log dan
masalah mengembalikan objek `triage`:

| Kolom | Arti |
| --- | --- |
| `effective_severity` | Tingkat keparahan yang ditampilkan. Tanpa aturan, nilainya sama dengan `severity`. |
| `ignored` | `true` jika aturan log mengabaikan log itu, atau jika masalahnya diarsipkan. |
| `rule_applied` | `true` jika aturan tingkat keparahan atau status diabaikan berlaku. `false` adalah nilai default, bukan data yang tidak terekam. |

Gunakan `triage.effective_severity` untuk tampilan. Pertahankan `severity`
sebagai nilai yang terekam. Secara default, daftar log tidak menyertakan log
yang diabaikan. Kirim `status=ignored` atau `status=all` di `GET /api/logs`
untuk menyertakannya.

Akun harus punya izin untuk mengelola masalah di proyek itu. Akses baca tidak
cukup. Tanpa izin itu, perubahan aturan mengembalikan `403` dengan
`code: forbidden`.

### Ubah aturan log

`PUT /api/logs/{log_id}/triage-rule` menetapkan aturan untuk log itu dan untuk
log berikutnya dengan signature yang sama. Body memerlukan `severity` dan
`ignored` sekaligus:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Respons `200 OK` berisi [log](#log-response) lengkap. `severity`-nya tetap
`warning`. `triage`-nya menampilkan aturan itu:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Kutipan ini hanya menampilkan kolom yang berubah. `severity` di permintaan
bernilai `source`, `info`, `warning`, `error`, atau `critical`. `source`
memulihkan tingkat keparahan yang terekam. Nilai ini tidak membuat log yang
diabaikan aktif kembali. Untuk menampilkan log itu lagi, kirim
`"ignored": false`.

### Ubah aturan masalah

`PUT /api/telemetry/issues/{issue_id}/triage-rule` menetapkan tingkat
keparahan yang ditampilkan untuk masalah terkelompok dan kemunculan
berikutnya. Body hanya menerima `severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Respons `200 OK` berisi [masalah](#issue-response) lengkap dalam versi 1.
`severity` dan `status` yang terekam tidak berubah:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Kutipan ini hanya menampilkan sebagian kolom. Aturan tidak menyelesaikan,
mengarsipkan, atau membuka kembali masalah. Gunakan
[perubahan status](#issue-status-response-examples) untuk itu. Prioritas
turunan mengikuti tingkat keparahan efektif yang baru. Baca masalah itu dengan
`response_version=2` atau `3` untuk melihatnya.

Tingkat keparahan yang tidak didukung mengembalikan `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Kolom body yang tidak dikenal, seperti `status` pada aturan masalah,
mengembalikan `422` dengan `code: invalid_json`. Log atau masalah yang tidak
ada atau tidak bisa dibaca mengembalikan `404` dengan `code: not_found`. Jika
respons hilang, baca lagi log atau masalahnya sebelum Anda mengirim aturan itu
lagi.

## Format respons error

Error aplikasi mengembalikan envelope JSON. Contoh ini menampilkan permintaan
yang ditolak; teks `error` dan `next` bergantung pada jenis error-nya:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Gunakan `code` untuk percabangan program dan `next_action` untuk otomatisasi.
Tampilkan `error` dan `next` sebagai teks biasa untuk dibaca orang. Jangan mem-parse
kata-katanya. Beberapa error menambahkan kolom, seperti `limit`, `reset_at`,
atau `retry_after_seconds`. Respons tanpa body JSON tidak punya `code`
LogBrew. Lihat [Error API](/id/reference/api-errors) untuk semua kode.

## Baca data dengan CLI

CLI membaca rute yang sama dan mengembalikan JSON yang sama dengan `--json`.
Mulai secara luas, lalu persempit:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Tambahkan `--pagination cursor` untuk mendapatkan envelope kursor. CLI meminta
versi respons masalah 4. Lihat [Baca halaman berikutnya](/id/reference/cli#read-the-next-page)
dan [Pantauan langsung](/id/reference/cli#live-watch).

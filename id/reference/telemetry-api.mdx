API Telemetri berupa JSON melalui HTTP di `https://api.logbrew.co`. SDK publik
mengirim batch yang dikelolanya ke `POST /v1/events`. Klien native kustom mengirim
envelope native ke `POST /api/telemetry/ingest`. Kedua rute ingest memerlukan
bearer ingest khusus proyek.

Pembacaan dan perubahan milik akun memakai bearer akun. Jangan pernah memakai
bearer akun atau sesi browser sebagai konfigurasi SDK atau ingest. Jangan
pernah mengirim bearer ingest ke rute baca.

## Kirim permintaan dengan lingkup terbatas

Gunakan daftar periksa ini sebelum klien mengirim permintaan:

1. Pilih rute dan metode HTTP dari tabel endpoint.
2. Gunakan bearer yang benar: bearer ingest untuk ingest, bearer akun untuk
   semua hal lain.
3. Pilih lingkup proyek yang didukung rute. Jangan perluas lingkup setelah
   respons kosong.
4. Tambahkan hanya kunci kueri yang diterima rute. Lihat
   [Filter kueri](/id/reference/telemetry-api-filters).
5. Kirim `Content-Type: application/json` jika rute punya body JSON.
6. Baca status HTTP dan body respons sebelum Anda mencoba lagi.
7. Jauhkan bearer, tiket feed, dan body respons lengkap dari log dan prompt
   agen.

## Endpoint

### Ingest

| Metode | Path | Tujuan |
| --- | --- | --- |
| `POST` | `/v1/events` | Ingest batch yang dibuat dan dikirim SDK LogBrew publik. |
| `POST` | `/api/telemetry/ingest` | Ingest envelope telemetri native dari klien kustom. |

Biarkan SDK membuat batch `/v1/events`. Jangan menyusunnya secara manual.
Untuk envelope native, lihat [Integrasi SDK](/id/guides/sdk-ingestion).

### Deployment

| Metode | Path | Perintah CLI |
| --- | --- | --- |
| `PUT` | `/api/telemetry/deployments/{deployment_id}` | `logbrew deploy` |
| `GET` | `/api/telemetry/deployments/{deployment_id}?project_id=<project-uuid>` | Tidak ada |
| `GET` | `/api/telemetry/deployments?project_id=<project-uuid>` | Tidak ada |

Catat deployment dari otomatisasi rilis setelah deployment berhasil atau
gagal. Body `PUT` berisi `project_id`, `release`, `environment`,
`service_name`, `status` (`succeeded` atau `failed`), `started_at`,
`finished_at`, dan `commit_sha` yang opsional. Gunakan nilai `release`,
`environment`, dan `service_name` yang sama dengan yang dikirim SDK Anda. Akun
harus memiliki proyek tersebut.

`deployment_id` adalah ID Anda sendiri untuk deployment. Percobaan ulang
dengan ID dan body yang sama mengembalikan deployment yang tersimpan. ID yang
sama dengan body berbeda gagal dengan `409` dan `idempotency_conflict`.
Gunakan ID baru untuk deployment yang berbeda.

Perintah `logbrew explain` di [CLI](/id/reference/cli) membaca rute ini dan
memvalidasi responsnya.

| Metode | Path | Perintah CLI |
| --- | --- | --- |
| `GET` | `/api/logs/{log_id}/investigation` | `logbrew explain log` |
| `GET` | `/api/telemetry/issues/{issue_id}/investigation` | `logbrew explain issue` |
| `GET` | `/api/telemetry/issues/{issue_id}/correction-verification` | `logbrew investigate issue <issue_id> verify` |
| `GET` | `/api/telemetry/traces/{trace_id}/investigation` | `logbrew explain trace` |
| `GET` | `/api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `logbrew explain span` |
| `GET` | `/api/telemetry/actions/{action_id}/investigation` | `logbrew explain action` |
| `GET` | `/api/telemetry/metrics/investigation` | `logbrew explain metric` |

### Akun dan masuk

Rute penggunaan, kuota, langganan, dan logout ada di
[API akun](/id/reference/account-api).

## Kode status sukses

| Operasi | Status sukses |
| --- | --- |
| Ingest, pembacaan, pembaruan masalah, aturan, deployment, analitik, dan tiket feed | `200 OK` |
| Koneksi feed langsung | `101 Switching Protocols`, lalu pesan WebSocket |

Respons `200` tidak membuktikan bahwa bukti sudah lengkap. Baca kolom cakupan,
pemotongan, dan status di respons.

## Filter kueri dan paginasi

Setiap rute baca menerima kunci kuerinya sendiri. Alias praktis
seperti `project`, `trace`, dan `user` bukan kunci kueri. Secara default, rute
daftar mengembalikan array polos, dan mengembalikan envelope kursor dengan
`pagination=cursor`. Daftar deployment selalu mengembalikan objek halaman.
Lihat [Filter kueri](/id/reference/telemetry-api-filters).

## Respons dan error

- [Format respons](/id/reference/telemetry-response-shapes)
  menampilkan satu contoh untuk setiap kelompok respons.
- [Error API](/id/reference/api-errors) mencantumkan kode error dan tindakan
  pemulihan.

Baca `code` sebelum pesan untuk manusia. Gunakan `next_action` untuk perilaku
program dan `next` untuk panduan bagi manusia. Jangan mem-parse kata-kata di
`error` atau `next`.

## Perbarui masalah

Permintaan ini memakai bearer akun. Bearer ini sengaja dibedakan dari
`LOGBREW_INGEST_BEARER`. Akun harus punya izin untuk mengelola masalah di
proyek tempat masalah itu berada. Jika tidak, permintaan gagal dengan `403`
dan `forbidden`. Izin yang sama mencakup perubahan status, prioritas, dan
penanggung jawab, serta aturan masalah dan log.

Setiap permintaan mengisi 1 atau lebih kolom berikut:

| Kolom | Nilai |
| --- | --- |
| `status` | `unresolved`, `resolved`, atau `archived`. `ignored` adalah nama lama untuk `archived`. |
| `priority` | `high`, `medium`, atau `low`. |
| `assignee` | ID pengguna, `me` untuk akun yang sedang masuk, atau `none` untuk menghapus penanggung jawab. |

Permintaan tanpa satu pun kolom ini gagal dengan `422` dan
`validation_failed`.

Masalah punya 0 atau 1 penanggung jawab. Penanggung jawab harus bisa membaca
proyek. Jika tidak, permintaan gagal dengan `422` dan `validation_failed`, dan
LogBrew tidak mengubah apa pun. Ambil daftar akun yang bisa Anda tugaskan dari
[Tampilkan daftar penanggung jawab](#list-assignees). Nilai `assignee` lain
juga gagal dengan `422` dan `validation_failed`.

Prioritas yang Anda tetapkan akan tetap seperti itu. Tanpa prioritas yang Anda
tetapkan, prioritas mengikuti tingkat keparahan masalah: `error` dan
`critical` menjadi `high`, `warning` menjadi `medium`, dan `info` menjadi
`low`.

Kolom yang sudah berisi nilai yang diminta tidak berubah. Anda bisa mengirim
permintaan yang sama lagi setelah timeout. Timeout tidak membuktikan bahwa
perubahan tidak terjadi. Baca masalah lagi sebelum Anda mengirim perubahan
yang berbeda.

### <span id="update-one-issue">Perbarui satu masalah</span>

Tambahkan `response_version=3` agar respons berisi `archived`, prioritas, dan
penanggung jawab:

```bash
curl -X PATCH "$LOGBREW_API_URL/api/telemetry/issues/$ISSUE_ID?response_version=3" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{ "status": "archived", "priority": "low", "assignee": "me" }'
```

Responsnya berupa masalah yang sudah diperbarui. Lihat
[contoh respons status masalah](/id/reference/telemetry-response-shapes#issue-status-response-examples).

### <span id="update-issues-in-bulk">Perbarui masalah secara massal</span>

Kirim `project_id` dan 1 sampai 100 ID masalah yang berbeda dari proyek itu:

```bash
curl -X POST "$LOGBREW_API_URL/api/telemetry/issues/bulk" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{
    "project_id": "<project-uuid>",
    "issue_ids": ["<issue-uuid-1>", "<issue-uuid-2>"],
    "assignee": "<user-uuid>"
  }'
```

Permintaan ini menerapkan perubahan yang sama ke setiap masalah. Respons
berisi `project_id` dan `results`, dengan 1 hasil untuk setiap ID masalah,
sesuai urutan di permintaan. Setiap hasil berisi `issue_id`, `outcome`, dan
`issue`. `issue` adalah masalah terkini dalam versi respons 3, atau `null`
untuk `not_found`.

| `outcome` | Arti |
| --- | --- |
| `updated` | LogBrew menerapkan perubahan. |
| `unchanged` | Masalah sudah berisi nilai yang diminta. |
| `not_found` | Proyek tidak punya masalah dengan ID ini. LogBrew tidak mengubah apa pun untuk ID itu. |

Daftar kosong, lebih dari 100 ID, atau ID yang berulang gagal dengan `422` dan
`validation_failed`. Pecah kumpulan yang lebih besar menjadi beberapa
permintaan. Jika akun tidak bisa membaca proyek, permintaan gagal dengan `404`
dan `not_found`.

### <span id="list-assignees">Tampilkan daftar penanggung jawab</span>

Kirim ID proyek untuk mendapatkan setiap akun yang bisa ditugaskan masalah di
proyek itu:

```bash
curl "$LOGBREW_API_URL/api/telemetry/issues/assignees?project_id=$PROJECT_ID" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Daftar ini berisi setiap akun yang bisa membaca proyek. Setiap entri berisi
`user_id`, `name`, dan `email`. `name` bernilai `null` jika akun tidak punya
nama. Lihat
[respons daftar penanggung jawab](/id/reference/telemetry-response-shapes#assignee-list-response).
Setiap akun yang bisa membaca proyek bisa mengambil daftar ini. Jika akun
tidak bisa membaca proyek, permintaan gagal dengan `404` dan `not_found`.

Saat anggota kehilangan akses ke proyek, masalah yang ditugaskan ke anggota
itu tidak menampilkan penanggung jawab. Jika anggota itu mendapatkan akses
lagi, masalah itu kembali menampilkan anggota tersebut, kecuali seseorang
sudah mengubah atau menghapus penanggung jawabnya sementara itu.

### Tetapkan aturan masalah dan log

Aturan mengubah cara LogBrew menampilkan sinyal yang cocok. Aturan tidak
menghapus data. `severity` yang terekam tetap sama, dan respons menampilkan
aturan di `triage`.

| Permintaan | Body JSON |
| --- | --- |
| `PUT /api/telemetry/issues/{issue_id}/triage-rule` | `{ "severity": "<value>" }` |
| `PUT /api/logs/{log_id}/triage-rule` | `{ "severity": "<value>", "ignored": true }` |

`severity` berisi `info`, `warning`, `error`, `critical`, atau `source`.
`source` menghapus tingkat keparahan pengganti dan kembali menampilkan tingkat
keparahan yang terekam. Untuk aturan log, `ignored: true` menyembunyikan log yang cocok dari
daftar log default. Baca log itu dengan `status=ignored` atau `status=all`.
Aturan berlaku untuk sinyal cocok yang tersimpan dan yang akan datang. Nilai
lain gagal dengan `422` dan `validation_failed`.

<Warning>
  Jangan kirim rilis kosong. LogBrew menolaknya agar pelacakan rilis tetap
  tepercaya.
</Warning>

Trang này đưa ra một ví dụ cho mỗi nhóm phản hồi của
[Telemetry API](/vi/reference/telemetry-api). Mọi giá trị đều là dữ liệu giả lập.
Để xem mã lỗi và cách khắc phục, đọc [Lỗi API](/vi/reference/api-errors).

## Đọc phản hồi

Đọc mọi phản hồi theo thứ tự sau:

1. Đọc trạng thái HTTP.
2. Kiểm tra body có đúng cấu trúc mà route quy định.
3. Kiểm tra mỗi `project_id` nằm trong phạm vi dự án đã yêu cầu.
4. Giữ nguyên các giá trị enum chuẩn và các định danh.
5. Chỉ làm theo `next_action` khi client hỗ trợ `code` và `target` của nó.
6. Coi `null`, trường bị lược bỏ và danh sách trống là ba trạng thái khác nhau.

Phản hồi `200 OK` có thể chứa danh sách trống. Danh sách log trống nghĩa là
không có log nào khớp với yêu cầu. Điều đó không có nghĩa là vấn đề, trace hay
hành động cũng trống. Không ghép các tín hiệu chỉ vì dấu thời gian của chúng
gần nhau. Chỉ chuyển sang một trace khi phản hồi chứa đúng `trace_id` của trace
đó.

`404` và danh sách trống là hai kết quả khác nhau. Route danh sách trả về `[]`
khi không có bản ghi nào khớp. Route chi tiết trả về `404` với `code: not_found`
khi không tìm thấy bản ghi nào đọc được. Cả hai kết quả đều không chứng minh
rằng việc gửi dữ liệu đã thất bại.

## Cần gửi gì

Phản hồi chỉ hữu ích khi telemetry bạn gửi đủ tốt. Gửi các giá trị sau trong
mọi envelope hoặc khi thiết lập SDK:

- `release` và `environment`.
- Tên ổn định cho dịch vụ, hành động và chỉ số.
- Ngữ cảnh trace khi log, span, hành động và vấn đề thuộc cùng một yêu cầu.
- Các giá trị mức độ nghiêm trọng chuẩn: `info`, `warning`, `error` và
  `critical`.
- Các thuộc tính giúp gỡ lỗi, không chứa thông tin bí mật hay dữ liệu cá nhân không cần
  thiết.

Xem [Tích hợp SDK](/vi/guides/sdk-ingestion) và
[Kiểm soát dữ liệu ghi nhận](/vi/guides/safe-capture).

## Phản hồi khi gửi dữ liệu

Các SDK công khai tự đọc phản hồi của `POST /v1/events`. Mã ứng dụng không cần
xử lý phản hồi này.

### Phản hồi batch của SDK

Một batch SDK thành công trả về `200 OK` cùng số lượng được chấp nhận cho từng
luồng:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Trường | Ý nghĩa |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Các sự kiện trong batch này mà LogBrew đã chấp nhận. |
| `already_accepted` | Các sự kiện có ID mà LogBrew đã chấp nhận trước đó. LogBrew không lưu lại chúng lần nữa. |
| `context_updated` | `true` khi batch đã cập nhật ngữ cảnh bản phát hành hoặc môi trường. |

Các số lượng chỉ tính cho batch này. Khi gửi lại một batch mà LogBrew đã chấp
nhận, phản hồi trả về `0` cho từng luồng và số sự kiện trong
`already_accepted`. Giữ nguyên ID sự kiện gốc khi thử lại.

### Phản hồi envelope gốc

`POST /api/telemetry/ingest` trả về `200 OK` cùng số mục được chấp nhận cho
từng luồng:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

Phản hồi gốc không có trường `metrics` hay `context_updated`. Không tự thêm
các trường này. `already_accepted` đếm các mục có `id` mà LogBrew đã chấp nhận
trước đó cho dự án. Xem [Gửi trực tiếp envelope gốc](/vi/guides/sdk-ingestion#required-envelope-fields).

### Lỗi khi gửi dữ liệu

`401` với `code: ingest_key_invalid` nghĩa là bearer token gửi dữ liệu đã bị
thu hồi, đã hết hạn hoặc không hợp lệ cho dự án. Với `POST /v1/events`, yêu cầu
thiếu bearer token hoặc dùng bearer token không phải khóa gửi dữ liệu sẽ nhận
`401` với `code: unauthorized`. Dùng bearer token gửi dữ liệu hiện tại thuộc
phạm vi dự án. Không thử lại bằng bearer token của tài khoản.

Một batch SDK bị từ chối trả về `422` với `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Các giá trị `error` khác gồm `SDK event batch requires at least one event` và
`SDK event type is not supported by this ingest route`. Kiểm tra phiên bản SDK
và cấu hình truyền tải. Không gửi batch trống. Không đổi loại sự kiện hay ID
chỉ để batch vượt qua bước kiểm tra hợp lệ.

Yêu cầu dùng phương thức khác `POST` trả về `405` với
`code: method_not_allowed`. Body JSON không đọc được trả về `code: invalid_json`.

## Định dạng phản hồi danh sách telemetry

Theo mặc định, route danh sách trả về một mảng JSON trần. Danh sách trống
thành công là `[]`.

Với `pagination=cursor`, route trả về một envelope. Khóa collection khớp với
loại tín hiệu:

| Route | Khóa collection |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, kèm `issue_id` ở cấp cao nhất |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, kèm `naming_quality` ở cấp cao nhất |

`next_cursor` là một object chứa các trường để đọc tiếp, hoặc `null` ở trang
cuối. Các dòng được sắp xếp từ mới nhất đến cũ nhất. Xem [phân trang bằng cursor](/vi/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Phản hồi log</span>

Một trang cursor của log với `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Log có `level` để tương thích và `severity` để hiển thị. Cả hai đều chứa giá trị
chuẩn. `triage` chứa kết quả của quy tắc mức độ nghiêm trọng. Xem
[phản hồi quy tắc mức độ nghiêm trọng](#severity-rule-responses).

`trace_id` và `span_id` là `null` khi log không có liên kết trace. Khi đó,
`next_action` là `inspect_related_logs` với target `telemetry_logs`. Log, vấn đề
và hành động dùng chung 2 cặp `next_action` này.

`GET /api/logs/{log_id}` trả về một log với cùng cấu trúc.

### <span id="issue-response">Phản hồi vấn đề</span>

`GET /api/telemetry/issues/{issue_id}` trả về một vấn đề đã gộp nhóm. Route danh
sách trả về các object giống hệt. Ví dụ này dùng phiên bản phản hồi mặc định 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

Ở phiên bản 1, `status` là `unresolved`, `resolved` hoặc `ignored`. Với vấn đề
đã lưu trữ, `triage.ignored` là `true`. Về các cặp `next_action` và các lượt
đọc tiếp theo, xem
[Điều tra một vấn đề](/vi/guides/investigate-an-issue).

`first_seen_at` và `last_seen_at` là thời điểm của lần xảy ra đầu tiên và gần
nhất. Hai giá trị này không đổi khi trạng thái thay đổi.

Một số trường chỉ xuất hiện khi LogBrew có dữ liệu:

| Trường | Khi nào xuất hiện |
| --- | --- |
| `span_id` | Vấn đề có liên kết span. Nếu không, trường này bị lược bỏ. |
| `diagnostics` | Lần xảy ra gần nhất có loại ngoại lệ hoặc breadcrumb. Xem [lịch sử lần xảy ra của vấn đề](#issue-occurrence-history). |
| `symbolication` | Chỉ có ở `GET /api/telemetry/issues/{issue_id}`, khi vấn đề có định danh artifact (tệp bản dựng) của bản phát hành. Xem [Source map JavaScript](/vi/guides/source-maps). |

`symbolication.status` là `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` hoặc `unavailable`. Route danh
sách, thao tác đổi trạng thái và thao tác đổi quy tắc không trả về
`symbolication`.

Với `response_version=2`, vấn đề có cùng các trường, kèm các thay đổi sau:

| Trường | Giá trị ở phiên bản 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` hoặc `archived`. Phiên bản 1 hiển thị `archived` thành `ignored`. |
| `priority` | `high`, `medium` hoặc `low`. |
| `priority_source` | `manual` khi một người đã đặt mức ưu tiên. `derived` khi mức ưu tiên theo mức độ nghiêm trọng hiệu lực. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Ví dụ này chỉ hiển thị một số trường. Mức ưu tiên suy ra là `high` cho `error`
và `critical`, `medium` cho `warning`, và `low` cho `info`. Mức ưu tiên này dựa
trên `triage.effective_severity`, nên quy tắc mức độ nghiêm trọng của vấn đề có
thể thay đổi nó.

Với `response_version=3`, vấn đề có mọi trường của phiên bản 2 và thêm
`assignee`. `assignee` là `null` khi vấn đề chưa có người phụ trách:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Trường | Ý nghĩa |
| --- | --- |
| `assignee.user_id` | ID người dùng của người phụ trách. Gửi giá trị này làm `assignee` trong bộ lọc hoặc thao tác thay đổi. |
| `assignee.name` | Tên người phụ trách, hoặc `null` khi tài khoản chưa có tên. |
| `assignee.email` | Địa chỉ email của người phụ trách. |

Vấn đề không hiển thị người phụ trách khi thành viên được giao không còn đọc
được dự án.

Với `response_version=4`, `assignee` có thêm `type`. Người phụ trách `user` có
`user_id`, `name` và `email`, giống phiên bản 3. Người phụ trách `team` có
`team_id`, `slug` và `name`. Phiên bản 3 hiển thị nhóm phụ trách là `null`.
CLI yêu cầu phiên bản 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Mọi `response_version` khác trả về `422` với `code: validation_failed`. Một
trang cursor dùng cùng phiên bản cho mọi vấn đề trong `issues`.

### <span id="assignee-list-response">Phản hồi danh sách người phụ trách</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` trả về mọi tài
khoản có thể được giao vấn đề trong dự án:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Thêm `response_version=2` để nhận thêm `teams`: mọi nhóm trong tổ chức của dự
án, kèm `team_id`, `slug` và `name`.

Nếu tài khoản không đọc được dự án, route trả về `404` với
`code: not_found`.

### <span id="action-response">Phản hồi hành động</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` theo dõi một đối tượng thực hiện hoặc một phiên. Coi `distinct_id`
và `session_id` là ID opaque (không diễn giải nội dung). `session_id` và
`trace_id` là `null` khi chưa ghi nhận. `span_id` bị lược bỏ khi chưa ghi nhận.
Hành động không có mức độ nghiêm trọng. Xem [Ghi nhận sự kiện sản phẩm](/vi/guides/product-events).

### Phản hồi chỉ số

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Mỗi mục là một mẫu. Không dùng số mẫu làm số sự kiện hay số người dùng.
`unit`, `temporality`, `trace_id` và `span_id` là `null` khi chưa ghi nhận.
Giá trị `null` không phải là 0.

### Phản hồi bản phát hành

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Mỗi dòng ứng với một dự án, bản phát hành, môi trường và dịch vụ. Các số lượng
của dòng chỉ mô tả riêng dòng đó.

`trace_health.status` là `unknown` khi dòng không có trace, hoặc là
`no_errors_observed` hay `errors_observed`. `error_rate_basis_points` là tỷ lệ
trace có span lỗi, từ `0` đến `10000`. Đây không phải tỷ lệ lỗi của mọi yêu
cầu.

`next_action` trỏ đến loại tín hiệu đầu tiên có dữ liệu, theo thứ tự sau:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Xem [Bản phát hành](/vi/concepts/releases).

### Phản hồi khám phá trace

`GET /api/telemetry/traces?pagination=cursor` trả về một dòng cho mỗi trace,
kèm biên nhận `naming_quality` cho trang được trả về:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` chỉ áp dụng cho trang được trả về. Đây không phải điểm số cho
toàn tài khoản. `truncated: true` nghĩa là còn trang khác. Khi trang có tên
chung chung, route không khớp hoặc thao tác chung chung, `next_action` là
`improve_trace_naming` với target `sdk_configuration`. Nếu không có
`pagination=cursor`, route trả về một mảng trace trần và không có
`naming_quality`.

`next_cursor` chứa `time` và `trace_id`. Gửi chúng dưới dạng `cursor_time` và
`cursor_trace_id`.

Với `response_version=2`, mỗi trace còn có `capture_span_count` và
`capture_error_count`. Khi đó `span_count` và `error_span_count` không đếm
[span ghi nhận](/vi/concepts/distributed-tracing#capture-spans). Phiên bản 1 có
đếm chúng. `status=error` khớp với một trace khi `error_span_count` hoặc
`capture_error_count` lớn hơn `0`.

`GET /api/telemetry/traces/{trace_id}` trả về các span của một trace.
`GET /api/telemetry/traces/{trace_id}/summary` trả về span gốc, các span lỗi,
dịch vụ, thời lượng và đường đi chậm nhất, không kèm thuộc tính thô của span.
`404` ở bản tóm tắt nghĩa là không có trace nào khớp với toàn bộ phạm vi. Không
bỏ bộ lọc để thử lại. Xem [phản hồi span và bản tóm tắt trace](#trace-spans-and-summary-responses).

### Danh sách trống và bản ghi không tồn tại

Lượt đọc danh sách có thể không có kết quả khớp. Lượt đọc chi tiết tuân theo quy
ước khác:

| Yêu cầu | Thành công | Không có bản ghi đọc được |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` với một [log](#log-response) | `404` với `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` với một [vấn đề](#issue-response) | `404` với `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` với các lần xảy ra | `404` với `code: not_found` ở trang đầu tiên |
| `GET /api/telemetry/traces/{trace_id}` | `200` với các span | `200` với `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` với một bản tóm tắt | `404` với `code: not_found` |

Log không tồn tại trả về `404` sau:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Vấn đề không tồn tại dùng `"error": "issue not found"`. Bản tóm tắt trace không
tồn tại dùng `"error": "trace not found"`. ID không xác định và ID mà tài khoản
không đọc được đều trả về cùng một phản hồi.

Danh sách với một `project_id` mà tài khoản không đọc được trả về `404` với
`"error": "project selection not found"`. ID dự án không xác định trả về cùng
phản hồi. Xem [lựa chọn dự án bị từ chối](#rejected-project-selections).

### <span id="rejected-project-selections">Lựa chọn dự án bị từ chối</span>

Danh sách log, vấn đề, hành động, chỉ số, bản phát hành và trace nhận một dự án
qua `project_id`, hoặc từ 2 đến 50 dự án qua `project_ids`. Danh mục thuộc tính
log nhận cùng các tham số chọn này. Lịch sử lần xảy ra của vấn đề không nhận
chúng.

Yêu cầu có cả `project_id` lẫn `project_ids` trả về `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` có UUID không hợp lệ, có ID lặp lại, hoặc có ít hơn 2 hay nhiều
hơn 50 ID cũng trả về `422` với `code: validation_failed`.

Nếu tài khoản không đọc được dự án của `project_id` hoặc một dự án trong tập
`project_ids`, toàn bộ yêu cầu trả về `404`. Yêu cầu không trả về các dự án còn lại thành kết quả một phần:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Hiển thị lỗi, không hiển thị danh sách trống hay số đếm bằng 0. Đọc lại danh
sách dự án. Không âm thầm bỏ một dự án, và không thử lại trên tất cả dự án.
Thông tin xác thực được ủy quyền, chẳng hạn một kết nối MCP, trả về `403` với
`code: forbidden` cho dự án nằm ngoài phạm vi kết nối đó. Xem
[phạm vi dự án](/vi/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Lỗi cursor</span>

Log, vấn đề, hành động, chỉ số và lần xảy ra của vấn đề dùng `cursor_time` và
`cursor_id`. Cursor bị từ chối trả về `422` với `code: validation_failed`.
Các lỗi này không có nghĩa là danh sách trống.

| Yêu cầu | `error` |
| --- | --- |
| `pagination=cursor` chỉ kèm 1 trong 2 trường cursor | `cursor_time and cursor_id must be sent together` |
| `cursor_time` không phải dấu thời gian RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Có trường cursor nhưng thiếu `pagination=cursor`, hoặc `pagination` có giá trị khác | `pagination must be cursor when cursor pagination is requested` |

Ví dụ:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Sao chép toàn bộ `next_cursor` từ trang trước. Không thay `cursor_time` bằng
thời gian hiện tại. Nếu bạn làm mất cursor, bắt đầu lại với
`pagination=cursor` và các bộ lọc ban đầu. Tham số truy vấn không xác định hoặc giá
trị sai kiểu trả về `422` với `"error": "invalid query parameters"`.

### Phản hồi cursor của bản phát hành

Cursor của bản phát hành có 5 trường. Yêu cầu thành công nhưng không có kết quả
khớp trả về `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Khi `next_cursor` khác `null`, gửi đủ 5 giá trị trong yêu cầu tiếp theo:

| Trường `next_cursor` | Tham số truy vấn |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` đánh dấu một vị trí. Tham số này không thay thế `project_id`
hay `project_ids`. Giữ nguyên các tham số dự án và bộ lọc ban đầu. Mã hóa URL
(URL-encode) từng giá trị.

Với `pagination=cursor`, cursor thiếu trường hoặc giá trị bản phát hành, môi
trường hay dịch vụ để trống sẽ trả về `422` với
`"error": "all release cursor fields must be sent together"`. `cursor_time`
không hợp lệ và thiếu `pagination=cursor` trả về cùng lỗi như
[các cursor khác](#cursor-errors).

### Lỗi khám phá trace

Các lỗi này áp dụng cho `GET /api/telemetry/traces`. Mỗi lỗi trả về `422` với
`code: validation_failed`. Yêu cầu bị từ chối không phải là kết quả trống.

| Yêu cầu | `error` |
| --- | --- |
| `status` khác `error` hoặc `ok` | `trace status must be error or ok` |
| `min_duration_ms` nhỏ hơn `0` | `minimum trace duration must not be negative` |
| Chỉ có 1 trường cursor, hoặc `cursor_trace_id` để trống | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` không phải dấu thời gian RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Có trường cursor nhưng thiếu `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |
| `response_version` khác `1` hoặc `2` | `trace response_version must be 1 or 2` |

Để lấy cả hai trạng thái trace, bỏ `status`. Với trang tiếp theo, sao chép
`next_cursor.time` vào `cursor_time` và `next_cursor.trace_id` vào
`cursor_trace_id`. Không gửi `cursor_id` cho trang trace. Xem
[bộ lọc trace](/vi/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Lịch sử lần xảy ra của vấn đề</span>

`GET /api/telemetry/issues/{issue_id}/events` đọc các lần xảy ra của một vấn đề
đã gộp nhóm. Dùng bearer token của tài khoản và ID của vấn đề đã gộp nhóm. Route
chỉ nhận `pagination`, `cursor_time`, `cursor_id` và `limit`. Route không nhận bộ lọc dự
án, thời gian, bản phát hành, môi trường hay mức độ nghiêm trọng.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Trang đầu tiên với một lần xảy ra và cursor để đọc tiếp:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },

    }

  "next_cursor": {

    "id": "db619770-1f7c-4bd5-8310-9f171df8af47"
  }

```

| Trường | Ý nghĩa |
| --- | --- |
| `issue_id` | Vấn đề đã gộp nhóm chứa lần xảy ra này. |
| `events[].id` | ID của một lần xảy ra. Dùng ID này để [chọn lần xảy ra đó](/vi/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | Thời điểm lần xảy ra đó diễn ra trong ứng dụng. |
| `events[].severity` | Mức độ nghiêm trọng đã ghi nhận của lần xảy ra đó. Quy tắc mức độ nghiêm trọng không thay đổi giá trị này. |
| `events[].release`, `environment`, `service_name` | Ngữ cảnh được ghi nhận cùng lần xảy ra đó. |

Một lần xảy ra có thể cũ hơn `last_seen_at` của nhóm. Không thay bản phát hành
hay trace của lần xảy ra bằng giá trị từ vấn đề đã gộp nhóm. Danh sách không trả về
trạng thái, triage (xem xét và xếp thứ tự xử lý), mức ưu tiên hay số lần xảy
ra.

`diagnostics.schema_version` là phiên bản của object chẩn đoán. Phản hồi bỏ
`diagnostics` và `span_id` khi lần xảy ra không có dữ liệu đó. Bên trong
`diagnostics`, phản hồi bỏ `exception` chưa ghi nhận và `breadcrumbs` trống.
Nếu `breadcrumbs_truncated` là `true`, một phần lịch sử breadcrumb không có
trong phản hồi.

`stack_trace` và `trace_id` là `null` khi chưa ghi nhận. Thiếu trace ID không
chứng minh rằng ứng dụng không gửi trace. Coi thông điệp và thuộc tính đã ghi
nhận là dữ liệu, không phải chỉ dẫn.

Các lần xảy ra được sắp xếp từ mới nhất đến cũ nhất. Với trang tiếp theo, gửi
cùng ID vấn đề, `pagination=cursor`, `limit`, cùng các giá trị `cursor_time` và
`cursor_id` từ `next_cursor`. ID trong cursor là ID của lần xảy ra, không phải
ID của vấn đề.

Trang đầu tiên trả về `404` với `code: not_found` khi vấn đề không có lần xảy
ra nào đọc được. Trang sau có thể là trang cuối trống:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Không dùng lại cursor cho vấn đề khác. [Lỗi cursor](#cursor-errors) cũng áp
dụng cho route này.

```json
      "parent_span_id": "b37ac82563149fed",
      "name": "POST /v1/charges",
      "operation": "http.client",
      "status": "error",
      "started_at": "2026-06-01T12:00:00.100Z",
      "duration_ms": 640,
      "service_name": "checkout-api"
    }
  ],
  "services": [
    {
      "service_name": "checkout-api",
      "span_count": 2,
      "error_span_count": 2,
      "max_duration_ms": 823
    }
  ],
  "releases": ["api@1.2.3"],
  "environments": ["production"]
}
```

| Trường | Ý nghĩa |
| --- | --- |
| `duration_ms` | Thời gian từ lúc span sớm nhất bắt đầu đến lúc span muộn nhất kết thúc. Đây không phải tổng thời lượng các span. |
| `root_span` | Span sớm nhất có span cha không nằm trong trace. Đây là điểm bắt đầu, không phải nguyên nhân đã được chứng minh. |
| `slowest_child_span` | Span dài nhất có ID của span cha, hoặc `null`. |
| `slowest_path` | Chuỗi span cha đã biết, từ span gốc đến `slowest_child_span`. Giá trị là `[]` khi `slowest_child_span` là `null`. |
| `error_spans` | Các span lỗi dài nhất, tối đa 5. `error_span_count` có thể lớn hơn. |

Cả hai route đều không trả về cursor hay trường báo bị cắt bớt. Không tự thêm
giá trị `truncated` mà phản hồi không có.

### Không có span khớp

Khi không có span nào khớp với trace ID và phạm vi, danh sách span trả về `200`
với `[]`. Bản tóm tắt trả về `404` với `"error": "trace not found"` và
`code: not_found`. Kiểm tra trace ID và phạm vi. Không bỏ bộ lọc chỉ để có kết
quả. Cả hai kết quả đều không chứng minh rằng ứng dụng không gửi telemetry.

## <span id="live-event-response-format">Định dạng phản hồi sự kiện trực tiếp</span>

Luồng trực tiếp gửi các sự kiện mới. Luồng không phát lại các sự kiện mà client
đã bỏ lỡ khi mất kết nối. Dùng các route danh sách để đọc bản ghi đã có.

### Tạo ticket

Gửi `POST /api/feed/ticket` với bearer token của tài khoản. Yêu cầu không có body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Phản hồi `200 OK` chứa ticket trong trường `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Ticket là thông tin xác thực ngắn hạn. Không ghi ticket vào log và không đưa nó
vào prompt của agent. Mở kết nối trước khi hết `expires_in_seconds`. Thời hạn
này chỉ giới hạn thời điểm bắt đầu kết nối, không giới hạn thời gian kết nối
được giữ.

`401` nghĩa là phiên đăng nhập tài khoản không hợp lệ. Đăng nhập lại trước khi
yêu cầu ticket. Phương thức khác `POST` trả về `405` với
`code: method_not_allowed`.

### Mở kết nối

Kết nối một WebSocket client tới
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Mã hóa URL cho
ticket. Không đặt bearer token của tài khoản hay bearer token gửi dữ liệu vào URL.
`401` nghĩa là ticket hoặc phiên đăng nhập tài khoản không hợp lệ. Tạo ticket
mới sau khi đăng nhập lại.

| Phản hồi | Nguyên nhân | Bước tiếp theo |
| --- | --- | --- |
| `422` với `"error": "feed ticket is required"` | Giá trị truy vấn `ticket` bị thiếu hoặc để trống. | Tạo ticket và kết nối bằng ticket đó. |
| `401` với `code: unauthorized` | Ticket đã hết hạn hoặc không hợp lệ. | Tạo ticket mới. Không thử lại với cùng ticket. |
| `code: invalid_websocket_upgrade` | Yêu cầu không phải là yêu cầu nâng cấp WebSocket hợp lệ. | Dùng WebSocket client. |
| `405` với `code: method_not_allowed` | Yêu cầu không dùng `GET`. | Dùng `GET` cho kết nối. |

Chờ một lúc trước khi kết nối lại sau lỗi. Không kết nối lại trong vòng lặp
không có thời gian chờ.

### Đọc các thông điệp

Mỗi thông điệp là một envelope `{ "type": "...", "data": ... }`. Đọc `type`
trước khi phân tích cú pháp `data`. Bỏ qua các loại mà client không hỗ trợ.

| Loại sự kiện | Dữ liệu |
| --- | --- |
| `native_log` | Dữ liệu log, theo cấu trúc [phản hồi log](#log-response). |
| `native_issue` | Dữ liệu vấn đề đã gộp nhóm, theo cấu trúc [phản hồi vấn đề](#issue-response) phiên bản 1. |
| `native_trace_span` | Một span, theo cấu trúc của một mục trong [danh sách span](#span-list). |
| `native_action` | Dữ liệu hành động sản phẩm, theo cấu trúc [phản hồi hành động](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Dữ liệu dự án. Đọc lại danh sách dự án khi dữ liệu này thay đổi. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Mức sử dụng của tài khoản, theo cấu trúc [mức sử dụng của tài khoản](/vi/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Sự kiện `native_issue` dùng phản hồi vấn đề phiên bản 1: vấn đề đã lưu trữ hiển
thị là `ignored`, và sự kiện không có mức ưu tiên. Chỉ số và bản phát hành không
phải là loại sự kiện trực tiếp. Đọc chúng bằng route danh sách tương ứng. Ticket
không chọn dự án. Kiểm tra `project_id` của từng sự kiện trước khi hiển thị
trong giao diện của một dự án. `logbrew watch --json` dùng luồng này. Xem
[Tham khảo CLI](/vi/reference/cli).

### Xử lý kết nối bị đóng

| Mã đóng | Lý do | Bước tiếp theo |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Chờ, rồi kết nối lại bằng ticket mới. Đọc lại các route danh sách để lấy các bản ghi đã bỏ lỡ. |
| `1008` | `live feed access changed; sign in again` | Ngừng kết nối lại. Đăng nhập lại trước khi tạo ticket mới. |

Các lần mất kết nối khác có thể không kèm lý do từ LogBrew. Sau khi kết nối lại,
đọc lại các route danh sách và đối chiếu bản ghi theo ID.

## <span id="issue-status-response-examples">Ví dụ phản hồi khi đổi trạng thái vấn đề</span>

`PATCH /api/telemetry/issues/{issue_id}` với `{ "status": "resolved" }`
trả về `200 OK` cùng vấn đề đã gộp nhóm sau khi cập nhật, theo cùng cấu trúc với
[phản hồi vấn đề](#issue-response). Tham số truy vấn `response_version` chọn
phiên bản. Phản hồi không trả về cờ thành công.

Body đặt 1 hoặc nhiều trường trong số `status`, `priority` và `assignee`.
`status` nhận `unresolved`, `resolved` hoặc `archived`. `ignored` là tên cũ của
`archived`. Xem [Cập nhật một vấn đề](/vi/reference/telemetry-api#update-one-issue).

Kiểm tra `id`, `status` và `priority` được trả về trước khi báo thành công.
Không dựng kết quả từ các giá trị đã gửi. Đổi trạng thái không xóa các lần xảy
ra và không thay đổi `first_seen_at` hay `last_seen_at`. Thao tác này cũng
không thay đổi `severity` hay quy tắc mức độ nghiêm trọng.

Thay đổi bị từ chối trả về `422` với `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Kết quả | Nguyên nhân |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Body không có trường nào trong 3 trường này. |
| `422`, `issue priority must be high, medium, or low` | Giá trị mức ưu tiên không được hỗ trợ. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | Giá trị người phụ trách không được hỗ trợ. |
| `422`, `issue assignee cannot read this project` | Người phụ trách không có quyền truy cập dự án. LogBrew không thay đổi gì. |
| `422`, `issue assignee team is not a team of this project's organization` | Nhóm không thuộc tổ chức của dự án. LogBrew không thay đổi gì. |
| `403` với `code: forbidden` | Tài khoản không có quyền quản lý vấn đề trong dự án. |
| `404` với `code: not_found` | Tài khoản không đọc được vấn đề, hoặc vấn đề không tồn tại. |

Trường đã có giá trị được yêu cầu sẽ không thay đổi. Sau khi hết thời gian chờ
hoặc mất phản hồi, gửi lại đúng yêu cầu đó, hoặc đọc vấn đề trước. Không gửi một
thay đổi khác trước khi đọc trạng thái hiện tại. Xem
[Thao tác ghi](/vi/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` trả về `200 OK` với 1 kết quả cho mỗi ID vấn
đề được yêu cầu, theo thứ tự trong yêu cầu. Mỗi vấn đề tìm thấy dùng cấu trúc
phiên bản 3. Thêm `"response_version": 2` vào body để nhận mỗi vấn đề theo cấu trúc
phiên bản 4. Kết quả `not_found` có `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

Ví dụ này chỉ hiển thị một số trường của vấn đề. `outcome` là `updated`,
`unchanged` hoặc `not_found`. Yêu cầu gửi lại trả về `unchanged` và không thay
đổi gì. Xem
[Cập nhật hàng loạt vấn đề](/vi/reference/telemetry-api#update-issues-in-bulk).

Yêu cầu hàng loạt thất bại toàn bộ trong các trường hợp sau:

| Kết quả | Nguyên nhân |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | Danh sách trống hoặc có hơn 100 ID. |
| `422`, `issue_ids must not contain duplicates` | Một ID xuất hiện nhiều hơn một lần. |
| `422` với `code: invalid_json` | Body có trường không xác định. |
| `403` với `code: forbidden` | Tài khoản không có quyền quản lý vấn đề trong dự án. |
| `404`, `project not found` | Tài khoản không đọc được dự án. |

## Phạm vi yêu cầu phân tích

Các route phân tích, route chuỗi chỉ số và route lượng tín hiệu đọc một dự án
trong một khoảng thời gian. Mọi yêu cầu đều cần `project_id` và `since`.
`since` nhận một thời lượng rút gọn như `24h` hoặc `7d`, hoặc một dấu thời gian
RFC3339. `until` nhận một dấu thời gian RFC3339 và mặc định là thời điểm gửi
yêu cầu. Khoảng thời gian bao gồm `since`, không bao gồm `until` và không được
vượt quá 31 ngày.

`service_name`, `release` và `environment` là các bộ lọc khớp chính xác, không
bắt buộc. Mỗi giá trị phải có từ 1 đến 256 ký tự sau khi LogBrew cắt khoảng
trắng. Route so sánh phân khúc đặt các bộ lọc này bên trong từng phân khúc,
không đặt ở cấp cao nhất.

Nếu tài khoản không đọc được dự án, các route này trả về `200 OK` với số đếm
bằng 0. Chúng không trả về `404`. Kết quả trống không xác nhận quyền truy cập
dự án. So sánh `project_id` với các dự án mà tài khoản đọc được. Yêu cầu qua một
kết nối MCP không bao gồm dự án trả về `403` và `forbidden`.

| Route | Giá trị `response_version` | Mặc định |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` hoặc `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` hoặc `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` hoặc `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` hoặc `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` hoặc `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Không nhận | Schema `1` |
| `POST /api/telemetry/analytics/paths` | Không nhận | Schema `1` |
| `GET /api/telemetry/metrics/series` | Không nhận | Schema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Mỗi phản hồi bắt đầu bằng `schema_version`, `query` và `purpose`. `query`
lặp lại phạm vi có hiệu lực. Trường này bỏ các bộ lọc mà bạn không gửi.
`purpose` là văn bản thuần giải thích route trả lời câu hỏi gì.

Một tỷ lệ bị lược bỏ khi mẫu số của nó bằng 0. Tỷ lệ bị lược bỏ không phải là `0`
và cũng không phải là `null`. Đọc `coverage` trước khi tin vào một tỷ lệ.

### <span id="shared-scope-errors">Lỗi phạm vi dùng chung</span>

Các lỗi này dùng HTTP `422` và `validation_failed`:

| Nguyên nhân | `error` |
| --- | --- |
| Thiếu `project_id` | `product analytics project_id is required` |
| Thiếu `since` | `product analytics since is required` |
| `since` không phải thời lượng hay dấu thời gian RFC3339 | `invalid since value` |
| `until` không phải dấu thời gian RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` không sớm hơn `until` | `product analytics since must be earlier than until` |
| Khoảng thời gian dài hơn 31 ngày | `product analytics range must not exceed 31 days` |
| Bộ lọc trống, hoặc bộ lọc dài hơn 256 ký tự | `product analytics context filters must be non-empty and at most 256 characters` |

Ví dụ, yêu cầu thiếu `project_id` trả về:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Route chuỗi chỉ số và route lượng tín hiệu dùng cùng quy tắc phạm vi, với văn
bản `error` riêng. Các mục bên dưới của từng route liệt kê những lỗi đó.

Tham số truy vấn không xác định trả về `422` với phản hồi
[tham số truy vấn không hợp lệ](/vi/reference/api-errors#invalid-query-parameters).
Trường JSON không xác định, thiếu trường JSON bắt buộc hoặc giá trị enum không
được hỗ trợ trả về `invalid_json`. Xem
[JSON không hợp lệ](/vi/reference/api-errors#invalid-json). Yêu cầu dùng sai
phương thức HTTP trả về `405` và `method_not_allowed`. Văn bản `next` của phản
hồi nêu phương thức và các trường được hỗ trợ. Xem
[Phương thức không được hỗ trợ](/vi/reference/api-errors#unsupported-method).

## Phản hồi tổng quan phân tích sản phẩm

`GET /api/telemetry/analytics/overview` cho thấy hoạt động trong một dự án:
lượng hành động, người dùng, phiên, một chuỗi thời gian, các hành động hàng đầu,
cùng các lượt xem trang, lượt xem màn hình và tương tác đã phân loại. Dùng route
này để tìm tên sự kiện chính xác cho các route phân tích khác.

Gửi `response_version=3`. Phiên bản 1 và 2 trả về cùng số đếm, nhưng giá trị
`estimation.method` của chúng là chuỗi giá trị cũ. Phiên bản 1 không kiểm tra loại chủ
thể khi đếm người dùng đã định danh. Phiên bản 2 và 3 chỉ đếm chủ thể loại
`user`, và thêm số đếm chủ thể ẩn danh cùng `subject_coverage`.

Yêu cầu này đọc một giờ, chia thành các khoảng gộp năm phút, và trả về hai dòng
trong mỗi danh sách hàng đầu:

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/overview" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T11:00:00Z" \
  --data-urlencode "until=2026-06-01T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "top_limit=2" \
  --data-urlencode "response_version=3"
```

### Tổng quan thành công

Trong kết quả giả lập này, dự án có 120 hành động nằm trong hai trên mười hai
khoảng gộp. Hai mươi hành động đến từ chủ thể ẩn danh. Mọi hành động đều có ID

### Đọc tổng quan

Năm số đếm trong `subject_coverage` cộng lại bằng tổng số sự kiện của phần
tương ứng. Chỉ `identified_user_events` được tính vào người dùng.
`anonymous_actions` bằng `summary.actions` trừ `identified_actions`.

`series` chỉ chứa các khoảng gộp có hoạt động. `expected_buckets` là số khoảng
gộp có thể có trong khoảng thời gian. Không vẽ khoảng gộp bị thiếu thành giá trị
0 đo được, trừ khi biểu đồ của bạn ghi rõ quy tắc đó. Các khoảng gộp được căn
theo ranh giới thời gian UTC. Khoảng thời gian bắt đầu giữa một khoảng gộp sẽ
bao gồm phần khoảng gộp chưa đầy đủ đó.

`classified_activity` đếm lượt xem trang, lượt xem màn hình và tương tác. Lượt
xem màn hình và tương tác cũng là hành động. Lượt xem trang thì không. Không
cộng `summary.actions` với `classified_activity.summary.events`.

Sao chép `kind` và `event_name` từ `classified_activity.top_events` vào các bước
phễu, tham số chọn tỷ lệ quay lại, tham số chọn vòng đời, điểm neo đường dẫn và
mục tiêu của phân khúc. Giá trị `true` trong `top_events_truncated` nghĩa là còn
các tên có lượng thấp hơn. Tăng `top_limit` tối đa đến 20 để xem thêm.

`analysis_level` là `no_data`, `event_only`, `user_level` hoặc
`user_and_session`. Nếu dự án không có hành động và không có sự kiện đã phân
loại, `next_action.code` là `capture_product_activity`. Xem
[Phân tích sản phẩm](/vi/concepts/product-analytics#use-the-analytics-api).

### <span id="overview-errors">Lỗi tổng quan</span>

Ngoài [lỗi phạm vi dùng chung](#shared-scope-errors), route tổng quan trả về
`422` và `validation_failed` cho các giá trị sau:

| Giá trị | `error` |
| --- | --- |
| `response_version` khác `1`, `2` hoặc `3` | `product analytics response_version must be 1, 2, or 3` |
| `top_limit` nằm ngoài `1` đến `20` | `product analytics top_limit must be between 1 and 20` |
| `interval` khác `auto`, `1m`, `5m`, `15m`, `1h`, `6h` hoặc `1d` | `product analytics interval is not supported` |
| `interval` chỉ định rõ nhưng cần hơn 500 khoảng gộp | `product analytics interval would exceed 500 buckets` |

`interval` mặc định là `auto`. Giá trị này chọn độ dài khoảng gộp nhỏ nhất cần
tối đa 300 khoảng gộp. `top_limit` mặc định là `10`.

## <span id="ordered-funnel-response">Phản hồi phễu theo thứ tự</span>

`POST /api/telemetry/analytics/funnel` đo mức hoàn thành theo thứ tự qua 2 đến
8 bước. Sao chép chính xác từng `kind` và `event_name` từ
`classified_activity.top_events` trong tổng quan. Tên hành động tương tự không
được tính là khớp. Body yêu cầu này đếm các phiên xem `/pricing` rồi hoàn tất
đăng ký trong vòng một giờ:

```json

  "since": "2026-08-01T00:00:00Z",
  "until": "2026-08-02T00:00:00Z",
  "environment": "production",
  "analysis_unit": "session",
  "conversion_window_seconds": 3600,
  "steps": [
    { "kind": "page_view", "event_name": "/pricing" },
    { "kind": "interaction", "event_name": "signup_completed" }
  ]
}
```

`analysis_unit` là `session` hoặc `identified_user`. Mặc định là `session`.
`kind` của bước là `page_view`, `screen_view` hoặc `interaction`. Route phễu
không nhận `response_version`.

### Đọc chuyển đổi và độ bao phủ

`entry_rate` bằng `entered_units` chia cho `candidate_units`: 50 trên 60.
`overall_conversion_rate` bằng `completed_units` chia cho `entered_units`:
15 trên 50, tức 30%. Đây không phải 15 chia cho mọi ứng viên. Các số đếm này
không giải thích vì sao các đơn vị dừng lại.

Độ bao phủ đếm sự kiện, không đếm phiên. Ở đây, 120 sự kiện khớp với một bước,
và 20 sự kiện trong số đó không có ID phiên. Kết quả loại 20 sự kiện này khỏi số
đếm phiên. Không coi chúng là 20 phiên thất bại.

Bước đầu tiên không có `conversion_from_previous`. Bước cuối cùng không có
`drop_off_to_next_units` và `drop_off_to_next_rate`.

Một đơn vị chỉ đạt tới các bước phía sau nếu thời điểm của các bước tăng dần
nghiêm ngặt. Các sự kiện có cùng dấu thời gian không thể thỏa mãn hai bước liên tiếp.
Bước cuối phải diễn ra trong vòng `conversion_window_seconds` tính từ bước đầu
tiên.

Chế độ phiên đếm phiên, không đếm người. Chỉ dùng `identified_user` cho các sự
kiện mang ID chủ thể opaque loại `user`. Chế độ đó có thể ghép các sự kiện từ
nhiều phiên khác nhau trong cửa sổ chuyển đổi. Giữ nguyên đơn vị và
các bước khi so sánh kết quả.

`conversion_window_seconds` mặc định là 24 giờ hoặc độ dài khoảng thời gian, tùy
giá trị nào ngắn hơn. Giá trị tối đa là độ dài khoảng thời gian tính bằng giây
nguyên, làm tròn lên.

### Phễu không có kết quả

Phản hồi trống thành công vẫn liệt kê các bước đã yêu cầu với `units` bằng 0.
Nếu không có đơn vị ứng viên nào, `summary` bỏ `entry_rate` và
`overall_conversion_rate`. Route không trả về `404` khi không có sự kiện nào
khớp.

Đọc `coverage` và `next_action` để tìm nguyên nhân:

| `next_action.code` | Nguyên nhân |
| --- | --- |
| `capture_product_activity` | Không có sự kiện đã phân loại nào trong phạm vi. |
| `choose_captured_funnel_steps` | Không có sự kiện nào khớp với một bước đã yêu cầu. |
| `sessionize_product_activity` | Có sự kiện của các bước, nhưng không sự kiện nào có ID phiên. |
| `identify_product_users` | Có sự kiện của các bước, nhưng không sự kiện nào có chủ thể loại `user`. |
| `verify_funnel_entry` | Không có đơn vị nào vào bước 1. |
| `investigate_funnel_drop_off` | Có đơn vị đã vào, nhưng không đơn vị nào hoàn thành mọi bước. |
| `compare_funnel_contexts` | Có ít nhất một đơn vị đã hoàn thành phễu. |

### Yêu cầu phễu bị từ chối

Ngoài [lỗi phạm vi dùng chung](#shared-scope-errors), các yêu cầu sau trả về
`422` và `validation_failed`. Ít hơn 2 hoặc nhiều hơn 8 bước:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`conversion_window_seconds` bằng `0`, hoặc lớn hơn độ dài khoảng thời gian:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`event_name` để trống, dài hơn 256 ký tự hoặc chứa ký tự điều khiển sẽ trả về
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Bước `interaction` cũng phải là tên hành động hợp lệ. Nếu không, lỗi là
`product analytics interaction event_name must be a bounded stable action name`.

Sửa yêu cầu trước khi gửi lại. Không bỏ bước hay đổi đơn vị phân tích chỉ để có
kết quả không trống.

## Phân tích theo sự kiện chính xác và phân tích tự động

Tỷ lệ quay lại và vòng đời nhận hai cấu trúc yêu cầu. Dùng `response_version`
để chọn cấu trúc trả lời đúng câu hỏi của bạn:

| Phân tích | `response_version` | Tham số chọn sự kiện |
| --- | --- | --- |
| Tỷ lệ quay lại cho sự kiện chính xác | `1`, hoặc bỏ trống | Gửi cả `start_event` và `return_event`. |
| Vòng đời cho một sự kiện chính xác | `1`, hoặc bỏ trống | Gửi `event`. |
| Tỷ lệ quay lại hoặc vòng đời tự động | `2` | Không gửi tham số chọn sự kiện nào. |

Một tham số chọn chính xác chứa `kind` và `event_name`. `kind` là `page_view`,
`screen_view` hoặc `interaction`. Sao chép `event_name` từ
`classified_activity.top_events`. Không đoán tên sự kiện từ nhãn của nút.

Cả hai cấu trúc chỉ đếm người dùng: các ID chủ thể opaque loại `user`. Chủ thể
ẩn danh và sự kiện không có ID chủ thể dùng được không được tính là người dùng.
Phản hồi không bao giờ trả về ID chủ thể.

Các kỳ cố định là `hour`, `day`, `week` và `thirty_day`. Đây là các thời lượng
cố định. `thirty_day` là 30 ngày, không phải một tháng theo lịch. Nếu bạn bỏ
`interval`, API dùng `hour` cho khoảng thời gian từ 48 giờ trở xuống, và `day`
cho khoảng thời gian dài hơn.

### Yêu cầu tỷ lệ quay lại theo sự kiện chính xác

Gửi body này tới `POST /api/telemetry/analytics/retention`. Yêu cầu này hỏi liệu
người dùng có hoàn tất thêm một lần thanh toán sau lần thanh toán đầu tiên của
họ trong khoảng thời gian hay không:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T00:00:00Z",
  "until": "2026-06-03T00:00:00Z",
  "response_version": 1,
  "interval": "day",
  "interval_count": 1,
  "mode": "return_on",
  "cohort_mode": "first_in_range",
  "start_event": { "kind": "interaction", "event_name": "checkout_completed" },
  "return_event": { "kind": "interaction", "event_name": "checkout_completed" }
}
```

Sự kiện bắt đầu khớp đầu tiên trong khoảng thời gian là mốc neo của mỗi người
dùng. Một lần quay lại phải xảy ra sau mốc neo đó (không tính trùng thời điểm)
và trước `until`. Hai tham số chọn có thể là cùng một sự kiện.

| Trường | Giá trị | Mặc định |

### Đọc tỷ lệ quay lại

Độ bao phủ đếm cả bốn sự kiện đã phân loại, nhưng chỉ ba sự kiện khớp với mỗi
tham số chọn thanh toán. Lượt xem trang không được tính là lần quay lại. Một
trong hai người dùng thanh toán lại, nên `return_rate_after_start` là `0.5`.

Chỉ người dùng thứ nhất có trọn một ngày quan sát sau mốc neo. Người dùng đó
quay lại trong ngày, nên tỷ lệ trên đường cong là `1.0`. Người dùng thứ hai chỉ
có 12 giờ quan sát. Người dùng đó không đủ điều kiện cho kỳ 0, nên ô của nhóm
người dùng (cohort) thứ hai bỏ `retention_rate`. Không tính người dùng đó là đã rời bỏ.

`weighted_retention_rate` chia tổng số người dùng quay lại cho tổng số người dùng
đủ điều kiện. `fully_observed_cohort_average_rate` là trung bình cộng đơn giản
của tỷ lệ ở các nhóm người dùng mà mọi người dùng đều đủ điều kiện. Nhóm người
dùng là các khoảng gộp cố định bắt đầu từ `since`. `cohorts` chỉ chứa các nhóm
người dùng có người dùng.

### Lỗi tỷ lệ quay lại

Ngoài [lỗi phạm vi dùng chung](#shared-scope-errors), các yêu cầu sau trả về

Trong mỗi khoảng gộp, số người dùng mới, quay lại và hoạt động trở lại cộng lại

`previous_active_subjects`.

đây, các số đếm theo ngày cộng lại bằng 5, nhưng

ý một hướng điều tra. Trường này không chỉ ra nguyên nhân.

```json
    "buckets_with_dormancy": 0
  },
  "buckets": []
}
```

Người dùng chỉ xuất hiện trong lịch sử vẫn có thể tạo ra các khoảng gộp có người
dùng không hoạt động khi khoảng thời gian phân tích không có hoạt động nào.

### Lỗi vòng đời

Ngoài [lỗi phạm vi dùng chung](#shared-scope-errors), các yêu cầu sau trả về
`422` và `validation_failed`:

| Nguyên nhân | `error` |
| --- | --- |
| Phiên bản 1 không có `event`, phiên bản 2 có `event`, hoặc một phiên bản khác | `product analytics lifecycle activity selection is contradictory` |
| `history_period_count` nằm ngoài `2` đến `31` | `product analytics lifecycle history_period_count must be between 2 and 31` |
| Tổng các kỳ lịch sử dài hơn 62 ngày | `product analytics lifecycle history must not exceed 62 days` |
| Hơn 100 khoảng gộp phân tích | `product analytics lifecycle interval would exceed 100 analysis buckets` |

Ví dụ, mười kỳ lịch sử `week` cần 70 ngày:

```json
{
  "error": "product analytics lifecycle history must not exceed 62 days",
  "code": "validation_failed",
  "next": "use fewer history periods or a narrower fixed interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

### Đọc phạm vi phân tích đã chọn

Phản hồi theo sự kiện chính xác có `schema_version: 1`. `query` của chúng lặp
lại các tham số chọn và bỏ `activity_scope`. Phản hồi tự động có
`schema_version: 2` và `query.activity_scope: "all_classified_activity"`.
Chúng bỏ các tham số chọn. Một tham số chọn khác có thể làm kết quả thay đổi
dù hoạt động đã ghi nhận không đổi.

## Phản hồi chuỗi chỉ số

Sao chép tên từ `GET /api/telemetry/metrics`. Yêu cầu này nhóm một bộ đếm delta
theo dịch vụ:

```bash
  --data-urlencode "until=2026-06-01T12:15:00Z" \

  --data-urlencode "group_by=service_name"
```

### Đọc chuỗi chỉ số

Điểm dữ liệu đầu tiên ghi nhận 10 công việc đã hoàn thành, không phải 10 mẫu.
`rate_per_second` chia mức thay đổi đó cho khoảng gộp 300 giây. `last` là mức
thay đổi được ghi nhận cuối cùng, không phải tổng. Xem
[ý nghĩa của phép tổng hợp chỉ số](/vi/concepts/telemetry#read-the-metric-value).

Loại và temporality của một chuỗi quyết định `aggregation.code` của chuỗi đó và
các giá trị thống kê trong mỗi điểm dữ liệu. Điểm dữ liệu bỏ giá trị thống kê
không áp dụng. Giá trị thống kê bị thiếu không phải là 0.

| Loại và temporality | `status` | `aggregation.code` | `value` | Các giá trị thống kê khác |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Mẫu cuối cùng | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Tổng các mức thay đổi | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 ước tính | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Loại bất kỳ, `cumulative` | `limited` | `raw_cumulative_last` | Mẫu thô cuối cùng | `last`, `min`, `max` |
| Mọi cặp khác | `limited` | `raw_last` | Mẫu thô cuối cùng | `last`, `min`, `max` |

`limited` là phản hồi thành công, không phải lỗi. Trạng thái này thêm
`aggregation.limitation` để giải thích vì sao LogBrew chỉ hiển thị giá trị thô.
`ready` không chứng minh dữ liệu đã được ghi nhận đầy đủ.

Đọc `coverage` trước khi vẽ biểu đồ:

- `samples` đếm mẫu của mọi chuỗi khớp, kể cả các chuỗi mà phản hồi không trả
  về.
- `series` đếm số chuỗi khớp. `returned_series` và `points` đếm dữ liệu được
  trả về.
- `truncated` là `true` khi `series_limit` đã loại các chuỗi có lượng thấp hơn.
- `expected_buckets_per_series` là số khoảng gộp có thể có trong khoảng thời
  gian.

Không thêm điểm dữ liệu cho khoảng gộp không có mẫu. Không chèn giá trị 0 hay
sao chép giá trị trước đó. Mỗi điểm dữ liệu trả về tối đa 3 `trace_exemplars`.
Một trace exemplar liên kết một mẫu với một trace. Nó không giải thích mọi mẫu
trong khoảng gộp. Nếu không điểm dữ liệu nào có trace exemplar,
`next_action.target` là `metric_samples`.

### Phạm vi và lỗi của chuỗi chỉ số

`project_id`, `name` và `since` là bắt buộc. `name` có tối đa 200 ký tự.
`interval` là `auto`, `1m`, `5m`, `15m`, `1h`, `6h` hoặc `1d`. Mặc định là
`auto`, giá trị này chọn độ dài khoảng gộp nhỏ nhất cần tối đa 300 khoảng gộp.
Độ dài khoảng gộp chỉ định rõ không được cần quá 500 khoảng gộp.

`group_by` là `none`, `service_name`, `release` hoặc `environment`. Mặc định là
`none`. Khi không nhóm, các loại, đơn vị và temporality khác nhau vẫn nằm trong
các chuỗi riêng. `series_limit` nhận `1` đến `20`. Mặc định là `10`.

Kết quả trống trả về `200` với `series: []` và `samples` bằng 0. Object
`coverage` bỏ `first_seen_at` và `last_seen_at`. Điều này không chứng minh
rằng ứng dụng chưa từng gửi chỉ số đó. Kiểm tra dự án, tên chỉ số và khoảng thời
gian.

Thiếu `name` trả về `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Khoảng gộp một phút trên bảy ngày trả về `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Các lỗi `422` khác là `metric series group_by is not supported`,
`metric series interval is not supported` và
`metric series_limit must be between 1 and 20`.

`POST /api/telemetry/analytics/paths` tìm các sự kiện có tên xảy ra trước hoặc

### Đọc đường dẫn

`share_of_anchored_sessions` chia số phiên của một đường dẫn cho cả bốn phiên
có điểm neo. Tỷ lệ là 50% và 25%, không phải 67% và 33%.
`unrepresented_sessions` đếm các phiên có điểm neo mà không đường dẫn nào được
trả về đại diện. `paths_truncated: true` nghĩa là kết quả chưa đầy đủ.

Độ bao phủ đếm sự kiện, không đếm phiên. Ở đây, năm sự kiện khớp với điểm neo,
nhưng một sự kiện không có ID phiên. Sự kiện đó không thể nằm trong đường dẫn.
Mỗi đường dẫn trả về tối đa 3 trace exemplar. Dùng trace ID từ chính phản hồi
của bạn. Liên kết trace không cho biết điều gì gây ra hành động của người dùng
hay một lỗi.

| Trường | Ý nghĩa |
| --- | --- |
| `following` | Bắt đầu tại điểm neo khớp sớm nhất trong mỗi phiên. Điểm neo có vị trí `0`. Các nút sau đó có vị trí dương. |
| `preceding` | Kết thúc tại điểm neo khớp muộn nhất trong mỗi phiên. Các nút trước đó có vị trí âm. Điểm neo có vị trí `0`. |
| `depth` | Số nút liền kề điểm neo, không tính điểm neo. `1` đến `8`. Mặc định là `4`. Một đường dẫn có thể có ít nút hơn. |
| `collapse_repeated` | Gộp các nút liên tiếp có cùng loại và tên. Mặc định là `true`. |
| `path_limit` | Số đường dẫn tối đa được trả về, xếp hạng theo số phiên. `1` đến `20`. Mặc định là `10`. |

Các nút được sắp xếp theo thời gian ở cả hai hướng. Đường dẫn không phải bản
phát lại đầy đủ của phiên. LogBrew đọc tối đa 1024 sự kiện có tên trong mỗi
phiên trước khi chọn điểm neo: các sự kiện sớm nhất với `following` và các sự
kiện muộn nhất với `preceding`. Điểm neo nằm ngoài giới hạn đó có thể bị lược
bỏ.

### <span id="filter-the-anchor-by-property">Lọc điểm neo theo thuộc tính</span>

Gửi tối đa bốn `property_filters`, mỗi bộ lọc có đúng một `key` và `value`.
Sao chép khóa từ [danh mục thuộc tính](#analytics-property-catalog). Bộ lọc chỉ
áp dụng cho điểm neo, không áp dụng cho các sự kiện xung quanh. Giá trị phân
biệt chữ hoa chữ thường. Khi có bộ lọc, `query` lặp lại chúng, và
`coverage.anchor_property_filters` báo cáo:

| Trường | Ý nghĩa |
| --- | --- |
| `context_events` | Sự kiện điểm neo trong phạm vi, trước khi áp dụng bộ lọc thuộc tính. |
| `property_ready_events` | Sự kiện điểm neo có mọi khóa đã yêu cầu. |
| `missing_property_events` | Sự kiện điểm neo thiếu một hoặc nhiều khóa đã yêu cầu. |
| `matching_events` | Sự kiện điểm neo có giá trị khớp với mọi bộ lọc. |
| `nonmatching_value_events` | Sự kiện điểm neo có mọi khóa nhưng có giá trị khác. |
| `property_ready_rate` | `property_ready_events` chia cho `context_events`. |
| `match_rate` | `matching_events` chia cho `property_ready_events`. |

Thiếu khóa và khác giá trị cần cách sửa khác nhau. Không cộng hai số này với
nhau. Object này bị lược bỏ khi yêu cầu không có bộ lọc thuộc tính.

### Đường dẫn trống và yêu cầu bị từ chối

Mảng `paths` trống có thể là phản hồi `200` thành công. Đọc `summary`,
`coverage` và `next_action`. Các mã sau phân biệt nguyên nhân:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` và
`narrow_or_move_path_anchor`.

Ngoài [lỗi phạm vi dùng chung](#shared-scope-errors), các yêu cầu sau trả về
`422` và `validation_failed`:

| Nguyên nhân | `error` |
| --- | --- |
| `depth` nằm ngoài `1` đến `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` nằm ngoài `1` đến `20` | `product analytics path_limit must be between 1 and 20` |
| Hơn bốn bộ lọc thuộc tính | `product analytics paths accept at most four exact anchor property filters` |
| Khóa không có trong danh mục thuộc tính | `product analytics path property keys must be supported privacy-safe keys` |
| Cùng một khóa xuất hiện hai lần | `product analytics path property keys must be unique` |
| Giá trị trống, dài hơn 256 ký tự hoặc chứa ký tự điều khiển | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

Ví dụ, `depth: 0` trả về:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">Danh mục thuộc tính phân tích</span>

`GET /api/telemetry/analytics/properties` liệt kê các khóa thuộc tính trên sự
kiện sản phẩm đã phân loại trong một dự án. Dùng các khóa này trong
[so sánh phân khúc](#analytics-segment-comparison) và bộ lọc điểm neo đường dẫn.
Danh mục trả về khóa và số đếm. Danh mục không bao giờ trả về giá trị thuộc tính
hay định danh.

### Đọc các khóa thuộc tính có sẵn

Gửi `project_id` và `since`. Bạn cũng có thể gửi `until`, `service_name`,
`release`, `environment`, `limit` và `response_version`. `limit` nhận từ `1`
đến `50` khóa. Mặc định là `20`. Gửi `response_version=2` để nhận giá trị
`estimation.method` công khai.

### Diễn giải danh mục

`source` là `standard_context` với khóa ngữ cảnh chuẩn, chẳng hạn
`resource.runtime.name`, hoặc `custom_tag` với khóa bắt đầu bằng `tag.`.
`value_type` luôn là `string`. `properties` được sắp xếp theo `events`, từ cao
xuống thấp.

`tag.plan` có trên 60 trong 100 sự kiện đã phân loại. Khóa này có khoảng 3 giá
trị khác nhau. Phần mô tả khóa không hiển thị các giá trị đó. Dùng các giá trị
mà bạn biết từ ứng dụng của mình. Không đoán giá trị từ số đếm. Một sự kiện có
thể có nhiều khóa, nên không cộng các số đếm `events` của từng khóa.

| Trường | Ý nghĩa |
| --- | --- |
| `summary.classified_events` | Số sự kiện đã phân loại trong phạm vi. Đây là mẫu số của mỗi `coverage_rate`. |
| `summary.available_property_keys` | Số khóa khác nhau ước tính, không phải số dòng được trả về. |
| `coverage.unindexed_events` | Sự kiện được ghi nhận trước khi có chỉ mục thuộc tính hiện tại. Chúng không thể đóng góp khóa. |
| `coverage.incomplete_index_events` | Sự kiện có một phần ngữ cảnh sai định dạng hoặc bị cắt bớt. Các khóa hợp lệ của chúng vẫn được tính. |
| `coverage.privacy_filtered_events` | Sự kiện mà LogBrew đã xóa các khóa tag tùy chỉnh nhạy cảm. Đây không phải số đếm khóa. |
| `coverage.properties_truncated` | `true` khi số khóa nhiều hơn `limit`. Thu hẹp phạm vi, hoặc tăng `limit` tối đa đến 50. |
| `coverage.values_returned` | Luôn là `false`. |

Mảng `properties` trống không chứng minh rằng dự án không có sự kiện sản phẩm.
Đọc `summary`, `coverage` và `next_action`.

`response_version` khác `1` hoặc `2` trả về
`product analytics response_version must be 1 or 2`. LogBrew kiểm tra
`response_version` trước các giá trị khác.

## <span id="analytics-segment-comparison">So sánh phân khúc phân tích</span>

`POST /api/telemetry/analytics/segments/compare` so sánh tần suất các phiên hoặc

trị thuộc tính. Phân khúc đầu tiên là phân khúc mốc.

### Định nghĩa phép so sánh

Gửi body JSON này cùng xác thực tài khoản và
`Content-Type: application/json`. Ở đây, `basic` và `premium` là giá trị gói của
ứng dụng ví dụ, không phải gói của LogBrew:


`target` và `segments` là bắt buộc. `analysis_unit` là `session` hoặc
`identified_user`. Mặc định là `session`, tức là đếm phiên, không đếm người.
`interval` nhận cùng các giá trị như route tổng quan. Mặc định là `auto`.

Mỗi phân khúc cần một `key` duy nhất, một `label` và một tập bộ lọc khác biệt:

- `key`: 1 đến 32 byte. Bắt đầu bằng chữ cái ASCII viết thường hoặc chữ số. Chỉ
  dùng chữ cái ASCII viết thường, chữ số, `_` và `-`.
- `label`: 1 đến 80 ký tự, không chứa ký tự điều khiển.
- `service_name`, `release`, `environment`: không bắt buộc. Mỗi giá trị có 1 đến
  256 ký tự, không chứa ký tự điều khiển.
- `property_filters`: 0 đến 4 bộ lọc. Mỗi khóa chỉ xuất hiện một lần trong một
  phân khúc. Sự kiện phải khớp với mọi bộ lọc của phân khúc. Giá trị phân biệt
  chữ hoa chữ thường, dài 1 đến 256 ký tự, và LogBrew cắt khoảng trắng ở đầu
  và cuối.

Phân khúc không có bộ lọc chọn toàn bộ hoạt động đã phân loại trong dự án và
khoảng thời gian. Các phân khúc có thể chồng lấn nhau. Nhãn hay khóa khác nhau
không làm cho hai tập bộ lọc giống hệt nhau trở nên hợp lệ.

### Đọc tỷ lệ và mức chênh lệch

`eligible_units` ước tính số phiên hoặc người dùng có hoạt động đã phân loại
trong phân khúc. `reached_units` ước tính bao nhiêu trong số đó đã đạt tới mục
tiêu. `reach_rate` bằng `reached_units` chia cho `eligible_units`. Sự kiện
không có ID của đơn vị đã chọn không được tính vào các đơn vị này.

Tỷ lệ của phân khúc mốc là 20%. Tỷ lệ của phân khúc premium là 30%. Mức chênh
lệch là 10 điểm phần trăm. Mức tăng tương đối là 50%, không phải 10%. Các sai
số thập phân nhỏ đến từ phép tính dấu phẩy động. Làm tròn tỷ lệ khi hiển thị,
nhưng tính toán bằng các giá trị được trả về. Phân khúc mốc không có
`comparison_to_baseline`. Mức tăng tương đối bị lược bỏ khi tỷ lệ đạt tới của
phân khúc mốc bằng 0.

Trong `query`, bộ lọc phân khúc mà bạn không gửi là `null`. Danh sách
`property_filters` trống bị lược bỏ.

`coverage.property_filters` có cùng các trường như
[độ bao phủ của bộ lọc điểm neo đường dẫn](#filter-the-anchor-by-property). Ở
đây, `matching_events` bằng `classified_events`. Tách riêng trường hợp thiếu
khóa và khác giá trị. Các phân khúc có thể chồng lấn, và một phiên có thể xuất
hiện trong nhiều khoảng gộp. Không cộng số đơn vị giữa các phân khúc hay các
khoảng gộp.

Phép so sánh này chỉ mang tính mô tả. `confidence.causal_inference` là
`not_established` và `confidence.statistical_significance` là `not_tested`.
Tỷ lệ 30% so với 20% không cho thấy một gói đã khiến số lượt thanh toán tăng
lên.

### Lỗi so sánh phân khúc

Ngoài [lỗi phạm vi dùng chung](#shared-scope-errors), các yêu cầu sau trả về
`422` và `validation_failed`:

| Nguyên nhân | `error` |
| --- | --- |
| Ít hơn 2 hoặc nhiều hơn 4 phân khúc | `product analytics segment comparison requires two through four segments` |
| Hai phân khúc có cùng khóa | `product analytics segment keys must be unique` |
| Hai phân khúc có cùng bộ lọc | `product analytics segment filters must be unique` |
| Khóa không gồm 1 đến 32 byte được phép | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| Nhãn trống, quá dài hoặc chứa ký tự điều khiển | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| Giá trị bộ lọc chứa ký tự điều khiển | `product analytics segment filters must be control-free` |
| Hơn bốn bộ lọc thuộc tính trong một phân khúc | `product analytics segments accept at most four exact property filters` |
| Khóa không có trong danh mục thuộc tính | `product analytics segment property keys must be supported privacy-safe keys` |
| Cùng một khóa thuộc tính xuất hiện hai lần trong một phân khúc | `product analytics segment property keys must be unique within each segment` |
| Giá trị thuộc tính trống, quá dài hoặc chứa ký tự điều khiển | `product analytics segment property values must be non-empty, control-free, and at most 256 characters` |
| `response_version` khác `1` hoặc `2` | `product analytics response_version must be 1 or 2` |

Các lỗi của `interval` giống với [lỗi tổng quan](#overview-errors).

Ví dụ, hai phân khúc có khóa khác nhau nhưng bộ lọc giống hệt nhau trả về:

Nhãn khác hay thứ tự bộ lọc thuộc tính khác không làm thay đổi các sự kiện được
chọn. Lỗi kiểm tra hợp lệ không phải bằng chứng cho thấy không có sự kiện nào

## Phản hồi lượng tín hiệu

`GET /api/telemetry/summary/volume` đếm các tín hiệu được giữ lại của một dự án
trong một khoảng thời gian. Route này yêu cầu `project_id` và `since`. Route
không nhận `project_ids`.

Để đếm 1 đến 50 dự án gộp lại, gửi `project_ids` và `since` đến
`GET /api/telemetry/summary/volume/combined`. Phản hồi có cùng cấu trúc. Trường
`query` của nó có `project_ids` thay cho `project_id`. Một trace có span trong
nhiều dự án được chọn chỉ được đếm một lần. Nếu tài khoản không đọc được một
trong các dự án, route này trả về `404` với
`"error": "project selection not found"`.

`until` không được ở tương lai. Nếu bỏ `until`, thời điểm kết thúc là lúc gửi
yêu cầu. `since` dạng rút gọn như `24h` được tính lùi từ `until`. `interval` là
`auto`, `1m`, `5m`, `15m`, `1h`, `6h` hoặc `1d`. Giá trị mặc định `auto` chọn
độ dài khoảng gộp nhỏ nhất cần tối đa 120 khoảng gộp. Một yêu cầu không được
cần quá 500 khoảng gộp. `response_version` duy nhất là `1`.

### Đọc mỗi số đếm theo đơn vị riêng của nó

| Tín hiệu | `total` đếm gì | Không hiểu thành |
| --- | --- | --- |
| `issues` | Số lần xảy ra của vấn đề được giữ lại | Số vấn đề đã gộp nhóm hoặc số người dùng bị ảnh hưởng |
| `logs` | Số sự kiện log được giữ lại | Số yêu cầu |
| `traces` | Số trace ID duy nhất, được tính tại span được giữ lại đầu tiên của chúng trong khoảng thời gian này | Số span hoặc số trace bắt đầu trong toàn bộ thời gian |
| `actions` | Số sự kiện hành động được giữ lại | Số người dùng hoặc số phiên |
| `metrics` | Số điểm chỉ số được giữ lại | Tổng giá trị chỉ số |

`total` là tổng số đếm của các khoảng gộp trong chuỗi. `peak` là số đếm lớn nhất
của một khoảng gộp. `non_empty_buckets` đếm các khoảng gộp có số đếm lớn hơn 0.
Năm chuỗi luôn xuất hiện theo thứ tự này. Không gộp số đếm của các tín hiệu khác
nhau thành một điểm tác động duy nhất.

Các khoảng gộp bắt đầu tại `query.since`. Mỗi khoảng gộp bao gồm thời điểm bắt
đầu và không bao gồm thời điểm kết thúc. Khoảng gộp cuối có thể ngắn hơn độ dài
khoảng gộp. Phản hồi không có chuỗi đếm bản phát hành. Không hiểu
`release_volume_not_included` là không có bản phát hành nào.

### Khoảng thời gian trống và bị rút ngắn

Nếu không có tín hiệu nào khớp, cả năm chuỗi vẫn còn, và các điểm dữ liệu của
chúng có số đếm 0 rõ ràng. Yêu cầu thất bại là trường hợp khác. Không thay lỗi
bằng một biểu đồ toàn giá trị 0.

So sánh `query.requested_since` với `query.since`. Nếu thời gian giữ dữ liệu
làm rút ngắn khoảng thời gian, `coverage.retention.window_clipped` là `true` và
`limitations` chứa `retention_window_clipped`. Nếu không còn phần nào của khoảng
thời gian đã yêu cầu, `query.bucket_count` là `0` và mỗi chuỗi có mảng `points`
trống. Điều này không chứng minh rằng không có sự kiện nào xảy ra trong giai
đoạn đó.

`policy_days` là `null` và `cutoff` bị lược bỏ khi không có giới hạn giữ dữ liệu
nào áp dụng. `sampling.upstream` luôn là `unknown`, kể cả khi
`storage_evaluation` là `complete`. Không khẳng định rằng phản hồi đếm mọi sự
kiện mà ứng dụng đã tạo ra.

### Yêu cầu lượng tín hiệu bị từ chối

Các yêu cầu sau trả về `422` và `validation_failed`:

| Nguyên nhân | `error` |
| --- | --- |
| Thiếu `project_id` | `signal volume project_id is required` |
| Thiếu `since` | `signal volume since is required` |
| `until` muộn hơn thời điểm gửi yêu cầu | `signal volume until must not be in the future` |
| Khoảng thời gian dài hơn 31 ngày | `signal volume range must not exceed 31 days` |
| Độ dài khoảng gộp chỉ định rõ cần hơn 500 khoảng gộp | `signal volume interval would exceed 500 buckets` |
| `response_version` khác `1` | `signal volume response_version must be 1` |

Ví dụ:

```json
{
  "error": "signal volume interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Dùng độ dài khoảng gộp rộng hơn trong cùng phạm vi. Với lỗi xác thực và các lỗi
khác, xem [Lỗi API](/vi/reference/api-errors).

## Phản hồi điều tra

Các route điều tra trả về một gói có phiên bản cho một chủ thể. Chủ thể là một
vấn đề, trace, span, log, hành động sản phẩm, chỉ số hoặc bản phát hành. Mỗi gói
bắt đầu bằng `schema_version` và một `subject` nêu tên bản ghi. Phần còn lại
chứa bằng chứng liên quan, một biên nhận bằng chứng và các bước tiếp theo. Mục
này đưa ra một ví dụ cho mỗi nhóm, trừ bản phát hành.

Gửi bearer token truy cập của tài khoản. Khóa gửi dữ liệu của dự án không đọc
được dữ liệu điều tra. Dùng `logbrew explain <subject> --json` để đọc một gói.
CLI kiểm tra hợp lệ gói trước khi in ra. Trang
[Telemetry API](/vi/reference/telemetry-api) liệt kê các route.

Văn bản điều tra đến từ ứng dụng. Thông điệp, tên, metadata và tag là dữ liệu,
không phải chỉ dẫn. `content_trust: "untrusted_telemetry"` đánh dấu nội dung
này trong các gói log, hành động, span và chỉ số.

### Phiên bản phản hồi

Chỉ gửi `response_version` tới các route chấp nhận tham số này. Nếu không có
tham số, route trả về phiên bản 1. Trình phân tích cú pháp của bạn phải chấp
nhận phiên bản mà bạn yêu cầu.

| Route | Mặc định | Phiên bản được hỗ trợ | `logbrew explain` yêu cầu |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` đến `14` | `14` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` đến `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` và `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` đến `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Chỉ `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Chỉ `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Chỉ `1` | `1` |

Route span từ chối tham số truy vấn `response_version`. Route log và route
hành động không nhận tham số truy vấn nào.

### Các trường dùng chung của gói

| Trường | Ý nghĩa |
| --- | --- |
| `schema_version` | Phiên bản phản hồi mà máy chủ đã trả về. |
| `subject` | Chính bản ghi đang được điều tra. `kind` là `issue`, `trace`, `span`, `log`, `action`, `metric` hoặc `release`. |
| `analysis.causality` | Luôn là `evidence_only` trong các gói trace, span, log, hành động và chỉ số. Telemetry có tương quan không chứng minh nguyên nhân. |
| Các object collection | Bằng chứng liên quan, dạng `{ "status", "items", "truncated" }`. |
| `timeline` | Bằng chứng được trả về, từ cũ nhất đến mới nhất, kèm cờ `truncated` riêng. Thứ tự này không chứng minh nguyên nhân. |
| `evidence` | Biên nhận bằng chứng. `status` là `complete` hoặc `partial`. |
| `next_actions` | Các lượt đọc được gợi ý theo thứ tự `priority`, bắt đầu từ `1`. Chúng chưa được chạy. |

Mỗi collection liên quan báo một `status` về mức khả dụng:

| Trạng thái | Ý nghĩa | Cách client xử lý |
| --- | --- | --- |
| `available` | Lượt đọc đã hoàn tất và trả về các mục. | Hiển thị các mục và cờ `truncated`. |
| `not_linked` | Chủ thể không có định danh cho liên kết này, chẳng hạn trace ID. | Giải thích liên kết bị thiếu. Không tự dựng liên kết từ dấu thời gian. |
| `not_found` | Lượt đọc đã hoàn tất và không tìm thấy bằng chứng nào được giữ lại. | Hiển thị kết quả trống. |
| `unavailable` | Lượt đọc không bắt buộc đã thất bại. Chủ thể vẫn hợp lệ. | Tiếp tục hiển thị chủ thể. Thử lại sau. Không hiển thị kết quả là 0 mục. |

Biên nhận bằng chứng có bốn danh sách tên trường ổn định đã sắp xếp:
`captured_fields`, `missing_fields`, `redacted_fields` và
`truncated_fields`. `status` chỉ là `complete` khi ba danh sách sau cùng trống.
Dữ liệu đã che không phải dữ liệu chưa ghi nhận. Dữ liệu bị cắt bớt không phải
dữ liệu đầy đủ. Không tự điền giá trị đã che hoặc bị cắt bớt.

### Giới hạn điều tra

Các giới hạn này áp dụng cho một phản hồi. Cờ `truncated` hoặc một mục trong
`truncated_fields` cho thấy giới hạn đã khiến dữ liệu bị bỏ bớt.

| Bằng chứng | Giới hạn |
| --- | --- |
| Các mục liên quan trong một collection | 20 |
| Số span được giữ lại được đọc cho một trace | 1.000 |
| Các mục trong timeline | 50 với gói log, hành động và span. 100 với gói trace và chỉ số. |
| Thuộc tính có cấu trúc (attributes, properties) và metadata | 64 giá trị vô hướng, 4 cấp object hoặc mảng, 16 mục trong mỗi mảng, 512 ký tự trong mỗi chuỗi |
| Khoảng thời gian tương quan | 5 phút trước và sau một log, hành động hoặc lần xảy ra đã chọn của vấn đề. Với trace hoặc span, 5 phút trước lúc bắt đầu và sau lúc kết thúc, tối đa 24 giờ. |

Mục của từng nhóm liệt kê giới hạn riêng.

### Phản hồi điều tra vấn đề

Dùng `GET /api/telemetry/issues/{issue_id}/investigation` để đọc bằng chứng cho
một lần xảy ra của vấn đề đã gộp nhóm.
Trang [Điều tra một vấn đề](/vi/guides/investigate-an-issue) cho biết cách đọc
bằng chứng theo thứ tự. Yêu cầu phiên bản 14:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=14" \
  --data-urlencode "selection=recommended"
```

Các tham số truy vấn là `response_version`, `selection` và `occurrence_id`.
`selection` là `recommended`, `first` hoặc `latest`. Các giá trị phân biệt chữ
hoa chữ thường. Ở phiên bản 2 đến 14, nếu bỏ tham số chọn, route dùng
`recommended`. Phiên bản 1 trả về lần xảy ra gần nhất được giữ lại và không nhận
tham số chọn. Bộ lọc của danh sách vấn đề không áp dụng cho lượt đọc này.

là `null`.

`subject.status` và các trạng thái trong `lifecycle` báo vấn đề đã lưu trữ là
`ignored`. Phản hồi danh sách và chi tiết vấn đề dùng `archived` từ phiên bản
phản hồi 2 trở đi.

Giới hạn của vấn đề: phần đề xuất đọc tối đa 50 lần xảy ra được giữ lại. Xu
hướng có tối đa 30 khoảng gộp. Mỗi phân bố trả về tối đa 10 giá trị. Một dấu
vết ngăn xếp (stack trace) có tối đa 32 khung.

#### Lỗi yêu cầu điều tra vấn đề

Chỉ dùng `selection` hoặc `occurrence_id`. Không gửi cả hai, kể cả khi chúng
chọn cùng một lần xảy ra:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Nguyên nhân | Cách khắc phục |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | Yêu cầu có cả hai tham số chọn. | Chỉ giữ một tham số chọn. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | Yêu cầu có tham số chọn nhưng dùng phiên bản 1 hoặc không có phiên bản. | Gửi `response_version=14`. Giữ nguyên tham số chọn. |
| `422` | `issue investigation response_version must be 1 through 14` | Phiên bản nằm ngoài phạm vi cho phép. | Gửi phiên bản được hỗ trợ. |
| `422` | `invalid query parameters` | Tham số không xác định, UUID không hợp lệ, phiên bản không phải số nguyên hoặc giá trị `selection` không xác định. | Sửa [truy vấn](/vi/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | Lần xảy ra không nằm trong lịch sử được giữ lại của nhóm này. | Sao chép ID lần xảy ra từ các sự kiện của chính vấn đề này. Không tự chuyển sang `latest` hay `recommended` khi chưa được chấp thuận. |
| `404` | `issue not found` | Không dự án nào đọc được có vấn đề này. | Kiểm tra tài khoản và UUID của vấn đề. Không gửi UUID của lần xảy ra làm ID vấn đề. |

Lần xảy ra không tồn tại không có nghĩa là vấn đề không tồn tại. `404` không cho
biết liệu tài khoản khác có đọc được vấn đề hay không.

### Phản hồi điều tra trace

Dùng `GET /api/telemetry/traces/{trace_id}/investigation` để đọc một trace cùng
đường đi lỗi, đường đi chậm nhất và các tín hiệu liên quan. Các tham số truy vấn là
`response_version`, `project_id`, `release` và `environment`. Tất cả đều không
bắt buộc. Yêu cầu phiên bản 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

Phiên bản 2 thêm `cause` và `fix` vào mỗi vấn đề liên quan. Phiên bản 3 thêm
`span_id` vào các vấn đề, hành động và chỉ số liên quan khi đã ghi nhận.

### Phản hồi điều tra span

Dùng `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` để
đọc một thao tác trong trace. Gửi `project_id`, `environment` và `release`. Cả
ba đều bắt buộc. Sao chép chúng từ span đã chọn. Không gửi `id` của dòng span
làm `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### Phản hồi điều tra log

Dùng `GET /api/logs/{log_id}/investigation` để đọc một log và bằng chứng liên

```bash
curl --fail-with-body -sS \
```

đọc liên quan dùng dự án, môi trường và bản phát hành của log, cùng 5 phút
trước và sau log. Các log lân cận cũng dùng cùng dịch vụ. Chúng không cần trace
ID. Các lượt đọc theo đúng trace cần trace ID của log và có thể bao gồm dịch vụ
khác. Bản tóm tắt trace dùng cùng trace ID và phạm vi, không có giới hạn khoảng
thời gian.

### Phản hồi điều tra hành động

### Phản hồi điều tra chỉ số

Dùng `GET /api/telemetry/metrics/investigation` để đọc một tên chỉ số trong một
dự án và một khoảng thời gian. Phản hồi có chuỗi hiện tại, phép so sánh với
khoảng thời gian liền trước có cùng độ dài, mẫu gần nhất, các trace exemplar và
các lần triển khai đã hoàn tất. Phiên bản 2 thêm mô tả chỉ số lấy từ mẫu gần
nhất được giữ lại. Phiên bản 1 luôn báo
`description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` và `since` là bắt buộc. `since` được tính vào khoảng thời
gian, còn `until` thì không. `until` mặc định là thời điểm hiện tại. Phép so
sánh cũng đọc khoảng thời gian liền trước có cùng độ dài.

không chứng minh rằng nó gây ra thay đổi đó.

Dự án mà tài khoản không đọc được trả về `200 OK` với
`analysis.status: "no_samples"`, không phải `404`. Kết quả trống không mô tả các
loại tín hiệu khác.

Giới hạn của chỉ số: khoảng thời gian tối đa 31 ngày. Mỗi chuỗi có tối đa 500
khoảng gộp. `series_limit` từ 1 đến 20, mặc định là 10. Phản hồi trả về tối đa
20 exemplar và 20 lần triển khai.

| HTTP | `error` | Cách khắc phục |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Bỏ `response_version` hoặc gửi `2`. |
| `422` | `metric series project_id is required` | Gửi một ID dự án đọc được. |
| `422` | `metric series name is required` | Sao chép tên từ danh sách chỉ số. |
| `422` | `metric series since is required` | Gửi một giá trị như `24h` hoặc một dấu thời gian RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | Dùng khoảng thời gian ngắn hơn. |
| `422` | `metric series interval would exceed 500 buckets` | Dùng `interval=auto` hoặc độ dài khoảng gộp rộng hơn. |
| `422` | `metric series_limit must be between 1 and 20` | Gửi giá trị từ 1 đến 20. |

`interval` là `auto`, `1m`, `5m`, `15m`, `1h`, `6h` hoặc `1d`. `group_by` là
`none`, `service_name`, `release` hoặc `environment`. Các giá trị khác trả về
`422`.

### Lỗi điều tra

| HTTP | Route | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Hành động | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, hành động, vấn đề | `invalid URL path parameters` khi ID trong đường dẫn URL không phải UUID |
| `422` | Vấn đề, trace, span, chỉ số | `invalid query parameters` khi có tham số không xác định hoặc giá trị sai kiểu |

`404` nghĩa là không dự án nào đọc được có bản ghi đó. Mỗi route cũng trả về
`401` khi không có xác thực hợp lệ và `405` với phương thức khác `GET`.
Xem [Lỗi API](/vi/reference/api-errors) để biết các phản hồi
[không tìm thấy](/vi/reference/api-errors#resource-not-found),
[đường dẫn](/vi/reference/api-errors#invalid-path-value),
[xác thực](/vi/reference/api-errors#authentication-failure) và
[phương thức](/vi/reference/api-errors#unsupported-method).

Một lượt đọc bằng chứng không bắt buộc có thể thất bại bên trong phản hồi
`200 OK`. Khi đó, collection báo `unavailable`. Không hiển thị nó thành
`not_found` hay thành 0 bản ghi.

## <span id="severity-values">Giá trị mức độ nghiêm trọng</span>

Các giá trị mức độ nghiêm trọng hiển thị cho người dùng là `info`, `warning`,
`error` và `critical`. SDK và runtime có thể gửi các bí danh phổ biến như
`trace`, `debug`, `warn` hoặc `fatal`. Phản hồi REST và phản hồi trực tiếp luôn
trả về giá trị chuẩn. Ví dụ, LogBrew nhận `warn` làm đầu vào và trả về
`warning`. Khi tiếp nhận dữ liệu, LogBrew từ chối các giá trị mức độ nghiêm
trọng không xác định.

| Bí danh | Giá trị chuẩn |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Phản hồi quy tắc mức độ nghiêm trọng</span>

Quy tắc mức độ nghiêm trọng thay đổi cách LogBrew hiển thị một log hoặc một vấn
đề. Quy tắc không thay đổi mức độ nghiêm trọng mà ứng dụng đã ghi nhận. Log và
vấn đề trả về object `triage`:

| Trường | Ý nghĩa |
| --- | --- |
| `effective_severity` | Mức độ nghiêm trọng cần hiển thị. Khi không có quy tắc, giá trị này bằng `severity`. |
| `ignored` | `true` khi quy tắc log bỏ qua log đó, hoặc khi vấn đề đã lưu trữ. |
| `rule_applied` | `true` khi có quy tắc mức độ nghiêm trọng hoặc trạng thái bỏ qua được áp dụng. `false` là giá trị mặc định, không phải dữ liệu bị thiếu. |

Dùng `triage.effective_severity` để hiển thị. Giữ `severity` là giá trị đã ghi
nhận. Theo mặc định, danh sách log không hiển thị các log bị bỏ qua. Gửi `status=ignored`
hoặc `status=all` trong `GET /api/logs` để lấy cả các log đó.

Tài khoản phải có quyền quản lý vấn đề trong dự án. Quyền đọc là chưa đủ. Nếu
không có quyền này, thao tác đổi quy tắc trả về `403` với `code: forbidden`.

### Đổi quy tắc log

`PUT /api/logs/{log_id}/triage-rule` đặt quy tắc cho log này và cho các log sau
có cùng chữ ký. Body cần cả `severity` lẫn `ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Phản hồi `200 OK` chứa toàn bộ [log](#log-response). `severity` của log vẫn là
`warning`. `triage` của log thể hiện quy tắc:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Đoạn trích này chỉ hiển thị các trường đã thay đổi. `severity` trong yêu cầu là
`source`, `info`, `warning`, `error` hoặc `critical`. `source` khôi phục mức độ
nghiêm trọng đã ghi nhận. Giá trị này không làm log bị bỏ qua hoạt động trở lại.
Để hiển thị lại log, gửi `"ignored": false`.

### Đổi quy tắc vấn đề

`PUT /api/telemetry/issues/{issue_id}/triage-rule` đặt mức độ nghiêm trọng hiển
thị của một vấn đề đã gộp nhóm và các lần xảy ra sau đó. Body chỉ nhận
`severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Phản hồi `200 OK` chứa toàn bộ [vấn đề](#issue-response) ở phiên bản 1.
`severity` đã ghi nhận và `status` không thay đổi:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Đoạn trích này chỉ hiển thị một số trường. Quy tắc không giải quyết, lưu trữ hay
mở lại vấn đề. Dùng [thao tác đổi trạng thái](#issue-status-response-examples)
cho việc đó. Mức ưu tiên suy ra sẽ theo mức độ nghiêm trọng hiệu lực mới. Đọc
vấn đề với `response_version=2` trở lên để xem mức ưu tiên đó.

Mức độ nghiêm trọng không được hỗ trợ trả về `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Trường không xác định trong body, chẳng hạn `status` trong quy tắc vấn đề, trả
về `422` với `code: invalid_json`. Log hoặc vấn đề không tồn tại hay không đọc
được trả về `404` với `code: not_found`. Nếu mất phản hồi, đọc lại log hoặc vấn
đề trước khi gửi lại quy tắc.

## Định dạng phản hồi lỗi

Lỗi ứng dụng trả về một envelope JSON. Ví dụ này cho thấy một yêu cầu bị từ
chối; văn bản `error` và `next` tùy thuộc vào lỗi cụ thể:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Dùng `code` để rẽ nhánh trong chương trình và `next_action` cho tự động hóa.
Hiển thị `error` và `next` cho người đọc dưới dạng văn bản thuần. Không phân tích
cú pháp câu chữ của chúng. Một số lỗi có thêm trường, chẳng hạn `limit`,
`reset_at` hoặc `retry_after_seconds`. Phản hồi không có body JSON thì không có
`code` của LogBrew. Xem [Lỗi API](/vi/reference/api-errors) để biết mọi mã lỗi.

## Đọc dữ liệu bằng CLI

CLI đọc cùng các route và trả về cùng JSON khi dùng `--json`. Bắt đầu với phạm
vi rộng, rồi thu hẹp dần:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Thêm `--pagination cursor` để nhận envelope cursor. CLI yêu cầu phản hồi vấn đề
phiên bản 4. Xem [Đọc trang tiếp theo](/vi/reference/cli#read-the-next-page)
và [Theo dõi trực tiếp](/vi/reference/cli#live-watch).

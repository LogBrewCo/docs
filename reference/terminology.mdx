LogBrew uses one term for each product concept. API fields, CLI flags, enum
values, event names, and attribute keys remain unchanged in every language.

## Observability and monitoring

| Term | Meaning |
| --- | --- |
| Observability | Understanding an application's behavior from the evidence it produces. |
| Telemetry | The signals that an application reports, such as logs, traces, and metrics. |
| Monitoring | Checking known conditions, such as a measured value against a threshold. |
| `o11y` | A short form of observability. The number counts the 11 letters between `o` and `y`. |

For signal selection and worked examples, read [Telemetry](/concepts/telemetry).

## AI agents

| Term | Meaning |
| --- | --- |
| MCP server | The hosted LogBrew server for the Model Context Protocol. AI agents use it to read approved projects, and to change them if you allow it. |
| MCP client | An application that connects an AI agent to an MCP server, such as Claude Code. |
| Approved project | A project that you selected when you gave an MCP client access. The client can use only approved projects. |
| Connection | The access that you give 1 MCP client when you approve it. It ends after 30 days without use, after 90 days, or when you revoke it. The CLI calls it a grant. |
| Scope | What a connection can do. `read` reads approved projects. `write` also changes them. You choose `write` when you approve the connection. |

To connect a client, read [Connect an AI agent with MCP](/guides/mcp).

## Observability signals

<AccordionGroup>
  <Accordion title="Issue">
    A grouped problem that can contain multiple occurrences. An occurrence is
    one captured instance of that issue. `first_seen_at` is the time of the
    first occurrence. `last_seen_at` is the time of the most recent occurrence.
  </Accordion>

  <Accordion title="Log">
    One timestamped event record. A log can carry severity, service, release,
    environment, trace context, and privacy-bounded attributes.
  </Accordion>

  <Accordion title="Trace and span">
    A trace follows work across a request or operation. A span is one timed
    operation inside that trace. A correlation to a trace is evidence of shared
    context; it is not proof of cause.
  </Accordion>

  <Accordion title="Metric">
    A runtime measurement with a defined unit, type, aggregation, and time
    window. Metric points are not interchangeable with log, trace, or issue
    counts.
  </Accordion>

  <Accordion title="Release">
    A deployed application or service version reported with telemetry. A release
    is not the same object as a project or repository.
  </Accordion>

  <Accordion title="Action">
    A classified product event, such as a signup, checkout, import, or failed
    job. Analytics classifies an action as a page view, a screen view, or an
    interaction. An action is not an automated command that LogBrew runs.
  </Accordion>
</AccordionGroup>

## Issue investigation

Not every occurrence contains every field.

| Term | Meaning |
| --- | --- |
| Severity | The urgency of a signal: `info`, `warning`, `error`, or `critical`. It is separate from issue status. |
| Issue status | The workflow state of a grouped issue: `unresolved`, `resolved`, or `archived`. It is not the outcome of one request. |
| Archived issue | An issue that the team removed from active triage. Older responses call this status `ignored`. |
| Issue priority | The triage order of a grouped issue: `high`, `medium`, or `low`. It follows severity until a person sets it. |
| Priority source | Where the priority comes from. `derived` follows severity: `error` and `critical` are `high`, `warning` is `medium`, and `info` is `low`. `manual` is a priority that a person set. |
| Issue assignee | The 1 account or 1 team that owns the next step on a grouped issue. An account must be able to read the project. A team must belong to the project's organization. |
| Team | A named group of members in an organization. Issues can be assigned to a team, and ownership rules can name it. A team gives its members no project access. |
| Ownership rule | A project rule that maps a stack frame path, module, route, service, or tag to the accounts or teams that own matching issues. |
| Suggested owner | An account or team that LogBrew proposes for an issue, from an ownership rule, a CODEOWNERS line, or recent activity. It is a suggestion, not an assignment. |
| Inbox | The list of issues that other people assigned to you or your teams. LogBrew does not send email for it. |
| Stack trace | Captured function-call evidence for an error. It is different from a distributed trace. |
| Stack frame | One entry in a stack trace. It can identify a function, module, file, line, or column. |
| Exception chain | Linked exceptions reported together, such as an error and its cause. Missing, redacted, or truncated entries limit the evidence. |
| Application frame | A stack frame marked as application code. It shows code to examine. It does not prove the fault. |
| Breadcrumb | A short recorded event before an issue occurrence. Breadcrumbs are not a complete recording of a session. |
| Handled exception | An exception that the application reported as handled. It does not prove that the operation succeeded. |
| Source map | A build artifact that maps generated JavaScript locations to original source locations. |
| Symbolicated frame | A frame whose generated location was resolved to original source information. |
| Baseline occurrence | The captured occurrence used as the reference for reproduction. |
| Provenance | Where an assessment comes from. `backend_observed` means that LogBrew observed it. `application_reported` means that the app reported it and LogBrew did not verify it. |
| Reproduction readiness | Whether the baseline occurrence has the evidence needed to try a reproduction. It is not a passed reproduction test. |

Use the [investigation guide](/guides/investigate-an-issue) for the reading
order and the response fields.

## Identity and correlation

A missing value does not prove that the related activity did not happen.

| Term | Meaning |
| --- | --- |
| Trace context | The trace and span identifiers that connect work across signals. |
| Root span | The span that starts a trace and has no parent span. The earliest returned span is not necessarily the root. |
| Child span | A span with a parent span in the same trace. |
| Correlation | An exact relationship that LogBrew returns, such as a shared trace ID. It does not prove cause. |
| Identified user | An app-supplied subject with a stable ID and kind `user`. |
| Anonymous subject | An app-supplied subject with kind `anonymous`. Counts keep it separate from identified users. |
| Unknown identity kind | A subject without a known kind. It is not counted as an identified user. |
| Missing subject | An event without a subject. This is different from a subject with an unknown kind. |

The identity kind shows how the app classified its subject. It does not prove
that the data is anonymous. A stable ID can still link activity.

## Scope and data quality

| Term | Meaning |
| --- | --- |
| Project | The primary owned product boundary. One project can contain multiple services or repository components. |
| Service | A reporting runtime or component inside a project. |
| Environment | An exact reporting context, such as production or staging. |
| Ingest key | A project key that sends telemetry to 1 project. It cannot read telemetry. |
| Read key | A project key that reads the telemetry of 1 project. It cannot send telemetry, change data, or sign in. See [Project key kinds](/guides/verify-setup#project-key-kinds). |
| Ingested | Accepted by the ingestion contract. It does not promise indefinite retention. |
| Indexed | Available to the specified index or query. It is not a synonym for ingested. |
| Retained | Present in the evaluated data window and inside the account's data retention. |
| Sampled | Some telemetry was selected before or during collection. |
| Coverage | A measured share with an explicit numerator and denominator. |
| Truncated | The response reached a bound. Omitted data is not necessarily absent. |
| Approximate | Estimated by the documented method rather than counted exactly. |
| Time window | The exact period that a query evaluates. |

## Plans and organizations

| Term | Meaning |
| --- | --- |
| Plan | A fixed set of monthly allowances with a retention period. The plans are Free, Pro, Business, and Enterprise. |
| Allowance | The amount of 1 telemetry type that a plan includes in 1 billing month, such as log bytes or trace spans. |
| Data retention | The number of days that LogBrew keeps an account's telemetry. LogBrew deletes older telemetry. It is different from product analytics retention. |
| New-account offer | The Pro allowances that accounts created before 2026-10-26 get free for 6 months. Afterward, the account uses its own plan. |
| Organization | A shared space for members, teams, and projects. Every plan has organizations with no limit on members or projects. |

For the allowances and the retention of each plan, read [Account API](/reference/account-api).

## Measurements and time

| Term | Meaning |
| --- | --- |
| Data point | One value at a reported time. Read the metric name and unit before you compare data points. |
| Time series | Values of the same measurement ordered by time. A gap does not mean that the value was zero. |
| Duration | The elapsed time of an operation. It is different from the time when the operation occurred. |
| Aggregation | A defined calculation across measurements, such as a sum or an average. |
| Time bucket | One interval in a chart or grouped result. Its start and end set the range. |
| Partial period | A period that is not yet complete. It is not a completed period with zero activity. |

Do not add the durations of overlapping child spans to get the total request
time. Do not compare an event count with a count of identified users.

## Evidence states

These states are not interchangeable:

- **Captured:** the evidence is present.
- **Missing:** the evidence was not captured.
- **Redacted:** the evidence was deliberately concealed.
- **Truncated:** the evidence exceeded a response or capture bound.
- **Unavailable:** the read could not provide the evidence.

`Likely cause` and `likely fix area` describe bounded diagnostic evidence, not a
proven root cause. `Reported impact` is supplied by the reporting application
unless a contract explicitly describes a LogBrew measurement.

## Product analytics

| Term | Meaning |
| --- | --- |
| Event | Classified product activity with an exact stable name. |
| Property | A context key used to describe or filter an event. |
| Session | A visit or app session, not a person. |
| Cohort | A bounded group defined by exact criteria. |
| Funnel | Ordered steps used to measure progression or conversion. |
| Retention | Return behavior measured with an explicit period and denominator. |
| Paths | Session journeys before or after a selected event. |
| Lifecycle | Groups identified subjects in each period as new within observed history, returning, resurrected, or dormant. |
| New in observed history | Active without an earlier selected event in the bounded history window. It does not mean a first-time customer. |

Partial periods, missing identity, incomplete property capture, sampling, and
truncation qualify the result. LogBrew surfaces those limits rather than
turning them into zero or certainty.

Read [Product analytics](/concepts/product-analytics) for the counting rules.
Use [Product event capture](/guides/product-events) to send classified activity
and typed identity.

This page shows one example for each response family of the
[Telemetry API](/reference/telemetry-api). All values are synthetic. For error
codes and recovery, see [API errors](/reference/api-errors).

## Read a response

Read every response in this order:

1. Read the HTTP status.
2. Make sure that the body has the shape that the route owns.
3. Make sure that each `project_id` is inside the requested project scope.
4. Keep canonical enum values and identifiers unchanged.
5. Follow `next_action` only when the client supports its `code` and
   `target`.
6. Keep `null`, an omitted field, and an empty list as different states.

A `200 OK` can contain an empty list. An empty log list means that no log
matched the request. It does not mean that issues, traces, or actions are also
empty. Do not join signals because their timestamps are close. Follow a trace
only when the response contains its exact `trace_id`.

## What to send

Responses are only as useful as the telemetry you send. Send these values on
every envelope or SDK setup:

- `release` and `environment`.
- Stable names for services, actions, and metrics.
- Trace context when logs, spans, actions, and issues belong to the same
  request.
- Canonical severity values: `info`, `warning`, `error`, and `critical`.
- Attributes that help debugging, without secrets or unnecessary personal data.

See [Send SDK telemetry](/guides/sdk-ingestion) and
[Safe capture](/guides/safe-capture).

## Ingestion response

Public SDKs read the `POST /v1/events` response for you. Application code does
not have to handle it.

`POST /api/telemetry/ingest` returns `200 OK` with accepted item counts for
each stream:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1
}
```

A `401` means that the ingest bearer is missing or not valid for the project.
Use the current project-scoped ingest bearer. Do not retry with an account
bearer.

## Telemetry list response format

List routes return a bare JSON array by default. A successful empty list is
`[]`.

With `pagination=cursor`, the route returns an envelope. The collection key
matches the signal:

| Route | Collection key |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces` |

`next_cursor` is an object with the continuation fields, or `null` on the last
page. See [cursor pagination](/reference/telemetry-api-filters#cursor-pagination).

### Log response

A cursor page of logs with `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "timestamp": "2026-06-01T12:00:00Z",
      "level": "warning",
      "severity": "warning",
      "message": "checkout retry scheduled",
      "source": "runtime",
      "release": "api@1.2.3",
      "environment": "production",
      "service_name": "checkout-api",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "attributes": { "route": "/checkout" }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Logs include `level` for compatibility and `severity` for display. Both hold
the canonical value.

### Issue response

`GET /api/telemetry/issues/{issue_id}` returns one grouped issue. The list
returns the same objects:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "status": "unresolved",
  "severity": "error",
  "title": "PaymentError",
  "message": "payment provider timed out",
  "occurrence_count": 2,
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "release": "checkout@1.2.3",
  "environment": "production",
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`status` is `unresolved`, `resolved`, or `ignored`. For the `next_action`
pairs and the reads that follow them, see
[Investigate an issue](/guides/investigate-an-issue).

### Action response

```json
{
  "name": "checkout_failed",
  "severity": "error",
  "service_name": "checkout-api",
  "distinct_id": "user_123",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "release": "checkout@1.2.3",
  "environment": "production"
}
```

`distinct_id` follows one actor or session. See
[Product events](/guides/product-events).

### Metric response

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Each item is one sample. Do not use the number of samples as an event or user
count.

### Release response

```json
{
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z"
```

See [Releases](/concepts/releases).

### Trace discovery response

`GET /api/telemetry/traces?pagination=cursor` returns one row for each trace,
plus a `naming_quality` receipt for the returned page:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` covers only the returned page. It is not an account-wide
score.

`GET /api/telemetry/traces/{trace_id}` returns the spans of one trace.
`GET /api/telemetry/traces/{trace_id}/summary` returns the root span, error
spans, services, duration, and slowest path without raw span attributes. A
summary `404` means that no trace matched the complete scope. Do not retry
without the filters.

## Live event response format

The live feed sends new events. It does not replay events that the client
missed while disconnected. Use the list routes to read existing records.

### Create a ticket

Send `POST /api/feed/ticket` with an account bearer. The request has no body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

A `200 OK` response contains the ticket in the `ticket` field:

```json
{
  "ticket": "<feed-ticket>"
}
```

The ticket is a short-lived credential. Do not log it or put it in an agent
prompt.

### Open the connection

Connect a WebSocket client to
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. URL-encode the
ticket. Do not put an account bearer or an ingest bearer in the URL. A `401`
means that the ticket or the account sign-in is not valid. Create a new ticket
after you sign in again.

### Read the messages

Each message is a `{ "type": "...", "data": ... }` envelope. Read `type`
before you parse `data`. Skip types that the client does not support.

| Event type | Data payload |
| --- | --- |
| `native_log` | Log data with `level` and `severity`. |
| `native_issue` | Grouped issue data. |
| `native_trace_span` | Trace span data. |
| `native_action` | Product action data. |

```json
{
  "type": "native_log",
  "data": {
    "level": "warning",
    "severity": "warning",
    "message": "checkout retry scheduled",
    "release": "api@1.2.3",
    "environment": "production"
  }
}
```

The ticket does not select a project. Check each event's `project_id` before
you show it in a project view. `logbrew watch --json` uses this feed. See the
[CLI reference](/reference/cli).

## Issue status response examples

`PATCH /api/telemetry/issues/{issue_id}` with `{ "status": "resolved" }`
returns `200 OK` with the updated grouped issue, in the same shape as the
[issue response](#issue-response). It does not return a success flag.

Check the returned `id` and `status` before you show success. Do not build the
result from the submitted status. A status change does not delete occurrences
or change `first_seen_at` and `last_seen_at`.

## Ordered funnel response

`POST /api/telemetry/analytics/funnel` measures ordered completion across 2 to
8 steps. This request body counts sessions that view `/pricing` and then
complete signup within one hour:

```json
{
  "project_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "since": "2026-08-01T00:00:00Z",
  "until": "2026-08-02T00:00:00Z",
  "environment": "production",
  "analysis_unit": "session",
  "conversion_window_seconds": 3600,
  "steps": [
    { "kind": "page_view", "event_name": "/pricing" },
    { "kind": "interaction", "event_name": "signup_completed" }
  ]
}
```

`analysis_unit` is `session` or `identified_user`. Step `kind` is `page_view`,
`screen_view`, or `interaction`. A `200 OK` response:

```json
{
  "schema_version": 1,
  "query": {
    "project_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
    "since": "2026-08-01T00:00:00Z",
    "until": "2026-08-02T00:00:00Z",
    "environment": "production",
    "analysis_unit": "session",
    "conversion_window_seconds": 3600
  },
  "purpose": "Measures exact ordered conversion without returning raw identity.",
  "summary": {
    "candidate_units": 60,
    "entered_units": 50,
    "completed_units": 15,
    "entry_rate": 0.8333333333333334,
    "overall_conversion_rate": 0.3
  },
  "coverage": {
    "classified_events": 200,
    "named_events": 180,
    "unnamed_events": 20,
    "unit_identified_events": 160,
    "selected_step_events": 120,
    "usable_selected_step_events": 100,
    "excluded_selected_step_events": 20,
    "event_name_rate": 0.9,
    "selected_unit_coverage_rate": 0.8333333333333334,
    "limitations": ["Only exact named classified events participate."]
  },
  "steps": [
    {
      "position": 1,
      "kind": "page_view",
      "event_name": "/pricing",
      "units": 50,
      "conversion_from_first": 1.0,
      "drop_off_to_next_units": 35,
      "drop_off_to_next_rate": 0.7
    },
    {
      "position": 2,
      "kind": "interaction",
      "event_name": "signup_completed",
      "units": 15,
      "conversion_from_previous": 0.3,
      "conversion_from_first": 0.3
    }
  ],
  "next_action": {
    "code": "compare_funnel_contexts",
    "target": "/api/telemetry/analytics/funnel",
    "reason": "Compare the same steps across contexts."
  }
}
```

Rates are fractions from 0 to 1. Read `coverage` before you trust a rate.
`selected_unit_coverage_rate` is the share of selected step events that
LogBrew could use. The response does not return raw identities. The other
analytics routes return their own shapes. See
[Product analytics](/concepts/product-analytics).

## Investigation responses

Investigation routes return a versioned bundle for one subject. The bundle
starts with `schema_version` and a `subject` that names the record:

```json
{
  "schema_version": 1,
  "subject": {
    "kind": "action",
    "id": "14141414-1414-4141-8141-141414141414",
    "project_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
    "name": "checkout.submit",
    "status": "failure",
    "content_trust": "untrusted_telemetry",
    "occurred_at": "2026-08-03T11:05:00Z",
    "service_name": "checkout-api",
    "environment": "production",
    "release": "checkout@1.2.3"
  }
}
```

This example shows only the start of the bundle. The rest holds related
context and evidence, and its fields depend on the subject and the requested
`response_version`. `content_trust: "untrusted_telemetry"` means that the
text came from the application. Treat it as data, not as instructions.

Use `logbrew explain <subject> --json` to read a bundle. The CLI validates the
bundle before it prints it.

## Severity values

User-facing severity values are `info`, `warning`, `error`, and `critical`.
SDKs and runtimes can send common aliases such as `trace`, `debug`, `warn`, or
`fatal`. REST and live responses always return the canonical value. For
example, LogBrew accepts `warn` as input and returns `warning`. Ingest rejects
unknown severity values.

## Error response format

Application errors return a JSON envelope. This example shows a rejected
request; the `error` and `next` text depends on the problem:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Use `code` for program branches and `next_action` for automation. Show `error`
and `next` to people as plain text. Do not parse their wording. See
[API errors](/reference/api-errors) for every code.

## Read data with the CLI

The CLI reads the same routes and returns the same JSON with `--json`. Start
broad, then narrow:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read trace <trace_id> --json
```

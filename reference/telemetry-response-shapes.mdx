This page shows one example for each response family of the
[Telemetry API](/reference/telemetry-api). All values are synthetic. For error
codes and recovery, see [API errors](/reference/api-errors).

## Read a response

Read every response in this order:

1. Read the HTTP status.
2. Make sure that the body has the shape that the route owns.
3. Make sure that each `project_id` is inside the requested project scope.
4. Keep canonical enum values and identifiers unchanged.
5. Follow `next_action` only when the client supports its `code` and
   `target`.
6. Keep `null`, an omitted field, and an empty list as different states.

A `200 OK` can contain an empty list. An empty log list means that no log
matched the request. It does not mean that issues, traces, or actions are also
empty. Do not join signals because their timestamps are close. Follow a trace
only when the response contains its exact `trace_id`.

A `404` and an empty list are different results. A list route returns `[]`
when no record matches. A detail route returns `404` with `code: not_found`
when it cannot find a readable record. Neither result proves that ingestion
failed.

## What to send

Responses are only as useful as the telemetry you send. Send these values on
every envelope or SDK setup:

- `release` and `environment`.
- Stable names for services, actions, and metrics.
- Trace context when logs, spans, actions, and issues belong to the same
  request.
- Canonical severity values: `info`, `warning`, `error`, and `critical`.
- Attributes that help debugging, without secrets or unnecessary personal data.

See [Send SDK telemetry](/guides/sdk-ingestion) and
[Safe capture](/guides/safe-capture).

## Ingestion response

Public SDKs read the `POST /v1/events` response for you. Application code does
not have to handle it.

### SDK batch response

A successful SDK batch returns `200 OK` with the accepted counts for each
stream:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Field | Meaning |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Events that LogBrew accepted from this batch. |
| `already_accepted` | Events whose ID LogBrew accepted earlier. LogBrew does not store them again. |
| `context_updated` | `true` when the batch updated the release or environment context. |

The counts cover only this batch. A retry of a batch that LogBrew already
accepted returns `0` for each stream and the number of events in
`already_accepted`. Keep the original event IDs when you retry.

### Native envelope response

`POST /api/telemetry/ingest` returns `200 OK` with accepted item counts for
each stream:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

The native response has no `metrics` or `context_updated` field. Do not add
them. `already_accepted` counts items whose `id` LogBrew accepted earlier for
the project. See the [direct native envelope](/guides/sdk-ingestion#required-envelope-fields).

### Ingestion errors

A `401` with `code: ingest_key_invalid` means that the ingest bearer is
revoked, expired, or not valid for the project. On `POST /v1/events`, a
missing bearer or a bearer that is not an ingest key returns `401` with
`code: unauthorized`. Use the current project-scoped ingest bearer. Do not
retry with an account bearer.

A rejected SDK batch returns `422` with `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Other `error` values include `SDK event batch requires at least one event` and
`SDK event type is not supported by this ingest route`. Check the SDK version
and the transport configuration. Do not send an empty batch. Do not change
event types or IDs only to make a batch pass validation.

A request with a method other than `POST` returns `405` with
`code: method_not_allowed`. An unreadable JSON body returns `code: invalid_json`.

## Telemetry list response format

List routes return a bare JSON array by default. A successful empty list is
`[]`.

With `pagination=cursor`, the route returns an envelope. The collection key
matches the signal:

| Route | Collection key |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, with a top-level `issue_id` |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, with a top-level `naming_quality` |

`next_cursor` is an object with the continuation fields, or `null` on the last
page. Rows are newest first. See [cursor pagination](/reference/telemetry-api-filters#cursor-pagination).

### Log response

A cursor page of logs with `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Logs include `level` for compatibility and `severity` for display. Both hold
the canonical value. `triage` holds the result of a severity rule. See
[severity rule responses](#severity-rule-responses).

`trace_id` and `span_id` are `null` when the log has no trace link. Then
`next_action` is `inspect_related_logs` with target `telemetry_logs`. Logs,
issues, and actions use the same 2 `next_action` pairs.

`GET /api/logs/{log_id}` returns one log in the same shape.

### Issue response

`GET /api/telemetry/issues/{issue_id}` returns one grouped issue. The list
returns the same objects. This example uses the default response version 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

In version 1, `status` is `unresolved`, `resolved`, or `ignored`. For an
archived issue, `triage.ignored` is `true`. For the `next_action` pairs and
the reads that follow them, see
[Investigate an issue](/guides/investigate-an-issue).

`first_seen_at` and `last_seen_at` are the times of the first and the most
recent occurrence. They do not change when the status changes.

Some fields appear only when LogBrew has the data:

| Field | When it appears |
| --- | --- |
| `span_id` | The issue has a span link. Otherwise the field is omitted. |
| `diagnostics` | The latest occurrence has an exception type or breadcrumbs. See [issue occurrence history](#issue-occurrence-history). |
| `symbolication` | Only on `GET /api/telemetry/issues/{issue_id}`, when the issue has a release-artifact identity. See [Source maps](/guides/source-maps). |

`symbolication.status` is `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved`, or `unavailable`. The list,
status changes, and rule changes do not return `symbolication`.

With `response_version=2`, the issue has the same fields, and these changes:

| Field | Version 2 value |
| --- | --- |
| `status` | `unresolved`, `resolved`, or `archived`. Version 1 shows `archived` as `ignored`. |
| `priority` | `high`, `medium`, or `low`. |
| `priority_source` | `manual` when a person set the priority. `derived` when the priority follows the effective severity. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

This example shows only some fields. A derived priority is `high` for `error`
and `critical`, `medium` for `warning`, and `low` for `info`. It uses
`triage.effective_severity`, so an issue severity rule can change it.

With `response_version=3`, the issue has all version 2 fields and `assignee`.
`assignee` is `null` when the issue has no assignee:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Field | Meaning |
| --- | --- |
| `assignee.user_id` | User ID of the assignee. Send it as `assignee` in a filter or a change. |
| `assignee.name` | Name of the assignee, or `null` when the account has no name. |
| `assignee.email` | Email address of the assignee. |

An issue shows no assignee when the assigned member cannot read the project
anymore. The CLI requests version 3.

Any other `response_version` returns `422` with `code: validation_failed`. A
cursor page uses the same version for every issue in `issues`.

### Assignee list response

`GET /api/telemetry/issues/assignees?project_id=<project_id>` returns every
account that can be assigned issues in the project:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

If the account cannot read the project, the route returns `404` with
`code: not_found`.

### Action response

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` follows one actor or session. Treat `distinct_id` and
`session_id` as opaque identifiers. `session_id` and `trace_id` are `null`
when they are missing. `span_id` is omitted when it is missing. An action has
no severity. See [Product events](/guides/product-events).

### Metric response

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Each item is one sample. Do not use the number of samples as an event or user
count. `unit`, `temporality`, `trace_id`, and `span_id` are `null` when they
are missing. A `null` value is not zero.

### Release response

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

One row covers one project, release, environment, and service. Its counts
describe only that row.

`trace_health.status` is `unknown` when the row has no traces,
`no_errors_observed`, or `errors_observed`. `error_rate_basis_points` is the
share of traces with an error span, from `0` to `10000`. It is not an error
rate for all requests.

`next_action` points to the first signal type that has data, in this order:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

See [Releases](/concepts/releases).

### Trace discovery response

`GET /api/telemetry/traces?pagination=cursor` returns one row for each trace,
plus a `naming_quality` receipt for the returned page:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` covers only the returned page. It is not an account-wide
score. `truncated: true` means that another page exists. When the page has a
generic name, an unmatched route, or a generic operation, `next_action` is
`improve_trace_naming` with target `sdk_configuration`. Without
`pagination=cursor`, the route returns a bare array of traces and no
`naming_quality`.

`next_cursor` holds `time` and `trace_id`. Send them as `cursor_time` and
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` returns the spans of one trace.
`GET /api/telemetry/traces/{trace_id}/summary` returns the root span, error
spans, services, duration, and slowest path without raw span attributes. A
summary `404` means that no trace matched the complete scope. Do not retry
without the filters. See [trace spans and summary responses](#trace-spans-and-summary-responses).

### Empty lists and missing records

A list read can have no matches. A detail read has a different contract:

| Request | Success | No readable record |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` with one [log](#log-response) | `404` with `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` with one [issue](#issue-response) | `404` with `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` with occurrences | `404` with `code: not_found` on the first page |
| `GET /api/telemetry/traces/{trace_id}` | `200` with spans | `200` with `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` with one summary | `404` with `code: not_found` |

A missing log returns this `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

A missing issue uses `"error": "issue not found"`. A missing trace summary uses
`"error": "trace not found"`. An unknown ID and an ID that the account cannot
read return the same response.

A list with one `project_id` that the account cannot read returns `200` with
an empty list. Check the project ID before you report that no data exists.

### Rejected project selections

The log, issue, action, metric, release, and trace lists accept one project
with `project_id` or 2 to 50 projects with `project_ids`. The log attribute
catalog accepts the same selectors. Issue occurrence history does not accept
them.

A request with both `project_id` and `project_ids` returns `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` with an invalid UUID, a repeated ID, or fewer than 2 or more than
50 IDs also returns `422` with `code: validation_failed`.

If the account cannot read one project in a `project_ids` set, the complete
request returns `404`. It does not return the other projects as a partial
result:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Show the error, not an empty list or a zero count. Read the project list
again. Do not remove a project silently, and do not retry across all
projects. A delegated credential, such as an MCP grant, returns `403` with
`code: forbidden` for a project outside its grant. See
[project scope](/reference/telemetry-api-filters#project-scope).

### Cursor errors

Logs, issues, actions, metrics, and issue occurrences use `cursor_time` and
`cursor_id`. A rejected cursor returns `422` with `code: validation_failed`.
These errors do not mean that the list is empty.

| Request | `error` |
| --- | --- |
| `pagination=cursor` with only 1 of the 2 cursor fields | `cursor_time and cursor_id must be sent together` |
| `cursor_time` that is not an RFC3339 timestamp | `cursor_time must be an RFC3339 timestamp` |
| Cursor fields without `pagination=cursor`, or another `pagination` value | `pagination must be cursor when cursor pagination is requested` |

For example:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Copy the complete `next_cursor` from the previous page. Do not replace
`cursor_time` with the current time. If you lost the cursor, start again with
`pagination=cursor` and the original filters. An unknown query key or a value
of the wrong type returns `422` with `"error": "invalid query parameters"`.

### Release cursor responses

A release cursor has 5 fields. A successful request with no matches returns
`200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

When `next_cursor` is not `null`, send all 5 values on the next request:

| `next_cursor` field | Query parameter |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` marks a position. It does not replace `project_id` or
`project_ids`. Keep the original project and filter parameters. URL-encode
each value.

With `pagination=cursor`, a partial cursor or a blank release, environment,
or service value returns `422` with
`"error": "all release cursor fields must be sent together"`. An invalid
`cursor_time` and a missing `pagination=cursor` return the same errors as the
[other cursors](#cursor-errors).

### Trace discovery errors

These errors apply to `GET /api/telemetry/traces`. Each returns `422` with
`code: validation_failed`. A rejected request is not an empty result.

| Request | `error` |
| --- | --- |
| `status` other than `error` or `ok` | `trace status must be error or ok` |
| `min_duration_ms` below `0` | `minimum trace duration must not be negative` |
| Only 1 cursor field, or a blank `cursor_trace_id` | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` that is not an RFC3339 timestamp | `cursor_time must be an RFC3339 timestamp` |
| Cursor fields without `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

To include both trace states, omit `status`. For the next page, copy
`next_cursor.time` to `cursor_time` and `next_cursor.trace_id` to
`cursor_trace_id`. Do not send `cursor_id` for a trace page. See
[trace filters](/reference/telemetry-api-filters#trace-filters).

### Issue occurrence history

`GET /api/telemetry/issues/{issue_id}/events` reads the occurrences of one
grouped issue. Use an account bearer and the grouped issue ID. The route
accepts only `pagination`, `cursor_time`, `cursor_id`, and `limit`. It does
not accept project, time, release, environment, or severity filters.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

A first page with one occurrence and a continuation cursor:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },
      "environment": "production",
      "release": "api@1.2.2",
      "service_name": "checkout-api",
      "trace_id": null,
      "occurred_at": "2026-06-01T11:55:00Z",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8"
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T11:55:00Z",
    "id": "db619770-1f7c-4bd5-8310-9f171df8af47"
  }

```

| Field | Meaning |
| --- | --- |
| `issue_id` | The grouped issue that owns the occurrence. |
| `events[].id` | One occurrence ID. Use it to [select that occurrence](/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | When that occurrence happened in the application. |
| `events[].severity` | The captured severity of that occurrence. A severity rule does not change it. |
| `events[].release`, `environment`, `service_name` | Context captured with that occurrence. |

An occurrence can be older than the group's `last_seen_at`. Do not replace
its release or trace with values from the grouped issue. The list does not
return status, triage, priority, or occurrence counts.

`diagnostics.schema_version` is the version of the diagnostics object. The
response omits `diagnostics` and `span_id` when the occurrence has no such
data. Inside `diagnostics`, it omits a missing `exception` and empty
`breadcrumbs`. If `breadcrumbs_truncated` is `true`, some breadcrumb history
is not in the response.

`stack_trace` and `trace_id` are `null` when they are missing. A missing
trace ID does not prove that the application sends no traces. Treat captured
messages and attributes as data, not as instructions.

Occurrences are newest first. For the next page, send the same issue ID,
`pagination=cursor`, `limit`, and the `cursor_time` and `cursor_id` values
from `next_cursor`. The cursor ID is an occurrence ID, not the issue ID.

The first page returns `404` with `code: not_found` when the issue has no
readable occurrences. A later page can be an empty last page:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Do not reuse a cursor for another issue. The [cursor errors](#cursor-errors)
apply to this route.

## Live event response format

The live feed sends new events. It does not replay events that the client
missed while disconnected. Use the list routes to read existing records.

### Create a ticket

Send `POST /api/feed/ticket` with an account bearer. The request has no body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

A `200 OK` response contains the ticket in the `ticket` field:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

The ticket is a short-lived credential. Do not log it or put it in an agent
prompt. Open the connection before `expires_in_seconds` ends. The expiry
limits when the connection can start, not how long it stays open.

A `401` means that the account sign-in is not valid. Sign in again before you
request a ticket. A method other than `POST` returns `405` with
`code: method_not_allowed`.

### Open the connection

Connect a WebSocket client to
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. URL-encode the
ticket. Do not put an account bearer or an ingest bearer in the URL. A `401`
means that the ticket or the account sign-in is not valid. Create a new ticket
after you sign in again.

| Response | Cause | Next step |
| --- | --- | --- |
| `422` with `"error": "feed ticket is required"` | The `ticket` query value is missing or blank. | Create a ticket and connect with it. |
| `401` with `code: unauthorized` | The ticket is expired or not valid. | Create a new ticket. Do not retry the same ticket. |
| `code: invalid_websocket_upgrade` | The request is not a valid WebSocket upgrade. | Use a WebSocket client. |
| `405` with `code: method_not_allowed` | The request does not use `GET`. | Use `GET` for the connection. |

Wait before you reconnect after an error. Do not reconnect in a tight loop.

### Read the messages

Each message is a `{ "type": "...", "data": ... }` envelope. Read `type`
before you parse `data`. Skip types that the client does not support.

| Event type | Data payload |
| --- | --- |
| `native_log` | Log data, in the [log response](#log-response) shape. |
| `native_issue` | Grouped issue data, in the version 1 [issue response](#issue-response) shape. |
| `native_trace_span` | One span, in the [span list](#span-list) item shape. |
| `native_action` | Product action data, in the [action response](#action-response) shape. |
| `project_created`, `project_updated`, `project_catalog_changed` | Project data. Read the project list again when it changes. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Account usage, in the [account usage](/reference/account-api#account-usage) shape. |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

A `native_issue` event uses the issue response version 1: an archived issue
shows `ignored`, and the event has no priority. Metrics and releases are not
live event types. Read them with their list routes. The ticket does not
select a project. Check each event's `project_id` before
you show it in a project view. `logbrew watch --json` uses this feed. See the
[CLI reference](/reference/cli).

### Handle a closed connection

| Close code | Reason | Next step |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Wait, then reconnect with a new ticket. Read the list routes again to get the records that you missed. |
| `1008` | `live feed access changed; sign in again` | Stop reconnecting. Sign in again before you create a new ticket. |

Other disconnects can have no LogBrew reason. After you reconnect, read the
list routes again and match records by ID.

## Issue status response examples

`PATCH /api/telemetry/issues/{issue_id}` with `{ "status": "resolved" }`
returns `200 OK` with the updated grouped issue, in the same shape as the
[issue response](#issue-response). The `response_version` query key selects
the version. It does not return a success flag.

The body sets 1 or more of `status`, `priority`, and `assignee`. `status`
accepts `unresolved`, `resolved`, or `archived`. `ignored` is an older name
for `archived`. See [Update one issue](/reference/telemetry-api#update-one-issue).

Check the returned `id`, `status`, and `priority` before you show success. Do
not build the result from the submitted values. A status change does not delete
occurrences or change `first_seen_at` and `last_seen_at`. It does not change
`severity` or a severity rule.

A rejected change returns `422` with `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Result | Cause |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | The body has none of the 3 fields. |
| `422`, `issue priority must be high, medium, or low` | The priority value is not supported. |
| `422`, `issue assignee must be me, none, or a user ID` | The assignee value is not supported. |
| `422`, `issue assignee cannot read this project` | The assignee has no access to the project. LogBrew changes nothing. |
| `403` with `code: forbidden` | The account cannot manage issues in the project. |
| `404` with `code: not_found` | The account cannot read the issue, or the issue does not exist. |

A field that already has the requested value does not change. After a timeout
or a lost response, send the same request again, or read the issue first. Do
not send a different change before you read the current state. See
[Writes](/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` returns `200 OK` with 1 result for each
requested issue ID, in the request order. Each found issue uses the version 3
shape. A `not_found` result has `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

This example shows only some issue fields. `outcome` is `updated`,
`unchanged`, or `not_found`. A repeated request returns `unchanged` and
changes nothing. See
[Update issues in bulk](/reference/telemetry-api#update-issues-in-bulk).

A bulk request fails as a whole in these cases:

| Result | Cause |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | The list is empty or has more than 100 IDs. |
| `422`, `issue_ids must not contain duplicates` | An ID occurs more than once. |
| `422` with `code: invalid_json` | The body has an unknown field. |
| `403` with `code: forbidden` | The account cannot manage issues in the project. |
| `404`, `project not found` | The account cannot read the project. |

Investigation routes return a versioned bundle for one subject. The bundle
starts with `schema_version` and a `subject` that names the record:

```json
{
  "schema_version": 1,
  "subject": {
    "kind": "action",
    "id": "14141414-1414-4141-8141-141414141414",
    "project_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
    "name": "checkout.submit",
```

## Severity values

User-facing severity values are `info`, `warning`, `error`, and `critical`.
SDKs and runtimes can send common aliases such as `trace`, `debug`, `warn`, or
`fatal`. REST and live responses always return the canonical value. For
example, LogBrew accepts `warn` as input and returns `warning`. Ingest rejects
unknown severity values.

| Alias | Canonical value |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## Severity rule responses

A severity rule changes how LogBrew shows a log or an issue. It does not
change the severity that the application captured. Logs and issues return a
`triage` object:

| Field | Meaning |
| --- | --- |
| `effective_severity` | The severity to show. Without a rule, it equals `severity`. |
| `ignored` | `true` when a log rule ignores the log, or when the issue is archived. |
| `rule_applied` | `true` when a severity rule or the ignored state applies. `false` is the default, not missing data. |

Use `triage.effective_severity` for display. Keep `severity` as the captured
value. By default, the log list omits ignored logs. Send `status=ignored` or
`status=all` on `GET /api/logs` to include them.

The account must have permission to manage issues in the project. Read
access is not enough. Without it, a rule change returns `403` with
`code: forbidden`.

### Change a log rule

`PUT /api/logs/{log_id}/triage-rule` sets the rule for the log and for later
logs with the same signature. The body needs both `severity` and `ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

A `200 OK` response contains the complete [log](#log-response). Its
`severity` stays `warning`. Its `triage` shows the rule:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

This excerpt shows only the changed fields. `severity` in the request is
`source`, `info`, `warning`, `error`, or `critical`. `source` restores the
captured severity. It does not make an ignored log active. To show the log
again, send `"ignored": false`.

### Change an issue rule

`PUT /api/telemetry/issues/{issue_id}/triage-rule` sets the displayed severity
of a grouped issue and its later occurrences. The body accepts only
`severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

A `200 OK` response contains the complete [issue](#issue-response) in version
1. The captured `severity` and `status` do not change:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

This excerpt shows only some fields. A rule does not resolve, archive, or
reopen an issue. Use the [status change](#issue-status-response-examples) for
that. A derived priority follows the new effective severity. Read the issue
with `response_version=2` or `3` to see it.

An unsupported severity returns `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

An unknown body field, such as `status` on an issue rule, returns `422` with
`code: invalid_json`. A missing or unreadable log or issue returns `404` with
`code: not_found`. If the response is lost, read the log or issue again
before you send the rule again.

## Error response format

Application errors return a JSON envelope. This example shows a rejected
request; the `error` and `next` text depends on the problem:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Use `code` for program branches and `next_action` for automation. Show `error`
and `next` to people as plain text. Do not parse their wording. Some errors
add fields, such as `limit`, `reset_at`, or `retry_after_seconds`. A response
without a JSON body has no LogBrew `code`. See
[API errors](/reference/api-errors) for every code.

## Read data with the CLI

The CLI reads the same routes and returns the same JSON with `--json`. Start
broad, then narrow:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Add `--pagination cursor` to get the cursor envelope. The CLI requests issue
response version 3. See [Read the next page](/reference/cli#read-the-next-page)
and [Live watch](/reference/cli#live-watch).

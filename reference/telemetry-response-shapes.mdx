This page shows one example for each response family of the
[Telemetry API](/reference/telemetry-api). All values are synthetic. For error
codes and recovery, see [API errors](/reference/api-errors).

## Read a response

Read every response in this order:

1. Read the HTTP status.
2. Make sure that the body has the shape that the route owns.
3. Make sure that each `project_id` is inside the requested project scope.
4. Keep canonical enum values and identifiers unchanged.
5. Follow `next_action` only when the client supports its `code` and
   `target`.
6. Keep `null`, an omitted field, and an empty list as different states.

A `200 OK` can contain an empty list. An empty log list means that no log
matched the request. It does not mean that issues, traces, or actions are also
empty. Do not join signals because their timestamps are close. Follow a trace
only when the response contains its exact `trace_id`.

A `404` and an empty list are different results. A list route returns `[]`
when no record matches. A detail route returns `404` with `code: not_found`
when it cannot find a readable record. Neither result proves that ingestion
failed.

## What to send

Responses are only as useful as the telemetry you send. Send these values on
every envelope or SDK setup:

- `release` and `environment`.
- Stable names for services, actions, and metrics.
- Trace context when logs, spans, actions, and issues belong to the same
  request.
- Canonical severity values: `info`, `warning`, `error`, and `critical`.
- Attributes that help debugging, without secrets or unnecessary personal data.

See [Send SDK telemetry](/guides/sdk-ingestion) and
[Safe capture](/guides/safe-capture).

## Ingestion response

Public SDKs read the `POST /v1/events` response for you. Application code does
not have to handle it.

### SDK batch response

A successful SDK batch returns `200 OK` with the accepted counts for each
stream:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Field | Meaning |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Events that LogBrew accepted from this batch. |
| `already_accepted` | Events whose ID LogBrew accepted earlier. LogBrew does not store them again. |
| `context_updated` | `true` when the batch updated the release or environment context. |

The counts cover only this batch. A retry of a batch that LogBrew already
accepted returns `0` for each stream and the number of events in
`already_accepted`. Keep the original event IDs when you retry.

### Native envelope response

`POST /api/telemetry/ingest` returns `200 OK` with accepted item counts for
each stream:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

The native response has no `metrics` or `context_updated` field. Do not add
them. `already_accepted` counts items whose `id` LogBrew accepted earlier for
the project. See the [direct native envelope](/guides/sdk-ingestion#required-envelope-fields).

### Ingestion errors

A `401` with `code: ingest_key_invalid` means that the ingest bearer is
revoked, expired, or not valid for the project. On `POST /v1/events`, a
missing bearer or a bearer that is not an ingest key returns `401` with
`code: unauthorized`. Use the current project-scoped ingest bearer. Do not
retry with an account bearer.

A rejected SDK batch returns `422` with `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Other `error` values include `SDK event batch requires at least one event` and
`SDK event type is not supported by this ingest route`. Check the SDK version
and the transport configuration. Do not send an empty batch. Do not change
event types or IDs only to make a batch pass validation.

A request with a method other than `POST` returns `405` with
`code: method_not_allowed`. An unreadable JSON body returns `code: invalid_json`.

## Telemetry list response format

List routes return a bare JSON array by default. A successful empty list is
`[]`.

With `pagination=cursor`, the route returns an envelope. The collection key
matches the signal:

| Route | Collection key |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, with a top-level `issue_id` |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, with a top-level `naming_quality` |

`next_cursor` is an object with the continuation fields, or `null` on the last
page. Rows are newest first. See [cursor pagination](/reference/telemetry-api-filters#cursor-pagination).

### Log response

A cursor page of logs with `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Logs include `level` for compatibility and `severity` for display. Both hold
the canonical value. `triage` holds the result of a severity rule. See
[severity rule responses](#severity-rule-responses).

`trace_id` and `span_id` are `null` when the log has no trace link. Then
`next_action` is `inspect_related_logs` with target `telemetry_logs`. Logs,
issues, and actions use the same 2 `next_action` pairs.

`GET /api/logs/{log_id}` returns one log in the same shape.

### Issue response

`GET /api/telemetry/issues/{issue_id}` returns one grouped issue. The list
returns the same objects. This example uses the default response version 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

In version 1, `status` is `unresolved`, `resolved`, or `ignored`. For an
archived issue, `triage.ignored` is `true`. For the `next_action` pairs and
the reads that follow them, see
[Investigate an issue](/guides/investigate-an-issue).

`first_seen_at` and `last_seen_at` are the times of the first and the most
recent occurrence. They do not change when the status changes.

Some fields appear only when LogBrew has the data:

| Field | When it appears |
| --- | --- |
| `span_id` | The issue has a span link. Otherwise the field is omitted. |
| `diagnostics` | The latest occurrence has an exception type or breadcrumbs. See [issue occurrence history](#issue-occurrence-history). |
| `symbolication` | Only on `GET /api/telemetry/issues/{issue_id}`, when the issue has a release-artifact identity. See [Source maps](/guides/source-maps). |

`symbolication.status` is `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved`, or `unavailable`. The list,
status changes, and rule changes do not return `symbolication`.

With `response_version=2`, the issue has the same fields, and these changes:

| Field | Version 2 value |
| --- | --- |
| `status` | `unresolved`, `resolved`, or `archived`. Version 1 shows `archived` as `ignored`. |
| `priority` | `high`, `medium`, or `low`. |
| `priority_source` | `manual` when a person set the priority. `derived` when the priority follows the effective severity. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

This example shows only some fields. A derived priority is `high` for `error`
and `critical`, `medium` for `warning`, and `low` for `info`. It uses
`triage.effective_severity`, so an issue severity rule can change it.

With `response_version=3`, the issue has all version 2 fields and `assignee`.
`assignee` is `null` when the issue has no assignee:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Field | Meaning |
| --- | --- |
| `assignee.user_id` | User ID of the assignee. Send it as `assignee` in a filter or a change. |
| `assignee.name` | Name of the assignee, or `null` when the account has no name. |
| `assignee.email` | Email address of the assignee. |

An issue shows no assignee when the assigned member cannot read the project
anymore.

With `response_version=4`, `assignee` also has `type`. A `user` assignee has
`user_id`, `name`, and `email`, as in version 3. A `team` assignee has
`team_id`, `slug`, and `name`. Version 3 shows a team assignee as `null`. The
CLI requests version 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Any other `response_version` returns `422` with `code: validation_failed`. A
cursor page uses the same version for every issue in `issues`.

### Assignee list response

`GET /api/telemetry/issues/assignees?project_id=<project_id>` returns every
account that can be assigned issues in the project:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Add `response_version=2` to also get `teams`: every team of the project's
organization, with `team_id`, `slug`, and `name`.

If the account cannot read the project, the route returns `404` with
`code: not_found`.

### Action response

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` follows one actor or session. Treat `distinct_id` and
`session_id` as opaque identifiers. `session_id` and `trace_id` are `null`
when they are missing. `span_id` is omitted when it is missing. An action has
no severity. See [Product events](/guides/product-events).

### Metric response

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Each item is one sample. Do not use the number of samples as an event or user
count. `unit`, `temporality`, `trace_id`, and `span_id` are `null` when they
are missing. A `null` value is not zero.

### Release response

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

One row covers one project, release, environment, and service. Its counts
describe only that row.

`trace_health.status` is `unknown` when the row has no traces,
`no_errors_observed`, or `errors_observed`. `error_rate_basis_points` is the
share of traces with an error span, from `0` to `10000`. It is not an error
rate for all requests.

`next_action` points to the first signal type that has data, in this order:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

See [Releases](/concepts/releases).

### Trace discovery response

`GET /api/telemetry/traces?pagination=cursor` returns one row for each trace,
plus a `naming_quality` receipt for the returned page:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` covers only the returned page. It is not an account-wide
score. `truncated: true` means that another page exists. When the page has a
generic name, an unmatched route, or a generic operation, `next_action` is
`improve_trace_naming` with target `sdk_configuration`. Without
`pagination=cursor`, the route returns a bare array of traces and no
`naming_quality`.

`next_cursor` holds `time` and `trace_id`. Send them as `cursor_time` and
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` returns the spans of one trace.
`GET /api/telemetry/traces/{trace_id}/summary` returns the root span, error
spans, services, duration, and slowest path without raw span attributes. A
summary `404` means that no trace matched the complete scope. Do not retry
without the filters. See [trace spans and summary responses](#trace-spans-and-summary-responses).

### Empty lists and missing records

A list read can have no matches. A detail read has a different contract:

| Request | Success | No readable record |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` with one [log](#log-response) | `404` with `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` with one [issue](#issue-response) | `404` with `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` with occurrences | `404` with `code: not_found` on the first page |
| `GET /api/telemetry/traces/{trace_id}` | `200` with spans | `200` with `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` with one summary | `404` with `code: not_found` |

A missing log returns this `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

A missing issue uses `"error": "issue not found"`. A missing trace summary uses
`"error": "trace not found"`. An unknown ID and an ID that the account cannot
read return the same response.

A list with one `project_id` that the account cannot read returns `200` with
an empty list. Check the project ID before you report that no data exists.

### Rejected project selections

The log, issue, action, metric, release, and trace lists accept one project
with `project_id` or 2 to 50 projects with `project_ids`. The log attribute
catalog accepts the same selectors. Issue occurrence history does not accept
them.

A request with both `project_id` and `project_ids` returns `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` with an invalid UUID, a repeated ID, or fewer than 2 or more than
50 IDs also returns `422` with `code: validation_failed`.

If the account cannot read one project in a `project_ids` set, the complete
request returns `404`. It does not return the other projects as a partial
result:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Show the error, not an empty list or a zero count. Read the project list
again. Do not remove a project silently, and do not retry across all
projects. A delegated credential, such as an MCP grant, returns `403` with
`code: forbidden` for a project outside its grant. See
[project scope](/reference/telemetry-api-filters#project-scope).

### Cursor errors

Logs, issues, actions, metrics, and issue occurrences use `cursor_time` and
`cursor_id`. A rejected cursor returns `422` with `code: validation_failed`.
These errors do not mean that the list is empty.

| Request | `error` |
| --- | --- |
| `pagination=cursor` with only 1 of the 2 cursor fields | `cursor_time and cursor_id must be sent together` |
| `cursor_time` that is not an RFC3339 timestamp | `cursor_time must be an RFC3339 timestamp` |
| Cursor fields without `pagination=cursor`, or another `pagination` value | `pagination must be cursor when cursor pagination is requested` |

For example:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Copy the complete `next_cursor` from the previous page. Do not replace
`cursor_time` with the current time. If you lost the cursor, start again with
`pagination=cursor` and the original filters. An unknown query key or a value
of the wrong type returns `422` with `"error": "invalid query parameters"`.

### Release cursor responses

A release cursor has 5 fields. A successful request with no matches returns
`200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

When `next_cursor` is not `null`, send all 5 values on the next request:

| `next_cursor` field | Query parameter |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` marks a position. It does not replace `project_id` or
`project_ids`. Keep the original project and filter parameters. URL-encode
each value.

With `pagination=cursor`, a partial cursor or a blank release, environment,
or service value returns `422` with
`"error": "all release cursor fields must be sent together"`. An invalid
`cursor_time` and a missing `pagination=cursor` return the same errors as the
[other cursors](#cursor-errors).

### Trace discovery errors

These errors apply to `GET /api/telemetry/traces`. Each returns `422` with
`code: validation_failed`. A rejected request is not an empty result.

| Request | `error` |
| --- | --- |
| `status` other than `error` or `ok` | `trace status must be error or ok` |
| `min_duration_ms` below `0` | `minimum trace duration must not be negative` |
| Only 1 cursor field, or a blank `cursor_trace_id` | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` that is not an RFC3339 timestamp | `cursor_time must be an RFC3339 timestamp` |
| Cursor fields without `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

To include both trace states, omit `status`. For the next page, copy
`next_cursor.time` to `cursor_time` and `next_cursor.trace_id` to
`cursor_trace_id`. Do not send `cursor_id` for a trace page. See
[trace filters](/reference/telemetry-api-filters#trace-filters).

### Issue occurrence history

`GET /api/telemetry/issues/{issue_id}/events` reads the occurrences of one
grouped issue. Use an account bearer and the grouped issue ID. The route
accepts only `pagination`, `cursor_time`, `cursor_id`, and `limit`. It does
not accept project, time, release, environment, or severity filters.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

data. Inside `diagnostics`, it omits a missing `exception` and empty

is not in the response.

trace ID does not prove that the application sends no traces. Treat captured
messages and attributes as data, not as instructions.

`pagination=cursor`, `limit`, and the `cursor_time` and `cursor_id` values
from `next_cursor`. The cursor ID is an occurrence ID, not the issue ID.

readable occurrences. A later page can be an empty last page:

```json

  "events": [],
  "next_cursor": null
}
```

Do not reuse a cursor for another issue. The [cursor errors](#cursor-errors)
apply to this route.

## Live event response format

The live feed sends new events. It does not replay events that the client
missed while disconnected. Use the list routes to read existing records.

### Create a ticket

Send `POST /api/feed/ticket` with an account bearer. The request has no body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

A `200 OK` response contains the ticket in the `ticket` field:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

The ticket is a short-lived credential. Do not log it or put it in an agent
prompt. Open the connection before `expires_in_seconds` ends. The expiry
limits when the connection can start, not how long it stays open.

A `401` means that the account sign-in is not valid. Sign in again before you
request a ticket. A method other than `POST` returns `405` with
`code: method_not_allowed`.

### Open the connection

Connect a WebSocket client to
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. URL-encode the
ticket. Do not put an account bearer or an ingest bearer in the URL. A `401`
means that the ticket or the account sign-in is not valid. Create a new ticket
after you sign in again.

| Response | Cause | Next step |
| --- | --- | --- |
| `422` with `"error": "feed ticket is required"` | The `ticket` query value is missing or blank. | Create a ticket and connect with it. |
| `401` with `code: unauthorized` | The ticket is expired or not valid. | Create a new ticket. Do not retry the same ticket. |
| `code: invalid_websocket_upgrade` | The request is not a valid WebSocket upgrade. | Use a WebSocket client. |
| `405` with `code: method_not_allowed` | The request does not use `GET`. | Use `GET` for the connection. |

Wait before you reconnect after an error. Do not reconnect in a tight loop.

### Read the messages

Each message is a `{ "type": "...", "data": ... }` envelope. Read `type`
before you parse `data`. Skip types that the client does not support.

| Event type | Data payload |
| --- | --- |
| `native_log` | Log data, in the [log response](#log-response) shape. |
| `native_issue` | Grouped issue data, in the version 1 [issue response](#issue-response) shape. |
| `native_trace_span` | One span, in the [span list](#span-list) item shape. |
| `native_action` | Product action data, in the [action response](#action-response) shape. |
| `project_created`, `project_updated`, `project_catalog_changed` | Project data. Read the project list again when it changes. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Account usage, in the [account usage](/reference/account-api#account-usage) shape. |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

A `native_issue` event uses the issue response version 1: an archived issue
shows `ignored`, and the event has no priority. Metrics and releases are not
live event types. Read them with their list routes. The ticket does not
select a project. Check each event's `project_id` before
you show it in a project view. `logbrew watch --json` uses this feed. See the
[CLI reference](/reference/cli).

### Handle a closed connection

| Close code | Reason | Next step |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Wait, then reconnect with a new ticket. Read the list routes again to get the records that you missed. |
| `1008` | `live feed access changed; sign in again` | Stop reconnecting. Sign in again before you create a new ticket. |

Other disconnects can have no LogBrew reason. After you reconnect, read the
list routes again and match records by ID.

## Issue status response examples

`PATCH /api/telemetry/issues/{issue_id}` with `{ "status": "resolved" }`
returns `200 OK` with the updated grouped issue, in the same shape as the
[issue response](#issue-response). The `response_version` query key selects
the version. It does not return a success flag.

The body sets 1 or more of `status`, `priority`, and `assignee`. `status`
accepts `unresolved`, `resolved`, or `archived`. `ignored` is an older name
for `archived`. See [Update one issue](/reference/telemetry-api#update-one-issue).

Check the returned `id`, `status`, and `priority` before you show success. Do
not build the result from the submitted values. A status change does not delete
occurrences or change `first_seen_at` and `last_seen_at`. It does not change
`severity` or a severity rule.

A rejected change returns `422` with `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Result | Cause |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | The body has none of the 3 fields. |
| `422`, `issue priority must be high, medium, or low` | The priority value is not supported. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | The assignee value is not supported. |
| `422`, `issue assignee cannot read this project` | The assignee has no access to the project. LogBrew changes nothing. |
| `422`, `issue assignee team is not a team of this project's organization` | The team does not belong to the project's organization. LogBrew changes nothing. |
| `403` with `code: forbidden` | The account cannot manage issues in the project. |
| `404` with `code: not_found` | The account cannot read the issue, or the issue does not exist. |

A field that already has the requested value does not change. After a timeout
or a lost response, send the same request again, or read the issue first. Do
not send a different change before you read the current state. See
[Writes](/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` returns `200 OK` with 1 result for each
requested issue ID, in the request order. Each found issue uses the version 3
shape. A `not_found` result has `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

This example shows only some issue fields. `outcome` is `updated`,
`unchanged`, or `not_found`. A repeated request returns `unchanged` and
changes nothing. See
[Update issues in bulk](/reference/telemetry-api#update-issues-in-bulk).

A bulk request fails as a whole in these cases:

| Result | Cause |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | The list is empty or has more than 100 IDs. |
| `422`, `issue_ids must not contain duplicates` | An ID occurs more than once. |
| `422` with `code: invalid_json` | The body has an unknown field. |
| `403` with `code: forbidden` | The account cannot manage issues in the project. |
| `404`, `project not found` | The account cannot read the project. |

## Analytics request scope

The analytics routes, the metric-series route, and the signal-volume route
read one project and one time range. Every request needs `project_id` and
`since`. `since` accepts a compact duration such as `24h` or `7d`, or an
RFC3339 timestamp. `until` accepts an RFC3339 timestamp and defaults to the
request time. The range includes `since`, excludes `until`, and cannot exceed
31 days.

`service_name`, `release`, and `environment` are optional exact filters. Each
value must have 1 to 256 characters after LogBrew trims spaces. The segment
comparison route puts these filters inside each segment, not at the top level.

If the account cannot read the project, these routes return `200 OK` with
zero counts. They do not return `404`. An empty result does not confirm
project access. Compare `project_id` with the projects that the account can
read. A request through an MCP grant that does not include the project returns
`403` and `forbidden`.

| Route | `response_version` values | Default |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2`, or `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` or `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` or `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` or `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` or `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Not accepted | Schema `1` |
| `POST /api/telemetry/analytics/paths` | Not accepted | Schema `1` |
| `GET /api/telemetry/metrics/series` | Not accepted | Schema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Each response starts with `schema_version`, `query`, and `purpose`. `query`
echoes the effective scope. It omits a filter that you did not send. `purpose`
is plain text that explains what the route answers.

A rate is omitted when its denominator is zero. An omitted rate is not `0`
and is not `null`. Read `coverage` before you trust a rate.

### Shared scope errors

These errors use HTTP `422` and `validation_failed`:

| Cause | `error` |
| --- | --- |
| No `project_id` | `product analytics project_id is required` |
| No `since` | `product analytics since is required` |
| `since` is not a duration or RFC3339 timestamp | `invalid since value` |
| `until` is not an RFC3339 timestamp | `product analytics until must be an RFC3339 timestamp` |
| `since` is not earlier than `until` | `product analytics since must be earlier than until` |
| The range is longer than 31 days | `product analytics range must not exceed 31 days` |
| An empty filter, or a filter longer than 256 characters | `product analytics context filters must be non-empty and at most 256 characters` |

For example, a request without `project_id` returns:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

The metric-series and signal-volume routes use the same scope rules, with
their own `error` text. Their sections below list those errors.

An unknown query key returns `422` with the
[invalid query parameters](/reference/api-errors#invalid-query-parameters)
response. An unknown JSON field, a missing required JSON field, or an
unsupported enum value returns `invalid_json`. See
[Invalid JSON](/reference/api-errors#invalid-json). A request with the wrong
HTTP method returns `405` and `method_not_allowed`. Its `next` text names the
supported method and fields. See
[Unsupported method](/reference/api-errors#unsupported-method).

## Product analytics overview response

`GET /api/telemetry/analytics/overview` shows the activity in one project:
action volume, users, sessions, a time series, top actions, and classified
page views, screen views, and interactions. Use it to find the exact event
names for the other analytics routes.

Send `response_version=3`. Versions 1 and 2 return the same counts, but their
`estimation.method` value is an older token. Version 1 does not check the
subject kind when it counts identified users. Versions 2 and 3 count only

`subject_coverage`.

```bash
  --data-urlencode "top_limit=2" \
```

### Read the overview

The five `subject_coverage` counts add up to the event total of their
section. Only `identified_user_events` counts toward users.
`anonymous_actions` is `summary.actions` minus `identified_actions`.

`series` contains only buckets that have activity. `expected_buckets` is the
number of possible buckets in the range. Do not draw a missing bucket as a
measured zero unless your chart states that rule. Buckets align to UTC
interval boundaries. A range that starts inside a bucket includes that
partial bucket.

Screen views and interactions are also actions. Page views are not. Do not
add `summary.actions` to `classified_activity.summary.events`.

steps, retention selectors, lifecycle selectors, path anchors, and segment
targets. A `true` value in `top_events_truncated` means that lower-volume
names exist. Increase `top_limit` up to 20 to see more.

`analysis_level` is `no_data`, `event_only`, `user_level`, or
`user_and_session`. If the project has no actions and no classified events,
`next_action.code` is `capture_product_activity`. See
[Product analytics](/concepts/product-analytics#use-the-analytics-api).

## Ordered funnel response

`POST /api/telemetry/analytics/funnel` measures ordered completion across 2 to
8 steps. Copy each exact `kind` and `event_name` from
`classified_activity.top_events` in the overview. A similar action name is
not a match. This request body counts sessions that view `/pricing` and then
complete signup within one hour:

```json
{
  "project_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "since": "2026-08-01T00:00:00Z",
  "until": "2026-08-02T00:00:00Z",
  "environment": "production",
  "analysis_unit": "session",
  "conversion_window_seconds": 3600,
  "steps": [
    { "kind": "page_view", "event_name": "/pricing" },
    { "kind": "interaction", "event_name": "signup_completed" }
  ]
}
```

`analysis_unit` is `session` or `identified_user`. The default is `session`.
Step `kind` is `page_view`, `screen_view`, or `interaction`. The funnel route
does not accept `response_version`.

### Read conversion and coverage

`entry_rate` is `entered_units` divided by `candidate_units`: 50 of 60.
`overall_conversion_rate` is `completed_units` divided by `entered_units`:
15 of 50, or 30%. It is not 15 divided by all candidates. These counts do not
explain why units stopped.

Coverage counts events, not sessions. Here, 120 events match a step, and 20
of them have no session ID. The result excludes those 20 events from the
session counts. Do not treat them as 20 failed sessions.

The first step has no `conversion_from_previous`. The last step has no
`drop_off_to_next_units` and no `drop_off_to_next_rate`.

A unit reaches a later step only when the step times strictly increase.
Events with the same timestamp cannot satisfy two consecutive steps. The final
step must occur within `conversion_window_seconds` of the first step.

Session mode counts sessions, not people. Use `identified_user` only for events
that carry an opaque subject ID of kind `user`. That mode can join events from
different sessions inside the conversion window. Keep the same unit and the
same steps when you compare results.

The default `conversion_window_seconds` is 24 hours or the length of the
range, whichever is shorter. The maximum is the range length in whole
seconds, rounded up.

### Empty funnel results

A successful empty response still lists the requested steps with zero
`units`. If there are no candidate units, `summary` omits `entry_rate` and
`overall_conversion_rate`. The route does not return `404` because no events
match.

Read `coverage` and `next_action` to find the cause:

| `next_action.code` | Cause |
| --- | --- |
| `capture_product_activity` | No classified events exist in the scope. |
| `choose_captured_funnel_steps` | No event matches a requested step. |
| `sessionize_product_activity` | Step events exist, but none has a session ID. |
| `identify_product_users` | Step events exist, but none has a subject of kind `user`. |
| `verify_funnel_entry` | No unit entered at step 1. |
| `investigate_funnel_drop_off` | Units entered, but no unit completed every step. |
| `compare_funnel_contexts` | At least one unit completed the funnel. |

`422` and `validation_failed`. Fewer than 2 or more than 8 steps:


A `conversion_window_seconds` of `0`, or a value above the range length:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",

```

An `event_name` that is empty, longer than 256 characters, or contains a
control character returns
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
An `interaction` step must also be a valid action name. Otherwise, the error
is `product analytics interaction event_name must be a bounded stable action name`.

Correct the request before you send it again. Do not remove steps or change
the analysis unit only to get a non-empty result.

## Exact-event and automatic analysis

Retention and lifecycle accept two request shapes. Use `response_version` to
select the shape that answers your question:

| Analysis | `response_version` | Event selectors |
| --- | --- | --- |
| Retention for exact events | `1`, or omitted | Send both `start_event` and `return_event`. |
| Lifecycle for one exact event | `1`, or omitted | Send `event`. |
| Automatic retention or lifecycle | `2` | Send no event selector. |

An exact selector contains `kind` and `event_name`. `kind` is `page_view`,
`screen_view`, or `interaction`. Copy `event_name` from
`classified_activity.top_events`. Do not guess an event name from a button
label.

Both shapes count only users: opaque subject IDs of kind `user`. Anonymous
subjects and events without a usable subject ID are not counted as users.
Responses never return subject IDs.

Fixed intervals are `hour`, `day`, `week`, and `thirty_day`. They are fixed
durations. `thirty_day` is 30 days, not a calendar month. If you omit
`interval`, the API uses `hour` for a range of 48 hours or less, and `day` for
a longer range.

### Exact-event retention request

Send this body to `POST /api/telemetry/analytics/retention`. It asks whether


| `mode` | `return_on` counts a return inside each exact period. `return_on_or_after` counts a return at or after the start of each period. | `return_on` |
| `cohort_mode` | `first_in_range` | `first_in_range` |

Besides the [shared scope errors](#shared-scope-errors), these requests return
`422` and `validation_failed`:

| Cause | `error` |
| --- | --- |
| Version 1 without both selectors, version 2 with a selector, or another version | `product analytics retention activity selection is contradictory` |
| `interval_count` other than `1` to `31` | `product analytics retention interval_count must be between 1 and 31` |
| Cohort buckets times `interval_count` is more than 500 | `product analytics retention interval and interval_count would exceed 500 cohort matrix cells` |

The cell limit uses the range and the periods, not the number of users. A
30-day range with `interval: "hour"` has 720 cohort buckets. With
`interval_count: 1`, that is 720 cells, which is more than 500:

```json
{
  "error": "product analytics retention interval and interval_count would exceed 500 cohort matrix cells",
  "code": "validation_failed",
  "next": "choose a wider interval, a shorter time range, or fewer retention periods",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

To use automatic retention, remove both selectors. Do not change the SDK to
correct this read request.

### Read a metric series

The first point records 10 completed jobs, not 10 samples. `rate_per_second`
divides that change by the 300-second bucket. `last` is the last recorded
change, not the sum. See
[metric aggregation meanings](/concepts/telemetry#read-the-metric-value).

The kind and temporality of a series select its `aggregation.code` and the
statistics in each point. A point omits a statistic that does not apply. A
missing statistic is not zero.

| Kind and temporality | `status` | `aggregation.code` | `value` | Other statistics |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Last sample | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Sum of changes | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | Approximate p95 | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Any kind, `cumulative` | `limited` | `raw_cumulative_last` | Last raw sample | `last`, `min`, `max` |
| Any other pair | `limited` | `raw_last` | Last raw sample | `last`, `min`, `max` |

`limited` is a successful response, not an error. It adds
`aggregation.limitation`, which explains why LogBrew shows only raw values.
`ready` does not prove complete capture.

Read `coverage` before you draw a chart:

- `samples` counts the samples of all matching series, including series that
  the response does not return.
- `series` counts matching series. `returned_series` and `points` count the
  returned data.
- `truncated` is `true` when `series_limit` removed lower-volume series.
- `expected_buckets_per_series` is the number of possible buckets in the range.

Do not add a point for a bucket without samples. Do not insert a zero or copy
the previous value. Each point returns up to 3 `trace_exemplars`. A trace
exemplar links one sample to a trace. It does not explain every sample in the
bucket. If no point has a trace exemplar, `next_action.target` is
`metric_samples`.

### Metric-series scope and errors

`project_id`, `name`, and `since` are required. `name` can have at most 200
characters. `interval` is `auto`, `1m`, `5m`, `15m`, `1h`, `6h`, or `1d`.
The default is `auto`, which selects the smallest interval with at most 300
buckets. An explicit interval cannot need more than 500 buckets.

`group_by` is `none`, `service_name`, `release`, or `environment`. The default
is `none`. Without grouping, different kinds, units, and temporalities stay in
separate series. `series_limit` accepts `1` to `20`. The default is `10`.

An empty result returns `200` with `series: []` and zero `samples`. The
`coverage` object omits `first_seen_at` and `last_seen_at`. This does not
prove that the application never sent the metric. Check the project, the
metric name, and the time range.

Omitting `name` returns `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

One-minute buckets across seven days return `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Other `422` errors are `metric series group_by is not supported`,
`metric series interval is not supported`, and
`metric series_limit must be between 1 and 20`.

### Read paths

`share_of_anchored_sessions` divides the sessions of a path by all four
anchored sessions. The shares are 50% and 25%, not 67% and 33%.
`unrepresented_sessions` counts anchored sessions that no returned path
represents. `paths_truncated: true` means that the result is incomplete.

Coverage counts events, not sessions. Here, five events match the anchor, but
one has no session ID. That event cannot enter a path. Each path returns up to
3 trace exemplars. Use a trace ID from your own response. A trace link does
not show what caused a user action or a failure.

| Field | Meaning |
| --- | --- |
| `following` | Starts at the earliest matching anchor in each session. The anchor has position `0`. Later nodes have positive positions. |
| `preceding` | Ends at the latest matching anchor in each session. Earlier nodes have negative positions. The anchor has position `0`. |
| `depth` | Number of nodes next to the anchor, not counting the anchor. `1` to `8`. The default is `4`. A path can have fewer nodes. |
| `collapse_repeated` | Combines consecutive nodes with the same kind and name. The default is `true`. |
| `path_limit` | Maximum returned paths, ranked by session count. `1` to `20`. The default is `10`. |

Nodes are in time order in both directions. A path is not a full session
replay. LogBrew reads at most 1024 named events per session before it selects
the anchor: the earliest events for `following` and the latest events for
`preceding`. An anchor outside that limit can be omitted.

### Filter the anchor by property

Send up to four `property_filters`, each with one exact `key` and `value`.
Copy the key from the [property catalog](#analytics-property-catalog). The
filters apply only to the anchor, not to the events around it. Values are
case-sensitive. When filters are present, `query` echoes them, and
`coverage.anchor_property_filters` reports:

| Field | Meaning |
| --- | --- |
| `context_events` | Anchor events in scope before the property filters. |
| `property_ready_events` | Anchor events that have every requested key. |
| `missing_property_events` | Anchor events without one or more requested keys. |
| `matching_events` | Anchor events whose values match every filter. |
| `nonmatching_value_events` | Anchor events that have every key but a different value. |
| `property_ready_rate` | `property_ready_events` divided by `context_events`. |
| `match_rate` | `matching_events` divided by `property_ready_events`. |

Missing keys and different values need different fixes. Do not add them
together. The object is omitted when the request has no property filter.

### Empty paths and rejected requests

An empty `paths` array can be a successful `200` response. Read `summary`,
`coverage`, and `next_action`. These codes separate the causes:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity`, and
`narrow_or_move_path_anchor`.

Besides the [shared scope errors](#shared-scope-errors), these requests return
`422` and `validation_failed`:

| Cause | `error` |
| --- | --- |
| `depth` other than `1` to `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` other than `1` to `20` | `product analytics path_limit must be between 1 and 20` |

## Analytics segment comparison

`POST /api/telemetry/analytics/segments/compare` compares how often sessions
or users reach one exact event across 2 to 4 segments in one project. A
segment selects events by service, release, environment, and property values.
The first segment is the baseline.

### Define the comparison

`Content-Type: application/json`. Here, `basic` and `premium` are plan values

`target` and `segments` are required. `analysis_unit` is `session` or
`identified_user`. The default is `session`, which counts sessions, not
people. `interval` accepts the same values as the overview. The default is
`auto`.

Each segment needs a unique `key`, a `label`, and a different filter set:

- `key`: 1 to 32 bytes. Start with a lowercase ASCII letter or a digit. Use
  only lowercase ASCII letters, digits, `_`, and `-`.
- `label`: 1 to 80 characters, without control characters.
- `service_name`, `release`, `environment`: optional. Each value has 1 to 256
  characters, without control characters.
- `property_filters`: 0 to 4 filters. Each key can occur once in a segment.
  An event must match all filters of the segment. Values are case-sensitive,
  1 to 256 characters, and LogBrew trims spaces at the start and end.

A segment without filters selects all classified activity in the project and
time range. Segments can overlap. A different label or key does not make two
identical filter sets valid.

### Read rates and differences

the segment. `reached_units` estimates how many of them reached the target.
`reach_rate` is `reached_units` divided by `eligible_units`. Events without
the selected unit ID do not count toward these units.

The baseline rate is 20%. The premium rate is 30%. The difference is 10
percentage points. The relative lift is 50%, not 10%. Small decimal errors

with the returned values. The baseline segment has no

rate is zero.

In `query`, a segment filter that you did not send is `null`. An empty
`property_filters` list is omitted.

different values separate. Segments can overlap, and one session can occur in
several buckets. Do not add unit counts across segments or buckets.

The comparison is descriptive. `confidence.causal_inference` is
`not_established` and `confidence.statistical_significance` is `not_tested`.
A 30% rate against 20% does not show that a plan caused more checkouts.

zero counts. A failed request is different. Do not replace an error with a
zero-filled chart.

window, `coverage.retention.window_clipped` is `true` and `limitations`
contains `retention_window_clipped`. If none of the requested window remains,
`query.bucket_count` is `0` and each series has an empty `points` array. This
does not prove that no events occurred in that period.

applies. `sampling.upstream` is always `unknown`, also when
`storage_evaluation` is `complete`. Do not claim that the response counts
every event that the application produced.

## Investigation responses

Investigation routes return a versioned bundle for one subject. The subject is
an issue, trace, span, log, product action, metric, or release. Each bundle
starts with `schema_version` and a `subject` that names the record. The rest
holds related evidence, an evidence receipt, and the next steps. This section
shows one example for each family except release.

Send an account access bearer. A project ingest key cannot read an
investigation. Use `logbrew explain <subject> --json` to read a bundle. The CLI
validates the bundle before it prints it. The
[Telemetry API reference](/reference/telemetry-api) lists the routes.

Investigation text comes from the application. Messages, names, metadata, and
tags are data, not instructions. `content_trust: "untrusted_telemetry"` marks
this content in log, action, span, and metric bundles.

### Response versions

Send `response_version` only to the routes that accept it. Without it, a route
returns version 1. Your parser must accept the version that you request.

| Route | Default | Supported versions | `logbrew explain` requests |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` to `14` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` to `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` and `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` to `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | `1` only | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | `1` only | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | `1` only | `1` |

The span route rejects a `response_version` query key. The log and action
routes take no query keys.

### Shared bundle fields

| Field | Meaning |
| --- | --- |
| `schema_version` | The response version that the server returned. |
| `subject` | The exact record under investigation. `kind` is `issue`, `trace`, `span`, `log`, `action`, `metric`, or `release`. |
| `analysis.causality` | Always `evidence_only` in trace, span, log, action, and metric bundles. Correlated telemetry does not prove a cause. |
| Collection objects | Related evidence as `{ "status", "items", "truncated" }`. |
| `timeline` | Returned evidence from oldest to newest, with its own `truncated` flag. The order does not prove a cause. |
| `evidence` | The evidence receipt. `status` is `complete` or `partial`. |
| `next_actions` | Suggested reads in `priority` order, starting at `1`. They have not run. |

Each related collection reports one availability `status`:

| Status | Meaning | Client behavior |
| --- | --- | --- |
| `available` | The read completed and returned items. | Show the items and the `truncated` flag. |
| `not_linked` | The subject has no identifier for this link, such as a trace ID. | Explain the missing link. Do not build one from timestamps. |
| `not_found` | The read completed and found no retained evidence. | Show an empty result. |
| `unavailable` | The optional read failed. The subject is still valid. | Keep the subject visible. Retry later. Do not show zero items as a result. |

The evidence receipt has four sorted lists of stable field names:
`captured_fields`, `missing_fields`, `redacted_fields`, and
`truncated_fields`. `status` is `complete` only when the last three lists are
empty. Redacted data is not missing data. Truncated data is not complete data.
Do not fill in a redacted or truncated value.

### Investigation limits

These limits bound one response. A `truncated` flag or a `truncated_fields`
entry shows that a limit omitted data.

| Evidence | Limit |
| --- | --- |
| Related items in one collection | 20 |
| Retained spans read for one trace | 1,000 |
| Timeline items | 50 for log, action, and span bundles. 100 for trace and metric bundles. |
| Structured attributes, properties, and metadata | 64 scalar values, 4 levels of objects or arrays, 16 items in each array, 512 characters in each string |
| Correlation time window | 5 minutes before and after a log, action, or selected issue occurrence. For a trace or span, 5 minutes before the start and after the end, at most 24 hours. |

Each family section lists its own limits.

### Issue investigation response

Use `GET /api/telemetry/issues/{issue_id}/investigation` to read the evidence
for one occurrence of a grouped issue. The
[issue investigation guide](/guides/investigate-an-issue) shows how to read
the evidence in order. Request version 13:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

The query keys are `response_version`, `selection`, and `occurrence_id`.
`selection` is `recommended`, `first`, or `latest`. The values are
case-sensitive. In versions 2 to 14, an omitted selector uses `recommended`.
Version 1 returns the latest retained occurrence and accepts no selector.
Issue-list filters do not apply to this read.

#### Issue investigation request errors

Use either `selection` or `occurrence_id`. Do not send both, even when they
select the same occurrence:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Cause | Recovery |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | The request has both selectors. | Keep one selector. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | The request has a selector and version 1, or no version. | Send `response_version=13`. Keep the selector. |
| `422` | `issue investigation response_version must be 1 through 14` | The version is out of range. | Send a supported version. |
| `422` | `invalid query parameters` | An unknown key, an invalid UUID, a non-integer version, or an unknown `selection` value. | Fix the [query](/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | The occurrence is not in this group's retained history. | Copy the occurrence ID from this issue's events. Do not use `latest` or `recommended` instead without approval. |
| `404` | `issue not found` | No readable project has this issue. | Check the account and the issue UUID. Do not send an occurrence UUID as the issue ID. |

A missing occurrence does not mean that the issue is missing. A `404` does
not show whether another account can read the issue.

### Span investigation response

read one operation in a trace. Send `project_id`, `environment`, and `release`.

row `id` as the `span_id`.

### Log investigation response

Use `GET /api/logs/{log_id}/investigation` to read one log and its related
evidence. This route has no query keys. Copy the log ID from a log list.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

The read can return evidence outside the filters of the log list. Related
reads use the log's project, environment, and release, and 5 minutes before
and after the log. Nearby logs also use the same service. They do not need a
trace ID. Exact-trace reads need the log's trace ID and can include other
services. The trace summary uses the same trace ID and scope, without the time
window.

### Action investigation response

Use `GET /api/telemetry/actions/{action_id}/investigation` to read one product
action, its reported status, and related evidence. This route has no query
keys. Related reads use the same window and scopes as a log investigation.

`correlations`, `timeline`, and `next_actions` use the log investigation
shapes. Related actions exclude the subject action.

### Metric investigation response

Use `GET /api/telemetry/metrics/investigation` to read one metric name in one
project and time range. The response has the current series, a comparison
with the preceding window of equal length, the latest sample, trace
exemplars, and completed deployments. Version 2 adds the metric description
from the latest retained sample. Version 1 always reports
`description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name`, and `since` are required. `since` is inclusive and
`until` is exclusive. `until` defaults to now. The comparison also reads the
preceding window of equal length.

20 exemplars and 20 deployments.

`none`, `service_name`, `release`, or `environment`. Other values return
`422`.

### Investigation errors

| HTTP | Route | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Action | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, action, issue | `invalid URL path parameters` when the path ID is not a UUID |
| `422` | Issue, trace, span, metric | `invalid query parameters` for an unknown key or a value of the wrong type |

A `404` means that no readable project has the record. Each route also returns
`401` without valid authentication and `405` for a method other than `GET`.
See [API errors](/reference/api-errors) for the
[not-found](/reference/api-errors#resource-not-found),
[path](/reference/api-errors#invalid-path-value),
[authentication](/reference/api-errors#authentication-failure), and
[method](/reference/api-errors#unsupported-method) responses.

An optional evidence read can fail inside a `200 OK` response. The collection
then reports `unavailable`. Do not show it as `not_found` or as zero records.

## Severity values

User-facing severity values are `info`, `warning`, `error`, and `critical`.
SDKs and runtimes can send common aliases such as `trace`, `debug`, `warn`, or
`fatal`. REST and live responses always return the canonical value. For
example, LogBrew accepts `warn` as input and returns `warning`. Ingest rejects
unknown severity values.

| Alias | Canonical value |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## Severity rule responses

A severity rule changes how LogBrew shows a log or an issue. It does not
change the severity that the application captured. Logs and issues return a
`triage` object:

| Field | Meaning |
| --- | --- |
| `effective_severity` | The severity to show. Without a rule, it equals `severity`. |
| `ignored` | `true` when a log rule ignores the log, or when the issue is archived. |
| `rule_applied` | `true` when a severity rule or the ignored state applies. `false` is the default, not missing data. |

Use `triage.effective_severity` for display. Keep `severity` as the captured
value. By default, the log list omits ignored logs. Send `status=ignored` or
`status=all` on `GET /api/logs` to include them.

The account must have permission to manage issues in the project. Read
access is not enough. Without it, a rule change returns `403` with
`code: forbidden`.

### Change a log rule

`PUT /api/logs/{log_id}/triage-rule` sets the rule for the log and for later
logs with the same signature. The body needs both `severity` and `ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

A `200 OK` response contains the complete [log](#log-response). Its
`severity` stays `warning`. Its `triage` shows the rule:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

This excerpt shows only the changed fields. `severity` in the request is
`source`, `info`, `warning`, `error`, or `critical`. `source` restores the
captured severity. It does not make an ignored log active. To show the log
again, send `"ignored": false`.

### Change an issue rule

`PUT /api/telemetry/issues/{issue_id}/triage-rule` sets the displayed severity
of a grouped issue and its later occurrences. The body accepts only
`severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

A `200 OK` response contains the complete [issue](#issue-response) in
version 1. The captured `severity` and `status` do not change:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

This excerpt shows only some fields. A rule does not resolve, archive, or
reopen an issue. Use the [status change](#issue-status-response-examples) for
that. A derived priority follows the new effective severity. Read the issue
with `response_version=2` or `3` to see it.

An unsupported severity returns `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

An unknown body field, such as `status` on an issue rule, returns `422` with
`code: invalid_json`. A missing or unreadable log or issue returns `404` with
`code: not_found`. If the response is lost, read the log or issue again
before you send the rule again.

## Error response format

Application errors return a JSON envelope. This example shows a rejected
request; the `error` and `next` text depends on the problem:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Use `code` for program branches and `next_action` for automation. Show `error`
and `next` to people as plain text. Do not parse their wording. Some errors
add fields, such as `limit`, `reset_at`, or `retry_after_seconds`. A response
without a JSON body has no LogBrew `code`. See
[API errors](/reference/api-errors) for every code.

## Read data with the CLI

The CLI reads the same routes and returns the same JSON with `--json`. Start
broad, then narrow:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Add `--pagination cursor` to get the cursor envelope. The CLI requests issue
response version 4. See [Read the next page](/reference/cli#read-the-next-page)
and [Live watch](/reference/cli#live-watch).

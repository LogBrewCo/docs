The [open-source LogBrew CLI](https://github.com/LogBrewCo/cli) reads
telemetry and manages account data from a terminal. Start with the
[CLI guide](/guides/cli) for installation, login, and common tasks.

## How the CLI works

Use readable text in a terminal. Use `--json` in scripts and coding agents.

Account login is necessary for account reads. Before you start a login, run
`logbrew status --json`. A person must complete browser authorization.
Project ingest keys send telemetry. They cannot replace account login.

Project creation, key creation, issue status, priority, and assignee changes,
deployments, and support updates change account data. Before you run one, make sure that the action and
the target are correct.

Run `logbrew --help` to see all commands. Add `--help` to a command, such as
`logbrew read logs --help`, to see its flags. Run `logbrew help json` for the
JSON rules.

| Command family | Purpose |
| --- | --- |
| `login`, `whoami`, `me`, `logout` | Start login, read the account identity, or close the local session. |
| `status`, `health`, `doctor`, `version`, `examples` | Read access, project readiness, the CLI version, or first-run examples. |
| `setup` | Install the SDK in the current app, write the ingest key, add the init code, and send a test event. With `--json` and without `--yes`, print the setup plan and change no files. |
| `projects` | Read the active project catalog. |
| `projects repositories` | Read connected repositories or discover components in one repository. |
| `projects create`, `projects keys create`, `projects keys revoke` | Create a project, create a project key for an existing project, or revoke a project key. |
| `projects setup` | Record observed setup for an existing project. |
| `projects archive`, `projects delete` | Archive a project, or delete it permanently after confirmation. |
| `usage`, `account usage` | Read usage, limits, quota state, and reset dates. |
| `mcp grants`, `mcp revoke` | List the MCP clients connected to your account by name, or revoke one connection. |
| `read` | Read logs, issues, actions, releases, metrics, traces, or one item. |
| `explain` | Read bounded evidence for an issue, log, action, trace, span, metric, or release. |
| `investigate issue` | Read issue investigation evidence, or verify a candidate deployment. |
| `issues archive`, `issues resolve`, `issues reopen` | Set the status of 1 issue, or of up to 100 issues in one project. |
| `issues priority` | Set the priority of 1 issue, or of up to 100 issues in one project. |
| `issues assign`, `issues unassign` | Set or remove the assignee, an account or a team, of 1 issue, or of up to 100 issues in one project. |
| `issues assignees` | List the accounts and teams that can be assigned issues in one project. |
| `issues owners` | List the suggested owners of 1 issue. |
| `issues ownership` | Read or set the ownership rules and CODEOWNERS file of one project. |
| `issues activity` | Read the change history of 1 issue. |
| `issues rule`, `logs rule` | Set the severity rule of 1 issue or 1 log signature. |
| `inbox` | Read the issues that others assigned to you or your teams, or mark them read. |
| `set issue`, `resolve`, `close`, `ignore`, `reopen` | Set the status of 1 issue. `close` means `resolved`. `ignore` and `ignored` mean `archived`. |
| `deploy` | Record one completed deployment. |
| `debug-artifacts` | Upload Apple or Android native debug files, or look up one image identity. |
| `analytics` | Read the overview, properties, comparisons, paths, funnels, retention, or lifecycle. |
| `support` | Create, read, reply to, close, or reopen support tickets. |
| `watch` | Stream live logs, issues, or actions. |

## Read a project doctor report

Use a project ID from `logbrew projects --json`:

```bash
logbrew doctor --project "<project_id>" --json
```

The command reads project state and one recent log. It does not create a
project, change a key, or record setup.

The report has `status`, `checks`, and `next`. Each check has `check`,
`status`, and `next`. The checks are `api`, `auth`, `project`, `ingest_key`,
`setup`, `telemetry`, and `logs`.

Exit code `0` means that the CLI wrote a report. It does not mean that the
project is ready. Read the report `status` and each check. A `not_checked`
check did not pass.

| Report `status` | Meaning and next step |
| --- | --- |
| `auth_invalid` | Account access is missing or invalid. A person runs `logbrew login`. |
| `project_missing` | This account cannot access the project. Use an ID from `logbrew projects --json`. |
| `api_unreachable` | The API request did not complete. Examine the network connection, then run the command again. |
| `check_failed` | A request failed or its response was invalid. Run the command again without changes. If it fails again, [report a problem](/guides/report-a-problem). |
| `needs_ingest_key` | The project has no active ingest key. Create a key only with permission to change the project. |
| `needs_setup` | SDK setup is necessary. Follow the [quickstart](/quickstart). |
| `needs_telemetry` | Setup started, but LogBrew has no telemetry for the project. Send a test event. |
| `ready` | The project has an active key and telemetry. Read the signal for your task. |

When the project read succeeds, the `logs` check is `visible`, `empty`,
`unavailable`, `error`, or `invalid_response`. This check does not change the
report `status`. An empty log result says nothing about other signals. A failed
read is not an empty result.

Use `next` as recovery guidance. It does not give permission to change account
or project state.

### Example: missing account access

Without account credentials, the command makes no API request. It writes this
report to standard output and exits with code `0`:

```json
{
  "checks": [
    { "check": "api", "next": "run the API reachability check first", "status": "not_checked" },
    { "check": "auth", "next": "run logbrew login", "status": "missing" },
    { "check": "project", "next": "resolve the prior check first", "status": "not_checked" },
    { "check": "ingest_key", "next": "resolve the prior check first", "status": "not_checked" },
    { "check": "setup", "next": "resolve the prior check first", "status": "not_checked" },
    { "check": "telemetry", "next": "resolve the prior check first", "status": "not_checked" },
    { "check": "logs", "next": "resolve the prior check first", "status": "not_checked" }
  ],
  "next": "run logbrew login",
  "status": "auth_invalid"
}
```

This report is different from the [project API
diagnosis](/concepts/projects#diagnose-project-setup). It does not contain the
API fields `state`, `setup_status`, or `next_action`.

## Filters

| Filter | Commands |
| --- | --- |
| `--project <project_id>` | logs, issues, actions, releases, metrics, traces, trace |
| `--release <release>` | logs, issues, actions, releases, metrics, traces, trace |
| `--environment <environment>` | logs, issues, actions, releases, metrics, traces, trace |
| `--service <service_name>` | logs, issues, actions, releases, metrics, traces |
| `--since 24h` | logs, issues, actions, releases, metrics, traces, analytics |
| `--until <RFC3339>` | logs, issues, actions, releases, metrics, traces, analytics |
| `--limit 100` | logs, issues, actions, releases, metrics, traces |
| `--severity error` | logs, watch |
| `--search checkout` | logs |
| `--trace <trace_id>` | logs |
| `--status unresolved` | issues (`unresolved`, `resolved`, `archived`) |
| `--priority high` | issues (`high`, `medium`, `low`) |
| `--assignee me` | issues (`me`, `none`, `my_teams`, a user ID, or `team:<team_id>`) |
| `--status error` | traces (`error`, `ok`) |
| `--min-duration-ms <milliseconds>` | traces |
| `--name <name>` | actions, metrics |
| `--user <distinct_id>` | actions |

`--since` accepts a duration such as `24h` or `7d`, or an RFC 3339 timestamp.
`--until` accepts an RFC 3339 timestamp. It is an exclusive end time and must
be later than `--since`. One issue by ID does not accept `--until`.

Log severity is `info`, `warning`, `error`, or `critical`. Issue status is the
workflow state of the issue, not its severity. `--status ignored` is an older
name for `--status archived`. `--status open` means `unresolved`, and
`--status closed` means `resolved`. `--assignee none` selects issues without an
assignee, and `--assignee my_teams` selects the issues of your teams. Any other
`--assignee` value fails with `invalid_assignee`.

The CLI also accepts these aliases: `--project-id`, `--env`, `--service-name`,
`--trace-id`, `--distinct-id`, and `--level` for `--severity`. Use the names in
the table in new scripts.

This command reads the errors of 1 day:

```bash
logbrew read logs --severity error \
  --since 2026-10-01T00:00:00Z --until 2026-10-02T00:00:00Z --json
```

The project ID selects the project. The service name selects a component in
that project. Put quotation marks around values that contain spaces:

```bash
logbrew read logs --project "<project_id>" \
  --service checkout-api --since 24h \
  --severity error --search "checkout failed" --json
```

For search text that starts with a hyphen, put `--` before the text:

```bash
logbrew logs --json -- --timeout
```

## Select an issue occurrence

An issue groups matching occurrences. Read the issue for its status,
occurrence count, and first and last seen times:

```bash
logbrew read issue "<issue_id>" --json
```

Use `explain issue` or `investigate issue` for evidence from one occurrence.
Without `--occurrence`, LogBrew selects the recommended occurrence. This is not
always the latest event. To read the latest event:

```bash
logbrew explain issue "<issue_id>" --occurrence latest --json
```

`--occurrence` also accepts `recommended`, `first`, or an occurrence ID that
LogBrew returned. These commands reject project, release, environment, and time
filters. Before you compare evidence, read the timestamp of the selected
occurrence. See [Investigate an issue](/guides/investigate-an-issue) for the
evidence fields.

## Change issue status and priority

Use 1 issue ID to change 1 issue:

```bash
logbrew issues archive "<issue_id>" --json
logbrew issues priority high "<issue_id>" --json
```

`archive` sets `archived`, `resolve` sets `resolved`, and `reopen` sets
`unresolved`. Priority is `high`, `medium`, or `low`. A priority that you set
stays fixed. Otherwise, the priority follows the issue severity.

To change more than 1 issue, add `--project`. All issues must be in that
project. One command changes up to 100 issues:

```bash
logbrew issues resolve "<issue_id_1>" "<issue_id_2>" \
  --project "<project_id>" --json
```

The result has 1 entry for each issue. Each entry is `updated`, `unchanged`,
or `not_found`. An `unchanged` issue already had the requested value. You can
run the same command again after a network failure.

These commands do not ask for confirmation. Check the issue IDs first. Issue
reads and changes show `archived` instead of `ignored`, and the `priority`,
`priority_source`, and `assignee` of each issue. See the
[issue response](/reference/telemetry-response-shapes#issue-response).

## Assign issues

An issue has 0 or 1 assignee: one account or one team. List the accounts and
teams that you can assign in a project:

```bash
logbrew issues assignees --project "<project_id>" --json
```

Assign 1 issue to an account, to yourself with `me`, or to a team:

```bash
logbrew issues assign "<user_id>" "<issue_id>" --json
logbrew issues assign me "<issue_id>" --json
logbrew issues assign "team:<team_id>" "<issue_id>" --json
```

Remove the assignee:

```bash
logbrew issues unassign "<issue_id>" --json
```

Add `--project` to change up to 100 issues of that project, as with status
and priority. An account must be able to read the project, and a team must
belong to the project's organization. To find the issues assigned to you or
your teams:

```bash
logbrew read issues --project "<project_id>" --assignee my_teams \
  --status unresolved --json
```

Text output shows the assignee name, or `team #<slug>` for a team. If the
account has no name, it shows the email address, then the user ID. An issue
without an assignee shows `unassigned`.

## Owners, history, and the inbox

```bash
logbrew issues owners "<issue_id>" --json
logbrew issues ownership --project "<project_id>" --json
logbrew issues ownership set --project "<project_id>" \
  --rules ownership.txt --codeowners .github/CODEOWNERS --json
logbrew issues activity "<issue_id>" --limit 50 --json
logbrew inbox --json
logbrew inbox read --json
```

`issues owners` lists the suggested owners and the evidence that it checked.
`issues ownership set` sends local files of at most 128 KiB each. An empty
file clears its text. `issues activity` and `inbox` take `--limit` from 1 to
200, and `--cursor-time` with `--cursor-id` from `next_cursor`. See
[Find who owns an issue](/guides/issue-workflow#find-who-owns-an-issue).

## Set severity rules

```bash
logbrew issues rule "<issue_id>" warning --json
logbrew logs rule "<log_id>" info --ignore --json
```

The severity is `info`, `warning`, `error`, `critical`, or `source`. `source`
shows the captured severity again. `--ignore` hides matching logs from the
default log list. Without `--ignore`, the rule shows them.

## Read the next page

Logs, issues, actions, metrics, and traces accept cursor pagination. Releases
do not. Use `--pagination cursor` for the first page:

```bash
logbrew read logs --project "<project_id>" --since 24h \
  --pagination cursor --limit 100 --json
```

The response has `logs` and `next_cursor`. A non-null `next_cursor` has `time`
and `id`. Send them with `--cursor-time` and `--cursor-id`:

```bash
logbrew read logs --project "<project_id>" --since 24h \
  --pagination cursor --limit 100 \
  --cursor-time "<returned_time>" \
  --cursor-id "<returned_id>" --json
```

Keep the same filters and limit on every page. Stop when `next_cursor` is
`null`. Use the cursor, not the row count, to decide if more pages exist. The
last page can be empty:

```json
{
  "logs": [],
  "next_cursor": null
}
```

Issues, actions, and metrics use the same shape with `issues`, `actions`, or
`metrics` in place of `logs`. Traces return `traces`, `next_cursor`, and
`naming_quality`. A trace cursor has `time` and `trace_id`. Send `trace_id`
with `--cursor-id`.

## Live watch

`logbrew watch --json` streams live logs, issues, and actions. Add `logs`,
`issues`, or `actions` to stream one type. `tail`, `follow`, and `stream` are
aliases of `watch`. Watch does not support traces or spans.

Watch needs `--json`. Without it, the command writes `watch streams JSON for
agents` and exits with code `1`.

Watch issue events show an archived issue as `ignored`, without a priority.
Read the issue to get its current status and priority.

Watch accepts only `--severity`, such as `--severity error,critical`.
`logbrew watch actions` does not accept `--severity`. The CLI
applies this filter after it receives events. It does not reduce what the
server sends. Watch has no project, release, environment, or time filter. For
those filters, use a `read` command. After a temporary disconnect, the CLI
waits and then reconnects.

## Read results and errors

Put `--json` before or after the command. Read the exit code before you use the
output. Do not parse human-readable output. It can change between versions.

| Exit code | Meaning |
| --- | --- |
| `0` | Success. JSON is on standard output. |
| `1` | The command failed while it ran, for example an API or network error. |
| `2` | The CLI rejected the command before it ran. |

Success output keeps the API response shape. It can be an array or an object.
Without cursor pagination, a log read returns an array. An empty array means
that no logs match. It is not an error.

Errors go to standard error. The exception is `debug-artifacts --json`, which
writes errors to standard output. A JSON error has `ok`, `error`, `message`, and
`next`. Use `error` as the stable failure code. Examine `next` before you run
the command it suggests.

For example, `logbrew watch traces --json` exits with code `2` and writes:

```json
{
  "ok": false,
  "error": "unknown_resource",
  "message": "unknown resource: traces",
  "next": "use logbrew traces for recent traces, or logbrew trace <trace_id> for one trace"
}
```

`logbrew read logs --limit 0 --json` exits with code `2` and writes:

```json
{
  "ok": false,
  "error": "invalid_limit",
  "message": "invalid limit: 0",
  "next": "use --limit with a positive whole number"
}
```

Correct the value and run the command again. A rejected command is not an
empty result. See [API errors](/reference/api-errors) for HTTP errors and the
[telemetry API reference](/reference/telemetry-api) for direct API requests.

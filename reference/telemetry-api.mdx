title: "Telemetry API"
description: "Send telemetry to LogBrew and read logs, issues, traces, actions, metrics, releases, and analytics over HTTP."
---

The telemetry API is JSON over HTTP at `https://api.logbrew.co`. Public SDKs
send their managed batches to `POST /v1/events`. Custom native clients send
native envelopes to `POST /api/telemetry/ingest`. Both ingest routes require a
project-scoped ingest bearer.

Reads and account-owned changes use an account bearer. Never use an account
bearer or a browser session as SDK or ingest configuration. Never send an
ingest bearer to a read route.

## Send a bounded request

Use this checklist before a client sends a request:

1. Choose the route and HTTP method from the endpoint table.
2. Use the correct bearer: an ingest bearer for ingestion, an account bearer
   for everything else.
3. Select the project scope that the route supports. Do not widen the scope
   after an empty response.
4. Add only query keys that the route accepts. See
   [Telemetry API query filters](/reference/telemetry-api-filters).
5. Send `Content-Type: application/json` when the route has a JSON body.
6. Read the HTTP status and the response body before you retry.
7. Keep bearers, feed tickets, and full response bodies out of logs and agent
   prompts.

## Endpoints

### Ingestion

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1/events` | Ingest batches that public LogBrew SDKs build and send. |
| `POST` | `/api/telemetry/ingest` | Ingest native telemetry envelopes from a custom client. |

Let the SDK build `/v1/events` batches. Do not construct them by hand. For the
native envelope, see [Send SDK telemetry](/guides/sdk-ingestion).

### Telemetry reads

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/logs` | List structured logs. |
| `GET` | `/api/telemetry/issues` | List grouped issues. |
| `GET` | `/api/telemetry/issues/{issue_id}` | Read one grouped issue. |
| `PATCH` | `/api/telemetry/issues/{issue_id}` | Update issue status. |
| `GET` | `/api/telemetry/traces` | Discover traces in a project scope. |
| `GET` | `/api/telemetry/traces/{trace_id}` | List spans for one trace. |
| `GET` | `/api/telemetry/traces/{trace_id}/summary` | Read a bounded summary of one trace. |
| `GET` | `/api/telemetry/actions` | List product actions. |
| `GET` | `/api/telemetry/metrics` | List metric samples. |
| `GET` | `/api/telemetry/releases` | List release summaries. |

### Investigations

Each investigation route returns a bounded evidence bundle for one subject.
The [CLI](/reference/cli) `logbrew explain` command reads these routes and
validates the response.

| Method | Path | CLI command |
| --- | --- | --- |
| `GET` | `/api/logs/{log_id}/investigation` | `logbrew explain log` |
| `GET` | `/api/telemetry/issues/{issue_id}/investigation` | `logbrew explain issue` |
| `GET` | `/api/telemetry/issues/{issue_id}/correction-verification` | `logbrew investigate issue <issue_id> verify` |
| `GET` | `/api/telemetry/traces/{trace_id}/investigation` | `logbrew explain trace` |
| `GET` | `/api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `logbrew explain span` |
| `GET` | `/api/telemetry/actions/{action_id}/investigation` | `logbrew explain action` |
| `GET` | `/api/telemetry/metrics/investigation` | `logbrew explain metric` |
| `GET` | `/api/telemetry/releases/investigation` | `logbrew explain release` |

### Product analytics

| Method | Path | CLI command |
| --- | --- | --- |
| `GET` | `/api/telemetry/analytics/overview` | `logbrew analytics overview` |
| `GET` | `/api/telemetry/analytics/properties` | `logbrew analytics properties` |
| `POST` | `/api/telemetry/analytics/funnel` | `logbrew analytics funnel` |
| `POST` | `/api/telemetry/analytics/retention` | `logbrew analytics retention` |

[Product analytics](/concepts/product-analytics).

### Live feed

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/feed/ticket` | Create a short-lived live-feed ticket with an account bearer. |
| `GET` | `/api/feed/live?ticket=<ticket>` | Open a WebSocket connection with that ticket. |

Usage, quota, subscription, and logout routes are in the

## Query filters and pagination

Each read route accepts its own query keys. Unknown keys fail closed. Friendly
aliases such as `project`, `trace`, and `user` are not query keys. List routes
return a bare array by default and a cursor envelope with `pagination=cursor`.
See [Telemetry API query filters](/reference/telemetry-api-filters).

## Responses and errors

- [Telemetry response shapes](/reference/telemetry-response-shapes) shows one
  example for each response family.
- [API errors](/reference/api-errors) lists error codes and recovery actions.

Read `code` before the human message. Use `next_action` for program behavior
and `next` for human guidance. Do not parse the wording of `error` or `next`.

## Update issue status

This request uses an account bearer. It is intentionally different from
`LOGBREW_INGEST_BEARER`.

```bash
curl -X PATCH "$LOGBREW_API_URL/api/telemetry/issues/$ISSUE_ID" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{ "status": "resolved" }'
```

Valid status values are `unresolved`, `resolved`, and `ignored`. A timeout
does not prove that the status did not change. Read the issue again before you
send the update again.

<Warning>
  Do not send blank releases. LogBrew rejects them so release tracking stays
  trustworthy.
</Warning>

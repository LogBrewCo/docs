The telemetry API is JSON over HTTP at `https://api.logbrew.co`. Public SDKs
send their managed batches to `POST /v1/events`. Custom native clients send
native envelopes to `POST /api/telemetry/ingest`. Both ingest routes require a
project-scoped ingest bearer.

Reads and account-owned changes use an account bearer. Never use an account
bearer or a browser session as SDK or ingest configuration. Never send an
ingest bearer to a read route.

## Send a bounded request

Use this checklist before a client sends a request:

1. Choose the route and HTTP method from the endpoint table.
2. Use the correct bearer: an ingest bearer for ingestion, an account bearer
   for everything else.
3. Select the project scope that the route supports. Do not widen the scope
   after an empty response.
4. Add only query keys that the route accepts. See
   [Telemetry API query filters](/reference/telemetry-api-filters).
5. Send `Content-Type: application/json` when the route has a JSON body.
6. Read the HTTP status and the response body before you retry.
7. Keep bearers, feed tickets, and full response bodies out of logs and agent
   prompts.

## Endpoints

### Ingestion

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1/events` | Ingest batches that public LogBrew SDKs build and send. |
| `POST` | `/api/telemetry/ingest` | Ingest native telemetry envelopes from a custom client. |

Let the SDK build `/v1/events` batches. Do not construct them by hand. For the
native envelope, see [Send SDK telemetry](/guides/sdk-ingestion).

### Deployments

| Method | Path | CLI command |
| --- | --- | --- |
| `PUT` | `/api/telemetry/deployments/{deployment_id}` | `logbrew deploy` |
| `GET` | `/api/telemetry/deployments/{deployment_id}?project_id=<project-uuid>` | None |
| `GET` | `/api/telemetry/deployments?project_id=<project-uuid>` | None |

Record a deployment from release automation after it succeeds or fails. The
`PUT` body has `project_id`, `release`, `environment`, `service_name`,
`status` (`succeeded` or `failed`), `started_at`, `finished_at`, and an
optional `commit_sha`. Use the same `release`, `environment`, and
`service_name` values that your SDK sends. The account must own the project.

`deployment_id` is your own ID for the deployment. A retry with the same ID
and the same body returns the stored deployment. The same ID with a different
body fails with `409` and `idempotency_conflict`. Use a new ID for a different
deployment.

## Success status codes

| Operation | Success status |
| --- | --- |
| Ingestion, reads, issue updates, rules, deployments, analytics, and feed tickets | `200 OK` |
| Live-feed connection | `101 Switching Protocols`, then WebSocket messages |

A `200` response does not prove that the evidence is complete. Read the
coverage, truncation, and status fields in the response.

## Query filters and pagination

Each read route accepts its own query keys. Friendly aliases such as
`project`, `trace`, and `user` are not query keys. List routes return a bare
array by default and a cursor envelope with `pagination=cursor`. The
deployment list always returns a page object. See
[Telemetry API query filters](/reference/telemetry-api-filters).

## Responses and errors

- [Telemetry response shapes](/reference/telemetry-response-shapes) shows one
  example for each response family.
- [API errors](/reference/api-errors) lists error codes and recovery actions.

Read `code` before the human message. Use `next_action` for program behavior
and `next` for human guidance. Do not parse the wording of `error` or `next`.

## Update issues

These requests use an account bearer. It is intentionally different from
`LOGBREW_INGEST_BEARER`. The account must have permission to manage issues in
the issue's project. If it does not, the request fails with `403` and
`forbidden`. The same permission covers status, priority, and assignee
changes, and issue and log rules.

Each request sets 1 or more of these fields:

| Field | Values |
| --- | --- |
| `status` | `unresolved`, `resolved`, or `archived`. `ignored` is an older name for `archived`. |
| `priority` | `high`, `medium`, or `low`. |
| `assignee` | A user ID, `me` for the signed-in account, `team:<team_id>` for a team, or `none` to remove the assignee. |

A request without any of these fields fails with `422` and
`validation_failed`.

An issue has 0 or 1 assignee: an account or a team. An account must be able to
read the project, and a team must belong to the project's organization. If
not, the request fails with `422` and `validation_failed`, and LogBrew changes
nothing. Get the accounts that you can assign from
[List assignees](#list-assignees). Any other `assignee` value also fails with
`422` and `validation_failed`.

A priority that you set stays fixed. Without a priority that you set, the
priority follows the issue severity: `error` and `critical` are `high`,
`warning` is `medium`, and `info` is `low`.

A field that already has the requested value does not change. You can send
the same request again after a timeout. A timeout does not prove that the
change did not occur. Read the issue again before you send a different change.

### Update one issue

Add `response_version=4` to get `archived`, the priority, and the assignee
in the response. In version 4, `assignee` is
`{ "type": "user", "user_id", "name", "email" }`,
`{ "type": "team", "team_id", "slug", "name" }`, or `null`. Version 3 shows a
team assignee as `null`.

```bash
curl -X PATCH "$LOGBREW_API_URL/api/telemetry/issues/$ISSUE_ID?response_version=4" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{ "status": "archived", "priority": "low", "assignee": "me" }'
```

The response is the updated issue. See
[issue status response examples](/reference/telemetry-response-shapes#issue-status-response-examples).

### Update issues in bulk

Send `project_id` and 1 to 100 different issue IDs from that project:

```bash
curl -X POST "$LOGBREW_API_URL/api/telemetry/issues/bulk" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{
    "project_id": "<project-uuid>",
    "issue_ids": ["<issue-uuid-1>", "<issue-uuid-2>"],
    "assignee": "<user-uuid>"
  }'
```

The request applies the same change to every issue. The response has
`project_id` and `results`, with 1 result for each issue ID, in the request
order. Each result has `issue_id`, `outcome`, and `issue`. `issue` is the
current issue in response version 3, or `null` for `not_found`. Add
`"response_version": 2` to the body to get each issue in response version 4.

| `outcome` | Meaning |
| --- | --- |
| `updated` | LogBrew applied the change. |
| `unchanged` | The issue already had the requested values. |
| `not_found` | The project has no issue with this ID. LogBrew changed nothing for it. |

An empty list, more than 100 IDs, or a repeated ID fails with `422` and
`validation_failed`. Split a larger set into more requests. If the account
cannot read the project, the request fails with `404` and `not_found`.

### List assignees

Send the project ID to get every account that can be assigned issues in that
project:

```bash
curl "$LOGBREW_API_URL/api/telemetry/issues/assignees?project_id=$PROJECT_ID" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

The list has every account that can read the project. Each entry has
`user_id`, `name`, and `email`. `name` is `null` when the account has no name.
Add `response_version=2` to also get `teams`: every team of the project's
organization, with `team_id`, `slug`, and `name`.
See the [assignee list response](/reference/telemetry-response-shapes#assignee-list-response).
Any account that can read the project can get this list. If the account
cannot read the project, the request fails with `404` and `not_found`.

When a member loses access to the project, the issues assigned to that member
show no assignee. If the member gets access again, the issues show that
member again, unless someone changed or removed the assignee in the meantime.

### Ownership and suggested owners

`GET /api/telemetry/issues/ownership?project_id=<project-uuid>` returns
`rules`, `codeowners`, `updated_at`, and `unresolved_owners`. Any account that
can read the project can read it. `PUT` with `project_id` and `rules`,
`codeowners`, or both replaces that text and needs permission to manage
issues. A field that you leave out keeps its text, and an empty string clears
it. Each text is at most 128 KiB. Invalid text fails with `422` and names the
line.

`GET /api/telemetry/issues/{issue_id}/owners?response_version=2` returns
`suggested_assignee`, `owners`, and `inputs`. Each owner has `type` (`user` or
`team`), `source` (`ownership_rule`, `codeowners`, or `recent_activity`),
`rule`, `line`, and `matched`. Version 1, the default, lists accounts only.

### Issue history

`GET /api/telemetry/issues/{issue_id}/activity?response_version=2` returns
`activity`, newest first, and `next_cursor`. Each entry has `type`
(`status`, `priority`, `assigned`, `unassigned`, `severity_rule`, or
`first_seen`), `value`, `actor_id`, `actor`, `assignee_id`, `assignee`,
`team`, and `at`. `limit` is 1 to 200, 50 by default. Send `cursor_time` and
`cursor_id` from `next_cursor` for the next page.

### Notifications

`GET /api/telemetry/issues/notifications` returns `notifications`, `unread`,
`read_at`, and `next_cursor`. Each notification is an assignment of an issue to
you or to your team by another account. `POST
/api/telemetry/issues/notifications/read` with an empty JSON object, or with
`read_at`, moves your read mark. The mark never moves back.

### Set issue and log rules

A rule changes how LogBrew shows matching signals. It does not delete data.
The captured `severity` stays unchanged, and the response shows the rule in
`triage`.

| Request | JSON body |
| --- | --- |
| `PUT /api/telemetry/issues/{issue_id}/triage-rule` | `{ "severity": "<value>" }` |
| `PUT /api/logs/{log_id}/triage-rule` | `{ "severity": "<value>", "ignored": true }` |

`severity` is `info`, `warning`, `error`, `critical`, or `source`. `source`
removes the override and shows the captured severity again. For a log rule,
`ignored: true` hides matching logs from the default log list. Read them with
`status=ignored` or `status=all`. The rule applies to retained and future
matching signals. Another value fails with `422` and `validation_failed`.

<Warning>
  Do not send blank releases. LogBrew rejects them so release tracking stays
  trustworthy.
</Warning>

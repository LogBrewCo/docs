The telemetry API is JSON over HTTP at `https://api.logbrew.co`. Public SDKs
send their managed batches to `POST /v1/events`. Custom native clients send
native envelopes to `POST /api/telemetry/ingest`. Both ingest routes require a
project-scoped ingest bearer.

Reads and account-owned changes use an account bearer. Never use an account
bearer or a browser session as SDK or ingest configuration. Never send an
ingest bearer to a read route.

## Send a bounded request

Use this checklist before a client sends a request:

1. Choose the route and HTTP method from the endpoint table.
2. Use the correct bearer: an ingest bearer for ingestion, an account bearer
   for everything else.
3. Select the project scope that the route supports. Do not widen the scope
   after an empty response.
4. Add only query keys that the route accepts. See
   [Telemetry API query filters](/reference/telemetry-api-filters).
5. Send `Content-Type: application/json` when the route has a JSON body.
6. Read the HTTP status and the response body before you retry.
7. Keep bearers, feed tickets, and full response bodies out of logs and agent
   prompts.

## Endpoints

### Ingestion

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1/events` | Ingest batches that public LogBrew SDKs build and send. |
| `POST` | `/api/telemetry/ingest` | Ingest native telemetry envelopes from a custom client. |

Let the SDK build `/v1/events` batches. Do not construct them by hand. For the
native envelope, see [Send SDK telemetry](/guides/sdk-ingestion).

### Telemetry reads

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/logs` | List structured logs. |
| `GET` | `/api/telemetry/issues` | List grouped issues. |
| `GET` | `/api/telemetry/issues/{issue_id}` | Read one grouped issue. |
| `PATCH` | `/api/telemetry/issues/{issue_id}` | Update the status, priority, or assignee of one issue. |
| `POST` | `/api/telemetry/issues/bulk` | Update the status, priority, or assignee of 1 to 100 issues in one project. |
| `GET` | `/api/telemetry/issues/assignees` | List the accounts that can be assigned issues in one project. |
| `GET` | `/api/telemetry/traces` | Discover traces in a project scope. |
| `GET` | `/api/telemetry/traces/{trace_id}` | List spans for one trace. |
| `GET` | `/api/telemetry/traces/{trace_id}/summary` | Read a bounded summary of one trace. |
| `GET` | `/api/telemetry/actions` | List product actions. |
| `GET` | `/api/telemetry/metrics` | List metric samples. |
| `GET` | `/api/telemetry/releases` | List release summaries. |

### Investigations

Each investigation route returns a bounded evidence bundle for one subject.
The [CLI](/reference/cli) `logbrew explain` command reads these routes and
validates the response.

| Method | Path | CLI command |
| --- | --- | --- |
| `GET` | `/api/logs/{log_id}/investigation` | `logbrew explain log` |
| `GET` | `/api/telemetry/issues/{issue_id}/investigation` | `logbrew explain issue` |
| `GET` | `/api/telemetry/issues/{issue_id}/correction-verification` | `logbrew investigate issue <issue_id> verify` |
| `GET` | `/api/telemetry/traces/{trace_id}/investigation` | `logbrew explain trace` |
| `GET` | `/api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `logbrew explain span` |
| `GET` | `/api/telemetry/actions/{action_id}/investigation` | `logbrew explain action` |
| `GET` | `/api/telemetry/metrics/investigation` | `logbrew explain metric` |
| `GET` | `/api/telemetry/releases/investigation` | `logbrew explain release` |

## Query filters and pagination

Each read route accepts its own query keys. Unknown keys fail closed. Friendly
aliases such as `project`, `trace`, and `user` are not query keys. List routes
return a bare array by default and a cursor envelope with `pagination=cursor`.
See [Telemetry API query filters](/reference/telemetry-api-filters).

## Responses and errors

- [Telemetry response shapes](/reference/telemetry-response-shapes) shows one
  example for each response family.
- [API errors](/reference/api-errors) lists error codes and recovery actions.

Read `code` before the human message. Use `next_action` for program behavior
and `next` for human guidance. Do not parse the wording of `error` or `next`.

## Update issues

These requests use an account bearer. It is intentionally different from
`LOGBREW_INGEST_BEARER`. The account must have permission to manage issues in
the issue's project. If it does not, the request fails with `403` and
`forbidden`. The same permission covers status, priority, and assignee
changes, and issue and log rules.

Each request sets 1 or more of these fields:

| Field | Values |
| --- | --- |
| `status` | `unresolved`, `resolved`, or `archived`. `ignored` is an older name for `archived`. |
| `priority` | `high`, `medium`, or `low`. |
| `assignee` | A user ID, `me` for the signed-in account, or `none` to remove the assignee. |

An issue has 0 or 1 assignee. The assignee must be able to read the project.
If not, the request fails with `422` and `validation_failed`, and LogBrew
changes nothing. Get the accounts that you can assign from
[List assignees](#list-assignees). Any other `assignee` value also fails with
`422` and `validation_failed`.

A priority that you set stays fixed. Without a priority that you set, the
priority follows the issue severity: `error` and `critical` are `high`,
`warning` is `medium`, and `info` is `low`.

A field that already has the requested value does not change. You can send
the same request again after a timeout. A timeout does not prove that the
change did not occur. Read the issue again before you send a different change.

### Update one issue

Add `response_version=3` to get `archived`, the priority, and the assignee
in the response:

```bash
curl -X PATCH "$LOGBREW_API_URL/api/telemetry/issues/$ISSUE_ID?response_version=3" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{ "status": "archived", "priority": "low", "assignee": "me" }'
```

The response is the updated issue. See
[issue status response examples](/reference/telemetry-response-shapes#issue-status-response-examples).

### Update issues in bulk

Send `project_id` and 1 to 100 different issue IDs from that project:

```bash
curl -X POST "$LOGBREW_API_URL/api/telemetry/issues/bulk" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  -H "Content-Type: application/json" \
  --data '{
    "project_id": "<project-uuid>",
    "issue_ids": ["<issue-uuid-1>", "<issue-uuid-2>"],
    "assignee": "<user-uuid>"
  }'
```

The request applies the same change to every issue. The response has 1 result
for each issue ID, in the request order. Each result has an `outcome`:

| `outcome` | Meaning |
| --- | --- |
| `updated` | LogBrew applied the change. |
| `unchanged` | The issue already had the requested values. |
| `not_found` | The project has no issue with this ID. LogBrew changed nothing for it. |

An empty list, more than 100 IDs, or a repeated ID fails with `422` and
`validation_failed`. Split a larger set into more requests. If the account
cannot read the project, the request fails with `404` and `not_found`.

### List assignees

Send the project ID to get every account that can be assigned issues in that
project:

```bash
curl "$LOGBREW_API_URL/api/telemetry/issues/assignees?project_id=$PROJECT_ID" \
  -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

The list has every account that can read the project. Each entry has
`user_id`, `name`, and `email`. `name` is `null` when the account has no name.
See the [assignee list response](/reference/telemetry-response-shapes#assignee-list-response).
Any account that can read the project can get this list. If the account
cannot read the project, the request fails with `404` and `not_found`.

When a member loses access to the project, the issues assigned to that member
show no assignee. If the member gets access again, the issues show that
member again, unless someone changed or removed the assignee in the meantime.

<Warning>
  Do not send blank releases. LogBrew rejects them so release tracking stays
  trustworthy.
</Warning>

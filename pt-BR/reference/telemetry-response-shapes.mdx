Esta página mostra um exemplo de cada família de respostas da
[API de telemetria](/pt-BR/reference/telemetry-api). Todos os valores são
fictícios. Para códigos de erro e recuperação, consulte
[Erros da API](/pt-BR/reference/api-errors).

## Leia uma resposta

Leia cada resposta nesta ordem:

1. Leia o status HTTP.
2. Confira se o corpo tem o formato definido pela rota.
3. Confira se cada `project_id` está dentro do escopo de projetos solicitado.
4. Mantenha os valores canônicos de enum e os identificadores sem alteração.
5. Siga `next_action` somente quando o cliente aceitar o `code` e o
   `target` dele.
6. Trate `null`, um campo omitido e uma lista vazia como estados diferentes.

Um `200 OK` pode conter uma lista vazia. Uma lista de logs vazia significa que
nenhum log correspondeu à requisição. Isso não significa que problemas, traces
ou ações também estejam vazios. Não junte sinais só porque os horários estão
próximos. Siga um trace somente quando a resposta trouxer o `trace_id` exato
dele.

Um `404` e uma lista vazia são resultados diferentes. Uma rota de lista retorna
`[]` quando nenhum item corresponde. Uma rota de detalhe retorna `404` com
`code: not_found` quando não encontra um item que a conta possa ler. Nenhum dos
dois resultados prova que a ingestão falhou.

## O que enviar

A utilidade das respostas depende da telemetria que você envia. Envie estes
valores em cada envelope ou configuração de SDK:

- `release` e `environment`.
- Nomes estáveis para serviços, ações e métricas.
- Contexto de trace quando logs, spans, ações e problemas pertencem à mesma
  requisição.
- Valores canônicos de gravidade: `info`, `warning`, `error` e `critical`.
- Atributos que ajudam na depuração, sem segredos nem dados pessoais
  desnecessários.

Consulte [Integração do SDK](/pt-BR/guides/sdk-ingestion) e
[Controlar dados capturados](/pt-BR/guides/safe-capture).

## Resposta da ingestão

Os SDKs públicos leem a resposta de `POST /v1/events` por você. O código da
aplicação não precisa tratá-la.

### Resposta de lote do SDK

Um lote do SDK bem-sucedido retorna `200 OK` com a contagem aceita de cada
fluxo:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Campo | Significado |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Eventos deste lote que o LogBrew aceitou. |
| `already_accepted` | Eventos cujo ID o LogBrew já tinha aceitado antes. O LogBrew não os armazena de novo. |
| `context_updated` | `true` quando o lote atualizou o contexto de versão ou de ambiente. |

As contagens cobrem só este lote. Uma nova tentativa de um lote que o LogBrew
já aceitou retorna `0` para cada fluxo e o número de eventos em
`already_accepted`. Mantenha os IDs originais dos eventos ao tentar novamente.

### Resposta do envelope nativo

`POST /api/telemetry/ingest` retorna `200 OK` com a contagem de itens aceitos
de cada fluxo:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

A resposta nativa não tem os campos `metrics` nem `context_updated`. Não os
adicione. `already_accepted` conta os itens cujo `id` o LogBrew já tinha
aceitado para o projeto. Consulte o
[envelope nativo direto](/pt-BR/guides/sdk-ingestion#required-envelope-fields).

### Erros de ingestão

Um `401` com `code: ingest_key_invalid` significa que o bearer token de
ingestão foi revogado, expirou ou não vale para o projeto. Em
`POST /v1/events`, um bearer token ausente, ou um que não seja uma chave de
ingestão, retorna `401` com `code: unauthorized`. Use o bearer token de
ingestão atual do projeto. Não tente novamente com o bearer token da conta.

Um lote do SDK rejeitado retorna `422` com `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Outros valores de `error` incluem `SDK event batch requires at least one event`
e `SDK event type is not supported by this ingest route`. Confira a versão do
SDK e a configuração do transporte. Não envie um lote vazio. Não altere tipos
nem IDs de eventos só para o lote passar na validação.

Uma requisição com um método diferente de `POST` retorna `405` com
`code: method_not_allowed`. Um corpo JSON ilegível retorna `code: invalid_json`.

## Formato de resposta das listas de telemetria

Por padrão, as rotas de lista retornam um array JSON simples. Uma lista vazia
bem-sucedida é `[]`.

Com `pagination=cursor`, a rota retorna um envelope. A chave da coleção
corresponde ao sinal:

| Rota | Chave da coleção |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, com um `issue_id` no nível superior |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, com um `naming_quality` no nível superior |

`next_cursor` é um objeto com os campos de continuação, ou `null` na última
página. As linhas vêm da mais recente para a mais antiga. Consulte
[paginação por cursor](/pt-BR/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Resposta de log</span>

Uma página de cursor de logs com `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Os logs incluem `level` por compatibilidade e `severity` para exibição. Os
dois têm o valor canônico. `triage` tem o resultado de uma regra de gravidade.
Consulte [respostas de regras de gravidade](#severity-rule-responses).

`trace_id` e `span_id` são `null` quando o log não tem vínculo com um trace.
Nesse caso, `next_action` é `inspect_related_logs` com o destino
`telemetry_logs`. Logs, problemas e ações usam os mesmos 2 pares de
`next_action`.

`GET /api/logs/{log_id}` retorna um log no mesmo formato.

### <span id="issue-response">Resposta de problema</span>

`GET /api/telemetry/issues/{issue_id}` retorna um problema agrupado. A lista
retorna os mesmos objetos. Este exemplo usa a versão de resposta padrão, a 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

Na versão 1, `status` é `unresolved`, `resolved` ou `ignored`. Em um problema
arquivado, `triage.ignored` é `true`. Para os pares de `next_action` e as
leituras que vêm depois deles, consulte
[Investigar um problema](/pt-BR/guides/investigate-an-issue).

`first_seen_at` e `last_seen_at` são os horários da primeira ocorrência e da
mais recente. Eles não mudam quando o status muda.

Alguns campos só aparecem quando o LogBrew tem os dados:

| Campo | Quando aparece |
| --- | --- |
| `span_id` | O problema tem vínculo com um span. Caso contrário, o campo é omitido. |
| `diagnostics` | A ocorrência mais recente tem um tipo de exceção ou breadcrumbs. Consulte [histórico de ocorrências do problema](#issue-occurrence-history). |
| `symbolication` | Só em `GET /api/telemetry/issues/{issue_id}`, quando o problema tem a identificação de um artefato da versão. Consulte [Source maps de JavaScript](/pt-BR/guides/source-maps). |

`symbolication.status` é `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` ou `unavailable`. A lista, as
mudanças de status e as mudanças de regra não retornam `symbolication`.

Com `response_version=2`, o problema tem os mesmos campos, com estas
mudanças:

| Campo | Valor na versão 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` ou `archived`. A versão 1 mostra `archived` como `ignored`. |
| `priority` | `high`, `medium` ou `low`. |
| `priority_source` | `manual` quando uma pessoa definiu a prioridade. `derived` quando a prioridade segue a gravidade efetiva. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Este exemplo mostra só alguns campos. Uma prioridade derivada é `high` para
`error` e `critical`, `medium` para `warning` e `low` para `info`. Ela usa
`triage.effective_severity`, então uma regra de gravidade do problema pode
mudá-la.

Com `response_version=3`, o problema tem todos os campos da versão 2 e
`assignee`. `assignee` é `null` quando o problema não tem responsável:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Campo | Significado |
| --- | --- |
| `assignee.user_id` | ID de usuário do responsável. Envie-o como `assignee` em um filtro ou em uma alteração. |
| `assignee.name` | Nome do responsável, ou `null` quando a conta não tem nome. |
| `assignee.email` | Endereço de e-mail do responsável. |

Um problema aparece sem responsável quando o membro atribuído não pode mais
ler o projeto.

Com `response_version=4`, `assignee` também tem `type`. Um responsável `user`
tem `user_id`, `name` e `email`, como na versão 3. Um responsável `team` tem
`team_id`, `slug` e `name`. A versão 3 mostra uma equipe responsável como
`null`. A CLI solicita a versão 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Qualquer outro `response_version` retorna `422` com
`code: validation_failed`. Uma página de cursor usa a mesma versão para todos
os problemas em `issues`.

### <span id="assignee-list-response">Resposta da lista de responsáveis</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` retorna todas as
contas que podem receber problemas atribuídos no projeto:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Adicione `response_version=2` para receber também `teams`: todas as equipes
da organização do projeto, com `team_id`, `slug` e `name`.

Se a conta não puder ler o projeto, a rota retorna `404` com
`code: not_found`.

### <span id="action-response">Resposta de ação</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` acompanha um ator ou uma sessão. Trate `distinct_id` e
`session_id` como identificadores opacos. `session_id` e `trace_id` são `null`
quando não foram capturados. `span_id` é omitido quando não foi capturado. Uma
ação não tem gravidade. Consulte
[Captura de eventos de produto](/pt-BR/guides/product-events).

### Resposta de métrica

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Cada item é uma amostra. Não use o número de amostras como contagem de eventos
ou de usuários. `unit`, `temporality`, `trace_id` e `span_id` são `null`
quando não foram capturados. Um valor `null` não é zero.

### Resposta de versão

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Uma linha cobre um projeto, uma versão, um ambiente e um serviço. As contagens
dela descrevem só essa linha.

`trace_health.status` é `unknown` quando a linha não tem traces. Nos outros
casos, é `no_errors_observed` ou `errors_observed`. `error_rate_basis_points`
é a parcela de traces com um span de erro, de `0` a `10000`. Não é uma taxa
de erro de todas as requisições.

`next_action` aponta para o primeiro tipo de sinal que tem dados, nesta ordem:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Consulte [Versões](/pt-BR/concepts/releases).

### Resposta da descoberta de traces

`GET /api/telemetry/traces?pagination=cursor` retorna uma linha para cada
trace, mais um resumo `naming_quality` da página retornada:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` cobre só a página retornada. Não é uma pontuação da conta
inteira. `truncated: true` significa que existe outra página. Quando a página
tem um nome genérico, uma rota sem correspondência ou uma operação genérica,
`next_action` é `improve_trace_naming` com o destino `sdk_configuration`. Sem
`pagination=cursor`, a rota retorna um array simples de traces, sem
`naming_quality`.

`next_cursor` contém `time` e `trace_id`. Envie-os como `cursor_time` e
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` retorna os spans de um trace.
`GET /api/telemetry/traces/{trace_id}/summary` retorna o span raiz, os spans
de erro, os serviços, a duração e o caminho mais lento, sem os atributos
brutos dos spans. Um `404` no resumo significa que nenhum trace correspondeu
ao escopo completo. Não remova os filtros para tentar novamente. Consulte
[respostas de spans e resumo de trace](#trace-spans-and-summary-responses).

### Listas vazias e itens inexistentes

Uma leitura de lista pode não ter correspondências. Uma leitura de detalhe tem
outro contrato:

| Requisição | Sucesso | Nenhum item legível |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` com um [log](#log-response) | `404` com `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` com um [problema](#issue-response) | `404` com `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` com ocorrências | `404` com `code: not_found` na primeira página |
| `GET /api/telemetry/traces/{trace_id}` | `200` com spans | `200` com `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` com um resumo | `404` com `code: not_found` |

Um log inexistente retorna este `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Um problema inexistente usa `"error": "issue not found"`. Um resumo de trace
inexistente usa `"error": "trace not found"`. Um ID desconhecido e um ID que a
conta não pode ler retornam a mesma resposta.

Uma lista com um `project_id` que a conta não pode ler retorna `200` com uma
lista vazia. Confira o ID do projeto antes de informar que não há dados.

### Seleções de projetos rejeitadas

As listas de logs, problemas, ações, métricas, versões e traces aceitam um
projeto com `project_id` ou de 2 a 50 projetos com `project_ids`. O catálogo
de atributos de logs aceita os mesmos seletores. O histórico de ocorrências do
problema não os aceita.

Uma requisição com `project_id` e `project_ids` ao mesmo tempo retorna `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` com um UUID inválido, um ID repetido, ou com menos de 2 ou mais
de 50 IDs também retorna `422` com `code: validation_failed`.

Se a conta não puder ler um dos projetos de um conjunto `project_ids`, a
requisição inteira retorna `404`. Ela não retorna os outros projetos como
resultado parcial:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Mostre o erro, não uma lista vazia nem uma contagem zero. Leia a lista de
projetos de novo. Não remova um projeto sem avisar e não tente novamente com
todos os projetos. Uma credencial delegada, como uma conexão MCP, retorna
`403` com `code: forbidden` para um projeto que a conexão não cobre. Consulte
[escopo de projetos](/pt-BR/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Erros de cursor</span>

Logs, problemas, ações, métricas e ocorrências de problemas usam `cursor_time`
e `cursor_id`. Um cursor rejeitado retorna `422` com `code: validation_failed`.
Esses erros não significam que a lista está vazia.

| Requisição | `error` |
| --- | --- |
| `pagination=cursor` com só 1 dos 2 campos do cursor | `cursor_time and cursor_id must be sent together` |
| `cursor_time` que não é um timestamp RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Campos de cursor sem `pagination=cursor`, ou com outro valor de `pagination` | `pagination must be cursor when cursor pagination is requested` |

Por exemplo:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Copie o `next_cursor` completo da página anterior. Não troque `cursor_time`
pelo horário atual. Se você perdeu o cursor, comece de novo com
`pagination=cursor` e os filtros originais. Um parâmetro de consulta desconhecido ou
um valor do tipo errado retorna `422` com `"error": "invalid query parameters"`.

### Respostas com cursor de versões

Um cursor de versões tem 5 campos. Uma requisição bem-sucedida sem
correspondências retorna `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Quando `next_cursor` não for `null`, envie os 5 valores na próxima requisição:

| Campo de `next_cursor` | Parâmetro de consulta |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` marca uma posição. Ele não substitui `project_id` nem
`project_ids`. Mantenha os parâmetros originais de projeto e de filtro.
Codifique cada valor para URL.

Com `pagination=cursor`, um cursor incompleto ou um valor em branco de versão,
ambiente ou serviço retorna `422` com
`"error": "all release cursor fields must be sent together"`. Um
`cursor_time` inválido e a falta de `pagination=cursor` retornam os mesmos
erros dos [outros cursores](#cursor-errors).

### Erros da descoberta de traces

Estes erros valem para `GET /api/telemetry/traces`. Cada um retorna `422` com
`code: validation_failed`. Uma requisição rejeitada não é um resultado vazio.

| Requisição | `error` |
| --- | --- |
| `status` diferente de `error` ou `ok` | `trace status must be error or ok` |
| `min_duration_ms` abaixo de `0` | `minimum trace duration must not be negative` |
| Só 1 campo de cursor, ou um `cursor_trace_id` em branco | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` que não é um timestamp RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Campos de cursor sem `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Para incluir traces com os dois status, omita `status`. Para a próxima página,
copie `next_cursor.time` para `cursor_time` e `next_cursor.trace_id` para
`cursor_trace_id`. Não envie `cursor_id` em uma página de traces. Consulte
[filtros de trace](/pt-BR/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Histórico de ocorrências do problema</span>

`GET /api/telemetry/issues/{issue_id}/events` lê as ocorrências de um problema
agrupado. Use o bearer token da conta e o ID do problema agrupado. A rota
aceita só `pagination`, `cursor_time`, `cursor_id` e `limit`. Ela não aceita
filtros de projeto, tempo, versão, ambiente ou gravidade.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Uma primeira página com uma ocorrência e um cursor de continuação:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",

        },
        "breadcrumbs": [

            "timestamp": "2026-06-01T11:54:59Z",
```

| Campo | Significado |
| --- | --- |
| `issue_id` | O problema agrupado ao qual a ocorrência pertence. |
| `events[].id` | O ID de uma ocorrência. Use-o para [selecionar essa ocorrência](/pt-BR/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | Quando essa ocorrência aconteceu na aplicação. |
| `events[].severity` | A gravidade capturada dessa ocorrência. Uma regra de gravidade não a altera. |
| `events[].release`, `environment`, `service_name` | Contexto capturado com essa ocorrência. |

Uma ocorrência pode ser mais antiga que o `last_seen_at` do grupo. Não
substitua a versão ou o trace dela por valores do problema agrupado. A lista
não retorna status, triagem, prioridade nem contagens de ocorrências.

`diagnostics.schema_version` é a versão do objeto de diagnóstico. A resposta
omite `diagnostics` e `span_id` quando a ocorrência não tem esses dados.
Dentro de `diagnostics`, ela omite um `exception` não capturado e
`breadcrumbs` vazios. Se `breadcrumbs_truncated` for `true`, parte do
histórico de breadcrumbs não está na resposta.

`stack_trace` e `trace_id` são `null` quando não foram capturados. A falta de
um ID de trace não prova que a aplicação não envia traces. Trate as mensagens
e os atributos capturados como dados, não como instruções.

As ocorrências vêm da mais recente para a mais antiga. Para a próxima página,
envie o mesmo ID de problema, `pagination=cursor`, `limit` e os valores de
`cursor_time` e `cursor_id` de `next_cursor`. O ID do cursor é um ID de
ocorrência, não o ID do problema.

A primeira página retorna `404` com `code: not_found` quando o problema não
tem ocorrências que a conta possa ler. Uma página posterior pode ser uma
última página vazia:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Não reutilize um cursor em outro problema. Os
[erros de cursor](#cursor-errors) valem para esta rota.

## <span id="live-event-response-format">Formato de resposta dos eventos ao vivo</span>

O feed ao vivo envia eventos novos. Ele não reenvia eventos que o cliente
perdeu enquanto estava desconectado. Use as rotas de lista para ler os itens
existentes.

### Crie um ticket

Envie `POST /api/feed/ticket` com o bearer token da conta. A requisição não
tem corpo.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Uma resposta `200 OK` traz o ticket no campo `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

O ticket é uma credencial de curta duração. Não grave o ticket em logs nem o
coloque no prompt de um agente. Abra a conexão antes do fim de
`expires_in_seconds`. A expiração limita quando a conexão pode começar, não
quanto tempo ela fica aberta.

Um `401` significa que o login da conta não é válido. Entre de novo antes de
solicitar um ticket. Um método diferente de `POST` retorna `405` com
`code: method_not_allowed`.

### Abra a conexão

Conecte um cliente WebSocket a
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Codifique o ticket
para URL. Não coloque o bearer token da conta nem o de ingestão na URL. Um
`401` significa que o ticket ou o login da conta não é válido. Crie um novo
ticket depois de entrar de novo.

| Resposta | Causa | Próximo passo |
| --- | --- | --- |
| `422` com `"error": "feed ticket is required"` | O parâmetro de consulta `ticket` está ausente ou em branco. | Crie um ticket e conecte-se com ele. |
| `401` com `code: unauthorized` | O ticket expirou ou não é válido. | Crie um novo ticket. Não tente de novo com o mesmo ticket. |
| `code: invalid_websocket_upgrade` | A requisição não é um upgrade de WebSocket válido. | Use um cliente WebSocket. |
| `405` com `code: method_not_allowed` | A requisição não usa `GET`. | Use `GET` para a conexão. |

Espere antes de reconectar depois de um erro. Não reconecte em um loop sem
pausa.

### Leia as mensagens

Cada mensagem é um envelope `{ "type": "...", "data": ... }`. Leia `type`
antes de interpretar `data`. Ignore os tipos que o cliente não aceita.

| Tipo de evento | Conteúdo |
| --- | --- |
| `native_log` | Dados de log, no formato da [resposta de log](#log-response). |
| `native_issue` | Dados do problema agrupado, no formato da [resposta de problema](#issue-response) da versão 1. |
| `native_trace_span` | Um span, no formato de um item da [lista de spans](#span-list). |
| `native_action` | Dados da ação de produto, no formato da [resposta de ação](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Dados do projeto. Leia a lista de projetos de novo quando ela mudar. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Uso da conta, no formato de [uso da conta](/pt-BR/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Um evento `native_issue` usa a versão 1 da resposta de problema: um problema
arquivado aparece como `ignored`, e o evento não tem prioridade. Métricas e
versões não são tipos de evento ao vivo. Leia-as pelas rotas de lista delas.
O ticket não seleciona um projeto. Confira o `project_id` de cada evento antes
de mostrá-lo na visão de um projeto. `logbrew watch --json` usa este feed.
Consulte a [referência da CLI](/pt-BR/reference/cli).

### Trate uma conexão fechada

| Código de fechamento | Motivo | Próximo passo |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Espere e reconecte com um novo ticket. Leia as rotas de lista de novo para obter os itens que você perdeu. |
| `1008` | `live feed access changed; sign in again` | Pare de reconectar. Entre de novo antes de criar um novo ticket. |

Outras desconexões podem vir sem um motivo do LogBrew. Depois de reconectar,
leia as rotas de lista de novo e associe os itens pelo ID.

## <span id="issue-status-response-examples">Exemplos de resposta de status do problema</span>

`PATCH /api/telemetry/issues/{issue_id}` com `{ "status": "resolved" }`
retorna `200 OK` com o problema agrupado atualizado, no mesmo formato da
[resposta de problema](#issue-response). O parâmetro de consulta `response_version`
escolhe a versão. A rota não retorna um indicador de sucesso.

O corpo define 1 ou mais destes campos: `status`, `priority` e `assignee`.
`status` aceita `unresolved`, `resolved` ou `archived`. `ignored` é um nome
antigo de `archived`. Consulte
[Atualizar um problema](/pt-BR/reference/telemetry-api#update-one-issue).

Confira `id`, `status` e `priority` retornados antes de mostrar sucesso. Não
monte o resultado com os valores enviados. Uma mudança de status não exclui
ocorrências nem altera `first_seen_at` e `last_seen_at`. Ela não altera
`severity` nem uma regra de gravidade.

Uma alteração rejeitada retorna `422` com `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Resultado | Causa |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | O corpo não tem nenhum dos 3 campos. |
| `422`, `issue priority must be high, medium, or low` | O valor de prioridade não é aceito. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | O valor de responsável não é aceito. |
| `422`, `issue assignee cannot read this project` | O responsável não tem acesso ao projeto. O LogBrew não altera nada. |
| `422`, `issue assignee team is not a team of this project's organization` | A equipe não pertence à organização do projeto. O LogBrew não altera nada. |
| `403` com `code: forbidden` | A conta não pode gerenciar problemas no projeto. |
| `404` com `code: not_found` | A conta não pode ler o problema, ou o problema não existe. |

Um campo que já tem o valor solicitado não muda. Depois de um timeout ou de uma
resposta perdida, envie a mesma requisição de novo ou leia o problema primeiro.
Não envie uma alteração diferente antes de ler o estado atual. Consulte
[Escritas](/pt-BR/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` retorna `200 OK` com 1 resultado para cada
ID de problema solicitado, na ordem da requisição. Cada problema encontrado usa
o formato da versão 3. Um resultado `not_found` tem `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

Este exemplo mostra só alguns campos do problema. `outcome` é `updated`,
`unchanged` ou `not_found`. Uma requisição repetida retorna `unchanged` e não
altera nada. Consulte
[Atualizar problemas em lote](/pt-BR/reference/telemetry-api#update-issues-in-bulk).

Uma requisição em lote falha por inteiro nestes casos:

| Resultado | Causa |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | A lista está vazia ou tem mais de 100 IDs. |
| `422`, `issue_ids must not contain duplicates` | Um ID aparece mais de uma vez. |
| `422` com `code: invalid_json` | O corpo tem um campo desconhecido. |
| `403` com `code: forbidden` | A conta não pode gerenciar problemas no projeto. |
| `404`, `project not found` | A conta não pode ler o projeto. |

## Escopo das requisições de análise

As rotas de análise, a rota de séries de métricas e a rota de volume de sinais
leem um projeto e um período. Toda requisição precisa de `project_id` e
`since`. `since` aceita uma duração compacta, como `24h` ou `7d`, ou um
timestamp RFC3339. `until` aceita um timestamp RFC3339 e, por padrão, é o
horário da requisição. O período inclui `since`, exclui `until` e não pode
passar de 31 dias.

`service_name`, `release` e `environment` são filtros exatos opcionais. Cada
valor precisa ter de 1 a 256 caracteres depois que o LogBrew remove os espaços
das pontas. A rota de comparação de segmentos coloca esses filtros dentro de
cada segmento, não no nível superior.

Se a conta não puder ler o projeto, essas rotas retornam `200 OK` com
contagens zeradas. Elas não retornam `404`. Um resultado vazio não confirma o
acesso ao projeto. Compare `project_id` com os projetos que a conta pode ler.
Uma requisição por uma conexão MCP que não inclui o projeto retorna `403` e
`forbidden`.

| Rota | Valores de `response_version` | Padrão |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` ou `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Não aceito | Esquema `1` |
| `POST /api/telemetry/analytics/paths` | Não aceito | Esquema `1` |
| `GET /api/telemetry/metrics/series` | Não aceito | Esquema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Cada resposta começa com `schema_version`, `query` e `purpose`. `query` repete
o escopo efetivo e omite os filtros que você não enviou. `purpose` é um texto
simples que explica o que a rota responde.

Uma taxa é omitida quando o denominador dela é zero. Uma taxa omitida não é
`0` nem `null`. Leia `coverage` antes de confiar em uma taxa.

### <span id="shared-scope-errors">Erros de escopo comuns</span>

Estes erros usam HTTP `422` e `validation_failed`:

| Causa | `error` |
| --- | --- |
| Sem `project_id` | `product analytics project_id is required` |
| Sem `since` | `product analytics since is required` |
| `since` não é uma duração nem um timestamp RFC3339 | `invalid since value` |
| `until` não é um timestamp RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` não é anterior a `until` | `product analytics since must be earlier than until` |
| O período tem mais de 31 dias | `product analytics range must not exceed 31 days` |
| Um filtro vazio, ou um filtro com mais de 256 caracteres | `product analytics context filters must be non-empty and at most 256 characters` |

Por exemplo, uma requisição sem `project_id` retorna:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

As rotas de séries de métricas e de volume de sinais usam as mesmas regras de
escopo, com textos próprios de `error`. As seções delas, mais abaixo, listam
esses erros.

Um parâmetro de consulta desconhecido retorna `422` com a resposta de
[parâmetros de consulta inválidos](/pt-BR/reference/api-errors#invalid-query-parameters).
Um campo JSON desconhecido, a falta de um campo JSON obrigatório ou um valor de
enum não aceito retorna `invalid_json`. Consulte
[JSON inválido](/pt-BR/reference/api-errors#invalid-json). Uma requisição com o
método HTTP errado retorna `405` e `method_not_allowed`. O texto de `next`
dela informa o método e os campos aceitos. Consulte
[Método não aceito](/pt-BR/reference/api-errors#unsupported-method).

## Resposta da visão geral de análise de produto

`GET /api/telemetry/analytics/overview` mostra a atividade de um projeto:
volume de ações, usuários, sessões, uma série temporal, as principais ações e
as visualizações de página, visualizações de tela e interações classificadas.
Use essa rota para encontrar os nomes exatos de eventos das outras rotas de
análise.

`POST /api/telemetry/analytics/funnel` mede a conclusão ordenada de 2 a 8
etapas. Copie cada `kind` e `event_name` exatos de
`classified_activity.top_events` na visão geral. Um nome de ação parecido não
é uma correspondência. Este corpo de requisição conta as sessões que
visualizam `/pricing` e depois concluem o cadastro em até uma hora:

```json
  "until": "2026-08-02T00:00:00Z",
  "environment": "production",
  "analysis_unit": "session",
  "conversion_window_seconds": 3600,
  "steps": [
    { "kind": "page_view", "event_name": "/pricing" },
    { "kind": "interaction", "event_name": "signup_completed" }
```

`analysis_unit` é `session` ou `identified_user`. O padrão é `session`. O
`kind` de cada etapa é `page_view`, `screen_view` ou `interaction`. A rota de
funil não aceita `response_version`.

### Leia a conversão e a cobertura

`entry_rate` é `entered_units` dividido por `candidate_units`: 50 de 60.
`overall_conversion_rate` é `completed_units` dividido por `entered_units`:
15 de 50, ou 30%. Não é 15 dividido por todos os candidatos. Essas contagens
não explicam por que as unidades pararam.

A cobertura conta eventos, não sessões. Aqui, 120 eventos correspondem a uma
etapa, e 20 deles não têm ID de sessão. O resultado exclui esses 20 eventos
das contagens de sessões. Não os trate como 20 sessões que falharam.

A primeira etapa não tem `conversion_from_previous`. A última etapa não tem
`drop_off_to_next_units` nem `drop_off_to_next_rate`.

Uma unidade só chega a uma etapa posterior quando os horários das etapas
aumentam estritamente. Eventos com o mesmo timestamp não podem cumprir duas
etapas seguidas. A etapa final precisa ocorrer em até
`conversion_window_seconds` depois da primeira etapa.

O modo de sessão conta sessões, não pessoas. Use `identified_user` só para
eventos que trazem um ID de identidade opaco do tipo `user`. Esse modo pode
juntar eventos de sessões diferentes dentro da janela de conversão. Mantenha a
mesma unidade e as mesmas etapas ao comparar resultados.

O `conversion_window_seconds` padrão é 24 horas ou a duração do período, o que
for menor. O máximo é a duração do período em segundos inteiros, arredondada
para cima.

### Resultados de funil vazios

Uma resposta vazia bem-sucedida ainda lista as etapas solicitadas com `units`
zerado. Se não houver unidades candidatas, `summary` omite `entry_rate` e
`overall_conversion_rate`. A rota não retorna `404` só porque nenhum evento
corresponde.

Leia `coverage` e `next_action` para encontrar a causa:

| `next_action.code` | Causa |
| --- | --- |
| `capture_product_activity` | Não existem eventos classificados no escopo. |
| `choose_captured_funnel_steps` | Nenhum evento corresponde a uma etapa solicitada. |
| `sessionize_product_activity` | Existem eventos das etapas, mas nenhum tem ID de sessão. |
| `identify_product_users` | Existem eventos das etapas, mas nenhum tem uma identidade do tipo `user`. |
| `verify_funnel_entry` | Nenhuma unidade entrou na etapa 1. |
| `investigate_funnel_drop_off` | Unidades entraram, mas nenhuma concluiu todas as etapas. |
| `compare_funnel_contexts` | Pelo menos uma unidade concluiu o funil. |

### Requisições de funil rejeitadas

Além dos [erros de escopo comuns](#shared-scope-errors), estas requisições
retornam `422` e `validation_failed`. Menos de 2 ou mais de 8 etapas:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Um `conversion_window_seconds` igual a `0`, ou um valor maior que a duração do
período:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Um `event_name` vazio, com mais de 256 caracteres ou com um caractere de
controle retorna
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Uma etapa `interaction` também precisa ter um nome de ação válido. Caso
contrário, o erro é `product analytics interaction event_name must be a bounded stable action name`.

Corrija a requisição antes de enviá-la de novo. Não remova etapas nem mude a
unidade de análise só para obter um resultado não vazio.

## Análise por evento exato e análise automática

Retenção e ciclo de vida aceitam dois formatos de requisição. Use
`response_version` para escolher o formato que responde à sua pergunta:

| Análise | `response_version` | Seletores de evento |
| --- | --- | --- |
| Retenção para eventos exatos | `1`, ou omitido | Envie `start_event` e `return_event`. |
| Ciclo de vida para um evento exato | `1`, ou omitido | Envie `event`. |
| Retenção ou ciclo de vida automáticos | `2` | Não envie seletor de evento. |

Um seletor exato contém `kind` e `event_name`. `kind` é `page_view`,
`screen_view` ou `interaction`. Copie `event_name` de
`classified_activity.top_events`. Não deduza um nome de evento pelo rótulo de
um botão.

Os dois formatos contam só usuários: IDs de identidade opacos do tipo `user`.
Identidades anônimas e eventos sem um ID de identidade utilizável não contam
como usuários. As respostas nunca retornam IDs de identidade.

fixas. `thirty_day` equivale a 30 dias, não a um mês do calendário. Se você
omitir `interval`, a API usa `hour` para um período de até 48 horas e `day`
para um período maior.

### Erros de retenção

Além dos [erros de escopo comuns](#shared-scope-errors), estas requisições
retornam `422` e `validation_failed`:

| Causa | `error` |
| --- | --- |
| Versão 1 sem os dois seletores, versão 2 com um seletor, ou outra versão | `product analytics retention activity selection is contradictory` |
| `interval_count` fora da faixa de `1` a `31` | `product analytics retention interval_count must be between 1 and 31` |
| O número de intervalos de coorte vezes `interval_count` passa de 500 | `product analytics retention interval and interval_count would exceed 500 cohort matrix cells` |

O limite de células depende do período consultado e dos períodos de retenção,
não do número de usuários. Um período de 30 dias com `interval: "hour"` tem
720 intervalos de coorte. Com `interval_count: 1`, são 720 células, mais que
500:

```json
{
  "error": "product analytics retention interval and interval_count would exceed 500 cohort matrix cells",
  "code": "validation_failed",
  "next": "choose a wider interval, a shorter time range, or fewer retention periods",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Para usar a retenção automática, remova os dois seletores. Não altere o SDK
para corrigir esta requisição de leitura.

### Requisição de ciclo de vida por evento exato

Envie este corpo para `POST /api/telemetry/analytics/lifecycle`. Ele
classifica os usuários por um evento, não por toda a atividade do projeto:

```json

  "since": "2026-06-01T00:00:00Z",

  "interval": "day",
```

LogBrew lê como histórico. Ele aceita de `2` a `31`. O padrão é `2`. Um
usuário pode estar inativo para este evento enquanto faz outras atividades.

| Mais de 100 intervalos de análise | `product analytics lifecycle interval would exceed 100 analysis buckets` |

`schema_version: 2` e `query.activity_scope: "all_classified_activity"`. Elas
omitem os seletores. Um seletor diferente pode mudar o resultado sem nenhuma
mudança na atividade capturada.

### Leia uma série de métricas

O primeiro ponto registra 10 tarefas concluídas, não 10 amostras.
`rate_per_second` divide essa variação pelo intervalo de 300 segundos. `last`
é a última variação registrada, não a soma. Consulte
[significados da agregação de métricas](/pt-BR/concepts/telemetry#read-the-metric-value).

O tipo e a temporalidade de uma série definem o `aggregation.code` e as
estatísticas de cada ponto. Um ponto omite as estatísticas que não se
aplicam. Uma estatística ausente não é zero.

| Tipo e temporalidade | `status` | `aggregation.code` | `value` | Outras estatísticas |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Última amostra | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Soma das variações | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 aproximado | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Qualquer tipo, `cumulative` | `limited` | `raw_cumulative_last` | Última amostra bruta | `last`, `min`, `max` |
| Qualquer outro par | `limited` | `raw_last` | Última amostra bruta | `last`, `min`, `max` |

`limited` é uma resposta bem-sucedida, não um erro. Ela adiciona
`aggregation.limitation`, que explica por que o LogBrew mostra só valores
brutos. `ready` não prova que a captura está completa.

Leia `coverage` antes de desenhar um gráfico:

- `samples` conta as amostras de todas as séries correspondentes, incluindo
  séries que a resposta não retorna.
- `series` conta as séries correspondentes. `returned_series` e `points`
  contam os dados retornados.
- `truncated` é `true` quando `series_limit` removeu séries de volume menor.
- `expected_buckets_per_series` é o número de intervalos possíveis no
  período.

Não adicione um ponto para um intervalo sem amostras. Não insira um zero nem
copie o valor anterior. Cada ponto retorna até 3 `trace_exemplars`. Um
exemplar de trace vincula uma amostra a um trace. Ele não explica todas as
amostras do intervalo. Se nenhum ponto tiver um exemplar de trace,
`next_action.target` é `metric_samples`.

### Escopo e erros da série de métricas

`project_id`, `name` e `since` são obrigatórios. `name` pode ter no máximo 200
caracteres. `interval` é `auto`, `1m`, `5m`, `15m`, `1h`, `6h` ou `1d`. O
padrão é `auto`, que escolhe a menor largura de intervalo com no máximo 300
intervalos. Uma largura explícita não pode gerar mais de 500 intervalos.

`group_by` é `none`, `service_name`, `release` ou `environment`. O padrão é
`none`. Sem agrupamento, tipos, unidades e temporalidades diferentes ficam em
séries separadas. `series_limit` aceita de `1` a `20`. O padrão é `10`.

Um resultado vazio retorna `200` com `series: []` e `samples` zerado. O objeto
`coverage` omite `first_seen_at` e `last_seen_at`. Isso não prova que a
aplicação nunca enviou a métrica. Confira o projeto, o nome da métrica e o
período.

Omitir `name` retorna `422`:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Intervalos de um minuto ao longo de sete dias retornam `422`:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Outros erros `422` são `metric series group_by is not supported`,
`metric series interval is not supported` e
`metric series_limit must be between 1 and 20`.

## Resposta da análise de caminhos

`POST /api/telemetry/analytics/paths` encontra os eventos nomeados antes ou
depois de um evento selecionado, na mesma sessão. O evento selecionado é a
âncora. Copie o `kind` e o `event_name` dele de
`classified_activity.top_events`. A rota retorna `schema_version: 1`. Ela não
aceita `response_version` nem `analysis_unit`.

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",

  "anchor": { "kind": "page_view", "event_name": "/checkout" },
  "depth": 2,
  "collapse_repeated": true,
  "path_limit": 2
}
```

`direction` e `anchor` são obrigatórios.

### Leia os caminhos

`share_of_anchored_sessions` divide as sessões de um caminho pelas quatro
sessões com âncora. As parcelas são 50% e 25%, não 67% e 33%.
`unrepresented_sessions` conta as sessões com âncora que nenhum caminho
retornado representa. `paths_truncated: true` significa que o resultado está
incompleto.

A cobertura conta eventos, não sessões. Aqui, cinco eventos correspondem à
âncora, mas um não tem ID de sessão. Esse evento não pode entrar em um
caminho. Cada caminho retorna até 3 exemplares de trace. Use um ID de trace da
sua própria resposta. Um vínculo com um trace não mostra o que causou uma ação
do usuário ou uma falha.

| Campo | Significado |
| --- | --- |
| `following` | Começa na primeira âncora correspondente de cada sessão. A âncora tem a posição `0`. Os nós seguintes têm posições positivas. |

| `path_limit` | Número máximo de caminhos retornados, ordenados pela contagem de sessões. De `1` a `20`. O padrão é `10`. |

Os nós ficam em ordem cronológica nas duas direções. Um caminho não é uma
reprodução completa da sessão. O LogBrew lê no máximo 1024 eventos nomeados
por sessão antes de escolher a âncora: os eventos mais antigos para
`following` e os mais recentes para `preceding`. Uma âncora fora desse limite
pode ser omitida.

### <span id="filter-the-anchor-by-property">Filtre a âncora por propriedade</span>

Envie até quatro `property_filters`, cada um com um `key` e um `value`
exatos. Copie a chave do [catálogo de propriedades](#analytics-property-catalog).
Os filtros valem só para a âncora, não para os eventos ao redor dela. Os
valores diferenciam maiúsculas de minúsculas. Quando há filtros, `query` os
repete, e `coverage.anchor_property_filters` informa:

| Campo | Significado |
| --- | --- |
| `context_events` | Eventos de âncora no escopo antes dos filtros de propriedade. |
| `property_ready_events` | Eventos de âncora que têm todas as chaves solicitadas. |
| `missing_property_events` | Eventos de âncora sem uma ou mais chaves solicitadas. |
| `matching_events` | Eventos de âncora cujos valores correspondem a todos os filtros. |
| `nonmatching_value_events` | Eventos de âncora que têm todas as chaves, mas um valor diferente. |
| `property_ready_rate` | `property_ready_events` dividido por `context_events`. |
| `match_rate` | `matching_events` dividido por `property_ready_events`. |

Chaves ausentes e valores diferentes pedem correções diferentes. Não some os
dois. O objeto é omitido quando a requisição não tem filtro de propriedade.

### Caminhos vazios e requisições rejeitadas

Um array `paths` vazio pode ser uma resposta `200` bem-sucedida. Leia
`summary`, `coverage` e `next_action`. Estes códigos distinguem as causas:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` e
`narrow_or_move_path_anchor`.

Além dos [erros de escopo comuns](#shared-scope-errors), estas requisições
retornam `422` e `validation_failed`:

| Causa | `error` |
| --- | --- |
| `depth` fora da faixa de `1` a `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` fora da faixa de `1` a `20` | `product analytics path_limit must be between 1 and 20` |
| Mais de quatro filtros de propriedade | `product analytics paths accept at most four exact anchor property filters` |
| Uma chave que não está no catálogo de propriedades | `product analytics path property keys must be supported privacy-safe keys` |
| A mesma chave duas vezes | `product analytics path property keys must be unique` |
| Um valor vazio, um valor com mais de 256 caracteres ou um caractere de controle | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

Por exemplo, `depth: 0` retorna:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">Catálogo de propriedades de análise</span>

`GET /api/telemetry/analytics/properties` lista as chaves de propriedade dos
eventos de produto classificados de um projeto. Use as chaves em
[comparações de segmentos](#analytics-segment-comparison) e em filtros de
âncora de caminhos. O catálogo retorna chaves e contagens. Ele nunca retorna
valores de propriedades nem identidades.

### Leia as chaves de propriedade disponíveis

Envie `project_id` e `since`. Você também pode enviar `until`,
`service_name`, `release`, `environment`, `limit` e `response_version`.
`limit` aceita de `1` a `50` chaves. O padrão é `20`. Envie
`response_version=2` para obter o valor público de `estimation.method`.

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/properties" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T00:00:00Z" \
  --data-urlencode "until=2026-06-02T00:00:00Z" \
  --data-urlencode "limit=20" \
  --data-urlencode "response_version=2"
```

## <span id="analytics-segment-comparison">Comparação de segmentos de análise</span>

`POST /api/telemetry/analytics/segments/compare` compara com que frequência
sessões ou usuários chegam a um evento exato em 2 a 4 segmentos de um
projeto. Um segmento seleciona eventos por serviço, versão, ambiente e valores
de propriedades. O primeiro segmento é a referência.

### Defina a comparação

Envie este corpo JSON com a autenticação da conta e
`Content-Type: application/json`. Aqui, `basic` e `premium` são valores de
plano da aplicação de exemplo, não planos do LogBrew:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }
  ]
}
```

`target` e `segments` são obrigatórios. `analysis_unit` é `session` ou
`identified_user`. O padrão é `session`, que conta sessões, não pessoas.
`interval` aceita os mesmos valores da visão geral. O padrão é `auto`.

Cada segmento precisa de um `key` único, um `label` e um conjunto de filtros
diferente:

- `key`: de 1 a 32 bytes. Comece com uma letra ASCII minúscula ou um dígito.
  Use só letras ASCII minúsculas, dígitos, `_` e `-`.
- `label`: de 1 a 80 caracteres, sem caracteres de controle.
- `service_name`, `release`, `environment`: opcionais. Cada valor tem de 1 a
  256 caracteres, sem caracteres de controle.
- `property_filters`: de 0 a 4 filtros. Cada chave pode aparecer uma vez em um
  segmento. Um evento precisa corresponder a todos os filtros do segmento. Os
  valores diferenciam maiúsculas de minúsculas e têm de 1 a 256 caracteres. O
  LogBrew remove os espaços do início e do fim.

Um segmento sem filtros seleciona toda a atividade classificada do projeto no
período. Os segmentos podem se sobrepor. Um rótulo ou uma chave diferente não
torna válidos dois conjuntos de filtros idênticos.

### Leia as taxas e as diferenças

`eligible_units` estima as sessões ou os usuários com atividade classificada
no segmento. `reached_units` estima quantos deles chegaram ao alvo.
`reach_rate` é `reached_units` dividido por `eligible_units`. Eventos sem o ID
da unidade selecionada não contam para essas unidades.

A taxa da referência é 20%. A taxa do premium é 30%. A diferença é de 10
pontos percentuais. O aumento relativo é de 50%, não de 10%. Pequenos erros
nas casas decimais vêm da aritmética de ponto flutuante. Arredonde as taxas
para exibição, mas calcule com os valores retornados. O segmento de referência
não tem `comparison_to_baseline`. O aumento relativo é omitido quando a taxa
de alcance da referência é zero.

Em `query`, um filtro de segmento que você não enviou é `null`. Uma lista
`property_filters` vazia é omitida.

`coverage.property_filters` tem os mesmos campos da
[cobertura dos filtros de âncora de caminhos](#filter-the-anchor-by-property).
Aqui, `matching_events` é igual a `classified_events`. Mantenha separadas as
chaves ausentes e os valores diferentes. Os segmentos podem se sobrepor, e uma
sessão pode aparecer em vários intervalos. Não some contagens de unidades
entre segmentos ou intervalos.

A comparação é descritiva. `confidence.causal_inference` é `not_established`
e `confidence.statistical_significance` é `not_tested`. Uma taxa de 30% contra
20% não mostra que um plano causou mais compras.

### Erros da comparação de segmentos

Além dos [erros de escopo comuns](#shared-scope-errors), estas requisições
retornam `422` e `validation_failed`:

| Dois segmentos com os mesmos filtros | `product analytics segment filters must be unique` |
| Uma chave que não tem de 1 a 32 bytes permitidos | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| Um rótulo vazio, longo demais ou com um caractere de controle | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| Um valor de filtro com um caractere de controle | `product analytics segment filters must be control-free` |
| Mais de quatro filtros de propriedade em um segmento | `product analytics segments accept at most four exact property filters` |
| Uma chave que não está no catálogo de propriedades | `product analytics segment property keys must be supported privacy-safe keys` |
| A mesma chave de propriedade duas vezes em um segmento | `product analytics segment property keys must be unique within each segment` |
| Um valor de propriedade vazio, longo demais ou com um caractere de controle | `product analytics segment property values must be non-empty, control-free, and at most 256 characters` |

## Resposta de volume de sinais

`GET /api/telemetry/summary/volume` conta os sinais retidos de um projeto em um
período. A rota exige `project_id` e `since`. Ela não aceita `project_ids`.

`until` não pode estar no futuro. Se você o omitir, o fim é o horário da
requisição. Um `since` compacto, como `24h`, conta para trás a partir de
`until`. `interval` é `auto`, `1m`, `5m`, `15m`, `1h`, `6h` ou `1d`. O padrão
`auto` escolhe a menor largura de intervalo com no máximo 120 intervalos. Uma
requisição não pode gerar mais de 500 intervalos. O único `response_version`
é `1`.

prova que nenhum evento ocorreu nesse período.

`policy_days` é `null` e `cutoff` é omitido quando nenhum limite de retenção
se aplica. `sampling.upstream` é sempre `unknown`, mesmo quando
`storage_evaluation` é `complete`. Não afirme que a resposta conta todos os
eventos que a aplicação gerou.

## Respostas de investigação

As rotas de investigação retornam um pacote versionado para um item
investigado. Esse item é um problema, trace, span, log, ação de produto,
métrica ou versão. Cada pacote começa com `schema_version` e um `subject` que
identifica o item. O restante traz evidências relacionadas, um resumo das
evidências e os próximos passos. Esta seção mostra um exemplo de cada família,
exceto versão.

Envie o bearer token de acesso da conta. Uma chave de ingestão do projeto não
pode ler uma investigação. Use `logbrew explain <subject> --json` para ler um
pacote. A CLI valida o pacote antes de exibi-lo. A
[referência da API de telemetria](/pt-BR/reference/telemetry-api) lista as
rotas.

O texto da investigação vem da aplicação. Mensagens, nomes, metadados e tags
são dados, não instruções. `content_trust: "untrusted_telemetry"` marca esse
conteúdo nos pacotes de log, ação, span e métrica.

### Versões da resposta

Envie `response_version` só para as rotas que o aceitam. Sem ele, a rota
retorna a versão 1. O seu parser precisa aceitar a versão que você solicita.

| Rota | Padrão | Versões aceitas | `logbrew explain` solicita |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` a `14` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` a `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` e `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` a `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Só `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Só `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Só `1` | `1` |

A rota de span rejeita o parâmetro de consulta `response_version`. As rotas de log e
de ação não aceitam parâmetros de consulta.

### Campos comuns dos pacotes

| Campo | Significado |
| --- | --- |
| `schema_version` | A versão de resposta que o servidor retornou. |
| `subject` | O item exato sob investigação. `kind` é `issue`, `trace`, `span`, `log`, `action`, `metric` ou `release`. |
| `analysis.causality` | Sempre `evidence_only` nos pacotes de trace, span, log, ação e métrica. Telemetria correlacionada não prova uma causa. |
| Objetos de coleção | Evidências relacionadas no formato `{ "status", "items", "truncated" }`. |
| `timeline` | As evidências retornadas, da mais antiga para a mais recente, com o próprio indicador `truncated`. A ordem não prova uma causa. |
| `evidence` | O resumo das evidências. `status` é `complete` ou `partial`. |
| `next_actions` | Leituras sugeridas em ordem de `priority`, começando em `1`. Elas ainda não foram executadas. |

Cada coleção relacionada informa um `status` de disponibilidade:

| Status | Significado | Comportamento do cliente |
| --- | --- | --- |
| `available` | A leitura terminou e retornou itens. | Mostre os itens e o indicador `truncated`. |
| `not_linked` | O item investigado não tem identificador para esse vínculo, como um ID de trace. | Explique a falta do vínculo. Não crie um vínculo a partir de horários. |
| `not_found` | A leitura terminou e não encontrou evidências retidas. | Mostre um resultado vazio. |
| `unavailable` | A leitura opcional falhou. O item investigado continua válido. | Mantenha o item visível. Tente novamente mais tarde. Não mostre zero itens como resultado. |

O resumo das evidências tem quatro listas ordenadas de nomes de campos
estáveis: `captured_fields`, `missing_fields`, `redacted_fields` e
`truncated_fields`. `status` só é `complete` quando as três últimas listas
estão vazias. Dado ocultado não é dado não capturado. Dado truncado não é dado
completo. Não preencha um valor ocultado ou truncado.

### Limites da investigação

Estes limites valem para uma resposta. Um indicador `truncated` ou um item em
`truncated_fields` mostra que um limite omitiu dados.

| Evidências | Limite |
| --- | --- |
| Itens relacionados em uma coleção | 20 |
| Spans retidos lidos para um trace | 1.000 |
| Itens da linha do tempo | 50 nos pacotes de log, ação e span. 100 nos pacotes de trace e métrica. |
| Atributos, propriedades e metadados estruturados | 64 valores escalares, 4 níveis de objetos ou arrays, 16 itens em cada array, 512 caracteres em cada string |
| Período de correlação | 5 minutos antes e depois de um log, de uma ação ou da ocorrência de problema selecionada. Para um trace ou span, 5 minutos antes do início e depois do fim, com no máximo 24 horas. |

A seção de cada família lista os próprios limites.

### Resposta de investigação de problema

Use `GET /api/telemetry/issues/{issue_id}/investigation` para ler as
evidências de uma ocorrência de um problema agrupado. O

Os parâmetros de consulta são `response_version`, `selection` e `occurrence_id`.
`selection` é `recommended`, `first` ou `latest`. Os valores diferenciam
maiúsculas de minúsculas. Nas versões de 2 a 14, quando o seletor é omitido,
vale `recommended`. A versão 1 retorna a ocorrência retida mais recente e não
aceita seletor. Os filtros da lista de problemas não valem para esta leitura.

| Campo | Versão | Significado |
| --- | --- | --- |
| `subject` | 1 | O problema agrupado. `first_seen_at`, `last_seen_at` e `occurrence_count` descrevem o grupo. |
| `event` | 1 | A ocorrência selecionada: SDK, `context`, `exception`, `stack_frames` e `breadcrumbs`. Na versão 1, é `null` quando nenhuma ocorrência mais recente pode ser lida. |
| `cause` | 1 | `status` é `reported_hypothesis`, `evidence_only` ou `unknown`. `signals` lista os sinais observados. |
| `fix` | 1 | Um local no código. `status` é `reported_location`, `observed_application_frame`, `observed_frame`, `observed_underlying_exception_frame` ou `unknown`. |
| `impact` | 1 | Contagens de ocorrências e `user_impact`. `reported` traz o impacto informado pela aplicação, ou `null`. |
| `correlations` | 1 | `trace`, `logs`, `actions`, `metrics` e `release`. |
| `occurrence_selection` | 2 | O seletor solicitado, o motivo e resumos das ocorrências selecionada, primeira, mais recente e recomendada. |
| `lifecycle` | 3 | `persisted_status`, `effective_status`, a atividade de status e `regression`. `effective_status` pode ser `regressed`. |
| `occurrence_analysis` | 4 | A tendência de ocorrências e as distribuições por versão, ambiente, serviço e SDK. |
| `event.exception_chain` | 5 | Até 8 exceções vinculadas. `relationship` é `reported`, `cause`, `context`, `aggregate_member` ou `suppressed`. |
| `event.request` | 6 | `method`, `route_template` e `response_status_code`. A chave não aparece quando nenhuma requisição foi capturada. |
| `grouping` | 7 | A `strategy` de agrupamento, os `components` dela e o uso de frames da pilha. |
| `correlations.release.deployment_status` | 8 | O estado da busca pela implantação. `deployment`, `time_since_deployment_ms` e `deployment_causality` só aparecem quando uma implantação foi encontrada. |
| `correlations.related_issues` | 9 | Outros problemas no mesmo trace. |
| `source_locator` | 10 | Repositório, componente, revisão e arquivo relativo ao repositório, quando o LogBrew consegue vinculá-los. |
| `reproduction` | 11 | `status` é `ready`, `partial` ou `insufficient_evidence`. |
| `next_actions` com o código `verify_correction` | 12 | Aparece quando `reproduction.status` é `ready`. |
| `impact.user_impact.count_method` | 13 | Informa uma contagem distinta aproximada como `approximate_distinct`. Versões anteriores usam um nome de valor mais antigo. `unavailable` significa que não há contagem. |
| `event.breadcrumbs[].data` | 14 | `method`, `url` e `status_code` de uma chamada HTTP, `from` e `to` de uma mudança de rota e `logger` de um registro de log. Um campo que o breadcrumb não tem é `null`. `url` nunca traz query nem fragmento. |

As chaves de uma versão posterior não aparecem em uma versão anterior. Não
interprete uma chave ausente como `null`.

`subject.status` e os status de `lifecycle` informam um problema arquivado
como `ignored`. As respostas de lista e de detalhe de problemas usam
`archived` a partir da versão de resposta 2.

Limites de problemas: a recomendação lê no máximo 50 ocorrências retidas. A
tendência tem no máximo 30 intervalos. Cada distribuição retorna no máximo 10
valores. Uma pilha tem no máximo 32 frames.

#### Erros de requisição da investigação de problema

Use `selection` ou `occurrence_id`. Não envie os dois, mesmo quando eles
selecionam a mesma ocorrência:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Causa | Recuperação |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | A requisição tem os dois seletores. | Mantenha um seletor. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | A requisição tem um seletor e a versão 1, ou nenhuma versão. | Envie `response_version=13`. Mantenha o seletor. |
| `422` | `issue investigation response_version must be 1 through 14` | A versão está fora da faixa. | Envie uma versão aceita. |
| `422` | `invalid query parameters` | Um parâmetro desconhecido, um UUID inválido, uma versão que não é um número inteiro ou um valor de `selection` desconhecido. | Corrija a [consulta](/pt-BR/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | A ocorrência não está no histórico retido deste grupo. | Copie o ID da ocorrência dos eventos deste problema. Não use `latest` ou `recommended` no lugar dele sem aprovação. |
| `404` | `issue not found` | Nenhum projeto que a conta pode ler tem este problema. | Confira a conta e o UUID do problema. Não envie o UUID de uma ocorrência como ID do problema. |

Uma ocorrência inexistente não significa que o problema não existe. Um `404`
não mostra se outra conta pode ler o problema.

### Resposta de investigação de trace

Use `GET /api/telemetry/traces/{trace_id}/investigation` para ler um trace com
o caminho da falha, o caminho mais lento e os sinais relacionados. Os parâmetros
de consulta são `response_version`, `project_id`, `release` e `environment`.
Todos são opcionais. Solicite a versão 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

A versão 2 adiciona `cause` e `fix` a cada problema relacionado. A versão 3
adiciona `span_id` aos problemas, ações e métricas relacionados quando ele foi
capturado.

### Resposta de investigação de span

Use `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` para
ler uma operação de um trace. Envie `project_id`, `environment` e `release`.

linha do span como `span_id`.

```bash
curl --fail-with-body -sS -G \

  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

A linha de base lê as 24 horas antes do início do span. `since` é inclusivo e
`until` é exclusivo. `error_rate_basis_points: 500` significa 5%.
`subject_percentile_basis_points: 9500` significa que 95% dos spans
semelhantes retidos não demoraram mais que este span. Os percentis são

base `not_found` não tem spans semelhantes retidos. Uma linha de base
`unavailable` é uma leitura que falhou, não uma contagem zero.

`parent_chain_status: "complete"` significa que a cadeia retida chega a uma
raiz. Isso não prova que o LogBrew reteve todos os spans da requisição. A
topologia retorna no máximo 64 ancestrais, 50 filhos diretos e 50 ligações
entre serviços.

### Resposta de investigação de log

Use `GET /api/logs/{log_id}/investigation` para ler um log e as evidências
relacionadas. Esta rota não tem parâmetros de consulta. Copie o ID do log de uma
lista de logs.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

A leitura pode retornar evidências fora dos filtros da lista de logs. As
leituras relacionadas usam o projeto, o ambiente e a versão do log, e 5
minutos antes e depois do log. Os logs próximos também usam o mesmo serviço.
Eles não precisam de ID de trace. As leituras pelo trace exato precisam do ID
de trace do log e podem incluir outros serviços. O resumo do trace usa o mesmo
ID de trace e o mesmo escopo, sem o período.

### Resposta de investigação de ação

Use `GET /api/telemetry/actions/{action_id}/investigation` para ler uma ação
de produto, o status informado dela e as evidências relacionadas. Esta rota
não tem parâmetros de consulta. As leituras relacionadas usam o mesmo período e os

de log. As ações relacionadas não incluem a ação investigada.

### Resposta de investigação de métrica

Use `GET /api/telemetry/metrics/investigation` para ler um nome de métrica em
um projeto e um período. A resposta traz a série atual, uma comparação com o
período anterior de mesma duração, a amostra mais recente, exemplares de trace
e as implantações concluídas. A versão 2 adiciona a descrição da métrica a
partir da amostra retida mais recente. A versão 1 sempre informa
`description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` e `since` são obrigatórios. `since` é inclusivo e `until`
é exclusivo. Por padrão, `until` é o momento atual. A comparação também lê o

`expected_buckets_per_series` conta os intervalos possíveis, não os intervalos
com dados. Não desenhe intervalos vazios como zero. Uma implantação perto de
uma variação não prova que ela causou a variação.

`analysis.status: "no_samples"`, não `404`. Um resultado vazio não descreve
outros tipos de sinal.

500 intervalos. `series_limit` vai de 1 a 20, com padrão 10. A resposta
retorna no máximo 20 exemplares e 20 implantações.

| HTTP | `error` | Recuperação |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Omita `response_version` ou envie `2`. |
| `422` | `metric series project_id is required` | Envie o ID de um projeto que a conta pode ler. |
| `422` | `metric series name is required` | Copie o nome da lista de métricas. |
| `422` | `metric series since is required` | Envie um valor como `24h` ou um timestamp RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | Use um período menor. |
| `422` | `metric series interval would exceed 500 buckets` | Use `interval=auto` ou um intervalo maior. |
| `422` | `metric series_limit must be between 1 and 20` | Envie um valor de 1 a 20. |

`interval` é `auto`, `1m`, `5m`, `15m`, `1h`, `6h` ou `1d`. `group_by` é
`none`, `service_name`, `release` ou `environment`. Outros valores retornam
`422`.

### Erros de investigação

| HTTP | Rota | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Ação | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, ação, problema | `invalid URL path parameters` quando o ID no caminho não é um UUID |
| `422` | Problema, trace, span, métrica | `invalid query parameters` para uma chave desconhecida ou um valor do tipo errado |

Um `404` significa que nenhum projeto que a conta pode ler tem o registro.
Cada rota também retorna `401` sem autenticação válida e `405` para um método
diferente de `GET`. Consulte [Erros da API](/pt-BR/reference/api-errors) para
ver as respostas de
[recurso não encontrado](/pt-BR/reference/api-errors#resource-not-found),
[caminho](/pt-BR/reference/api-errors#invalid-path-value),
[autenticação](/pt-BR/reference/api-errors#authentication-failure) e
[método](/pt-BR/reference/api-errors#unsupported-method).

Uma leitura opcional de evidências pode falhar dentro de uma resposta
`200 OK`. Nesse caso, a coleção informa `unavailable`. Não a mostre como
`not_found` nem como zero registros.

## <span id="severity-values">Valores de gravidade</span>

Os valores de gravidade exibidos às pessoas são `info`, `warning`, `error` e
`critical`. SDKs e runtimes podem enviar aliases comuns, como `trace`,
`debug`, `warn` ou `fatal`. As respostas REST e ao vivo sempre retornam o valor
canônico. Por exemplo, o LogBrew aceita `warn` na entrada e retorna `warning`.
A ingestão rejeita valores de gravidade desconhecidos.

| Alias | Valor canônico |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Respostas de regras de gravidade</span>

Uma regra de gravidade muda como o LogBrew mostra um log ou um problema. Ela
não muda a gravidade que a aplicação capturou. Logs e problemas retornam um
objeto `triage`:

| Campo | Significado |
| --- | --- |
| `effective_severity` | A gravidade a exibir. Sem regra, é igual a `severity`. |
| `ignored` | `true` quando uma regra de log ignora o log, ou quando o problema está arquivado. |
| `rule_applied` | `true` quando uma regra de gravidade ou o estado ignorado se aplica. `false` é o padrão, não um dado ausente. |

Use `triage.effective_severity` para exibir a gravidade. Mantenha `severity`
como o valor capturado. Por padrão, a lista de logs omite os logs ignorados.
Para incluí-los, envie `status=ignored` ou `status=all` em `GET /api/logs`.

A conta precisa de permissão para gerenciar problemas no projeto. Acesso de
leitura não basta. Sem essa permissão, uma mudança de regra retorna `403` com
`code: forbidden`.

### Altere uma regra de log

`PUT /api/logs/{log_id}/triage-rule` define a regra para o log e para os logs
posteriores com a mesma assinatura. O corpo precisa de `severity` e de
`ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Uma resposta `200 OK` contém o [log](#log-response) completo. O `severity`
dele continua `warning`. O `triage` mostra a regra:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Este trecho mostra só os campos alterados. Na requisição, `severity` é
`source`, `info`, `warning`, `error` ou `critical`. `source` restaura a
gravidade capturada. Ele não torna ativo um log ignorado. Para mostrar o log
de novo, envie `"ignored": false`.

### Altere uma regra de problema

`PUT /api/telemetry/issues/{issue_id}/triage-rule` define a gravidade exibida
de um problema agrupado e das ocorrências posteriores dele. O corpo aceita só
`severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Uma resposta `200 OK` contém o [problema](#issue-response) completo na versão
1 da resposta. O `severity` e o `status` capturados não mudam:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Este trecho mostra só alguns campos. Uma regra não resolve, não arquiva nem
reabre um problema. Para isso, use a
[mudança de status](#issue-status-response-examples). Uma prioridade derivada
acompanha a nova gravidade efetiva. Para vê-la, leia o problema com
`response_version=2` ou `3`.

Uma gravidade não aceita retorna `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Um campo desconhecido no corpo, como `status` em uma regra de problema,
retorna `422` com `code: invalid_json`. Um log ou problema inexistente, ou que
a conta não pode ler, retorna `404` com `code: not_found`. Se a resposta se
perder, leia o log ou o problema de novo antes de reenviar a regra.

## Formato da resposta de erro

Os erros da aplicação retornam um envelope JSON. Este exemplo mostra uma
requisição rejeitada. O texto de `error` e de `next` varia conforme o erro:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Use `code` para as ramificações do programa e `next_action` para automação.
Mostre `error` e `next` às pessoas como texto simples. Não analise a redação
deles. Alguns erros adicionam campos, como `limit`, `reset_at` ou
`retry_after_seconds`. Uma resposta sem corpo JSON não tem `code` do LogBrew.
Consulte [Erros da API](/pt-BR/reference/api-errors) para ver todos os
códigos.

## Leia dados com a CLI

A CLI lê as mesmas rotas e retorna o mesmo JSON com `--json`. Comece com uma
leitura ampla e depois restrinja:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Adicione `--pagination cursor` para receber o envelope de cursor. A CLI
solicita a versão 4 da resposta de problemas. Consulte
[Ler a próxima página](/pt-BR/reference/cli#read-the-next-page) e
[Acompanhamento ao vivo](/pt-BR/reference/cli#live-watch).

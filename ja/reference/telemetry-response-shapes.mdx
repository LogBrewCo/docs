このページでは、[テレメトリ API](/ja/reference/telemetry-api) のレスポンスの種類ごとに例を1つずつ示します。値はすべて架空のものです。エラーコードと対処方法は、[API エラー](/ja/reference/api-errors)を参照してください。

## レスポンスを読む

どのレスポンスも、次の順に読みます。

1. HTTP ステータスを確認します。
2. 本文が、そのルートが定める形になっていることを確認します。
3. 各 `project_id` が、リクエストしたプロジェクトの範囲内にあることを確認します。
4. 正規の列挙値と識別子は、変更せずにそのまま使います。
5. `next_action` には、クライアントがその `code` と `target` に対応している場合にだけ従います。
6. `null`、省略されたフィールド、空のリストは、それぞれ別の状態として扱います。

`200 OK` でも、空のリストを返すことがあります。ログの一覧が空なら、リクエストに一致したログがなかったという意味です。課題、トレース、アクションも空だという意味ではありません。タイムスタンプが近いという理由だけで、シグナル同士を結び付けないでください。トレースをたどるのは、レスポンスにそのトレースの `trace_id` が正確に含まれている場合だけにしてください。

`404` と空のリストは、別の結果です。一覧のルートは、一致するレコードがないと `[]` を返します。詳細のルートは、読み取れるレコードが見つからないと、`code: not_found` 付きの `404` を返します。どちらの結果も、取り込みが失敗したことの証明にはなりません。

## 送信する値

レスポンスが役に立つかどうかは、送信するテレメトリ次第です。どのエンベロープや SDK の設定でも、次の値を送信してください。

- `release` と `environment`。
- サービス、アクション、メトリクスの、変わらない名前。
- ログ、スパン、アクション、課題が同じリクエストに属する場合は、トレースコンテキスト。
- 正規の重大度の値：`info`、`warning`、`error`、`critical`。
- デバッグに役立つ属性。ただし、シークレットや不要な個人データは含めないでください。

[SDK 連携](/ja/guides/sdk-ingestion)と[取得するデータを管理する](/ja/guides/safe-capture)を参照してください。

## 取り込みのレスポンス

公開 SDK は、`POST /v1/events` のレスポンスを自動で読み取ります。アプリケーションのコードで処理する必要はありません。

### SDK バッチのレスポンス

SDK のバッチが成功すると、ストリームごとの受け付け件数とともに `200 OK` が返ります。

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| フィールド | 意味 |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | このバッチのうち、LogBrew が受け付けたイベント。 |
| `already_accepted` | 同じ ID のイベントを LogBrew が以前に受け付けていたもの。LogBrew はこれらを再び保存しません。 |
| `context_updated` | バッチがリリースまたは環境のコンテキストを更新した場合は `true`。 |

件数は、このバッチの分だけです。LogBrew がすでに受け付けたバッチを再試行すると、各ストリームは `0` を返し、`already_accepted` にイベントの件数が入ります。再試行するときは、元のイベント ID をそのまま使ってください。

### ネイティブエンベロープのレスポンス

`POST /api/telemetry/ingest` は、ストリームごとの受け付けた項目の件数とともに `200 OK` を返します。

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

ネイティブのレスポンスには、`metrics` フィールドも `context_updated` フィールドもありません。これらを追加しないでください。`already_accepted` は、そのプロジェクトで同じ `id` の項目を LogBrew が以前に受け付けていた件数です。[ネイティブエンベロープを直接送信する方法](/ja/guides/sdk-ingestion#required-envelope-fields)を参照してください。

### 取り込みのエラー

`code: ingest_key_invalid` 付きの `401` は、取り込み用の Bearer トークンが無効化されたか、期限切れか、そのプロジェクトで有効でないことを示します。`POST /v1/events` では、Bearer トークンがない場合や、取り込みキーではない Bearer トークンを使った場合に、`code: unauthorized` 付きの `401` が返ります。現在の、プロジェクト単位の取り込み用 Bearer トークンを使ってください。アカウントの Bearer トークンで再試行しないでください。

SDK のバッチが拒否されると、`code: validation_failed` 付きの `422` が返ります。

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`error` の値には、ほかに `SDK event batch requires at least one event` と `SDK event type is not supported by this ingest route` があります。SDK のバージョンとトランスポートの設定を確認してください。空のバッチは送信しないでください。検証を通すためだけに、イベントの種類や ID を変更しないでください。

`POST` 以外のメソッドのリクエストには、`code: method_not_allowed` 付きの `405` が返ります。読み取れない JSON 本文には、`code: invalid_json` が返ります。

## テレメトリ一覧のレスポンス形式

一覧のルートは、デフォルトでは JSON 配列をそのまま返します。成功して結果が空の場合は `[]` です。

`pagination=cursor` を指定すると、ルートはエンベロープを返します。コレクションのキーはシグナルに対応します。

| ルート | コレクションのキー |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`。最上位に `issue_id` も入ります |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`。最上位に `naming_quality` も入ります |

`next_cursor` は、続きを読むためのフィールドを持つオブジェクトです。最後のページでは `null` になります。行は新しい順に並びます。[カーソルベースのページネーション](/ja/reference/telemetry-api-filters#cursor-pagination)を参照してください。

### <span id="log-response">ログのレスポンス</span>

`limit=1` を指定した、ログのカーソルページの例です。

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

ログには、互換性のための `level` と、表示用の `severity` が含まれます。どちらにも正規の値が入ります。`triage` には、重大度ルールを適用した結果が入ります。[重大度ルールのレスポンス](#severity-rule-responses)を参照してください。

ログにトレースへのリンクがない場合、`trace_id` と `span_id` は `null` です。このとき `next_action` は `inspect_related_logs` で、ターゲットは `telemetry_logs` です。ログ、課題、アクションは、同じ2組の `next_action` を使います。

`GET /api/logs/{log_id}` は、1件のログを同じ形で返します。

### <span id="issue-response">課題のレスポンス</span>

`GET /api/telemetry/issues/{issue_id}` は、グループ化された課題を1件返します。一覧も同じオブジェクトを返します。この例では、デフォルトのレスポンスバージョン1を使います。

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

バージョン1では、`status` は `unresolved`、`resolved`、`ignored` のいずれかです。アーカイブ済みの課題では、`triage.ignored` が `true` になります。`next_action` の組み合わせと、それに続けて行う読み取りについては、[課題を調査する](/ja/guides/investigate-an-issue)を参照してください。

`first_seen_at` と `last_seen_at` は、最初の発生事象と最新の発生事象の時刻です。ステータスが変わっても、これらは変わりません。

一部のフィールドは、LogBrew がそのデータを持っている場合にだけ含まれます。

| フィールド | 含まれる条件 |
| --- | --- |
| `span_id` | 課題にスパンへのリンクがある場合。ない場合、このフィールドは省略されます。 |
| `diagnostics` | 最新の発生事象に、例外の型または直前の手順がある場合。[課題の発生事象の履歴](#issue-occurrence-history)を参照してください。 |
| `symbolication` | `GET /api/telemetry/issues/{issue_id}` だけで、課題にリリースのビルド成果物の識別情報がある場合。[JavaScript ソースマップ](/ja/guides/source-maps)を参照してください。 |

`symbolication.status` は、`resolved`、`invalid_metadata`、`artifact_not_found`、`source_not_resolved`、`unavailable` のいずれかです。一覧、ステータスの変更、ルールの変更では、`symbolication` は返りません。

`response_version=2` を指定すると、課題は同じフィールドを持ち、次の点が変わります。

| フィールド | バージョン2の値 |
| --- | --- |
| `status` | `unresolved`、`resolved`、`archived` のいずれか。バージョン1では、`archived` は `ignored` と表示されます。 |
| `priority` | `high`、`medium`、`low` のいずれか。 |
| `priority_source` | 人が優先度を設定した場合は `manual`。優先度が実際に適用された重大度に従う場合は `derived`。 |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

この例は、一部のフィールドだけを示しています。導出された優先度は、`error` と `critical` では `high`、`warning` では `medium`、`info` では `low` になります。この優先度は `triage.effective_severity` に基づくため、課題の重大度ルールで変わることがあります。

`response_version=3` を指定すると、課題はバージョン2のすべてのフィールドに加えて、`assignee` を持ちます。課題に担当者がいない場合、`assignee` は `null` です。

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| フィールド | 意味 |
| --- | --- |
| `assignee.user_id` | 担当者のユーザー ID。フィルターや変更では、これを `assignee` として送信します。 |
| `assignee.name` | 担当者の名前。アカウントに名前がない場合は `null`。 |
| `assignee.email` | 担当者のメールアドレス。 |

割り当てられたメンバーがプロジェクトを読み取れなくなると、その課題は担当者なしとして表示されます。

`response_version=4` では、`assignee` に `type` も含まれます。`user` の担当者には、バージョン3と同じく `user_id`、`name`、`email` があります。`team` の担当者には `team_id`、`slug`、`name` があります。バージョン3では、チームの担当者は `null` と表示されます。CLI はバージョン4をリクエストします。

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

それ以外の `response_version` では、`code: validation_failed` 付きの `422` が返ります。カーソルページでは、`issues` 内のすべての課題に同じバージョンが使われます。

### <span id="assignee-list-response">担当者の一覧のレスポンス</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` は、そのプロジェクトで課題を割り当てられるすべてのアカウントを返します。

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

`response_version=2` を追加すると、`teams` も取得できます。プロジェクトの組織に属するすべてのチームが、`team_id`、`slug`、`name` とともに含まれます。

アカウントがプロジェクトを読み取れない場合、このルートは `code: not_found` 付きの `404` を返します。

### <span id="action-response">アクションのレスポンス</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` は、1人のアクターまたは1つのセッションを追跡します。`distinct_id` と `session_id` は、不透明な識別子として扱ってください。`session_id` と `trace_id` は、値がない場合は `null` です。`span_id` は、値がない場合は省略されます。アクションには重大度がありません。[プロダクトイベントの取得](/ja/guides/product-events)を参照してください。

### メトリクスのレスポンス

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

各項目は1つのサンプルです。サンプルの数を、イベント数やユーザー数として使わないでください。`unit`、`temporality`、`trace_id`、`span_id` は、値がない場合は `null` です。`null` はゼロではありません。

### リリースのレスポンス

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

1行は、1つのプロジェクト、リリース、環境、サービスの組み合わせに対応します。その件数は、その行だけを表します。

`trace_health.status` は、行にトレースがない場合は `unknown`、それ以外は `no_errors_observed` または `errors_observed` です。`error_rate_basis_points` は、エラーのスパンを含むトレースの割合で、`0` から `10000` までの値です。すべてのリクエストのエラー率ではありません。

`next_action` は、データがある最初のシグナルの種類を、次の順で指します。

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

[リリース](/ja/concepts/releases)を参照してください。

### トレースの検索のレスポンス

`GET /api/telemetry/traces?pagination=cursor` は、トレースごとに1行を返し、返したページについての `naming_quality` の集計も返します。

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` は、返したページだけを対象にします。アカウント全体のスコアではありません。`truncated: true` は、次のページがあることを示します。ページに汎用的な名前、一致しないルート、汎用的な処理の種類がある場合、`next_action` は `improve_trace_naming` で、ターゲットは `sdk_configuration` です。`pagination=cursor` を指定しない場合、このルートはトレースの配列をそのまま返し、`naming_quality` は返しません。

`next_cursor` には `time` と `trace_id` が入ります。これらを `cursor_time` と `cursor_trace_id` として送信します。

`response_version=2` を指定すると、各トレースに `capture_span_count` と `capture_error_count` も入ります。その場合、`span_count` と `error_span_count` には[取得用のスパン](/ja/concepts/distributed-tracing#capture-spans)が含まれません。バージョン1では含まれます。`status=error` は、`error_span_count` または `capture_error_count` が `0` より大きいトレースに一致します。

`GET /api/telemetry/traces/{trace_id}` は、1つのトレースのスパンを返します。`GET /api/telemetry/traces/{trace_id}/summary` は、ルートスパン、エラーのスパン、サービス、所要時間、最も遅い経路を返します。スパンの生の属性は返しません。概要の `404` は、指定した範囲全体に一致するトレースがなかったことを示します。フィルターを外して再試行しないでください。[トレースのスパンと概要のレスポンス](#trace-spans-and-summary-responses)を参照してください。

### 空の一覧と存在しないレコード

一覧の読み取りでは、一致するものがないことがあります。詳細の読み取りは、別の決まりに従います。

| リクエスト | 成功 | 読み取れるレコードがない場合 |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | 1件の[ログ](#log-response)とともに `200` | `code: not_found` 付きの `404` |
| `GET /api/telemetry/issues/{issue_id}` | 1件の[課題](#issue-response)とともに `200` | `code: not_found` 付きの `404` |
| `GET /api/telemetry/issues/{issue_id}/events` | 発生事象とともに `200` | 最初のページで `code: not_found` 付きの `404` |
| `GET /api/telemetry/traces/{trace_id}` | スパンとともに `200` | `[]` とともに `200` |
| `GET /api/telemetry/traces/{trace_id}/summary` | 1件の概要とともに `200` | `code: not_found` 付きの `404` |

ログが存在しない場合は、次の `404` が返ります。

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

課題が存在しない場合は `"error": "issue not found"`、トレースの概要が存在しない場合は `"error": "trace not found"` が返ります。存在しない ID と、アカウントが読み取れない ID には、同じレスポンスが返ります。

アカウントが読み取れない `project_id` を1つ指定した一覧は、`404` と `"error": "project selection not found"` を返します。存在しないプロジェクト ID にも、同じレスポンスが返ります。[拒否されるプロジェクトの指定](#rejected-project-selections)を参照してください。

### <span id="rejected-project-selections">拒否されるプロジェクトの指定</span>

ログ、課題、アクション、メトリクス、リリース、トレースの一覧では、`project_id` で1つのプロジェクトを指定するか、`project_ids` で2〜50個のプロジェクトを指定できます。ログの属性カタログも、同じ指定方法を受け付けます。課題の発生事象の履歴は、これらを受け付けません。

`project_id` と `project_ids` の両方を指定したリクエストには、`422` が返ります。

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` に無効な UUID や重複した ID が含まれる場合や、ID の数が2個未満または50個を超える場合も、`code: validation_failed` 付きの `422` が返ります。

アカウントが `project_id` のプロジェクトを読み取れない場合、または `project_ids` の中に読み取れないプロジェクトが1つでもある場合、リクエスト全体が `404` を返します。ほかのプロジェクトの結果を一部だけ返すことはありません。

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

空の一覧やゼロ件ではなく、このエラーを表示してください。プロジェクトの一覧を読み直してください。プロジェクトを黙って除外したり、すべてのプロジェクトに広げて再試行したりしないでください。MCP の接続のような委任された認証情報では、その許可の範囲外のプロジェクトに対して `code: forbidden` 付きの `403` が返ります。[プロジェクトの範囲](/ja/reference/telemetry-api-filters#project-scope)を参照してください。

### <span id="cursor-errors">カーソルのエラー</span>

ログ、課題、アクション、メトリクス、課題の発生事象では、`cursor_time` と `cursor_id` を使います。拒否されたカーソルには、`code: validation_failed` 付きの `422` が返ります。これらのエラーは、一覧が空だという意味ではありません。

| リクエスト | `error` |
| --- | --- |
| `pagination=cursor` で、2つのカーソルフィールドのうち1つだけを送信した | `cursor_time and cursor_id must be sent together` |
| `cursor_time` が RFC3339 形式のタイムスタンプではない | `cursor_time must be an RFC3339 timestamp` |
| `pagination=cursor` なしでカーソルフィールドを送信した、または `pagination` に別の値を指定した | `pagination must be cursor when cursor pagination is requested` |

例：

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

前のページの `next_cursor` を、そのまま全部コピーしてください。`cursor_time` を現在時刻に置き換えないでください。カーソルを失った場合は、`pagination=cursor` と元のフィルターで最初から読み直してください。不明なクエリキーや、型の違う値を送信すると、`"error": "invalid query parameters"` 付きの `422` が返ります。

### リリースのカーソルのレスポンス

リリースのカーソルには5つのフィールドがあります。リクエストが成功して一致するものがない場合は、`200` が返ります。

```json
{
  "releases": [],
  "next_cursor": null
}
```

`next_cursor` が `null` でない場合は、次のリクエストで5つの値をすべて送信します。

| `next_cursor` のフィールド | クエリパラメーター |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` は位置を示す値です。`project_id` や `project_ids` の代わりにはなりません。元のプロジェクトとフィルターのパラメーターは、そのまま使ってください。それぞれの値は URL エンコードしてください。

`pagination=cursor` で、カーソルの一部だけを送信した場合や、リリース、環境、サービスの値が空の場合は、`"error": "all release cursor fields must be sent together"` 付きの `422` が返ります。無効な `cursor_time` と、`pagination=cursor` がない場合には、[ほかのカーソル](#cursor-errors)と同じエラーが返ります。

### トレースの検索のエラー

これらのエラーは `GET /api/telemetry/traces` に適用されます。どれも `code: validation_failed` 付きの `422` を返します。拒否されたリクエストは、空の結果ではありません。

| リクエスト | `error` |
| --- | --- |
| `status` が `error` でも `ok` でもない | `trace status must be error or ok` |
| `min_duration_ms` が `0` 未満 | `minimum trace duration must not be negative` |
| カーソルフィールドが1つだけ、または `cursor_trace_id` が空 | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` が RFC3339 形式のタイムスタンプではない | `cursor_time must be an RFC3339 timestamp` |
| `pagination=cursor` なしでカーソルフィールドを送信した | `pagination must be cursor when cursor pagination is requested` |
| `response_version` が `1` でも `2` でもない | `trace response_version must be 1 or 2` |

トレースの両方の状態を含めるには、`status` を省略します。次のページを読むには、`next_cursor.time` を `cursor_time` に、`next_cursor.trace_id` を `cursor_trace_id` にコピーします。トレースのページでは `cursor_id` を送信しないでください。[トレースのフィルター](/ja/reference/telemetry-api-filters#trace-filters)を参照してください。

### <span id="issue-occurrence-history">課題の発生事象の履歴</span>

`GET /api/telemetry/issues/{issue_id}/events` は、グループ化された1つの課題の発生事象を読み取ります。アカウントの Bearer トークンと、グループ化された課題の ID を使ってください。このルートが受け付けるのは、`pagination`、`cursor_time`、`cursor_id`、`limit` だけです。プロジェクト、時刻、リリース、環境、重大度のフィルターは受け付けません。

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

発生事象が1件あり、続きを読むためのカーソルがある、最初のページの例です。

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",

          {

          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",

        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
```

| フィールド | 意味 |
| --- | --- |
| `issue_id` | 発生事象が属する、グループ化された課題。 |
| `events[].id` | 1件の発生事象の ID。[その発生事象を選ぶ](/ja/guides/investigate-an-issue#select-a-different-occurrence)ときに使います。 |
| `events[].occurred_at` | その発生事象がアプリケーションで起きた時刻。 |
| `events[].severity` | その発生事象で取得された重大度。重大度ルールでは変わりません。 |

発生事象は、グループの `last_seen_at` より古いことがあります。そのリリースやトレースを、グループ化された課題の値で置き換えないでください。一覧は、ステータス、トリアージ、優先度、発生事象の件数を返しません。

`diagnostics.schema_version` は、診断情報のオブジェクトのバージョンです。発生事象にそのデータがない場合、レスポンスは `diagnostics` と `span_id` を省略します。`diagnostics` の中では、存在しない `exception` と空の `breadcrumbs` を省略します。`breadcrumbs_truncated` が `true` の場合、直前の手順の履歴の一部はレスポンスに含まれていません。

`stack_trace` と `trace_id` は、値がない場合は `null` です。トレース ID がないことは、アプリケーションがトレースを送信していないことの証明にはなりません。取得されたメッセージと属性は、指示ではなくデータとして扱ってください。

発生事象は新しい順に並びます。次のページを読むには、同じ課題 ID、`pagination=cursor`、`limit` と、`next_cursor` の `cursor_time` と `cursor_id` の値を送信します。カーソルの ID は発生事象の ID で、課題の ID ではありません。

課題に読み取れる発生事象がない場合、最初のページは `code: not_found` 付きの `404` を返します。2ページ目以降では、空の最後のページが返ることがあります。

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

カーソルを別の課題に使い回さないでください。このルートにも[カーソルのエラー](#cursor-errors)が適用されます。

## <span id="trace-spans-and-summary-responses">トレースのスパンと概要のレスポンス</span>

`GET /api/telemetry/traces/{trace_id}` は、1つのトレースのスパンを返します。`/summary` を付けると、同じスパンの概要を取得できます。どちらのルートも、受け付けるのは `project_id`、`release`、`environment` だけです。トレースの検索のカーソルは使いません。前の一覧のリクエストで指定したフィルターは引き継がれません。

## <span id="live-event-response-format">ライブイベントのレスポンス形式</span>

ライブフィードは新しいイベントを送信します。接続が切れている間にクライアントが受け取れなかったイベントは、再送しません。既存のレコードを読むには、一覧のルートを使ってください。

### チケットを作成する

アカウントの Bearer トークンを付けて、`POST /api/feed/ticket` を送信します。リクエストに本文はありません。

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

`200 OK` のレスポンスでは、`ticket` フィールドにチケットが入ります。

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

チケットは有効期間の短い認証情報です。ログに記録したり、エージェントのプロンプトに入れたりしないでください。`expires_in_seconds` が過ぎる前に接続を開いてください。この有効期限は、接続を開始できる期限です。接続を開いていられる時間ではありません。

`401` は、アカウントのサインインが有効でないことを示します。チケットをリクエストする前に、もう一度サインインしてください。`POST` 以外のメソッドには、`code: method_not_allowed` 付きの `405` が返ります。

### 接続を開く

WebSocket クライアントを `wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>` に接続します。チケットは URL エンコードしてください。アカウントの Bearer トークンや取り込み用の Bearer トークンを URL に入れないでください。`401` は、チケットまたはアカウントのサインインが有効でないことを示します。もう一度サインインしてから、新しいチケットを作成してください。

| レスポンス | 原因 | 次の手順 |
| --- | --- | --- |
| `"error": "feed ticket is required"` 付きの `422` | クエリの `ticket` の値がないか、空です。 | チケットを作成し、それを使って接続します。 |
| `code: unauthorized` 付きの `401` | チケットが期限切れか、有効ではありません。 | 新しいチケットを作成します。同じチケットで再試行しないでください。 |
| `code: invalid_websocket_upgrade` | リクエストが有効な WebSocket のアップグレードではありません。 | WebSocket クライアントを使います。 |
| `code: method_not_allowed` 付きの `405` | リクエストが `GET` を使っていません。 | 接続には `GET` を使います。 |

エラーのあとは、少し待ってから再接続してください。間を空けずに再接続を繰り返さないでください。

### メッセージを読む

各メッセージは `{ "type": "...", "data": ... }` 形式のエンベロープです。`data` を解析する前に `type` を読んでください。クライアントが対応していない種類は読み飛ばしてください。

| イベントの種類 | データのペイロード |
| --- | --- |
| `native_log` | ログのデータ。[ログのレスポンス](#log-response)と同じ形です。 |
| `native_issue` | グループ化された課題のデータ。バージョン1の[課題のレスポンス](#issue-response)と同じ形です。 |
| `native_trace_span` | 1つのスパン。[スパンの一覧](#span-list)の項目と同じ形です。 |
| `native_action` | プロダクトアクションのデータ。[アクションのレスポンス](#action-response)と同じ形です。 |
| `project_created`, `project_updated`, `project_catalog_changed` | プロジェクトのデータ。変更があったら、プロジェクトの一覧を読み直してください。 |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | アカウントの使用量。[アカウントの使用量](/ja/reference/account-api#account-usage)と同じ形です。 |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }

```

`native_issue` イベントは、課題のレスポンスのバージョン1を使います。アーカイブ済みの課題は `ignored` と表示され、イベントには優先度がありません。メトリクスとリリースは、ライブイベントの種類にはありません。それぞれの一覧のルートで読んでください。チケットはプロジェクトを選びません。プロジェクトのビューに表示する前に、各イベントの `project_id` を確認してください。`logbrew watch --json` はこのフィードを使います。[CLI リファレンス](/ja/reference/cli)を参照してください。

### 切断された接続を処理する

| クローズコード | 理由 | 次の手順 |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | 少し待ってから、新しいチケットで再接続します。受け取れなかったレコードを取得するため、一覧のルートを読み直します。 |
| `1008` | `live feed access changed; sign in again` | 再接続をやめます。もう一度サインインしてから、新しいチケットを作成します。 |

LogBrew の理由がないまま切断されることもあります。再接続したら、一覧のルートを読み直し、ID でレコードを照合してください。

## <span id="issue-status-response-examples">課題のステータスのレスポンス例</span>

`{ "status": "resolved" }` を付けて `PATCH /api/telemetry/issues/{issue_id}` を送信すると、更新されたグループ化された課題とともに `200 OK` が返ります。形は[課題のレスポンス](#issue-response)と同じです。バージョンは、クエリキーの `response_version` で選びます。成功を示すフラグは返りません。

本文では、`status`、`priority`、`assignee` のうち1つ以上を設定します。`status` には `unresolved`、`resolved`、`archived` を指定できます。`ignored` は `archived` の古い名前です。[1件の課題を更新する](/ja/reference/telemetry-api#update-one-issue)を参照してください。

成功を表示する前に、返された `id`、`status`、`priority` を確認してください。送信した値から結果を組み立てないでください。ステータスを変更しても、発生事象は削除されず、`first_seen_at` と `last_seen_at` も変わりません。`severity` や重大度ルールも変わりません。

変更が拒否されると、`code: validation_failed` 付きの `422` が返ります。

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| 結果 | 原因 |
| --- | --- |
| `422`、`issue update requires status, priority, or assignee` | 本文に3つのフィールドのどれもありません。 |
| `422`、`issue priority must be high, medium, or low` | 優先度の値に対応していません。 |
| `422`、`issue assignee must be me, none, a user ID, or team:<team_id>` | 担当者の値に対応していません。 |
| `422`、`issue assignee cannot read this project` | 担当者にプロジェクトへのアクセス権がありません。LogBrew は何も変更しません。 |
| `422`、`issue assignee team is not a team of this project's organization` | チームがプロジェクトの組織に属していません。LogBrew は何も変更しません。 |
| `code: forbidden` 付きの `403` | アカウントが、そのプロジェクトの課題を管理できません。 |
| `code: not_found` 付きの `404` | アカウントが課題を読み取れないか、課題が存在しません。 |

すでにリクエストした値になっているフィールドは変わりません。タイムアウトした場合やレスポンスを受け取れなかった場合は、同じリクエストをもう一度送信するか、先に課題を読み取ってください。現在の状態を読み取る前に、別の変更を送信しないでください。[書き込み](/ja/reference/api-errors#writes)を参照してください。

`POST /api/telemetry/issues/bulk` は、リクエストした課題 ID ごとに1件の結果を、リクエストの順で `200 OK` とともに返します。見つかった課題は、どれもバージョン3の形です。本文に `"response_version": 2` を追加すると、各課題がバージョン4の形で返ります。`not_found` の結果では `issue: null` になります。

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

この例は、課題のフィールドの一部だけを示しています。`outcome` は `updated`、`unchanged`、`not_found` のいずれかです。同じリクエストを繰り返すと `unchanged` が返り、何も変わりません。[課題を一括で更新する](/ja/reference/telemetry-api#update-issues-in-bulk)を参照してください。

次の場合、一括リクエストは全体が失敗します。

| 結果 | 原因 |
| --- | --- |
| `422`、`issue_ids must name 1 to 100 issues` | 一覧が空か、ID が100個を超えています。 |
| `422`、`issue_ids must not contain duplicates` | 同じ ID が2回以上含まれています。 |
| `code: invalid_json` 付きの `422` | 本文に不明なフィールドがあります。 |
| `code: forbidden` 付きの `403` | アカウントが、そのプロジェクトの課題を管理できません。 |
| `404`、`project not found` | アカウントがプロジェクトを読み取れません。 |

## 分析のリクエストの範囲

分析のルート、メトリクスの系列のルート、シグナル量のルートは、1つのプロジェクトと1つの期間を読み取ります。どのリクエストにも `project_id` と `since` が必要です。`since` には、`24h` や `7d` のような短い形式の時間か、RFC3339 形式のタイムスタンプを指定します。`until` には RFC3339 形式のタイムスタンプを指定します。省略すると、リクエストの時刻になります。期間には `since` が含まれ、`until` は含まれません。期間は31日を超えられません。

`service_name`、`release`、`environment` は、完全一致で絞り込む任意のフィルターです。それぞれの値は、LogBrew が前後の空白を取り除いたあとで1〜256文字でなければなりません。セグメント比較のルートでは、これらのフィルターを最上位ではなく、各セグメントの中に入れます。

アカウントがプロジェクトを読み取れない場合、これらのルートは件数ゼロで `200 OK` を返します。`404` は返しません。結果が空でも、プロジェクトにアクセスできることの確認にはなりません。`project_id` を、アカウントが読み取れるプロジェクトと照らし合わせてください。そのプロジェクトを含まない MCP の接続を通したリクエストには、`403` と `forbidden` が返ります。

| ルート | `response_version` の値 | デフォルト |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`、`2`、`3` のいずれか | `1` |
| `GET /api/telemetry/analytics/properties` | `1` または `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` または `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` または `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` または `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | 受け付けません | スキーマ `1` |
| `POST /api/telemetry/analytics/paths` | 受け付けません | スキーマ `1` |
| `GET /api/telemetry/metrics/series` | 受け付けません | スキーマ `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

どのレスポンスも、`schema_version`、`query`、`purpose` で始まります。`query` は、実際に適用された範囲をそのまま返します。送信しなかったフィルターは省略されます。`purpose` は、そのルートが何に答えるかを説明するプレーンテキストです。

分母がゼロの場合、率は省略されます。省略された率は `0` でも `null` でもありません。率を信頼する前に `coverage` を読んでください。

### <span id="shared-scope-errors">共通の範囲のエラー</span>

これらのエラーは、HTTP `422` と `validation_failed` を使います。

| 原因 | `error` |
| --- | --- |
| `project_id` がない | `product analytics project_id is required` |
| `since` がない | `product analytics since is required` |
| `since` が時間の形式でも RFC3339 形式のタイムスタンプでもない | `invalid since value` |
| `until` が RFC3339 形式のタイムスタンプではない | `product analytics until must be an RFC3339 timestamp` |
| `since` が `until` より前ではない | `product analytics since must be earlier than until` |
| 期間が31日を超えている | `product analytics range must not exceed 31 days` |
| フィルターが空か、256文字を超えている | `product analytics context filters must be non-empty and at most 256 characters` |

たとえば、`project_id` のないリクエストは次を返します。

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

メトリクスの系列とシグナル量のルートも同じ範囲のルールを使いますが、`error` の文言はそれぞれ異なります。それらのエラーは、以下の各セクションに記載しています。

不明なクエリキーには、[無効なクエリパラメーター](/ja/reference/api-errors#invalid-query-parameters)のレスポンスとともに `422` が返ります。不明な JSON フィールド、必須の JSON フィールドの欠落、対応していない列挙値には `invalid_json` が返ります。[無効な JSON](/ja/reference/api-errors#invalid-json)を参照してください。HTTP メソッドが正しくないリクエストには、`405` と `method_not_allowed` が返ります。その `next` の文言には、対応しているメソッドとフィールドが示されます。[対応していないメソッド](/ja/reference/api-errors#unsupported-method)を参照してください。

## プロダクト分析の概要のレスポンス

`GET /api/telemetry/analytics/overview` は、1つのプロジェクトのアクティビティを示します。アクションの量、ユーザー、セッション、時系列、上位アクション、分類済みのページビュー、スクリーンビュー、インタラクションが含まれます。ほかの分析のルートで使う正確なイベント名を探すときに使います。

`response_version=3` を送信してください。バージョン1と2も同じ件数を返しますが、`estimation.method` の値は古いトークンです。バージョン1は、識別済みユーザーを数えるときにサブジェクトの種類を確認しません。バージョン2と3は、種類が `user` のサブジェクトだけを数え、匿名サブジェクトの件数と `subject_coverage` を追加します。


### 概要を読む

`subject_coverage` の5つの件数を足すと、そのセクションのイベントの合計になります。ユーザーとして数えるのは `identified_user_events` だけです。`anonymous_actions` は、`summary.actions` から `identified_actions` を引いた値です。

`series` には、アクティビティのある時間バケットだけが入ります。`expected_buckets` は、期間内にありうる時間バケットの数です。グラフにそのルールを明記しない限り、欠けている時間バケットを、測定されたゼロとして描かないでください。時間バケットは UTC の区切りにそろえられます。期間が時間バケットの途中から始まる場合、その一部だけの時間バケットも含まれます。

`classified_activity` は、ページビュー、スクリーンビュー、インタラクションを数えます。スクリーンビューとインタラクションはアクションでもあります。ページビューはアクションではありません。`summary.actions` を `classified_activity.summary.events` に足さないでください。

`classified_activity.top_events` の `kind` と `event_name` を、ファネルのステップ、再訪のセレクター、ライフサイクルのセレクター、パスの基準、セグメントの対象にコピーしてください。`top_events_truncated` が `true` の場合は、件数がもっと少ない名前もあることを示します。もっと見るには、`top_limit` を最大20まで増やします。

`analysis_level` は、`no_data`、`event_only`、`user_level`、`user_and_session` のいずれかです。プロジェクトにアクションも分類済みのイベントもない場合、`next_action.code` は `capture_product_activity` です。[プロダクト分析](/ja/concepts/product-analytics#use-the-analytics-api)を参照してください。

### <span id="overview-errors">概要のエラー</span>

[共通の範囲のエラー](#shared-scope-errors)に加えて、概要は次の値に対して `422` と `validation_failed` を返します。

| 値 | `error` |
| --- | --- |
| `response_version` が `1`、`2`、`3` のいずれでもない | `product analytics response_version must be 1, 2, or 3` |
| `top_limit` が `1` から `20` の範囲外 | `product analytics top_limit must be between 1 and 20` |
| `interval` が `auto`、`1m`、`5m`、`15m`、`1h`、`6h`、`1d` のいずれでもない | `product analytics interval is not supported` |
| 明示した `interval` で、500個を超える時間バケットが必要になる | `product analytics interval would exceed 500 buckets` |

`interval` のデフォルトは `auto` です。`auto` は、時間バケットが300個以下で済む最小の間隔を選びます。`top_limit` のデフォルトは `10` です。

`POST /api/telemetry/analytics/funnel` は、2〜8個のステップを順に完了したかを測定します。概要の `classified_activity.top_events` から、正確な `kind` と `event_name` をそれぞれコピーしてください。似た名前のアクションは一致とみなされません。次のリクエスト本文は、`/pricing` を表示してから1時間以内にサインアップを完了したセッションを数えます。

`analysis_unit` は `session` または `identified_user` です。デフォルトは `session` です。ステップの `kind` は、`page_view`、`screen_view`、`interaction` のいずれかです。ファネルのルートは `response_version` を受け付けません。

### コンバージョンとカバレッジを読む

`entry_rate` は、`entered_units` を `candidate_units` で割った値です。この例では60のうち50です。`overall_conversion_rate` は、`completed_units` を `entered_units` で割った値です。この例では50のうち15で、30%です。15をすべての候補の数で割った値ではありません。これらの件数は、単位が途中で止まった理由を説明しません。

カバレッジは、セッションではなくイベントを数えます。この例では、120件のイベントがステップに一致し、そのうち20件にはセッション ID がありません。結果では、この20件のイベントをセッションの件数から除外します。これを、失敗した20件のセッションとして扱わないでください。

最初のステップには `conversion_from_previous` がありません。最後のステップには、`drop_off_to_next_units` も `drop_off_to_next_rate` もありません。

単位が後のステップに到達したとみなされるのは、ステップの時刻が厳密に増えている場合だけです。タイムスタンプが同じイベントで、連続する2つのステップを満たすことはできません。最後のステップは、最初のステップから `conversion_window_seconds` 以内に発生する必要があります。

セッションのモードは、人ではなくセッションを数えます。`identified_user` は、種類が `user` の不透明なサブジェクト ID を持つイベントにだけ使ってください。このモードでは、コンバージョン期間内であれば、別々のセッションのイベントを結び付けることがあります。結果を比較するときは、同じ単位と同じステップを使ってください。

`conversion_window_seconds` のデフォルトは、24時間と期間の長さのうち短いほうです。最大値は期間の長さを秒単位で切り上げた値です。

### 空のファネルの結果

成功した空のレスポンスにも、リクエストしたステップが `units` ゼロで一覧表示されます。候補の単位がない場合、`summary` は `entry_rate` と `overall_conversion_rate` を省略します。一致するイベントがなくても、このルートは `404` を返しません。

原因を見つけるには、`coverage` と `next_action` を読みます。

| `next_action.code` | 原因 |
| --- | --- |
| `capture_product_activity` | 範囲内に分類済みのイベントがありません。 |
| `choose_captured_funnel_steps` | リクエストしたステップに一致するイベントがありません。 |
| `sessionize_product_activity` | ステップのイベントはありますが、セッション ID を持つものがありません。 |
| `identify_product_users` | ステップのイベントはありますが、種類が `user` のサブジェクトを持つものがありません。 |
| `verify_funnel_entry` | ステップ1に入った単位がありません。 |
| `investigate_funnel_drop_off` | 単位は入りましたが、すべてのステップを完了した単位がありません。 |
| `compare_funnel_contexts` | 少なくとも1つの単位がファネルを完了しました。 |

### 拒否されるファネルのリクエスト

[共通の範囲のエラー](#shared-scope-errors)に加えて、次のリクエストは `422` と `validation_failed` を返します。ステップが2個未満、または8個を超える場合：

```json

  "code": "validation_failed",

  "next_action": { "code": "fix_request", "target": "request" }

```

`conversion_window_seconds` が `0` の場合、または期間の長さを超える値の場合：

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`event_name` が空の場合、256文字を超える場合、制御文字を含む場合は、`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters` が返ります。`interaction` のステップは、有効なアクション名でもある必要があります。そうでない場合のエラーは `product analytics interaction event_name must be a bounded stable action name` です。

リクエストを修正してから送信し直してください。空でない結果を得るためだけに、ステップを削除したり分析の単位を変えたりしないでください。

## 特定イベントの分析と自動分析

再訪とライフサイクルでは、2種類のリクエストの形を使えます。知りたいことに合う形を、`response_version` で選びます。

| 分析 | `response_version` | イベントのセレクター |
| --- | --- | --- |
| 特定イベントの再訪 | `1`、または省略 | `start_event` と `return_event` の両方を送信します。 |
| 1つの特定イベントのライフサイクル | `1`、または省略 | `event` を送信します。 |
| 自動の再訪またはライフサイクル | `2` | イベントのセレクターを送信しません。 |

特定イベントのセレクターには `kind` と `event_name` が入ります。`kind` は、`page_view`、`screen_view`、`interaction` のいずれかです。`event_name` は `classified_activity.top_events` からコピーしてください。ボタンのラベルからイベント名を推測しないでください。

どちらの形でも、数えるのはユーザー、つまり種類が `user` の不透明なサブジェクト ID だけです。匿名サブジェクトと、使えるサブジェクト ID のないイベントは、ユーザーとして数えません。レスポンスがサブジェクト ID を返すことはありません。

固定の間隔は、`hour`、`day`、`week`、`thirty_day` です。どれも決まった長さの時間です。`thirty_day` は30日間で、暦の1か月ではありません。`interval` を省略すると、API は期間が48時間以下なら `hour`、それより長ければ `day` を使います。

`response_version: 2` を送信し、`start_event` と `return_event` は送信しません。対応しているページビュー、スクリーンビュー、インタラクションはすべて、開始としても再訪としても数えます。このバージョンで選ぶのはイベントの集合です。SDK の取得形式を選ぶものではありません。

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T00:00:00Z",
  "until": "2026-06-03T00:00:00Z",
  "response_version": 2,
  "interval": "day",
  "interval_count": 1,
  "mode": "return_on",
  "cohort_mode": "first_in_range"
```

## メトリクスの系列のレスポンス

`GET /api/telemetry/metrics/series` は、1つのプロジェクトで、1つのメトリクス名に完全一致するものを読み取ります。名前は `GET /api/telemetry/metrics` からコピーしてください。次のリクエストは、delta のカウンターをサービスごとにまとめます。

```bash
curl --get "https://api.logbrew.co/api/telemetry/metrics/series" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "name=jobs.completed" \
  --data-urlencode "since=2026-06-01T12:00:00Z" \
  --data-urlencode "until=2026-06-01T12:15:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name"
```

### メトリクスの系列を読む

最初のポイントは、完了したジョブが10件だったことを記録しています。サンプルが10個あったという意味ではありません。`rate_per_second` は、その変化量を300秒の時間バケットで割った値です。`last` は最後に記録された変化量で、合計ではありません。[メトリクスの集計の意味](/ja/concepts/telemetry#read-the-metric-value)を参照してください。

系列の種類と temporality によって、`aggregation.code` と、各ポイントに入る統計値が決まります。当てはまらない統計値は、ポイントから省略されます。統計値がないことは、ゼロという意味ではありません。

| 種類と temporality | `status` | `aggregation.code` | `value` | その他の統計値 |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | 最後のサンプル | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | 変化量の合計 | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 の概算値 | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| 任意の種類、`cumulative` | `limited` | `raw_cumulative_last` | 最後の生のサンプル | `last`, `min`, `max` |
| その他の組み合わせ | `limited` | `raw_last` | 最後の生のサンプル | `last`, `min`, `max` |

`limited` は成功したレスポンスで、エラーではありません。`aggregation.limitation` が追加され、LogBrew が生の値だけを表示する理由を説明します。`ready` は、取得が完全であることの証明にはなりません。

グラフを描く前に、`coverage` を読んでください。

- `samples` は、一致したすべての系列のサンプルを数えます。レスポンスが返さない系列も含みます。
- `series` は、一致した系列を数えます。`returned_series` と `points` は、返されたデータを数えます。
- `series_limit` によって件数の少ない系列が除かれた場合、`truncated` は `true` になります。
- `expected_buckets_per_series` は、期間内にありうる時間バケットの数です。

サンプルのない時間バケットにポイントを追加しないでください。ゼロを入れたり、前の値をコピーしたりしないでください。各ポイントは、最大3つの `trace_exemplars` を返します。トレースの exemplar は、1つのサンプルを1つのトレースに結び付けます。時間バケット内のすべてのサンプルを説明するものではありません。トレースの exemplar を持つポイントがない場合、`next_action.target` は `metric_samples` です。

### メトリクスの系列の範囲とエラー

`project_id`、`name`、`since` は必須です。`name` は最大200文字です。`interval` は、`auto`、`1m`、`5m`、`15m`、`1h`、`6h`、`1d` のいずれかです。デフォルトは `auto` で、時間バケットが300個以下で済む最小の間隔を選びます。明示した間隔で、500個を超える時間バケットが必要になってはいけません。

`group_by` は、`none`、`service_name`、`release`、`environment` のいずれかです。デフォルトは `none` です。まとめない場合でも、種類、単位、temporality が違うものは別の系列になります。`series_limit` には `1` から `20` を指定できます。デフォルトは `10` です。

結果が空の場合は、`series: []` とゼロの `samples` とともに `200` が返ります。`coverage` オブジェクトでは `first_seen_at` と `last_seen_at` が省略されます。これは、アプリケーションがそのメトリクスを一度も送信していないことの証明にはなりません。プロジェクト、メトリクス名、期間を確認してください。

`name` を省略すると、`422` が返ります。

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

7日間を1分ごとの時間バケットで読み取ると、`422` が返ります。

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

ほかの `422` エラーには、`metric series group_by is not supported`、`metric series interval is not supported`、`metric series_limit must be between 1 and 20` があります。

## パス分析のレスポンス

### パスを読む

`share_of_anchored_sessions` は、パスのセッション数を、基準イベントを含む4つのセッションすべてで割った値です。割合は50%と25%で、67%と33%ではありません。`unrepresented_sessions` は、基準イベントを含むセッションのうち、返されたどのパスにも表されていないものの数です。`paths_truncated: true` は、結果が完全ではないことを示します。

カバレッジは、セッションではなくイベントを数えます。この例では、5件のイベントが基準イベントに一致しますが、そのうち1件にはセッション ID がありません。そのイベントはパスに入れません。各パスは、最大3つのトレースの exemplar を返します。トレース ID は、自分が受け取ったレスポンスのものを使ってください。トレースへのリンクは、ユーザーのアクションや失敗の原因を示すものではありません。

| フィールド | 意味 |
| --- | --- |
| `following` | 各セッションで、一致する最も早い基準イベントから始まります。基準イベントの位置は `0` です。あとのノードの位置は正の値です。 |
| `preceding` | 各セッションで、一致する最も遅い基準イベントで終わります。前のノードの位置は負の値です。基準イベントの位置は `0` です。 |
| `depth` | 基準イベントの隣に並ぶノードの数。基準イベント自体は数えません。`1`〜`8`。デフォルトは `4`。パスのノードはこれより少ないこともあります。 |
| `collapse_repeated` | 種類と名前が同じ連続したノードを1つにまとめます。デフォルトは `true`。 |
| `path_limit` | 返すパスの最大数。セッション数の順に並びます。`1`〜`20`。デフォルトは `10`。 |

どちらの方向でも、ノードは時刻の順に並びます。パスは、セッション全体を再現したものではありません。LogBrew は、基準イベントを選ぶ前に、セッションごとに最大1024件の名前付きイベントを読み取ります。`following` では最も早いイベント、`preceding` では最も遅いイベントを読み取ります。この上限の外にある基準イベントは、省略されることがあります。

### <span id="filter-the-anchor-by-property">プロパティで基準イベントを絞り込む</span>

`property_filters` を最大4つ送信できます。それぞれに、完全一致の `key` と `value` を1つずつ指定します。キーは[プロパティカタログ](#analytics-property-catalog)からコピーしてください。フィルターは基準イベントにだけ適用され、その前後のイベントには適用されません。値は大文字と小文字を区別します。フィルターがある場合、`query` はそれをそのまま返し、`coverage.anchor_property_filters` に次の値が入ります。

| フィールド | 意味 |
| --- | --- |
| `context_events` | プロパティのフィルターを適用する前の、範囲内の基準イベント。 |
| `property_ready_events` | リクエストしたキーをすべて持つ基準イベント。 |
| `missing_property_events` | リクエストしたキーのうち、1つ以上を持たない基準イベント。 |
| `matching_events` | 値がすべてのフィルターに一致する基準イベント。 |
| `nonmatching_value_events` | キーはすべて持っているが、値が違う基準イベント。 |
| `property_ready_rate` | `property_ready_events` を `context_events` で割った値。 |
| `match_rate` | `matching_events` を `property_ready_events` で割った値。 |

キーがない場合と値が違う場合とでは、必要な対処が違います。この2つを足し合わせないでください。リクエストにプロパティのフィルターがない場合、このオブジェクトは省略されます。

### 空のパスと拒否されるリクエスト

空の `paths` 配列が、成功した `200` のレスポンスであることもあります。`summary`、`coverage`、`next_action` を読んでください。次のコードで原因を区別できます：`capture_product_activity`、`choose_captured_path_anchor`、`capture_anchor_properties`、`improve_anchor_property_coverage`、`verify_anchor_property_values`、`sessionize_product_activity`、`narrow_or_move_path_anchor`。

[共通の範囲のエラー](#shared-scope-errors)に加えて、次のリクエストは `422` と `validation_failed` を返します。

| 原因 | `error` |
| --- | --- |
| `depth` が `1` から `8` の範囲外 | `product analytics path depth must be between 1 and 8` |
| `path_limit` が `1` から `20` の範囲外 | `product analytics path_limit must be between 1 and 20` |
| プロパティのフィルターが5つ以上 | `product analytics paths accept at most four exact anchor property filters` |
| プロパティカタログにないキー | `product analytics path property keys must be supported privacy-safe keys` |
| 同じキーを2回指定した | `product analytics path property keys must be unique` |
| 値が空、256文字を超える、または制御文字を含む | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

たとえば、`depth: 0` は次を返します。

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">分析のプロパティカタログ</span>

`GET /api/telemetry/analytics/properties` は、1つのプロジェクトで、分類済みのプロダクトイベントにあるプロパティのキーを一覧表示します。これらのキーは、[セグメント比較](#analytics-segment-comparison)とパスの基準イベントのフィルターで使います。カタログが返すのはキーと件数です。プロパティの値や識別情報を返すことはありません。

### 使えるプロパティのキーを読む

`project_id` と `since` を送信します。`until`、`service_name`、`release`、`environment`、`limit`、`response_version` も送信できます。`limit` には `1` から `50` 個のキーを指定できます。デフォルトは `20` です。公開用の `estimation.method` の値を取得するには、`response_version=2` を送信します。

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/properties" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T00:00:00Z" \
  --data-urlencode "until=2026-06-02T00:00:00Z" \
  --data-urlencode "limit=20" \
  --data-urlencode "response_version=2"
```

### プロパティカタログの成功


## <span id="analytics-segment-comparison">分析のセグメント比較</span>

`POST /api/telemetry/analytics/segments/compare` は、1つのプロジェクトの2〜4個のセグメントについて、セッションやユーザーが1つの特定イベントにどのくらい到達するかを比較します。セグメントは、サービス、リリース、環境、プロパティの値でイベントを選びます。最初のセグメントが比較の基準になります。

### 比較を定義する

アカウントの認証と `Content-Type: application/json` を付けて、次の JSON 本文を送信します。この例の `basic` と `premium` は、例のアプリケーションのプランの値です。LogBrew のプランではありません。

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }
  ]
}
```

`target` と `segments` は必須です。`analysis_unit` は `session` または `identified_user` です。デフォルトは `session` で、人ではなくセッションを数えます。`interval` には概要と同じ値を指定できます。デフォルトは `auto` です。

各セグメントには、重複しない `key`、`label`、ほかと異なるフィルターの組み合わせが必要です。

- `key`：1〜32バイト。小文字の ASCII 英字か数字で始めます。使えるのは、小文字の ASCII 英字、数字、`_`、`-` だけです。
- `label`：1〜80文字。制御文字は使えません。
- `service_name`、`release`、`environment`：任意。それぞれの値は1〜256文字で、制御文字は使えません。
- `property_filters`：0〜4個のフィルター。1つのセグメントで、同じキーは1回しか使えません。イベントは、セグメントのすべてのフィルターに一致する必要があります。値は大文字と小文字を区別し、1〜256文字です。LogBrew は前後の空白を取り除きます。

フィルターのないセグメントは、そのプロジェクトと期間内の、分類済みのアクティビティすべてを選びます。セグメント同士が重なることもあります。ラベルやキーが違っても、フィルターの組み合わせが同じ2つのセグメントは有効になりません。

### セグメント比較の成功

この架空の結果では、基準のセグメントでは50セッションのうち10セッションがチェックアウトに到達しています。premium のセグメントでは、60セッションのうち18セッションが到達しています。

```json
{
  "schema_version": 2,
  "query": {
    "project_id": "11111111-1111-4111-8111-111111111111",
    "since": "2026-06-01T11:00:00Z",
    "until": "2026-06-01T12:00:00Z",
    "interval": "1h",
```

### 率と差を読む

`eligible_units` は、セグメント内で分類済みのアクティビティがあるセッションまたはユーザーの推定数です。`reached_units` は、そのうち対象のイベントに到達した数の推定値です。`reach_rate` は、`reached_units` を `eligible_units` で割った値です。選択した単位の ID がないイベントは、これらの単位には数えません。

基準の率は20%、premium の率は30%です。差は10ポイントです。相対的な上昇率は50%で、10%ではありません。小数の小さな誤差は、浮動小数点演算によるものです。表示するときは率を丸めますが、計算には返された値を使ってください。基準のセグメントには `comparison_to_baseline` がありません。基準の到達率がゼロの場合、相対的な上昇率は省略されます。

`query` では、送信しなかったセグメントのフィルターは `null` になります。空の `property_filters` の一覧は省略されます。

`coverage.property_filters` のフィールドは、[パスの基準イベントのフィルターのカバレッジ](#filter-the-anchor-by-property)と同じです。この例では、`matching_events` は `classified_events` と等しくなります。キーがない場合と値が違う場合は、分けて扱ってください。セグメント同士は重なることがあり、1つのセッションが複数の時間バケットに入ることもあります。セグメントや時間バケットをまたいで単位の件数を足さないでください。

この比較は、状況を記述するものです。`confidence.causal_inference` は `not_established`、`confidence.statistical_significance` は `not_tested` です。30%と20%の差は、あるプランによってチェックアウトが増えたことを示すものではありません。

### セグメント比較のエラー

[共通の範囲のエラー](#shared-scope-errors)に加えて、次のリクエストは `422` と `validation_failed` を返します。

| 原因 | `error` |
| --- | --- |
| セグメントが2個未満、または4個を超える | `product analytics segment comparison requires two through four segments` |
| 2つのセグメントのキーが同じ | `product analytics segment keys must be unique` |
| 2つのセグメントのフィルターが同じ | `product analytics segment filters must be unique` |
| キーが、使える文字で1〜32バイトになっていない | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| ラベルが空、長すぎる、または制御文字を含む | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| フィルターの値が制御文字を含む | `product analytics segment filters must be control-free` |
| 1つのセグメントにプロパティのフィルターが5つ以上 | `product analytics segments accept at most four exact property filters` |
| プロパティカタログにないキー | `product analytics segment property keys must be supported privacy-safe keys` |
| 1つのセグメントで同じプロパティのキーを2回指定した | `product analytics segment property keys must be unique within each segment` |
| プロパティの値が空、長すぎる、または制御文字を含む | `product analytics segment property values must be non-empty, control-free, and at most 256 characters` |

ラベルやプロパティのフィルターの順序が違っても、選ばれるイベントは変わりません。検証に失敗したことは、一致するイベントがないことの証拠にはなりません。

## シグナル量のレスポンス

`GET /api/telemetry/summary/volume` は、1つのプロジェクトと期間について、保持済みのシグナルを数えます。`project_id` と `since` が必要です。`project_ids` は受け付けません。

1〜50件のプロジェクトをまとめて数えるには、`project_ids` と `since` を `GET /api/telemetry/summary/volume/combined` に送信します。レスポンスの形は同じです。`query` には `project_id` の代わりに `project_ids` が入ります。選んだ複数のプロジェクトにスパンがあるトレースは、1件として数えます。アカウントがそのうち1つのプロジェクトでも読み取れない場合、このルートは `404` と `"error": "project selection not found"` を返します。

`until` に未来の時刻は指定できません。省略すると、リクエストの時刻が終了になります。`24h` のような短い形式の `since` は、`until` からさかのぼって数えます。`interval` は、`auto`、`1m`、`5m`、`15m`、`1h`、`6h`、`1d` のいずれかです。デフォルトの `auto` は、時間バケットが120個以下で済む最小の間隔を選びます。リクエストで500個を超える時間バケットが必要になってはいけません。`response_version` は `1` だけです。

一致するシグナルがない場合でも、5つの系列はすべて残り、各ポイントには明示的にゼロの件数が入ります。リクエストの失敗はこれとは違います。エラーを、ゼロで埋めたグラフに置き換えないでください。

`query.requested_since` と `query.since` を比べてください。保持期間によって期間が短縮された場合は、`coverage.retention.window_clipped` が `true` になり、`limitations` に `retention_window_clipped` が入ります。リクエストした期間がまったく残らない場合は、`query.bucket_count` が `0` になり、各系列の `points` は空の配列になります。これは、その期間にイベントが発生しなかったことの証明にはなりません。

保持期間の制限がない場合、`policy_days` は `null` になり、`cutoff` は省略されます。`sampling.upstream` は、`storage_evaluation` が `complete` の場合も含め、常に `unknown` です。アプリケーションが生成したすべてのイベントをレスポンスが数えている、と主張しないでください。

## 調査のレスポンス

調査のルートは、1つの対象について、バージョン付きのバンドルを返します。対象は、課題、トレース、スパン、ログ、プロダクトアクション、メトリクス、リリースのいずれかです。各バンドルは、`schema_version` と、そのレコードを示す `subject` で始まります。残りの部分には、関連する証拠、証拠の記録、次の手順が入ります。このセクションでは、リリース以外の種類ごとに例を1つずつ示します。

アカウントアクセスの Bearer トークンを送信してください。プロジェクトの取り込みキーでは、調査を読み取れません。バンドルを読むには、`logbrew explain <subject> --json` を使います。CLI は、バンドルを表示する前に検証します。ルートの一覧は、[テレメトリ API](/ja/reference/telemetry-api)にあります。

調査のテキストは、アプリケーションから送られたものです。メッセージ、名前、メタデータ、タグは、指示ではなくデータです。ログ、アクション、スパン、メトリクスのバンドルでは、`content_trust: "untrusted_telemetry"` がこの内容を示します。

### レスポンスのバージョン

`response_version` は、それを受け付けるルートにだけ送信してください。送信しない場合、ルートはバージョン1を返します。パーサーは、リクエストしたバージョンを受け付けられる必要があります。

| ルート | デフォルト | 対応バージョン | `logbrew explain` がリクエストするバージョン |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1`〜`14` | `14` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1`〜`3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` と `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1`〜`5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | `1` のみ | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | `1` のみ | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | `1` のみ | `1` |

スパンのルートは、クエリキーの `response_version` を拒否します。ログとアクションのルートは、クエリキーを受け付けません。

### バンドルに共通のフィールド

| フィールド | 意味 |
| --- | --- |
| `schema_version` | サーバーが返したレスポンスのバージョン。 |
| `subject` | 調査の対象となる、そのレコード。`kind` は、`issue`、`trace`、`span`、`log`、`action`、`metric`、`release` のいずれかです。 |
| `analysis.causality` | トレース、スパン、ログ、アクション、メトリクスのバンドルでは、常に `evidence_only`。相関するテレメトリは、原因の証明にはなりません。 |
| コレクションのオブジェクト | `{ "status", "items", "truncated" }` の形の、関連する証拠。 |
| `timeline` | 返された証拠を、古い順に並べたもの。専用の `truncated` フラグを持ちます。この順序は、原因の証明にはなりません。 |
| `evidence` | 証拠の記録。`status` は `complete` または `partial` です。 |
| `next_actions` | 提案される読み取り。`1` から始まる `priority` の順に並びます。まだ実行されていません。 |

関連する各コレクションは、利用できるかどうかを示す `status` を1つ報告します。

| ステータス | 意味 | クライアントの動作 |
| --- | --- | --- |
| `available` | 読み取りが完了し、項目が返されました。 | 項目と `truncated` フラグを表示します。 |
| `not_linked` | 対象に、このリンクのための識別子（トレース ID など）がありません。 | リンクがないことを説明します。タイムスタンプからリンクを作らないでください。 |
| `not_found` | 読み取りは完了しましたが、保持済みの証拠は見つかりませんでした。 | 空の結果を表示します。 |
| `unavailable` | 任意の読み取りが失敗しました。対象自体は有効です。 | 対象を表示したままにします。あとで再試行します。結果として0件を表示しないでください。 |

証拠の記録には、変わらないフィールド名を並べた4つのリストがあります：`captured_fields`、`missing_fields`、`redacted_fields`、`truncated_fields`。`status` が `complete` になるのは、あとの3つのリストが空の場合だけです。秘匿済みのデータは、未取得のデータではありません。一部省略されたデータは、完全なデータではありません。秘匿済みの値や一部省略された値を補わないでください。

### 調査の上限

これらの上限は、1つのレスポンスの範囲を決めます。`truncated` フラグや `truncated_fields` の項目があれば、上限によってデータが省略されたことを示します。

| 証拠 | 上限 |
| --- | --- |
| 1つのコレクション内の関連する項目 | 20 |
| 1つのトレースについて読み取る保持済みのスパン | 1,000 |
| タイムラインの項目 | ログ、アクション、スパンのバンドルでは50。トレースとメトリクスのバンドルでは100。 |
| 構造化された属性、プロパティ、メタデータ | スカラー値64個、オブジェクトや配列の階層4段、各配列の項目16個、各文字列512文字 |
| 相関を調べる時間の範囲 | ログ、アクション、選択した課題の発生事象の前後5分。トレースやスパンでは、開始の5分前から終了の5分後まで（最大24時間）。 |

種類ごとの上限は、それぞれのセクションに記載しています。

### 課題の調査のレスポンス

グループ化された課題の1件の発生事象について証拠を読むには、`GET /api/telemetry/issues/{issue_id}/investigation` を使います。証拠を順に読む方法は、[課題を調査する](/ja/guides/investigate-an-issue)で説明しています。バージョン14をリクエストします。

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=14" \
  --data-urlencode "selection=recommended"
```

クエリキーは、`response_version`、`selection`、`occurrence_id` です。`selection` は、`recommended`、`first`、`latest` のいずれかです。値は大文字と小文字を区別します。バージョン2〜14では、セレクターを省略すると `recommended` が使われます。バージョン1は、保持済みの最新の発生事象を返し、セレクターを受け付けません。課題の一覧のフィルターは、この読み取りには適用されません。

#### 課題の調査のリクエストのエラー

`selection` か `occurrence_id` のどちらかを使います。同じ発生事象を選ぶ場合でも、両方を送信しないでください。

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | 原因 | 対処 |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | リクエストに両方のセレクターがあります。 | セレクターを1つだけにします。 |
| `422` | `issue occurrence selection requires response_version=2 through 14` | リクエストにセレクターがあり、バージョンが1か、バージョンの指定がありません。 | `response_version=14` を送信します。セレクターはそのままにします。 |
| `422` | `issue investigation response_version must be 1 through 14` | バージョンが範囲外です。 | 対応しているバージョンを送信します。 |
| `422` | `invalid query parameters` | 不明なキー、無効な UUID、整数でないバージョン、または不明な `selection` の値があります。 | [クエリ](/ja/reference/api-errors#invalid-query-parameters)を修正します。 |
| `404` | `issue occurrence not found` | その発生事象が、このグループの保持済みの履歴にありません。 | この課題のイベントから、発生事象の ID をコピーします。承認なしに、代わりに `latest` や `recommended` を使わないでください。 |

### トレースの調査のレスポンス

1つのトレースを、その失敗の経路、最も遅い経路、関連するシグナルとともに読むには、`GET /api/telemetry/traces/{trace_id}/investigation` を使います。クエリキーは、`response_version`、`project_id`、`release`、`environment` です。どれも任意です。バージョン3をリクエストします。

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

バージョン2では、関連する各課題に `cause` と `fix` が追加されます。バージョン3では、関連する課題、アクション、メトリクスに、取得されていれば `span_id` が追加されます。

### スパンの調査のレスポンス

トレース内の1つの処理を読むには、`GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` を使います。`project_id`、`environment`、`release` を送信します。3つとも必須です。これらは選択したスパンからコピーしてください。スパンの行の `id` を `span_id` として送信しないでください。

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

| `baseline` | プロジェクト、環境、リリース、サービス、処理の種類、名前が同じ、それより前のスパン。 |
| `correlations.logs` | 同じトレース ID とスパン ID を持つログ。 |
| `correlations.issues`, `actions`, `metrics` | 同じプロジェクト、環境、リリースで、同じトレース ID を持つシグナル。 |
| `timeline[].offset_ms` | スパンの開始からのミリ秒数。負の値は、スパンより前であることを示します。 |

ベースラインは、スパンの開始前の24時間を読み取ります。`since` はその時刻を含み、`until` はその時刻を含みません。`error_rate_basis_points: 500` は5%を意味します。`subject_percentile_basis_points: 9500` は、保持済みの同種のスパンの95%が、このスパン以下の時間で終わったことを意味します。パーセンタイルは概算です。値と一緒に `baseline.limitations` も残してください。`not_found` のベースラインには、保持済みの同種のスパンがありません。`unavailable` のベースラインは読み取りの失敗で、件数ゼロではありません。

`parent_chain_status: "complete"` は、保持済みの親子のつながりがルートスパンまで届いていることを示します。LogBrew がリクエストのすべてのスパンを保持したことの証明にはなりません。トポロジーが返すのは、最大64個の祖先、50個の直接の子、50個のサービス間のつながりです。

| HTTP | `error` | 対処 |
| --- | --- | --- |
| `422` | `trace_id must be a non-zero 32-character hexadecimal value` | LogBrew のトレースのレスポンスから `trace_id` をコピーします。 |
| `422` | `span_id must be a non-zero 16-character hexadecimal value` | LogBrew のトレースのレスポンスから `span_id` をコピーします。 |
| `422` | `environment and release must be non-empty exact span scope values` | 選択したスパンから範囲をコピーします。 |
| `422` | `invalid query parameters` | `project_id`、`environment`、`release` を送信し、ほかのキーは送信しません。 |
| `404` | `span not found` | ID、プロジェクト、環境、リリースを確認します。 |

### ログの調査のレスポンス

1件のログと、それに関連する証拠を読むには、`GET /api/logs/{log_id}/investigation` を使います。このルートにクエリキーはありません。ログの ID は、ログの一覧からコピーしてください。

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

この読み取りでは、ログの一覧のフィルターの範囲外の証拠が返ることもあります。関連する読み取りでは、そのログのプロジェクト、環境、リリースと、ログの前後5分を使います。近くのログは、同じサービスも条件にします。近くのログにトレース ID は必要ありません。トレースが完全に一致する読み取りには、そのログのトレース ID が必要で、ほかのサービスが含まれることもあります。トレースの概要は、同じトレース ID と範囲を使いますが、時間の範囲は使いません。

### アクションの調査のレスポンス

```bash
curl --fail-with-body -sS \
```

### メトリクスの調査のレスポンス

1つのプロジェクトと期間で、1つのメトリクス名を読むには、`GET /api/telemetry/metrics/investigation` を使います。レスポンスには、現在の系列、同じ長さの直前の期間との比較、最新のサンプル、トレースの exemplar、完了したデプロイが入ります。バージョン2では、保持済みの最新のサンプルから取ったメトリクスの説明が追加されます。バージョン1は、常に `description_status: "not_captured"` を報告します。

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`、`name`、`since` は必須です。`since` はその時刻を含み、`until` はその時刻を含みません。`until` のデフォルトは現在時刻です。比較では、同じ長さの直前の期間も読み取ります。

`relative_change_percent` は `(current - previous) / abs(previous) * 100` です。前の値がゼロか、値がない場合は `null` です。`expected_buckets_per_series` は、ありうる時間バケットの数で、データのある時間バケットの数ではありません。空の時間バケットをゼロとして描かないでください。変化の近くにデプロイがあっても、そのデプロイが変化の原因だという証明にはなりません。

アカウントが読み取れないプロジェクトには、`404` ではなく、`analysis.status: "no_samples"` とともに `200 OK` が返ります。空の結果は、ほかのシグナルの種類については何も示しません。

メトリクスの上限：期間は最大31日です。各系列の時間バケットは最大500個です。`series_limit` は1〜20で、デフォルトは10です。レスポンスが返す exemplar は最大20件、デプロイは最大20件です。

| HTTP | `error` | 対処 |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | `response_version` を省略するか、`2` を送信します。 |
| `422` | `metric series project_id is required` | 読み取れるプロジェクトの ID を1つ送信します。 |
| `422` | `metric series name is required` | メトリクスの一覧から名前をコピーします。 |
| `422` | `metric series since is required` | `24h` のような値か、RFC 3339 形式のタイムスタンプを送信します。 |
| `422` | `metric series range must not exceed 31 days` | もっと短い期間を使います。 |
| `422` | `metric series interval would exceed 500 buckets` | `interval=auto` か、もっと広い間隔を使います。 |
| `422` | `metric series_limit must be between 1 and 20` | 1〜20の値を送信します。 |

`interval` は、`auto`、`1m`、`5m`、`15m`、`1h`、`6h`、`1d` のいずれかです。`group_by` は、`none`、`service_name`、`release`、`environment` のいずれかです。ほかの値には `422` が返ります。

### 調査のエラー

| HTTP | ルート | `error` |
| --- | --- | --- |
| `404` | ログ | `log not found` |
| `404` | アクション | `action not found` |
| `404` | トレース | `trace not found` |
| `422` | トレース | `trace investigation response_version must be 1, 2, or 3` |
| `400` | ログ、アクション、課題 | パスの ID が UUID でない場合は `invalid URL path parameters` |
| `422` | 課題、トレース、スパン、メトリクス | 不明なキーや型の違う値には `invalid query parameters` |

`404` は、そのレコードを持つ、読み取れるプロジェクトがないことを示します。どのルートも、有効な認証がない場合は `401` を、`GET` 以外のメソッドには `405` を返します。[見つからない場合](/ja/reference/api-errors#resource-not-found)、[パス](/ja/reference/api-errors#invalid-path-value)、[認証](/ja/reference/api-errors#authentication-failure)、[メソッド](/ja/reference/api-errors#unsupported-method)のレスポンスについては、[API エラー](/ja/reference/api-errors)を参照してください。

任意の証拠の読み取りは、`200 OK` のレスポンスの中で失敗することがあります。その場合、コレクションは `unavailable` を報告します。それを `not_found` やレコード0件として表示しないでください。

## <span id="severity-values">重大度の値</span>

ユーザーに見える重大度の値は、`info`、`warning`、`error`、`critical` です。SDK やランタイムは、`trace`、`debug`、`warn`、`fatal` のような一般的な別名を送信できます。REST とライブのレスポンスは、常に正規の値を返します。たとえば、LogBrew は入力として `warn` を受け付け、`warning` を返します。取り込みでは、不明な重大度の値は拒否されます。

| 別名 | 正規の値 |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">重大度ルールのレスポンス</span>

重大度ルールは、LogBrew がログや課題をどう表示するかを変えます。アプリケーションが取得した重大度は変えません。ログと課題は、`triage` オブジェクトを返します。

| フィールド | 意味 |
| --- | --- |
| `effective_severity` | 表示する重大度。ルールがない場合は `severity` と同じです。 |
| `ignored` | ログのルールがそのログを無視する場合、または課題がアーカイブ済みの場合は `true`。 |
| `rule_applied` | 重大度ルールまたは無視の状態が適用されている場合は `true`。`false` はデフォルトの値で、データがないという意味ではありません。 |

表示には `triage.effective_severity` を使います。`severity` は、取得された値としてそのまま残します。デフォルトでは、ログの一覧は無視されたログを省略します。含めるには、`GET /api/logs` で `status=ignored` または `status=all` を送信します。

アカウントには、そのプロジェクトの課題を管理する権限が必要です。読み取りのアクセス権だけでは足りません。権限がない場合、ルールの変更には `code: forbidden` 付きの `403` が返ります。

### ログのルールを変更する

`PUT /api/logs/{log_id}/triage-rule` は、そのログと、同じシグネチャを持つ以降のログにルールを設定します。本文には `severity` と `ignored` の両方が必要です。

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

`200 OK` のレスポンスには、完全な[ログ](#log-response)が入ります。その `severity` は `warning` のままです。その `triage` にルールが示されます。

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

この抜粋は、変更されたフィールドだけを示しています。リクエストの `severity` は、`source`、`info`、`warning`、`error`、`critical` のいずれかです。`source` は、取得された重大度に戻します。無視されたログを有効に戻すものではありません。ログをもう一度表示するには、`"ignored": false` を送信します。

### 課題のルールを変更する

`PUT /api/telemetry/issues/{issue_id}/triage-rule` は、グループ化された課題とその以降の発生事象について、表示する重大度を設定します。本文で受け付けるのは `severity` だけです。

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

`200 OK` のレスポンスには、バージョン1の完全な[課題](#issue-response)が入ります。取得された `severity` と `status` は変わりません。

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

この抜粋は、一部のフィールドだけを示しています。ルールで課題を解決、アーカイブ、再開することはできません。それには[ステータスの変更](#issue-status-response-examples)を使ってください。導出された優先度は、新しく実際に適用された重大度に従います。それを確認するには、`response_version=2` 以降で課題を読み取ります。

対応していない重大度には `422` が返ります。

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

課題のルールに `status` を入れるなど、本文に不明なフィールドがあると、`code: invalid_json` 付きの `422` が返ります。ログや課題が存在しないか読み取れない場合は、`code: not_found` 付きの `404` が返ります。レスポンスを受け取れなかった場合は、ルールをもう一度送信する前に、ログや課題を読み直してください。

## エラーレスポンスの形式

アプリケーションのエラーは、JSON のエンベロープを返します。次の例は、拒否されたリクエストを示しています。`error` と `next` の文言は、問題によって変わります。

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

プログラムの分岐には `code` を、自動化には `next_action` を使います。`error` と `next` は、プレーンテキストとして人に表示します。その文言を解析しないでください。エラーによっては、`limit`、`reset_at`、`retry_after_seconds` などのフィールドが追加されます。JSON の本文がないレスポンスには、LogBrew の `code` はありません。すべてのコードについては、[API エラー](/ja/reference/api-errors)を参照してください。

## CLI でデータを読む

CLI は同じルートを読み取り、`--json` を付けると同じ JSON を返します。最初は広く読み、それから絞り込みます。

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

カーソルのエンベロープを取得するには、`--pagination cursor` を追加します。CLI は、課題のレスポンスバージョン4をリクエストします。[次のページを読む](/ja/reference/cli#read-the-next-page)と[ライブ監視](/ja/reference/cli#live-watch)を参照してください。

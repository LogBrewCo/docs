LogBrew używa jednego terminu dla każdego pojęcia w produkcie. Pola API, flagi
CLI, wartości wyliczeniowe, nazwy zdarzeń i klucze atrybutów pozostają bez
zmian w każdym języku.

## Obserwowalność i monitorowanie

| Termin | Znaczenie |
| --- | --- |
| Obserwowalność | Rozumienie zachowania aplikacji na podstawie dowodów, które ona generuje. |
| Telemetria | Sygnały, które zgłasza aplikacja, takie jak logi, ślady i metryki. |
| Monitorowanie | Sprawdzanie znanych warunków, na przykład zmierzonej wartości względem progu. |
| `o11y` | Skrót angielskiego słowa „observability” (obserwowalność). Liczba oznacza 11 liter między `o` a `y`. |

Wybór sygnałów i przykłady opisuje strona [Telemetria](/pl/concepts/telemetry).

## Agenci AI

| Termin | Znaczenie |
| --- | --- |
| Serwer MCP | Hostowany serwer LogBrew dla protokołu Model Context Protocol. Agenci AI używają go do odczytu zatwierdzonych projektów. |
| Klient MCP | Aplikacja, która łączy agenta AI z serwerem MCP, na przykład Claude Code. |
| Zatwierdzony projekt | Projekt wybrany podczas przyznawania dostępu klientowi MCP. Klient może odczytywać tylko zatwierdzone projekty. |
| Połączenie | Dostęp, który dajesz 1 klientowi MCP, gdy go zatwierdzasz. Wygasa po 30 dniach bez użycia, po 90 dniach albo gdy je unieważnisz. W CLI nazywa się „grant”. |

Aby połączyć klienta, przeczytaj [Połącz agenta AI przez MCP](/pl/guides/mcp).

## Sygnały obserwowalności

<AccordionGroup>
  <Accordion title="Problem">
    Zgrupowany błąd, który może zawierać wiele wystąpień. Wystąpienie to jeden
    zarejestrowany przypadek tego problemu. `first_seen_at` to czas pierwszego
    wystąpienia. `last_seen_at` to czas najnowszego wystąpienia.
  </Accordion>

  <Accordion title="Log">
    Jeden wpis zdarzenia ze znacznikiem czasu. Log może zawierać poziom
    ważności, usługę, wydanie, środowisko, kontekst śladu i atrybuty
    ograniczone zasadami prywatności.
  </Accordion>

  <Accordion title="Ślad i span">
    Ślad śledzi pracę w ramach żądania lub operacji. Span to jedna mierzona
    operacja w tym śladzie. Korelacja ze śladem jest dowodem wspólnego
    kontekstu, a nie dowodem przyczyny.
  </Accordion>

  <Accordion title="Metryka">
    Pomiar z działającej aplikacji z określoną jednostką, typem, agregacją i
    oknem czasowym. Punkty metryk nie są wymienne z liczbą logów, śladów ani
    problemów.
  </Accordion>

  <Accordion title="Wydanie">
    Wdrożona wersja aplikacji lub usługi zgłaszana razem z telemetrią. Wydanie
    to nie to samo co projekt ani repozytorium.
  </Accordion>

  <Accordion title="Akcja">
    Sklasyfikowane zdarzenie produktowe, na przykład założenie konta,
    realizacja zakupu, import lub nieudane zadanie. Analityka klasyfikuje akcję
    jako wyświetlenie strony, wyświetlenie ekranu lub interakcję. Akcja nie
    jest automatycznym poleceniem, które uruchamia LogBrew.
  </Accordion>
</AccordionGroup>

## Analiza problemów

Nie każde wystąpienie zawiera wszystkie pola.

| Termin | Znaczenie |
| --- | --- |
| Ważność | Pilność sygnału: `info`, `warning`, `error` lub `critical`. Jest niezależna od statusu problemu. |
| Status problemu | Stan zgrupowanego problemu w procesie obsługi: `unresolved`, `resolved` lub `archived`. To nie jest wynik jednego żądania. |
| Zarchiwizowany problem | Problem, który zespół usunął z aktywnego triażu. Starsze odpowiedzi nazywają ten status `ignored`. |
| Priorytet problemu | Kolejność zgrupowanego problemu w triażu: `high`, `medium` lub `low`. Wynika z ważności, dopóki ktoś go nie ustawi. |
| Źródło priorytetu | Skąd pochodzi priorytet. `derived` wynika z ważności: `error` i `critical` dają `high`, `warning` daje `medium`, a `info` daje `low`. `manual` to priorytet ustawiony przez osobę. |
| Przypisanie problemu | Konto albo zespół, które odpowiada za następny krok w zgrupowanym problemie: dokładnie 1 konto albo 1 zespół. Konto musi mieć dostęp do odczytu projektu. Zespół musi należeć do organizacji projektu. |
| Zespół | Grupa członków organizacji, która ma nazwę. Problemy można przypisać do zespołu, a reguły własności mogą go wskazywać. Zespół nie daje swoim członkom dostępu do projektu. |
| Reguła własności | Reguła projektu, która łączy ścieżkę ramki stosu, moduł, trasę, usługę lub tag z kontami albo zespołami będącymi właścicielami pasujących problemów. |
| Proponowany właściciel | Konto albo zespół, które LogBrew proponuje dla problemu na podstawie reguły własności, wiersza z CODEOWNERS albo ostatniej aktywności. To propozycja, a nie przypisanie. |
| Skrzynka odbiorcza | Lista problemów, które inne osoby przypisały tobie lub twoim zespołom. LogBrew nie wysyła o nich e-maili. |
| Stack trace | Zarejestrowane dowody wywołań funkcji dla błędu. To coś innego niż ślad rozproszony. |
| Ramka stosu | Jeden wpis w stack trace. Może wskazywać funkcję, moduł, plik, wiersz lub kolumnę. |
| Łańcuch wyjątków | Powiązane wyjątki zgłoszone razem, na przykład błąd i jego przyczyna. Brakujące, zamaskowane lub obcięte wpisy ograniczają dowody. |
| Ramka aplikacji | Ramka stosu oznaczona jako kod aplikacji. Pokazuje kod do sprawdzenia. Nie dowodzi, gdzie leży błąd. |
| Breadcrumb | Krótkie zarejestrowane zdarzenie przed wystąpieniem problemu. Breadcrumby nie są pełnym zapisem sesji. |
| Obsłużony wyjątek | Wyjątek, który aplikacja zgłosiła jako obsłużony. Nie dowodzi, że operacja się powiodła. |
| Mapa źródeł (source map) | Artefakt builda, który mapuje lokalizacje w wygenerowanym JavaScripcie na lokalizacje w oryginalnym kodzie źródłowym. |
| Zsymbolizowana ramka | Ramka, której wygenerowaną lokalizację przetłumaczono na informacje o oryginalnym kodzie źródłowym. |
| Wystąpienie bazowe | Zarejestrowane wystąpienie używane jako punkt odniesienia przy odtwarzaniu błędu. |
| Pochodzenie | Skąd pochodzi ocena. `backend_observed` oznacza, że LogBrew to zaobserwował. `application_reported` oznacza, że zgłosiła to aplikacja, a LogBrew tego nie zweryfikował. |
| Gotowość do odtworzenia | Czy wystąpienie bazowe ma dowody potrzebne do próby odtworzenia. To nie jest zaliczony test odtworzenia. |

Kolejność odczytu i pola odpowiedzi opisuje przewodnik
[Zbadaj problem](/pl/guides/investigate-an-issue).

## Tożsamość i korelacja

Brak wartości nie dowodzi, że powiązana aktywność nie miała miejsca.

| Termin | Znaczenie |
| --- | --- |
| Kontekst śladu | Identyfikatory śladu i spanu, które łączą pracę między sygnałami. |
| Span główny | Span, który rozpoczyna ślad i nie ma spanu nadrzędnego. Najwcześniejszy zwrócony span nie musi być spanem głównym. |
| Span podrzędny | Span, który ma span nadrzędny w tym samym śladzie. |
| Korelacja | Dokładna relacja zwracana przez LogBrew, na przykład wspólne ID śladu. Nie dowodzi przyczyny. |
| Zidentyfikowany użytkownik | Podmiot przekazany przez aplikację, ze stałym ID i rodzajem `user`. |
| Anonimowy podmiot | Podmiot przekazany przez aplikację, z rodzajem `anonymous`. Liczby traktują go oddzielnie od zidentyfikowanych użytkowników. |
| Nieznany rodzaj tożsamości | Podmiot bez znanego rodzaju. Nie jest liczony jako zidentyfikowany użytkownik. |
| Brakujący podmiot | Zdarzenie bez podmiotu. To coś innego niż podmiot o nieznanym rodzaju. |

Rodzaj tożsamości pokazuje, jak aplikacja sklasyfikowała swój podmiot. Nie
dowodzi, że dane są anonimowe. Stałe ID nadal może łączyć aktywność.

## Zakres i jakość danych

| Termin | Znaczenie |
| --- | --- |
| Projekt | Podstawowa granica własności w produkcie. Jeden projekt może zawierać wiele usług lub komponentów repozytorium. |
| Usługa | Środowisko uruchomieniowe lub komponent w projekcie, który zgłasza dane. |
| Środowisko | Dokładny kontekst zgłaszania, na przykład production lub staging. |
| Przyjęte | Zaakceptowane przez kontrakt przyjmowania danych. Nie oznacza bezterminowego przechowywania. |
| Zindeksowane | Dostępne dla wskazanego indeksu lub zapytania. To nie jest synonim słowa „przyjęte”. |
| Przechowywane | Obecne w ocenianym oknie danych i w czasie przechowywania danych konta. |
| Próbkowane | Część telemetrii została wybrana przed zbieraniem danych lub w jego trakcie. |
| Pokrycie | Zmierzony udział z jawnie podanym licznikiem i mianownikiem. |
| Obcięte | Odpowiedź osiągnęła limit. Pominięte dane niekoniecznie nie istnieją. |
| Przybliżone | Oszacowane udokumentowaną metodą zamiast dokładnego policzenia. |
| Okno czasowe | Dokładny okres, który ocenia zapytanie. |

## Plany i organizacje

| Termin | Znaczenie |
| --- | --- |
| Plan | Stały zestaw miesięcznych przydziałów i czas przechowywania danych. Plany to Free, Pro, Business i Enterprise. |
| Przydział | Ilość jednego rodzaju telemetrii, którą plan obejmuje w 1 miesiącu rozliczeniowym, na przykład bajty logów lub spany śladów. |
| Czas przechowywania danych | Liczba dni, przez które LogBrew trzyma telemetrię konta. LogBrew usuwa starszą telemetrię. To co innego niż utrzymanie w analityce produktowej. |
| Oferta beta | Przydziały planu Pro, które konto dostaje za darmo na 6 miesięcy podczas publicznej bety. Potem konto używa własnego planu. |
| Organizacja | Wspólna przestrzeń dla członków, zespołów i projektów. Każdy plan ma organizacje bez limitu członków i projektów. |

Przydziały i czas przechowywania danych każdego planu opisuje [API konta](/pl/reference/account-api).

## Pomiary i czas

| Termin | Znaczenie |
| --- | --- |
| Punkt danych | Jedna wartość w zgłoszonym czasie. Zanim porównasz punkty danych, odczytaj nazwę i jednostkę metryki. |
| Szereg czasowy | Wartości tego samego pomiaru uporządkowane według czasu. Luka nie oznacza, że wartość wynosiła zero. |
| Czas trwania | Czas, który upłynął podczas operacji. To coś innego niż moment, w którym operacja wystąpiła. |
| Agregacja | Określone obliczenie na wielu pomiarach, na przykład suma lub średnia. |
| Przedział czasu | Jeden przedział na wykresie lub w zgrupowanym wyniku. Jego początek i koniec wyznaczają zakres. |
| Niepełny okres | Okres, który jeszcze się nie zakończył. To nie jest zakończony okres bez aktywności. |

Nie sumuj czasów trwania nakładających się spanów podrzędnych, aby uzyskać
łączny czas żądania. Nie porównuj liczby zdarzeń z liczbą zidentyfikowanych
użytkowników.

## Stany dowodów

Tych stanów nie można stosować zamiennie:

- **Zarejestrowane:** dowody są dostępne.
- **Brakujące:** dowody nie zostały zarejestrowane.
- **Zamaskowane:** dowody zostały celowo ukryte.
- **Obcięte:** dowody przekroczyły limit odpowiedzi lub rejestrowania.
- **Niedostępne:** odczyt nie mógł dostarczyć dowodów.

`Likely cause` (prawdopodobna przyczyna) i `likely fix area` (prawdopodobne
miejsce poprawki) opisują ograniczone dowody diagnostyczne, a nie udowodnioną
przyczynę źródłową. `Reported impact` (zgłoszony wpływ) dostarcza aplikacja
zgłaszająca dane, chyba że kontrakt wyraźnie opisuje pomiar LogBrew.

## Analityka produktowa

| Termin | Znaczenie |
| --- | --- |
| Zdarzenie | Sklasyfikowana aktywność w produkcie o dokładnej, stałej nazwie. |
| Właściwość | Klucz kontekstu używany do opisu lub filtrowania zdarzenia. |
| Sesja | Wizyta lub sesja w aplikacji, a nie osoba. |
| Kohorta | Ograniczona grupa określona dokładnymi kryteriami. |
| Lejek | Uporządkowane kroki służące do mierzenia postępu lub konwersji. |
| Utrzymanie | Powroty mierzone z jawnie podanym okresem i mianownikiem. |
| Ścieżki | Przebieg sesji przed wybranym zdarzeniem lub po nim. |
| Cykl życia | Grupuje zidentyfikowane podmioty w każdym okresie jako nowe w obserwowanej historii, powracające, ponownie aktywne lub uśpione. |
| Nowy w obserwowanej historii | Aktywny bez wcześniejszego wybranego zdarzenia w ograniczonym oknie historii. Nie oznacza klienta, który pojawił się po raz pierwszy. |

Niepełne okresy, brakująca tożsamość, niepełne rejestrowanie właściwości,
próbkowanie i obcięcie ograniczają wynik. LogBrew pokazuje te ograniczenia,
zamiast zamieniać je na zero lub pewność.

Zasady liczenia opisuje strona [Analityka produktowa](/pl/concepts/product-analytics).
Aby wysyłać sklasyfikowaną aktywność i typowaną tożsamość, skorzystaj z
przewodnika [Rejestrowanie zdarzeń produktowych](/pl/guides/product-events).

Ta strona pokazuje po jednym przykładzie każdego rodzaju odpowiedzi
[API telemetrii](/pl/reference/telemetry-api). Wszystkie wartości są syntetyczne.
Kody błędów i sposoby naprawy opisuje strona [Błędy API](/pl/reference/api-errors).

## Jak odczytać odpowiedź

Odczytuj każdą odpowiedź w tej kolejności:

1. Sprawdź status HTTP.
2. Upewnij się, że treść ma strukturę, którą określa dana trasa.
3. Upewnij się, że każdy `project_id` mieści się w żądanym zakresie projektów.
4. Nie zmieniaj kanonicznych wartości wyliczeniowych ani identyfikatorów.
5. Wykonuj `next_action` tylko wtedy, gdy klient obsługuje jego `code` i
   `target`.
6. Rozróżniaj `null`, pominięte pole i pustą listę. To 3 różne stany.

Odpowiedź `200 OK` może zawierać pustą listę. Pusta lista logów oznacza, że
żaden log nie pasuje do żądania. Nie oznacza, że problemy, ślady lub akcje też
są puste. Nie łącz sygnałów tylko dlatego, że mają zbliżone znaczniki czasu.
Przechodź do śladu tylko wtedy, gdy odpowiedź zawiera jego dokładny `trace_id`.

`404` i pusta lista to różne wyniki. Trasa listy zwraca `[]`, gdy żaden
rekord nie pasuje. Trasa szczegółów zwraca `404` z `code: not_found`, gdy
nie znajduje rekordu dostępnego do odczytu. Żaden z tych wyników nie dowodzi,
że przyjmowanie danych się nie powiodło.

## Co wysyłać

Odpowiedzi są tak przydatne, jak telemetria, którą wysyłasz. Wysyłaj te
wartości w każdej kopercie lub konfiguracji SDK:

- `release` i `environment`.
- Stałe nazwy usług, akcji i metryk.
- Kontekst śladu, gdy logi, spany (pojedyncze mierzone operacje), akcje i
  problemy należą do tego samego żądania.
- Kanoniczne wartości ważności: `info`, `warning`, `error` i `critical`.
- Atrybuty pomocne w debugowaniu, bez sekretów i zbędnych danych osobowych.

Zobacz [Integracja SDK](/pl/guides/sdk-ingestion) i
[Kontrola rejestrowanych danych](/pl/guides/safe-capture).

## Odpowiedź przyjmowania danych

Publiczne SDK same odczytują odpowiedź `POST /v1/events`. Kod aplikacji nie
musi jej obsługiwać.

### Odpowiedź na paczkę SDK

Przyjęta paczka SDK zwraca `200 OK` z liczbą przyjętych zdarzeń dla każdego
strumienia:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Pole | Znaczenie |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Zdarzenia z tej paczki, które LogBrew przyjął. |
| `already_accepted` | Zdarzenia, których ID LogBrew przyjął wcześniej. LogBrew nie zapisuje ich ponownie. |
| `context_updated` | `true`, gdy paczka zaktualizowała kontekst wydania lub środowiska. |

Liczby dotyczą tylko tej paczki. Ponowienie paczki, którą LogBrew już przyjął,
zwraca `0` dla każdego strumienia, a w `already_accepted` liczbę zdarzeń. Przy
ponowieniu zachowaj oryginalne ID zdarzeń.

### Odpowiedź na natywną kopertę

`POST /api/telemetry/ingest` zwraca `200 OK` z liczbą przyjętych elementów dla
każdego strumienia:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

Natywna odpowiedź nie ma pól `metrics` ani `context_updated`. Nie dodawaj ich.
`already_accepted` liczy elementy, których `id` LogBrew przyjął wcześniej dla
projektu. Zobacz [bezpośrednie wysyłanie natywnej koperty](/pl/guides/sdk-ingestion#required-envelope-fields).

### Błędy przyjmowania danych

`401` z `code: ingest_key_invalid` oznacza, że token bearer wysyłania został
unieważniony, wygasł lub nie jest ważny dla projektu. W `POST /v1/events` brak
tokena bearer albo token bearer, który nie jest kluczem wysyłania, zwraca `401`
z `code: unauthorized`. Użyj aktualnego tokena bearer wysyłania przypisanego do
projektu. Nie ponawiaj żądania z tokenem bearer konta.

Odrzucona paczka SDK zwraca `422` z `code: validation_failed`:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Inne wartości `error` to między innymi
`SDK event batch requires at least one event` i
`SDK event type is not supported by this ingest route`. Sprawdź wersję SDK i
konfigurację transportu. Nie wysyłaj pustej paczki. Nie zmieniaj typów ani ID
zdarzeń tylko po to, aby paczka przeszła walidację.

Żądanie z metodą inną niż `POST` zwraca `405` z `code: method_not_allowed`.
Nieczytelna treść JSON zwraca `code: invalid_json`.

## Format odpowiedzi list telemetrii

Trasy list domyślnie zwracają zwykłą tablicę JSON. Pusta lista w udanej
odpowiedzi to `[]`.

Z `pagination=cursor` trasa zwraca kopertę (envelope). Klucz kolekcji
odpowiada sygnałowi:

| Trasa | Klucz kolekcji |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events` oraz `issue_id` na najwyższym poziomie |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces` oraz `naming_quality` na najwyższym poziomie |

`next_cursor` to obiekt z polami kontynuacji albo `null` na ostatniej stronie.
Wiersze są posortowane od najnowszych. Zobacz [paginację kursorową](/pl/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Odpowiedź z logami</span>

Strona kursora z logami przy `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Logi zawierają `level` dla zgodności i `severity` do wyświetlania. Oba pola mają
wartość kanoniczną. `triage` zawiera wynik reguły ważności. Zobacz
[odpowiedzi reguł ważności](#severity-rule-responses).

`trace_id` i `span_id` mają wartość `null`, gdy log nie jest powiązany ze
śladem. Wtedy `next_action` to `inspect_related_logs` z celem `telemetry_logs`.
Logi, problemy i akcje używają tych samych 2 par `next_action`.

`GET /api/logs/{log_id}` zwraca jeden log w tej samej strukturze.

### <span id="issue-response">Odpowiedź z problemem</span>

`GET /api/telemetry/issues/{issue_id}` zwraca jeden zgrupowany problem. Lista
zwraca te same obiekty. Ten przykład używa domyślnej wersji odpowiedzi 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

W wersji 1 `status` to `unresolved`, `resolved` lub `ignored`. Dla
zarchiwizowanego problemu `triage.ignored` ma wartość `true`. Pary
`next_action` i odczyty, które po nich następują, opisuje przewodnik
[Zbadaj problem](/pl/guides/investigate-an-issue).

`first_seen_at` i `last_seen_at` to czasy pierwszego i ostatniego wystąpienia.
Nie zmieniają się po zmianie statusu.

Niektóre pola pojawiają się tylko wtedy, gdy LogBrew ma dane:

| Pole | Kiedy się pojawia |
| --- | --- |
| `span_id` | Problem jest powiązany ze spanem. W przeciwnym razie pole jest pominięte. |
| `diagnostics` | Ostatnie wystąpienie ma typ wyjątku lub breadcrumby. Zobacz [historię wystąpień problemu](#issue-occurrence-history). |
| `symbolication` | Tylko w `GET /api/telemetry/issues/{issue_id}`, gdy problem ma tożsamość artefaktu wydania. Zobacz [Mapy źródeł JavaScript](/pl/guides/source-maps). |

`symbolication.status` to `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` lub `unavailable`. Lista, zmiany
statusu i zmiany reguł nie zwracają `symbolication`.

Z `response_version=2` problem ma te same pola, z następującymi zmianami:

| Pole | Wartość w wersji 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` lub `archived`. Wersja 1 pokazuje `archived` jako `ignored`. |
| `priority` | `high`, `medium` lub `low`. |
| `priority_source` | `manual`, gdy priorytet ustawiła osoba. `derived`, gdy priorytet wynika z efektywnego poziomu ważności. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Ten przykład pokazuje tylko część pól. Wyliczony priorytet to `high` dla
`error` i `critical`, `medium` dla `warning` oraz `low` dla `info`. Korzysta z
`triage.effective_severity`, więc reguła ważności problemu może go zmienić.

Z `response_version=3` problem ma wszystkie pola wersji 2 oraz `assignee`.
`assignee` ma wartość `null`, gdy problem nie ma przypisania:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Pole | Znaczenie |
| --- | --- |
| `assignee.user_id` | ID użytkownika przypisanego konta. Wysyłaj je jako `assignee` w filtrze lub zmianie. |
| `assignee.name` | Nazwa przypisanego konta albo `null`, gdy konto nie ma nazwy. |
| `assignee.email` | Adres e-mail przypisanego konta. |

Problem nie pokazuje przypisania, gdy przypisany członek nie ma już
dostępu do odczytu projektu.

Z `response_version=4` pole `assignee` ma też `type`. Przypisanie do konta
(`user`) ma `user_id`, `name` i `email`, tak jak w wersji 3. Przypisanie do
zespołu (`team`) ma `team_id`, `slug` i `name`. Wersja 3 pokazuje przypisanie
do zespołu jako `null`. CLI żąda wersji 4:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Każda inna wartość `response_version` zwraca `422` z
`code: validation_failed`. Strona kursora używa tej samej wersji dla każdego
problemu w `issues`.

### <span id="assignee-list-response">Odpowiedź z listą kont i zespołów do przypisania</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` zwraca każde
konto, któremu można przypisywać problemy w projekcie:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Dodaj `response_version=2`, aby dostać też `teams`: każdy zespół organizacji
projektu z `team_id`, `slug` i `name`.

Jeśli konto nie może odczytać projektu, trasa zwraca `404` z
`code: not_found`.

### <span id="action-response">Odpowiedź z akcją</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` śledzi jednego aktora lub jedną sesję. Traktuj `distinct_id` i
`session_id` jako nieprzezroczyste identyfikatory (opaque). `session_id` i
`trace_id` mają wartość `null`, gdy ich brakuje. `span_id` jest pomijany, gdy
go brakuje. Akcja nie ma poziomu ważności. Zobacz
[Rejestrowanie zdarzeń produktowych](/pl/guides/product-events).

### Odpowiedź z metryką

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Każdy element to jedna próbka. Nie używaj liczby próbek jako liczby zdarzeń
ani użytkowników. `unit`, `temporality`, `trace_id` i `span_id` mają wartość
`null`, gdy ich brakuje. Wartość `null` to nie zero.

### Odpowiedź z wydaniem

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Jeden wiersz obejmuje jeden projekt, wydanie, środowisko i usługę. Jego liczby
opisują tylko ten wiersz.

`trace_health.status` to `unknown`, gdy wiersz nie ma śladów, a w pozostałych
przypadkach `no_errors_observed` lub `errors_observed`.
`error_rate_basis_points` to udział śladów ze spanem błędu, od `0` do `10000`.
To nie jest wskaźnik błędów dla wszystkich żądań.

`next_action` wskazuje pierwszy typ sygnału, który ma dane, w tej kolejności:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Zobacz [Wydania](/pl/concepts/releases).

### Odpowiedź z wyszukiwania śladów

`GET /api/telemetry/traces?pagination=cursor` zwraca jeden wiersz dla każdego
śladu oraz potwierdzenie `naming_quality` dla zwróconej strony:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` dotyczy tylko zwróconej strony. To nie jest wynik dla całego
konta. `truncated: true` oznacza, że istnieje kolejna strona. Gdy strona ma
ogólną nazwę, niedopasowaną trasę HTTP lub ogólną operację, `next_action` to
`improve_trace_naming` z celem `sdk_configuration`. Bez `pagination=cursor`
trasa zwraca zwykłą tablicę śladów bez `naming_quality`.

`next_cursor` zawiera `time` i `trace_id`. Wyślij je jako `cursor_time` i
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` zwraca spany jednego śladu.
`GET /api/telemetry/traces/{trace_id}/summary` zwraca span główny, spany
błędów, usługi, czas trwania i najwolniejszą ścieżkę, bez surowych atrybutów
spanów. `404` z podsumowania oznacza, że żaden ślad nie pasuje do pełnego
zakresu. Nie usuwaj filtrów, aby ponowić żądanie. Zobacz [odpowiedzi ze spanami i podsumowaniem śladu](#trace-spans-and-summary-responses).

### Puste listy i brakujące rekordy

Odczyt listy może nie mieć dopasowań. Odczyt szczegółów działa według innych
zasad:

| Żądanie | Sukces | Brak rekordu dostępnego do odczytu |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` z jednym [logiem](#log-response) | `404` z `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` z jednym [problemem](#issue-response) | `404` z `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` z wystąpieniami | `404` z `code: not_found` na pierwszej stronie |
| `GET /api/telemetry/traces/{trace_id}` | `200` ze spanami | `200` z `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` z jednym podsumowaniem | `404` z `code: not_found` |

Brakujący log zwraca taki `404`:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Brakujący problem używa `"error": "issue not found"`. Brakujące podsumowanie
śladu używa `"error": "trace not found"`. Nieznane ID i ID, którego konto nie
może odczytać, zwracają tę samą odpowiedź.

Lista z jednym `project_id`, którego konto nie może odczytać, zwraca `200` z
pustą listą. Sprawdź ID projektu, zanim zgłosisz, że danych nie ma.

### Odrzucony wybór projektów

Listy logów, problemów, akcji, metryk, wydań i śladów przyjmują jeden projekt w
`project_id` albo od 2 do 50 projektów w `project_ids`. Katalog atrybutów logów
przyjmuje te same selektory. Historia wystąpień problemu ich nie przyjmuje.

Żądanie z `project_id` i `project_ids` jednocześnie zwraca `422`:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` z nieprawidłowym UUID, powtórzonym ID albo z mniej niż 2 lub
więcej niż 50 ID również zwraca `422` z `code: validation_failed`.

Jeśli konto nie może odczytać jednego projektu ze zbioru `project_ids`, całe
żądanie zwraca `404`. Nie zwraca pozostałych projektów jako wyniku częściowego:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Pokaż błąd, a nie pustą listę ani zerową liczbę. Odczytaj listę projektów
ponownie. Nie usuwaj projektu po cichu i nie ponawiaj żądania dla wszystkich
projektów. Delegowane poświadczenie, na przykład połączenie MCP, zwraca `403` z
`code: forbidden` dla projektu, którego to połączenie nie obejmuje. Zobacz
[zakres projektów](/pl/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Błędy kursora</span>

Logi, problemy, akcje, metryki i wystąpienia problemów używają `cursor_time` i
`cursor_id`. Odrzucony kursor zwraca `422` z `code: validation_failed`. Te
błędy nie oznaczają, że lista jest pusta.

| Żądanie | `error` |
| --- | --- |
| `pagination=cursor` tylko z 1 z 2 pól kursora | `cursor_time and cursor_id must be sent together` |
| `cursor_time`, który nie jest znacznikiem czasu RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Pola kursora bez `pagination=cursor` albo z inną wartością `pagination` | `pagination must be cursor when cursor pagination is requested` |

Na przykład:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Skopiuj cały `next_cursor` z poprzedniej strony. Nie zastępuj `cursor_time`
bieżącym czasem. Jeśli kursor zaginął, zacznij od nowa z `pagination=cursor` i
pierwotnymi filtrami. Nieznany parametr zapytania lub wartość niewłaściwego typu
zwraca `422` z `"error": "invalid query parameters"`.

### Odpowiedzi z kursorem wydań

Kursor wydań ma 5 pól. Udane żądanie bez dopasowań zwraca `200`:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Gdy `next_cursor` nie jest `null`, wyślij wszystkie 5 wartości w następnym
żądaniu:

| Pole `next_cursor` | Parametr zapytania |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` oznacza pozycję. Nie zastępuje `project_id` ani
`project_ids`. Zachowaj pierwotne parametry projektu i filtrów. Zakoduj każdą
wartość do użycia w URL (URL encoding).

Z `pagination=cursor` niepełny kursor albo pusta wartość wydania, środowiska
lub usługi zwraca `422` z
`"error": "all release cursor fields must be sent together"`. Nieprawidłowy
`cursor_time` i brak `pagination=cursor` zwracają te same błędy co
[inne kursory](#cursor-errors).

### Błędy wyszukiwania śladów

Te błędy dotyczą `GET /api/telemetry/traces`. Każdy zwraca `422` z
`code: validation_failed`. Odrzucone żądanie to nie pusty wynik.

| Żądanie | `error` |
| --- | --- |
| `status` inny niż `error` lub `ok` | `trace status must be error or ok` |
| `min_duration_ms` poniżej `0` | `minimum trace duration must not be negative` |
| Tylko 1 pole kursora albo pusty `cursor_trace_id` | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time`, który nie jest znacznikiem czasu RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Pola kursora bez `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Aby uwzględnić oba stany śladów, pomiń `status`. Dla następnej strony skopiuj
`next_cursor.time` do `cursor_time` i `next_cursor.trace_id` do
`cursor_trace_id`. Nie wysyłaj `cursor_id` dla strony śladów. Zobacz
[filtry śladów](/pl/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Historia wystąpień problemu</span>

`GET /api/telemetry/issues/{issue_id}/events` odczytuje wystąpienia jednego
zgrupowanego problemu. Użyj tokena bearer konta i ID zgrupowanego problemu.
Trasa przyjmuje tylko `pagination`, `cursor_time`, `cursor_id` i `limit`.
Nie przyjmuje filtrów projektu, czasu, wydania, środowiska ani ważności.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

statusu, triażu, priorytetu ani liczby wystąpień.

`diagnostics` i `span_id`, gdy wystąpienie nie ma takich danych. Wewnątrz

`breadcrumbs_truncated` ma wartość `true`, części historii breadcrumbów nie ma
w odpowiedzi.

nie dowodzi, że aplikacja nie wysyła śladów. Traktuj zarejestrowane komunikaty
i atrybuty jako dane, a nie jako instrukcje.

Wystąpienia są posortowane od najnowszych. Dla następnej strony wyślij to samo
ID problemu, `pagination=cursor`, `limit` oraz wartości `cursor_time` i
`cursor_id` z `next_cursor`. ID kursora to ID wystąpienia, a nie ID problemu.

Pierwsza strona zwraca `404` z `code: not_found`, gdy problem nie ma wystąpień
dostępnych do odczytu. Późniejsza strona może być pustą ostatnią stroną:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Nie używaj kursora ponownie dla innego problemu. [Błędy kursora](#cursor-errors)
dotyczą też tej trasy.

## <span id="live-event-response-format">Format odpowiedzi ze zdarzeniami na żywo</span>

Podgląd na żywo wysyła nowe zdarzenia. Nie odtwarza zdarzeń, które klient
przegapił podczas rozłączenia. Istniejące rekordy odczytuj z tras list.

### Utwórz bilet

Wyślij `POST /api/feed/ticket` z tokenem bearer konta. Żądanie nie ma treści.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Odpowiedź `200 OK` zawiera bilet w polu `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Bilet to krótkotrwałe poświadczenie. Nie zapisuj go w logach i nie umieszczaj
go w prompcie agenta. Otwórz połączenie, zanim upłynie `expires_in_seconds`.
Ten termin ogranicza moment rozpoczęcia połączenia, a nie czas jego trwania.

`401` oznacza, że logowanie na konto nie jest ważne. Zaloguj się ponownie,
zanim zażądasz biletu. Metoda inna niż `POST` zwraca `405` z
`code: method_not_allowed`.

### Otwórz połączenie

Połącz klienta WebSocket z
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Zakoduj bilet do
użycia w URL. Nie umieszczaj w URL tokena bearer konta ani tokena bearer
wysyłania. `401` oznacza, że bilet lub logowanie na konto nie jest ważne. Po
ponownym zalogowaniu się utwórz nowy bilet.

| Odpowiedź | Przyczyna | Następny krok |
| --- | --- | --- |
| `422` z `"error": "feed ticket is required"` | Brakuje wartości zapytania `ticket` albo jest pusta. | Utwórz bilet i połącz się z jego użyciem. |
| `401` z `code: unauthorized` | Bilet wygasł lub jest nieważny. | Utwórz nowy bilet. Nie ponawiaj połączenia z tym samym biletem. |
| `code: invalid_websocket_upgrade` | Żądanie nie jest prawidłowym żądaniem przejścia na WebSocket (upgrade). | Użyj klienta WebSocket. |
| `405` z `code: method_not_allowed` | Żądanie nie używa `GET`. | Do połączenia użyj `GET`. |

Po błędzie odczekaj, zanim połączysz się ponownie. Nie łącz się ponownie w
ciasnej pętli.

### Odczytaj komunikaty

Każdy komunikat to koperta `{ "type": "...", "data": ... }`. Odczytaj `type`,
zanim sparsujesz `data`. Pomijaj typy, których klient nie obsługuje.

| Typ zdarzenia | Dane |
| --- | --- |
| `native_log` | Dane logu w strukturze [odpowiedzi z logami](#log-response). |
| `native_issue` | Dane zgrupowanego problemu w strukturze [odpowiedzi z problemem](#issue-response) w wersji 1. |
| `native_trace_span` | Jeden span w strukturze elementu [listy spanów](#span-list). |
| `native_action` | Dane akcji produktowej w strukturze [odpowiedzi z akcją](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Dane projektu. Po zmianie odczytaj listę projektów ponownie. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Wykorzystanie konta w strukturze [wykorzystania konta](/pl/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Zdarzenie `native_issue` używa wersji 1 odpowiedzi z problemem: zarchiwizowany
problem ma status `ignored`, a zdarzenie nie ma priorytetu. Metryki i wydania
nie są typami zdarzeń na żywo. Odczytuj je z ich tras list. Bilet nie
wybiera projektu. Sprawdź `project_id` każdego zdarzenia, zanim pokażesz je w
widoku projektu. `logbrew watch --json` korzysta z tego podglądu na żywo.
Zobacz [dokumentację referencyjną CLI](/pl/reference/cli).

### Obsłuż zamknięte połączenie

| Kod zamknięcia | Powód | Następny krok |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Odczekaj, a potem połącz się ponownie z nowym biletem. Ponownie odczytaj dane z tras list, aby pobrać przegapione rekordy. |
| `1008` | `live feed access changed; sign in again` | Przestań łączyć się ponownie. Zaloguj się ponownie, zanim utworzysz nowy bilet. |

Inne rozłączenia mogą nie mieć powodu podanego przez LogBrew. Po ponownym
połączeniu ponownie odczytaj dane z tras list i dopasuj rekordy według ID.

## <span id="issue-status-response-examples">Przykłady odpowiedzi na zmianę statusu problemu</span>

`PATCH /api/telemetry/issues/{issue_id}` z `{ "status": "resolved" }` zwraca
`200 OK` ze zaktualizowanym zgrupowanym problemem w tej samej strukturze co
[odpowiedź z problemem](#issue-response). Parametr zapytania
`response_version` wybiera wersję. Odpowiedź nie zawiera flagi powodzenia.

Treść ustawia co najmniej jedno z pól `status`, `priority` i `assignee`.
`status` przyjmuje `unresolved`, `resolved` lub `archived`. `ignored` to
starsza nazwa `archived`. Zobacz [Zaktualizuj jeden problem](/pl/reference/telemetry-api#update-one-issue).

Sprawdź zwrócone `id`, `status` i `priority`, zanim pokażesz powodzenie. Nie
buduj wyniku z wysłanych wartości. Zmiana statusu nie usuwa wystąpień ani nie
zmienia `first_seen_at` i `last_seen_at`. Nie zmienia też `severity` ani
reguły ważności.

Odrzucona zmiana zwraca `422` z `code: validation_failed`:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Wynik | Przyczyna |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Treść nie ma żadnego z 3 pól. |
| `422`, `issue priority must be high, medium, or low` | Wartość priorytetu nie jest obsługiwana. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | Wartość `assignee` nie jest obsługiwana. |
| `422`, `issue assignee cannot read this project` | Przypisane konto nie ma dostępu do projektu. LogBrew niczego nie zmienia. |
| `422`, `issue assignee team is not a team of this project's organization` | Zespół nie należy do organizacji projektu. LogBrew niczego nie zmienia. |
| `403` z `code: forbidden` | Konto nie może zarządzać problemami w projekcie. |
| `404` z `code: not_found` | Konto nie może odczytać problemu albo problem nie istnieje. |

Pole, które ma już żądaną wartość, się nie zmienia. Po przekroczeniu limitu
czasu lub utracie odpowiedzi wyślij to samo żądanie ponownie albo najpierw
odczytaj problem. Nie wysyłaj innej zmiany, zanim odczytasz bieżący stan.
Zobacz [Zapisy](/pl/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` zwraca `200 OK` z 1 wynikiem dla każdego
żądanego ID problemu, w kolejności z żądania. Każdy znaleziony problem ma
strukturę wersji 3. Wynik `not_found` ma `issue: null`:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

Ten przykład pokazuje tylko część pól problemu. `outcome` to `updated`,
`unchanged` lub `not_found`. Powtórzone żądanie zwraca `unchanged` i niczego
nie zmienia. Zobacz
[Zaktualizuj wiele problemów naraz](/pl/reference/telemetry-api#update-issues-in-bulk).

Żądanie zbiorcze kończy się błędem w całości w tych przypadkach:

| Wynik | Przyczyna |
| --- | --- |
| `422`, `issue_ids must name 1 to 100 issues` | Lista jest pusta lub ma więcej niż 100 ID. |
| `422`, `issue_ids must not contain duplicates` | Jakieś ID występuje więcej niż raz. |
| `422` z `code: invalid_json` | Treść ma nieznane pole. |
| `403` z `code: forbidden` | Konto nie może zarządzać problemami w projekcie. |
| `404`, `project not found` | Konto nie może odczytać projektu. |

## Zakres żądań analityki

Trasy analityki, trasa szeregu metryki i trasa wolumenu sygnałów
odczytują jeden projekt i jeden zakres czasu. Każde żądanie wymaga
`project_id` i `since`. `since` przyjmuje skrócony zapis czasu trwania, na
przykład `24h` lub `7d`, albo znacznik czasu RFC3339. `until` przyjmuje
znacznik czasu RFC3339, a domyślnie ma wartość czasu żądania. Zakres obejmuje
`since`, wyklucza `until` i nie może przekraczać 31 dni.

`service_name`, `release` i `environment` to opcjonalne filtry dokładne. Każda
wartość musi mieć od 1 do 256 znaków po usunięciu spacji przez LogBrew.
Trasa porównania segmentów umieszcza te filtry wewnątrz każdego segmentu, a
nie na najwyższym poziomie.

Jeśli konto nie może odczytać projektu, te trasy zwracają `200 OK` z
zerowymi liczbami. Nie zwracają `404`. Pusty wynik nie potwierdza dostępu do
projektu. Porównaj `project_id` z projektami, które konto może odczytać.
Żądanie przez połączenie MCP, które nie obejmuje projektu, zwraca `403` i
`forbidden`.

| Trasa | Wartości `response_version` | Domyślnie |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` lub `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` lub `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` lub `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` lub `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` lub `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Nie przyjmuje | Schemat `1` |
| `POST /api/telemetry/analytics/paths` | Nie przyjmuje | Schemat `1` |
| `GET /api/telemetry/metrics/series` | Nie przyjmuje | Schemat `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Każda odpowiedź zaczyna się od `schema_version`, `query` i `purpose`. `query`
powtarza efektywny zakres. Pomija filtr, którego nie wysłano. `purpose` to
zwykły tekst, który wyjaśnia, na jakie pytanie odpowiada trasa.

Wskaźnik jest pomijany, gdy jego mianownik wynosi zero. Pominięty wskaźnik nie
oznacza ani `0`, ani `null`. Odczytaj `coverage`, zanim zaufasz wskaźnikowi.

### <span id="shared-scope-errors">Wspólne błędy zakresu</span>

Te błędy używają HTTP `422` i `validation_failed`:

| Przyczyna | `error` |
| --- | --- |
| Brak `project_id` | `product analytics project_id is required` |
| Brak `since` | `product analytics since is required` |
| `since` nie jest czasem trwania ani znacznikiem czasu RFC3339 | `invalid since value` |
| `until` nie jest znacznikiem czasu RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` nie jest wcześniejsze niż `until` | `product analytics since must be earlier than until` |
| Zakres jest dłuższy niż 31 dni | `product analytics range must not exceed 31 days` |
| Pusty filtr albo filtr dłuższy niż 256 znaków | `product analytics context filters must be non-empty and at most 256 characters` |

Na przykład żądanie bez `project_id` zwraca:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Trasy szeregu metryki i wolumenu sygnałów stosują te same zasady zakresu, ale
z własnym tekstem `error`. Te błędy wymieniają sekcje tych tras poniżej.

Nieznany parametr zapytania zwraca `422` z odpowiedzią
[nieprawidłowe parametry zapytania](/pl/reference/api-errors#invalid-query-parameters).
Nieznane pole JSON, brak wymaganego pola JSON lub nieobsługiwana wartość wyliczeniowa
zwraca `invalid_json`. Zobacz
[Nieprawidłowy JSON](/pl/reference/api-errors#invalid-json). Żądanie z
niewłaściwą metodą HTTP zwraca `405` i `method_not_allowed`. Jego tekst `next`
podaje obsługiwaną metodę i pola. Zobacz
[Nieobsługiwana metoda](/pl/reference/api-errors#unsupported-method).

`entry_rate` to `entered_units` podzielone przez `candidate_units`: 50 z 60.
`overall_conversion_rate` to `completed_units` podzielone przez
`entered_units`: 15 z 50, czyli 30%. To nie jest 15 podzielone przez wszystkie
jednostki kandydujące. Te liczby nie wyjaśniają, dlaczego jednostki się
zatrzymały.

Pokrycie liczy zdarzenia, a nie sesje. Tutaj 120 zdarzeń pasuje do kroku, a
20 z nich nie ma ID sesji. Wynik wyklucza tych 20 zdarzeń z liczby sesji. Nie
traktuj ich jako 20 nieudanych sesji.

Pierwszy krok nie ma `conversion_from_previous`. Ostatni krok nie ma
`drop_off_to_next_units` ani `drop_off_to_next_rate`.

kroków. Ostatni krok musi nastąpić w ciągu `conversion_window_seconds` od
pierwszego kroku.

Tryb sesji liczy sesje, a nie osoby. Używaj `identified_user` tylko dla
zdarzeń, które mają nieprzezroczyste ID podmiotu rodzaju `user`. Ten tryb może
łączyć zdarzenia z różnych sesji w obrębie okna konwersji. Porównując wyniki,
zachowaj tę samą jednostkę i te same kroki.

Domyślne `conversion_window_seconds` to 24 godziny albo długość zakresu,
zależnie od tego, która wartość jest mniejsza. Maksimum to długość zakresu w
pełnych sekundach, zaokrąglona w górę.

### Puste wyniki lejka

Udana pusta odpowiedź nadal wymienia żądane kroki z zerowym `units`. Jeśli nie
ma jednostek kandydujących, `summary` pomija `entry_rate` i
`overall_conversion_rate`. Trasa nie zwraca `404` z powodu braku pasujących
zdarzeń.

Aby znaleźć przyczynę, odczytaj `coverage` i `next_action`:

| `next_action.code` | Przyczyna |
| --- | --- |
| `capture_product_activity` | W zakresie nie ma sklasyfikowanych zdarzeń. |
| `choose_captured_funnel_steps` | Żadne zdarzenie nie pasuje do żądanego kroku. |
| `sessionize_product_activity` | Zdarzenia kroków istnieją, ale żadne nie ma ID sesji. |
| `identify_product_users` | Zdarzenia kroków istnieją, ale żadne nie ma podmiotu rodzaju `user`. |
| `verify_funnel_entry` | Żadna jednostka nie weszła do lejka w kroku 1. |
| `investigate_funnel_drop_off` | Jednostki weszły do lejka, ale żadna nie ukończyła wszystkich kroków. |

### Odrzucone żądania lejka

Oprócz [wspólnych błędów zakresu](#shared-scope-errors) te żądania zwracają
`422` i `validation_failed`. Mniej niż 2 lub więcej niż 8 kroków:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`conversion_window_seconds` równe `0` albo większe niż długość zakresu:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`event_name`, które jest puste, dłuższe niż 256 znaków lub zawiera znak
sterujący, zwraca
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Krok `interaction` musi też mieć prawidłową nazwę akcji. W przeciwnym razie
błąd to `product analytics interaction event_name must be a bounded stable action name`.

Popraw żądanie, zanim wyślesz je ponownie. Nie usuwaj kroków i nie zmieniaj
jednostki analizy tylko po to, aby dostać niepusty wynik.

## Tryb dokładnych zdarzeń i tryb automatyczny

Utrzymanie i cykl życia przyjmują 2 struktury żądania. Użyj
`response_version`, aby wybrać strukturę, która odpowiada na twoje pytanie:

| Tryb | `response_version` | Selektory zdarzeń |
| --- | --- | --- |
| Utrzymanie dla dokładnych zdarzeń | `1` albo pominięte | Wyślij `start_event` i `return_event`. |
| Cykl życia dla jednego dokładnego zdarzenia | `1` albo pominięte | Wyślij `event`. |
| Automatyczne utrzymanie lub cykl życia | `2` | Nie wysyłaj selektora zdarzenia. |

Dokładny selektor zawiera `kind` i `event_name`. `kind` to `page_view`,
`screen_view` lub `interaction`. Skopiuj `event_name` z
`classified_activity.top_events`. Nie zgaduj nazwy zdarzenia na podstawie
etykiety przycisku.

Obie struktury liczą tylko użytkowników, czyli nieprzezroczyste ID podmiotów
rodzaju `user`. Anonimowe podmioty i zdarzenia bez użytecznego ID podmiotu nie
są liczone jako użytkownicy. Odpowiedzi nigdy nie zwracają ID podmiotów.

Stałe długości przedziału to `hour`, `day`, `week` i `thirty_day`. To stałe
czasy trwania. `thirty_day` to 30 dni, a nie miesiąc kalendarzowy. Jeśli
pominiesz `interval`, API używa `hour` dla zakresu do 48 godzin włącznie i
`day` dla dłuższego zakresu.

### Błędy utrzymania

Oprócz [wspólnych błędów zakresu](#shared-scope-errors) te żądania zwracają
`422` i `validation_failed`:

| Przyczyna | `error` |
| --- | --- |
| Wersja 1 bez obu selektorów, wersja 2 z selektorem albo inna wersja | `product analytics retention activity selection is contradictory` |
| `interval_count` spoza zakresu od `1` do `31` | `product analytics retention interval_count must be between 1 and 31` |
| Liczba przedziałów kohort pomnożona przez `interval_count` przekracza 500 | `product analytics retention interval and interval_count would exceed 500 cohort matrix cells` |

Limit komórek zależy od zakresu i okresów, a nie od liczby użytkowników.
Zakres 30 dni z `interval: "hour"` ma 720 przedziałów kohort. Przy
`interval_count: 1` daje to 720 komórek, czyli więcej niż 500:

```json
{
  "error": "product analytics retention interval and interval_count would exceed 500 cohort matrix cells",
  "code": "validation_failed",
  "next": "choose a wider interval, a shorter time range, or fewer retention periods",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Aby użyć automatycznego utrzymania, usuń oba selektory. Nie zmieniaj SDK, aby
poprawić to żądanie odczytu.

### Żądanie cyklu życia dla dokładnego zdarzenia

Wyślij tę treść do `POST /api/telemetry/analytics/lifecycle`. Klasyfikuje

`2`. Użytkownik może być uśpiony dla tego zdarzenia, a jednocześnie wykonywać
inne czynności.

### Odczytaj cykl życia

1 czerwca A jest użytkownikiem powracającym, B – ponownie aktywnym, C – nowym,
a D – uśpionym. 2 czerwca A i B są użytkownikami powracającymi, a C jest
uśpiony dla realizacji zakupu mimo wyświetlenia strony. Zmiana netto 2
czerwca to `2 - 3 = -1`.

W każdym przedziale nowi, powracający i ponownie aktywni użytkownicy sumują
się do `active_subjects`. `returning_subjects` plus `dormant_subjects` równa
się `previous_active_subjects`. `net_active_change` to `active_subjects` minus
`previous_active_subjects`.

Nie sumuj dziennych liczb aktywnych użytkowników, aby uzyskać liczbę
unikalnych użytkowników. Tutaj dzienne liczby sumują się do 5, ale
`analysis_active_subjects` wynosi 3. W historii i okresie analizy występuje
czterech unikalnych użytkowników.

`fully_observed` ma wartość `false` dla ostatniego przedziału, który kończy się
po `until`. Jego liczby mogą się zmienić, gdy cały okres będzie można
zaobserwować. `next_action` sugeruje dalszą analizę. Nie wskazuje przyczyny.

Wyślij `response_version: 2` bez selektora `event`. Każde obsługiwane

### Błędy cyklu życia

Oprócz [wspólnych błędów zakresu](#shared-scope-errors) te żądania zwracają
`422` i `validation_failed`:

| Przyczyna | `error` |
| --- | --- |
| Wersja 1 bez `event`, wersja 2 z `event` albo inna wersja | `product analytics lifecycle activity selection is contradictory` |
| `history_period_count` spoza zakresu od `2` do `31` | `product analytics lifecycle history_period_count must be between 2 and 31` |
| Okresy historii trwające łącznie dłużej niż 62 dni | `product analytics lifecycle history must not exceed 62 days` |
| Więcej niż 100 przedziałów analizy | `product analytics lifecycle interval would exceed 100 analysis buckets` |

Na przykład 10 okresów historii `week` wymaga 70 dni:

```json
{
  "error": "product analytics lifecycle history must not exceed 62 days",
  "code": "validation_failed",
  "next": "use fewer history periods or a narrower fixed interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

### Odczytaj wybrany zakres analizy

Odpowiedzi dla dokładnych zdarzeń mają `schema_version: 1`. Ich `query`
powtarza selektory i pomija `activity_scope`. Odpowiedzi automatyczne mają
`schema_version: 2` i `query.activity_scope: "all_classified_activity"`.
Pomijają selektory. Inny selektor może zmienić wynik, nawet jeśli
zarejestrowana aktywność się nie zmieniła.

Rodzaj i temporalność szeregu wyznaczają jego `aggregation.code` i statystyki w
każdym punkcie. Punkt pomija statystykę, która nie ma zastosowania. Brakująca

| Rodzaj i temporalność | `status` | `aggregation.code` | `value` | Inne statystyki |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Ostatnia próbka | `last`, `min`, `max`, `average` |

które wyjaśnia, dlaczego LogBrew pokazuje tylko surowe wartości. `ready` nie
dowodzi, że zarejestrowano wszystkie dane.

- `samples` liczy próbki wszystkich pasujących szeregów, także tych, których

  dane.

  wolumenie.
- `expected_buckets_per_series` to liczba możliwych przedziałów w zakresie.

Nie dodawaj punktu dla przedziału bez próbek. Nie wstawiaj zera i nie kopiuj
poprzedniej wartości. Każdy punkt zwraca do 3 `trace_exemplars`. Przykładowy
ślad (trace exemplar) łączy jedną próbkę ze śladem. Nie wyjaśnia wszystkich
próbek w przedziale. Jeśli żaden punkt nie ma przykładowego śladu,
`next_action.target` to `metric_samples`.

`project_id`, `name` i `since` są wymagane. `name` może mieć najwyżej 200
znaków. `interval` to `auto`, `1m`, `5m`, `15m`, `1h`, `6h` lub `1d`.
Domyślnie `auto`, czyli najmniejsza długość przedziału, przy której liczba
przedziałów nie przekracza 300. Jawnie podana długość przedziału nie może
wymagać więcej niż 500 przedziałów.

`group_by` to `none`, `service_name`, `release` lub `environment`. Domyślnie

Pusty wynik zwraca `200` z `series: []` i zerowym `samples`. Obiekt
`coverage` pomija `first_seen_at` i `last_seen_at`. To nie dowodzi, że
aplikacja nigdy nie wysłała metryki. Sprawdź projekt, nazwę metryki i zakres
czasu.

Przedziały jednominutowe w zakresie 7 dni zwracają `422`:


Inne błędy `422` to `metric series group_by is not supported`,

odtworzeniem sesji. LogBrew odczytuje najwyżej 1024 nazwane zdarzenia na
sesję, zanim wybierze zdarzenie kotwiczące: najwcześniejsze zdarzenia dla `following` i
najpóźniejsze dla `preceding`. Zdarzenie kotwiczące poza tym limitem może zostać pominięte.

### <span id="filter-the-anchor-by-property">Filtruj zdarzenie kotwiczące według właściwości</span>

Wyślij do 4 `property_filters`, każdy z jednym dokładnym `key` i `value`.
Skopiuj klucz z [katalogu właściwości](#analytics-property-catalog). Filtry
dotyczą tylko zdarzenia kotwiczącego, a nie zdarzeń wokół niego. Wartości rozróżniają wielkość
liter. Gdy filtry są obecne, `query` je powtarza, a
`coverage.anchor_property_filters` podaje:

| Pole | Znaczenie |
| --- | --- |
| `context_events` | Zdarzenia kotwiczące w zakresie przed zastosowaniem filtrów właściwości. |
| `property_ready_events` | Zdarzenia kotwiczące, które mają każdy żądany klucz. |
| `missing_property_events` | Zdarzenia kotwiczące bez co najmniej jednego żądanego klucza. |
| `matching_events` | Zdarzenia kotwiczące, których wartości pasują do każdego filtra. |
| `nonmatching_value_events` | Zdarzenia kotwiczące, które mają każdy klucz, ale inną wartość. |
| `property_ready_rate` | `property_ready_events` podzielone przez `context_events`. |
| `match_rate` | `matching_events` podzielone przez `property_ready_events`. |

Brakujące klucze i niepasujące wartości wymagają różnych poprawek. Nie sumuj
ich. Obiekt jest pomijany, gdy żądanie nie ma filtra właściwości.

### Puste ścieżki i odrzucone żądania

Pusta tablica `paths` może być udaną odpowiedzią `200`. Odczytaj `summary`,
`coverage` i `next_action`. Te kody rozróżniają przyczyny:
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` i
`narrow_or_move_path_anchor`.

Oprócz [wspólnych błędów zakresu](#shared-scope-errors) te żądania zwracają
`422` i `validation_failed`:

| Przyczyna | `error` |
| --- | --- |
| `depth` spoza zakresu od `1` do `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` spoza zakresu od `1` do `20` | `product analytics path_limit must be between 1 and 20` |
| Więcej niż 4 filtry właściwości | `product analytics paths accept at most four exact anchor property filters` |
| Klucz, którego nie ma w katalogu właściwości | `product analytics path property keys must be supported privacy-safe keys` |
| Ten sam klucz 2 razy | `product analytics path property keys must be unique` |
| Pusta wartość, wartość dłuższa niż 256 znaków albo znak sterujący | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

Na przykład `depth: 0` zwraca:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

zdarzeń kotwiczących ścieżek. Katalog zwraca klucze i liczby. Nigdy nie zwraca wartości

## <span id="analytics-segment-comparison">Porównanie segmentów w analityce</span>

`POST /api/telemetry/analytics/segments/compare` porównuje, jak często sesje
lub użytkownicy docierają do jednego dokładnego zdarzenia, w 2–4 segmentach w
jednym projekcie. Segment wybiera zdarzenia według usługi, wydania, środowiska
i wartości właściwości. Pierwszy segment jest segmentem bazowym.

### Zdefiniuj porównanie

Wyślij tę treść JSON z uwierzytelnieniem konta i
`Content-Type: application/json`. Tutaj `basic` i `premium` to wartości planu
w przykładowej aplikacji, a nie plany LogBrew:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }
  ]
}
```

`target` i `segments` są wymagane. `analysis_unit` to `session` lub
`identified_user`. Domyślnie `session`, czyli liczone są sesje, a nie osoby.
`interval` przyjmuje te same wartości co przegląd. Domyślnie `auto`.

Każdy segment potrzebuje unikalnego `key`, etykiety `label` i innego zestawu
filtrów:

- `key`: od 1 do 32 bajtów. Zacznij od małej litery ASCII lub cyfry. Używaj
  tylko małych liter ASCII, cyfr, `_` i `-`.
- `label`: od 1 do 80 znaków, bez znaków sterujących.
- `service_name`, `release`, `environment`: opcjonalne. Każda wartość ma od 1
  do 256 znaków, bez znaków sterujących.
- `property_filters`: od 0 do 4 filtrów. Każdy klucz może wystąpić w segmencie
  tylko raz. Zdarzenie musi pasować do wszystkich filtrów segmentu. Wartości
  rozróżniają wielkość liter i mają od 1 do 256 znaków. LogBrew usuwa spacje z
  ich początku i końca.

Segment bez filtrów wybiera całą sklasyfikowaną aktywność w projekcie i
zakresie czasu. Segmenty mogą się nakładać. Inna etykieta lub inny klucz nie
sprawia, że 2 identyczne zestawy filtrów są prawidłowe.

## Odpowiedź z wolumenem sygnałów

`GET /api/telemetry/summary/volume` liczy przechowywane sygnały dla jednego
projektu i zakresu czasu. Wymaga `project_id` i `since`. Nie przyjmuje
`project_ids`.

`until` nie może być w przyszłości. Jeśli go pominiesz, koniec zakresu to czas
żądania. Skrócone `since`, na przykład `24h`, liczy wstecz od `until`.
`interval` to `auto`, `1m`, `5m`, `15m`, `1h`, `6h` lub `1d`. Domyślne `auto`
wybiera najmniejszą długość przedziału, przy której liczba przedziałów nie
przekracza 120. Żądanie nie może wymagać więcej niż 500 przedziałów. Jedyna
wartość `response_version` to `1`.

`release_volume_not_included` jako zera wydań.

Jeśli żaden sygnał nie pasuje, wszystkie 5 szeregów pozostaje, a ich punkty mają
jawne zerowe liczby. Nieudane żądanie to inna sytuacja. Nie zastępuj błędu
wykresem wypełnionym zerami.

Porównaj `query.requested_since` z `query.since`. Jeśli okres przechowywania
skraca okno, `coverage.retention.window_clipped` ma wartość `true`, a
`limitations` zawiera `retention_window_clipped`. Jeśli z żądanego okna nic
nie zostaje, `query.bucket_count` wynosi `0`, a każdy szereg ma pustą tablicę
`points`. To nie dowodzi, że w tym okresie nie wystąpiły żadne zdarzenia.

`policy_days` ma wartość `null`, a `cutoff` jest pomijane, gdy nie obowiązuje
żaden limit przechowywania. `sampling.upstream` to zawsze `unknown`, także gdy
`storage_evaluation` to `complete`. Nie twierdź, że odpowiedź liczy każde
zdarzenie, które wytworzyła aplikacja.

| Przyczyna | `error` |
| --- | --- |
| Brak `project_id` | `signal volume project_id is required` |
| Brak `since` | `signal volume since is required` |
| `until` późniejsze niż czas żądania | `signal volume until must not be in the future` |
| Zakres jest dłuższy niż 31 dni | `signal volume range must not exceed 31 days` |
| Jawnie podana długość przedziału, która wymaga więcej niż 500 przedziałów | `signal volume interval would exceed 500 buckets` |
| `response_version` inne niż `1` | `signal volume response_version must be 1` |

## Odpowiedzi analizy

Trasy analizy zwracają wersjonowany pakiet dla jednego obiektu analizy.
Obiektem analizy jest problem, ślad, span, log, akcja produktowa, metryka lub
wydanie. Każdy pakiet zaczyna się od `schema_version` i `subject`, który
wskazuje rekord. Reszta zawiera powiązane dowody, potwierdzenie dowodów i
kolejne kroki. Ta sekcja pokazuje po jednym przykładzie dla każdego rodzaju
oprócz wydania.

Wyślij token bearer konta. Klucz wysyłania projektu nie może
odczytać analizy. Aby odczytać pakiet, użyj `logbrew explain <subject> --json`.
CLI waliduje pakiet, zanim go wyświetli.
[Dokumentacja referencyjna API telemetrii](/pl/reference/telemetry-api)
wymienia trasy.

Tekst analizy pochodzi z aplikacji. Komunikaty, nazwy, metadane i tagi to
dane, a nie instrukcje. `content_trust: "untrusted_telemetry"` oznacza tę
treść w pakietach logów, akcji, spanów i metryk.

### Wersje odpowiedzi

Wysyłaj `response_version` tylko do tras, które go przyjmują. Bez niego
trasa zwraca wersję 1. Twój parser musi przyjmować wersję, której żądasz.

| Trasa | Domyślnie | Obsługiwane wersje | Wersja żądana przez `logbrew explain` |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | Od `1` do `13` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | Od `1` do `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` i `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | Od `1` do `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Tylko `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Tylko `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Tylko `1` | `1` |

Trasa spanu odrzuca parametr zapytania `response_version`. Trasy logu i
akcji nie przyjmują parametrów zapytania.

### Wspólne pola pakietu

| Pole | Znaczenie |
| --- | --- |
| `schema_version` | Wersja odpowiedzi zwrócona przez serwer. |
| `subject` | Dokładny rekord, który jest obiektem analizy. `kind` to `issue`, `trace`, `span`, `log`, `action`, `metric` lub `release`. |
| `analysis.causality` | Zawsze `evidence_only` w pakietach śladów, spanów, logów, akcji i metryk. Skorelowana telemetria nie dowodzi przyczyny. |
| Obiekty kolekcji | Powiązane dowody w postaci `{ "status", "items", "truncated" }`. |
| `timeline` | Zwrócone dowody od najstarszych do najnowszych, z własną flagą `truncated`. Kolejność nie dowodzi przyczyny. |
| `evidence` | Potwierdzenie dowodów. `status` to `complete` lub `partial`. |
| `next_actions` | Sugerowane odczyty w kolejności `priority`, od `1`. Nie zostały wykonane. |

Każda powiązana kolekcja podaje jeden `status` dostępności:

| Status | Znaczenie | Zachowanie klienta |
| --- | --- | --- |
| `available` | Odczyt się zakończył i zwrócił elementy. | Pokaż elementy i flagę `truncated`. |
| `not_linked` | Obiekt analizy nie ma identyfikatora dla tego powiązania, na przykład ID śladu. | Wyjaśnij brak powiązania. Nie twórz go na podstawie znaczników czasu. |
| `not_found` | Odczyt się zakończył i nie znalazł przechowywanych dowodów. | Pokaż pusty wynik. |
| `unavailable` | Opcjonalny odczyt się nie powiódł. Obiekt analizy jest nadal prawidłowy. | Nadal pokazuj obiekt analizy. Ponów później. Nie pokazuj 0 elementów jako wyniku. |

Potwierdzenie dowodów ma 4 posortowane listy stałych nazw pól:
`captured_fields`, `missing_fields`, `redacted_fields` i
`truncated_fields`. `status` to `complete` tylko wtedy, gdy 3 ostatnie listy
są puste. Zamaskowane dane to nie brakujące dane. Obcięte dane to nie pełne
dane. Nie uzupełniaj zamaskowanej ani obciętej wartości.

### Limity analizy

Te limity ograniczają jedną odpowiedź. Flaga `truncated` lub wpis w
`truncated_fields` pokazuje, że limit pominął dane.

| Dowody | Limit |
| --- | --- |
| Powiązane elementy w jednej kolekcji | 20 |
| Przechowywane spany odczytane dla jednego śladu | 1000 |
| Elementy osi czasu | 50 dla pakietów logów, akcji i spanów. 100 dla pakietów śladów i metryk. |
| Ustrukturyzowane atrybuty, właściwości i metadane | 64 wartości skalarne, 4 poziomy obiektów lub tablic, 16 elementów w każdej tablicy, 512 znaków w każdym ciągu |
| Okno czasowe korelacji | 5 minut przed logiem, akcją lub wybranym wystąpieniem problemu i 5 minut po nich. Dla śladu lub spanu 5 minut przed startem i po końcu, najwyżej 24 godziny. |

Sekcja każdego rodzaju wymienia jego własne limity.

### Odpowiedź z analizą problemu

Użyj `GET /api/telemetry/issues/{issue_id}/investigation`, aby odczytać
dowody dla jednego wystąpienia zgrupowanego problemu.
Przewodnik [Zbadaj problem](/pl/guides/investigate-an-issue) pokazuje,
w jakiej kolejności czytać dowody. Żądaj wersji 13:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

Parametry zapytania to `response_version`, `selection` i `occurrence_id`.
`selection` to `recommended`, `first` lub `latest`. Wartości rozróżniają
wielkość liter. W wersjach od 2 do 13 pominięty selektor oznacza
`recommended`. Wersja 1 zwraca ostatnie przechowywane wystąpienie i nie
przyjmuje selektora. Filtry listy problemów nie dotyczą tego odczytu.

`ignored`. Odpowiedzi z listą i szczegółami problemów używają `archived` od
wersji odpowiedzi 2.

wystąpień. Trend ma najwyżej 30 przedziałów. Każdy rozkład zwraca najwyżej 10
wartości. Stos ma najwyżej 32 ramki.

#### Błędy żądania analizy problemu

Użyj `selection` albo `occurrence_id`. Nie wysyłaj obu, nawet gdy wybierają to
samo wystąpienie:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 13 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Przyczyna | Naprawa |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | Żądanie ma oba selektory. | Zostaw jeden selektor. |
| `422` | `issue occurrence selection requires response_version=2 through 13` | Żądanie ma selektor i wersję 1 albo nie ma wersji. | Wyślij `response_version=13`. Zostaw selektor. |
| `422` | `issue investigation response_version must be 1 through 13` | Wersja jest poza zakresem. | Wyślij obsługiwaną wersję. |
| `422` | `invalid query parameters` | Nieznany parametr, nieprawidłowy UUID, wersja, która nie jest liczbą całkowitą, albo nieznana wartość `selection`. | Popraw [zapytanie](/pl/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | Wystąpienia nie ma w przechowywanej historii tej grupy. | Skopiuj ID wystąpienia ze zdarzeń tego problemu. Nie używaj zamiast niego `latest` ani `recommended` bez zgody. |
| `404` | `issue not found` | Żaden projekt dostępny do odczytu nie ma tego problemu. | Sprawdź konto i UUID problemu. Nie wysyłaj UUID wystąpienia jako ID problemu. |

Brak wystąpienia nie oznacza, że brakuje problemu. `404` nie pokazuje, czy
inne konto może odczytać problem.

### Odpowiedź z analizą śladu

Użyj `GET /api/telemetry/traces/{trace_id}/investigation`, aby odczytać jeden
ślad wraz z jego ścieżką błędu, najwolniejszą ścieżką i powiązanymi
sygnałami. Parametry zapytania to `response_version`, `project_id`, `release` i
`environment`. Wszystkie są opcjonalne. Żądaj wersji 3:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

Wersja 2 dodaje `cause` i `fix` do każdego powiązanego problemu. Wersja 3
dodaje `span_id` do powiązanych problemów, akcji i metryk, gdy zostało
zarejestrowane.

Punkt odniesienia (`baseline`) obejmuje 24 godziny przed startem spanu.

wartościami. Punkt odniesienia `not_found` nie ma przechowywanych spanów tego

zerowa liczba.

### Odpowiedź z analizą logu

Użyj `GET /api/logs/{log_id}/investigation`, aby odczytać jeden log i
powiązane z nim dowody. Ta trasa nie ma parametrów zapytania. Skopiuj ID logu
z listy logów.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

Odczyt może zwrócić dowody spoza filtrów listy logów. Powiązane odczyty
używają projektu, środowiska i wydania logu oraz okna 5 minut przed logiem i
5 minut po nim. Pobliskie logi muszą też mieć tę samą usługę. Nie potrzebują
ID śladu. Odczyty dokładnego śladu wymagają ID śladu logu i mogą obejmować
inne usługi. Podsumowanie śladu używa tego samego ID śladu i zakresu, ale bez
okna czasowego.

### Odpowiedź z analizą akcji

Użyj `GET /api/telemetry/actions/{action_id}/investigation`, aby odczytać
jedną akcję produktową, jej zgłoszony status i powiązane dowody. Ta trasa
nie ma parametrów zapytania. Powiązane odczyty używają tego samego okna i
zakresów co analiza logu.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/telemetry/actions/$ACTION_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

`correlations`, `timeline` i `next_actions` mają takie same struktury jak w
analizie logu. Powiązane akcje nie obejmują akcji, która jest obiektem
analizy.

prywatności, aby spełnić tę sugestię.

### Odpowiedź z analizą metryki

Użyj `GET /api/telemetry/metrics/investigation`, aby odczytać jedną nazwę
metryki w jednym projekcie i zakresie czasu. Odpowiedź zawiera bieżący szereg,
porównanie z poprzedzającym oknem o tej samej długości, ostatnią próbkę,
przykładowe ślady i ukończone wdrożenia. Wersja 2 dodaje opis metryki z
ostatniej przechowywanej próbki. Wersja 1 zawsze podaje
`description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` i `since` są wymagane. `since` jest włączne, a `until`
wyłączne. Domyślnie `until` to bieżący moment. Porównanie odczytuje też
poprzedzające okno o tej samej długości.

`relative_change_percent` to `(current - previous) / abs(previous) * 100`.
Ma wartość `null`, gdy poprzednia wartość wynosi zero lub jej brakuje.
`expected_buckets_per_series` liczy możliwe przedziały, a nie przedziały z
danymi. Nie rysuj pustych przedziałów jako zera. Wdrożenie w pobliżu zmiany
nie dowodzi, że ją spowodowało.

Projekt, którego konto nie może odczytać, zwraca `200 OK` z
`analysis.status: "no_samples"`, a nie `404`. Pusty wynik nie opisuje innych
typów sygnałów.

Limity metryk: zakres to najwyżej 31 dni. Każdy szereg ma najwyżej 500
przedziałów. `series_limit` wynosi od 1 do 20, domyślnie 10. Odpowiedź zwraca
najwyżej 20 przykładowych śladów i 20 wdrożeń.

| HTTP | `error` | Naprawa |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Pomiń `response_version` albo wyślij `2`. |
| `422` | `metric series project_id is required` | Wyślij ID jednego projektu, który konto może odczytać. |
| `422` | `metric series name is required` | Skopiuj nazwę z listy metryk. |
| `422` | `metric series since is required` | Wyślij wartość taką jak `24h` albo znacznik czasu RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | Użyj krótszego zakresu. |
| `422` | `metric series interval would exceed 500 buckets` | Użyj `interval=auto` albo dłuższego przedziału. |
| `422` | `metric series_limit must be between 1 and 20` | Wyślij wartość od 1 do 20. |

`interval` to `auto`, `1m`, `5m`, `15m`, `1h`, `6h` lub `1d`. `group_by` to
`none`, `service_name`, `release` lub `environment`. Inne wartości zwracają
`422`.

### Błędy analizy

| HTTP | Trasa | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Akcja | `action not found` |
| `404` | Ślad | `trace not found` |
| `422` | Ślad | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, akcja, problem | `invalid URL path parameters`, gdy ID w ścieżce nie jest UUID |
| `422` | Problem, ślad, span, metryka | `invalid query parameters` dla nieznanego parametru lub wartości niewłaściwego typu |

`404` oznacza, że żaden projekt dostępny do odczytu nie ma tego rekordu.
Każda trasa zwraca też `401` bez prawidłowego uwierzytelnienia i `405` dla
metody innej niż `GET`. Odpowiedzi
[o braku zasobu](/pl/reference/api-errors#resource-not-found),
[o nieprawidłowej wartości w ścieżce](/pl/reference/api-errors#invalid-path-value),
[o błędzie uwierzytelniania](/pl/reference/api-errors#authentication-failure) i
[o nieobsługiwanej metodzie](/pl/reference/api-errors#unsupported-method)
opisuje strona [Błędy API](/pl/reference/api-errors).

Opcjonalny odczyt dowodów może się nie powieść wewnątrz odpowiedzi `200 OK`.
Kolekcja podaje wtedy `unavailable`. Nie pokazuj jej jako `not_found` ani jako
0 rekordów.

## <span id="severity-values">Wartości ważności</span>

Wartości ważności widoczne dla użytkownika to `info`, `warning`, `error` i
`critical`. SDK i środowiska uruchomieniowe mogą wysyłać popularne aliasy,
takie jak `trace`, `debug`, `warn` lub `fatal`. Odpowiedzi REST i odpowiedzi
na żywo zawsze zwracają wartość kanoniczną. Na przykład LogBrew przyjmuje
`warn` na wejściu i zwraca `warning`. Przyjmowanie danych odrzuca nieznane
wartości ważności.

| Alias | Wartość kanoniczna |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Odpowiedzi reguł ważności</span>

Reguła ważności zmienia sposób, w jaki LogBrew pokazuje log lub problem. Nie
zmienia poziomu ważności zarejestrowanego przez aplikację. Logi i problemy
zwracają obiekt `triage`:

| Pole | Znaczenie |
| --- | --- |
| `effective_severity` | Poziom ważności do wyświetlenia. Bez reguły jest równy `severity`. |
| `ignored` | `true`, gdy reguła logu ignoruje log albo gdy problem jest zarchiwizowany. |
| `rule_applied` | `true`, gdy obowiązuje reguła ważności lub stan ignorowania. `false` to wartość domyślna, a nie brak danych. |

Do wyświetlania używaj `triage.effective_severity`. Zachowaj `severity` jako
zarejestrowaną wartość. Domyślnie lista logów pomija ignorowane logi. Aby je
uwzględnić, wyślij `status=ignored` lub `status=all` w `GET /api/logs`.

Konto musi mieć uprawnienie do zarządzania problemami w projekcie. Dostęp do
odczytu nie wystarcza. Bez tego uprawnienia zmiana reguły zwraca `403` z
`code: forbidden`.

### Zmień regułę logu

`PUT /api/logs/{log_id}/triage-rule` ustawia regułę dla logu i późniejszych
logów z tą samą sygnaturą. Treść wymaga zarówno `severity`, jak i `ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Odpowiedź `200 OK` zawiera pełny [log](#log-response). Jego `severity`
pozostaje `warning`. Jego `triage` pokazuje regułę:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Ten fragment pokazuje tylko zmienione pola. `severity` w żądaniu to
`source`, `info`, `warning`, `error` lub `critical`. `source` przywraca
zarejestrowany poziom ważności. Nie przywraca zignorowanego logu do stanu
aktywnego. Aby znowu pokazać log, wyślij `"ignored": false`.

### Zmień regułę problemu

`PUT /api/telemetry/issues/{issue_id}/triage-rule` ustawia wyświetlany poziom
ważności zgrupowanego problemu i jego późniejszych wystąpień. Treść przyjmuje
tylko `severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Odpowiedź `200 OK` zawiera pełny [problem](#issue-response) w wersji 1.
Zarejestrowane `severity` i `status` się nie zmieniają:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Ten fragment pokazuje tylko część pól. Reguła nie rozwiązuje, nie
archiwizuje ani nie otwiera ponownie problemu. Do tego służy
[zmiana statusu](#issue-status-response-examples). Wyliczony priorytet
wynika z nowego efektywnego poziomu ważności. Aby go zobaczyć, odczytaj
problem z `response_version=2` lub `3`.

Nieobsługiwany poziom ważności zwraca `422`:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Nieznane pole treści, na przykład `status` w regule problemu, zwraca `422` z
`code: invalid_json`. Brakujący albo niedostępny do odczytu log lub problem
zwraca `404` z `code: not_found`. Jeśli odpowiedź zaginie, odczytaj log lub
problem ponownie, zanim znowu wyślesz regułę.

## Format odpowiedzi z błędem

Błędy aplikacji zwracają kopertę JSON. Ten przykład pokazuje odrzucone
żądanie. Tekst `error` i `next` zależy od rodzaju błędu:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Używaj `code` do rozgałęzień w programie, a `next_action` do automatyzacji.
Pokazuj ludziom `error` i `next` jako zwykły tekst. Nie parsuj ich treści.
Niektóre błędy dodają pola, takie jak `limit`, `reset_at` lub
`retry_after_seconds`. Odpowiedź bez treści JSON nie ma `code` LogBrew.
Wszystkie kody opisuje strona [Błędy API](/pl/reference/api-errors).

## Odczytuj dane w CLI

CLI odczytuje te same trasy i z `--json` zwraca ten sam JSON. Zacznij od
szerokiego zakresu, a potem go zawężaj:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Dodaj `--pagination cursor`, aby dostać kopertę kursora. CLI żąda wersji 4
odpowiedzi z problemem. Zobacz [Odczytaj następną stronę](/pl/reference/cli#read-the-next-page)
i [Obserwowanie na żywo](/pl/reference/cli#live-watch).

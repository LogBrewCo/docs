Zainstaluj pakiet SDK LogBrew dla swojego środowiska uruchomieniowego. SDK
formatuje zdarzenia i je dostarcza. Przewodnik pakietu opisuje jego typy
zdarzeń, limity i sposób ponawiania.

Wykonaj te kroki dla każdej integracji:

1. Zainstaluj pakiet SDK dla swojego środowiska uruchomieniowego.
2. Przechowuj klucz wysyłania przypisany do projektu poza systemem kontroli
   wersji.
3. Ustaw stałe wartości usługi, środowiska i wydania.
4. Wyślij z aplikacji jedno bezpieczne zdarzenie testowe.
5. Odczytaj wynik dostarczenia. Następnie znajdź zdarzenie w LogBrew.

Przyjęta paczka dotarła do API LogBrew. Filtry nadal mogą ukrywać jej
zdarzenia. Wybierz właściwy projekt i zakres czasu. Następnie dopasuj usługę,
środowisko, wydanie i typ sygnału.

Zanim włączysz rejestrowanie, [wybierz i przetestuj zatwierdzone pola](/pl/guides/safe-capture).
Aby zasilić danymi widok „Analityka”, wykonaj kroki z przewodnika
[Rejestrowanie zdarzeń produktowych](/pl/guides/product-events).

## Wartości ważności

Dla logów i problemów używaj `info`, `warning`, `error` lub `critical`.
Zestawy SDK i środowiska uruchomieniowe mogą wysyłać aliasy, takie jak
`trace`, `debug`, `warn` lub `fatal`. LogBrew zamienia przyjęte aliasy na
wartości kanoniczne.

telemetrię. Użyj konfiguracji SDK lub konfiguracji wysyłania z LogBrew

### Śledzenie żądań w Node.js

Do korelacji śladów, w których spanem głównym jest żądanie, użyj
`@logbrew/sdk` 0.1.16 lub nowszego i `@logbrew/node` 0.1.11 lub nowszego.

Express wymaga `@logbrew/express` 0.1.5 lub nowszego. Fastify i NestJS
wymagają swojego pakietu LogBrew w wersji 0.1.6 lub nowszej.

Te integracje tworzą lub kontynuują jeden span żądania. Nazwa spanu to
dopasowany szablon trasy. Logi, problemy, akcje i metryki w ramach żądania
dziedziczą jego kontekst śladu i spanu. Nowszy pakiet nie dodaje kontekstu do
zdarzeń wysłanych przed aktualizacją.

Domyślna integracja żądań nie rejestruje treści żądań ani odpowiedzi, ciągów
zapytań, dowolnych nagłówków ani surowych wartości `traceparent`.

### ASP.NET Core

CLI w wersji 0.1.55 lub nowszej wykrywa projekty .NET 10, które używają
`Microsoft.NET.Sdk.Web`. Wyświetl podgląd planu konfiguracji z katalogu
głównego projektu. To polecenie nie zmienia twoich plików:

```bash
logbrew setup --json
```

Plan dla opublikowanej wersji instaluje integrację z hostem:

```bash
dotnet add package LogBrew.AspNetCore --version 0.1.3
```

Ustaw `LOGBREW_SERVER_API_KEY`, `LOGBREW_SERVICE_NAME`,
`LOGBREW_ENVIRONMENT` i `LOGBREW_RELEASE` poza systemem kontroli wersji.
Zarejestruj LogBrew w hoście i umieść jego middleware po routingu:

```csharp
using LogBrew;

var builder = WebApplication.CreateBuilder(args);
builder.AddLogBrew();

var app = builder.Build();
app.UseRouting();
app.UseLogBrew();
app.MapGet("/", () => "ok");
app.Run();
```

Bez `LOGBREW_SERVER_API_KEY` oba wywołania rejestrujące bezpiecznie nic nie
robią.
[Pakiet NuGet ASP.NET Core](https://www.nuget.org/packages/LogBrew.AspNetCore/0.1.3)
wskazuje opublikowaną integrację z hostem. Jego publiczny przewodnik opisuje
cykl życia hosta, rejestrowanie żądań, rejestrowanie problemów, ograniczenia
prywatności i odzyskiwanie po błędach.

### Java: Maven lub Gradle

CLI w wersji 0.1.54 lub nowszej wykrywa `pom.xml`, `build.gradle` i
`build.gradle.kts`. Wyświetl podgląd planu konfiguracji z katalogu głównego
projektu. To polecenie nie zmienia twoich plików:

```bash
logbrew setup --json
```

W Mavenie dodaj opublikowany pakiet:

```xml
<dependency>
  <groupId>co.logbrew</groupId>
  <artifactId>logbrew-sdk</artifactId>
  <version>0.1.13</version>
</dependency>
```

W Gradle Kotlin DSL dodaj ten sam artefakt z Maven Central:

```kotlin
implementation("co.logbrew:logbrew-sdk:0.1.13")
```

Użyj Javy 11 lub nowszej.

Aplikacje Spring Boot 3 i 4 mogą udostępnić własny bean `LogBrewClient`.
Włącza on opcjonalne integracje żądań, wyjątków, klienta HTTP, JDBC i pamięci
podręcznej.

Rejestrowanie Spring Kafka trzeba jawnie włączyć ustawieniem
`logbrew.kafka.enabled=true`. Korzysta ono z istniejącej w aplikacji
zależności Spring Kafka i beana klienta.

[Artefakt Java SDK w Maven Central](https://central.sonatype.com/artifact/co.logbrew/logbrew-sdk/0.1.13)
wskazuje opublikowany pakiet. Jego publiczny przewodnik opisuje dostarczanie
przez HTTP z limitami, zamykanie, logowanie, konfigurację Springa, korelację
Kafka i ograniczenia prywatności.

### C++ z CMake

SDK dla C++ wymaga C++17 i CMake 3.16 lub nowszego. CLI w wersji 0.1.39 lub
nowszej wykrywa `CMakeLists.txt` w katalogu głównym. Uruchom
`logbrew setup --json`, aby wyświetlić podgląd tego planu konfiguracji bez
zmieniania plików:

```cmake
include(FetchContent)
FetchContent_Declare(
  logbrew
  GIT_REPOSITORY https://github.com/LogBrewCo/sdk.git
  GIT_TAG cpp/logbrew-cpp/v0.2.3
  GIT_SHALLOW TRUE
  SOURCE_SUBDIR cpp/logbrew-cpp
)
FetchContent_MakeAvailable(logbrew)

target_link_libraries(your_app PRIVATE LogBrew::LogBrew)
```

Główny target nie ma zależności. Aby wysyłać paczki przez opcjonalny
transport libcurl, zastąp końcowe wywołanie `FetchContent_MakeAvailable` i
powyższe linkowanie targetu tym kodem:

```cmake
set(LOGBREW_BUILD_HTTP_TRANSPORT ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(logbrew)
target_link_libraries(your_app PRIVATE LogBrew::HttpTransport)
```

Skonfiguruj aplikację. Następnie zbuduj ją, aby przetestować wybraną wersję
SDK:

```bash
cmake -S . -B build &&
cmake --build build
```

Jeśli build nie może pobrać monorepo SDK, użyj osobnego pliku
`logbrew-cpp-0.2.3.tar.gz` z
[wydania C++ 0.2.3](https://github.com/LogBrewCo/sdk/releases/tag/cpp/logbrew-cpp/v0.2.3).
Rozpakowany pakiet obsługuje `cmake --install` i
`find_package(LogBrew 0.2.3 CONFIG REQUIRED)`. Jego przewodnik opisuje
typowany kontekst, dowody problemów, zdarzenia spanów, metryki, akcje i
dostarczanie przez HTTP.

## <span id="javascript-queue-tracing">Śledzenie kolejek w JavaScript</span>

Integracje kolejek dla Node to osobne pakiety npm. Zainstaluj podstawowe
pakiety JavaScript LogBrew, pakiet integracji i klienta kolejki lub brokera,
którego twoja aplikacja już używa.

| Kolejka lub broker | Instalacja |
| --- | --- |
| BullMQ | `npm install @logbrew/sdk @logbrew/node @logbrew/bullmq bullmq` |
| KafkaJS | `npm install @logbrew/sdk @logbrew/node @logbrew/kafkajs kafkajs` |
| RabbitMQ / amqplib | `npm install @logbrew/sdk @logbrew/node @logbrew/amqplib amqplib` |
| Amazon SQS | `npm install @logbrew/sdk @logbrew/node @logbrew/aws-sqs @aws-sdk/client-sqs` |

Używaj tych pakietów do jawnej korelacji śladów wokół wybranych wywołań
kolejki. Tę korelację kontroluje aplikacja. LogBrew nie zarządza połączeniem z
brokerem, nie tworzy kolejek i domyślnie nie modyfikuje globalnie każdego
klienta.

<Warning>
  Nie umieszczaj w konfiguracji SDK treści wiadomości z kolejki, dowolnych
  nagłówków wiadomości, adresów URL brokerów ani tokenów sesji lub konta
  (bearer). Użyj serwerowej konfiguracji wysyłania z LogBrew przypisanej do
  projektu.
</Warning>

## <span id="required-envelope-fields">Bezpośrednie wysyłanie natywnej koperty</span>

`POST /api/telemetry/ingest` jest tylko dla własnych klientów, dla których nie
ma publicznego SDK LogBrew. Publiczne zestawy SDK używają własnego formatu
paczek. Ten endpoint nie przyjmuje tego formatu.

W jednej natywnej kopercie wyślij od 1 do 512 elementów. Wszystkie elementy w
jednej kopercie mają wspólny projekt, usługę, wydanie, środowisko i
opcjonalny kontekst śladu.

| Pole | Wymagane | Uwagi |
| --- | --- | --- |
| `project_id` | Tak | UUID projektu LogBrew. Musi pasować do projektu klucza wysyłania. |
| `environment` | Tak | Środowisko wdrożenia. Najwyżej 64 bajty UTF-8, bez białych znaków, `/` i `\`. Wartość `None` jest odrzucana. |
| `release` | Tak | Wersja kodu. Najwyżej 200 bajtów UTF-8, bez `/`, `\`, tabulatorów i znaków nowego wiersza. Nie może mieć wartości `.` ani `..`. |
| `service_name` | Tak | Logiczna nazwa usługi, na przykład `checkout-api`. Nie może być pusta. |
| `sdk_name` | Tak | Identyfikator SDK lub własnego klienta. |
| `sdk_version` | Tak | Wersja SDK lub własnego klienta. |
| `items` | Tak | Od 1 do 512 elementów `log`, `trace_span`, `issue` lub `action`. |
| `trace_id` | Nie | ID śladu wspólne dla skorelowanych elementów koperty. Wymagane, gdy element ma `span_id`. |

### Pola elementów

Każdy element ma `type` i obiekt `data`. Element logu używa `level`. Element
problemu używa `severity`. Oba przyjmują wartości opisane w sekcji
[Wartości ważności](/pl/concepts/telemetry#severity-values).

| Pole elementu | Dotyczy | Uwagi |
| --- | --- | --- |
| `id` | Wszystkich elementów | Opcjonalne ID zdarzenia nadane przez klienta. Od 1 do 200 znaków, unikalne w kopercie. |
| `span_id` | `log`, `issue`, `action` | Opcjonalne. 16 znaków szesnastkowych, nie same zera. Koperta musi mieć `trace_id`. |
| `name` | `action` | Wymagane. Najwyżej 64 bajty UTF-8. Nie może zaczynać się od `$` ani zaczynać lub kończyć białym znakiem. Nie może też zawierać znaków sterujących ani niewidocznych znaków formatowania. |

Jeśli twój klient może ponawiać wysyłkę, wysyłaj `id` z każdym elementem. Gdy
ponowienie wyśle przyjęty już element z tym samym `id` i tą samą treścią,
LogBrew nie zapisze go drugi raz. Odpowiedź policzy ten element w
`already_accepted`.

### Pola elementu problemu

Element `issue` zgłasza jedno wystąpienie błędu. LogBrew grupuje pasujące
wystąpienia w jeden problem.

| Pole problemu | Wymagane | Uwagi |
| --- | --- | --- |
| `severity` | Tak | Ważność błędu, na przykład `error`. |
| `title` | Tak | Krótki tytuł na liście problemów. |
| `message` | Tak | Komunikat błędu. |
| `exception_type` | Nie | Typ wyjątku lub błędu, na przykład `TypeError`. |
| `stack_trace` | Nie | Tekst śladu stosu z twojego środowiska uruchomieniowego. |
| `stack_frames` | Tak | Tablica ramek stosu. Wyślij `[]`, gdy nie masz ramek. |
| `fingerprint` | Nie | Klucz grupowania. Wystąpienia z tą samą wartością trafiają do jednego problemu. |
| `attributes` | Tak | Obiekt JSON z dodatkowym kontekstem. Wyślij `{}`, gdy nie masz kontekstu. |
| `occurred_at` | Tak | Czas błędu w formacie RFC 3339, na przykład `2026-06-01T12:00:00Z`. |

Ramka stosu przyjmuje `module`, `function`, `filename`, `line`, `column`,
`in_app` i `debug_id`. Wszystkie pola ramki są opcjonalne. Ustaw `in_app` na
`true` dla ramek z własnego kodu. `debug_id` to UUID, który wskazuje artefakt
wydania używany do symbolizacji.

Bez `fingerprint` LogBrew grupuje według `exception_type`, a gdy go brakuje,
według `title`. Używa też `module`, `function` i `filename` z pierwszych 8
ramek. Bez ramek używa `title` i `message`. Numery wierszy i kolumn nie
zmieniają grupy.

### Przykładowe żądanie

Przykład wysyła jeden element `issue`, jeden element `log` i jeden element
`action`. Zapisz poniższy JSON jako `telemetry-envelope.json`. Zastąp
przykładowe ID projektu dokładnym ID projektu twojego klucza wysyłania. Ustaw
znaczniki czasu na bieżący czas UTC zdarzenia testowego. Użyj własnych wartości
usługi i wydania.

```json telemetry-envelope.json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "environment": "production",
  "release": "api@1.2.3",
  "service_name": "checkout-api",
  "sdk_name": "custom-native-client",
  "sdk_version": "1.0.0",
  "items": [
    {
      "type": "issue",
      "data": {
        "id": "evt_example_issue_0001",
        "severity": "error",
        "title": "PaymentError: card authorization timed out",
        "message": "card authorization timed out after 3 attempts",
        "exception_type": "PaymentError",
        "stack_trace": "PaymentError: card authorization timed out after 3 attempts\n    at authorizeCard (src/payments/authorize.js:42:11)\n    at submitOrder (src/checkout/submit.js:18:5)",
        "stack_frames": [
          {
            "function": "authorizeCard",
            "filename": "src/payments/authorize.js",
            "line": 42,
            "column": 11,
            "in_app": true
          },
          {
            "function": "submitOrder",
            "filename": "src/checkout/submit.js",
            "line": 18,
            "column": 5,
            "in_app": true
          }
        ],
        "attributes": { "route": "/checkout" },
        "occurred_at": "2026-06-01T12:00:00Z"
      }
    },
    {
      "type": "log",
      "data": {
        "id": "evt_example_log_0001",
        "level": "warning",
        "message": "checkout retry scheduled",
        "source": "runtime",
        "attributes": { "route": "/checkout" },
        "occurred_at": "2026-06-01T12:00:00Z"
      }
    },
    {
      "type": "action",
      "data": {
        "id": "evt_example_action_0001",
        "name": "checkout_failed",
        "distinct_id": "user_123",
        "session_id": "session_456",
        "occurred_at": "2026-06-01T12:00:00Z",
        "properties": { "cart_total": 4200 }
      }
    }
  ]
}
```

Wczytaj wartość klucza wysyłania projektu do `LOGBREW_INGEST_BEARER` z
chronionej konfiguracji. Nie wypisuj jej i nie używaj poświadczenia konta.
Poniższe polecenie wysyła plik jeden raz. Wymaga curl 7.76.0 lub nowszego:

```bash
: "${LOGBREW_INGEST_BEARER:?load the project-scoped ingest key}" &&
curl --fail-with-body --silent --show-error \
  "https://api.logbrew.co/api/telemetry/ingest" \
  -H "Authorization: Bearer $LOGBREW_INGEST_BEARER" \
  -H "Content-Type: application/json" \
  --data-binary @telemetry-envelope.json \
  --write-out '\nHTTP %{http_code}\n'
```

Odczytaj status HTTP i treść odpowiedzi. `--fail-with-body` zachowuje treść
błędu i przy błędach HTTP zwraca niezerowy kod wyjścia. Błąd sieci lub
przekroczenie limitu czasu nie mówi, czy LogBrew przyjął żądanie. Wyślij ten
sam plik ponownie tylko wtedy, gdy jego elementy mają wartości `id`. Bez
wartości `id` drugie wysłanie może zapisać elementy dwa razy.

### Odpowiedź

Udane żądanie zwraca `200` z liczbą nowych elementów w każdym strumieniu.
`already_accepted` liczy elementy, które dostarczyło już wcześniejsze żądanie.

```json
{
  "issues": 1,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

### Błędy

Nieprawidłowy lub unieważniony klucz wysyłania zwraca `401`. Klucz innego
projektu też zwraca `401`:

```json
{
  "error": "Invalid ingest key",
  "code": "ingest_key_invalid",
  "next": "create a project-scoped ingest key, then retry ingestion with that key",
  "next_action": {
    "code": "configure_ingest_key",
    "target": "project_ingest_key"
  }
}
```

Użyj klucza wysyłania przypisanego do projektu. Nie zastępuj go
poświadczeniem konta. Klucz artefaktów nie może wysyłać telemetrii.

Koperta, która narusza regułę pola, zwraca `422` z kodem `validation_failed`.
Pole `error` wskazuje regułę. Pole `next` mówi, jak poprawić żądanie. Na
przykład `"items": []` zwraca:

```json
{
  "error": "native telemetry envelope cannot be empty",
  "code": "validation_failed",
  "next": "send at least one native telemetry item",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Nie wysyłaj koperty, gdy nie ma zdarzeń. Koperta z więcej niż 512 elementami
zwraca `422` z błędem `native telemetry envelope exceeds the item limit`.
Podziel ją na paczki po najwyżej 512 elementów. W każdej paczce zachowaj
projekt i wspólny kontekst.

W przypadku limitów wykorzystania, limitów żądań i błędów usługi postępuj
zgodnie ze zwróconym `code` opisanym na stronie [Błędy API](/pl/reference/api-errors).

<Tip>
  Ustaw wydanie i środowisko w konfiguracji SDK. Dla każdej operacji twórz lub
  kontynuuj kontekst śladu. Nie używaj jednego ID śladu do niezwiązanych ze
  sobą zadań.
</Tip>

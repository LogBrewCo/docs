Interfejs wiersza poleceń (CLI) LogBrew odczytuje w terminalu logi, problemy,
ślady i akcje. Może też zmieniać status problemów. Użyj `--json`, aby
przekazać skryptom i agentom AI ustrukturyzowany wynik.

Zanim uruchomisz polecenie, zastąp każdy symbol zastępczy w nawiasach ostrych.
Używaj ID projektów, problemów i śladów zwróconych przez LogBrew.

## Zainstaluj CLI

Wybierz jedną metodę instalacji.

macOS lub Linux:

```bash
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/LogBrewCo/cli/releases/latest/download/logbrew-cli-installer.sh | sh
```

Windows (PowerShell):

```powershell
powershell -ExecutionPolicy Bypass -c "irm https://github.com/LogBrewCo/cli/releases/latest/download/logbrew-cli-installer.ps1 | iex"
```

Homebrew:

```bash
brew install LogBrewCo/tap/logbrew
```

npm:

```bash
npm install -g logbrew-cli@latest
```

Cargo:

```bash
cargo install logbrew-cli
```

W systemie Windows możesz też zainstalować pakiet MSI z
[najnowszego wydania](https://github.com/LogBrewCo/cli/releases/latest).

<Note>
  Cargo wymaga Rusta 1.87 lub nowszego. Pozostałe metody instalują natywny
  plik binarny i nie wymagają Rusta.
</Note>

## Zaktualizuj CLI

CLI nie aktualizuje się automatycznie. Użyj tej samej metody co przy
instalacji.

Homebrew:

```bash
brew update && brew upgrade LogBrewCo/tap/logbrew
```

npm:

```bash
npm install -g logbrew-cli@latest
```

Cargo:

```bash
cargo install --locked logbrew-cli
```

Jeśli używasz instalatora dla powłoki lub dla PowerShella, uruchom go ponownie.

Następnie odczytaj wersję. Porównaj ją z
[najnowszym wydaniem](https://github.com/LogBrewCo/cli/releases/latest):

```bash
logbrew version --json
```

JSON zawiera pola `ok`, `name`, `version`, `binary`, `os` i `arch`.

## Zaloguj się i sprawdź sesję

Sprawdź konto używane w bieżącym terminalu:

```bash
logbrew status --json
logbrew whoami --json
```

Jeśli `whoami` pokazuje oczekiwane konto, przejdź dalej. Jeśli nie, zaloguj
się. Logowanie u dostawcy kończy człowiek w przeglądarce. Agent kodujący musi
poprosić człowieka o ten krok.

```bash
logbrew login --provider github
```

Dostawca to `github` (domyślnie), `gitlab`, `bitbucket` lub `google`. Użyj `--no-open`,
aby wypisać adres URL logowania bez otwierania przeglądarki. `--json` też
wypisuje dane do przekazania logowania i nie otwiera przeglądarki.

Po zalogowaniu uruchom ponownie `status` i `whoami`. Nie umieszczaj poświadczeń
konta w prompcie, raporcie ani pliku źródłowym.

## Zaplanuj konfigurację SDK

Przejdź do katalogu z manifestem pakietu lub builda aplikacji. W monorepo
wybierz jedną aplikację lub usługę. Następnie uruchom:

```bash
logbrew setup --json
```

Odczytaj `detected`, `install_ready`, `install_plan` i `next`. Plan podaje
środowisko uruchomieniowe, framework, menedżer pakietów i polecenie instalacji.
CLI nie instaluje pakietów i nie zmienia plików. `logbrew init`, `install`,
`configure` i `sdk` zwracają ten sam plan.

<Warning>
  W konfiguracji SDK umieść klucz wysyłania projektu. Nigdy nie używaj
  poświadczenia konta jako klucza SDK. Nie przechowuj kluczy wysyłania w
  systemie kontroli wersji.
</Warning>

Kroki dla poszczególnych środowisk uruchomieniowych opisuje strona
[Integracja SDK](/pl/guides/sdk-ingestion). Uruchom
`logbrew examples`, aby zobaczyć krótką listę typowych poleceń.

## Odczytuj, twórz i konfiguruj projekty

Wyświetl aktywne projekty na swoim koncie:

```bash
logbrew projects --json
```

Wybierz ID projektu z wyniku. Używaj go przy kluczach i odczytach.

Aby utworzyć klucz wysyłania dla istniejącego projektu, wskaż nowy plik poza
systemem kontroli wersji. CLI zapisuje klucz w tym pliku z dostępem tylko dla
właściciela. Nie wypisuje klucza ani ścieżki pliku.

```bash
logbrew projects keys create "<project_id>" --ingest-key-file "<private_key_file>" --json
```

| Flaga | Wartość |
| --- | --- |
| `--kind` | `sdk` (domyślnie), `browser`, `server`, `cli`, `artifact` lub `read`. Klucz `artifact` przesyła mapy źródeł (source maps) i natywne pliki debugowania. Nie może wysyłać telemetrii. Klucz `read` czyta telemetrię 1 projektu i nie może jej wysyłać. Zobacz [Rodzaje kluczy projektu](/pl/guides/verify-setup#project-key-kinds). |
| `--label` | Nazwa klucza, maksymalnie 120 znaków. Domyślnie `CLI-created SDK key`. |

Wynik JSON zawiera `status`, `project_id`, `ingest_key`, `checks` i `next`.
`ingest_key` zawiera pola klucza: `id`, `label`, `kind`, `created_at` i
`expires_at`. Wymianę klucza opisuje strona [Wymień klucz wysyłania](/pl/guides/rotate-ingest-key).

Aby unieważnić klucz, użyj jego `id` z tego wyniku:

```bash
logbrew projects keys revoke "<project_id>" "<key_id>" --yes --json
```

Klucz przestaje działać przy następnym żądaniu.

To polecenie tworzy poświadczenie. Zanim je uruchomisz, upewnij się, że projekt
jest właściwy. Jeśli wynik jest niepewny, uruchom to samo polecenie ponownie.
CLI wznowi wtedy oczekującą próbę. Użyj `--abandon-retry` tylko wtedy, gdy
chcesz zacząć nową próbę.

Aby utworzyć nowy projekt, wykonaj kroki z [szybkiego startu](/pl/quickstart).
Ten przewodnik używa polecenia
`logbrew projects create "<name>" --ingest-key-file "<private_key_file>"`,
które zapisuje pierwszy klucz w ten sam sposób. Uruchom
`logbrew setup --create-project`, aby przeczytać pomoc dotyczącą tworzenia
projektu. To polecenie nie tworzy projektu.

Po kroku konfiguracji możesz go zapisać w projekcie. Wartość `--source` to
`api`, `cli` lub `sdk`:

```bash
logbrew projects setup "<project_id>" --source cli --environment production --json
```

Następnie sprawdź gotowość projektu:

```bash
logbrew doctor --project "<project_id>" --json
```

Kod wyjścia `0` nie oznacza, że wszystkie sprawdzenia się powiodły. Odczytaj
`status` raportu i każde sprawdzenie. Zobacz [opis raportu diagnostyki
projektu](/pl/reference/cli#read-a-project-doctor-report).

## Sprawdź wykorzystanie konta

Odczytaj wykorzystanie i limity. To nie zmienia stanu konta ani rozliczeń.

```bash
logbrew usage --json
```

`logbrew account usage --json` zwraca ten sam wynik. Odpowiedź podaje plan,
stan limitu, datę odnowienia, łączne wykorzystanie według projektu i rodzaju
telemetrii oraz następny krok. Pola to między innymi `plan`, `state`,
`reset_at`, `by_project`, `by_stream` i `next`.

## Obserwuj zdarzenia na żywo

Użyj polecenia watch, aby widzieć nowe zdarzenia podczas testowania zmiany.
Naciśnij Ctrl+C, aby zakończyć.

```bash
logbrew watch --severity error,critical --json
```

Watch przesyła strumieniowo tylko JSON. Bez `--json` polecenie kończy się
błędem. Dodaj `logs`, `issues` lub `actions`, aby obserwować jeden typ, na
przykład `logbrew watch logs --json`. Watch nie obsługuje śladów ani spanów.

Watch nie ma filtra projektu, wydania ani środowiska. Dla jednego projektu
użyj odczytów opisanych wyżej. Obsługiwane zasoby i filtry opisuje sekcja
[Obserwowanie na żywo](/pl/reference/cli#live-watch).

## Poznaj kontekst, zanim zmienisz kod

Zanim zaproponujesz poprawkę, odczytaj kontekst.

<Steps>
  <Step title="Odczytaj problem">
    ```bash
    logbrew read issue "<issue_id>" --json
    ```
  </Step>

  <Step title="Odczytaj ślad">
    Wykonaj ten krok tylko wtedy, gdy problem ma ID śladu. Problem bez śladu
    też jest poprawny.

    ```bash
    logbrew read trace "<trace_id>" --project "<project_id>" --json
    ```
  </Step>

  <Step title="Odczytaj wyjaśnienie">
    ```bash
    logbrew explain issue "<issue_id>" --json
    ```

    Dla logu użyj `logbrew explain log "<log_id>" --json`. Dla akcji użyj
    `logbrew explain action "<action_id>" --json`.
  </Step>

  <Step title="Rozwiąż po weryfikacji">
    ```bash
    logbrew set issue "<issue_id>" resolved --json
    ```

    Aby zmienić status, priorytet lub przypisanie w wielu problemach,
    zobacz [Zmień status i priorytet problemu](/pl/reference/cli#change-issue-status-and-priority)
    i przewodnik [Zarządzanie problemami](/pl/guides/issue-workflow).
  </Step>
</Steps>

## Wynik JSON

- Umieść `--json` przed poleceniem lub po nim, na przykład
  `logbrew --json status` lub `logbrew status --json`.
- Zanim użyjesz wyniku, sprawdź kod wyjścia.
- Błędy w formacie JSON zawierają `ok`, `error`, `message` i `next`. Przekroczenie limitu
  czasu nie dowodzi, że zapis się nie powiódł. Zanim powtórzysz zapis,
  przeczytaj jego zasady ponawiania.
- Nie automatyzuj na podstawie wyniku bez `--json`. Jego format może się
  zmienić.

Kody wyjścia i przykłady błędów opisuje sekcja
[Odczytaj wyniki i błędy](/pl/reference/cli#read-results-and-errors).

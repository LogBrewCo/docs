LogBrew is an observability platform for developers and coding agents. Your
applications send telemetry to LogBrew. Use the native `logbrew` CLI, the API,
or the website to read that evidence for the project you select.

## <span id="what-is-observability">Observability and telemetry</span>

Telemetry is data that an application sends about its operation. Observability
is the ability to examine application behavior through that data.

Monitoring measures known conditions, such as error rate or response time.
Observability helps you examine behavior outside those known conditions. A
monitoring chart can show that checkout latency increased. An investigation
connects the service, release, error, log, and trace for that change when the
application captured that evidence.

## <span id="what-logbrew-tracks">Signals</span>

| Signal | Use it to |
| --- | --- |
| Issues | Find repeated failures that LogBrew groups by a stable fingerprint. |
| Logs | Read the records that one component reported. |
| Traces | Examine the operations in one request or job. |
| Metrics | Compare a measured value over time. |
| Actions | Examine product activity from a person or a system. |

The [telemetry guide](/concepts/telemetry) explains each signal and its
fields. Each signal has its own list. An empty Logs view can occur while
Issues or Traces contain data.

## <span id="keep-project-and-service-separate">Project and service</span>

A project is the access boundary for telemetry. One project can contain
several services, such as a web app, an API, and a mobile app. A service is
the component that sent a signal. Project and service names can be the same,
but the filters select different scopes.

Environment, release, and time filters also change the results. Before you
compare two results, make sure that these filters match. See
[Projects](/concepts/projects) and [Releases](/concepts/releases).

## <span id="follow-exact-relationships">Trace relationships</span>

A trace contains spans. Each span records one operation, its duration, and
its status. Logs, issues, actions, and metrics can carry the identifiers of
their active trace and span. Only matching identifiers link a signal to a
trace. Do not link signals by message, release, or timestamp alone.

Read the trace state before you open a trace:

| State | Meaning |
| --- | --- |
| `available` | Exact trace evidence is available to open. |
| `not_linked` | The event was captured without active trace context. |
| `not_found` | A trace reference exists, but no trace matched the selected scope. |
| `unavailable` | The trace read could not complete at that time. |

See [Distributed tracing](/concepts/distributed-tracing) for propagation and
missing-context checks.

## <span id="read-evidence-states-before-drawing-a-conclusion">Evidence limits</span>

LogBrew shows only the evidence that your application captured. Responses
mark evidence as captured, missing, redacted, truncated, or unavailable. Some
counts are approximate. An empty field is not a zero measurement, and an
`unavailable` read does not show that the data does not exist.

## <span id="a-practical-investigation">Examine a failed checkout</span>

If checkout failures increase after a release, use this sequence:

1. Select the project and the time range of the failure.
2. Open unresolved issues, or read recent error logs.
3. Read the service, environment, release, and occurrence time.
4. Open the exception, stack, and breadcrumb evidence when it is available.
5. If the selected occurrence has an `available` trace, open that trace.
6. Compare a metric trend with the event time. A time match does not show a cause.
7. Record the missing, redacted, or truncated evidence before you change code.

One occurrence can have different evidence from another occurrence of the
same issue.

## <span id="built-for-people-and-coding-agents">For developers and coding agents</span>

Every CLI read command supports `--json`. Read the exit code before you use
a result. API errors return a stable `code` and a `next_action`. Use those
fields in program logic instead of the English message. Use an account
credential for reads. A project ingest key only sends telemetry.

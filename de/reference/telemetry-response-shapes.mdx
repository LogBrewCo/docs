Diese Seite zeigt ein Beispiel für jede Antwortfamilie der
[Telemetrie-API](/de/reference/telemetry-api). Alle Werte sind synthetisch.
Fehlercodes und Wiederherstellung finden Sie unter
[API-Fehler](/de/reference/api-errors).

## Eine Antwort lesen

Lesen Sie jede Antwort in dieser Reihenfolge:

1. Lesen Sie den HTTP-Status.
2. Prüfen Sie, dass der Antwort-Body die Struktur der Route hat.
3. Prüfen Sie, dass jede `project_id` im angefragten Projektbereich liegt.
4. Lassen Sie kanonische Enum-Werte und Kennungen unverändert.
5. Folgen Sie `next_action` nur, wenn der Client dessen `code` und `target`
   unterstützt.
6. Behandeln Sie `null`, ein ausgelassenes Feld und eine leere Liste als
   unterschiedliche Zustände.

Ein `200 OK` kann eine leere Liste enthalten. Eine leere Log-Liste bedeutet,
dass kein Log zur Anfrage passte. Sie bedeutet nicht, dass auch Issues, Traces
oder Aktionen leer sind. Verbinden Sie Signale nicht, nur weil ihre Zeitstempel
nah beieinander liegen. Folgen Sie einem Trace nur, wenn die Antwort seine
genaue `trace_id` enthält.

Ein `404` und eine leere Liste sind verschiedene Ergebnisse. Eine Listenroute
gibt `[]` zurück, wenn kein Datensatz passt. Eine Detailroute gibt `404` mit
`code: not_found` zurück, wenn sie keinen lesbaren Datensatz findet. Keines
der beiden Ergebnisse beweist, dass die Signalaufnahme fehlgeschlagen ist.

## Was Sie senden sollten

Antworten sind nur so nützlich wie die Telemetrie, die Sie senden. Senden Sie
diese Werte mit jedem Umschlag oder in jeder SDK-Einrichtung:

- `release` und `environment`.
- Stabile Namen für Dienste, Aktionen und Metriken.
- Trace-Kontext, wenn Logs, Spans, Aktionen und Issues zur selben Anfrage
  gehören.
- Kanonische Schweregrade: `info`, `warning`, `error` und `critical`.
- Attribute, die beim Debuggen helfen, ohne Geheimnisse oder unnötige
  personenbezogene Daten.

Siehe [SDK-Integration](/de/guides/sdk-ingestion) und
[Erfasste Daten steuern](/de/guides/safe-capture).

## Antwort der Signalaufnahme

Öffentliche SDKs lesen die Antwort von `POST /v1/events` für Sie. Ihr
Anwendungscode muss sie nicht verarbeiten.

### Antwort auf einen SDK-Batch

Ein erfolgreicher SDK-Batch gibt `200 OK` mit der Zahl der angenommenen
Ereignisse pro Stream zurück:

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Feld | Bedeutung |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Ereignisse, die LogBrew aus diesem Batch angenommen hat. |
| `already_accepted` | Ereignisse, deren ID LogBrew schon früher angenommen hat. LogBrew speichert sie nicht noch einmal. |
| `context_updated` | `true`, wenn der Batch den Release- oder Umgebungskontext aktualisiert hat. |

Die Zahlen gelten nur für diesen Batch. Wiederholen Sie einen Batch, den
LogBrew schon angenommen hat, gibt die Antwort `0` für jeden Stream zurück und
die Zahl der Ereignisse in `already_accepted`. Behalten Sie bei einer
Wiederholung die ursprünglichen Ereignis-IDs.

### Antwort auf einen nativen Umschlag

`POST /api/telemetry/ingest` gibt `200 OK` mit der Zahl der angenommenen
Einträge pro Stream zurück:

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

Die native Antwort hat kein Feld `metrics` und kein Feld `context_updated`.
Ergänzen Sie diese Felder nicht. `already_accepted` zählt Einträge, deren `id`
LogBrew für das Projekt schon früher angenommen hat. Siehe
[direkter nativer Umschlag](/de/guides/sdk-ingestion#required-envelope-fields).

### Fehler bei der Signalaufnahme

Ein `401` mit `code: ingest_key_invalid` bedeutet, dass das Ingest-Bearer-Token
widerrufen, abgelaufen oder für das Projekt nicht gültig ist. Bei
`POST /v1/events` gibt ein fehlendes Bearer-Token oder ein Bearer-Token, das
kein Ingest-Schlüssel ist, `401` mit `code: unauthorized` zurück. Verwenden Sie
das aktuelle Ingest-Bearer-Token des Projekts. Wiederholen Sie die Anfrage
nicht mit einem Konto-Bearer-Token.

Ein abgelehnter SDK-Batch gibt `422` mit `code: validation_failed` zurück:

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Weitere `error`-Werte sind `SDK event batch requires at least one event` und
`SDK event type is not supported by this ingest route`. Prüfen Sie die
SDK-Version und die Transportkonfiguration. Senden Sie keinen leeren Batch.
Ändern Sie keine Ereignistypen oder IDs, nur damit ein Batch die Validierung
besteht.

Eine Anfrage mit einer anderen Methode als `POST` gibt `405` mit
`code: method_not_allowed` zurück. Ein unlesbarer JSON-Body gibt
`code: invalid_json` zurück.

## Antwortformat für Telemetrielisten

Listenrouten geben standardmäßig ein einfaches JSON-Array zurück. Eine
erfolgreiche leere Liste ist `[]`.

Mit `pagination=cursor` gibt die Route einen Umschlag zurück. Der
Sammlungsschlüssel entspricht dem Signal:

| Route | Sammlungsschlüssel |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, mit `issue_id` auf oberster Ebene |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, mit `naming_quality` auf oberster Ebene |

`next_cursor` ist ein Objekt mit den Feldern für die Fortsetzung, oder `null`
auf der letzten Seite. Die neuesten Zeilen stehen zuerst. Siehe
[Cursor-Paginierung](/de/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Log-Antwort</span>

Eine Cursor-Seite mit Logs bei `limit=1`:

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Logs enthalten `level` für die Kompatibilität und `severity` für die Anzeige.
Beide enthalten den kanonischen Wert. `triage` enthält das Ergebnis einer
Schweregrad-Regel. Siehe
[Antworten zu Schweregrad-Regeln](#severity-rule-responses).

`trace_id` und `span_id` sind `null`, wenn das Log keinen Trace-Link hat. Dann
ist `next_action` gleich `inspect_related_logs` mit dem Ziel
`telemetry_logs`. Logs, Issues und Aktionen verwenden dieselben 2 Paare für
`next_action`.

`GET /api/logs/{log_id}` gibt ein einzelnes Log in derselben Struktur zurück.

### <span id="issue-response">Issue-Antwort</span>

`GET /api/telemetry/issues/{issue_id}` gibt ein gruppiertes Issue zurück. Die
Liste gibt dieselben Objekte zurück. Dieses Beispiel verwendet die
Standard-Antwortversion 1:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

In Version 1 ist `status` gleich `unresolved`, `resolved` oder `ignored`. Bei
einem archivierten Issue ist `triage.ignored` gleich `true`. Die Paare für
`next_action` und die Lesezugriffe danach finden Sie unter
[Issue untersuchen](/de/guides/investigate-an-issue).

`first_seen_at` und `last_seen_at` sind die Zeitpunkte des ersten und des
jüngsten Vorkommens. Sie ändern sich nicht, wenn sich der Status ändert.

Manche Felder erscheinen nur, wenn LogBrew die Daten hat:

| Feld | Wann es erscheint |
| --- | --- |
| `span_id` | Das Issue hat einen Span-Link. Sonst fehlt das Feld. |
| `diagnostics` | Das jüngste Vorkommen hat einen Ausnahmetyp oder vorherige Schritte. Siehe [Vorkommensverlauf eines Issues](#issue-occurrence-history). |
| `symbolication` | Nur bei `GET /api/telemetry/issues/{issue_id}`, wenn das Issue eine Release-Artefakt-Identität hat. Siehe [Source Maps](/de/guides/source-maps). |

`symbolication.status` ist `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` oder `unavailable`. Die Liste,
Statusänderungen und Regeländerungen geben `symbolication` nicht zurück.

Mit `response_version=2` hat das Issue dieselben Felder, mit diesen
Änderungen:

| Feld | Wert in Version 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` oder `archived`. Version 1 zeigt `archived` als `ignored`. |
| `priority` | `high`, `medium` oder `low`. |
| `priority_source` | `manual`, wenn eine Person die Priorität gesetzt hat. `derived`, wenn die Priorität dem effektiven Schweregrad folgt. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Dieses Beispiel zeigt nur einige Felder. Eine abgeleitete Priorität ist
`high` bei `error` und `critical`, `medium` bei `warning` und `low` bei
`info`. Sie verwendet `triage.effective_severity`. Eine Schweregrad-Regel für
Issues kann sie also ändern.

Mit `response_version=3` hat das Issue alle Felder aus Version 2 und
zusätzlich `assignee`. `assignee` ist `null`, wenn das Issue keine zuständige
Person hat:

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Feld | Bedeutung |
| --- | --- |
| `assignee.user_id` | Nutzer-ID der zuständigen Person. Senden Sie sie als `assignee` in einem Filter oder einer Änderung. |
| `assignee.name` | Name der zuständigen Person, oder `null`, wenn das Konto keinen Namen hat. |
| `assignee.email` | E-Mail-Adresse der zuständigen Person. |

Ein Issue zeigt keine zuständige Person, wenn das zugewiesene Mitglied das
Projekt nicht mehr lesen kann.

Mit `response_version=4` hat `assignee` zusätzlich `type`. Eine Zuweisung an
ein Konto (`user`) hat `user_id`, `name` und `email` wie in Version 3. Eine
Zuweisung an ein Team (`team`) hat `team_id`, `slug` und `name`. Version 3
zeigt eine Zuweisung an ein Team als `null`. Die CLI fordert Version 4 an:

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Jeder andere Wert für `response_version` gibt `422` mit
`code: validation_failed` zurück. Eine Cursor-Seite verwendet für jedes Issue
in `issues` dieselbe Version.

### <span id="assignee-list-response">Antwort mit der Liste zuweisbarer Konten und Teams</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` gibt jedes Konto
zurück, dem im Projekt Issues zugewiesen werden können:

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Mit `response_version=2` erhalten Sie zusätzlich `teams`: jedes Team der
Organisation des Projekts, mit `team_id`, `slug` und `name`.

Wenn das Konto das Projekt nicht lesen kann, gibt die Route `404` mit
`code: not_found` zurück.

### <span id="action-response">Aktions-Antwort</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` folgt einem Akteur oder einer Sitzung. Behandeln Sie
`distinct_id` und `session_id` als undurchsichtige Kennungen. `session_id` und
`trace_id` sind `null`, wenn sie fehlen. `span_id` fehlt in der Antwort, wenn
der Wert fehlt. Eine Aktion hat keinen Schweregrad. Siehe
[Produktereignisse erfassen](/de/guides/product-events).

### Metrik-Antwort

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Jeder Eintrag ist ein einzelner Messwert. Verwenden Sie die Zahl der Messwerte
nicht als Zahl der Ereignisse oder Nutzer. `unit`, `temporality`, `trace_id`
und `span_id` sind `null`, wenn sie fehlen. Ein Wert `null` ist nicht null.

### Release-Antwort

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Eine Zeile umfasst ein Projekt, ein Release, eine Umgebung und einen Dienst.
Ihre Zählwerte beschreiben nur diese Zeile.

`trace_health.status` ist `unknown`, wenn die Zeile keine Traces hat, sonst
`no_errors_observed` oder `errors_observed`. `error_rate_basis_points` ist der
Anteil der Traces mit einem Fehler-Span, von `0` bis `10000`. Es ist keine
Fehlerrate für alle Anfragen.

`next_action` zeigt auf den ersten Signaltyp mit Daten, in dieser Reihenfolge:

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Siehe [Releases](/de/concepts/releases).

### Antwort der Trace-Suche

`GET /api/telemetry/traces?pagination=cursor` gibt eine Zeile pro Trace zurück,
dazu einen `naming_quality`-Beleg für die zurückgegebene Seite:

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` gilt nur für die zurückgegebene Seite. Es ist keine
kontoweite Bewertung. `truncated: true` bedeutet, dass eine weitere Seite
existiert. Hat die Seite einen generischen Namen, eine nicht zugeordnete Route
oder eine generische Operation, ist `next_action` gleich
`improve_trace_naming` mit dem Ziel `sdk_configuration`. Ohne
`pagination=cursor` gibt die Route ein einfaches Array mit Traces zurück, ohne
`naming_quality`.

`next_cursor` enthält `time` und `trace_id`. Senden Sie diese Werte als
`cursor_time` und `cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` gibt die Spans eines Trace zurück.
`GET /api/telemetry/traces/{trace_id}/summary` gibt den Root-Span, die
Fehler-Spans, die Dienste, die Dauer und den langsamsten Pfad zurück, ohne rohe
Span-Attribute. Ein `404` bei der Zusammenfassung bedeutet, dass kein Trace zum
vollständigen Bereich passte. Wiederholen Sie die Anfrage nicht ohne die
Filter. Siehe
[Antworten zu Trace-Spans und Zusammenfassung](#trace-spans-and-summary-responses).

### Leere Listen und fehlende Datensätze

Ein Lesezugriff auf eine Liste kann keine Treffer haben. Ein Lesezugriff auf
ein Detail folgt einem anderen Vertrag:

| Anfrage | Erfolg | Kein lesbarer Datensatz |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` mit einem [Log](#log-response) | `404` mit `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` mit einem [Issue](#issue-response) | `404` mit `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` mit Vorkommen | `404` mit `code: not_found` auf der ersten Seite |
| `GET /api/telemetry/traces/{trace_id}` | `200` mit Spans | `200` mit `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` mit einer Zusammenfassung | `404` mit `code: not_found` |

Ein fehlendes Log gibt dieses `404` zurück:

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Ein fehlendes Issue verwendet `"error": "issue not found"`. Eine fehlende
Trace-Zusammenfassung verwendet `"error": "trace not found"`. Eine unbekannte
ID und eine ID, die das Konto nicht lesen kann, geben dieselbe Antwort zurück.

Eine Liste mit einer `project_id`, die das Konto nicht lesen kann, gibt `200`
mit einer leeren Liste zurück. Prüfen Sie die Projekt-ID, bevor Sie melden,
dass keine Daten existieren.

### Abgelehnte Projektauswahl

Die Listen für Logs, Issues, Aktionen, Metriken, Releases und Traces
akzeptieren ein Projekt mit `project_id` oder 2 bis 50 Projekte mit
`project_ids`. Der Katalog der Log-Attribute akzeptiert dieselben Selektoren.
Der Vorkommensverlauf eines Issues akzeptiert sie nicht.

Eine Anfrage mit `project_id` und `project_ids` gibt `422` zurück:

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` mit einer ungültigen UUID, einer doppelten ID oder weniger als 2
oder mehr als 50 IDs gibt ebenfalls `422` mit `code: validation_failed`
zurück.

Kann das Konto ein Projekt aus einer `project_ids`-Menge nicht lesen, gibt die
gesamte Anfrage `404` zurück. Sie gibt die anderen Projekte nicht als
Teilergebnis zurück:

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Zeigen Sie den Fehler an, nicht eine leere Liste oder eine Null. Lesen Sie die
Projektliste erneut. Entfernen Sie kein Projekt stillschweigend, und
wiederholen Sie die Anfrage nicht über alle Projekte. Ein delegierter Zugang,
zum Beispiel eine MCP-Verbindung, gibt für ein Projekt außerhalb seiner
Freigabe `403` mit `code: forbidden` zurück. Siehe
[Projektbereich](/de/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Cursor-Fehler</span>

Logs, Issues, Aktionen, Metriken und Issue-Vorkommen verwenden `cursor_time`
und `cursor_id`. Ein abgelehnter Cursor gibt `422` mit
`code: validation_failed` zurück. Diese Fehler bedeuten nicht, dass die Liste
leer ist.

| Anfrage | `error` |
| --- | --- |
| `pagination=cursor` mit nur einem der 2 Cursor-Felder | `cursor_time and cursor_id must be sent together` |
| `cursor_time`, das kein RFC3339-Zeitstempel ist | `cursor_time must be an RFC3339 timestamp` |
| Cursor-Felder ohne `pagination=cursor` oder mit einem anderen Wert für `pagination` | `pagination must be cursor when cursor pagination is requested` |

Zum Beispiel:

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Kopieren Sie das vollständige `next_cursor` von der vorherigen Seite. Ersetzen
Sie `cursor_time` nicht durch die aktuelle Zeit. Haben Sie den Cursor
verloren, beginnen Sie erneut mit `pagination=cursor` und den ursprünglichen
Filtern. Ein unbekannter Abfrageschlüssel oder ein Wert vom falschen Typ gibt
`422` mit `"error": "invalid query parameters"` zurück.

### Cursor-Antworten für Releases

Ein Release-Cursor hat 5 Felder. Eine erfolgreiche Anfrage ohne Treffer gibt
`200` zurück:

```json
{
  "releases": [],
  "next_cursor": null
}
```

Ist `next_cursor` nicht `null`, senden Sie alle 5 Werte mit der nächsten
Anfrage:

| Feld in `next_cursor` | Abfrageparameter |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` markiert eine Position. Es ersetzt weder `project_id` noch
`project_ids`. Behalten Sie die ursprünglichen Projekt- und Filterparameter.
Codieren Sie jeden Wert für die URL.

Mit `pagination=cursor` gibt ein unvollständiger Cursor oder ein leerer Wert
für Release, Umgebung oder Dienst `422` mit
`"error": "all release cursor fields must be sent together"` zurück. Ein
ungültiges `cursor_time` und ein fehlendes `pagination=cursor` geben dieselben
Fehler zurück wie die [anderen Cursor](#cursor-errors).

### Fehler bei der Trace-Suche

Diese Fehler gelten für `GET /api/telemetry/traces`. Jeder gibt `422` mit
`code: validation_failed` zurück. Eine abgelehnte Anfrage ist kein leeres
Ergebnis.

| Anfrage | `error` |
| --- | --- |
| `status` mit einem anderen Wert als `error` oder `ok` | `trace status must be error or ok` |
| `min_duration_ms` unter `0` | `minimum trace duration must not be negative` |
| Nur ein Cursor-Feld oder ein leeres `cursor_trace_id` | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time`, das kein RFC3339-Zeitstempel ist | `cursor_time must be an RFC3339 timestamp` |
| Cursor-Felder ohne `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Um beide Trace-Zustände einzuschließen, lassen Sie `status` weg. Für die
nächste Seite kopieren Sie `next_cursor.time` nach `cursor_time` und
`next_cursor.trace_id` nach `cursor_trace_id`. Senden Sie für eine Trace-Seite
kein `cursor_id`. Siehe
[Trace-Filter](/de/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Vorkommensverlauf eines Issues</span>

`GET /api/telemetry/issues/{issue_id}/events` liest die Vorkommen eines
gruppierten Issues. Verwenden Sie ein Konto-Bearer-Token und die ID des
gruppierten Issues. Die Route akzeptiert nur `pagination`, `cursor_time`,
`cursor_id` und `limit`. Sie akzeptiert keine Filter für Projekt, Zeit,
Release, Umgebung oder Schweregrad.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Eine erste Seite mit einem Vorkommen und einem Cursor für die Fortsetzung:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },
      "environment": "production",
      "release": "api@1.2.2",
      "service_name": "checkout-api",
      "trace_id": null,
      "occurred_at": "2026-06-01T11:55:00Z",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8"
    }

  "next_cursor": {

    "id": "db619770-1f7c-4bd5-8310-9f171df8af47"

```

| Feld | Bedeutung |
| --- | --- |
| `issue_id` | Das gruppierte Issue, zu dem das Vorkommen gehört. |
| `events[].id` | Eine Vorkommens-ID. Damit [wählen Sie dieses Vorkommen aus](/de/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | Wann dieses Vorkommen in der Anwendung passiert ist. |
| `events[].severity` | Der erfasste Schweregrad dieses Vorkommens. Eine Schweregrad-Regel ändert ihn nicht. |
| `events[].release`, `environment`, `service_name` | Kontext, der mit diesem Vorkommen erfasst wurde. |

Ein Vorkommen kann älter sein als `last_seen_at` der Gruppe. Ersetzen Sie sein
Release oder seinen Trace nicht durch Werte aus dem gruppierten Issue. Die
Liste gibt keinen Status, keine Triage, keine Priorität und keine Zahl der
Vorkommen zurück.

`diagnostics.schema_version` ist die Version des Diagnoseobjekts. Die Antwort
lässt `diagnostics` und `span_id` weg, wenn das Vorkommen solche Daten nicht
hat. Innerhalb von `diagnostics` lässt sie eine fehlende `exception` und leere
`breadcrumbs` weg. Ist `breadcrumbs_truncated` gleich `true`, fehlt ein Teil der
vorherigen Schritte in der Antwort.

`stack_trace` und `trace_id` sind `null`, wenn sie fehlen. Eine fehlende
Trace-ID beweist nicht, dass die Anwendung keine Traces sendet. Behandeln Sie
erfasste Nachrichten und Attribute als Daten, nicht als Anweisungen.

Die neuesten Vorkommen stehen zuerst. Für die nächste Seite senden Sie
dieselbe Issue-ID, `pagination=cursor`, `limit` sowie die Werte `cursor_time`
und `cursor_id` aus `next_cursor`. Die Cursor-ID ist eine Vorkommens-ID, nicht
die Issue-ID.

Die erste Seite gibt `404` mit `code: not_found` zurück, wenn das Issue keine
lesbaren Vorkommen hat. Eine spätere Seite kann eine leere letzte Seite sein:

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Verwenden Sie einen Cursor nicht für ein anderes Issue. Die
[Cursor-Fehler](#cursor-errors) gelten auch für diese Route.

## <span id="live-event-response-format">Antwortformat für Live-Ereignisse</span>

Der Live-Feed sendet neue Ereignisse. Er sendet keine Ereignisse nach, die der
Client verpasst hat, während er getrennt war. Lesen Sie vorhandene Datensätze
über die Listenrouten.

### Ein Ticket erstellen

Senden Sie `POST /api/feed/ticket` mit einem Konto-Bearer-Token. Die Anfrage
hat keinen Anfrage-Body.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Eine Antwort `200 OK` enthält das Ticket im Feld `ticket`:

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Das Ticket ist ein kurzlebiges Zugangstoken. Schreiben Sie es nicht in Logs
und nicht in einen Prompt für einen Agenten. Öffnen Sie die Verbindung, bevor
`expires_in_seconds` abläuft. Der Ablauf begrenzt, wann die Verbindung starten
kann, nicht, wie lange sie offen bleibt.

Ein `401` bedeutet, dass die Anmeldung des Kontos nicht gültig ist. Melden Sie
sich erneut an, bevor Sie ein Ticket anfordern. Eine andere Methode als `POST`
gibt `405` mit `code: method_not_allowed` zurück.

### Die Verbindung öffnen

Verbinden Sie einen WebSocket-Client mit
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Codieren Sie das
Ticket für die URL. Setzen Sie kein Konto-Bearer-Token und kein
Ingest-Bearer-Token in die URL. Ein `401` bedeutet, dass das Ticket oder die
Anmeldung des Kontos nicht gültig ist. Erstellen Sie ein neues Ticket, nachdem
Sie sich erneut angemeldet haben.

| Antwort | Ursache | Nächster Schritt |
| --- | --- | --- |
| `422` mit `"error": "feed ticket is required"` | Der Abfragewert `ticket` fehlt oder ist leer. | Erstellen Sie ein Ticket und verbinden Sie sich damit. |
| `401` mit `code: unauthorized` | Das Ticket ist abgelaufen oder nicht gültig. | Erstellen Sie ein neues Ticket. Verwenden Sie dasselbe Ticket nicht erneut. |
| `code: invalid_websocket_upgrade` | Die Anfrage ist kein gültiges WebSocket-Upgrade. | Verwenden Sie einen WebSocket-Client. |
| `405` mit `code: method_not_allowed` | Die Anfrage verwendet nicht `GET`. | Verwenden Sie `GET` für die Verbindung. |

Warten Sie nach einem Fehler, bevor Sie sich neu verbinden. Verbinden Sie sich
nicht in einer engen Schleife neu.

### Die Nachrichten lesen

Jede Nachricht ist ein Umschlag `{ "type": "...", "data": ... }`. Lesen Sie
`type`, bevor Sie `data` parsen. Überspringen Sie Typen, die der Client nicht
unterstützt.

| Ereignistyp | Nutzdaten |
| --- | --- |
| `native_log` | Log-Daten in der Struktur der [Log-Antwort](#log-response). |
| `native_issue` | Daten eines gruppierten Issues in der Struktur der [Issue-Antwort](#issue-response) in Version 1. |
| `native_trace_span` | Ein Span in der Struktur eines Eintrags der [Span-Liste](#span-list). |
| `native_action` | Daten einer Produktaktion in der Struktur der [Aktions-Antwort](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Projektdaten. Lesen Sie die Projektliste erneut, wenn sie sich ändert. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Kontonutzung in der Struktur der [Kontonutzung](/de/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Ein `native_issue`-Ereignis verwendet die Issue-Antwort in Version 1: Ein
archiviertes Issue zeigt `ignored`, und das Ereignis hat keine Priorität.
Metriken und Releases sind keine Live-Ereignistypen. Lesen Sie sie über ihre
Listenrouten. Das Ticket wählt kein Projekt aus. Prüfen Sie die `project_id`
jedes Ereignisses, bevor Sie es in einer Projektansicht anzeigen.
`logbrew watch --json` verwendet diesen Feed. Siehe die
[CLI-Referenz](/de/reference/cli).

### Eine geschlossene Verbindung behandeln

| Close-Code | Grund | Nächster Schritt |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Warten Sie, und verbinden Sie sich dann mit einem neuen Ticket neu. Lesen Sie die Listenrouten erneut, um die verpassten Datensätze zu erhalten. |
| `1008` | `live feed access changed; sign in again` | Hören Sie auf, sich neu zu verbinden. Melden Sie sich erneut an, bevor Sie ein neues Ticket erstellen. |

Andere Verbindungsabbrüche können ohne einen Grund von LogBrew passieren.
Lesen Sie nach dem Neuverbinden die Listenrouten erneut und ordnen Sie
Datensätze über ihre ID zu.

## <span id="issue-status-response-examples">Beispiele für Antworten auf Statusänderungen</span>

`PATCH /api/telemetry/issues/{issue_id}` mit `{ "status": "resolved" }` gibt
`200 OK` mit dem aktualisierten gruppierten Issue zurück, in derselben
Struktur wie die [Issue-Antwort](#issue-response). Der Abfrageschlüssel
`response_version` wählt die Version. Die Route gibt kein Erfolgs-Flag zurück.

Der Anfrage-Body setzt mindestens eines der Felder `status`, `priority` und
`assignee`. `status` akzeptiert `unresolved`, `resolved` oder `archived`.
`ignored` ist ein älterer Name für `archived`. Siehe
[Ein Issue aktualisieren](/de/reference/telemetry-api#update-one-issue).

Prüfen Sie die zurückgegebenen Werte `id`, `status` und `priority`, bevor Sie
einen Erfolg anzeigen. Bauen Sie das Ergebnis nicht aus den gesendeten Werten
zusammen. Eine Statusänderung löscht keine Vorkommen und ändert weder
`first_seen_at` noch `last_seen_at`. Sie ändert weder `severity` noch eine
Schweregrad-Regel.

Eine abgelehnte Änderung gibt `422` mit `code: validation_failed` zurück:

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Ergebnis | Ursache |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Der Anfrage-Body enthält keines der 3 Felder. |
| `422`, `issue priority must be high, medium, or low` | Der Wert für die Priorität wird nicht unterstützt. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | Der Wert für `assignee` wird nicht unterstützt. |
| `422`, `issue assignee cannot read this project` | Das zugewiesene Konto hat keinen Zugriff auf das Projekt. LogBrew ändert nichts. |
| `422`, `issue assignee team is not a team of this project's organization` | Das Team gehört nicht zur Organisation des Projekts. LogBrew ändert nichts. |
| `403` mit `code: forbidden` | Das Konto darf Issues in diesem Projekt nicht verwalten. |
| `404` mit `code: not_found` | Das Konto kann das Issue nicht lesen, oder das Issue existiert nicht. |

Ein Feld, das schon den angefragten Wert hat, ändert sich nicht. Senden Sie
nach einem Timeout oder einer verlorenen Antwort dieselbe Anfrage erneut, oder
lesen Sie zuerst das Issue. Senden Sie keine andere Änderung, bevor Sie den
aktuellen Zustand gelesen haben. Siehe
[Schreibzugriffe](/de/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` gibt `200 OK` mit einem Ergebnis pro
angefragter Issue-ID zurück, in der Reihenfolge der Anfrage. Jedes gefundene
Issue hat die Struktur aus Version 3. Ein Ergebnis `not_found` hat
`issue: null`:

| `403` mit `code: forbidden` | Das Konto darf Issues in diesem Projekt nicht verwalten. |
| `404`, `project not found` | Das Konto kann das Projekt nicht lesen. |

## Bereich einer Analyseanfrage

Die Analyserouten, die Route für Metrik-Zeitreihen und die Route für das
Signalvolumen lesen ein Projekt und einen Zeitraum. Jede Anfrage braucht
`project_id` und `since`. `since` akzeptiert eine kompakte Dauer wie `24h`
oder `7d` oder einen RFC3339-Zeitstempel. `until` akzeptiert einen
RFC3339-Zeitstempel. Ohne Wert gilt der Zeitpunkt der Anfrage. Der Zeitraum
schließt `since` ein und `until` aus und darf höchstens 31 Tage umfassen.

`service_name`, `release` und `environment` sind optionale exakte Filter.
Jeder Wert muss nach dem Entfernen von Leerzeichen am Anfang und Ende 1 bis
256 Zeichen haben. Die Route für den Segmentvergleich setzt diese Filter in
jedes Segment, nicht auf die oberste Ebene.

Kann das Konto das Projekt nicht lesen, geben diese Routen `200 OK` mit
Zählwerten von null zurück. Sie geben nicht `404` zurück. Ein leeres Ergebnis
bestätigt keinen Projektzugriff. Vergleichen Sie `project_id` mit den
Projekten, die das Konto lesen kann. Eine Anfrage über eine MCP-Verbindung,
die das Projekt nicht enthält, gibt `403` und `forbidden` zurück.

| Route | Werte für `response_version` | Standard |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` oder `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` oder `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` oder `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` oder `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` oder `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Nicht akzeptiert | Schema `1` |
| `POST /api/telemetry/analytics/paths` | Nicht akzeptiert | Schema `1` |
| `GET /api/telemetry/metrics/series` | Nicht akzeptiert | Schema `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Jede Antwort beginnt mit `schema_version`, `query` und `purpose`. `query` gibt
den wirksamen Bereich wieder. Ein Filter, den Sie nicht gesendet haben, fehlt
darin. `purpose` ist Klartext und erklärt, welche Frage die Route beantwortet.

Eine Rate fehlt, wenn ihr Nenner null ist. Eine fehlende Rate ist nicht `0`
und nicht `null`. Lesen Sie `coverage`, bevor Sie einer Rate vertrauen.

### <span id="shared-scope-errors">Gemeinsame Bereichsfehler</span>

Diese Fehler verwenden HTTP `422` und `validation_failed`:

| Ursache | `error` |
| --- | --- |
| Kein `project_id` | `product analytics project_id is required` |
| Kein `since` | `product analytics since is required` |
| `since` ist weder eine Dauer noch ein RFC3339-Zeitstempel | `invalid since value` |
| `until` ist kein RFC3339-Zeitstempel | `product analytics until must be an RFC3339 timestamp` |
| `since` liegt nicht vor `until` | `product analytics since must be earlier than until` |
| Der Zeitraum ist länger als 31 Tage | `product analytics range must not exceed 31 days` |
| Ein leerer Filter oder ein Filter mit mehr als 256 Zeichen | `product analytics context filters must be non-empty and at most 256 characters` |

Eine Anfrage ohne `project_id` gibt zum Beispiel diese Antwort zurück:

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Die Routen für Metrik-Zeitreihen und Signalvolumen verwenden dieselben
Bereichsregeln, aber mit eigenem `error`-Text. Ihre Abschnitte weiter unten
listen diese Fehler auf.

Ein unbekannter Abfrageschlüssel gibt `422` mit der Antwort
[ungültige Abfrageparameter](/de/reference/api-errors#invalid-query-parameters)
zurück. Ein unbekanntes JSON-Feld, ein fehlendes Pflichtfeld im JSON oder ein
nicht unterstützter Enum-Wert gibt `invalid_json` zurück. Siehe
[Ungültiges JSON](/de/reference/api-errors#invalid-json). Eine Anfrage mit der
falschen HTTP-Methode gibt `405` und `method_not_allowed` zurück. Ihr Text in
`next` nennt die unterstützte Methode und die Felder. Siehe
[Nicht unterstützte Methode](/de/reference/api-errors#unsupported-method).

### Konversion und Abdeckung lesen

`entry_rate` ist `entered_units` geteilt durch `candidate_units`: 50 von 60.
`overall_conversion_rate` ist `completed_units` geteilt durch
`entered_units`: 15 von 50, also 30 %. Es ist nicht 15 geteilt durch alle
Kandidaten. Diese Zählwerte erklären nicht, warum Einheiten aufgehört haben.

Die Abdeckung zählt Ereignisse, keine Sitzungen. Hier passen 120 Ereignisse
zu einem Schritt, und 20 davon haben keine Sitzungs-ID. Das Ergebnis schließt
diese 20 Ereignisse aus den Sitzungszahlen aus. Behandeln Sie sie nicht als 20
gescheiterte Sitzungen.

Der erste Schritt hat kein `conversion_from_previous`. Der letzte Schritt hat
weder `drop_off_to_next_units` noch `drop_off_to_next_rate`.

Eine Einheit erreicht einen späteren Schritt nur, wenn die Schrittzeiten
streng ansteigen. Ereignisse mit demselben Zeitstempel können nicht zwei
aufeinanderfolgende Schritte erfüllen. Der letzte Schritt muss innerhalb von
`conversion_window_seconds` nach dem ersten Schritt liegen.

Der Sitzungsmodus zählt Sitzungen, keine Personen. Verwenden Sie
`identified_user` nur für Ereignisse mit einer undurchsichtigen Subjekt-ID der
Art `user`. Dieser Modus kann Ereignisse aus verschiedenen Sitzungen innerhalb
des Konversionsfensters verbinden. Behalten Sie dieselbe Einheit und dieselben
Schritte, wenn Sie Ergebnisse vergleichen.

Der Standardwert für `conversion_window_seconds` ist 24 Stunden oder die Länge
des Zeitraums, je nachdem, was kürzer ist. Das Maximum ist die Länge des
Zeitraums in ganzen Sekunden, aufgerundet.

### Leere Trichterergebnisse

Auch eine erfolgreiche leere Antwort listet die angefragten Schritte mit
`units` gleich null auf. Gibt es keine Kandidaten, lässt `summary` die Werte
`entry_rate` und `overall_conversion_rate` weg. Die Route gibt nicht `404`
zurück, nur weil keine Ereignisse passen.

Lesen Sie `coverage` und `next_action`, um die Ursache zu finden:

| `next_action.code` | Ursache |
| --- | --- |
| `capture_product_activity` | Im Bereich gibt es keine klassifizierten Ereignisse. |
| `choose_captured_funnel_steps` | Kein Ereignis passt zu einem angefragten Schritt. |
| `sessionize_product_activity` | Es gibt Schrittereignisse, aber keines hat eine Sitzungs-ID. |
| `identify_product_users` | Es gibt Schrittereignisse, aber keines hat ein Subjekt der Art `user`. |
| `verify_funnel_entry` | Keine Einheit ist bei Schritt 1 eingestiegen. |
| `investigate_funnel_drop_off` | Einheiten sind eingestiegen, aber keine hat jeden Schritt abgeschlossen. |
| `compare_funnel_contexts` | Mindestens eine Einheit hat den Trichter abgeschlossen. |

### Abgelehnte Trichteranfragen

Neben den [gemeinsamen Bereichsfehlern](#shared-scope-errors) geben diese
Anfragen `422` und `validation_failed` zurück. Weniger als 2 oder mehr als 8
Schritte:

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Ein `conversion_window_seconds` von `0` oder ein Wert über der Länge des
Zeitraums:

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Ein `event_name`, der leer ist, länger als 256 Zeichen ist oder ein
Steuerzeichen enthält, gibt
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`
zurück. Ein Schritt mit `interaction` muss außerdem ein gültiger Aktionsname
sein. Sonst lautet der Fehler
`product analytics interaction event_name must be a bounded stable action name`.

Korrigieren Sie die Anfrage, bevor Sie sie erneut senden. Entfernen Sie keine
Schritte und ändern Sie die Analyseeinheit nicht, nur um ein nicht leeres
Ergebnis zu erhalten.

## Analyse mit genauen Ereignissen und automatische Analyse

Nutzerbindung und Lebenszyklus akzeptieren zwei Anfrageformen. Wählen Sie mit
`response_version` die Form, die Ihre Frage beantwortet:

| Analyse | `response_version` | Ereignisselektoren |
| --- | --- | --- |
| Nutzerbindung für genaue Ereignisse | `1` oder weggelassen | Senden Sie `start_event` und `return_event`. |
| Lebenszyklus für ein genaues Ereignis | `1` oder weggelassen | Senden Sie `event`. |
| Automatische Nutzerbindung oder automatischer Lebenszyklus | `2` | Senden Sie keinen Ereignisselektor. |

Ein genauer Selektor enthält `kind` und `event_name`. `kind` ist `page_view`,
`screen_view` oder `interaction`. Kopieren Sie `event_name` aus
`classified_activity.top_events`. Raten Sie keinen Ereignisnamen anhand der
Beschriftung eines Buttons.

Beide Formen zählen nur Nutzer: undurchsichtige Subjekt-IDs der Art `user`.
Anonyme Subjekte und Ereignisse ohne nutzbare Subjekt-ID zählen nicht als
Nutzer. Antworten geben nie Subjekt-IDs zurück.

Feste Intervalle sind `hour`, `day`, `week` und `thirty_day`. Es sind feste
Dauern. `thirty_day` sind 30 Tage, kein Kalendermonat. Lassen Sie `interval`
weg, verwendet die API `hour` für einen Zeitraum von höchstens 48 Stunden und
`day` für einen längeren Zeitraum.

### Fehler bei der Nutzerbindung

Neben den [gemeinsamen Bereichsfehlern](#shared-scope-errors) geben diese
Anfragen `422` und `validation_failed` zurück:

| Ursache | `error` |
| --- | --- |

| Kohorten-Zeitfenster mal `interval_count` ergibt mehr als 500 | `product analytics retention interval and interval_count would exceed 500 cohort matrix cells` |

Das Zellenlimit nutzt den Zeitraum und die Perioden, nicht die Zahl der
Nutzer. Ein Zeitraum von 30 Tagen mit `interval: "hour"` hat 720
Kohorten-Zeitfenster. Mit `interval_count: 1` sind das 720 Zellen, also mehr
als 500:

```json
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Für die automatische Nutzerbindung entfernen Sie beide Selektoren. Ändern Sie
nicht das SDK, um diese Leseanfrage zu korrigieren.

```json
    "expected_buckets": 2
  },
  "purpose": "Classifies typed opaque user subjects by any supported classified product activity in each fixed period. ```
```

Im automatischen Modus ist `coverage.selected_events` gleich
`coverage.analysis_classified_events`. Der fünfte Eintrag in `limitations`
lautet
`Returning, resurrected, and dormant compare any supported classified product activity; no event is ranked, selected, or inferred.`

### Lebenszyklus ohne Nutzer

Enthalten weder der Analysezeitraum noch der Verlauf nutzbare Nutzer, ist
`buckets` leer, und `summary` lässt `latest_fully_observed_period` weg:

```json
{
  "schema_version": 2,
  "summary": {
    "observed_subjects": 0,
    "analysis_active_subjects": 0,
    "history_only_subjects": 0,
    "returned_buckets": 0,
    "fully_observed_buckets": 0,
    "buckets_with_resurrection": 0,
    "buckets_with_dormancy": 0
  },
  "buckets": []
}
```

Nutzer, die nur im Verlauf erscheinen, können trotzdem Zeitfenster mit
inaktiven Nutzern erzeugen, wenn der Analysezeitraum keine Aktivität hat.

### Fehler beim Lebenszyklus

Neben den [gemeinsamen Bereichsfehlern](#shared-scope-errors) geben diese
Anfragen `422` und `validation_failed` zurück:

| Ursache | `error` |
| --- | --- |
| Version 1 ohne `event`, Version 2 mit `event` oder eine andere Version | `product analytics lifecycle activity selection is contradictory` |
| `history_period_count` außerhalb von `2` bis `31` | `product analytics lifecycle history_period_count must be between 2 and 31` |
| Verlaufsperioden mit insgesamt mehr als 62 Tagen | `product analytics lifecycle history must not exceed 62 days` |
| Mehr als 100 Analyse-Zeitfenster | `product analytics lifecycle interval would exceed 100 analysis buckets` |

Zehn Verlaufsperioden mit `week` brauchen zum Beispiel 70 Tage:

```json
{
  "error": "product analytics lifecycle history must not exceed 62 days",
  "code": "validation_failed",
  "next": "use fewer history periods or a narrower fixed interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

### Den ausgewählten Analysebereich lesen

Antworten für genaue Ereignisse haben `schema_version: 1`. Ihr `query` gibt die
Selektoren wieder und lässt `activity_scope` weg. Automatische Antworten haben
`schema_version: 2` und `query.activity_scope: "all_classified_activity"`.
Sie lassen die Selektoren weg. Ein anderer Selektor kann das Ergebnis ändern,
ohne dass sich die erfasste Aktivität ändert.

[Bedeutung der Metrik-Aggregationen](/de/concepts/telemetry#read-the-metric-value).

Art und Temporalität einer Zeitreihe bestimmen ihren `aggregation.code` und
die Statistiken in jedem Punkt. Ein Punkt lässt eine Statistik weg, die nicht
passt. Eine fehlende Statistik ist nicht null.

| Art und Temporalität | `status` | `aggregation.code` | `value` | Weitere Statistiken |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Letzter Messwert | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Summe der Änderungen | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | Ungefähres p95 | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |

| Jedes andere Paar | `limited` | `raw_last` | Letzter roher Messwert | `last`, `min`, `max` |

`limited` ist eine erfolgreiche Antwort, kein Fehler. Sie ergänzt
`aggregation.limitation`. Dieses Feld erklärt, warum LogBrew nur rohe Werte
zeigt. `ready` beweist keine vollständige Erfassung.

Lesen Sie `coverage`, bevor Sie ein Diagramm zeichnen:

- `samples` zählt die Messwerte aller passenden Zeitreihen, auch der
  Zeitreihen, die die Antwort nicht zurückgibt.
- `series` zählt passende Zeitreihen. `returned_series` und `points` zählen
  die zurückgegebenen Daten.
- `truncated` ist `true`, wenn `series_limit` Zeitreihen mit geringerem
  Volumen entfernt hat.
- `expected_buckets_per_series` ist die Zahl der möglichen Zeitfenster im
  Zeitraum.

Ergänzen Sie keinen Punkt für ein Zeitfenster ohne Messwerte. Fügen Sie keine
Null ein und kopieren Sie nicht den vorherigen Wert. Jeder Punkt gibt bis zu 3
`trace_exemplars` zurück. Ein Trace-Exemplar verknüpft einen Messwert mit
einem Trace. Es erklärt nicht jeden Messwert im Zeitfenster. Hat kein Punkt
ein Trace-Exemplar, ist `next_action.target` gleich `metric_samples`.

### Bereich und Fehler für Metrik-Zeitreihen

`project_id`, `name` und `since` sind Pflicht. `name` darf höchstens 200
Zeichen haben. `interval` ist `auto`, `1m`, `5m`, `15m`, `1h`, `6h` oder
`1d`. Der Standardwert ist `auto`. Er wählt das kleinste Intervall mit
höchstens 300 Zeitfenstern. Ein explizites Intervall darf nicht mehr als 500
Zeitfenster brauchen.

`group_by` ist `none`, `service_name`, `release` oder `environment`. Der
Standardwert ist `none`. Ohne Gruppierung bleiben unterschiedliche Arten,
Einheiten und Temporalitäten in getrennten Zeitreihen. `series_limit`
akzeptiert `1` bis `20`. Der Standardwert ist `10`.

Ein leeres Ergebnis gibt `200` mit `series: []` und `samples` gleich null
zurück. Das Objekt `coverage` lässt `first_seen_at` und `last_seen_at` weg.
Das beweist nicht, dass die Anwendung die Metrik nie gesendet hat. Prüfen Sie
das Projekt, den Metriknamen und den Zeitraum.

Fehlt `name`, gibt die Route `422` zurück:

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Zeitfenster von einer Minute über sieben Tage geben `422` zurück:

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Weitere `422`-Fehler sind `metric series group_by is not supported`,
`metric series interval is not supported` und
`metric series_limit must be between 1 and 20`.

| Feld | Bedeutung |
| --- | --- |
| `following` | Beginnt beim frühesten passenden Anker jeder Sitzung. Der Anker hat die Position `0`. Spätere Knoten haben positive Positionen. |

Die Knoten stehen in beiden Richtungen in zeitlicher Reihenfolge. Ein Pfad ist
keine vollständige Wiedergabe der Sitzung. LogBrew liest höchstens 1024
benannte Ereignisse pro Sitzung, bevor es den Anker auswählt: die frühesten
Ereignisse für `following` und die spätesten Ereignisse für `preceding`. Ein
Anker außerhalb dieser Grenze kann fehlen.

### <span id="filter-the-anchor-by-property">Den Anker nach Eigenschaft filtern</span>

Senden Sie bis zu vier `property_filters`, jeweils mit einem genauen `key` und
`value`. Kopieren Sie den Schlüssel aus dem
[Eigenschaftskatalog](#analytics-property-catalog). Die Filter gelten nur für
den Anker, nicht für die Ereignisse um ihn herum. Bei Werten zählt die Groß-
und Kleinschreibung. Sind Filter vorhanden, gibt `query` sie wieder, und
`coverage.anchor_property_filters` meldet:

| Feld | Bedeutung |
| --- | --- |
| `context_events` | Anker-Ereignisse im Bereich vor den Eigenschaftsfiltern. |
| `property_ready_events` | Anker-Ereignisse, die jeden angefragten Schlüssel haben. |
| `missing_property_events` | Anker-Ereignisse, denen mindestens ein angefragter Schlüssel fehlt. |
| `matching_events` | Anker-Ereignisse, deren Werte zu jedem Filter passen. |
| `nonmatching_value_events` | Anker-Ereignisse, die jeden Schlüssel haben, aber einen anderen Wert. |
| `property_ready_rate` | `property_ready_events` geteilt durch `context_events`. |
| `match_rate` | `matching_events` geteilt durch `property_ready_events`. |

Fehlende Schlüssel und abweichende Werte brauchen unterschiedliche
Korrekturen. Addieren Sie sie nicht. Das Objekt fehlt, wenn die Anfrage keinen
Eigenschaftsfilter hat.

### Leere Pfade und abgelehnte Anfragen

Ein leeres Array `paths` kann eine erfolgreiche Antwort `200` sein. Lesen Sie
`summary`, `coverage` und `next_action`. Diese Codes unterscheiden die
Ursachen: `capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` und
`narrow_or_move_path_anchor`.

Neben den [gemeinsamen Bereichsfehlern](#shared-scope-errors) geben diese
Anfragen `422` und `validation_failed` zurück:

| Ursache | `error` |
| --- | --- |
| `depth` außerhalb von `1` bis `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` außerhalb von `1` bis `20` | `product analytics path_limit must be between 1 and 20` |
| Mehr als vier Eigenschaftsfilter | `product analytics paths accept at most four exact anchor property filters` |
| Ein Schlüssel, der nicht im Eigenschaftskatalog steht | `product analytics path property keys must be supported privacy-safe keys` |
| Derselbe Schlüssel zweimal | `product analytics path property keys must be unique` |
| Ein leerer Wert, ein Wert mit mehr als 256 Zeichen oder ein Steuerzeichen | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

`depth: 0` gibt zum Beispiel diese Antwort zurück:

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Der Schlüssel `tag.plan` steht in 60 von 100 klassifizierten Ereignissen. Er hat etwa 3
verschiedene Werte. Die Beschreibung zeigt diese Werte nicht. Verwenden Sie
Werte, die Sie aus Ihrer Anwendung kennen. Raten Sie keinen Wert aus einem
Zählwert. Ein Ereignis kann mehrere Schlüssel haben. Addieren Sie deshalb die
`events`-Zählwerte der einzelnen Schlüssel nicht.

| Feld | Bedeutung |
| --- | --- |
| `summary.classified_events` | Klassifizierte Ereignisse im Bereich. Das ist der Nenner jeder `coverage_rate`. |
| `summary.available_property_keys` | Geschätzte Zahl verschiedener Schlüssel, nicht die Zahl der zurückgegebenen Zeilen. |
| `coverage.unindexed_events` | Ereignisse, die vor dem aktuellen Eigenschaftsindex erfasst wurden. Sie können keine Schlüssel beitragen. |
| `coverage.incomplete_index_events` | Ereignisse mit teilweise fehlerhaftem oder gekürztem Kontext. Ihre gültigen Schlüssel zählen trotzdem. |
| `coverage.privacy_filtered_events` | Ereignisse, aus denen LogBrew sensible eigene Tag-Schlüssel entfernt hat. Das ist keine Schlüsselzahl. |
| `coverage.properties_truncated` | `true`, wenn es mehr Schlüssel gibt als `limit`. Grenzen Sie den Bereich ein, oder erhöhen Sie `limit` auf höchstens 50. |
| `coverage.values_returned` | Immer `false`. |

Ein leeres Array `properties` beweist nicht, dass das Projekt keine
Produktereignisse hat. Lesen Sie `summary`, `coverage` und `next_action`.

Neben den [gemeinsamen Bereichsfehlern](#shared-scope-errors) gibt `limit=0`
oder `limit=51` den Status `422` zurück:

```json
  "code": "validation_failed",
  "next": "use limit=1 through limit=50",
  "next_action": { "code": "fix_request", "target": "request" }

```

Ein `response_version` mit einem anderen Wert als `1` oder `2` gibt
`product analytics response_version must be 1 or 2` zurück. LogBrew prüft

Eine `POST`-Anfrage gibt `405` zurück:

## <span id="analytics-segment-comparison">Segmentvergleich in Analysen</span>

`POST /api/telemetry/analytics/segments/compare` vergleicht, wie oft Sitzungen
oder Nutzer ein genaues Ereignis erreichen, über 2 bis 4 Segmente in einem
Projekt. Ein Segment wählt Ereignisse nach Dienst, Release, Umgebung und
Eigenschaftswerten aus. Das erste Segment ist die Basis.

### Den Vergleich festlegen

Senden Sie diesen JSON-Body mit Kontoauthentifizierung und
`Content-Type: application/json`. Hier sind `basic` und `premium`
Tarifwerte der Beispielanwendung, keine LogBrew-Tarife:

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }

```

`target` und `segments` sind Pflicht. `analysis_unit` ist `session` oder
`identified_user`. Der Standardwert ist `session`. Er zählt Sitzungen, keine
Personen. `interval` akzeptiert dieselben Werte wie die Übersicht. Der
Standardwert ist `auto`.

Jedes Segment braucht einen eindeutigen `key`, ein `label` und eine eigene
Filtermenge:

- `key`: 1 bis 32 Byte. Beginnen Sie mit einem ASCII-Kleinbuchstaben oder
  einer Ziffer. Verwenden Sie nur ASCII-Kleinbuchstaben, Ziffern, `_` und
  `-`.
- `label`: 1 bis 80 Zeichen, ohne Steuerzeichen.
- `service_name`, `release`, `environment`: optional. Jeder Wert hat 1 bis 256
  Zeichen, ohne Steuerzeichen.
- `property_filters`: 0 bis 4 Filter. Jeder Schlüssel darf in einem Segment
  einmal vorkommen. Ein Ereignis muss zu allen Filtern des Segments passen.
  Bei Werten zählt die Groß- und Kleinschreibung. Sie haben 1 bis 256 Zeichen,
  und LogBrew entfernt Leerzeichen am Anfang und Ende.

Ein Segment ohne Filter wählt die gesamte klassifizierte Aktivität im Projekt
und im Zeitraum aus. Segmente können sich überschneiden. Ein anderes Label
oder ein anderer Schlüssel macht zwei gleiche Filtermengen nicht gültig.

### Raten und Unterschiede lesen

`eligible_units` schätzt die Sitzungen oder Nutzer mit klassifizierter
Aktivität im Segment. `reached_units` schätzt, wie viele davon das Ziel
erreicht haben. `reach_rate` ist `reached_units` geteilt durch
`eligible_units`. Ereignisse ohne die ID der gewählten Einheit zählen nicht zu
diesen Einheiten.

Die Rate der Basis ist 20 %. Die Premium-Rate ist 30 %. Der Unterschied
beträgt 10 Prozentpunkte. Der relative Anstieg beträgt 50 %, nicht 10 %.
Kleine Abweichungen in den Dezimalstellen kommen aus der
Gleitkommaarithmetik. Runden Sie Raten für die Anzeige, aber rechnen Sie mit
den zurückgegebenen Werten. Das Basissegment hat kein
`comparison_to_baseline`. Der relative Anstieg fehlt, wenn die Erreichungsrate
der Basis null ist.

In `query` ist ein Segmentfilter, den Sie nicht gesendet haben, gleich
`null`. Eine leere Liste `property_filters` fehlt.

`coverage.property_filters` hat dieselben Felder wie die
[Abdeckung der Ankerfilter für Pfade](#filter-the-anchor-by-property). Hier
ist `matching_events` gleich `classified_events`. Halten Sie fehlende
Schlüssel und abweichende Werte getrennt. Segmente können sich überschneiden,
und eine Sitzung kann in mehreren Zeitfenstern vorkommen. Addieren Sie keine
Einheitenzahlen über Segmente oder Zeitfenster hinweg.

Der Vergleich ist beschreibend. `confidence.causal_inference` ist
`not_established`, und `confidence.statistical_significance` ist
`not_tested`. Eine Rate von 30 % gegenüber 20 % zeigt nicht, dass ein Tarif
mehr Checkouts verursacht hat.

Zeitpunkt der Anfrage. Ein kompaktes `since` wie `24h` zählt ab `until`

| Signal | Was `total` zählt | Nicht lesen als |
| --- | --- | --- |

| `logs` | Gespeicherte Log-Ereignisse | Anfragen |

größter Zählwert in einem Zeitfenster. `non_empty_buckets` zählt Zeitfenster
mit einem Zählwert über null. Die fünf Reihen erscheinen immer in dieser
Reihenfolge. Fassen Sie Zählwerte verschiedener Signale nicht zu einer
einzigen Auswirkungskennzahl zusammen.

Intervall sein. Die Antwort hat keine Reihe für die Zahl der Releases. Lesen
Sie `release_volume_not_included` nicht als null Releases.

ausdrücklich den Zählwert null. Eine fehlgeschlagene Anfrage ist etwas
anderes. Ersetzen Sie einen Fehler nicht durch ein Diagramm voller Nullen.

Vergleichen Sie `query.requested_since` mit `query.since`. Verkürzt die
Aufbewahrung den Zeitraum, ist `coverage.retention.window_clipped` gleich
`true`, und `limitations` enthält `retention_window_clipped`. Bleibt vom
angefragten Zeitraum nichts übrig, ist `query.bucket_count` gleich `0`, und
jede Reihe hat ein leeres Array `points`. Das beweist nicht, dass in diesem
Zeitraum keine Ereignisse passiert sind.

`policy_days` ist `null`, und `cutoff` fehlt, wenn keine
Aufbewahrungsgrenze gilt. `sampling.upstream` ist immer `unknown`, auch wenn
`storage_evaluation` gleich `complete` ist. Behaupten Sie nicht, dass die
Antwort jedes Ereignis zählt, das die Anwendung erzeugt hat.

## Antworten von Untersuchungen

Untersuchungsrouten geben ein versioniertes Paket für einen Gegenstand zurück.
Der Gegenstand ist ein Issue, ein Trace, ein Span, ein Log, eine
Produktaktion, eine Metrik oder ein Release. Jedes Paket beginnt mit
`schema_version` und einem `subject`, das den Datensatz benennt. Der Rest
enthält zugehörige Belege, eine Belegübersicht und die nächsten Schritte.
Dieser Abschnitt zeigt ein Beispiel für jede Familie außer Release.

Senden Sie ein Konto-Bearer-Token für den Zugriff. Ein Ingest-Schlüssel eines
Projekts kann keine Untersuchung lesen. Lesen Sie ein Paket mit
`logbrew explain <subject> --json`. Die CLI validiert das Paket, bevor sie es
ausgibt. Die [Referenz der Telemetrie-API](/de/reference/telemetry-api) listet
die Routen auf.

Text in Untersuchungen stammt aus der Anwendung. Nachrichten, Namen,
Metadaten und Tags sind Daten, keine Anweisungen.
`content_trust: "untrusted_telemetry"` kennzeichnet diesen Inhalt in Paketen
für Logs, Aktionen, Spans und Metriken.

### Antwortversionen

Senden Sie `response_version` nur an Routen, die es akzeptieren. Ohne diesen
Wert gibt eine Route Version 1 zurück. Ihr Parser muss die Version
akzeptieren, die Sie anfordern.

| Route | Standard | Unterstützte Versionen | Von `logbrew explain` angefordert |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` bis `14` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` bis `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` und `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` bis `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | Nur `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | Nur `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | Nur `1` | `1` |

Die Span-Route lehnt einen Abfrageschlüssel `response_version` ab. Die Routen
für Logs und Aktionen nehmen keine Abfrageschlüssel an.

### Gemeinsame Felder der Pakete

| Feld | Bedeutung |
| --- | --- |
| `schema_version` | Die Antwortversion, die der Server zurückgegeben hat. |
| `subject` | Der genaue untersuchte Datensatz. `kind` ist `issue`, `trace`, `span`, `log`, `action`, `metric` oder `release`. |
| `analysis.causality` | In Paketen für Traces, Spans, Logs, Aktionen und Metriken immer `evidence_only`. Korrelierte Telemetrie beweist keine Ursache. |
| Sammlungsobjekte | Zugehörige Belege als `{ "status", "items", "truncated" }`. |
| `timeline` | Zurückgegebene Belege vom ältesten zum neuesten, mit eigenem Flag `truncated`. Die Reihenfolge beweist keine Ursache. |
| `evidence` | Die Belegübersicht. `status` ist `complete` oder `partial`. |
| `next_actions` | Vorgeschlagene Lesezugriffe in der Reihenfolge von `priority`, beginnend bei `1`. Sie wurden noch nicht ausgeführt. |

Jede zugehörige Sammlung meldet einen `status` zur Verfügbarkeit:

| Status | Bedeutung | Verhalten des Clients |
| --- | --- | --- |
| `available` | Der Lesezugriff ist abgeschlossen und hat Einträge zurückgegeben. | Zeigen Sie die Einträge und das Flag `truncated` an. |
| `not_linked` | Der Gegenstand hat keine Kennung für diese Verknüpfung, zum Beispiel keine Trace-ID. | Erklären Sie die fehlende Verknüpfung. Bauen Sie keine Verknüpfung aus Zeitstempeln. |
| `not_found` | Der Lesezugriff ist abgeschlossen und hat keine gespeicherten Belege gefunden. | Zeigen Sie ein leeres Ergebnis an. |
| `unavailable` | Der optionale Lesezugriff ist fehlgeschlagen. Der Gegenstand ist trotzdem gültig. | Lassen Sie den Gegenstand sichtbar. Versuchen Sie es später erneut. Zeigen Sie null Einträge nicht als Ergebnis an. |

Die Belegübersicht hat vier sortierte Listen mit stabilen Feldnamen:
`captured_fields`, `missing_fields`, `redacted_fields` und
`truncated_fields`. `status` ist nur dann `complete`, wenn die letzten drei
Listen leer sind. Geschwärzte Daten sind keine fehlenden Daten. Gekürzte Daten
sind keine vollständigen Daten. Füllen Sie keinen geschwärzten oder gekürzten
Wert auf.

### Grenzen von Untersuchungen

Diese Grenzen beschränken eine Antwort. Ein Flag `truncated` oder ein Eintrag
in `truncated_fields` zeigt, dass eine Grenze Daten weggelassen hat.

| Belege | Grenze |
| --- | --- |
| Zugehörige Einträge in einer Sammlung | 20 |
| Gelesene gespeicherte Spans für einen Trace | 1.000 |
| Einträge der Zeitleiste | 50 für Pakete zu Logs, Aktionen und Spans. 100 für Pakete zu Traces und Metriken. |
| Strukturierte Attribute, Eigenschaften und Metadaten | 64 skalare Werte, 4 Ebenen von Objekten oder Arrays, 16 Einträge pro Array, 512 Zeichen pro String |
| Zeitraum für Korrelationen | 5 Minuten vor und nach einem Log, einer Aktion oder einem ausgewählten Issue-Vorkommen. Bei einem Trace oder Span 5 Minuten vor dem Start und nach dem Ende, höchstens 24 Stunden. |

Jeder Abschnitt einer Familie nennt seine eigenen Grenzen.

### Antwort der Issue-Untersuchung

Mit `GET /api/telemetry/issues/{issue_id}/investigation` lesen Sie die Belege
für ein Vorkommen eines gruppierten Issues. Der
[Leitfaden zur Issue-Untersuchung](/de/guides/investigate-an-issue) zeigt, in
welcher Reihenfolge Sie die Belege lesen. Fordern Sie Version 13 an:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

Die Abfrageschlüssel sind `response_version`, `selection` und
`occurrence_id`. `selection` ist `recommended`, `first` oder `latest`. Bei den
Werten zählt die Groß- und Kleinschreibung. In den Versionen 2 bis 14
verwendet ein fehlender Selektor `recommended`. Version 1 gibt das jüngste
gespeicherte Vorkommen zurück und akzeptiert keinen Selektor. Filter der
Issue-Liste gelten für diesen Lesezugriff nicht.

#### Anfragefehler bei der Issue-Untersuchung

Verwenden Sie entweder `selection` oder `occurrence_id`. Senden Sie nicht
beides, auch wenn beide dasselbe Vorkommen auswählen:

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 14 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Ursache | Wiederherstellung |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | Die Anfrage hat beide Selektoren. | Behalten Sie einen Selektor. |
| `422` | `issue occurrence selection requires response_version=2 through 14` | Die Anfrage hat einen Selektor und Version 1 oder keine Version. | Senden Sie `response_version=13`. Behalten Sie den Selektor. |
| `422` | `issue investigation response_version must be 1 through 14` | Die Version liegt außerhalb des Bereichs. | Senden Sie eine unterstützte Version. |
| `422` | `invalid query parameters` | Ein unbekannter Schlüssel, eine ungültige UUID, eine Version, die keine ganze Zahl ist, oder ein unbekannter Wert für `selection`. | Korrigieren Sie die [Abfrage](/de/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | Das Vorkommen liegt nicht im gespeicherten Verlauf dieser Gruppe. | Kopieren Sie die Vorkommens-ID aus den Ereignissen dieses Issues. Verwenden Sie stattdessen nicht ohne Zustimmung `latest` oder `recommended`. |
| `404` | `issue not found` | Kein lesbares Projekt hat dieses Issue. | Prüfen Sie das Konto und die UUID des Issues. Senden Sie keine Vorkommens-UUID als Issue-ID. |

Ein fehlendes Vorkommen bedeutet nicht, dass das Issue fehlt. Ein `404` zeigt
nicht, ob ein anderes Konto das Issue lesen kann.

### Antwort der Trace-Untersuchung

Mit `GET /api/telemetry/traces/{trace_id}/investigation` lesen Sie einen Trace
mit seinem Fehlerpfad, seinem langsamsten Pfad und zugehörigen Signalen. Die
Abfrageschlüssel sind `response_version`, `project_id`, `release` und
`environment`. Alle sind optional. Fordern Sie Version 3 an:

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

Version 2 ergänzt `cause` und `fix` bei jedem zugehörigen Issue. Version 3
ergänzt `span_id` bei zugehörigen Issues, Aktionen und Metriken, wenn der Wert
erfasst wurde.

Paket. Um diesen Span zu lesen, rufen Sie die Span-Route mit `project_id`,
`environment` und `release` des Spans auf.

### Antwort der Span-Untersuchung

Mit `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` lesen
Sie eine Operation in einem Trace. Senden Sie `project_id`, `environment` und
`release`. Alle drei sind Pflicht. Kopieren Sie sie aus dem ausgewählten
Span. Senden Sie nicht die Zeilen-`id` des Spans als `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

| `timeline[].offset_ms` | Millisekunden ab dem Start des Spans. Ein negativer Wert liegt vor dem Span. |

Die Basis liest die 24 Stunden vor dem Start des Spans. `since` ist
inklusiv, `until` ist exklusiv. `error_rate_basis_points: 500` bedeutet 5 %.
`subject_percentile_basis_points: 9500` bedeutet, dass 95 % der gespeicherten
Vergleichs-Spans nicht länger dauerten als dieser Span. Perzentile sind
ungefähr. Behalten Sie `baseline.limitations` bei den Werten. Eine Basis mit
`not_found` hat keine gespeicherten Vergleichs-Spans. Eine Basis mit
`unavailable` ist ein fehlgeschlagener Lesezugriff, keine Null.

`parent_chain_status: "complete"` bedeutet, dass die gespeicherte Kette einen
Root erreicht. Es beweist nicht, dass LogBrew jeden Span der Anfrage
gespeichert hat. Die Topologie gibt höchstens 64 Vorfahren, 50 direkte
Child-Spans und 50 dienstübergreifende Kanten zurück.

| HTTP | `error` | Wiederherstellung |
| --- | --- | --- |
| `422` | `trace_id must be a non-zero 32-character hexadecimal value` | Kopieren Sie `trace_id` aus einer Trace-Antwort von LogBrew. |
| `422` | `span_id must be a non-zero 16-character hexadecimal value` | Kopieren Sie `span_id` aus einer Trace-Antwort von LogBrew. |
| `422` | `environment and release must be non-empty exact span scope values` | Kopieren Sie den Bereich aus dem ausgewählten Span. |
| `422` | `invalid query parameters` | Senden Sie `project_id`, `environment` und `release` und keinen anderen Schlüssel. |
| `404` | `span not found` | Prüfen Sie die IDs, das Projekt, die Umgebung und das Release. |

### Antwort der Log-Untersuchung

Mit `GET /api/logs/{log_id}/investigation` lesen Sie ein Log und seine
zugehörigen Belege. Diese Route hat keine Abfrageschlüssel. Kopieren Sie die
Log-ID aus einer Log-Liste.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

Der Lesezugriff kann Belege außerhalb der Filter der Log-Liste zurückgeben.

Dienst. Sie brauchen keine Trace-ID. Lesezugriffe für den genauen Trace
brauchen die Trace-ID des Logs und können andere Dienste einschließen. Die
Trace-Zusammenfassung verwendet dieselbe Trace-ID und denselben Bereich, aber
ohne den Zeitraum.

### Antwort der Aktions-Untersuchung

Produktaktion, ihren gemeldeten Status und zugehörige Belege. Diese Route hat
keine Abfrageschlüssel. Zugehörige Lesezugriffe verwenden denselben Zeitraum

### Antwort der Metrik-Untersuchung

Mit `GET /api/telemetry/metrics/investigation` lesen Sie einen Metriknamen in
einem Projekt und einem Zeitraum. Die Antwort enthält die aktuelle Zeitreihe,
einen Vergleich mit dem gleich langen vorherigen Zeitraum, den jüngsten
Messwert, Trace-Exemplare und abgeschlossene Bereitstellungen. Version 2 ergänzt
die Beschreibung der Metrik aus dem jüngsten gespeicherten Messwert. Version 1
meldet immer `description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` und `since` sind Pflicht. `since` ist inklusiv, `until`
ist exklusiv. Ohne Wert ist `until` der aktuelle Zeitpunkt. Der Vergleich liest
außerdem den gleich langen vorherigen Zeitraum.

```json
      "code": "review_deployment",
      "target": "release_investigation",
      "reason": "Review release-scoped telemetry for a completed deployment inside the compared evidence window without treating temporal proximity as causality.",
      "context": {
        "project_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa", "trace_id": null,
        "span_id": null, "environment": "production", "release": "checkout@1.2.3",
        "service_name": "checkout-api"
      }
    }
  ]
}
```

</Accordion>

| Feld | Bedeutung |
| --- | --- |
| `subject.description_status` | `captured`, `not_captured` oder `unavailable`. |
| `query` | Die normalisierte Abfrage. `service_name`, `release` und `environment` erscheinen nur, wenn sie gesendet wurden. |
| `analysis.status` | `no_samples`, `change_observed`, `no_change_observed`, `baseline_not_found` oder `comparison_unavailable`. |
| `analysis.focus` | Der Vergleichseintrag mit der größten relativen Änderung, oder mit der größten absoluten Änderung, wenn es keine relative Änderung gibt. `null`, wenn kein Eintrag vergleichbar ist. |
| `series[].aggregation.code` | `gauge_last`, `delta_sum`, `distribution_p95`, `raw_cumulative_last` oder `raw_last`. |
| `comparison.status` | `available`, `partial`, `not_found`, `unavailable` oder `no_current_samples`. |
| `comparison.items[]` | Das jüngste nicht leere Zeitfenster jedes Zeitraums für dieselbe Identität der Zeitreihe. |
| `latest_sample` | Der jüngste rohe Messwert, mit SDK, `context`, `metadata` und Trace-Link. |
| `exemplars` | Rohe Messwerte mit einer Trace-ID. `coverage` zählt die verknüpften Messwerte. |
| `deployments` | Abgeschlossene Bereitstellungen vom Beginn des vorherigen Zeitraums bis `until`. |
| `next_actions[]` | `code`, `target`, ein `reason` als Klartext und ein `context`-Bereich für den nächsten Lesezugriff. |

`relative_change_percent` ist `(current - previous) / abs(previous) * 100`.
Der Wert ist `null`, wenn der vorherige Wert null ist oder fehlt.
`expected_buckets_per_series` zählt mögliche Zeitfenster, nicht Zeitfenster
mit Daten. Zeichnen Sie leere Zeitfenster nicht als null. Eine Bereitstellung in
der Nähe einer Änderung beweist nicht, dass sie die Änderung verursacht hat.

Ein Projekt, das das Konto nicht lesen kann, gibt `200 OK` mit
`analysis.status: "no_samples"` zurück, nicht `404`. Ein leeres Ergebnis sagt
nichts über andere Signaltypen aus.

Grenzen für Metriken: Der Zeitraum umfasst höchstens 31 Tage. Jede Zeitreihe
hat höchstens 500 Zeitfenster. `series_limit` ist 1 bis 20, Standardwert 10.
Die Antwort gibt höchstens 20 Exemplare und 20 Bereitstellungen zurück.

| HTTP | `error` | Wiederherstellung |
| --- | --- | --- |
| `422` | `metric investigation response_version must be 1 or 2` | Lassen Sie `response_version` weg oder senden Sie `2`. |
| `422` | `metric series project_id is required` | Senden Sie eine lesbare Projekt-ID. |
| `422` | `metric series name is required` | Kopieren Sie den Namen aus der Metrikliste. |
| `422` | `metric series since is required` | Senden Sie einen Wert wie `24h` oder einen Zeitstempel nach RFC 3339. |
| `422` | `metric series range must not exceed 31 days` | Verwenden Sie einen kürzeren Zeitraum. |
| `422` | `metric series interval would exceed 500 buckets` | Verwenden Sie `interval=auto` oder ein breiteres Intervall. |
| `422` | `metric series_limit must be between 1 and 20` | Senden Sie einen Wert von 1 bis 20. |

`interval` ist `auto`, `1m`, `5m`, `15m`, `1h`, `6h` oder `1d`. `group_by`
ist `none`, `service_name`, `release` oder `environment`. Andere Werte geben
`422` zurück.

### Fehler bei Untersuchungen

| HTTP | Route | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Aktion | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, Aktion, Issue | `invalid URL path parameters`, wenn die ID im Pfad keine UUID ist |
| `422` | Issue, Trace, Span, Metrik | `invalid query parameters` bei einem unbekannten Schlüssel oder einem Wert vom falschen Typ |

Ein `404` bedeutet, dass kein lesbares Projekt den Datensatz hat. Jede Route
gibt außerdem `401` ohne gültige Authentifizierung zurück und `405` bei einer
anderen Methode als `GET`. Unter [API-Fehler](/de/reference/api-errors) finden
Sie die Antworten zu
[nicht gefunden](/de/reference/api-errors#resource-not-found),
[Pfad](/de/reference/api-errors#invalid-path-value),
[Authentifizierung](/de/reference/api-errors#authentication-failure) und
[Methode](/de/reference/api-errors#unsupported-method).

Ein optionaler Lesezugriff auf Belege kann innerhalb einer Antwort `200 OK`
fehlschlagen. Die Sammlung meldet dann `unavailable`. Zeigen Sie sie nicht als
`not_found` und nicht als null Datensätze an.

## <span id="severity-values">Schweregrade</span>

Für Nutzer sichtbare Schweregrade sind `info`, `warning`, `error` und
`critical`. SDKs und Laufzeiten können gängige Aliasse wie `trace`, `debug`,
`warn` oder `fatal` senden. REST- und Live-Antworten geben immer den
kanonischen Wert zurück. LogBrew akzeptiert zum Beispiel `warn` als Eingabe
und gibt `warning` zurück. Die Signalaufnahme lehnt unbekannte Schweregrade
ab.

| Alias | Kanonischer Wert |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Antworten zu Schweregrad-Regeln</span>

Eine Schweregrad-Regel ändert, wie LogBrew ein Log oder ein Issue anzeigt. Sie
ändert nicht den Schweregrad, den die Anwendung erfasst hat. Logs und Issues
geben ein Objekt `triage` zurück:

| Feld | Bedeutung |
| --- | --- |
| `effective_severity` | Der anzuzeigende Schweregrad. Ohne Regel ist er gleich `severity`. |
| `ignored` | `true`, wenn eine Log-Regel das Log ignoriert oder wenn das Issue archiviert ist. |
| `rule_applied` | `true`, wenn eine Schweregrad-Regel oder der ignorierte Zustand gilt. `false` ist der Standardwert, keine fehlenden Daten. |

Verwenden Sie `triage.effective_severity` für die Anzeige. Behalten Sie
`severity` als erfassten Wert. Standardmäßig lässt die Log-Liste ignorierte
Logs weg. Senden Sie `status=ignored` oder `status=all` an `GET /api/logs`, um
sie einzuschließen.

Das Konto braucht die Berechtigung, Issues im Projekt zu verwalten.
Lesezugriff reicht nicht. Ohne diese Berechtigung gibt eine Regeländerung
`403` mit `code: forbidden` zurück.

### Eine Log-Regel ändern

`PUT /api/logs/{log_id}/triage-rule` setzt die Regel für das Log und für
spätere Logs mit derselben Signatur. Der Anfrage-Body braucht `severity` und
`ignored`:

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Eine Antwort `200 OK` enthält das vollständige [Log](#log-response). Sein
`severity` bleibt `warning`. Sein `triage` zeigt die Regel:

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Dieser Ausschnitt zeigt nur die geänderten Felder. `severity` in der Anfrage
ist `source`, `info`, `warning`, `error` oder `critical`. `source` stellt den
erfassten Schweregrad wieder her. Es macht ein ignoriertes Log nicht wieder
aktiv. Um das Log wieder anzuzeigen, senden Sie `"ignored": false`.

### Eine Issue-Regel ändern

`PUT /api/telemetry/issues/{issue_id}/triage-rule` setzt den angezeigten
Schweregrad eines gruppierten Issues und seiner späteren Vorkommen. Der
Anfrage-Body akzeptiert nur `severity`:

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Eine Antwort `200 OK` enthält das vollständige [Issue](#issue-response) in
Version 1. Die erfassten Werte `severity` und `status` ändern sich nicht:

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Dieser Ausschnitt zeigt nur einige Felder. Eine Regel löst, archiviert oder
öffnet ein Issue nicht wieder. Verwenden Sie dafür die
[Statusänderung](#issue-status-response-examples). Eine abgeleitete Priorität
folgt dem neuen effektiven Schweregrad. Lesen Sie das Issue mit
`response_version=2` oder `3`, um sie zu sehen.

Ein nicht unterstützter Schweregrad gibt `422` zurück:

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Ein unbekanntes Feld im Anfrage-Body, zum Beispiel `status` bei einer
Issue-Regel, gibt `422` mit `code: invalid_json` zurück. Ein fehlendes oder
nicht lesbares Log oder Issue gibt `404` mit `code: not_found` zurück. Geht die
Antwort verloren, lesen Sie das Log oder Issue erneut, bevor Sie die Regel
noch einmal senden.

## Format von Fehlerantworten

Anwendungsfehler von LogBrew geben einen JSON-Umschlag zurück. Dieses
Beispiel zeigt eine abgelehnte Anfrage. Der Text in `error` und `next` hängt
vom Problem ab:

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Verwenden Sie `code` für Verzweigungen im Programm und `next_action` für
Automatisierung. Zeigen Sie `error` und `next` Menschen als Klartext an.
Werten Sie ihren Wortlaut nicht maschinell aus. Manche Fehler ergänzen Felder
wie `limit`, `reset_at` oder `retry_after_seconds`. Eine Antwort ohne
JSON-Body hat keinen `code` von LogBrew. Alle Codes finden Sie unter
[API-Fehler](/de/reference/api-errors).

## Daten mit der CLI lesen

Die CLI liest dieselben Routen und gibt mit `--json` dasselbe JSON zurück.
Beginnen Sie breit und grenzen Sie dann ein:

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Fügen Sie `--pagination cursor` hinzu, um den Cursor-Umschlag zu erhalten. Die
CLI fordert die Issue-Antwortversion 4 an. Siehe
[Die nächste Seite lesen](/de/reference/cli#read-the-next-page) und
[Live-Beobachtung](/de/reference/cli#live-watch).

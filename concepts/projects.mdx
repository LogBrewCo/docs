A project is the access boundary for telemetry. Every accepted signal belongs
to one project, and every read command can filter by project.

Use a separate project when telemetry needs a separate ownership or access
boundary. For most teams, that is one app, service, or product area. A
repository does not have to match one project. A monorepo can send several
services to one project.

## <span id="project-service-environment">Project, service, environment</span>

| Term | Example | Use it for |
| --- | --- | --- |
| Project | `checkout-platform` | Ownership and access. |
| Service | `checkout-api` | The app or service that sent the signal. |
| Environment | `production` | Runtime context. |
| Release | `api@1.2.3` | Code version. |

## <span id="recommended-model">Set up a project</span>

[Install the CLI](/guides/cli). Run `logbrew status --json` to read your
account access. If access is not valid, a human runs `logbrew login`. A
project ingest key cannot sign you in.

<Steps>
  <Step title="Create or select a project">
    List your projects first. Create a project only if it does not exist.

    ```bash
    logbrew projects --json
    install -d -m 700 "$HOME/.logbrew"

    logbrew projects create checkout-api \
      --runtime node \
      --environment production \
      --ingest-key-file "$HOME/.logbrew/checkout-api.ingest" \
      --json
    ```

    The CLI writes the ingest key to a new owner-only file. It never prints
    the key or the file path. If the result is not clear, run the exact
    command again. The CLI reuses its pending request identity. The
    [Quickstart](/quickstart) shows how to read the project ID from the
    result.

    For an existing project, record the setup state:

    ```bash
    logbrew projects setup "<project_id>" --source cli --environment production --json
    ```

    `logbrew setup --create-project` only shows help. It does not create a
    project.
  </Step>

  <Step title="Set service names in the SDK">
    Use names from your repository and deployment, such as `api`, `worker`,
    `web`, `ios`, or `checkout-api`. A service name is a label, not a project
    selector. The ingest key selects the project. Renaming a service does not
    move stored events.
  </Step>

  <Step title="Use standard environments">
    Use `production`, `staging`, `preview`, and `local`. If your deployment
    uses other names, use them consistently.
  </Step>

  <Step title="Send a test event and read it">
    Configure the SDK with the project ingest key, as the
    [SDK ingestion guide](/guides/sdk-ingestion) describes. Keep the key out
    of source control. Send one safe event, then read it:

    ```bash
    logbrew read logs --project "<project_id>" --json
    ```

    Each signal has its own list. An empty log list does not mean that the
    project has no issues or traces.
  </Step>
</Steps>

## Diagnose project setup

Read setup state with the project doctor. Do not infer setup state from local
files or an empty log query.

```bash
: "${LOGBREW_PROJECT_ID:?set a project UUID}"

logbrew doctor --project "$LOGBREW_PROJECT_ID" --json
```

The CLI returns a report with `status`, `checks`, and `next`. Exit code `0`
does not show that all checks passed. Read each item in `checks`. See the
[CLI reference](/reference/cli).

### Direct API response

API clients call `GET /api/projects/{project_id}/doctor` with account
authentication. The endpoint has no query parameters or request body. Never
use a project ingest key for this read.

A `200` response has these keys: `project_id`, `state`, `setup_status`,
`setup_acknowledged`, `has_active_ingest_key`, `first_telemetry_seen_at`,
`last_seen_at`, `last_signal`, `next`, and `next_action`. Timestamps are
RFC3339 or `null`. `last_signal` is a display-safe summary, not a raw signal.

| `state` | `next_action.code` | `next_action.target` |
| --- | --- | --- |
| `needs_ingest_key` | `create_ingest_key` | `project_ingest_keys` |
| `needs_setup` | `choose_setup_path` | `project_setup` |
| `needs_telemetry` | `send_first_telemetry` | `telemetry_ingest` |
| `ready` | `inspect_recent_telemetry` | `telemetry_reads` |

`setup_status` is `created`, `setup_started`, `sdk_seen`,
`first_telemetry_seen`, or `active`. `setup_acknowledged` is `true` only for
the last three values.

| Response | Next step |
| --- | --- |
| `404`, `code: "not_found"` | Missing, archived, and other-account projects give the same result. Read the project ID again from `logbrew projects`. Do not try other IDs. |
| `405`, `code: "method_not_allowed"` | Use `GET` without a body or query parameters. |

If the read still fails, [report a problem](/guides/report-a-problem). Do not
include credentials, headers, signal bodies, customer data, local paths, or
source code.

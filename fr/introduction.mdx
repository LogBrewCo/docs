LogBrew est une plateforme d’observabilité pour les développeurs et les agents
de codage. Vos applications envoient de la télémétrie à LogBrew. Pour lire ces
preuves dans le projet que vous sélectionnez, utilisez le tableau de bord, la
CLI native `logbrew`, l’API ou le serveur MCP hébergé.

## <span id="what-is-observability">Observabilité et télémétrie</span>

La télémétrie désigne les données qu’une application envoie sur son
fonctionnement. L’observabilité est la capacité à examiner le comportement de
l’application à partir de ces données.

La surveillance mesure des conditions connues, comme le taux d’erreur ou le
temps de réponse. L’observabilité vous aide à examiner un comportement en
dehors de ces conditions connues. Un graphique de surveillance peut montrer que
la latence du paiement a augmenté. Une investigation relie alors le service, la
version, l’erreur, le log et la trace de ce changement, si l’application a
capturé ces preuves.

La surveillance de l’infrastructure mesure des ressources, comme le CPU et la
mémoire. Ces mesures ne montrent pas le résultat d’une requête de paiement
précise. La télémétrie applicative enregistre la requête, l’erreur et la
version.

## <span id="what-logbrew-tracks">Signaux</span>

| Signal | À utiliser pour |
| --- | --- |
| Problèmes | Trouver les échecs répétés que LogBrew regroupe par empreinte stable. |
| Logs | Lire les enregistrements envoyés par un composant. |
| Traces | Examiner les opérations d’une requête ou d’une tâche. |
| Métriques | Comparer une valeur mesurée dans le temps. |
| Actions | Examiner l’activité produit d’une personne ou d’un système. |

La page [Télémétrie](/fr/concepts/telemetry) décrit chaque signal et ses
champs. Chaque signal a sa propre liste. La vue Logs peut être vide alors que
Problèmes ou Traces contiennent des données.

### Choisir un point de départ

| Tâche | Commencer par | Continuer avec |
| --- | --- | --- |
| Comparer une valeur connue avec ses limites. | La tendance d’une métrique | Les problèmes et les logs du même projet sur la même période. |
| Trouver les échecs répétés. | Les problèmes | Une occurrence, sa trace de pile et sa trace. |
| Examiner les opérations d’une requête ou d’une tâche. | Une trace | Ses spans, puis les logs, problèmes, actions et métriques qui portent le même ID de trace. |
| Lire les enregistrements d’un composant. | Les logs | Les attributs, le service, l’environnement et le contexte de trace. |
| Examiner l’activité produit. | [Analyses produit](/fr/concepts/product-analytics) | La couverture des identités, les sessions, la rétention et le cycle de vie sur la même période. |

## <span id="keep-project-and-service-separate">Projet et service</span>

Un projet est la limite d’accès de la télémétrie. Un projet peut contenir
plusieurs services, par exemple une application web, une API et une
application mobile. Un service est le composant qui a envoyé un signal. Un
projet et un service peuvent porter le même nom, mais leurs filtres
sélectionnent des périmètres différents. Un filtre de service sélectionne les
résultats de ce service dans le projet sélectionné.

Les filtres d’environnement, de version et de période modifient aussi les
résultats. Avant de comparer deux résultats, vérifiez que ces filtres sont
identiques. Consultez [Projets et configuration](/fr/concepts/projects) et
[Versions](/fr/concepts/releases).

## <span id="follow-exact-relationships">Liens avec une trace</span>

Une trace contient des spans. Chaque span enregistre une opération, sa durée et
son statut. Les logs, problèmes, actions et métriques portent les identifiants
de leur trace et de leur span. Seuls des identifiants identiques relient un
signal à une trace. Ne reliez pas des signaux uniquement par leur message,
leur version ou leur horodatage.

Si l’application envoie un signal sans contexte de trace actif, LogBrew donne
au signal une trace de capture. Cette trace montre que LogBrew a stocké le
signal. Elle ne montre pas le chemin d’une requête. Consultez
[Spans de capture](/fr/concepts/distributed-tracing#capture-spans).

Les réponses d’investigation donnent un `status` à chaque source de preuves
facultative, comme la trace. Lisez le `status` de la trace avant de l’ouvrir :

| État | Signification |
| --- | --- |
| `available` | LogBrew a lu les preuves, et la réponse les contient. |
| `not_linked` | L’événement n’a pas d’identifiant permettant un lien exact, comme un ID de trace. Certains événements anciens n’ont pas d’ID de trace. |
| `not_found` | L’événement a un identifiant exact, mais aucune preuve stockée ne correspond au périmètre sélectionné. |
| `unavailable` | La lecture de cette source n’a pas pu aboutir à ce moment-là. Le reste de la réponse reste valide. |

Consultez [Traçage distribué](/fr/concepts/distributed-tracing) pour la
propagation du contexte et la vérification du contexte manquant.

## <span id="read-evidence-states-before-drawing-a-conclusion">Limites des preuves</span>

LogBrew montre uniquement les preuves que votre application a capturées. Une
trace montre uniquement les opérations que l’application a enregistrées. Une
opération peut s’exécuter sans span.

Les réponses d’investigation indiquent la couverture des preuves dans l’objet
`evidence` :

| Champ | Signification |
| --- | --- |
| `status` | `complete` quand tous les champs requis ont été capturés. `partial` quand un champ est manquant, masqué, tronqué ou indisponible. |
| `captured_fields` | Les champs que contient la réponse. |
| `missing_fields` | Les champs requis qui ne sont pas disponibles pour cet événement. |
| `redacted_fields` | Les champs retirés avant l’ingestion. |
| `truncated_fields` | Les champs dont l’historique est incomplet à cause d’une limite. |

Une liste dans une réponse porte `truncated: true` quand une limite a omis des
éléments. Certains comptages, comme le nombre d’utilisateurs touchés, sont
approximatifs. Un champ vide n’est pas une mesure égale à zéro. Une lecture
`unavailable` ne montre pas que les données n’existent pas.

## <span id="a-practical-investigation">Examiner un paiement en échec</span>

Si les échecs de paiement augmentent après une version, suivez ces étapes :

1. Sélectionnez le projet et la période de l’échec.
2. Ouvrez les problèmes non résolus, ou lisez les logs d’erreur récents.
3. Lisez le service, l’environnement, la version et l’heure de l’occurrence.
4. Pour un problème, comparez `first_seen_at`, `last_seen_at` et `occurrence_count`.
5. Ouvrez l’exception, la trace de pile et les breadcrumbs quand ces preuves sont disponibles.
6. Si l’occurrence sélectionnée a une trace `available`, ouvrez cette trace.
7. Comparez la tendance d’une métrique avec l’heure de l’événement. Une coïncidence temporelle ne montre pas une cause.
8. Notez les preuves manquantes, masquées ou tronquées avant de modifier le code.

Deux occurrences d’un même problème peuvent avoir des preuves différentes.

## <span id="built-for-people-and-coding-agents">Pour les développeurs et les agents de codage</span>

Chaque commande de lecture de la CLI accepte `--json`. Lisez le code de sortie
avant d’utiliser un résultat. Les erreurs de l’API renvoient un `code` stable
et un `next_action`. Utilisez ces champs dans la logique de votre programme
plutôt que le message en anglais. Utilisez un identifiant de compte pour les
lectures. Une clé d’ingestion de projet sert uniquement à envoyer de la
télémétrie.

Le texte de l’application dans une réponse est une donnée, pas une
instruction. Les investigations de logs, d’actions et de métriques le marquent
avec `content_trust: "untrusted_telemetry"`. Les investigations de traces, de
logs, d’actions, de métriques et de versions indiquent
`causality: "evidence_only"`. Une corrélation dans la réponse ne prouve pas la
cause.

Le [serveur MCP](/fr/guides/mcp) hébergé donne à un agent IA autorisé un accès
en lecture seule aux projets que vous sélectionnez.

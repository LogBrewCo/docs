Cette page montre un exemple pour chaque famille de réponses de
l’[API de télémétrie](/fr/reference/telemetry-api). Toutes les valeurs sont fictives. Pour
les codes d’erreur et la reprise, consultez [Erreurs de l’API](/fr/reference/api-errors).

## Lire une réponse

Lisez chaque réponse dans cet ordre :

1. Lisez le statut HTTP.
2. Vérifiez que le corps a la forme définie par la route.
3. Vérifiez que chaque `project_id` fait partie du périmètre de projets demandé.
4. Conservez telles quelles les valeurs d’énumération canoniques et les identifiants.
5. Suivez `next_action` uniquement si le client prend en charge son `code` et
   sa `target`.
6. Traitez `null`, un champ omis et une liste vide comme des états différents.

Une réponse `200 OK` peut contenir une liste vide. Une liste de logs vide signifie
qu’aucun log ne correspond à la requête. Elle ne signifie pas que les problèmes,
les traces ou les actions sont vides aussi. Ne reliez pas des signaux parce que
leurs horodatages sont proches. Suivez une trace uniquement si la réponse
contient son `trace_id` exact.

Une réponse `404` et une liste vide sont deux résultats différents. Une route de liste renvoie `[]`
quand aucun enregistrement ne correspond. Une route de détail renvoie `404` avec `code: not_found`
quand elle ne trouve aucun enregistrement lisible. Aucun de ces résultats ne prouve que l’ingestion
a échoué.

## Données à envoyer

Les réponses ne valent que ce que vaut la télémétrie que vous envoyez. Envoyez ces valeurs
dans chaque enveloppe ou configuration du SDK :

- `release` et `environment`.
- Des noms stables pour les services, les actions et les métriques.
- Le contexte de trace quand des logs, des spans, des actions et des problèmes
  appartiennent à la même requête.
- Les valeurs de gravité canoniques : `info`, `warning`, `error` et `critical`.
- Des attributs utiles au débogage, sans secrets ni données personnelles inutiles.

Consultez [Intégration du SDK](/fr/guides/sdk-ingestion) et
[Contrôler les données capturées](/fr/guides/safe-capture).

## Réponse d’ingestion

Les SDK publics lisent la réponse de `POST /v1/events` à votre place. Le code de
l’application n’a pas à la traiter.

### Réponse à un lot du SDK

Un lot du SDK accepté renvoie `200 OK` avec le nombre de signaux acceptés pour
chaque flux :

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| Champ | Signification |
| --- | --- |
| `issues`, `logs`, `trace_spans`, `actions`, `metrics` | Les signaux de ce lot que LogBrew a acceptés. |
| `already_accepted` | Les signaux dont LogBrew a déjà accepté l’ID. LogBrew ne les stocke pas de nouveau. |
| `context_updated` | `true` quand le lot a mis à jour le contexte de version ou d’environnement. |

Les nombres portent uniquement sur ce lot. Si vous renvoyez un lot que LogBrew a
déjà accepté, la réponse contient `0` pour chaque flux et le nombre de signaux dans
`already_accepted`. Gardez les ID d’origine des signaux quand vous réessayez.

### Réponse à une enveloppe native

`POST /api/telemetry/ingest` renvoie `200 OK` avec le nombre d’éléments acceptés
pour chaque flux :

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

La réponse native n’a pas de champ `metrics` ni `context_updated`. Ne les ajoutez
pas. `already_accepted` compte les éléments dont LogBrew a déjà accepté l’`id` pour
ce projet. Consultez l’[enveloppe native directe](/fr/guides/sdk-ingestion#required-envelope-fields).

### Erreurs d’ingestion

Une réponse `401` avec `code: ingest_key_invalid` signifie que le jeton bearer d’ingestion est
révoqué, expiré ou non valide pour le projet. Sur `POST /v1/events`, un jeton bearer
absent, ou un jeton bearer qui n’est pas une clé d’ingestion, renvoie `401` avec
`code: unauthorized`. Utilisez le jeton bearer d’ingestion actuel du projet. Ne
réessayez pas avec un jeton bearer de compte.

Un lot du SDK refusé renvoie `422` avec `code: validation_failed` :

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Les autres valeurs de `error` incluent `SDK event batch requires at least one event` et
`SDK event type is not supported by this ingest route`. Vérifiez la version du SDK
et la configuration du transport. N’envoyez pas de lot vide. Ne modifiez pas
les types ou les ID des signaux dans le seul but de faire passer la validation.

Une requête avec une autre méthode que `POST` renvoie `405` avec
`code: method_not_allowed`. Un corps JSON illisible renvoie `code: invalid_json`.

## Format des réponses de liste de télémétrie

Par défaut, les routes de liste renvoient un tableau JSON brut. Une liste vide
réussie vaut `[]`.

Avec `pagination=cursor`, la route renvoie une enveloppe. La clé de la collection
correspond au signal :

| Route | Clé de la collection |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`, avec un `issue_id` au premier niveau |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`, avec un `naming_quality` au premier niveau |

`next_cursor` est un objet qui contient les champs de continuation, ou `null` sur la dernière
page. Les lignes vont de la plus récente à la plus ancienne. Consultez la [pagination par curseur](/fr/reference/telemetry-api-filters#cursor-pagination).

### <span id="log-response">Réponse de log</span>

Une page de logs avec curseur et `limit=1` :

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

Les logs contiennent `level` pour la compatibilité et `severity` pour l’affichage. Les deux
contiennent la valeur canonique. `triage` contient le résultat d’une règle de gravité. Consultez
les [réponses des règles de gravité](#severity-rule-responses).

`trace_id` et `span_id` valent `null` quand le log n’a pas de lien de trace. Dans ce cas,
`next_action` vaut `inspect_related_logs` avec la cible `telemetry_logs`. Les logs,
les problèmes et les actions utilisent les deux mêmes paires `next_action`.

`GET /api/logs/{log_id}` renvoie un seul log, sous la même forme.

### <span id="issue-response">Réponse de problème</span>

`GET /api/telemetry/issues/{issue_id}` renvoie un problème groupé. La liste
renvoie les mêmes objets. Cet exemple utilise la version de réponse par défaut, la version 1 :

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

En version 1, `status` vaut `unresolved`, `resolved` ou `ignored`. Pour un
problème archivé, `triage.ignored` vaut `true`. Pour les paires `next_action` et
les lectures qui en découlent, consultez
[Investiguer un problème](/fr/guides/investigate-an-issue).

`first_seen_at` et `last_seen_at` sont les heures de la première et de la plus
récente occurrence. Elles ne changent pas quand le statut change.

Certains champs n’apparaissent que si LogBrew dispose des données :

| Champ | Quand il apparaît |
| --- | --- |
| `span_id` | Le problème a un lien de span. Sinon, le champ est omis. |
| `diagnostics` | La dernière occurrence a un type d’exception ou des Breadcrumbs. Consultez l’[historique des occurrences d’un problème](#issue-occurrence-history). |
| `symbolication` | Uniquement sur `GET /api/telemetry/issues/{issue_id}`, quand le problème a une identité d’artefact de version. Consultez [Source maps JavaScript](/fr/guides/source-maps). |

`symbolication.status` vaut `resolved`, `invalid_metadata`,
`artifact_not_found`, `source_not_resolved` ou `unavailable`. La liste,
les changements de statut et les changements de règle ne renvoient pas `symbolication`.

Avec `response_version=2`, le problème a les mêmes champs, avec ces changements :

| Champ | Valeur en version 2 |
| --- | --- |
| `status` | `unresolved`, `resolved` ou `archived`. La version 1 affiche `archived` sous la forme `ignored`. |
| `priority` | `high`, `medium` ou `low`. |
| `priority_source` | `manual` quand une personne a défini la priorité. `derived` quand la priorité suit la gravité effective. |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

Cet exemple ne montre que certains champs. Une priorité dérivée vaut `high` pour `error`
et `critical`, `medium` pour `warning` et `low` pour `info`. Elle utilise
`triage.effective_severity` : une règle de gravité de problème peut donc la modifier.

Avec `response_version=3`, le problème a tous les champs de la version 2, plus `assignee`.
`assignee` vaut `null` quand le problème n’a pas de responsable :

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| Champ | Signification |
| --- | --- |
| `assignee.user_id` | ID utilisateur du responsable. Envoyez-le comme `assignee` dans un filtre ou une modification. |
| `assignee.name` | Nom du responsable, ou `null` quand le compte n’a pas de nom. |
| `assignee.email` | Adresse e-mail du responsable. |

Un problème n’affiche aucun responsable quand le membre attribué ne peut plus lire
le projet.

Avec `response_version=4`, `assignee` a aussi un `type`. Un responsable `user`
a `user_id`, `name` et `email`, comme dans la version 3. Un responsable `team`
a `team_id`, `slug` et `name`. La version 3 affiche une équipe responsable
comme `null`. La CLI demande la version 4 :

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

Toute autre valeur de `response_version` renvoie `422` avec `code: validation_failed`. Une
page avec curseur utilise la même version pour chaque problème de `issues`.

### <span id="assignee-list-response">Réponse de la liste des responsables</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` renvoie chaque
compte à qui l’on peut attribuer des problèmes dans le projet :

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

Ajoutez `response_version=2` pour obtenir aussi `teams` : chaque équipe de
l’organisation du projet, avec `team_id`, `slug` et `name`.

Si le compte ne peut pas lire le projet, la route renvoie `404` avec
`code: not_found`.

### <span id="action-response">Réponse d’action</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` suit un même acteur ou une même session. Traitez `distinct_id` et
`session_id` comme des identifiants opaques. `session_id` et `trace_id` valent `null`
quand ils manquent. `span_id` est omis quand il manque. Une action n’a
pas de gravité. Consultez [Capture d’événements produit](/fr/guides/product-events).

### Réponse de métrique

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

Chaque élément est un échantillon. N’utilisez pas le nombre d’échantillons comme un nombre
d’événements ou d’utilisateurs. `unit`, `temporality`, `trace_id` et `span_id` valent `null` quand ils
manquent. Une valeur `null` n’est pas zéro.

### Réponse de version

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

Une ligne couvre un projet, une version, un environnement et un service. Ses nombres
décrivent uniquement cette ligne.

`trace_health.status` vaut `unknown` quand la ligne n’a pas de trace, sinon
`no_errors_observed` ou `errors_observed`. `error_rate_basis_points` est la
part des traces qui ont un span en erreur, de `0` à `10000`. Ce n’est pas un taux
d’erreur de toutes les requêtes.

`next_action` désigne le premier type de signal qui a des données, dans cet ordre :

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

Consultez [Versions](/fr/concepts/releases).

### Réponse de la découverte des traces

`GET /api/telemetry/traces?pagination=cursor` renvoie une ligne pour chaque trace,
plus un reçu `naming_quality` pour la page renvoyée :

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` couvre uniquement la page renvoyée. Ce n’est pas un score pour
tout le compte. `truncated: true` signifie qu’une autre page existe. Quand la page contient un
nom générique, une route non reconnue ou une opération générique, `next_action` vaut
`improve_trace_naming` avec la cible `sdk_configuration`. Sans
`pagination=cursor`, la route renvoie un tableau brut de traces, sans
`naming_quality`.

`next_cursor` contient `time` et `trace_id`. Envoyez-les comme `cursor_time` et
`cursor_trace_id`.

`GET /api/telemetry/traces/{trace_id}` renvoie les spans d’une trace.
`GET /api/telemetry/traces/{trace_id}/summary` renvoie le span racine, les spans
en erreur, les services, la durée et le chemin le plus lent, sans les attributs bruts des spans. Une
réponse `404` du résumé signifie qu’aucune trace ne correspond au périmètre complet. Ne réessayez pas
sans les filtres. Consultez les [réponses des spans et du résumé de trace](#trace-spans-and-summary-responses).

### Listes vides et enregistrements introuvables

Une lecture de liste peut ne renvoyer aucune correspondance. Une lecture de détail suit un autre contrat :

| Requête | Succès | Aucun enregistrement lisible |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200` avec un [log](#log-response) | `404` avec `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200` avec un [problème](#issue-response) | `404` avec `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200` avec des occurrences | `404` avec `code: not_found` sur la première page |
| `GET /api/telemetry/traces/{trace_id}` | `200` avec des spans | `200` avec `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200` avec un résumé | `404` avec `code: not_found` |

Un log introuvable renvoie cette réponse `404` :

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Un problème introuvable utilise `"error": "issue not found"`. Un résumé de trace introuvable utilise
`"error": "trace not found"`. Un ID inconnu et un ID que le compte ne peut pas
lire renvoient la même réponse.

Une liste avec un `project_id` que le compte ne peut pas lire renvoie `200` avec
une liste vide. Vérifiez l’ID du projet avant d’annoncer qu’aucune donnée n’existe.

### Sélections de projets refusées

Les listes de logs, de problèmes, d’actions, de métriques, de versions et de traces acceptent un projet
avec `project_id`, ou de 2 à 50 projets avec `project_ids`. Le catalogue des attributs
de logs accepte les mêmes sélecteurs. L’historique des occurrences d’un problème ne les
accepte pas.

Une requête qui contient à la fois `project_id` et `project_ids` renvoie `422` :

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

`project_ids` avec un UUID invalide, un ID répété, ou moins de 2 ou plus de
50 ID renvoie aussi `422` avec `code: validation_failed`.

Si le compte ne peut pas lire l’un des projets d’un ensemble `project_ids`, toute la
requête renvoie `404`. Elle ne renvoie pas les autres projets comme résultat
partiel :

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

Affichez l’erreur, pas une liste vide ni un nombre égal à zéro. Relisez la liste
des projets. Ne retirez pas un projet sans le signaler, et ne réessayez pas sur tous
les projets. Un identifiant délégué, comme une connexion MCP, renvoie `403` avec
`code: forbidden` pour un projet hors de son autorisation. Consultez le
[périmètre de projets](/fr/reference/telemetry-api-filters#project-scope).

### <span id="cursor-errors">Erreurs de curseur</span>

Les logs, les problèmes, les actions, les métriques et les occurrences de problème utilisent `cursor_time` et
`cursor_id`. Un curseur refusé renvoie `422` avec `code: validation_failed`.
Ces erreurs ne signifient pas que la liste est vide.

| Requête | `error` |
| --- | --- |
| `pagination=cursor` avec un seul des deux champs du curseur | `cursor_time and cursor_id must be sent together` |
| `cursor_time` qui n’est pas un horodatage RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Champs du curseur sans `pagination=cursor`, ou avec une autre valeur de `pagination` | `pagination must be cursor when cursor pagination is requested` |

Par exemple :

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Copiez le `next_cursor` complet de la page précédente. Ne remplacez pas
`cursor_time` par l’heure actuelle. Si vous avez perdu le curseur, recommencez avec
`pagination=cursor` et les filtres d’origine. Un paramètre de requête inconnu ou une valeur
du mauvais type renvoie `422` avec `"error": "invalid query parameters"`.

### Réponses du curseur de versions

Un curseur de versions a 5 champs. Une requête réussie sans correspondance renvoie
`200` :

```json
{
  "releases": [],
  "next_cursor": null
}
```

Quand `next_cursor` ne vaut pas `null`, envoyez les 5 valeurs dans la requête suivante :

| Champ de `next_cursor` | Paramètre de requête |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` marque une position. Il ne remplace pas `project_id` ni
`project_ids`. Gardez les paramètres de projet et de filtre d’origine. Encodez
chaque valeur pour l’URL.

Avec `pagination=cursor`, un curseur incomplet ou une valeur vide de version, d’environnement
ou de service renvoie `422` avec
`"error": "all release cursor fields must be sent together"`. Un
`cursor_time` invalide et un `pagination=cursor` absent renvoient les mêmes erreurs que les
[autres curseurs](#cursor-errors).

### Erreurs de la découverte des traces

Ces erreurs s’appliquent à `GET /api/telemetry/traces`. Chacune renvoie `422` avec
`code: validation_failed`. Une requête refusée n’est pas un résultat vide.

| Requête | `error` |
| --- | --- |
| `status` autre que `error` ou `ok` | `trace status must be error or ok` |
| `min_duration_ms` inférieur à `0` | `minimum trace duration must not be negative` |
| Un seul champ du curseur, ou un `cursor_trace_id` vide | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` qui n’est pas un horodatage RFC3339 | `cursor_time must be an RFC3339 timestamp` |
| Champs du curseur sans `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

Pour inclure les deux états de trace, omettez `status`. Pour la page suivante, copiez
`next_cursor.time` dans `cursor_time` et `next_cursor.trace_id` dans
`cursor_trace_id`. N’envoyez pas `cursor_id` pour une page de traces. Consultez les
[filtres de traces](/fr/reference/telemetry-api-filters#trace-filters).

### <span id="issue-occurrence-history">Historique des occurrences d’un problème</span>

`GET /api/telemetry/issues/{issue_id}/events` lit les occurrences d’un
problème groupé. Utilisez un jeton bearer de compte et l’ID du problème groupé. La route
accepte uniquement `pagination`, `cursor_time`, `cursor_id` et `limit`. Elle
n’accepte pas de filtre de projet, de temps, de version, d’environnement ou de gravité.

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

Une première page avec une occurrence et un curseur de continuation :

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },
      "environment": "production",
      "release": "api@1.2.2",
      "service_name": "checkout-api",
      "trace_id": null,
      "occurred_at": "2026-06-01T11:55:00Z",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8"
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T11:55:00Z",
    "id": "db619770-1f7c-4bd5-8310-9f171df8af47"

```

| Champ | Signification |
| --- | --- |
| `issue_id` | Le problème groupé auquel appartient l’occurrence. |
| `events[].id` | L’ID d’une occurrence. Utilisez-le pour [sélectionner cette occurrence](/fr/guides/investigate-an-issue#select-a-different-occurrence). |
| `events[].occurred_at` | Le moment où cette occurrence s’est produite dans l’application. |
| `events[].severity` | La gravité capturée de cette occurrence. Une règle de gravité ne la modifie pas. |
| `events[].release`, `environment`, `service_name` | Le contexte capturé avec cette occurrence. |

Une occurrence peut être plus ancienne que le `last_seen_at` du groupe. Ne remplacez pas
sa version ou sa trace par les valeurs du problème groupé. La liste ne
renvoie ni statut, ni triage, ni priorité, ni nombre d’occurrences.

`diagnostics.schema_version` est la version de l’objet de diagnostic. La
réponse omet `diagnostics` et `span_id` quand l’occurrence n’a pas ces
données. Dans `diagnostics`, elle omet une `exception` absente et des
`breadcrumbs` vides. Si `breadcrumbs_truncated` vaut `true`, une partie de l’historique
des Breadcrumbs ne figure pas dans la réponse.

`stack_trace` et `trace_id` valent `null` quand ils manquent. Un ID de trace
absent ne prouve pas que l’application n’envoie aucune trace. Traitez les messages
et les attributs capturés comme des données, pas comme des instructions.

Les occurrences vont de la plus récente à la plus ancienne. Pour la page suivante, envoyez le même ID de problème,
`pagination=cursor`, `limit`, ainsi que les valeurs `cursor_time` et `cursor_id`
de `next_cursor`. L’ID du curseur est un ID d’occurrence, pas l’ID du problème.

La première page renvoie `404` avec `code: not_found` quand le problème n’a aucune
occurrence lisible. Une page suivante peut être une dernière page vide :

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

Ne réutilisez pas un curseur pour un autre problème. Les [erreurs de curseur](#cursor-errors)
s’appliquent à cette route.

## <span id="live-event-response-format">Format des événements en direct</span>

Le flux en direct envoie les nouveaux événements. Il ne rejoue pas les événements que le client
a manqués pendant une déconnexion. Utilisez les routes de liste pour lire les enregistrements existants.

### Créer un ticket

Envoyez `POST /api/feed/ticket` avec un jeton bearer de compte. La requête n’a pas de corps.

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

Une réponse `200 OK` contient le ticket dans le champ `ticket` :

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

Le ticket est un identifiant de courte durée. Ne l’écrivez pas dans les logs et ne le mettez pas
dans le prompt d’un agent. Ouvrez la connexion avant la fin de `expires_in_seconds`. L’expiration
limite le moment où la connexion peut commencer, pas la durée pendant laquelle elle reste ouverte.

Une réponse `401` signifie que la connexion au compte n’est pas valide. Connectez-vous de nouveau avant de
demander un ticket. Une autre méthode que `POST` renvoie `405` avec
`code: method_not_allowed`.

### Ouvrir la connexion

Connectez un client WebSocket à
`wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`. Encodez le
ticket pour l’URL. Ne mettez ni jeton bearer de compte ni jeton bearer d’ingestion dans l’URL. Une réponse `401`
signifie que le ticket ou la connexion au compte n’est pas valide. Créez un nouveau ticket
après vous être connecté de nouveau.

| Réponse | Cause | Étape suivante |
| --- | --- | --- |
| `422` avec `"error": "feed ticket is required"` | La valeur de requête `ticket` est absente ou vide. | Créez un ticket et ouvrez la connexion avec. |
| `401` avec `code: unauthorized` | Le ticket a expiré ou n’est pas valide. | Créez un nouveau ticket. Ne réessayez pas avec le même ticket. |
| `code: invalid_websocket_upgrade` | La requête n’est pas une mise à niveau WebSocket valide. | Utilisez un client WebSocket. |
| `405` avec `code: method_not_allowed` | La requête n’utilise pas `GET`. | Utilisez `GET` pour la connexion. |

Après une erreur, attendez avant de rouvrir la connexion. Ne rouvrez pas la connexion en boucle serrée.

### Lire les messages

Chaque message est une enveloppe `{ "type": "...", "data": ... }`. Lisez `type`
avant d’analyser `data`. Ignorez les types que le client ne prend pas en charge.

| Type d’événement | Contenu de `data` |
| --- | --- |
| `native_log` | Données de log, sous la forme de la [réponse de log](#log-response). |
| `native_issue` | Données du problème groupé, sous la forme de la [réponse de problème](#issue-response) en version 1. |
| `native_trace_span` | Un span, sous la forme d’un élément de la [liste des spans](#span-list). |
| `native_action` | Données d’action produit, sous la forme de la [réponse d’action](#action-response). |
| `project_created`, `project_updated`, `project_catalog_changed` | Données de projet. Relisez la liste des projets quand elle change. |
| `usage_updated`, `usage_limit_warning`, `usage_limit_blocked` | Utilisation du compte, sous la forme de l’[utilisation du compte](/fr/reference/account-api#account-usage). |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

Un événement `native_issue` utilise la version 1 de la réponse de problème : un problème archivé
affiche `ignored`, et l’événement n’a pas de priorité. Les métriques et les versions ne sont pas
des types d’événements en direct. Lisez-les avec leurs routes de liste. Le ticket ne
sélectionne pas de projet. Vérifiez le `project_id` de chaque événement avant
de l’afficher dans la vue d’un projet. `logbrew watch --json` utilise ce flux. Consultez la
[référence de la CLI](/fr/reference/cli).

### Gérer une connexion fermée

| Code de fermeture | Motif | Étape suivante |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | Attendez, puis rouvrez la connexion avec un nouveau ticket. Relisez les routes de liste pour récupérer les enregistrements manqués. |
| `1008` | `live feed access changed; sign in again` | Arrêtez de rouvrir la connexion. Connectez-vous de nouveau avant de créer un nouveau ticket. |

D’autres déconnexions peuvent n’avoir aucun motif LogBrew. Après avoir rouvert la connexion, relisez les
routes de liste et rapprochez les enregistrements par ID.

## <span id="issue-status-response-examples">Exemples de réponses de statut de problème</span>

`PATCH /api/telemetry/issues/{issue_id}` avec `{ "status": "resolved" }`
renvoie `200 OK` avec le problème groupé mis à jour, sous la même forme que la
[réponse de problème](#issue-response). Le paramètre de requête `response_version` choisit
la version. La route ne renvoie pas d’indicateur de succès.

Le corps définit au moins un des champs `status`, `priority` et `assignee`. `status`
accepte `unresolved`, `resolved` ou `archived`. `ignored` est un ancien nom
de `archived`. Consultez [Mettre à jour un problème](/fr/reference/telemetry-api#update-one-issue).

Vérifiez les valeurs renvoyées de `id`, `status` et `priority` avant d’afficher un succès. Ne
construisez pas le résultat à partir des valeurs envoyées. Un changement de statut ne supprime pas
d’occurrences et ne modifie ni `first_seen_at` ni `last_seen_at`. Il ne modifie pas
`severity` ni une règle de gravité.

Une modification refusée renvoie `422` avec `code: validation_failed` :

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| Résultat | Cause |
| --- | --- |
| `422`, `issue update requires status, priority, or assignee` | Le corps ne contient aucun des 3 champs. |
| `422`, `issue priority must be high, medium, or low` | La valeur de priorité n’est pas prise en charge. |
| `422`, `issue assignee must be me, none, a user ID, or team:<team_id>` | La valeur du responsable n’est pas prise en charge. |
| `422`, `issue assignee cannot read this project` | Le responsable n’a pas accès au projet. LogBrew ne modifie rien. |
| `422`, `issue assignee team is not a team of this project's organization` | L’équipe n’appartient pas à l’organisation du projet. LogBrew ne modifie rien. |
| `403` avec `code: forbidden` | Le compte ne peut pas gérer les problèmes du projet. |
| `404` avec `code: not_found` | Le compte ne peut pas lire le problème, ou le problème n’existe pas. |

Un champ qui a déjà la valeur demandée ne change pas. Après un délai dépassé
ou une réponse perdue, renvoyez la même requête, ou lisez d’abord le problème. N’envoyez
pas une autre modification avant d’avoir lu l’état actuel. Consultez
[Écritures](/fr/reference/api-errors#writes).

`POST /api/telemetry/issues/bulk` renvoie `200 OK` avec un résultat pour chaque
ID de problème demandé, dans l’ordre de la requête. Chaque problème trouvé utilise la forme
de la version 3. Un résultat `not_found` contient `issue: null` :

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
```

## Périmètre des requêtes d’analyse

Les routes d’analyse, la route des séries de métriques et la route du volume de signaux
lisent un projet sur une période. Chaque requête exige `project_id` et
`since`. `since` accepte une durée compacte comme `24h` ou `7d`, ou un
horodatage RFC3339. `until` accepte un horodatage RFC3339 et vaut par défaut l’heure de la
requête. La période inclut `since`, exclut `until` et ne peut pas dépasser
31 jours.

`service_name`, `release` et `environment` sont des filtres exacts facultatifs. Chaque
valeur doit compter de 1 à 256 caractères une fois que LogBrew a retiré les espaces. La route de
comparaison de segments place ces filtres dans chaque segment, pas au premier niveau.

Si le compte ne peut pas lire le projet, ces routes renvoient `200 OK` avec
des nombres à zéro. Elles ne renvoient pas `404`. Un résultat vide ne confirme pas
l’accès au projet. Comparez `project_id` avec les projets que le compte peut
lire. Une requête passée par une connexion MCP qui n’inclut pas le projet renvoie
`403` et `forbidden`.

| Route | Valeurs de `response_version` | Par défaut |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`, `2` ou `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` ou `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | Non acceptée | Schéma `1` |
| `POST /api/telemetry/analytics/paths` | Non acceptée | Schéma `1` |
| `GET /api/telemetry/metrics/series` | Non acceptée | Schéma `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

Chaque réponse commence par `schema_version`, `query` et `purpose`. `query`
reprend le périmètre effectif. Il omet un filtre que vous n’avez pas envoyé. `purpose`
est un texte simple qui explique à quelle question la route répond.

Un taux est omis quand son dénominateur vaut zéro. Un taux omis ne vaut ni `0`
ni `null`. Lisez `coverage` avant de vous fier à un taux.

### <span id="shared-scope-errors">Erreurs de périmètre communes</span>

Ces erreurs utilisent HTTP `422` et `validation_failed` :

| Cause | `error` |
| --- | --- |
| Pas de `project_id` | `product analytics project_id is required` |
| Pas de `since` | `product analytics since is required` |
| `since` n’est ni une durée ni un horodatage RFC3339 | `invalid since value` |
| `until` n’est pas un horodatage RFC3339 | `product analytics until must be an RFC3339 timestamp` |
| `since` n’est pas antérieur à `until` | `product analytics since must be earlier than until` |
| La période dépasse 31 jours | `product analytics range must not exceed 31 days` |
| Un filtre vide, ou un filtre de plus de 256 caractères | `product analytics context filters must be non-empty and at most 256 characters` |

Par exemple, une requête sans `project_id` renvoie :

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Les routes des séries de métriques et du volume de signaux appliquent les mêmes règles de périmètre, avec
leur propre texte `error`. Leurs sections ci-dessous listent ces erreurs.

Un paramètre de requête inconnu renvoie `422` avec la réponse
[paramètres de requête invalides](/fr/reference/api-errors#invalid-query-parameters).
Un champ JSON inconnu, un champ JSON obligatoire absent ou une
valeur d’énumération non prise en charge renvoie `invalid_json`. Consultez
[JSON invalide](/fr/reference/api-errors#invalid-json). Une requête avec la mauvaise
méthode HTTP renvoie `405` et `method_not_allowed`. Son texte `next` indique la
méthode et les champs pris en charge. Consultez
[Méthode non prise en charge](/fr/reference/api-errors#unsupported-method).

## Réponse de la vue d’ensemble des analyses produit

`GET /api/telemetry/analytics/overview` montre l’activité d’un projet :
volume d’actions, utilisateurs, sessions, une série temporelle, les principales actions, et les
vues de page, vues d’écran et interactions classifiées. Utilisez-la pour trouver les noms exacts
des événements à utiliser dans les autres routes d’analyse.

Envoyez `response_version=3`. Les versions 1 et 2 renvoient les mêmes nombres, mais leur
valeur `estimation.method` utilise un ancien nom. La version 1 ne vérifie pas le
type de sujet quand elle compte les utilisateurs identifiés. Les versions 2 et 3 comptent uniquement
les sujets de type `user`, et elles ajoutent les nombres de sujets anonymes et
`subject_coverage`.

Cette requête lit une heure en intervalles de cinq minutes et renvoie deux lignes dans
chaque classement :

```bash

  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T11:00:00Z" \
  --data-urlencode "until=2026-06-01T12:00:00Z" \
```

## <span id="ordered-funnel-response">Réponse d’entonnoir ordonné</span>

correspond pas. Ce corps de requête compte les sessions qui consultent `/pricing` puis
terminent l’inscription en moins d’une heure :

Le `kind` d’une étape vaut `page_view`, `screen_view` ou `interaction`. La route d’entonnoir

### Lire la conversion et la couverture

`entry_rate` vaut `entered_units` divisé par `candidate_units` : 50 sur 60.
`overall_conversion_rate` vaut `completed_units` divisé par `entered_units` :
15 sur 50, soit 30 %. Ce n’est pas 15 divisé par tous les candidats. Ces nombres
n’expliquent pas pourquoi des unités se sont arrêtées.

La couverture compte des événements, pas des sessions. Ici, 120 événements correspondent à une étape, et 20
d’entre eux n’ont pas d’ID de session. Le résultat exclut ces 20 événements des
nombres de sessions. Ne les traitez pas comme 20 sessions en échec.

La première étape n’a pas de `conversion_from_previous`. La dernière étape n’a ni
`drop_off_to_next_units` ni `drop_off_to_next_rate`.

Une unité n’atteint une étape suivante que si les heures des étapes sont strictement croissantes.
Des événements avec le même horodatage ne peuvent pas valider deux étapes consécutives. La dernière
étape doit se produire dans les `conversion_window_seconds` qui suivent la première étape.

Le mode session compte des sessions, pas des personnes. Utilisez `identified_user` uniquement pour les événements
qui portent un ID de sujet opaque de type `user`. Ce mode peut relier des événements de
sessions différentes dans la fenêtre de conversion. Gardez la même unité et les
mêmes étapes quand vous comparez des résultats.

La valeur par défaut de `conversion_window_seconds` est 24 heures ou la durée de la
période, selon la plus courte. Le maximum est la durée de la période en secondes
entières, arrondie au supérieur.

### Résultats d’entonnoir vides

Une réponse vide réussie liste quand même les étapes demandées, avec des
`units` à zéro. S’il n’y a aucune unité candidate, `summary` omet `entry_rate` et
`overall_conversion_rate`. La route ne renvoie pas `404` parce qu’aucun événement
ne correspond.

Lisez `coverage` et `next_action` pour trouver la cause :

| `next_action.code` | Cause |
| --- | --- |
| `capture_product_activity` | Aucun événement classifié n’existe dans le périmètre. |
| `choose_captured_funnel_steps` | Aucun événement ne correspond à une étape demandée. |
| `sessionize_product_activity` | Des événements d’étape existent, mais aucun n’a d’ID de session. |
| `identify_product_users` | Des événements d’étape existent, mais aucun n’a de sujet de type `user`. |
| `verify_funnel_entry` | Aucune unité n’est entrée à l’étape 1. |
| `investigate_funnel_drop_off` | Des unités sont entrées, mais aucune n’a terminé toutes les étapes. |
| `compare_funnel_contexts` | Au moins une unité a terminé l’entonnoir. |

### Requêtes d’entonnoir refusées

En plus des [erreurs de périmètre communes](#shared-scope-errors), ces requêtes renvoient
`422` et `validation_failed`. Moins de 2 ou plus de 8 étapes :

```json
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
```

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Un `event_name` vide, de plus de 256 caractères ou qui contient un
caractère de contrôle renvoie
`product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`.
Une étape `interaction` doit aussi avoir un nom d’action valide. Sinon, l’erreur
est `product analytics interaction event_name must be a bounded stable action name`.

Corrigez la requête avant de la renvoyer. Ne retirez pas d’étapes et ne changez pas
l’unité d’analyse dans le seul but d’obtenir un résultat non vide.

## Analyse par événement exact et analyse automatique

La rétention et le cycle de vie acceptent deux formes de requête. Utilisez `response_version` pour
choisir la forme qui répond à votre question :

| Analyse | `response_version` | Sélecteurs d’événements |
| --- | --- | --- |
| Rétention sur des événements exacts | `1`, ou omis | Envoyez à la fois `start_event` et `return_event`. |
| Cycle de vie sur un événement exact | `1`, ou omis | Envoyez `event`. |
| Rétention ou cycle de vie automatiques | `2` | N’envoyez aucun sélecteur d’événement. |

Un sélecteur exact contient `kind` et `event_name`. `kind` vaut `page_view`,
`screen_view` ou `interaction`. Copiez `event_name` depuis
`classified_activity.top_events`. Ne devinez pas un nom d’événement à partir du libellé
d’un bouton.

Les deux formes comptent uniquement des utilisateurs : des ID de sujet opaques de type `user`. Les sujets
anonymes et les événements sans ID de sujet utilisable ne sont pas comptés comme utilisateurs.
Les réponses ne renvoient jamais d’ID de sujet.

Les intervalles fixes sont `hour`, `day`, `week` et `thirty_day`. Ce sont des durées
fixes. `thirty_day` dure 30 jours, pas un mois civil. Si vous omettez
`interval`, l’API utilise `hour` pour une période de 48 heures ou moins, et `day` pour
une période plus longue.

En plus des [erreurs de périmètre communes](#shared-scope-errors), ces requêtes renvoient
`422` et `validation_failed` :

| Cause | `error` |
| --- | --- |

corriger cette requête de lecture.

Elles omettent les sélecteurs. Un autre sélecteur peut changer le résultat sans
aucun changement dans l’activité capturée.

### Lire une série de métrique

Le premier point enregistre 10 tâches terminées, pas 10 échantillons. `rate_per_second`
divise cette variation par l’intervalle de 300 secondes. `last` est la dernière variation
enregistrée, pas la somme. Consultez la
[signification des agrégations de métriques](/fr/concepts/telemetry#read-the-metric-value).

Le type et la temporalité d’une série déterminent son `aggregation.code` et les
statistiques de chaque point. Un point omet une statistique qui ne s’applique pas. Une
statistique absente n’est pas zéro.

| Type et temporalité | `status` | `aggregation.code` | `value` | Autres statistiques |
| --- | --- | --- | --- | --- |
| `gauge`, `instant` | `ready` | `gauge_last` | Dernier échantillon | `last`, `min`, `max`, `average` |
| `counter`, `delta` | `ready` | `delta_sum` | Somme des variations | `last`, `min`, `max`, `average`, `sum`, `rate_per_second` |
| `histogram`, `delta` | `ready` | `distribution_p95` | p95 approximatif | `min`, `max`, `average`, `sum`, `p50`, `p95`, `p99` |
| Tout type, `cumulative` | `limited` | `raw_cumulative_last` | Dernier échantillon brut | `last`, `min`, `max` |
| Toute autre paire | `limited` | `raw_last` | Dernier échantillon brut | `last`, `min`, `max` |

`limited` est une réponse réussie, pas une erreur. Elle ajoute
`aggregation.limitation`, qui explique pourquoi LogBrew n’affiche que des valeurs brutes.
`ready` ne prouve pas que la capture est complète.

Lisez `coverage` avant de tracer un graphique :

- `samples` compte les échantillons de toutes les séries correspondantes, y compris les séries que
  la réponse ne renvoie pas.
- `series` compte les séries correspondantes. `returned_series` et `points` comptent les
  données renvoyées.
- `truncated` vaut `true` quand `series_limit` a retiré des séries de plus faible volume.
- `expected_buckets_per_series` est le nombre d’intervalles possibles dans la période.

N’ajoutez pas de point pour un intervalle sans échantillon. N’insérez pas de zéro et ne copiez pas
la valeur précédente. Chaque point renvoie jusqu’à 3 `trace_exemplars`. Un exemplaire
de trace relie un échantillon à une trace. Il n’explique pas tous les échantillons de
l’intervalle. Si aucun point n’a d’exemplaire de trace, `next_action.target` vaut
`metric_samples`.

### Périmètre et erreurs des séries de métriques

`project_id`, `name` et `since` sont obligatoires. `name` compte au plus 200
caractères. `interval` vaut `auto`, `1m`, `5m`, `15m`, `1h`, `6h` ou `1d`.
La valeur par défaut est `auto`, qui choisit la plus petite durée d’intervalle donnant au plus 300
intervalles. Une durée d’intervalle explicite ne peut pas exiger plus de 500 intervalles.

`group_by` vaut `none`, `service_name`, `release` ou `environment`. La valeur par défaut
est `none`. Sans regroupement, les types, unités et temporalités différents restent dans
des séries séparées. `series_limit` accepte de `1` à `20`. La valeur par défaut est `10`.

Un résultat vide renvoie `200` avec `series: []` et des `samples` à zéro. L’objet
`coverage` omet `first_seen_at` et `last_seen_at`. Cela ne
prouve pas que l’application n’a jamais envoyé la métrique. Vérifiez le projet, le
nom de la métrique et la période.

Omettre `name` renvoie `422` :

```json
{
  "error": "metric series name is required",
  "code": "validation_failed",
  "next": "send the exact metric name returned by /api/telemetry/metrics",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Des intervalles d’une minute sur sept jours renvoient `422` :

```json
{
  "error": "metric series interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

Les autres erreurs `422` sont `metric series group_by is not supported`,
`metric series interval is not supported` et
`metric series_limit must be between 1 and 20`.

complète de la session. LogBrew lit au plus 1024 événements nommés par session avant de choisir
l’ancre : les premiers événements pour `following` et les derniers pour
`preceding`. Une ancre hors de cette limite peut être omise.

### <span id="filter-the-anchor-by-property">Filtrer l’ancre par propriété</span>

Envoyez jusqu’à quatre `property_filters`, chacun avec une `key` et une `value` exactes.
Copiez la clé depuis le [catalogue de propriétés](#analytics-property-catalog). Les
filtres s’appliquent uniquement à l’ancre, pas aux événements qui l’entourent. Les valeurs sont
sensibles à la casse. Quand des filtres sont présents, `query` les reprend, et
`coverage.anchor_property_filters` indique :

| Champ | Signification |
| --- | --- |
| `context_events` | Événements d’ancre dans le périmètre, avant les filtres de propriété. |
| `property_ready_events` | Événements d’ancre qui ont toutes les clés demandées. |
| `missing_property_events` | Événements d’ancre auxquels il manque au moins une clé demandée. |
| `matching_events` | Événements d’ancre dont les valeurs correspondent à tous les filtres. |
| `nonmatching_value_events` | Événements d’ancre qui ont toutes les clés, mais une valeur différente. |
| `property_ready_rate` | `property_ready_events` divisé par `context_events`. |
| `match_rate` | `matching_events` divisé par `property_ready_events`. |

Les clés manquantes et les valeurs différentes demandent des corrections différentes. Ne les additionnez
pas. L’objet est omis quand la requête n’a aucun filtre de propriété.

### Parcours vides et requêtes refusées

Un tableau `paths` vide peut être une réponse `200` réussie. Lisez `summary`,
`coverage` et `next_action`. Ces codes distinguent les causes :
`capture_product_activity`, `choose_captured_path_anchor`,
`capture_anchor_properties`, `improve_anchor_property_coverage`,
`verify_anchor_property_values`, `sessionize_product_activity` et
`narrow_or_move_path_anchor`.

En plus des [erreurs de périmètre communes](#shared-scope-errors), ces requêtes renvoient
`422` et `validation_failed` :

| Cause | `error` |
| --- | --- |
| `depth` hors de `1` à `8` | `product analytics path depth must be between 1 and 8` |
| `path_limit` hors de `1` à `20` | `product analytics path_limit must be between 1 and 20` |
| Plus de quatre filtres de propriété | `product analytics paths accept at most four exact anchor property filters` |
| Une clé absente du catalogue de propriétés | `product analytics path property keys must be supported privacy-safe keys` |
| La même clé deux fois | `product analytics path property keys must be unique` |
| Une valeur vide, une valeur de plus de 256 caractères ou un caractère de contrôle | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

Par exemple, `depth: 0` renvoie :

```json
  "code": "validation_failed",

  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">Catalogue des propriétés d’analyse</span>

`GET /api/telemetry/analytics/properties` liste les clés de propriété des
événements produit classifiés d’un projet. Utilisez ces clés dans les
[comparaisons de segments](#analytics-segment-comparison) et les filtres d’ancre de parcours.
Le catalogue renvoie des clés et des nombres. Il ne renvoie jamais de valeurs de propriété ni
d’identités.

### Lire les clés de propriété disponibles

Envoyez `project_id` et `since`. Vous pouvez aussi envoyer `until`, `service_name`,
`release`, `environment`, `limit` et `response_version`. `limit` accepte
de `1` à `50` clés. La valeur par défaut est `20`. Envoyez `response_version=2` pour obtenir la
valeur publique de `estimation.method`.

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/properties" \
```


Une valeur de `response_version` autre que `1` ou `2` renvoie
`product analytics response_version must be 1 or 2`. LogBrew vérifie
`response_version` avant les autres valeurs.

```json

```

## <span id="analytics-segment-comparison">Comparaison de segments d’analyse</span>

`POST /api/telemetry/analytics/segments/compare` compare la fréquence à laquelle des sessions
ou des utilisateurs atteignent un événement exact, sur 2 à 4 segments d’un même projet. Un
segment sélectionne des événements selon le service, la version, l’environnement et des valeurs de propriété.
Le premier segment sert de référence.

### Définir la comparaison

Envoyez ce corps JSON avec une authentification de compte et
`Content-Type: application/json`. Ici, `basic` et `premium` sont des valeurs de forfait
de l’application d’exemple, pas des forfaits LogBrew :

```json

  "since": "2026-06-01T11:00:00Z",
```

`target` et `segments` sont obligatoires. `analysis_unit` vaut `session` ou
`identified_user`. La valeur par défaut est `session`, qui compte des sessions, pas
des personnes. `interval` accepte les mêmes valeurs que la vue d’ensemble. La valeur par défaut est
`auto`.

Chaque segment exige une `key` unique, un `label` et un ensemble de filtres différent :

- `key` : de 1 à 32 octets. Commencez par une lettre ASCII minuscule ou un chiffre. Utilisez
  uniquement des lettres ASCII minuscules, des chiffres, `_` et `-`.
- `label` : de 1 à 80 caractères, sans caractère de contrôle.
- `service_name`, `release`, `environment` : facultatifs. Chaque valeur compte de 1 à 256
  caractères, sans caractère de contrôle.
- `property_filters` : de 0 à 4 filtres. Chaque clé peut apparaître une fois par segment.
  Un événement doit correspondre à tous les filtres du segment. Les valeurs sont sensibles à la casse,
  comptent de 1 à 256 caractères, et LogBrew retire les espaces au début et à la fin.

Un segment sans filtre sélectionne toute l’activité classifiée du projet sur la
période. Les segments peuvent se chevaucher. Un label ou une clé différents ne rendent pas valides deux
ensembles de filtres identiques.

### Lire les taux et les écarts

`eligible_units` estime les sessions ou les utilisateurs qui ont une activité classifiée dans
le segment. `reached_units` estime combien d’entre eux ont atteint la cible.
`reach_rate` vaut `reached_units` divisé par `eligible_units`. Les événements sans
l’ID de l’unité sélectionnée ne comptent pas dans ces unités.

Le taux du segment de référence est de 20 %. Le taux du segment premium est de 30 %. L’écart est de 10
points de pourcentage. La hausse relative est de 50 %, pas de 10 %. De petites erreurs décimales
viennent de l’arithmétique à virgule flottante. Arrondissez les taux pour l’affichage, mais calculez
avec les valeurs renvoyées. Le segment de référence n’a pas de
`comparison_to_baseline`. La hausse relative est omise quand le taux d’atteinte du segment de
référence vaut zéro.

Dans `query`, un filtre de segment que vous n’avez pas envoyé vaut `null`. Une liste
`property_filters` vide est omise.

`coverage.property_filters` a les mêmes champs que la
[couverture des filtres d’ancre de parcours](#filter-the-anchor-by-property). Ici,
`matching_events` est égal à `classified_events`. Gardez séparées les clés manquantes et
les valeurs différentes. Les segments peuvent se chevaucher, et une session peut apparaître dans
plusieurs intervalles. N’additionnez pas les nombres d’unités entre segments ou entre intervalles.

La comparaison est descriptive. `confidence.causal_inference` vaut
`not_established` et `confidence.statistical_significance` vaut `not_tested`.
Un taux de 30 % contre 20 % ne montre pas qu’un forfait a entraîné plus de paiements.

### Erreurs de comparaison de segments

En plus des [erreurs de périmètre communes](#shared-scope-errors), ces requêtes renvoient
`422` et `validation_failed` :

| Cause | `error` |
| --- | --- |
| Moins de 2 ou plus de 4 segments | `product analytics segment comparison requires two through four segments` |
| Deux segments avec la même clé | `product analytics segment keys must be unique` |
| Deux segments avec les mêmes filtres | `product analytics segment filters must be unique` |
| Une clé qui ne compte pas de 1 à 32 octets autorisés | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| Un label vide, trop long ou qui contient un caractère de contrôle | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| Une valeur de filtre avec un caractère de contrôle | `product analytics segment filters must be control-free` |
| Plus de quatre filtres de propriété dans un segment | `product analytics segments accept at most four exact property filters` |
| Une clé absente du catalogue de propriétés | `product analytics segment property keys must be supported privacy-safe keys` |
| La même clé de propriété deux fois dans un segment | `product analytics segment property keys must be unique within each segment` |
| Une valeur de propriété vide, trop longue ou qui contient un caractère de contrôle | `product analytics segment property values must be non-empty, control-free, and at most 256 characters` |
| Une valeur de `response_version` autre que `1` ou `2` | `product analytics response_version must be 1 or 2` |

Les erreurs de `interval` sont les mêmes que les [erreurs de la vue d’ensemble](#overview-errors).

Par exemple, deux segments avec des clés différentes et des filtres identiques renvoient :

```json

  "code": "validation_failed",

  "next_action": { "code": "fix_request", "target": "request" }
}
```

Un autre label ou un autre ordre des filtres de propriété ne change pas
les événements sélectionnés. Un échec de validation n’est pas une preuve qu’aucun événement
ne correspond.

Une requête `GET` renvoie `405` :

```json
{
  "error": "Method not allowed",
  "code": "method_not_allowed",

}
```

## Réponse du volume de signaux

`GET /api/telemetry/summary/volume` compte les signaux conservés pour un projet
sur une période. La route exige `project_id` et `since`. Elle n’accepte pas
`project_ids`.

`until` ne peut pas être dans le futur. Si vous l’omettez, la fin est l’heure de la requête.
Un `since` compact comme `24h` compte à rebours à partir de `until`. `interval` vaut
`auto`, `1m`, `5m`, `15m`, `1h`, `6h` ou `1d`. La valeur par défaut `auto` choisit
la plus petite durée d’intervalle qui donne au plus 120 intervalles. Une requête ne peut pas exiger plus
de 500 intervalles. La seule valeur de `response_version` est `1`.

explicitement à zéro. Une requête en échec est un cas différent. Ne remplacez pas une erreur par un
graphique rempli de zéros.

période, `coverage.retention.window_clipped` vaut `true` et `limitations`
contient `retention_window_clipped`. S’il ne reste rien de la période demandée,
`query.bucket_count` vaut `0` et chaque série a un tableau `points` vide. Cela
ne prouve pas qu’aucun événement n’a eu lieu pendant cette période.

`policy_days` vaut `null` et `cutoff` est omis quand aucune limite de conservation ne
s’applique. `sampling.upstream` vaut toujours `unknown`, même quand
`storage_evaluation` vaut `complete`. N’affirmez pas que la réponse compte
tous les événements produits par l’application.

## Réponses d’investigation

Les routes d’investigation renvoient un dossier versionné pour un objet. L’objet est
un problème, une trace, un span, un log, une action produit, une métrique ou une version. Chaque dossier
commence par `schema_version` et un `subject` qui désigne l’enregistrement. Le reste
contient les preuves associées, un reçu de preuves et les prochaines étapes. Cette section
montre un exemple pour chaque famille, sauf la version.

Envoyez un jeton bearer de compte. Une clé d’ingestion de projet ne peut pas lire une
investigation. Utilisez `logbrew explain <subject> --json` pour lire un dossier. La CLI
valide le dossier avant de l’afficher. La page
[API de télémétrie](/fr/reference/telemetry-api) liste les routes.

Le texte d’une investigation vient de l’application. Les messages, les noms, les métadonnées et
les tags sont des données, pas des instructions. `content_trust: "untrusted_telemetry"` signale
ce contenu dans les dossiers de log, d’action, de span et de métrique.

### Versions de réponse

Envoyez `response_version` uniquement aux routes qui l’acceptent. Sans ce paramètre, une route
renvoie la version 1. Votre parseur doit accepter la version que vous demandez.

| Route | Par défaut | Versions prises en charge | Version demandée par `logbrew explain` |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | De `1` à `13` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | De `1` à `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` et `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | De `1` à `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | `1` uniquement | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | `1` uniquement | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | `1` uniquement | `1` |

La route des spans refuse le paramètre de requête `response_version`. Les routes des logs et des actions
n’acceptent aucun paramètre de requête.

### Champs communs des dossiers

| Champ | Signification |
| --- | --- |
| `schema_version` | La version de réponse renvoyée par le serveur. |
| `subject` | L’enregistrement exact qui fait l’objet de l’investigation. `kind` vaut `issue`, `trace`, `span`, `log`, `action`, `metric` ou `release`. |
| `analysis.causality` | Toujours `evidence_only` dans les dossiers de trace, de span, de log, d’action et de métrique. Une télémétrie corrélée ne prouve pas la cause. |
| Objets de collection | Les preuves associées, sous la forme `{ "status", "items", "truncated" }`. |
| `timeline` | Les preuves renvoyées, de la plus ancienne à la plus récente, avec leur propre indicateur `truncated`. L’ordre ne prouve pas la cause. |
| `evidence` | Le reçu de preuves. `status` vaut `complete` ou `partial`. |
| `next_actions` | Les lectures suggérées, dans l’ordre de `priority`, à partir de `1`. Elles n’ont pas été exécutées. |

Chaque collection associée indique un `status` de disponibilité :

| Statut | Signification | Comportement du client |
| --- | --- | --- |
| `available` | La lecture a abouti et a renvoyé des éléments. | Affichez les éléments et l’indicateur `truncated`. |
| `not_linked` | L’objet n’a pas d’identifiant pour ce lien, par exemple un ID de trace. | Expliquez que le lien manque. N’en construisez pas un à partir des horodatages. |
| `not_found` | La lecture a abouti et n’a trouvé aucune preuve conservée. | Affichez un résultat vide. |
| `unavailable` | La lecture facultative a échoué. L’objet reste valide. | Gardez l’objet visible. Réessayez plus tard. N’affichez pas zéro élément comme résultat. |

Le reçu de preuves contient quatre listes ordonnées de noms de champs stables :
`captured_fields`, `missing_fields`, `redacted_fields` et
`truncated_fields`. `status` vaut `complete` uniquement quand les trois dernières listes sont
vides. Une donnée masquée n’est pas une donnée manquante. Une donnée tronquée n’est pas une donnée complète.
Ne complétez pas une valeur masquée ou tronquée.

### Limites des investigations

Ces limites bornent une réponse. Un indicateur `truncated` ou une entrée de `truncated_fields`
montre qu’une limite a omis des données.

| Preuves | Limite |
| --- | --- |
| Éléments associés dans une collection | 20 |
| Spans conservés lus pour une trace | 1 000 |
| Éléments de la chronologie | 50 pour les dossiers de log, d’action et de span. 100 pour les dossiers de trace et de métrique. |
| Attributs structurés, propriétés et métadonnées | 64 valeurs scalaires, 4 niveaux d’objets ou de tableaux, 16 éléments par tableau, 512 caractères par chaîne |
| Période de corrélation | 5 minutes avant et après un log, une action ou l’occurrence de problème sélectionnée. Pour une trace ou un span, 5 minutes avant le début et après la fin, 24 heures au maximum. |

La section de chaque famille liste ses propres limites.

### Réponse d’investigation d’un problème

Utilisez `GET /api/telemetry/issues/{issue_id}/investigation` pour lire les preuves
d’une occurrence d’un problème groupé. Le guide
[Investiguer un problème](/fr/guides/investigate-an-issue) montre comment lire
les preuves dans l’ordre. Demandez la version 13 :

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

Les paramètres de requête sont `response_version`, `selection` et `occurrence_id`.
`selection` vaut `recommended`, `first` ou `latest`. Les valeurs sont
sensibles à la casse. Dans les versions 2 à 13, un sélecteur omis utilise `recommended`.
La version 1 renvoie la dernière occurrence conservée et n’accepte aucun sélecteur.
Les filtres de la liste des problèmes ne s’appliquent pas à cette lecture.

#### Erreurs de requête d’investigation d’un problème

Utilisez soit `selection`, soit `occurrence_id`. N’envoyez pas les deux, même quand ils
sélectionnent la même occurrence :

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 13 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | Cause | Correction |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | La requête contient les deux sélecteurs. | Gardez un seul sélecteur. |
| `422` | `issue occurrence selection requires response_version=2 through 13` | La requête contient un sélecteur avec la version 1, ou sans version. | Envoyez `response_version=13`. Gardez le sélecteur. |
| `422` | `issue investigation response_version must be 1 through 13` | La version est hors limites. | Envoyez une version prise en charge. |
| `422` | `invalid query parameters` | Un paramètre inconnu, un UUID invalide, une version qui n’est pas un entier ou une valeur de `selection` inconnue. | Corrigez la [requête](/fr/reference/api-errors#invalid-query-parameters). |
| `404` | `issue occurrence not found` | L’occurrence ne fait pas partie de l’historique conservé de ce groupe. | Copiez l’ID d’occurrence depuis les événements de ce problème. N’utilisez pas `latest` ou `recommended` à la place sans accord. |
| `404` | `issue not found` | Aucun projet lisible ne contient ce problème. | Vérifiez le compte et l’UUID du problème. N’envoyez pas un UUID d’occurrence comme ID de problème. |

Une occurrence introuvable ne signifie pas que le problème est introuvable. Une réponse `404`
n’indique pas si un autre compte peut lire le problème.

### Réponse d’investigation d’un span

Utilisez `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` pour
lire une opération d’une trace. Envoyez `project_id`, `environment` et `release`.
Les trois sont obligatoires. Copiez-les depuis le span sélectionné. N’envoyez pas l’`id`
de la ligne du span comme `span_id`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

conservé. Une référence `unavailable` est une lecture en échec, pas un nombre égal à zéro.

racine. Cela ne prouve pas que LogBrew a conservé tous les spans de la requête.

### Réponse d’investigation d’un log

Utilisez `GET /api/logs/{log_id}/investigation` pour lire un log et ses preuves
associées. Cette route n’accepte aucun paramètre de requête. Copiez l’ID du log depuis une liste de logs.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

La lecture peut renvoyer des preuves hors des filtres de la liste des logs. Les lectures
associées utilisent le projet, l’environnement et la version du log, et les 5 minutes avant
et après le log. Les logs proches utilisent aussi le même service. Ils n’ont pas besoin d’un
ID de trace. Les lectures par trace exacte exigent l’ID de trace du log et peuvent inclure d’autres
services. Le résumé de trace utilise le même ID de trace et le même périmètre, sans la
période.

### Réponse d’investigation d’une action

Utilisez `GET /api/telemetry/actions/{action_id}/investigation` pour lire une action
produit, son statut signalé et ses preuves associées. Cette route n’accepte aucun paramètre de
requête. Les lectures associées utilisent la même période et les mêmes périmètres qu’une investigation de log.

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/telemetry/actions/$ACTION_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

`correlations`, `timeline` et `next_actions` utilisent les formes de l’investigation
de log. Les actions associées excluent l’action qui fait l’objet de l’investigation.

### Réponse d’investigation d’une métrique

Utilisez `GET /api/telemetry/metrics/investigation` pour lire un nom de métrique dans un
projet sur une période. La réponse contient la série actuelle, une comparaison
avec la période précédente de même durée, le dernier échantillon, les exemplaires
de trace et les déploiements terminés. La version 2 ajoute la description de la métrique
tirée du dernier échantillon conservé. La version 1 indique toujours
`description_status: "not_captured"`.

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`, `name` et `since` sont obligatoires. `since` est inclus et
`until` est exclu. `until` vaut par défaut l’heure actuelle. La comparaison lit aussi la
période précédente de même durée.

| `422` | `metric investigation response_version must be 1 or 2` | Omettez `response_version` ou envoyez `2`. |
| `422` | `metric series project_id is required` | Envoyez l’ID d’un projet lisible. |
| `422` | `metric series name is required` | Copiez le nom depuis la liste des métriques. |
| `422` | `metric series since is required` | Envoyez une valeur comme `24h` ou un horodatage RFC 3339. |

| `422` | `metric series interval would exceed 500 buckets` | Utilisez `interval=auto` ou une durée d’intervalle plus large. |
| `422` | `metric series_limit must be between 1 and 20` | Envoyez une valeur de 1 à 20. |

`none`, `service_name`, `release` ou `environment`. Les autres valeurs renvoient
`422`.

### Erreurs d’investigation

| HTTP | Route | `error` |
| --- | --- | --- |
| `404` | Log | `log not found` |
| `404` | Action | `action not found` |
| `404` | Trace | `trace not found` |
| `422` | Trace | `trace investigation response_version must be 1, 2, or 3` |
| `400` | Log, action, problème | `invalid URL path parameters` quand l’ID du chemin n’est pas un UUID |
| `422` | Problème, trace, span, métrique | `invalid query parameters` pour un paramètre inconnu ou une valeur du mauvais type |

Une réponse `404` signifie qu’aucun projet lisible ne contient l’enregistrement. Chaque route renvoie aussi
`401` sans authentification valide et `405` pour une autre méthode que `GET`.
Consultez [Erreurs de l’API](/fr/reference/api-errors) pour les réponses
[ressource introuvable](/fr/reference/api-errors#resource-not-found),
[chemin invalide](/fr/reference/api-errors#invalid-path-value),
[échec d’authentification](/fr/reference/api-errors#authentication-failure) et
[méthode non prise en charge](/fr/reference/api-errors#unsupported-method).

Une lecture facultative de preuves peut échouer au sein d’une réponse `200 OK`. La collection
indique alors `unavailable`. Ne l’affichez pas comme `not_found` ni comme zéro enregistrement.

## <span id="severity-values">Valeurs de gravité</span>

Les valeurs de gravité visibles par l’utilisateur sont `info`, `warning`, `error` et `critical`.
Les SDK et les runtimes peuvent envoyer des alias courants comme `trace`, `debug`, `warn` ou
`fatal`. Les réponses REST et en direct renvoient toujours la valeur canonique. Par
exemple, LogBrew accepte `warn` en entrée et renvoie `warning`. L’ingestion refuse
les valeurs de gravité inconnues.

| Alias | Valeur canonique |
| --- | --- |
| `trace`, `debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">Réponses des règles de gravité</span>

Une règle de gravité change la façon dont LogBrew affiche un log ou un problème. Elle ne
change pas la gravité capturée par l’application. Les logs et les problèmes renvoient un
objet `triage` :

| Champ | Signification |
| --- | --- |
| `effective_severity` | La gravité à afficher. Sans règle, elle est égale à `severity`. |
| `ignored` | `true` quand une règle de log ignore le log, ou quand le problème est archivé. |
| `rule_applied` | `true` quand une règle de gravité ou l’état ignoré s’applique. `false` est la valeur par défaut, pas une donnée manquante. |

Utilisez `triage.effective_severity` pour l’affichage. Gardez `severity` comme valeur
capturée. Par défaut, la liste des logs omet les logs ignorés. Envoyez `status=ignored` ou
`status=all` sur `GET /api/logs` pour les inclure.

Le compte doit avoir l’autorisation de gérer les problèmes du projet. L’accès en lecture
ne suffit pas. Sans cette autorisation, un changement de règle renvoie `403` avec
`code: forbidden`.

### Modifier une règle de log

`PUT /api/logs/{log_id}/triage-rule` définit la règle pour ce log et pour les logs
suivants qui ont la même signature. Le corps exige à la fois `severity` et `ignored` :

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

Une réponse `200 OK` contient le [log](#log-response) complet. Sa valeur
`severity` reste `warning`. Son objet `triage` montre la règle :

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

Cet extrait ne montre que les champs modifiés. Dans la requête, `severity` vaut
`source`, `info`, `warning`, `error` ou `critical`. `source` rétablit la
gravité capturée. Cette valeur ne réactive pas un log ignoré. Pour afficher de nouveau le
log, envoyez `"ignored": false`.

### Modifier une règle de problème

`PUT /api/telemetry/issues/{issue_id}/triage-rule` définit la gravité affichée
d’un problème groupé et de ses occurrences suivantes. Le corps accepte uniquement
`severity` :

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

Une réponse `200 OK` contient le [problème](#issue-response) complet en
version 1. Les valeurs capturées de `severity` et de `status` ne changent pas :

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

Cet extrait ne montre que certains champs. Une règle ne résout pas, n’archive pas et ne
rouvre pas un problème. Utilisez pour cela le [changement de statut](#issue-status-response-examples).
Une priorité dérivée suit la nouvelle gravité effective. Lisez le problème
avec `response_version=2` ou `3` pour la voir.

Une gravité non prise en charge renvoie `422` :

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Un champ de corps inconnu, comme `status` dans une règle de problème, renvoie `422` avec
`code: invalid_json`. Un log ou un problème introuvable ou illisible renvoie `404` avec
`code: not_found`. Si la réponse est perdue, relisez le log ou le problème
avant de renvoyer la règle.

## Format des réponses d’erreur

Les erreurs applicatives renvoient une enveloppe JSON. Cet exemple montre une requête
refusée. Le texte de `error` et de `next` dépend de l’erreur :

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Utilisez `code` pour les branches du programme et `next_action` pour l’automatisation. Montrez `error`
et `next` aux personnes sous forme de texte simple. N’analysez pas leur formulation. Certaines erreurs
ajoutent des champs, comme `limit`, `reset_at` ou `retry_after_seconds`. Une réponse
sans corps JSON n’a pas de `code` LogBrew. Consultez
[Erreurs de l’API](/fr/reference/api-errors) pour tous les codes.

## Lire les données avec la CLI

La CLI lit les mêmes routes et renvoie le même JSON avec `--json`. Commencez
large, puis affinez :

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

Ajoutez `--pagination cursor` pour obtenir l’enveloppe avec curseur. La CLI demande la version 4
de la réponse de problème. Consultez [Lire la page suivante](/fr/reference/cli#read-the-next-page)
et [Suivi en direct](/fr/reference/cli#live-watch).

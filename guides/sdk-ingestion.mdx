Install the LogBrew SDK package for your runtime. The SDK formats events and
delivers them. The package guide lists its event types, limits, and retry
behavior.

Do these steps for each integration:

1. Install the SDK package for your runtime.
2. Keep the project-scoped ingest key outside source control.
3. Set stable service, environment, and release values.
4. Send one safe test event from the application.
5. Read the delivery result. Then find the event in LogBrew.

An accepted batch reached the LogBrew API. Filters can still hide its events.
Select the correct project and time range. Then match the service,
environment, release, and signal type.

Before you enable capture, [select and test approved fields](/guides/safe-capture).
To populate Analytics, follow [Product event capture](/guides/product-events).

## <span id="item-types">Signals and shared context</span>

The first five cards are signals. Release and environment are context for
those signals. They are not a separate event type.

<CardGroup cols={2}>
  <Card title="log" icon="file-text">
    A structured message with severity, source, time, and safe context.
  </Card>

  <Card title="trace_span" icon="route">
    One timed operation, linked to its trace by trace and span IDs.
  </Card>

  <Card title="issue" icon="bug">
    A captured failure, its severity, and the error details that the app sent.
  </Card>

  <Card title="action" icon="mouse-pointer-click">
    An action in your app, with optional subject, session, and safe properties.
  </Card>

  <Card title="metric" icon="chart-line">
    One numeric measurement with a name, kind, value, unit, and temporality.
  </Card>

  <Card title="release and environment" icon="tags">
    The code version and environment attached to later events in the same SDK scope.
  </Card>
</CardGroup>

## Severity values

Use `info`, `warning`, `error`, or `critical` for logs and issues. SDKs and
runtimes can send aliases such as `trace`, `debug`, `warn`, or `fatal`.
LogBrew normalizes accepted aliases to the canonical values.

### Node.js request tracing

For request-root trace correlation, use `@logbrew/sdk` 0.1.16 or newer and
`@logbrew/node` 0.1.11 or newer.

Express requires `@logbrew/express` 0.1.5 or newer. Fastify and NestJS require
their LogBrew package at 0.1.6 or newer.

These integrations create or continue one request span. The span name uses
the matched route template. Logs, issues, actions, and metrics inside the
request inherit its trace and span context. A newer package does not add
context to events that were sent before the upgrade.

The default request integration does not capture request or response bodies,
query strings, arbitrary headers, or raw `traceparent` values.

### ASP.NET Core

CLI v0.1.55 or newer detects .NET 10 projects that use
`Microsoft.NET.Sdk.Web`. Preview the setup plan from the project root. This
command does not change your files:

```bash
logbrew setup --json
```

The released plan installs the host integration:

```bash
dotnet add package LogBrew.AspNetCore --version 0.1.2
```

Set `LOGBREW_SERVER_API_KEY`, `LOGBREW_SERVICE_NAME`,
`LOGBREW_ENVIRONMENT`, and `LOGBREW_RELEASE` outside source control. Register
LogBrew with the host and place its middleware after routing:

```csharp
using LogBrew;

var builder = WebApplication.CreateBuilder(args);
builder.AddLogBrew();

var app = builder.Build();
app.UseRouting();
app.UseLogBrew();
app.MapGet("/", () => "ok");
app.Run();
```

Without `LOGBREW_SERVER_API_KEY`, both registration calls are safe no-ops. The
[ASP.NET Core NuGet package](https://www.nuget.org/packages/LogBrew.AspNetCore/0.1.2)
identifies the released host integration. Its public package guide covers host
lifecycle, request capture, issue capture, privacy limits, and recovery.

### Java with Maven or Gradle

CLI v0.1.54 or newer detects `pom.xml`, `build.gradle`, and
`build.gradle.kts`. Preview the setup plan from the project root. This command
does not change your files:

```bash
logbrew setup --json
```

For Maven, add the released package:

```xml
<dependency>
  <groupId>co.logbrew</groupId>
  <artifactId>logbrew-sdk</artifactId>
  <version>0.1.10</version>
</dependency>
```

For Gradle Kotlin DSL, add the same Maven Central artifact:

```kotlin
implementation("co.logbrew:logbrew-sdk:0.1.10")
```

Use Java 11 or newer.

Spring Boot 3 and 4 applications can expose an app-owned `LogBrewClient` bean.
It enables optional request, exception, HTTP client, JDBC, and cache
integrations.

Spring Kafka capture is explicitly opt in with
`logbrew.kafka.enabled=true`. It uses the application's existing Spring Kafka
dependency and client bean.

The [Java SDK artifact on Maven Central](https://central.sonatype.com/artifact/co.logbrew/logbrew-sdk/0.1.10)
identifies the released package. Its public guide covers bounded HTTP delivery,
shutdown, logging, Spring configuration, Kafka correlation, and privacy limits.

### C++ with CMake

The C++ SDK requires C++17 and CMake 3.16 or newer. CLI v0.1.39 or newer
detects a root `CMakeLists.txt`. Run `logbrew setup --json` to preview this
setup plan without changing your files:

```cmake
include(FetchContent)
FetchContent_Declare(
  logbrew
  GIT_REPOSITORY https://github.com/LogBrewCo/sdk.git
  GIT_TAG cpp/logbrew-cpp/v0.2.3
  GIT_SHALLOW TRUE
  SOURCE_SUBDIR cpp/logbrew-cpp
)
FetchContent_MakeAvailable(logbrew)

target_link_libraries(your_app PRIVATE LogBrew::LogBrew)
```

The core target is dependency-free. To send batches through the optional
libcurl transport, replace the final `FetchContent_MakeAvailable` call and
target link above with:

```cmake
set(LOGBREW_BUILD_HTTP_TRANSPORT ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(logbrew)
target_link_libraries(your_app PRIVATE LogBrew::HttpTransport)
```

Configure the application. Then build it to test the selected SDK version:

```bash
cmake -S . -B build &&
cmake --build build
```

For builds that cannot fetch the SDK monorepo, use the scoped
`logbrew-cpp-0.2.3.tar.gz` asset from the
[C++ 0.2.3 release](https://github.com/LogBrewCo/sdk/releases/tag/cpp/logbrew-cpp/v0.2.3).
The extracted package supports `cmake --install` and
`find_package(LogBrew 0.2.3 CONFIG REQUIRED)`. Its package guide covers typed
context, issue evidence, span events, metrics, actions, and HTTP delivery.

## JavaScript queue tracing

Node queue integrations are separate npm packages. Install the base LogBrew
JavaScript packages, the integration package, and the queue or broker client
your app already uses.

| Queue or broker | Install |
| --- | --- |
| BullMQ | `npm install @logbrew/sdk @logbrew/node @logbrew/bullmq bullmq` |
| KafkaJS | `npm install @logbrew/sdk @logbrew/node @logbrew/kafkajs kafkajs` |
| RabbitMQ / amqplib | `npm install @logbrew/sdk @logbrew/node @logbrew/amqplib amqplib` |
| Amazon SQS | `npm install @logbrew/sdk @logbrew/node @logbrew/aws-sqs @aws-sdk/client-sqs` |

Use these packages for explicit, app-owned trace correlation around the queue
calls you select. LogBrew does not own your broker connection, create queues, or
globally patch every client by default.

<Warning>
  Keep queue payloads, arbitrary message headers, broker URLs, and session or
  account bearer values out of SDK configuration. Use project-scoped server
  ingest configuration from LogBrew.
</Warning>

## <span id="required-envelope-fields">Direct native envelope</span>

Use `POST /api/telemetry/ingest` only for a custom client that no public
LogBrew SDK supports. Public SDKs use their own batch format. This endpoint
does not accept that format.

Send 1 to 512 items in one native envelope. All items in one envelope share
the project, service, release, environment, and optional trace context.

| Field | Required | Notes |
| --- | --- | --- |
| `project_id` | Yes | UUID for the LogBrew project. It must match the project of the ingest key. |
| `environment` | Yes | Deployment environment. 64 characters or fewer, with no whitespace, `/`, or `\`. The value `None` is rejected. |
| `release` | Yes | Code version. 200 characters or fewer, with no `/`, `\`, tabs, or newlines. It cannot be `.` or `..`. |
| `service_name` | Yes | Logical service name, such as `checkout-api`. It must not be blank. |
| `sdk_name` | Yes | SDK or custom-client identifier. |
| `sdk_version` | Yes | SDK or custom-client version. |
| `items` | Yes | 1 to 512 `log`, `trace_span`, `issue`, or `action` items. |
| `trace_id` | No | Trace ID shared by correlated envelope items. Required when an item has `span_id`. |

### Item fields

Each item has a `type` and a `data` object. A log item uses `level`. An issue
item uses `severity`. Both accept the values in [Severity values](/concepts/telemetry#severity-values).

| Item field | Applies to | Notes |
| --- | --- | --- |
| `id` | All items | Optional client event ID. 1 to 200 characters, unique in the envelope. |
| `span_id` | `log`, `issue`, `action` | Optional. 16 hexadecimal characters, not all zeros. The envelope must have `trace_id`. |
| `name` | `action` | Required. 64 UTF-8 bytes or fewer. It must not start with `$`, start or end with whitespace, or contain control or invisible formatting characters. |

Send an `id` with each item when your client can retry. When a retry sends
an accepted item again with the same `id` and content, LogBrew does not store
it again. The response counts that item in `already_accepted`.

### Example request

Save the JSON below as `telemetry-envelope.json`. Replace the example project
ID with the exact project ID for your ingest key. Set the timestamps to the
test event's current UTC time. Use your own service and release values.

```json telemetry-envelope.json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "environment": "production",
  "release": "api@1.2.3",
  "service_name": "checkout-api",
  "sdk_name": "custom-native-client",
  "sdk_version": "1.0.0",
  "items": [
    {
      "type": "log",
      "data": {
        "id": "evt_example_log_0001",
        "level": "warning",
        "message": "checkout retry scheduled",
        "source": "runtime",
        "attributes": { "route": "/checkout" },
        "occurred_at": "2026-06-01T12:00:00Z"
      }
    },
    {
      "type": "action",
      "data": {
        "id": "evt_example_action_0001",
        "name": "checkout_failed",
        "distinct_id": "user_123",
        "session_id": "session_456",
        "occurred_at": "2026-06-01T12:00:00Z",
        "properties": { "cart_total": 4200 }
      }
    }
  ]
}
```

Load the project-scoped ingest value into `LOGBREW_INGEST_BEARER` through
your protected configuration. Do not print it or use an account credential.
The following command sends the file once. It requires curl 7.76.0 or newer:

```bash
: "${LOGBREW_INGEST_BEARER:?load the project-scoped ingest key}" &&
curl --fail-with-body --silent --show-error \
  "https://api.logbrew.co/api/telemetry/ingest" \
  -H "Authorization: Bearer $LOGBREW_INGEST_BEARER" \
  -H "Content-Type: application/json" \
  --data-binary @telemetry-envelope.json \
  --write-out '\nHTTP %{http_code}\n'
```

Read the HTTP status and body. `--fail-with-body` preserves an error body and
returns a nonzero exit status for HTTP errors. A network failure or timeout
does not tell you whether LogBrew accepted the request. Send the same file
again only when its items have `id` values. Without `id` values, a second
send can store the items two times.

### Response

A successful request returns `200` with counts of the new items by stream.
`already_accepted` counts items that an earlier request already delivered.

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

### Errors

An invalid or revoked ingest key returns `401`. A key for a different project
also returns `401`:

```json
{
  "error": "Invalid ingest key",
  "code": "ingest_key_invalid",
  "next": "create a project-scoped ingest key, then retry ingestion with that key",
  "next_action": {
    "code": "configure_ingest_key",
    "target": "project_ingest_key"
  }
}
```

Use a project-scoped ingest key. Do not replace it with an account
credential. An artifact key cannot send telemetry.

An envelope that breaks a field rule returns `422` with code
`validation_failed`. The `error` field names the rule. The `next` field tells
you how to fix the request. For example, `"items": []` returns:

```json
{
  "error": "native telemetry envelope cannot be empty",
  "code": "validation_failed",
  "next": "send at least one native telemetry item",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

Do not send an envelope when there are no events. An envelope with more than
512 items returns `422` with the error
`native telemetry envelope exceeds the item limit`. Split it into batches of
512 or fewer items. Keep the project and shared context in each batch.

For usage limits, rate limits, and service failures, follow the returned
`code` in [API errors](/reference/api-errors).

<Tip>
  Set release and environment in SDK setup. Create or continue trace context
  for each operation. Do not reuse one trace ID for unrelated work.
</Tip>

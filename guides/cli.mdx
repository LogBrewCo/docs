The LogBrew command line interface (CLI) reads logs, issues, traces, and
actions from a terminal. It can also update issue status. Use `--json` for
structured output to scripts and AI agents.

Replace each angle-bracket placeholder before you run a command. Use project,
issue, and trace IDs that LogBrew returned.

## Install the CLI

Select one installation method.

macOS or Linux:

```bash
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/LogBrewCo/cli/releases/latest/download/logbrew-cli-installer.sh | sh
```

Windows (PowerShell):

```powershell
powershell -ExecutionPolicy Bypass -c "irm https://github.com/LogBrewCo/cli/releases/latest/download/logbrew-cli-installer.ps1 | iex"
```

Homebrew:

```bash
brew install LogBrewCo/tap/logbrew
```

npm:

```bash
npm install -g logbrew-cli@latest
```

Cargo:

```bash
cargo install logbrew-cli
```

On Windows, you can also install the MSI from the
[latest release](https://github.com/LogBrewCo/cli/releases/latest).

<Note>
  Cargo needs Rust 1.87 or newer. The other methods install a native binary
  and do not need Rust.
</Note>

## Update the CLI

The CLI does not update itself. Use the same method that installed it.

Homebrew:

```bash
brew update && brew upgrade LogBrewCo/tap/logbrew
```

npm:

```bash
npm install -g logbrew-cli@latest
```

Cargo:

```bash
cargo install --locked logbrew-cli
```

For the shell or PowerShell installer, run the installer again.

Then read the version. Compare it with the
[latest release](https://github.com/LogBrewCo/cli/releases/latest):

```bash
logbrew version --json
```

The JSON gives `ok`, `name`, `version`, `binary`, `os`, and `arch`.

## Sign in and verify the session

Read the account for the current terminal:

```bash
logbrew status --json
logbrew whoami --json
```

If `whoami` shows the expected account, continue. If not, sign in. A person
completes the provider login in the browser. A coding agent must ask a person
to do this step.

```bash
logbrew login --provider github
```

The provider is `github` (default), `gitlab`, `bitbucket`, or `google`. Use `--no-open`
to print the login URL without opening a browser. `--json` prints the login
URL as JSON and does not open a browser.

After login, run `status` and `whoami` again. Do not put account credentials in
a prompt, report, or source file.

## <span id="set-up-a-project">Set up a project</span>

Go to the directory that contains the package or build manifest of the app. In
a monorepo, select one app or service. Then run:

```bash
logbrew setup
```

Setup selects or creates a project, installs the SDK, writes the ingest key to
the env file, and adds the init code. It shows each file change and asks you
to confirm. Then it sends a test event that LogBrew reads back. See
[Set up with one command](/quickstart#set-up-with-one-command).

Agents and scripts add `--yes --json`. These options add more steps:

| Option | Effect |
| --- | --- |
| `--mcp` | Add the hosted MCP server to the project configuration of Claude Code, Cursor, and VS Code. |
| `--project <project_id>` | Use an existing project. |
| `--sample-data` | Load sample data into a project that has no events. |

## <span id="plan-sdk-setup">Plan SDK setup</span>

To read the setup plan without changes, run:

```bash
logbrew setup --json
```

Read `detected`, `install_ready`, `install_plan`, and `next`. The plan gives
the runtime, framework, package manager, and install command. This command
does not install packages or change files. `logbrew init`, `install`,
`configure`, and `sdk` give the same plan.

<Warning>
  Put a project ingest key in the SDK configuration. Never use an account
  credential as an SDK key. Keep ingest keys out of source control.
</Warning>

See [Send SDK telemetry](/guides/sdk-ingestion) for runtime-specific steps. Run
`logbrew examples` for a short list of common commands.

## Read, create, and configure projects

List the active projects in your account:

```bash
logbrew projects --json
```

Select a project ID from the result. Use it for keys and reads.

To create an ingest key for an existing project, select a new file outside
source control. The CLI writes the key to that owner-only file. It does not
print the key or the file path.

```bash
logbrew projects keys create "<project_id>" --ingest-key-file "<private_key_file>" --json
```

| Flag | Value |
| --- | --- |
| `--kind` | `sdk` (default), `browser`, `server`, `cli`, `artifact`, or `read`. An `artifact` key uploads source maps and native debug files. It cannot send telemetry. A `read` key reads the telemetry of 1 project and cannot send it. See [Project key kinds](/guides/verify-setup#project-key-kinds). |
| `--label` | A name for the key, up to 120 characters. The default is `CLI-created SDK key`. |

The JSON result has `status`, `project_id`, `ingest_key`, `checks`, and
`next`. `ingest_key` has the key `id`, `label`, `kind`, `created_at`, and
`expires_at`. To replace a key, see [Rotate an ingest key](/guides/rotate-ingest-key).

To revoke a key, use its `id` from that result:

```bash
logbrew projects keys revoke "<project_id>" "<key_id>" --yes --json
```

The key stops working at its next request.

This command creates a credential. Before you run it, make sure that the
project is correct. If the result is uncertain, run the same command again. The
CLI then reuses the pending attempt. Use `--abandon-retry` only to start a new
attempt.

To create a new project, follow the [quickstart](/quickstart). It uses
`logbrew projects create "<name>" --ingest-key-file "<private_key_file>"`,
which stores the first key in the same way. Run `logbrew setup --create-project`
to read the project creation help. That command does not create a project.

After a setup step, you can record it for the project. The `--source` value is
`api`, `cli`, or `sdk`:

```bash
logbrew projects setup "<project_id>" --source cli --environment production --json
```

Then read project readiness:

```bash
logbrew doctor --project "<project_id>" --json
```

Exit code `0` does not mean that all checks passed. Read the report `status`
and each check. See the [doctor report
reference](/reference/cli#read-a-project-doctor-report).

## Read account usage

Read usage and limits. This does not change account or billing state.

```bash
logbrew usage --json
```

`logbrew account usage --json` gives the same result. The response gives the
plan, quota state, reset date, usage totals by project and by telemetry kind,
and a next step. The fields include `plan`, `state`, `reset_at`, `by_project`,
`by_stream`, and `next`.

## Common investigations

Filter each read by project. Add release, environment, time, or severity
filters when the command supports them. See [Filters](/reference/cli#filters).

<CardGroup cols={2}>
  <Card title="Issues in a release" icon="tag">
    ```bash
    logbrew read issues --project "<project_id>" --release api@1.2.3 --status unresolved --json
    ```
  </Card>

  <Card title="One failed request" icon="route">
    ```bash
    logbrew read trace "<trace_id>" --project "<project_id>" --json
    ```
  </Card>

  <Card title="Logs for a release" icon="file-text">
    ```bash
    logbrew read logs --project "<project_id>" --release api@1.2.3 --since 24h --json
    ```
  </Card>

  <Card title="Issues assigned to you" icon="user">
    ```bash
    logbrew read issues --project "<project_id>" --assignee me --status unresolved --json
    ```
  </Card>
</CardGroup>

## Watch live events

Use watch to see new events while you test a change. Press Ctrl+C to stop.

```bash
logbrew watch --severity error,critical --json
```

Watch streams JSON only. Without `--json`, the command stops with an error.
Add `logs`, `issues`, or `actions` to watch one type, such as
`logbrew watch logs --json`. Watch does not support traces or spans.

Watch has no project, release, or environment filter. For one project, use the
reads above. See [Live watch](/reference/cli#live-watch) for the supported
resources and filters.

## Explain before you change code

Read the context before you propose a fix.

<Steps>
  <Step title="Read the issue">
    ```bash
    logbrew read issue "<issue_id>" --json
    ```
  </Step>

  <Step title="Read the trace">
    Do this step only if the issue has a trace ID. An issue without a trace is
    still valid.

    ```bash
    logbrew read trace "<trace_id>" --project "<project_id>" --json
    ```
  </Step>

  <Step title="Read the explanation">
    ```bash
    logbrew explain issue "<issue_id>" --json
    ```

    For a log, use `logbrew explain log "<log_id>" --json`. For an action, use
    `logbrew explain action "<action_id>" --json`.
  </Step>

  <Step title="Resolve after verification">
    ```bash
    logbrew set issue "<issue_id>" resolved --json
    ```

    To change status, priority, or assignee for many issues, see
    [Change issue status and priority](/reference/cli#change-issue-status-and-priority)
    and the [issue workflow](/guides/issue-workflow).
  </Step>
</Steps>

## JSON output

- Put `--json` before or after the command, such as `logbrew --json status` or
  `logbrew status --json`.
- Read the exit code before you use the output.
- JSON errors have `ok`, `error`, `message`, and `next`. A timeout does not
  prove that a write failed. Before you repeat a write, read its retry rules.
- Do not automate with output that has no `--json`. It can change.

See [Read results and errors](/reference/cli#read-results-and-errors) for exit
codes and error examples.

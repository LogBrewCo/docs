An issue groups error occurrences that share a fingerprint. Read the group
summary and one occurrence before you change status, priority, or assignee.
A status, priority, or assignee change records a team decision. It does not repair software or rewrite captured events.

Install the [LogBrew CLI](/guides/cli) and run `logbrew login` before you start.

## Issues and occurrences

An issue list returns a group summary, not a full event. Read these fields
before you open the detail:

| Field | Meaning |
| --- | --- |
| `title` | Captured failure title. |
| `severity` | Captured severity. |
| `triage.effective_severity` | Severity that LogBrew uses after issue rules. `severity` keeps the captured value. `triage.rule_applied` is `true` when a rule applies. |
| `occurrence_count` | Number of retained occurrences in the group. |
| `first_seen_at` | Time of the earliest retained occurrence. |
| `last_seen_at` | Time of the latest retained occurrence. |
| `project_id` | Project that contains the issue. |
| `service_name` | Service of the latest occurrence. |
| `release` | Release of the latest occurrence. |
| `environment` | Environment of the latest occurrence. |
| `status` | Workflow state of the issue. See [Status values](#status-values). |
| `priority` | Triage order of the issue. See [Priority](#priority). |
| `priority_source` | `manual` when a person set the priority. `derived` when it follows severity. |
| `assignee` | Account or team that owns the next step, or `null`. See [Assign issues](#assign-issues). |

The occurrence count is not an affected-user count. Counts and times apply to
the returned scope, not to the full error history. A `--since` or `--until`
filter limits the occurrences that LogBrew counts. When you report a count,
also report the filters that produced it.

## Status values

| Status | Meaning |
| --- | --- |
| `unresolved` | The issue needs a decision. |
| `resolved` | The team marked the issue as fixed. The status does not prove the fix. |
| `archived` | The team removed the issue from active triage. |

`archived` was previously named `ignored`. The two names select the same
issues, and both are accepted as input. `logbrew read`, `logbrew issues`, and
API versions 2 and 3 show `archived`. API version 1 (the default), the live
watch stream, and the issue investigation response show `ignored`. The
dashboard shows the statuses as Unsolved, Solved, and Archived.

Status applies to the whole issue, not to one occurrence. Severity shows
urgency, and status records the decision. Keep the two separate. A `critical`
issue can be `resolved` after a verified fix. An `archived` issue keeps its
captured severity.

LogBrew does not reopen a resolved issue automatically. When a new occurrence
arrives after resolution, the investigation reports
`lifecycle.effective_status` as `regressed`. The `status` stays `resolved`
until a person reopens the issue.

## Priority

Priority sets the order in which the team triages issues:

| Priority | Meaning |
| --- | --- |
| `high` | Examine the issue first. |
| `medium` | Examine the issue after the `high` issues. |
| `low` | The issue can wait. |

Each issue has a priority. If nobody sets it, it follows the issue severity:
`error` and `critical` are `high`, `warning` is `medium`, and `info` is `low`.
When an issue rule changes the severity, priority follows
`triage.effective_severity`. Then `priority_source` is `derived`. When a person
sets the priority, it stays fixed and `priority_source` is `manual`.

To list the issues to examine first:

```bash
logbrew read issues --project "<project_id>" --status unresolved \
  --priority high --since 24h --json
```

## Assign issues

Assign an issue to show who owns the next step. An issue has 0 or 1 assignee:
one account or one team.

<Steps>
  <Step title="Find who can be assigned">
    ```bash
    logbrew issues assignees --project "<project_id>" --json
    ```

    `assignees` has every account that can read the project, with `user_id`,
    `name`, and `email`. `teams` has every team of the project's organization,
    with `team_id`, `slug`, and `name`. You cannot assign an account that
    cannot read the project, or a team of another organization.
  </Step>

  <Step title="Assign the issue">
    ```bash
    logbrew issues assign "<user_id>" "<issue_id>" --json
    logbrew issues assign "team:<team_id>" "<issue_id>" --json
    ```

    Use `me` instead of a user ID to assign the issue to yourself. Use
    `logbrew issues unassign "<issue_id>" --json` to remove the assignee.
    Add `--project` to change up to 100 issues of one project.
  </Step>

  <Step title="Read your issues">
    ```bash
    logbrew read issues --project "<project_id>" --assignee me \
      --status unresolved --json
    ```

    Use `--assignee my_teams` for the issues of your teams,
    `--assignee "team:<team_id>"` for one team, and `--assignee none` for
    issues that nobody owns.
  </Step>
</Steps>

To assign issues, you need permission to manage issues in the project. The
same permission lets you change status, priority, ownership rules, and issue
and log rules. Organization owners and admins create teams and choose their
members. A team gives its members no project access.

When a member loses access to the project, the issues assigned to that member
show no assignee. When a team is deleted, the issues assigned to it show no
assignee. These issues appear in `--assignee none` reads. If the member gets
access again, the issues show that member again, unless someone changed or
removed the assignee in the meantime.

## Find who owns an issue

```bash
logbrew issues owners "<issue_id>" --json
```

The result lists the suggested owners, best first, and a
`suggested_assignee`. Each owner has a `source`:

| `source` | Meaning |
| --- | --- |
| `ownership_rule` | A rule of the project matches the issue. `rule`, `line`, and `matched` show the rule and what it matched. |
| `codeowners` | A line of the project's CODEOWNERS file matches a stack frame path. |
| `recent_activity` | The account changed the issue or was assigned to it. |

`inputs` counts the stack frame paths, modules, route template, tags, and rules
that LogBrew checked. If the list is empty and `inputs` shows no paths, the
issue has no evidence to match, not no owner.

Write ownership rules in a text file, one rule per line:

```text
# type:pattern owner...
path:src/payments/** ada@example.com #payments
url:/checkout/* #web
service:billing-api ada@example.com
tags.region:eu-* #europe
module:app.billing.* ada@example.com
```

A `path` pattern matches the end of a stack frame path, so `src/payments/**`
matches frames under any deployment directory. `*` matches any text. Owners
are account emails or `#team-slug`. The last matching rule comes first.
Then send the rules, a GitHub CODEOWNERS file, or both:

```bash
logbrew issues ownership set --project "<project_id>" \
  --rules ownership.txt --codeowners .github/CODEOWNERS --json
logbrew issues ownership --project "<project_id>" --json
```

In CODEOWNERS, an email names an account and `@org/team-slug` names the team
with that slug. Rules that name an account without project access or an
unknown team fail with `422`. CODEOWNERS owners that name nobody appear in
`unresolved_owners`. An empty file clears its text.

## Read the issue history

```bash
logbrew issues activity "<issue_id>" --json
```

The history lists every status, priority, assignee, and severity rule change,
newest first, with the account that made it. It ends with `first_seen`. An
account that lost project access keeps only its ID. Use `--limit` and the
`next_cursor` values to read more.

## Read your inbox

```bash
logbrew inbox --json
logbrew inbox read --json
```

The inbox lists the issues that other people assigned to you or to your teams,
newest first. `unread` counts the assignments after your read mark.
`logbrew inbox read` moves the read mark to now. LogBrew does not send email
for these assignments. The inbox shows only projects that you can read now.

## Recommended workflow

<Steps>
  <Step title="List unresolved issues in one scope">
    ```bash
    logbrew read issues --project "<project_id>" --environment production \
      --release api@1.2.3 --status unresolved --since 24h --json
    ```

    Keep the same filters on later list reads. An empty result means that no
    issue matches this scope. It does not prove that the project has no
    errors. Copy the exact issue ID, not the title.
  </Step>

  <Step title="Read the issue detail">
    ```bash
    logbrew read issue "<issue_id>" --json
    ```

    Confirm that the returned project is correct before you continue. Reads
    return a snapshot. Read the issue again before you change status.
  </Step>

  <Step title="Investigate one occurrence">
    ```bash
    logbrew investigate issue "<issue_id>" --occurrence recommended --json
    ```

    The detail and investigation reads do not use list filters. Compare
    `subject.project_id`, `event.occurred_at`, release, and environment with
    your scope. The recommended occurrence can be older than the latest one.
    Follow [Investigate an issue](/guides/investigate-an-issue) for the full
    evidence review.
  </Step>

  <Step title="Follow trace evidence only when available">
    Read the trace only when `correlations.trace.status` is `available`. Use
    the trace ID from the response. Never invent one.

    ```bash
    logbrew read trace "<trace_id>" --project "<project_id>" --json
    logbrew read logs --trace "<trace_id>" --project "<project_id>" \
      --since 24h --json
    ```

    The trace read has no time filter. If the status is `not_linked`,
    continue with the issue evidence.
  </Step>

  <Step title="Verify the candidate deployment">
    Use the investigated occurrence as the baseline. Get the deployment ID from
    deployment evidence or your release process.

    ```bash
    logbrew investigate issue "<issue_id>" verify \
      --baseline-occurrence "<occurrence_id>" \
      --candidate-deployment "<deployment_id>" \
      --json
    ```

    No recurrence in the observation window does not prove a permanent fix.
    If `status` is `insufficient_traffic` or `unavailable`, keep the issue
    `unresolved`. Follow the returned next action.
  </Step>

  <Step title="Change status, priority, or assignee">
    Run one command. These commands do not ask for confirmation, so check the
    issue ID first.

    ```bash
    logbrew issues resolve "<issue_id>" --json
    logbrew issues archive "<issue_id>" --json
    logbrew issues reopen "<issue_id>" --json
    logbrew issues priority low "<issue_id>" --json
    logbrew issues assign me "<issue_id>" --json
    ```

    Without `--project`, each command takes 1 issue ID. Check the exit code
    and the returned `status`, `priority`, and `assignee`. If the result is
    missing, read the issue again before the next change.

    Older scripts can use `logbrew set issue "<issue_id>" resolved` and the
    `resolve`, `ignore`, and `reopen` shortcuts. `ignore` sets `archived`.
  </Step>
</Steps>

## Change many issues at once

Add `--project` to change up to 100 issues of one project in one command:

```bash
logbrew issues archive "<issue_id_1>" "<issue_id_2>" "<issue_id_3>" \
  --project "<project_id>" --json
```

The command applies one change to every issue. Each issue ID can appear only
once. The CLI rejects more than 100 IDs or a repeated ID before it sends a
request. The result has 1 entry for each issue, in the order of the command:

| Outcome | Meaning |
| --- | --- |
| `updated` | LogBrew applied the change. |
| `unchanged` | The issue already had the requested value. |
| `not_found` | The project has no issue with this ID. LogBrew changed nothing for it. |

Each entry has `issue_id`, `outcome`, and `issue`. `issue` is the current
issue, or `null` for `not_found`. You can run the same command again after a
network failure. Issues that changed already show `unchanged`. For more than
100 issues, run more commands. For a `not_found` result, copy the ID again from
an issue list of that project. See
[Update issues in bulk](/reference/telemetry-api#update-issues-in-bulk) for
the API request.

## Choose the next status

- **Keep it `unresolved`** when the failure is active or the fix is not
  verified. A missing trace is not a reason to archive an issue.
- **Set `resolved`** after the team accepts the fix evidence. A proposed fix is
  not evidence.
- **Set `archived`** for an accepted condition or a test-only signal. The
  decision applies to every occurrence of the issue. The command has no reason
  field, so record the reason in your team's work record.
- **Reopen with `unresolved`** when a new occurrence arrives after
  resolution. `lifecycle.regression.first_reappeared_occurrence` identifies
  it. Compare it with the occurrence used for resolution. Do not create a
  different issue.

## Hand off the investigation

Give the next person references, not a raw event dump:

- Issue ID, status, priority, assignee, and severity.
- Project, service, environment, and release.
- First-seen time, last-seen time, and occurrence count.
- Selected occurrence ID and `occurrence_selection.reason`.
- `fix.status`, `cause.status`, and their `provenance`.
- Trace status and trace ID, if available.
- Reproduction status and missing evidence.
- Candidate deployment verification result.
- The next action that the response returned.

Label proposed causes and fixes as proposals.

## Recover from CLI errors

Check the process exit code before you parse output. On success, JSON goes to
standard output. A parse error exits with code `2`. A runtime error exits with
code `1`. JSON errors go to standard error and contain `ok: false`, `error`,
`message`, and `next`. Show `next` as guidance. Do not run it automatically.

For example, `logbrew issues archive "<issue_id_1>" "<issue_id_2>" --json`
has no `--project`. It exits with code `2` before a request, with the error
`invalid_issue_command`.

When the API rejects a request, `error` is `api_error`. Read `status` for the
HTTP status and `api_code` for the API error code.

| Result | Recovery |
| --- | --- |
| `not_logged_in` | Ask a person to run `logbrew login`, then retry the read. |
| `invalid_issue_command` | Correct the command. Use `--project` for more than 1 issue, at most 100 IDs, and each ID once. |
| Invalid issue ID | Copy the exact ID from an issue list or detail response. |
| Issue not found | Confirm the signed-in account and the project. |
| A change fails with `status` `403` | The account cannot manage issues in this project. Ask a person with access. |
| `invalid_assignee` | The `--assignee` filter takes `me`, `none`, `my_teams`, a user ID, or `team:<team_id>`. |
| An assign fails with `status` `422` and `api_code` `validation_failed` | The account cannot read the project, or the team is not in the project's organization. Pick one from `logbrew issues assignees`. |
| `invalid_ownership_command`, `invalid_ownership_file` | Correct the command. An ownership file must be UTF-8 text of at most 128 KiB. |
| `invalid_inbox_command` | Use `logbrew inbox` or `logbrew inbox read`. |
| `investigation_response_invalid` | The response failed CLI validation. Retry once. If it repeats, update the CLI or report the problem. Do not bypass validation. |
| Trace status `not_linked` | Continue with the issue evidence. Do not read a trace. |
| Trace status `unavailable` | Retry the investigation read later. |
| Verification `insufficient_traffic` | Keep the issue `unresolved`. Wait for traffic on the candidate release, then verify again. |

A failed response does not prove that a status, priority, or assignee change
had no effect. Read the
issue before you try again.

## What makes a useful issue

- A clear title and a readable message.
- A stable fingerprint.
- Stack frames, when available.
- Release, environment, and service context.
- Trace context, when captured with the occurrence.
- Small, relevant attributes, not full payload dumps.

See the [Telemetry API reference](/reference/telemetry-api) for list filters
and response contracts.

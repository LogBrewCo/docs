Use this page when telemetry is missing, incomplete, or too broad. Check
access first. Then keep the project, service, release, environment, and time
range fixed while you find the cause.

<Note>
  Add `--json` for agent workflows. A failed check returns a stable `next`
  field.
</Note>

## Start with the fast checks

| Symptom | First check | Next step |
| --- | --- | --- |
| CLI is not signed in | `logbrew status --json` | A person runs `logbrew login`. |
| A project is missing | `logbrew projects --json` | Use an ID from the project list. |
| Setup state is unclear | `logbrew doctor --project "<project_id>" --json` | Follow the returned `next` value. |
| Logs are empty | Read logs for the exact project and time range | Check other signal types separately. |
| Results are too broad | Add project, service, release, and environment filters | Keep the same scope in each read. |
| A trace is missing | Read the issue detail | Read a trace only when the response has a trace ID. |
| JavaScript frames show built code | Check the build and source-map pair | Follow [JavaScript source maps](/guides/source-maps). |

## Recover missing first telemetry

Run these read-only commands before you change SDK configuration:

```bash
logbrew version --json
logbrew status --json
logbrew projects --json
logbrew doctor --project "<project_id>" --json
```

`logbrew doctor` checks API access, authentication, the project, the ingest
key, setup, telemetry, and log visibility. It does not change the project.
Read the overall `status` and each check in the
[doctor report](/reference/cli#read-a-project-doctor-report). Exit code `0`
does not mean that every check passed.

| Doctor status | Next step |
| --- | --- |
| `needs_ingest_key` | Create a project-scoped ingest key. See [Rotate an ingest key](/guides/rotate-ingest-key). |
| `needs_setup` | Complete SDK setup. See [SDK ingestion](/guides/sdk-ingestion). |
| `needs_telemetry` | Send one safe test event from the app, then run the doctor again. |
| `ready` | Read recent logs, issues, releases, or traces. |

A `ready` project can still have no logs, because each signal type is separate.

### Send one safe test event

Send one test log with a unique message from the installed SDK. Do not include
a token, user data, or a request body. Record the project ID, service,
environment, release, UTC start time, and SDK version. Wait for delivery, then
read a short time range in the same project. Do not send more test events while
delivery is pending.

## Find missing logs

Read a small, exact scope first:

```bash
logbrew read releases --project "<project_id>" --environment production --json
logbrew read logs --project "<project_id>" --environment production \
  --release checkout@1 --since 1h --limit 20 --json
```

Check these items in order:

1. The project ID belongs to the app that sent the event.
2. Service, release, and environment match exactly, including case and
   whitespace.
3. The time range includes the event time. An app-supplied `occurred_at` must
   be in UTC.
4. No search or severity filter hides the event.
5. The app sent the signal type that you read. A log does not create an issue
   or a trace.

If the event is still missing, remove one filter at a time:

1. Keep the project and widen the time range.
2. Remove the release filter.
3. Remove the environment filter.
4. Remove the service filter.
5. Remove search and severity filters.

Stop when the event appears. The last filter that you removed does not match
the app configuration. Do not read all projects instead of the configured
project.

| Result | What it shows | Next check |
| --- | --- | --- |
| No rows in one project | No match in that scope | Check time and filters. |
| Logs, but no issues | No grouped error matches the filters | Check that the app sent an error. |
| Issue without a trace | The occurrence has no usable trace link | Read the trace status in the issue investigation. |
| Event appears after you remove a filter | That filter excluded the event | Fix the filter or the app value. |

LogBrew stores only the telemetry that the app sends. Remove credentials,
request bodies, query values, and personal data before delivery. Use
[Safe capture](/guides/safe-capture) to check your field selection.

## Check issues and traces

Use an issue ID or trace ID that LogBrew returned. Never invent one.

```bash
logbrew read issues --project "<project_id>" --environment production \
  --status unresolved --since 24h --json
logbrew read issue "<issue_id>" --json
logbrew read trace "<trace_id>" --json
logbrew read logs --trace "<trace_id>" --json
```

Issue status and trace status are different. The trace status values
`not_linked`, `not_found`, and `unavailable` have different meanings. See
[Investigate an issue](/guides/investigate-an-issue) for each value. Read the
issue and its logs before you resolve, ignore, or reopen it.

## Handle CLI and API errors

In JSON mode, a CLI error contains `ok`, `error`, `message`, and `next`:

```json
{
  "ok": false,
  "error": "not_logged_in",
  "message": "not logged in: run logbrew login",
  "next": "run logbrew login"
}
```

| Status or error | Recovery |
| --- | --- |
| `not_logged_in` or HTTP `401` | A person runs `logbrew login`. Then retry the read. |
| HTTP `403` | Use the correct credential for the project. Do not show the credential value. |
| HTTP `404` | Use a current project, issue, or trace ID from a response. |
| HTTP `422` | Correct the named field. |
| HTTP `429` | Stop automatic retries. Follow the returned guidance. |
| HTTP `5xx` | Wait, retry one read, and report the problem if it continues. |

See [API errors](/reference/api-errors) for each error code.

## Secure a compromised account

If someone else might have an account access token, refresh token, or session
cookie, sign out all LogBrew clients. Follow the
[account-wide sign-out](/reference/account-api#every-logbrew-login)
procedure. A person must approve this action. After success, clear local
LogBrew credentials on each client and sign in again from a trusted client.

Account-wide sign-out does not rotate project ingest keys. If an ingest key was
exposed, [rotate the ingest key](/guides/rotate-ingest-key).

## Keep troubleshooting safe

Use an account access credential for CLI reads. Use a project-scoped ingest
credential only for SDK writes. Do not put tokens, authorization headers, raw
logs, customer data, request bodies, local paths, or source code in a command,
chat, or support ticket.

Before you report a problem, repeat one read with the smallest scope that still
fails. Record the command without credential values, the error code, the
project ID, and the filter values. If the checks do not solve the problem,
[report a problem](/guides/report-a-problem).

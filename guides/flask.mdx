Use `logbrew-flask` 0.1.6 or newer. It captures request spans and unhandled
exceptions. The optional logging handler connects Python logs to the request
trace. Request-duration metrics are also optional.

The package requires Python 3.10 or newer and Flask 3.1 or newer.

<Note>
  Use a project-scoped server ingest key in the application. Do not use the
  account credential that authorizes the CLI.
</Note>

Replace `<project_id>`, `<trace_id>`, and `<issue_id>` with IDs from LogBrew.
Use a development project for the test requests. The shell examples use Bash.

## Send the first request

<Steps>
  <Step title="Create or select a project key">
    Sign in with the [CLI](/guides/cli). Then use a new project or an existing
    project. Do not run both examples. For a new project, store its ingest key
    in a new owner-only file:

    ```bash
    install -d -m 700 "$HOME/.logbrew"
    logbrew projects create my-flask-app \
      --runtime flask \
      --environment development \
      --ingest-key-file "$HOME/.logbrew/my-flask-app.ingest" \
      --json
    ```

    For an existing project, get its ID from `logbrew projects --json`. Then
    create a separate server key:

    ```bash
    logbrew projects keys create "<project_id>" \
      --kind server \
      --label "Flask server" \
      --ingest-key-file "$HOME/.logbrew/my-flask-app.ingest" \
      --json
    ```

    The CLI stores the ingest key with owner-only permissions. It does not
    print the key or its file path. Use your deployment platform's secret
    manager instead of this local file in production.

    If a creation request has an uncertain result, run the exact command again.
  </Step>

  <Step title="Install the released integration">
    Create or activate the application's virtual environment, then install the
    framework package. It installs the compatible core SDK dependency.

    ```bash
    python3 -m pip install "logbrew-flask>=0.1.6,<0.2"
    ```
  </Step>

  <Step title="Configure deployment identity">
    Load the project key locally without printing it. Set a stable service,
    environment, and release so every signal has useful deployment context.

    ```bash
    export LOGBREW_SERVER_API_KEY="$(tr -d '\r\n' < "$HOME/.logbrew/my-flask-app.ingest")"
    export LOGBREW_SERVICE_NAME="my-flask-app"
    export LOGBREW_ENVIRONMENT="development"
    export LOGBREW_RELEASE="my-flask-app@1.0.0"
    ```

    `init_logbrew()` checks explicit arguments first, then Flask application
    configuration, then these environment variables. If no service name is
    configured, it uses the Flask import name.
  </Step>

  <Step title="Initialize Flask once">
    For a new app, save the example as `app.py`. Add the initializer after you
    create the Flask application. The logging handler is optional. It lets
    application logs share the active request trace and span.

    ```python
    import logging

    from flask import Flask
    from logbrew_flask import init_logbrew
    from logbrew_sdk import LogBrewLoggingHandler

    app = Flask(__name__)
    logbrew = init_logbrew(app, capture_request_metrics=True)

    logger = logging.getLogger("my-flask-app")
    logger.setLevel(logging.INFO)
    logger.addHandler(LogBrewLoggingHandler(logbrew.client))


    @app.get("/health")
    def health() -> dict[str, bool]:
        logger.info("health check completed")
        return {"ok": True}
    ```

    Repeated `init_logbrew(app)` calls return the same Flask extension. They do
    not install duplicate request or exception hooks. The initializer does not
    add logging handlers. Add the handler to the app-owned logger once.
  </Step>

  <Step title="Run one request">
    Start the app and call the route from another terminal. Replace `app` in
    the command if your application uses a different module name.

    ```bash
    flask --app app run
    ```

    ```bash
    curl -fsS http://127.0.0.1:5000/health
    ```

    Delivery runs on a background worker and does not hold the response open.
  </Step>

  <Step title="Verify hosted evidence">
    Read the exact project and deployment scope. Look for the health request's
    trace and the correlated log from the example's logging handler.

    ```bash
    logbrew read traces \
      --project "<project_id>" \
      --service my-flask-app \
      --environment development \
      --release my-flask-app@1.0.0 \
      --since 1h \
      --json

    logbrew read logs \
      --project "<project_id>" \
      --service my-flask-app \
      --environment development \
      --release my-flask-app@1.0.0 \
      --search "health check completed" \
      --since 1h \
      --json
    ```

    Copy the returned trace ID into the bounded investigation command:

    ```bash
    logbrew explain trace "<trace_id>" --json
    ```

    A matching read confirms that LogBrew stored the signal. A local `200`
    response proves only that Flask handled the request.
  </Step>
</Steps>

## Choose the signals you need

The initializer starts with request traces and unhandled exceptions enabled.
Request metrics and Python log forwarding are separate choices.

| Option | Default | Use it when |
| --- | --- | --- |
| `capture_successful_requests` | `True` | You want one span for each completed request. A response with status `500` or higher still creates a span when this option is off. |
| `capture_exceptions` | `True` | You want a typed issue and matching error span for exceptions that Flask reports as unhandled. |
| `capture_request_metrics` | `False` | You want a duration histogram for completed requests. |
| `LogBrewLoggingHandler` | Not attached | You want selected Python log records to become LogBrew logs. |
| `flush_on_response` | `False` | Keep this default for background delivery. Enable it only for a controlled diagnostic that must surface response-path delivery. |

Start with the defaults. Add request metrics when you need a latency view.
Add the logging handler only to the loggers that help an investigation.

By default, the initializer owns an HTTP transport. It queues each event, and
a background worker starts delivery as soon as one event is in the queue.
Delivery does not hold the response open. Transport failures do not break the
Flask response.

`flush_on_response=True` sends queued events on the response path instead.
With that option, `raise_flush_errors=True` raises delivery errors. Use both
only for a controlled diagnostic.

## Control log content

Add one `LogBrewLoggingHandler` to the logger that owns the messages you need.
The handler does not replace the app's console or file handlers. It does not
patch Flask or the Python logging module. Adding the same handler twice
duplicates logs. If the app also uses the root logger, check propagation
before you attach a second handler.

A log inside a request inherits the active trace and span. A log outside a
request has no request trace.

The handler sends the formatted message, logger name, and LogBrew level. It
also sends the source file name, module, function, line, thread, and process
names, but not the full source path. Primitive values from `extra={...}`
become metadata. Review those values before you log from a user-facing
request.

Python `DEBUG` records become LogBrew `info`. `WARNING` becomes `warning`, and
`CRITICAL` becomes `critical`. The original Python level name and number stay
in metadata. To send fewer records, give the handler its own level, such as
`LogBrewLoggingHandler(logbrew.client, level=logging.WARNING)`.

The console and LogBrew can receive the same record. For example, configure
the console before you create the Flask app:

```python
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)
```

The console gets formatted text. LogBrew keeps the message, level, logger, and
metadata as separate fields.

A log record with `exc_info` includes the exception type and message. The
full exception text is sent only when the handler has
`include_exception_text=True`. This is separate from automatic exception
capture, which never sends the exception message. Do not put credentials,
personal data, or request bodies in log or exception messages.

## What the integration captures

| Signal | Default behavior |
| --- | --- |
| Request trace | One server span with method, Flask route template, status code, and duration. |
| Exception issue | Title `<METHOD> <route template> failed`, unhandled type, fixed `Unhandled exception` summary, `flask.middleware` mechanism, handled state, and up to 32 sanitized frames. |
| Application log | Opt in with `LogBrewLoggingHandler`; an in-request log inherits the active trace and span. |
| Request metric | Opt in with `capture_request_metrics=True`; emits the `http.server.duration` delta histogram with the description `Duration of one completed server request.` |
| Inbound trace | Continues a valid W3C `traceparent` with a new child span. |

Span names use the HTTP method and the matched route template. For example,
`/orders/100` and `/orders/200` share `GET /orders/<int:order_id>`. An
unmatched request uses the fixed `<unmatched>` label. A missing or invalid
`traceparent` starts a new trace.

Span metadata contains the method, route template, endpoint, status code, and
duration. It does not contain the concrete path or a query string.

The request span covers the full Flask dispatch.
Before-request hooks, error handlers, and teardown share the request trace. A
streamed response ends its span when the body finishes or closes.

### Test exception capture

A `4xx` or `5xx` status appears on the request span. The status alone does not
prove that an exception occurred. Read both traces and issues before you
diagnose a failure. LogBrew does not replace Flask error handlers or change the
response status.

In a development project, add a temporary route. Call it once. Remove it
before you deploy:

```python
@app.get("/logbrew-test-error")
def handle_test_error() -> None:
    raise RuntimeError("local capture check")
```

The request returns status `500`. Find the new issue and the request metric:

```bash
logbrew read issues --project "<project_id>" --since 1h --json
logbrew explain issue "<issue_id>" --json

logbrew explain metric http.server.duration \
  --project "<project_id>" \
  --service my-flask-app \
  --environment development \
  --release my-flask-app@1.0.0 \
  --since 1h \
  --json
```

Check the issue's service, environment, release, exception type, and request
trace. The issue must not contain the text `local capture check`.

### Connect outbound work to the request

The Python SDK has app-owned helpers for `requests`, `urllib`, `httpx`,
`aiohttp`, database, cache, and queue work. Each helper creates a child span
of the active request trace. The SDK does not patch these libraries globally.
The [`logbrew-flask` package](https://pypi.org/project/logbrew-flask/) shows
examples.

Give each helper a stable operation name and a route or statement template.
Do not put record IDs, customer values, SQL bind values, or message payloads
in those names. Add child spans only where the dependency matters to the
request. A span for every small call makes the trace harder to read.
Outbound HTTP helpers add one W3C `traceparent` header. They
do not capture full URLs, query strings, bodies, cookies, or arbitrary
headers. Database, cache, and queue helpers do not capture bind values,
results, cache values, or queue payloads.

## Privacy and process lifecycle

Automatic Flask capture omits concrete request paths, query strings, request
and response bodies, cookies, arbitrary headers, raw `traceparent` values,
baggage, and tracestate.

Automatic exception capture never reads or sends `str(error)`. It uses the
fixed summary `Unhandled exception` and marks each exception-chain message as
redacted. Frames contain a file basename and bounded code identity. They do
not contain raw traceback text, source code, local variables, or absolute
paths.

Create the app and LogBrew client inside each worker process. Gunicorn's
default per-worker app loading works. Do not use Gunicorn `--preload` with a
client created in the parent process. For uWSGI, use per-worker app loading
such as `--lazy-apps`. The Python client rejects reuse after a process fork.

Call `logbrew.client.shutdown()` from the process manager's per-worker
shutdown hook. It sends the remaining queued events and closes the client. Do
not call it after every request. After shutdown, the client rejects new
events from that worker.

A response can finish before the worker sends its last queued events. During
a deploy or scale-down, a graceful shutdown gives those events a final
delivery attempt.

## Recover from setup problems

| Symptom | Check | Next action |
| --- | --- | --- |
| `LOGBREW_SERVER_API_KEY is required` | The initializer did not receive a non-empty project key. | Configure the project-scoped server key through Flask config, an explicit argument, or the environment. |
| No trace appears | Project, service, environment, release, or time filters do not match. | Run `logbrew doctor --project "<project_id>" --json`, then repeat the scoped trace read. |
| Traces appear but logs do not | Request instrumentation does not attach a Python logging handler automatically. | Add one `LogBrewLoggingHandler` to the app-owned logger. |
| Requests work but final events are missing during shutdown | The process exits before the background worker flushes its retained tail. | Call `logbrew.client.shutdown()` from the worker shutdown hook. |
| Worker reports `process_ownership_error` | The client was created before the worker process forked. | Load the app per worker and create a new client in that process. |

For account access, key, and readback errors, see
[Troubleshooting](/guides/troubleshooting). For other runtimes, see
[Send SDK telemetry](/guides/sdk-ingestion).

本页为[遥测 API](/zh-Hans/reference/telemetry-api) 的每类响应各给出 1 个示例。所有值均为模拟值。错误码和恢复方法请参阅 [API 错误](/zh-Hans/reference/api-errors)。

## 读取响应

按以下顺序读取每个响应：

1. 读取 HTTP 状态。
2. 确认响应体符合该路由规定的结构。
3. 确认每个 `project_id` 都在请求的项目范围内。
4. 保持规范枚举值和标识符不变。
5. 只有客户端支持 `next_action` 的 `code` 和 `target` 时，才执行它。
6. 把 `null`、省略的字段和空列表当作 3 种不同的状态。

`200 OK` 可以包含空列表。空的日志列表表示没有日志匹配该请求，不表示问题、链路或操作也为空。不要因为时间戳相近就关联信号。只有响应包含准确的 `trace_id` 时，才沿该链路继续读取。

`404` 和空列表是不同的结果。没有记录匹配时，列表路由返回 `[]`。找不到可读取的记录时，详情路由返回 `404` 和 `code: not_found`。这两种结果都不能证明数据接收失败。

## 应发送的数据

你发送的遥测数据决定了响应的价值。在每个封装或每次 SDK 配置中发送以下值：

- `release` 和 `environment`。
- 服务、操作和指标的稳定名称。
- 日志、Span（一次计时操作）、操作和问题属于同一请求时，发送链路上下文。
- 规范的严重程度值：`info`、`warning`、`error` 和 `critical`。
- 有助于调试的属性，但不要包含机密信息或不必要的个人信息。

请参阅 [SDK 接入](/zh-Hans/guides/sdk-ingestion)和[控制采集的数据](/zh-Hans/guides/safe-capture)。

## 数据接收响应

公开 SDK 会替你读取 `POST /v1/events` 的响应。应用代码无需处理它。

### SDK 批次响应

SDK 批次成功时返回 `200 OK`，并给出每个数据流已接收的数量：

```json
{
  "issues": 1,
  "logs": 2,
  "trace_spans": 3,
  "actions": 1,
  "metrics": 1,
  "already_accepted": 0,
  "context_updated": true,
  "next": "review accepted telemetry in logs, issues, traces, actions, metrics, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `issues`、`logs`、`trace_spans`、`actions`、`metrics` | LogBrew 从该批次接收的信号数。 |
| `already_accepted` | ID 已被 LogBrew 接收过的信号数。LogBrew 不会再次存储这些信号。 |
| `context_updated` | 该批次更新了版本或环境上下文时为 `true`。 |

这些数量只涵盖该批次。重试一个 LogBrew 已接收的批次时，每个数据流都返回 `0`，信号数会计入 `already_accepted`。重试时保留原始事件 ID。

### 原生封装响应

`POST /api/telemetry/ingest` 返回 `200 OK`，并给出每个数据流已接收的条目数：

```json
{
  "issues": 0,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

原生响应没有 `metrics` 或 `context_updated` 字段。不要添加它们。`already_accepted` 统计 `id` 已被 LogBrew 为该项目接收过的条目。请参阅[直接发送原生封装](/zh-Hans/guides/sdk-ingestion#required-envelope-fields)。

### 数据接收错误

`401` 和 `code: ingest_key_invalid` 表示接入 Bearer 令牌已撤销、已过期，或对该项目无效。在 `POST /v1/events` 上，缺少 Bearer 令牌或令牌不是接入密钥时，返回 `401` 和 `code: unauthorized`。使用当前的项目级接入 Bearer 令牌。不要改用账号 Bearer 令牌重试。

被拒绝的 SDK 批次返回 `422` 和 `code: validation_failed`：

```json
{
  "error": "SDK event ids must be unique within a batch",
  "code": "validation_failed",
  "next": "send release/environment context plus issue, log, span, action, or metric events from a current LogBrew SDK",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

其他 `error` 值包括 `SDK event batch requires at least one event` 和 `SDK event type is not supported by this ingest route`。检查 SDK 版本和传输配置。不要发送空批次。不要只为了通过验证而更改信号类型或 ID。

使用 `POST` 以外的方法时，请求返回 `405` 和 `code: method_not_allowed`。无法读取的 JSON 请求体返回 `code: invalid_json`。

## 遥测列表响应格式

列表路由默认返回不带外层对象的 JSON 数组。成功但为空的列表是 `[]`。

使用 `pagination=cursor` 时，路由返回一个封装。集合键与信号对应：

| 路由 | 集合键 |
| --- | --- |
| `/api/logs` | `logs` |
| `/api/telemetry/issues` | `issues` |
| `/api/telemetry/issues/{issue_id}/events` | `events`，外加顶层 `issue_id` |
| `/api/telemetry/actions` | `actions` |
| `/api/telemetry/metrics` | `metrics` |
| `/api/telemetry/releases` | `releases` |
| `/api/telemetry/traces` | `traces`，外加顶层 `naming_quality` |

`next_cursor` 是包含续读字段的对象，在最后一页为 `null`。各行按从新到旧排列。请参阅[游标分页](/zh-Hans/reference/telemetry-api-filters#cursor-pagination)。

### <span id="log-response">日志响应</span>

使用 `limit=1` 的日志游标分页：

```json
{
  "logs": [
    {
      "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "level": "warning",
      "severity": "warning",
      "triage": {
        "effective_severity": "warning",
        "ignored": false,
        "rule_applied": false
      },
      "source": "runtime",
      "message": "checkout retry scheduled",
      "attributes": { "route": "/checkout" },
      "occurred_at": "2026-06-01T12:00:00Z",
      "environment": "production",
      "release": "api@1.2.3",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7",
      "service_name": "checkout-api",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8",
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": {
    "time": "2026-06-01T12:00:00Z",
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d"
  }
}
```

日志包含用于兼容的 `level` 和用于显示的 `severity`。两者都是规范值。`triage` 保存严重程度规则的结果。请参阅[严重程度规则响应](#severity-rule-responses)。

日志没有关联链路时，`trace_id` 和 `span_id` 为 `null`。此时 `next_action` 为 `inspect_related_logs`，目标为 `telemetry_logs`。日志、问题和操作使用同样的 2 组 `next_action` 值。

`GET /api/logs/{log_id}` 以相同结构返回 1 条日志。

### <span id="issue-response">问题响应</span>

`GET /api/telemetry/issues/{issue_id}` 返回 1 个分组问题。列表返回同样的对象。本示例使用默认的响应版本 1：

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "fingerprint": "payment-error",
  "severity": "error",
  "triage": {
    "effective_severity": "error",
    "ignored": false,
    "rule_applied": false
  },
  "title": "PaymentError",
  "message": "payment provider timed out",
  "stack_trace": null,
  "attributes": {},
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  },
  "status": "unresolved",
  "occurrence_count": 2,
  "first_seen_at": "2026-07-13T07:00:00Z",
  "last_seen_at": "2026-07-13T08:00:00Z"
}
```

在版本 1 中，`status` 为 `unresolved`、`resolved` 或 `ignored`。已归档的问题的 `triage.ignored` 为 `true`。`next_action` 的各组值及其后续读取，请参阅[排查问题](/zh-Hans/guides/investigate-an-issue)。

`first_seen_at` 和 `last_seen_at` 分别是首次和最近一次发生记录的时间。状态变化时，它们不会改变。

有些字段只在 LogBrew 有相应数据时出现：

| 字段 | 出现条件 |
| --- | --- |
| `span_id` | 问题关联了 Span。否则省略该字段。 |
| `diagnostics` | 最近一次发生记录包含异常类型或操作记录（Breadcrumbs）。请参阅[问题发生记录历史](#issue-occurrence-history)。 |
| `symbolication` | 仅在 `GET /api/telemetry/issues/{issue_id}` 中出现，且问题需要有版本构建产物标识。请参阅 [JavaScript Source Map](/zh-Hans/guides/source-maps)。 |

`symbolication.status` 为 `resolved`、`invalid_metadata`、`artifact_not_found`、`source_not_resolved` 或 `unavailable`。列表、状态更改和规则更改都不返回 `symbolication`。

使用 `response_version=2` 时，问题包含相同的字段，并有以下变化：

| 字段 | 版本 2 的值 |
| --- | --- |
| `status` | `unresolved`、`resolved` 或 `archived`。版本 1 把 `archived` 显示为 `ignored`。 |
| `priority` | `high`、`medium` 或 `low`。 |
| `priority_source` | 有人手动设置优先级时为 `manual`。优先级跟随有效严重程度时为 `derived`。 |

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "archived",
  "severity": "error",
  "priority": "low",
  "priority_source": "manual"
}
```

本示例只显示部分字段。自动推导的优先级规则如下：`error` 和 `critical` 为 `high`，`warning` 为 `medium`，`info` 为 `low`。推导基于 `triage.effective_severity`，所以问题的严重程度规则可以改变它。

使用 `response_version=3` 时，问题包含版本 2 的全部字段，外加 `assignee`。问题没有负责人时，`assignee` 为 `null`：

```json
{
  "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
  "status": "unresolved",
  "priority": "high",
  "priority_source": "derived",
  "assignee": {
    "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
    "name": "Ada Example",
    "email": "ada@example.com"
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `assignee.user_id` | 负责人的用户 ID。在筛选条件或更改请求中把它作为 `assignee` 发送。 |
| `assignee.name` | 负责人的名称；账号没有名称时为 `null`。 |
| `assignee.email` | 负责人的电子邮件地址。 |

被分配的成员无法再读取该项目时，问题不显示负责人。

使用 `response_version=4` 时，`assignee` 还带有 `type`。`user` 类型的负责人与版本 3 一样，有 `user_id`、`name` 和 `email`。`team` 类型的负责人有 `team_id`、`slug` 和 `name`。版本 3 把团队负责人显示为 `null`。CLI 请求的是版本 4：

```json
{
  "assignee": {
    "type": "team",
    "team_id": "7c1d2e3f-4a5b-4c6d-8e7f-9a0b1c2d3e4f",
    "slug": "payments",
    "name": "Payments"
  }
}
```

其他任何 `response_version` 都返回 `422` 和 `code: validation_failed`。在一页游标结果中，`issues` 里的每个问题都使用同一版本。

### <span id="assignee-list-response">负责人列表响应</span>

`GET /api/telemetry/issues/assignees?project_id=<project_id>` 返回该项目中所有可被分配问题的账号：

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "assignees": [
    {
      "user_id": "5d6e7f80-1a2b-4c3d-8e4f-5a6b7c8d9e0f",
      "name": "Ada Example",
      "email": "ada@example.com"
    },
    {
      "user_id": "0f1e2d3c-4b5a-4968-8776-655443322110",
      "name": null,
      "email": "sam@example.com"
    }
  ]
}
```

添加 `response_version=2` 还可以获取 `teams`：该项目所在组织的每个团队，包含 `team_id`、`slug` 和 `name`。

如果账号无法读取该项目，路由返回 `404` 和 `code: not_found`。

### <span id="action-response">操作响应</span>

```json
{
  "id": "d8ee3a6f-3918-440b-96cb-14166419399a",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "checkout_failed",
  "distinct_id": "user_123",
  "session_id": "session_456",
  "occurred_at": "2026-06-01T12:00:00Z",
  "properties": { "surface": "checkout" },
  "environment": "production",
  "release": "checkout@1.2.3",
  "service_name": "checkout-api",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "next_action": {
    "code": "inspect_trace",
    "target": "trace_summary"
  }
}
```

`distinct_id` 跟随 1 个操作者或会话。把 `distinct_id` 和 `session_id` 当作不透明标识符。`session_id` 和 `trace_id` 缺失时为 `null`。`span_id` 缺失时会被省略。操作没有严重程度。请参阅[产品事件采集](/zh-Hans/guides/product-events)。

```json
{
  "id": "6f1c2d3e-4a5b-4c6d-8e7f-901234567890",
  "event_id": "metric-1",
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "name": "http.server.duration",
  "kind": "histogram",
  "value": 12.5,
  "unit": "ms",
  "temporality": "delta",
  "attributes": {},
  "occurred_at": "2026-07-13T08:00:00Z",
  "environment": "production",
  "release": "checkout@1.2.3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "service_name": "checkout-api",
  "sdk_name": "@logbrew/node",
  "sdk_version": "0.1.8"
}
```

每个条目是 1 个样本。不要把样本数当作事件数或用户数。`unit`、`temporality`、`trace_id` 和 `span_id` 缺失时为 `null`。`null` 值不等于零。

### 版本响应

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "release": "api@1.2.3",
  "environment": "production",
  "service_name": "checkout-api",
  "issue_count": 3,
  "log_count": 824,
  "trace_span_count": 421,
  "action_count": 19,
  "metric_count": 87,
  "first_seen_at": "2026-06-01T12:00:00Z",
  "last_seen_at": "2026-06-01T12:15:00Z",
  "trace_health": {
    "status": "errors_observed",
    "trace_count": 42,
    "error_trace_count": 3,
    "error_rate_basis_points": 714
  },
  "next_action": {
    "code": "inspect_release_issues",
    "target": "telemetry_issues"
  }
}
```

1 行对应 1 个项目、版本、环境和服务的组合。行内的数量只描述该行。

`trace_health.status` 的值为 `unknown`（该行没有链路）、`no_errors_observed` 或 `errors_observed`。`error_rate_basis_points` 是含有错误 Span 的链路所占的比例，取值从 `0` 到 `10000`。它不是所有请求的错误率。

`next_action` 按以下顺序指向第一个有数据的信号类型：

| `code` | `target` |
| --- | --- |
| `inspect_release_issues` | `telemetry_issues` |
| `inspect_release_traces` | `trace_explorer` |
| `inspect_release_logs` | `telemetry_logs` |
| `inspect_release_actions` | `telemetry_actions` |
| `inspect_release_metrics` | `telemetry_metrics` |
| `review_release_telemetry` | `telemetry_reads` |

请参阅[版本](/zh-Hans/concepts/releases)。

### 链路发现响应

`GET /api/telemetry/traces?pagination=cursor` 为每条链路返回 1 行，并为返回的这一页附上 `naming_quality` 回执：

```json
{
  "traces": [
    {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "project_ids": ["123e4567-e89b-12d3-a456-426614174000"],
      "root_span_name": "POST /checkout",
      "root_service_name": "checkout-api",
      "root_operation": "http.server",
      "span_count": 3,
      "error_span_count": 1,
      "service_count": 1,
      "started_at": "2026-06-01T12:00:00Z",
      "duration_ms": 45,
      "services": ["checkout-api"],
      "releases": ["checkout@1.2.3"],
      "environments": ["production"],
      "next_action": {
        "code": "inspect_trace",
        "target": "trace_summary"
      }
    }
  ],
  "next_cursor": null,
  "naming_quality": {
    "evaluated_traces": 1,
    "meaningful_name_traces": 1,
    "generic_name_traces": 0,
    "unmatched_route_traces": 0,
    "generic_operation_traces": 0,
    "truncated": false,
    "next_action": null
  }
}
```

`naming_quality` 只涵盖返回的这一页，不是整个账号的评分。`truncated: true` 表示还有下一页。当这一页里有通用名称、未匹配的路由或通用操作名时，`next_action` 为 `improve_trace_naming`，目标为 `sdk_configuration`。不使用 `pagination=cursor` 时，路由返回不带外层对象的链路数组，且没有 `naming_quality`。

`next_cursor` 包含 `time` 和 `trace_id`。把它们作为 `cursor_time` 和 `cursor_trace_id` 发送。

`GET /api/telemetry/traces/{trace_id}` 返回 1 条链路的所有 Span。`GET /api/telemetry/traces/{trace_id}/summary` 返回根 Span、错误 Span、服务、耗时和最慢路径，不含原始 Span 属性。摘要返回 `404` 表示没有链路匹配完整的范围。不要去掉筛选条件后重试。请参阅[链路 Span 与摘要响应](#trace-spans-and-summary-responses)。

### 空列表与缺失的记录

列表读取可能没有匹配结果。详情读取遵循不同的约定：

| 请求 | 成功 | 没有可读取的记录 |
| --- | --- | --- |
| `GET /api/logs/{log_id}` | `200`，含 1 条[日志](#log-response) | `404` 和 `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}` | `200`，含 1 个[问题](#issue-response) | `404` 和 `code: not_found` |
| `GET /api/telemetry/issues/{issue_id}/events` | `200`，含发生记录 | 第一页返回 `404` 和 `code: not_found` |
| `GET /api/telemetry/traces/{trace_id}` | `200`，含 Span | `200` 和 `[]` |
| `GET /api/telemetry/traces/{trace_id}/summary` | `200`，含 1 份摘要 | `404` 和 `code: not_found` |

缺失的日志返回以下 `404`：

```json
{
  "error": "log not found",
  "code": "not_found",
  "next": "check the resource id or filters and retry",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

缺失的问题使用 `"error": "issue not found"`。缺失的链路摘要使用 `"error": "trace not found"`。未知的 ID 和账号无法读取的 ID 返回相同的响应。

如果列表只指定了 1 个 `project_id`，而账号无法读取该项目，会返回 `200` 和空列表。报告“没有数据”之前，先检查项目 ID。

### 被拒绝的项目选择

日志、问题、操作、指标、版本和链路列表接受用 `project_id` 指定 1 个项目，或用 `project_ids` 指定 2 到 50 个项目。日志属性目录接受同样的选择参数。问题发生记录历史不接受这些参数。

同时包含 `project_id` 和 `project_ids` 的请求返回 `422`：

```json
{
  "error": "project_id and project_ids are mutually exclusive",
  "code": "validation_failed",
  "next": "use project_id for one project, project_ids=uuid,uuid for two to fifty projects, or omit both for all readable projects",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

如果 `project_ids` 包含无效的 UUID、重复的 ID，或 ID 少于 2 个、多于 50 个，也会返回 `422` 和 `code: validation_failed`。

如果账号无法读取 `project_ids` 中的某个项目，整个请求都返回 `404`，不会把其他项目作为部分结果返回：

```json
{
  "error": "project selection not found",
  "code": "not_found",
  "next": "refresh readable projects and retry with only project IDs you can read",
  "next_action": {
    "code": "check_resource",
    "target": "resource"
  }
}
```

显示这个错误，不要显示空列表或零计数。重新读取项目列表。不要悄悄移除某个项目，也不要改为在所有项目中重试。委托凭据（例如 MCP 授权）访问其授权范围之外的项目时，返回 `403` 和 `code: forbidden`。请参阅[项目范围](/zh-Hans/reference/telemetry-api-filters#project-scope)。

### <span id="cursor-errors">游标错误</span>

日志、问题、操作、指标和问题发生记录使用 `cursor_time` 和 `cursor_id`。被拒绝的游标返回 `422` 和 `code: validation_failed`。这些错误不表示列表为空。

| 请求 | `error` |
| --- | --- |
| `pagination=cursor`，但只有 2 个游标字段中的 1 个 | `cursor_time and cursor_id must be sent together` |
| `cursor_time` 不是 RFC3339 时间戳 | `cursor_time must be an RFC3339 timestamp` |
| 有游标字段但没有 `pagination=cursor`，或 `pagination` 为其他值 | `pagination must be cursor when cursor pagination is requested` |

例如：

```json
{
  "error": "cursor_time and cursor_id must be sent together",
  "code": "validation_failed",
  "next": "send pagination=cursor alone for the first page, then send cursor_time and cursor_id together from next_cursor",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

从上一页完整复制 `next_cursor`。不要用当前时间替换 `cursor_time`。如果丢失了游标，用 `pagination=cursor` 和原始筛选条件从头开始。未知的查询键或类型错误的值返回 `422` 和 `"error": "invalid query parameters"`。

### 版本游标响应

版本游标有 5 个字段。请求成功但没有匹配结果时返回 `200`：

```json
{
  "releases": [],
  "next_cursor": null
}
```

`next_cursor` 不为 `null` 时，在下一个请求中发送全部 5 个值：

| `next_cursor` 字段 | 查询参数 |
| --- | --- |
| `time` | `cursor_time` |
| `project_id` | `cursor_project_id` |
| `release` | `cursor_release` |
| `environment` | `cursor_environment` |
| `service_name` | `cursor_service_name` |

`cursor_project_id` 只标记位置，不能代替 `project_id` 或 `project_ids`。保留原始的项目和筛选参数。对每个值进行 URL 编码。

使用 `pagination=cursor` 时，游标不完整，或版本、环境、服务的值为空，都会返回 `422` 和 `"error": "all release cursor fields must be sent together"`。无效的 `cursor_time` 和缺少 `pagination=cursor` 返回的错误与[其他游标](#cursor-errors)相同。

### 链路发现错误

以下错误适用于 `GET /api/telemetry/traces`。每种错误都返回 `422` 和 `code: validation_failed`。被拒绝的请求不等于空结果。

| 请求 | `error` |
| --- | --- |
| `status` 不是 `error` 或 `ok` | `trace status must be error or ok` |
| `min_duration_ms` 小于 `0` | `minimum trace duration must not be negative` |
| 只有 1 个游标字段，或 `cursor_trace_id` 为空 | `cursor_time and cursor_trace_id must be sent together` |
| `cursor_time` 不是 RFC3339 时间戳 | `cursor_time must be an RFC3339 timestamp` |
| 有游标字段但没有 `pagination=cursor` | `pagination must be cursor when cursor pagination is requested` |

要同时包含两种链路状态，省略 `status`。读取下一页时，把 `next_cursor.time` 复制到 `cursor_time`，把 `next_cursor.trace_id` 复制到 `cursor_trace_id`。读取链路分页时不要发送 `cursor_id`。请参阅[链路筛选条件](/zh-Hans/reference/telemetry-api-filters#trace-filters)。

### <span id="issue-occurrence-history">问题发生记录历史</span>

`GET /api/telemetry/issues/{issue_id}/events` 读取 1 个分组问题的发生记录。使用账号 Bearer 令牌和分组问题 ID。该路由只接受 `pagination`、`cursor_time`、`cursor_id` 和 `limit`，不接受项目、时间、版本、环境或严重程度筛选条件。

```bash
curl --get "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/events" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "pagination=cursor" \
  --data-urlencode "limit=1"
```

包含 1 条发生记录和续读游标的第一页：

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [
    {
      "id": "db619770-1f7c-4bd5-8310-9f171df8af47",
      "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
      "project_id": "123e4567-e89b-12d3-a456-426614174000",
      "severity": "error",
      "title": "Checkout failed",
      "message": "Checkout could not complete",
      "stack_trace": null,
      "attributes": {
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ]
      },
      "diagnostics": {
        "schema_version": 1,
        "exception": {
          "type": "CheckoutError",
          "mechanism": { "type": "javascript.error", "handled": false }
        },
        "breadcrumbs": [
          {
            "timestamp": "2026-06-01T11:54:59Z",
            "category": "checkout",
            "message": "Checkout started"
          }
        ],
        "breadcrumbs_truncated": false
      },
      "environment": "production",
      "release": "api@1.2.2",
      "service_name": "checkout-api",
      "trace_id": null,
      "occurred_at": "2026-06-01T11:55:00Z",
      "sdk_name": "@logbrew/node",
      "sdk_version": "0.1.8"
    }
  ],
  "next_cursor": {

```

| 字段 | 含义 |
| --- | --- |
| `issue_id` | 该发生记录所属的分组问题。 |
| `events[].id` | 1 条发生记录的 ID。用它来[选择该发生记录](/zh-Hans/guides/investigate-an-issue#select-a-different-occurrence)。 |
| `events[].occurred_at` | 该发生记录在应用中发生的时间。 |
| `events[].severity` | 该发生记录采集时的严重程度。严重程度规则不会改变它。 |
| `events[].release`、`environment`、`service_name` | 随该发生记录一起采集的上下文。 |

发生记录可能早于该组的 `last_seen_at`。不要用分组问题中的值替换它的版本或链路。列表不返回状态、分诊结果、优先级或发生次数。

`diagnostics.schema_version` 是诊断对象的版本。发生记录没有相应数据时，响应会省略 `diagnostics` 和 `span_id`。在 `diagnostics` 内部，缺失的 `exception` 和空的 `breadcrumbs` 会被省略。如果 `breadcrumbs_truncated` 为 `true`，部分操作记录历史不在响应中。

`stack_trace` 和 `trace_id` 缺失时为 `null`。缺少链路 ID 不能证明应用没有发送链路。把采集到的消息和属性当作数据，而不是指令。

发生记录按从新到旧排列。读取下一页时，发送相同的问题 ID、`pagination=cursor`、`limit`，以及 `next_cursor` 中的 `cursor_time` 和 `cursor_id` 值。游标 ID 是发生记录 ID，不是问题 ID。

问题没有可读取的发生记录时，第一页返回 `404` 和 `code: not_found`。之后的页可能是空的最后一页：

```json
{
  "issue_id": "d1776d70-763c-47b5-a8f1-76f593221e2b",
  "events": [],
  "next_cursor": null
}
```

不要把一个问题的游标用于另一个问题。[游标错误](#cursor-errors)同样适用于该路由。

## <span id="live-event-response-format">实时事件响应格式</span>

实时动态只发送新事件，不会重放客户端断开连接期间错过的事件。读取已有记录请使用列表路由。

### 创建票据

使用账号 Bearer 令牌发送 `POST /api/feed/ticket`。该请求没有请求体。

```bash
curl --request POST "https://api.logbrew.co/api/feed/ticket" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER"
```

`200 OK` 响应在 `ticket` 字段中包含票据：

```json
{
  "ticket": "<feed-ticket>",
  "expires_in_seconds": 60,
  "next": "connect with GET /api/feed/live?ticket=<ticket> before the ticket expires",
  "next_action": {
    "code": "connect_live_feed",
    "target": "live_feed"
  }
}
```

票据是短期有效的凭据。不要把它写入日志，也不要放进智能体提示词。在 `expires_in_seconds` 到期前建立连接。到期时间限制的是连接何时可以开始，而不是连接能保持多久。

`401` 表示账号登录状态无效。请先重新登录，再请求票据。使用 `POST` 以外的方法时，返回 `405` 和 `code: method_not_allowed`。

### 建立连接

用 WebSocket 客户端连接到 `wss://api.logbrew.co/api/feed/live?ticket=<feed-ticket>`。对票据进行 URL 编码。不要把账号 Bearer 令牌或接入 Bearer 令牌放进 URL。`401` 表示票据或账号登录状态无效。重新登录后，创建新的票据。

| 响应 | 原因 | 下一步 |
| --- | --- | --- |
| `422` 和 `"error": "feed ticket is required"` | `ticket` 查询值缺失或为空。 | 创建票据，并用它连接。 |
| `401` 和 `code: unauthorized` | 票据已过期或无效。 | 创建新的票据。不要用同一张票据重试。 |
| `code: invalid_websocket_upgrade` | 该请求不是有效的 WebSocket 升级请求。 | 使用 WebSocket 客户端。 |
| `405` 和 `code: method_not_allowed` | 该请求没有使用 `GET`。 | 使用 `GET` 建立连接。 |

出错后先等待，再重新连接。不要在紧凑的循环中反复重连。

### 读取消息

每条消息都是 `{ "type": "...", "data": ... }` 封装。先读取 `type`，再解析 `data`。跳过客户端不支持的类型。

| 事件类型 | 数据负载 |
| --- | --- |
| `native_log` | 日志数据，结构与[日志响应](#log-response)相同。 |
| `native_issue` | 分组问题数据，结构与版本 1 的[问题响应](#issue-response)相同。 |
| `native_trace_span` | 1 个 Span，结构与 [Span 列表](#span-list)中的条目相同。 |
| `native_action` | 产品操作数据，结构与[操作响应](#action-response)相同。 |
| `project_created`、`project_updated`、`project_catalog_changed` | 项目数据。项目发生变化时，重新读取项目列表。 |
| `usage_updated`、`usage_limit_warning`、`usage_limit_blocked` | 账号用量，结构与[账号用量](/zh-Hans/reference/account-api#account-usage)相同。 |

```json
{
  "type": "native_log",
  "data": {
    "id": "150d1288-bec2-49ec-a036-3f7ac55f1b2d",
    "project_id": "123e4567-e89b-12d3-a456-426614174000",
    "level": "warning",
    "severity": "warning",
    "triage": {
      "effective_severity": "warning",
      "ignored": false,
      "rule_applied": false
    },
    "source": "runtime",
    "message": "checkout retry scheduled",
    "attributes": { "route": "/checkout" },
    "occurred_at": "2026-06-01T12:00:00Z",
    "environment": "production",
    "release": "api@1.2.3",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "service_name": "checkout-api",
    "sdk_name": "@logbrew/node",
    "sdk_version": "0.1.8",
    "next_action": {
      "code": "inspect_trace",
      "target": "trace_summary"
    }
  }
}
```

`native_issue` 事件使用问题响应版本 1：已归档的问题显示为 `ignored`，事件中没有优先级。指标和版本不是实时事件类型，请用各自的列表路由读取。票据不选择项目。在项目视图中显示每个事件之前，先检查它的 `project_id`。`logbrew watch --json` 使用的就是这个实时动态。请参阅 [CLI 参考](/zh-Hans/reference/cli)。

### 处理已关闭的连接

| 关闭代码 | 原因 | 下一步 |
| --- | --- | --- |
| `1013` | `live feed fell behind; reconnect to resync` | 等待片刻，然后用新票据重新连接。重新读取列表路由，获取错过的记录。 |
| `1008` | `live feed access changed; sign in again` | 停止重连。重新登录后再创建新票据。 |

其他断开连接的情况可能没有 LogBrew 给出的原因。重新连接后，再次读取列表路由，并按 ID 匹配记录。

## <span id="issue-status-response-examples">问题状态响应示例</span>

使用 `{ "status": "resolved" }` 调用 `PATCH /api/telemetry/issues/{issue_id}` 会返回 `200 OK` 和更新后的分组问题，结构与[问题响应](#issue-response)相同。查询键 `response_version` 用于选择版本。该请求不返回表示成功的标志。

请求体设置 `status`、`priority` 和 `assignee` 中的 1 个或多个。`status` 接受 `unresolved`、`resolved` 或 `archived`。`ignored` 是 `archived` 的旧名称。请参阅[更新单个问题](/zh-Hans/reference/telemetry-api#update-one-issue)。

显示成功之前，先检查返回的 `id`、`status` 和 `priority`。不要根据提交的值拼出结果。状态更改不会删除发生记录，也不会改变 `first_seen_at` 和 `last_seen_at`。它不会改变 `severity` 或严重程度规则。

被拒绝的更改返回 `422` 和 `code: validation_failed`：

```json
{
  "error": "issue status must be unresolved, resolved, or archived",
  "code": "validation_failed",
  "next": "use status=unresolved, status=resolved, or status=archived",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| 结果 | 原因 |
| --- | --- |
| `422`，`issue update requires status, priority, or assignee` | 请求体不含这 3 个字段中的任何一个。 |
| `422`，`issue priority must be high, medium, or low` | 不支持该优先级值。 |
| `422`，`issue assignee must be me, none, a user ID, or team:<team_id>` | 不支持该负责人值。 |
| `422`，`issue assignee cannot read this project` | 该负责人无权访问该项目。LogBrew 不做任何更改。 |
| `422`，`issue assignee team is not a team of this project's organization` | 该团队不属于该项目所在的组织。LogBrew 不做任何更改。 |
| `403` 和 `code: forbidden` | 该账号无法管理该项目中的问题。 |
| `404` 和 `code: not_found` | 该账号无法读取该问题，或该问题不存在。 |

已经是所请求值的字段不会变化。超时或响应丢失后，重新发送同一个请求，或先读取该问题。读取当前状态之前，不要发送不同的更改。请参阅[写入请求](/zh-Hans/reference/api-errors#writes)。

`POST /api/telemetry/issues/bulk` 返回 `200 OK`，按请求顺序为每个请求的问题 ID 给出 1 个结果。找到的每个问题都使用版本 3 的结构。`not_found` 结果包含 `issue: null`：

```json
{
  "project_id": "123e4567-e89b-12d3-a456-426614174000",
  "results": [
    {
      "issue_id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
      "outcome": "updated",
      "issue": {
        "id": "9b2b4b3a-bd4e-4f85-a0f6-48118f037c17",
        "status": "archived",
        "priority": "high",
        "priority_source": "derived",
        "assignee": null
      }
    },
    {
      "issue_id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
      "outcome": "not_found",
      "issue": null
    }
  ]
}
```

本示例只显示部分问题字段。`outcome` 为 `updated`、`unchanged` 或 `not_found`。重复的请求返回 `unchanged`，不做任何更改。请参阅[批量更新问题](/zh-Hans/reference/telemetry-api#update-issues-in-bulk)。

在以下情况下，整个批量请求都会失败：

| 结果 | 原因 |
| --- | --- |
| `422`，`issue_ids must name 1 to 100 issues` | 列表为空，或包含超过 100 个 ID。 |
| `422`，`issue_ids must not contain duplicates` | 某个 ID 出现了不止 1 次。 |
| `422` 和 `code: invalid_json` | 请求体包含未知字段。 |
| `403` 和 `code: forbidden` | 该账号无法管理该项目中的问题。 |
| `404`，`project not found` | 该账号无法读取该项目。 |

## 分析请求范围

分析路由、指标序列路由和信号数量路由读取 1 个项目和 1 个时间范围。每个请求都需要 `project_id` 和 `since`。`since` 接受 `24h` 或 `7d` 这样的简写时长，或 RFC3339 时间戳。`until` 接受 RFC3339 时间戳，默认为请求时间。时间范围包含 `since`，不包含 `until`，且不能超过 31 天。

`service_name`、`release` 和 `environment` 是可选的精确筛选条件。LogBrew 去掉首尾空格后，每个值必须为 1 到 256 个字符。分群对比路由把这些筛选条件放在每个分群内部，而不是顶层。

如果账号无法读取该项目，这些路由返回 `200 OK` 和零计数，不会返回 `404`。空结果不能确认项目访问权限。把 `project_id` 与该账号可读取的项目进行比较。通过不包含该项目的 MCP 授权发出的请求返回 `403` 和 `forbidden`。

| 路由 | `response_version` 值 | 默认值 |
| --- | --- | --- |
| `GET /api/telemetry/analytics/overview` | `1`、`2` 或 `3` | `1` |
| `GET /api/telemetry/analytics/properties` | `1` 或 `2` | `1` |
| `POST /api/telemetry/analytics/segments/compare` | `1` 或 `2` | `1` |
| `POST /api/telemetry/analytics/retention` | `1` 或 `2` | `1` |
| `POST /api/telemetry/analytics/lifecycle` | `1` 或 `2` | `1` |
| `POST /api/telemetry/analytics/funnel` | 不接受 | 结构版本 `1` |
| `POST /api/telemetry/analytics/paths` | 不接受 | 结构版本 `1` |
| `GET /api/telemetry/metrics/series` | 不接受 | 结构版本 `1` |
| `GET /api/telemetry/summary/volume` | `1` | `1` |

每个响应都以 `schema_version`、`query` 和 `purpose` 开头。`query` 回显实际生效的范围，省略你没有发送的筛选条件。`purpose` 是纯文本，说明该路由回答什么问题。

分母为零时，比率会被省略。省略的比率既不是 `0`，也不是 `null`。信任某个比率之前，先读取 `coverage`。

### <span id="shared-scope-errors">通用范围错误</span>

以下错误使用 HTTP `422` 和 `validation_failed`：

| 原因 | `error` |
| --- | --- |
| 没有 `project_id` | `product analytics project_id is required` |
| 没有 `since` | `product analytics since is required` |
| `since` 既不是时长，也不是 RFC3339 时间戳 | `invalid since value` |
| `until` 不是 RFC3339 时间戳 | `product analytics until must be an RFC3339 timestamp` |
| `since` 不早于 `until` | `product analytics since must be earlier than until` |
| 时间范围超过 31 天 | `product analytics range must not exceed 31 days` |
| 筛选条件为空，或超过 256 个字符 | `product analytics context filters must be non-empty and at most 256 characters` |

例如，不带 `project_id` 的请求返回：

```json
{
  "error": "product analytics project_id is required",
  "code": "validation_failed",
  "next": "choose one owned project and send its project_id",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

指标序列路由和信号数量路由使用同样的范围规则，但有各自的 `error` 文本。下文对应的小节列出了这些错误。

未知的查询键返回 `422` 和[无效的查询参数](/zh-Hans/reference/api-errors#invalid-query-parameters)响应。未知的 JSON 字段、缺少必填的 JSON 字段或不支持的枚举值返回 `invalid_json`。请参阅[无效的 JSON](/zh-Hans/reference/api-errors#invalid-json)。使用错误 HTTP 方法的请求返回 `405` 和 `method_not_allowed`，其 `next` 文本会指出受支持的方法和字段。请参阅[不支持的方法](/zh-Hans/reference/api-errors#unsupported-method)。

## 产品分析概览响应

`GET /api/telemetry/analytics/overview` 显示 1 个项目中的活动：操作量、用户、会话、时间序列、热门操作，以及已分类的页面浏览、屏幕浏览和互动。用它查找其他分析路由所需的准确事件名称。

发送 `response_version=3`。版本 1 和 2 返回相同的计数，但 `estimation.method` 使用旧的标记值。版本 1 统计已识别用户时不检查主体类型。版本 2 和 3 只统计类型为 `user` 的主体，并增加了匿名主体计数和 `subject_coverage`。

以下请求以 5 分钟为时间桶读取 1 小时的数据，每个热门列表返回 2 行：

```bash

  --data-urlencode "until=2026-06-01T12:00:00Z" \
```

### 解读概览

5 个 `subject_coverage` 计数相加等于所在部分的事件总数。只有 `identified_user_events` 计入用户。`anonymous_actions` 等于 `summary.actions` 减去 `identified_actions`。

`series` 只包含有活动的时间桶。`expected_buckets` 是该时间范围内可能的时间桶数。除非图表注明了这条规则，否则不要把缺失的时间桶画成实测的零。时间桶按 UTC 时间间隔边界对齐。如果时间范围从某个时间桶中间开始，结果会包含这个不完整的时间桶。

`classified_activity` 统计页面浏览、屏幕浏览和互动。屏幕浏览和互动同时也是操作，页面浏览不是。不要把 `summary.actions` 加到 `classified_activity.summary.events` 上。

把 `classified_activity.top_events` 中的 `kind` 和 `event_name` 复制到漏斗步骤、留存选择器、生命周期选择器、路径锚点和分群目标中。`top_events_truncated` 为 `true` 表示还有出现次数更少的名称未列出。把 `top_limit` 调高（最多 20）可以看到更多。

`analysis_level` 为 `no_data`、`event_only`、`user_level` 或 `user_and_session`。如果项目没有操作，也没有已分类的事件，`next_action.code` 为 `capture_product_activity`。请参阅[产品分析](/zh-Hans/concepts/product-analytics#use-the-analytics-api)。

### <span id="overview-errors">概览错误</span>

除[通用范围错误](#shared-scope-errors)外，概览在遇到以下值时返回 `422` 和 `validation_failed`：

| 值 | `error` |
| --- | --- |
| `response_version` 不是 `1`、`2` 或 `3` | `product analytics response_version must be 1, 2, or 3` |
| `top_limit` 不在 `1` 到 `20` 之间 | `product analytics top_limit must be between 1 and 20` |
| `interval` 不是 `auto`、`1m`、`5m`、`15m`、`1h`、`6h` 或 `1d` | `product analytics interval is not supported` |
| 显式指定的 `interval` 需要超过 500 个时间桶 | `product analytics interval would exceed 500 buckets` |

`interval` 默认为 `auto`，会选择所需时间桶不超过 300 个的最小间隔。`top_limit` 默认为 `10`。

## <span id="ordered-funnel-response">有序漏斗响应</span>

`POST /api/telemetry/analytics/funnel` 衡量 2 到 8 个步骤的按顺序完成情况。从概览的 `classified_activity.top_events` 中复制每个准确的 `kind` 和 `event_name`。名称相似的操作不算匹配。以下请求体统计先浏览 `/pricing`、然后在 1 小时内完成注册的会话：

```json

  "steps": [
```

`analysis_unit` 为 `session` 或 `identified_user`，默认为 `session`。步骤的 `kind` 为 `page_view`、`screen_view` 或 `interaction`。漏斗路由不接受 `response_version`。

比率是 0 到 1 之间的小数。信任某个比率之前，先读取 `coverage`。`selected_unit_coverage_rate` 是 LogBrew 能够使用的所选步骤事件所占的比例。响应不返回原始身份信息。请参阅[产品分析](/zh-Hans/concepts/product-analytics#measure-a-funnel)。

### 解读转化率和覆盖率

`entry_rate` 等于 `entered_units` 除以 `candidate_units`：60 个中有 50 个。`overall_conversion_rate` 等于 `completed_units` 除以 `entered_units`：50 个中有 15 个，即 30%。它不是 15 除以所有候选单位。这些计数无法说明单位为什么中途流失。

覆盖率统计的是事件，不是会话。这里有 120 个事件匹配某个步骤，其中 20 个没有会话 ID。结果在会话计数中排除了这 20 个事件。不要把它们当作 20 个失败的会话。

第一个步骤没有 `conversion_from_previous`。最后一个步骤没有 `drop_off_to_next_units`，也没有 `drop_off_to_next_rate`。

只有各步骤的时间严格递增时，单位才会到达后面的步骤。时间戳相同的事件不能同时满足两个相邻步骤。最后一个步骤必须在第一个步骤之后的 `conversion_window_seconds` 内发生。

会话模式统计的是会话，不是人。只有事件带有类型为 `user` 的不透明主体 ID 时，才使用 `identified_user`。该模式可以把转化窗口内不同会话中的事件关联起来。比较结果时，保持相同的单位和相同的步骤。

`conversion_window_seconds` 默认取 24 小时和时间范围长度中较短的一个。最大值是时间范围的长度，以整秒计，向上取整。

### 空漏斗结果

成功但为空的响应仍会列出所请求的步骤，其 `units` 为零。如果没有候选单位，`summary` 会省略 `entry_rate` 和 `overall_conversion_rate`。路由不会因为没有事件匹配而返回 `404`。

读取 `coverage` 和 `next_action` 找出原因：

| `next_action.code` | 原因 |
| --- | --- |
| `capture_product_activity` | 该范围内没有已分类的事件。 |
| `choose_captured_funnel_steps` | 没有事件匹配所请求的步骤。 |
| `sessionize_product_activity` | 有步骤事件，但都没有会话 ID。 |
| `identify_product_users` | 有步骤事件，但都没有类型为 `user` 的主体。 |
| `verify_funnel_entry` | 没有单位进入步骤 1。 |
| `investigate_funnel_drop_off` | 有单位进入，但没有单位完成所有步骤。 |
| `compare_funnel_contexts` | 至少有 1 个单位完成了漏斗。 |

### 被拒绝的漏斗请求

除[通用范围错误](#shared-scope-errors)外，以下请求返回 `422` 和 `validation_failed`。步骤少于 2 个或多于 8 个：

```json
{
  "error": "product analytics funnel requires two through eight ordered steps",
  "code": "validation_failed",
  "next": "send a steps array containing 2 through 8 exact classified event selectors",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`conversion_window_seconds` 为 `0`，或大于时间范围的长度：

```json
{
  "error": "product analytics funnel conversion window must fit inside the query range",
  "code": "validation_failed",
  "next": "use conversion_window_seconds from 1 through the selected range length",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

`event_name` 为空、超过 256 个字符或包含控制字符时，返回 `product analytics funnel event_name must be non-empty, control-free, and at most 256 characters`。`interaction` 步骤还必须是有效的操作名称，否则错误为 `product analytics interaction event_name must be a bounded stable action name`。

先修正请求，再重新发送。不要只为了得到非空结果而删除步骤或更改分析单位。

## 精确事件分析与自动分析

留存和生命周期接受两种请求结构。用 `response_version` 选择能回答你问题的结构：

| 分析 | `response_version` | 事件选择器 |
| --- | --- | --- |
| 精确事件的留存 | `1`，或省略 | 同时发送 `start_event` 和 `return_event`。 |
| 单个精确事件的生命周期 | `1`，或省略 | 发送 `event`。 |
| 自动留存或自动生命周期 | `2` | 不发送事件选择器。 |

精确选择器包含 `kind` 和 `event_name`。`kind` 为 `page_view`、`screen_view` 或 `interaction`。从 `classified_activity.top_events` 复制 `event_name`。不要根据按钮文字猜测事件名称。

两种结构都只统计用户，即类型为 `user` 的不透明主体 ID。匿名主体和没有可用主体 ID 的事件不计为用户。响应从不返回主体 ID。

固定间隔为 `hour`、`day`、`week` 和 `thirty_day`，都是固定时长。`thirty_day` 是 30 天，不是日历月。如果省略 `interval`，时间范围不超过 48 小时时 API 使用 `hour`，更长时使用 `day`。

### 解读生命周期

6 月 1 日，A 为持续活跃，B 为重新活跃，C 为新增，D 为休眠。6 月 2 日，A 和 B 为持续活跃；C 虽然浏览了页面，但对结账而言处于休眠状态。6 月 2 日的净变化为 `2 - 3 = -1`。

在每个时间桶中，新增、持续活跃和重新活跃的用户数相加等于 `active_subjects`。`returning_subjects` 加 `dormant_subjects` 等于 `previous_active_subjects`。`net_active_change` 等于 `active_subjects` 减去 `previous_active_subjects`。

不要把每日活跃数相加来得到去重用户数。这里每日计数相加为 5，但 `analysis_active_subjects` 为 3。历史和分析期间一共出现了 4 个不同的用户。

如果最后一个时间桶在 `until` 之后才结束，它的 `fully_observed` 为 `false`。等整个周期都可观测时，它的计数可能会变化。`next_action` 建议的是一个排查方向，并不表明原因。

### 自动生命周期

发送 `response_version: 2`，且不发送 `event` 选择器。每个受支持的页面浏览、屏幕浏览和互动都算作活动：

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T00:00:00Z",
  "until": "2026-06-03T00:00:00Z",
  "response_version": 2,
  "interval": "day",
  "history_period_count": 2
}
```

该响应的 `summary`、`buckets` 和 `next_action` 结构与精确事件响应相同。以下摘录显示有变化的字段：

```json
{
  "schema_version": 2,
  "query": {
    "project_id": "11111111-1111-4111-8111-111111111111",
    "since": "2026-06-01T00:00:00Z",
    "until": "2026-06-03T00:00:00Z",
    "history_since": "2026-05-30T00:00:00Z",
    "activity_scope": "all_classified_activity",
    "interval": "day",
    "interval_seconds": 86400,
    "history_period_count": 2,
    "expected_buckets": 2
  },
  "purpose": "Classifies typed opaque user subjects by any supported classified product activity in each fixed period. It does not choose or infer a top event. new_within_observed_history, returning, resurrected, and dormant remain disjoint; anonymous and unidentified subjects are excluded from user counts, incomplete buckets are marked, and raw identifiers are never returned."
}
```

在自动模式下，`coverage.selected_events` 等于 `coverage.analysis_classified_events`。`limitations` 的第 5 项是 `Returning, resurrected, and dormant compare any supported classified product activity; no event is ranked, selected, or inferred.`

### 没有用户的生命周期

如果分析时间范围和历史中都没有可用的用户，`buckets` 为空，`summary` 省略 `latest_fully_observed_period`：

```json
{
  "schema_version": 2,
  "summary": {
    "observed_subjects": 0,
    "analysis_active_subjects": 0,
    "history_only_subjects": 0,
    "returned_buckets": 0,
    "fully_observed_buckets": 0,
    "buckets_with_resurrection": 0,
    "buckets_with_dormancy": 0
  },
  "buckets": []
}
```

分析时间范围内没有活动时，只在历史中出现的用户仍可能产生含有休眠用户的时间桶。

### 生命周期错误

除[通用范围错误](#shared-scope-errors)外，以下请求返回 `422` 和 `validation_failed`：

| 原因 | `error` |
| --- | --- |
| 版本 1 没有 `event`，版本 2 带有 `event`，或使用了其他版本 | `product analytics lifecycle activity selection is contradictory` |
| `history_period_count` 不在 `2` 到 `31` 之间 | `product analytics lifecycle history_period_count must be between 2 and 31` |
| 历史周期总长超过 62 天 | `product analytics lifecycle history must not exceed 62 days` |
| 分析时间桶超过 100 个 | `product analytics lifecycle interval would exceed 100 analysis buckets` |

例如，10 个 `week` 历史周期需要 70 天：

```json
{
  "error": "product analytics lifecycle history must not exceed 62 days",
  "code": "validation_failed",
  "next": "use fewer history periods or a narrower fixed interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

### 读取所选的分析范围

精确事件响应带有 `schema_version: 1`。其 `query` 回显选择器，并省略 `activity_scope`。自动响应带有 `schema_version: 2` 和 `query.activity_scope: "all_classified_activity"`，并省略选择器。即使采集的活动没有任何变化，换一个选择器也可能改变结果。

| 类型和时间性 | `status` | `aggregation.code` | `value` | 其他统计值 |

### <span id="filter-the-anchor-by-property">按属性筛选锚点</span>

最多发送 4 个 `property_filters`，每个包含 1 个准确的 `key` 和 `value`。从[属性目录](#analytics-property-catalog)复制键。筛选条件只作用于锚点，不作用于锚点周围的事件。值区分大小写。有筛选条件时，`query` 会回显它们，`coverage.anchor_property_filters` 会报告：

| 字段 | 含义 |
| --- | --- |
| `context_events` | 应用属性筛选条件之前，范围内的锚点事件。 |
| `property_ready_events` | 具备所有请求键的锚点事件。 |
| `missing_property_events` | 缺少 1 个或多个请求键的锚点事件。 |
| `matching_events` | 值与所有筛选条件都匹配的锚点事件。 |
| `nonmatching_value_events` | 具备所有键但值不同的锚点事件。 |
| `property_ready_rate` | `property_ready_events` 除以 `context_events`。 |
| `match_rate` | `matching_events` 除以 `property_ready_events`。 |

缺少键和值不同需要不同的修复方法。不要把它们加在一起。请求没有属性筛选条件时，会省略该对象。

### 空路径与被拒绝的请求

空的 `paths` 数组可能是成功的 `200` 响应。读取 `summary`、`coverage` 和 `next_action`。以下代码可区分各种原因：`capture_product_activity`、`choose_captured_path_anchor`、`capture_anchor_properties`、`improve_anchor_property_coverage`、`verify_anchor_property_values`、`sessionize_product_activity` 和 `narrow_or_move_path_anchor`。

除[通用范围错误](#shared-scope-errors)外，以下请求返回 `422` 和 `validation_failed`：

| 原因 | `error` |
| --- | --- |
| `depth` 不在 `1` 到 `8` 之间 | `product analytics path depth must be between 1 and 8` |
| `path_limit` 不在 `1` 到 `20` 之间 | `product analytics path_limit must be between 1 and 20` |
| 属性筛选条件超过 4 个 | `product analytics paths accept at most four exact anchor property filters` |
| 键不在属性目录中 | `product analytics path property keys must be supported privacy-safe keys` |
| 同一个键出现 2 次 | `product analytics path property keys must be unique` |
| 值为空、超过 256 个字符，或包含控制字符 | `product analytics path property values must be non-empty, control-free, and at most 256 characters` |

例如，`depth: 0` 返回：

```json
{
  "error": "product analytics path depth must be between 1 and 8",
  "code": "validation_failed",
  "next": "use depth from 1 through 8 adjacent named events",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

## <span id="analytics-property-catalog">分析属性目录</span>

`GET /api/telemetry/analytics/properties` 列出 1 个项目中已分类产品事件上的属性键。在[分群对比](#analytics-segment-comparison)和路径锚点筛选条件中使用这些键。目录返回键和计数，从不返回属性值或身份信息。

### 读取可用的属性键

发送 `project_id` 和 `since`。也可以发送 `until`、`service_name`、`release`、`environment`、`limit` 和 `response_version`。`limit` 接受 `1` 到 `50` 个键，默认为 `20`。发送 `response_version=2` 可以获取公开的 `estimation.method` 值。

```bash
curl --get "https://api.logbrew.co/api/telemetry/analytics/properties" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --data-urlencode "project_id=<project_id>" \
  --data-urlencode "since=2026-06-01T00:00:00Z" \
  --data-urlencode "until=2026-06-02T00:00:00Z" \
  --data-urlencode "limit=20" \
  --data-urlencode "response_version=2"
```

### 属性目录成功响应

```json
    "limit": 20
```

| `coverage.properties_truncated` | 键的数量超过 `limit` 时为 `true`。缩小范围，或把 `limit` 调高（最多 50）。 |
| `coverage.values_returned` | 始终为 `false`。 |

## <span id="analytics-segment-comparison">分析分群对比</span>

`POST /api/telemetry/analytics/segments/compare` 比较 1 个项目中 2 到 4 个分群里的会话或用户到达某个准确事件的频率。分群按服务、版本、环境和属性值选择事件。第一个分群是基准。

### 定义对比

使用账号身份验证和 `Content-Type: application/json` 发送以下 JSON 请求体。这里的 `basic` 和 `premium` 是示例应用的套餐值，不是 LogBrew 的套餐：

```json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "since": "2026-06-01T11:00:00Z",
  "until": "2026-06-01T12:00:00Z",
  "interval": "1h",
  "analysis_unit": "session",
  "response_version": 2,
  "target": { "kind": "interaction", "event_name": "checkout_completed" },
  "segments": [
    {
      "key": "basic",
      "label": "Basic plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "basic" }]
    },
    {
      "key": "premium",
      "label": "Premium plan",
      "service_name": "checkout-api",
      "environment": "production",
      "property_filters": [{ "key": "tag.plan", "value": "premium" }]
    }
  ]
}
```

`target` 和 `segments` 为必填项。`analysis_unit` 为 `session` 或 `identified_user`。默认为 `session`，统计的是会话，不是人。`interval` 接受与概览相同的值，默认为 `auto`。

每个分群都需要唯一的 `key`、1 个 `label` 和一组不同的筛选条件：

- `key`：1 到 32 字节。以小写 ASCII 字母或数字开头。只能使用小写 ASCII 字母、数字、`_` 和 `-`。
- `label`：1 到 80 个字符，不含控制字符。
- `service_name`、`release`、`environment`：可选。每个值为 1 到 256 个字符，不含控制字符。
- `property_filters`：0 到 4 个筛选条件。每个键在一个分群中只能出现 1 次。事件必须匹配该分群的所有筛选条件。值区分大小写，长度为 1 到 256 个字符，LogBrew 会去掉首尾空格。

没有筛选条件的分群会选择该项目和时间范围内的所有已分类活动。分群可以重叠。两个分群的筛选条件完全相同时，即使标签或键不同，请求也无效。

### 解读比率和差异

`eligible_units` 估算分群中有已分类活动的会话数或用户数。`reached_units` 估算其中到达目标的数量。`reach_rate` 等于 `reached_units` 除以 `eligible_units`。没有所选单位 ID 的事件不计入这些单位。

基准比率为 20%，premium 比率为 30%。两者相差 10 个百分点。相对提升为 50%，而不是 10%。微小的小数误差来自浮点运算。显示时可以对比率取整，但计算时使用返回的值。基准分群没有 `comparison_to_baseline`。基准到达率为零时，会省略相对提升。

在 `query` 中，你没有发送的分群筛选条件为 `null`。空的 `property_filters` 列表会被省略。

`coverage.property_filters` 的字段与[路径锚点筛选覆盖率](#filter-the-anchor-by-property)相同。这里 `matching_events` 等于 `classified_events`。把缺少键和值不同分开处理。分群可以重叠，1 个会话可能出现在多个时间桶中。不要跨分群或跨时间桶相加单位计数。

这种对比是描述性的。`confidence.causal_inference` 为 `not_established`，`confidence.statistical_significance` 为 `not_tested`。30% 对 20% 并不能说明某个套餐带来了更多结账。

### 分群对比错误

除[通用范围错误](#shared-scope-errors)外，以下请求返回 `422` 和 `validation_failed`：

| 原因 | `error` |
| --- | --- |
| 分群少于 2 个或多于 4 个 | `product analytics segment comparison requires two through four segments` |
| 2 个分群使用相同的键 | `product analytics segment keys must be unique` |
| 2 个分群使用相同的筛选条件 | `product analytics segment filters must be unique` |
| 键不是 1 到 32 个允许的字节 | `product analytics segment keys must be 1 through 32 machine-safe bytes` |
| 标签为空、过长或包含控制字符 | `product analytics segment labels must be non-empty, control-free, and at most 80 characters` |
| 筛选值包含控制字符 | `product analytics segment filters must be control-free` |
| 1 个分群中的属性筛选条件超过 4 个 | `product analytics segments accept at most four exact property filters` |
| 键不在属性目录中 | `product analytics segment property keys must be supported privacy-safe keys` |
| 同一个属性键在 1 个分群中出现 2 次 | `product analytics segment property keys must be unique within each segment` |
| 属性值为空、过长或包含控制字符 | `product analytics segment property values must be non-empty, control-free, and at most 256 characters` |
| `response_version` 不是 `1` 或 `2` | `product analytics response_version must be 1 or 2` |

`interval` 的错误与[概览错误](#overview-errors)相同。

例如，2 个键不同但筛选条件相同的分群返回：


### 空的和被缩短的时间范围

如果没有信号匹配，5 个序列仍然都在，其数据点的计数明确为零。请求失败则是另一回事。不要用全零图表代替错误。

比较 `query.requested_since` 和 `query.since`。如果数据保留缩短了时间范围，`coverage.retention.window_clipped` 为 `true`，`limitations` 包含 `retention_window_clipped`。如果请求的时间范围已全部超出保留期，`query.bucket_count` 为 `0`，每个序列的 `points` 数组为空。这不能证明该时段内没有产生信号。

不适用任何数据保留限制时，`policy_days` 为 `null`，并省略 `cutoff`。`sampling.upstream` 始终为 `unknown`，即使 `storage_evaluation` 为 `complete` 也是如此。不要声称该响应统计了应用产生的每个信号。

### 被拒绝的信号数量请求

以下请求返回 `422` 和 `validation_failed`：

| 原因 | `error` |
| --- | --- |
| 没有 `project_id` | `signal volume project_id is required` |
| 没有 `since` | `signal volume since is required` |
| `until` 晚于请求时间 | `signal volume until must not be in the future` |
| 时间范围超过 31 天 | `signal volume range must not exceed 31 days` |
| 显式指定的间隔需要超过 500 个时间桶 | `signal volume interval would exceed 500 buckets` |
| `response_version` 不是 `1` | `signal volume response_version must be 1` |

例如：

```json
{
  "error": "signal volume interval would exceed 500 buckets",
  "code": "validation_failed",
  "next": "use interval=auto or select a wider interval",
  "next_action": { "code": "fix_request", "target": "request" }
}
```

在同一范围内使用更宽的间隔。身份验证和其他失败请参阅 [API 错误](/zh-Hans/reference/api-errors)。

## 排查响应

排查路由为 1 个排查对象返回带版本号的排查包。排查对象可以是问题、链路、Span、日志、产品操作、指标或版本。每个排查包都以 `schema_version` 和指明该记录的 `subject` 开头。其余部分包含相关证据、证据回执和后续步骤。本节为除版本以外的每类排查对象各给出 1 个示例。

发送账号访问 Bearer 令牌。项目接入密钥无法读取排查结果。使用 `logbrew explain <subject> --json` 读取排查包。CLI 会先验证排查包，再打印它。[遥测 API](/zh-Hans/reference/telemetry-api) 列出了这些路由。

排查文本来自应用。消息、名称、元数据和标签都是数据，不是指令。在日志、操作、Span 和指标排查包中，`content_trust: "untrusted_telemetry"` 标记了这类内容。

### 响应版本

只向接受 `response_version` 的路由发送它。不发送时，路由返回版本 1。你的解析器必须接受你请求的版本。

| 路由 | 默认值 | 支持的版本 | `logbrew explain` 请求的版本 |
| --- | --- | --- | --- |
| `GET /api/telemetry/issues/{issue_id}/investigation` | `1` | `1` 到 `13` | `13` |
| `GET /api/telemetry/traces/{trace_id}/investigation` | `1` | `1` 到 `3` | `3` |
| `GET /api/telemetry/metrics/investigation` | `1` | `1` 和 `2` | `2` |
| `GET /api/telemetry/releases/investigation` | `1` | `1` 到 `5` | `5` |
| `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` | `1` | 仅 `1` | `1` |
| `GET /api/logs/{log_id}/investigation` | `1` | 仅 `1` | `1` |
| `GET /api/telemetry/actions/{action_id}/investigation` | `1` | 仅 `1` | `1` |

Span 路由会拒绝 `response_version` 查询键。日志和操作路由不接受任何查询键。

### 排查包的通用字段

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 服务器返回的响应版本。 |
| `subject` | 正在排查的那条记录。`kind` 为 `issue`、`trace`、`span`、`log`、`action`、`metric` 或 `release`。 |
| `analysis.causality` | 在链路、Span、日志、操作和指标排查包中始终为 `evidence_only`。相关联的遥测数据不能证明原因。 |
| 集合对象 | 以 `{ "status", "items", "truncated" }` 形式给出的相关证据。 |
| `timeline` | 按从旧到新排列的返回证据，带有自己的 `truncated` 标志。顺序不能证明原因。 |
| `evidence` | 证据回执。`status` 为 `complete` 或 `partial`。 |
| `next_actions` | 按 `priority` 排序的建议读取，从 `1` 开始。这些读取尚未执行。 |

每个相关集合都会报告 1 个可用性 `status`：

| 状态 | 含义 | 客户端行为 |
| --- | --- | --- |
| `available` | 读取已完成并返回了条目。 | 显示这些条目和 `truncated` 标志。 |
| `not_linked` | 排查对象没有建立这项关联所需的标识符，例如链路 ID。 | 说明缺少关联。不要根据时间戳构造关联。 |
| `not_found` | 读取已完成，但没有找到已保留的证据。 | 显示空结果。 |
| `unavailable` | 可选读取失败。排查对象仍然有效。 | 继续显示排查对象。稍后重试。不要把零个条目显示为结果。 |

证据回执包含 4 个已排序的稳定字段名列表：`captured_fields`、`missing_fields`、`redacted_fields` 和 `truncated_fields`。只有后 3 个列表都为空时，`status` 才为 `complete`。已隐藏的数据不是缺失的数据。已截断的数据不是完整的数据。不要补填已隐藏或已截断的值。

### 排查上限

这些上限限制单个响应的大小。`truncated` 标志或 `truncated_fields` 中的条目表示某个上限省略了数据。

| 证据 | 上限 |
| --- | --- |
| 1 个集合中的相关条目 | 20 |
| 1 条链路读取的已保留 Span | 1,000 |
| 时间线条目 | 日志、操作和 Span 排查包为 50。链路和指标排查包为 100。 |
| 结构化属性、属性和元数据 | 64 个标量值，对象或数组最多 4 层，每个数组 16 个条目，每个字符串 512 个字符 |
| 关联时间范围 | 日志、操作或所选问题发生记录前后各 5 分钟。链路或 Span 为开始前 5 分钟到结束后 5 分钟，最长 24 小时。 |

每类排查对象的小节会列出各自的上限。

### 问题排查响应

使用 `GET /api/telemetry/issues/{issue_id}/investigation` 读取分组问题某条发生记录的证据。[排查问题](/zh-Hans/guides/investigate-an-issue)介绍了如何按顺序阅读这些证据。请求版本 13：

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/issues/$LOGBREW_ISSUE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=13" \
  --data-urlencode "selection=recommended"
```

查询键为 `response_version`、`selection` 和 `occurrence_id`。`selection` 为 `recommended`、`first` 或 `latest`，值区分大小写。在版本 2 到 13 中，省略选择器时使用 `recommended`。版本 1 返回最近一条已保留的发生记录，不接受选择器。问题列表的筛选条件不适用于这次读取。

| `occurrence_selection` | 2 | 请求的选择器、选择原因，以及所选、首次、最近和推荐的发生记录摘要。 |
| `lifecycle` | 3 | `persisted_status`、`effective_status`、状态变更记录和 `regression`。`effective_status` 可能为 `regressed`。 |
| `occurrence_analysis` | 4 | 发生趋势，以及版本、环境、服务和 SDK 的分布。 |
| `event.exception_chain` | 5 | 最多 8 个关联的异常。`relationship` 为 `reported`、`cause`、`context`、`aggregate_member` 或 `suppressed`。 |
| `event.request` | 6 | `method`、`route_template` 和 `response_status_code`。没有采集到请求时，不含该键。 |
| `grouping` | 7 | 分组 `strategy`、它的 `components`，以及堆栈帧的使用情况。 |
| `correlations.release.deployment_status` | 8 | 部署查找状态。只有找到部署时，才会出现 `deployment`、`time_since_deployment_ms` 和 `deployment_causality`。 |
| `correlations.related_issues` | 9 | 同一链路上的其他问题。 |
| `source_locator` | 10 | LogBrew 能关联时给出的代码仓库、组件、修订版本和仓库内相对文件路径。 |
| `reproduction` | 11 | `status` 为 `ready`、`partial` 或 `insufficient_evidence`。 |
| `next_actions` 代码 `verify_correction` | 12 | `reproduction.status` 为 `ready` 时出现。 |
| `impact.user_impact.count_method` | 13 | 把近似去重计数报告为 `approximate_distinct`。早期版本使用旧的值名称。`unavailable` 表示没有计数。 |

早期版本中没有后续版本新增的键。不要把缺失的键理解为 `null`。

`subject.status` 和 `lifecycle` 中的状态把已归档的问题报告为 `ignored`。问题列表和详情响应在响应版本 2 及以后使用 `archived`。

问题上限：推荐最多读取 50 条已保留的发生记录。趋势最多 30 个时间桶。每个分布最多返回 10 个值。每个堆栈最多 32 个帧。

#### 问题排查请求错误

`selection` 和 `occurrence_id` 只能用其中一个。即使两者选择同一条发生记录，也不要同时发送：

```json
{
  "error": "selection and occurrence_id are mutually exclusive",
  "code": "validation_failed",
  "next": "use response_version=2 through 13 with at most one of selection=first|latest|recommended or an exact occurrence_id copied from GET /api/telemetry/issues/{issue_id}/events",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

| HTTP | `error` | 原因 | 恢复方法 |
| --- | --- | --- | --- |
| `422` | `selection and occurrence_id are mutually exclusive` | 请求同时包含两个选择器。 | 只保留 1 个选择器。 |
| `422` | `issue occurrence selection requires response_version=2 through 13` | 请求带有选择器，但使用版本 1 或未指定版本。 | 发送 `response_version=13`，保留选择器。 |
| `422` | `issue investigation response_version must be 1 through 13` | 版本超出范围。 | 发送受支持的版本。 |
| `422` | `invalid query parameters` | 未知的键、无效的 UUID、非整数的版本，或未知的 `selection` 值。 | 修正[查询](/zh-Hans/reference/api-errors#invalid-query-parameters)。 |
| `404` | `issue occurrence not found` | 该发生记录不在该组已保留的历史中。 | 从该问题的发生记录列表中复制发生记录 ID。未经批准，不要改用 `latest` 或 `recommended`。 |
| `404` | `issue not found` | 没有可读取的项目包含该问题。 | 检查账号和问题 UUID。不要把发生记录 UUID 当作问题 ID 发送。 |

找不到发生记录不代表问题不存在。`404` 不表明其他账号能否读取该问题。

### 链路排查响应

使用 `GET /api/telemetry/traces/{trace_id}/investigation` 读取 1 条链路及其失败路径、最慢路径和相关信号。查询键为 `response_version`、`project_id`、`release` 和 `environment`，都是可选的。请求版本 3：

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "response_version=3"
```

版本 2 为每个相关问题添加 `cause` 和 `fix`。版本 3 在采集到 `span_id` 时，把它添加到相关问题、操作和指标中。

| --- | --- |

### Span 排查响应

使用 `GET /api/telemetry/traces/{trace_id}/spans/{span_id}/investigation` 读取链路中的 1 个 Span。发送 `project_id`、`environment` 和 `release`，三者都是必填项。从所选的 Span 中复制它们。不要把 Span 行的 `id` 当作 `span_id` 发送。

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/traces/$TRACE_ID/spans/$SPAN_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "environment=production" \
  --data-urlencode "release=checkout@1.2.3"
```

### 日志排查响应

使用 `GET /api/logs/{log_id}/investigation` 读取 1 条日志及其相关证据。该路由没有查询键。从日志列表中复制日志 ID。

```bash
curl --fail-with-body -sS \
  "https://api.logbrew.co/api/logs/$LOG_ID/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN"
```

这次读取可能返回日志列表筛选条件之外的证据。相关读取使用该日志的项目、环境和版本，以及日志前后各 5 分钟。附近日志还要求服务相同，但不需要链路 ID。精确链路读取需要该日志的链路 ID，并且可以包含其他服务。链路摘要使用相同的链路 ID 和范围，但不限制时间范围。

### 操作排查响应

```bash
curl --fail-with-body -sS \
```

### 指标排查响应

使用 `GET /api/telemetry/metrics/investigation` 读取 1 个项目在某个时间范围内的 1 个指标名称。响应包含当前序列、与前一个等长时间范围的比较、最新样本、链路示例和已完成的部署。版本 2 添加来自最近一个已保留样本的指标描述。版本 1 始终报告 `description_status: "not_captured"`。

```bash
curl --fail-with-body -sS -G \
  "https://api.logbrew.co/api/telemetry/metrics/investigation" \
  -H "Authorization: Bearer $LOGBREW_TOKEN" \
  --data-urlencode "project_id=$PROJECT_ID" \
  --data-urlencode "name=http.server.duration" \
  --data-urlencode "since=2026-08-02T12:00:00Z" \
  --data-urlencode "until=2026-08-03T12:00:00Z" \
  --data-urlencode "interval=5m" \
  --data-urlencode "group_by=service_name" \
  --data-urlencode "environment=production" \
  --data-urlencode "series_limit=12" \
  --data-urlencode "response_version=2"
```

`project_id`、`name` 和 `since` 为必填项。包含 `since`，不包含 `until`。`until` 默认为当前时间。比较还会读取前一个等长的时间范围。

`relative_change_percent` 等于 `(current - previous) / abs(previous) * 100`。前一个值为零或缺失时，它为 `null`。`expected_buckets_per_series` 统计的是可能的时间桶，不是有数据的时间桶。不要把空的时间桶画成零。变化附近有部署，不能证明是该部署导致了变化。

账号无法读取的项目会返回 `200 OK` 和 `analysis.status: "no_samples"`，而不是 `404`。空结果不描述其他信号类型。

| --- | --- | --- |

| `422` | `metric series interval would exceed 500 buckets` | 使用 `interval=auto` 或更宽的间隔。 |

### 排查错误

| HTTP | 路由 | `error` |
| --- | --- | --- |
| `404` | 日志 | `log not found` |
| `404` | 操作 | `action not found` |
| `404` | 链路 | `trace not found` |
| `422` | 链路 | `trace investigation response_version must be 1, 2, or 3` |
| `400` | 日志、操作、问题 | 路径中的 ID 不是 UUID 时返回 `invalid URL path parameters` |
| `422` | 问题、链路、Span、指标 | 未知的键或类型错误的值返回 `invalid query parameters` |

`404` 表示没有可读取的项目包含该记录。每个路由在缺少有效身份验证时还会返回 `401`，在使用 `GET` 以外的方法时返回 `405`。[未找到](/zh-Hans/reference/api-errors#resource-not-found)、[路径](/zh-Hans/reference/api-errors#invalid-path-value)、[身份验证](/zh-Hans/reference/api-errors#authentication-failure)和[方法](/zh-Hans/reference/api-errors#unsupported-method)响应请参阅 [API 错误](/zh-Hans/reference/api-errors)。

可选的证据读取可能在 `200 OK` 响应内部失败。此时该集合报告 `unavailable`。不要把它显示为 `not_found` 或零条记录。

## <span id="severity-values">严重程度值</span>

面向用户的严重程度值为 `info`、`warning`、`error` 和 `critical`。SDK 和运行时可以发送常见别名，例如 `trace`、`debug`、`warn` 或 `fatal`。REST 和实时响应始终返回规范值。例如，LogBrew 接受输入的 `warn`，并返回 `warning`。数据接收会拒绝未知的严重程度值。

| 别名 | 规范值 |
| --- | --- |
| `trace`、`debug` | `info` |
| `warn` | `warning` |
| `fatal` | `critical` |

## <span id="severity-rule-responses">严重程度规则响应</span>

严重程度规则会改变 LogBrew 显示日志或问题的方式，但不会改变应用采集时的严重程度。日志和问题会返回 `triage` 对象：

| 字段 | 含义 |
| --- | --- |
| `effective_severity` | 要显示的严重程度。没有规则时，它等于 `severity`。 |
| `ignored` | 日志规则忽略了该日志，或问题已归档时为 `true`。 |
| `rule_applied` | 严重程度规则或已忽略状态生效时为 `true`。`false` 是默认值，不表示数据缺失。 |

显示时使用 `triage.effective_severity`。把 `severity` 保留为采集时的值。日志列表默认省略已忽略的日志。要包含它们，在 `GET /api/logs` 上发送 `status=ignored` 或 `status=all`。

账号必须有权管理该项目中的问题，只有读取权限是不够的。没有该权限时，规则更改返回 `403` 和 `code: forbidden`。

### 更改日志规则

`PUT /api/logs/{log_id}/triage-rule` 为该日志以及之后具有相同签名的日志设置规则。请求体需要同时包含 `severity` 和 `ignored`：

```bash
curl --request PUT "https://api.logbrew.co/api/logs/$LOG_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "info", "ignored": true }'
```

`200 OK` 响应包含完整的[日志](#log-response)。其 `severity` 仍为 `warning`，`triage` 显示该规则：

```json
{
  "severity": "warning",
  "triage": {
    "effective_severity": "info",
    "ignored": true,
    "rule_applied": true
  }
}
```

以下摘录只显示有变化的字段。请求中的 `severity` 为 `source`、`info`、`warning`、`error` 或 `critical`。`source` 会恢复采集时的严重程度，但不会让已忽略的日志重新生效。要再次显示该日志，发送 `"ignored": false`。

### 更改问题规则

`PUT /api/telemetry/issues/{issue_id}/triage-rule` 设置分组问题及其之后发生记录的显示严重程度。请求体只接受 `severity`：

```bash
curl --request PUT "https://api.logbrew.co/api/telemetry/issues/$ISSUE_ID/triage-rule" \
  --header "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
  --header "Content-Type: application/json" \
  --data '{ "severity": "warning" }'
```

`200 OK` 响应包含版本 1 的完整[问题](#issue-response)。采集时的 `severity` 和 `status` 不会改变：

```json
{
  "severity": "error",
  "status": "unresolved",
  "triage": {
    "effective_severity": "warning",
    "ignored": false,
    "rule_applied": true
  }
}
```

以下摘录只显示部分字段。规则不会解决、归档或重新打开问题。要执行这些更改，使用[状态更改](#issue-status-response-examples)。自动推导的优先级会跟随新的有效严重程度。用 `response_version=2` 或 `3` 读取问题即可看到它。

不支持的严重程度返回 `422`：

```json
{
  "error": "triage severity must be source, info, warning, error, or critical",
  "code": "validation_failed",
  "next": "use source to restore captured severity, or choose info, warning, error, or critical",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

请求体中的未知字段（例如问题规则中的 `status`）返回 `422` 和 `code: invalid_json`。不存在或无法读取的日志或问题返回 `404` 和 `code: not_found`。如果响应丢失，先重新读取日志或问题，再重新发送规则。

## 错误响应格式

应用错误返回 JSON 封装。以下示例是一个被拒绝的请求；`error` 和 `next` 文本取决于具体错误：

```json
{
  "error": "<what is wrong>",
  "code": "validation_failed",
  "next": "<how to fix it>",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

用 `code` 做程序分支，用 `next_action` 做自动化。把 `error` 和 `next` 作为纯文本展示给用户。不要解析它们的措辞。有些错误会添加字段，例如 `limit`、`reset_at` 或 `retry_after_seconds`。没有 JSON 响应体的响应不含 LogBrew `code`。所有错误码请参阅 [API 错误](/zh-Hans/reference/api-errors)。

## 使用 CLI 读取数据

CLI 读取相同的路由，并在使用 `--json` 时返回相同的 JSON。先宽泛查询，再逐步缩小范围：

```bash
logbrew read releases --environment production --json
logbrew read issues --release api@1.2.3 --status unresolved --json
logbrew read logs --release api@1.2.3 --since 24h --json
logbrew read actions --name checkout_failed --since 24h --json
logbrew read traces --status error --since 24h --json
logbrew read trace <trace_id> --json
```

添加 `--pagination cursor` 可以获取游标封装。CLI 请求的是问题响应版本 4。请参阅[读取下一页](/zh-Hans/reference/cli#read-the-next-page)和[实时查看](/zh-Hans/reference/cli#live-watch)。

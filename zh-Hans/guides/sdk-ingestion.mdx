安装适合你运行时的 LogBrew SDK 包。SDK 负责格式化并投递信号。每个包的指南列出了它的信号类型、限制和重试行为。

在应用目录中运行 `npx logbrew-cli@latest setup`，它会替你完成下面这些步骤。参见[用一条命令完成接入](/zh-Hans/quickstart#set-up-with-one-command)。

每次接入都完成以下步骤：

1. 安装适合你运行时的 SDK 包。
2. 把项目级接入密钥放在版本控制之外。
3. 设置稳定的服务、环境和版本值。
4. 从应用发送一条安全的测试信号。
5. 查看投递结果。然后在 LogBrew 中找到这条信号。

批次被接受，说明它已到达 LogBrew API。但筛选条件仍可能隐藏其中的信号。选择正确的项目和时间范围。然后核对服务、环境、版本和信号类型。

启用采集之前，先[选择并测试允许采集的字段](/zh-Hans/guides/safe-capture)。要让“分析”中有数据，按[产品事件采集](/zh-Hans/guides/product-events)操作。

## 严重程度取值

日志和问题使用 `info`、`warning`、`error` 或 `critical`。SDK 和运行时可能发送 `trace`、`debug`、`warn` 或 `fatal` 等别名。LogBrew 会把接受的别名转换为对应的规范值。

### Node.js 请求链路追踪

要实现以请求为根 Span 的链路关联，使用 `@logbrew/sdk` 0.1.16 或更高版本，以及 `@logbrew/node` 0.1.11 或更高版本。

Express 需要 `@logbrew/express` 0.1.5 或更高版本。Fastify 和 NestJS 需要各自的 LogBrew 包为 0.1.6 或更高版本。

这些集成会创建或延续一个请求 Span。Span 名称使用匹配到的路由模板。请求内的日志、问题、操作和指标会继承它的链路和 Span 上下文。升级包不会为升级前已发送的信号补充上下文。

默认的请求集成不会采集请求体或响应体、查询字符串、任意请求头，或原始 `traceparent` 值。

### ASP.NET Core

CLI v0.1.55 或更高版本可以检测使用 `Microsoft.NET.Sdk.Web` 的 .NET 10 项目。在项目根目录预览接入计划。该命令不会修改你的文件：

```bash
logbrew setup --json
```

已发布的计划会安装宿主集成：

```bash
dotnet add package LogBrew.AspNetCore --version 0.1.3
```

在版本控制之外设置 `LOGBREW_SERVER_API_KEY`、`LOGBREW_SERVICE_NAME`、`LOGBREW_ENVIRONMENT` 和 `LOGBREW_RELEASE`。在宿主中注册 LogBrew，并把它的中间件放在路由之后：

```csharp
using LogBrew;

var builder = WebApplication.CreateBuilder(args);
builder.AddLogBrew();

var app = builder.Build();
app.UseRouting();
app.UseLogBrew();
app.MapGet("/", () => "ok");
app.Run();
```

未设置 `LOGBREW_SERVER_API_KEY` 时，这两个注册调用都是安全的空操作。[ASP.NET Core NuGet 包](https://www.nuget.org/packages/LogBrew.AspNetCore/0.1.3)标识了已发布的宿主集成。它的公开包指南介绍了宿主生命周期、请求采集、问题采集、隐私限制和恢复方法。

### 使用 Maven 或 Gradle 的 Java

CLI v0.1.54 或更高版本可以检测 `pom.xml`、`build.gradle` 和 `build.gradle.kts`。在项目根目录预览接入计划。该命令不会修改你的文件：

```bash
logbrew setup --json
```

使用 Maven 时，添加已发布的包：

```xml
<dependency>
  <groupId>co.logbrew</groupId>
  <artifactId>logbrew-sdk</artifactId>
  <version>0.1.13</version>
</dependency>
```

使用 Gradle Kotlin DSL 时，添加同一个 Maven Central 构件：

```kotlin
implementation("co.logbrew:logbrew-sdk:0.1.13")
```

使用 Java 11 或更高版本。

Spring Boot 3 和 4 应用可以暴露一个由应用持有的 `LogBrewClient` bean。它会启用可选的请求、异常、HTTP 客户端、JDBC 和缓存集成。

Spring Kafka 采集需要显式开启：设置 `logbrew.kafka.enabled=true`。它使用应用已有的 Spring Kafka 依赖和客户端 bean。

[Maven Central 上的 Java SDK 构件](https://central.sonatype.com/artifact/co.logbrew/logbrew-sdk/0.1.13)标识了已发布的包。它的公开指南介绍了有上限的 HTTP 投递、关闭流程、日志、Spring 配置、Kafka 关联和隐私限制。

### 使用 CMake 的 C++

C++ SDK 需要 C++17 和 CMake 3.16 或更高版本。CLI v0.1.39 或更高版本可以检测根目录下的 `CMakeLists.txt`。运行 `logbrew setup --json` 可以预览以下接入计划，不会修改你的文件：

```cmake
include(FetchContent)
FetchContent_Declare(
  logbrew
  GIT_REPOSITORY https://github.com/LogBrewCo/sdk.git
  GIT_TAG cpp/logbrew-cpp/v0.2.3
  GIT_SHALLOW TRUE
  SOURCE_SUBDIR cpp/logbrew-cpp
)
FetchContent_MakeAvailable(logbrew)

target_link_libraries(your_app PRIVATE LogBrew::LogBrew)
```

核心 target 没有外部依赖。要通过可选的 libcurl 传输发送批次，把上面最后的 `FetchContent_MakeAvailable` 调用和 target 链接替换为：

```cmake
set(LOGBREW_BUILD_HTTP_TRANSPORT ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(logbrew)
target_link_libraries(your_app PRIVATE LogBrew::HttpTransport)
```

配置应用。然后构建应用，测试所选的 SDK 版本：

```bash
cmake -S . -B build &&
cmake --build build
```

如果构建环境无法拉取 SDK monorepo，使用 [C++ 0.2.3 版本](https://github.com/LogBrewCo/sdk/releases/tag/cpp/logbrew-cpp/v0.2.3)中单独提供的 `logbrew-cpp-0.2.3.tar.gz` 资源文件。解压后的包支持 `cmake --install` 和 `find_package(LogBrew 0.2.3 CONFIG REQUIRED)`。它的包指南介绍了类型化上下文、问题证据、Span 事件、指标、操作和 HTTP 投递。

## <span id="javascript-queue-tracing">JavaScript 队列链路追踪</span>

Node 队列集成是独立的 npm 包。安装 LogBrew JavaScript 基础包、对应的集成包，以及应用已在使用的队列或消息代理客户端。

| 队列或消息代理 | 安装 |
| --- | --- |
| BullMQ | `npm install @logbrew/sdk @logbrew/node @logbrew/bullmq bullmq` |
| KafkaJS | `npm install @logbrew/sdk @logbrew/node @logbrew/kafkajs kafkajs` |
| RabbitMQ / amqplib | `npm install @logbrew/sdk @logbrew/node @logbrew/amqplib amqplib` |

<Warning>
  不要把队列消息体、任意消息头、消息代理 URL，以及会话或账号 Bearer 令牌写进 SDK 配置。使用 LogBrew 提供的项目级服务端接入配置。
</Warning>

## <span id="required-envelope-fields">直接发送原生封装</span>

只有在没有公开 LogBrew SDK 支持的自定义客户端中，才使用 `POST /api/telemetry/ingest`。公开 SDK 使用自己的批次格式。该端点不接受这种格式。

每个原生封装发送 1 到 512 个条目。同一封装中的所有条目共享项目、服务、版本、环境和可选的链路上下文。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `project_id` | 是 | LogBrew 项目的 UUID。必须与接入密钥所属的项目一致。 |
| `environment` | 是 | 部署环境。不超过 64 个 UTF-8 字节，不能包含空白字符、`/` 或 `\`。值 `None` 会被拒绝。 |
| `release` | 是 | 代码版本。不超过 200 个 UTF-8 字节，不能包含 `/`、`\`、制表符或换行符。不能是 `.` 或 `..`。 |
| `service_name` | 是 | 逻辑服务名，例如 `checkout-api`。不能为空。 |
| `sdk_name` | 是 | SDK 或自定义客户端的标识。 |
| `sdk_version` | 是 | SDK 或自定义客户端的版本。 |
| `items` | 是 | 1 到 512 个 `log`、`trace_span`、`issue` 或 `action` 条目。 |
| `trace_id` | 否 | 封装中相互关联的条目共享的 Trace ID。如果某个条目有 `span_id`，则必须提供。 |

### 条目字段

每个条目都有 `type` 和一个 `data` 对象。日志条目使用 `level`。问题条目使用 `severity`。两者都接受[严重程度值](/zh-Hans/concepts/telemetry#severity-values)中列出的值。

| 条目字段 | 适用于 | 说明 |
| --- | --- | --- |
| `id` | 所有条目 | 可选的客户端事件 ID。1 到 200 个字符，在封装内唯一。 |
| `span_id` | `log`、`issue`、`action` | 可选。16 个十六进制字符，不能全为零。封装必须有 `trace_id`。 |
| `name` | `action` | 必填。不超过 64 个 UTF-8 字节。不能以 `$` 开头，不能以空白字符开头或结尾，也不能包含控制字符或不可见的格式字符。 |

如果客户端可能重试，为每个条目发送 `id`。重试时，如果再次发送 `id` 和内容都相同的已接受条目，LogBrew 不会重复存储。响应会把该条目计入 `already_accepted`。

### 问题条目字段

`issue` 条目报告一次错误的发生记录。LogBrew 会把匹配的发生记录归入同一个问题。

| 问题字段 | 必填 | 说明 |
| --- | --- | --- |
| `severity` | 是 | 错误的严重程度，例如 `error`。 |
| `title` | 是 | 问题列表中显示的简短标题。 |
| `message` | 是 | 错误消息。 |
| `exception_type` | 否 | 异常或错误类型，例如 `TypeError`。 |
| `stack_trace` | 否 | 运行时输出的堆栈跟踪文本。 |
| `stack_frames` | 是 | 堆栈帧数组。没有堆栈帧时发送 `[]`。 |
| `fingerprint` | 否 | 分组键。值相同的发生记录归入同一个问题。 |
| `attributes` | 是 | 包含额外上下文的 JSON 对象。没有上下文时发送 `{}`。 |
| `occurred_at` | 是 | 错误发生的时间，采用 RFC 3339 格式，例如 `2026-06-01T12:00:00Z`。 |

堆栈帧接受 `module`、`function`、`filename`、`line`、`column`、`in_app` 和 `debug_id`。所有堆栈帧字段都是可选的。对来自你自己代码的帧，将 `in_app` 设为 `true`。`debug_id` 是一个 UUID，用于标识符号化所用的版本构件。

没有 `fingerprint` 时，LogBrew 按 `exception_type` 分组；缺少 `exception_type` 时改用 `title`。LogBrew 还会使用前 8 个帧的 `module`、`function` 和 `filename`。没有帧时，LogBrew 使用 `title` 和 `message`。行号和列号不会改变分组。

### 请求示例

这个示例发送一个 `issue` 条目、一个 `log` 条目和一个 `action` 条目。把下面的 JSON 保存为 `telemetry-envelope.json`。将示例项目 ID 替换为接入密钥对应的确切项目 ID。把时间戳设为发送测试信号时的当前 UTC 时间。使用你自己的服务和版本值。

```json telemetry-envelope.json
{
  "project_id": "11111111-1111-4111-8111-111111111111",
  "environment": "production",
  "release": "api@1.2.3",
  "service_name": "checkout-api",
  "sdk_name": "custom-native-client",
  "sdk_version": "1.0.0",
  "items": [
    {
      "type": "issue",
      "data": {
        "id": "evt_example_issue_0001",
        "severity": "error",
        "title": "PaymentError: card authorization timed out",
        "message": "card authorization timed out after 3 attempts",
        "exception_type": "PaymentError",
        "stack_trace": "PaymentError: card authorization timed out after 3 attempts\n    at authorizeCard (src/payments/authorize.js:42:11)\n    at submitOrder (src/checkout/submit.js:18:5)",
        "stack_frames": [
          {
            "function": "authorizeCard",
            "filename": "src/payments/authorize.js",
            "line": 42,
            "column": 11,
            "in_app": true
          },
          {
            "function": "submitOrder",
            "filename": "src/checkout/submit.js",
            "line": 18,
            "column": 5,
            "in_app": true
          }
        ],
        "attributes": { "route": "/checkout" },
        "occurred_at": "2026-06-01T12:00:00Z"
      }
    },
    {
      "type": "log",
      "data": {
        "id": "evt_example_log_0001",
        "level": "warning",
        "message": "checkout retry scheduled",
        "source": "runtime",
        "attributes": { "route": "/checkout" },
        "occurred_at": "2026-06-01T12:00:00Z"
      }
    },
    {
      "type": "action",
      "data": {
        "id": "evt_example_action_0001",
        "name": "checkout_failed",
        "distinct_id": "user_123",
        "session_id": "session_456",
        "occurred_at": "2026-06-01T12:00:00Z",
        "properties": { "cart_total": 4200 }
      }
    }
  ]
}
```

通过受保护的配置，把项目级接入密钥加载到 `LOGBREW_INGEST_BEARER`。不要打印它，也不要使用账号凭据。以下命令会发送一次该文件。它需要 curl 7.76.0 或更高版本：

```bash
: "${LOGBREW_INGEST_BEARER:?load the project-scoped ingest key}" &&
curl --fail-with-body --silent --show-error \
  "https://api.logbrew.co/api/telemetry/ingest" \
  -H "Authorization: Bearer $LOGBREW_INGEST_BEARER" \
  -H "Content-Type: application/json" \
  --data-binary @telemetry-envelope.json \
  --write-out '\nHTTP %{http_code}\n'
```

查看 HTTP 状态和响应体。`--fail-with-body` 会保留错误响应体，并在 HTTP 出错时返回非零退出状态。网络故障或超时无法说明 LogBrew 是否已接受请求。只有当条目都带有 `id` 值时，才再次发送同一个文件。没有 `id` 值时，第二次发送可能导致条目被存储两次。

### 响应

请求成功时返回 `200`，以及按数据流统计的新条目数量。`already_accepted` 统计之前的请求已经投递过的条目。

```json
{
  "issues": 1,
  "logs": 1,
  "trace_spans": 0,
  "actions": 1,
  "already_accepted": 0,
  "next": "review accepted telemetry in logs, issues, traces, actions, or live feed",
  "next_action": {
    "code": "review_ingested_telemetry",
    "target": "telemetry_reads"
  }
}
```

### 错误

无效或已撤销的接入密钥会返回 `401`。属于其他项目的密钥也会返回 `401`：

```json
{
  "error": "Invalid ingest key",
  "code": "ingest_key_invalid",
  "next": "create a project-scoped ingest key, then retry ingestion with that key",
  "next_action": {
    "code": "configure_ingest_key",
    "target": "project_ingest_key"
  }
}
```

使用项目级接入密钥。不要用账号凭据代替它。构建产物密钥不能发送遥测数据。

违反字段规则的封装会返回 `422` 和错误码 `validation_failed`。`error` 字段指出违反的规则。`next` 字段说明如何修正请求。例如，`"items": []` 会返回：

```json
{
  "error": "native telemetry envelope cannot be empty",
  "code": "validation_failed",
  "next": "send at least one native telemetry item",
  "next_action": {
    "code": "fix_request",
    "target": "request"
  }
}
```

没有信号时不要发送封装。超过 512 个条目的封装会返回 `422` 和错误 `native telemetry envelope exceeds the item limit`。把它拆分成每批不超过 512 个条目。每个批次都保留项目和共享上下文。

遇到用量限制、速率限制和服务故障时，按 [API 错误](/zh-Hans/reference/api-errors)中返回的 `code` 处理。

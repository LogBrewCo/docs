Create a development project. Send one Node.js log. Read it back from
LogBrew. The CLI creates the project and saves its ingest key. Browser
sign-in is necessary only when the CLI has no valid account access.

<Note>
  Use `--json` for agent workflows. Keep credentials in protected local
  configuration. Pass only variable names between people, tools, and agents.
</Note>

## <span id="first-project-success-path">Before you start</span>

Prepare:

- Node.js 18 or newer.
- LogBrew CLI v0.1.30 or newer.
- `jq`.
- Bash or Zsh.
- A package directory for a server-side Node.js app.

The sample uses project `quickstart-node`, environment `development`, and
release `quickstart@1`. Keep this test separate from production. For another
runtime, use the [SDK ingestion guide](/guides/sdk-ingestion).

<Warning>
  Keep the ingest-key file outside the repository, readable only by you. Do
  not put this server key in browser code, a public bundle, or a prompt.
</Warning>

## Send and read your first log

<Steps>
  <Step title="Read account status" id="confirm-account-access">
    Install the CLI with the command in the [CLI guide](/guides/cli). Then
    read its account state.

    ```bash
    logbrew status --json
    ```

    **Checkpoint:** status reports authenticated account access. If it does
    not, a human runs `logbrew login` once. Then run `logbrew status --json`
    again. An agent must not start a new login when the current
    authentication works.
  </Step>

  <Step title="Create one project from the CLI">
    Select a new file in an owner-only directory. The CLI writes the project
    ingest key to that file before it reports success. It never prints the key
    or its file path.

    ```bash
    install -d -m 700 "$HOME/.logbrew"

    project_result="$(
      logbrew projects create quickstart-node \
        --runtime node \
        --environment development \
        --ingest-key-file "$HOME/.logbrew/quickstart-node.ingest" \
        --json
    )"
    export LOGBREW_PROJECT_ID="$(jq -er '.project.id' <<<"$project_result")"
    jq '{status, setup_status: .setup.status, ingest_key_kind: .ingest_key.kind, next}' \
      <<<"$project_result"
    unset project_result
    ```

    Project creation changes account state. The destination file must not
    exist. If the result is not clear, run the exact command again. The CLI
    reuses its pending request identity. Use `--abandon-retry` only to start a
    different attempt.

    **Checkpoint:** output reports `status: "created"`, setup status
    `created`, and an ingest-key kind. The project exists and the key is
    stored. This does not show telemetry delivery. See
    [Projects](/concepts/projects).
  </Step>

  <Step title="Install the Node.js SDK">
    ```bash
    npm install @logbrew/sdk @logbrew/node
    ```

    Never use an account credential as SDK configuration. Keep the project
    key out of command output, prompts, tickets, source files, and package
    configuration.
  </Step>

  <Step title="Send one safe SDK log">
    Send release and environment markers with one placeholder-only `info` log.
    The key is set only for this Node.js process. Application identity goes
    in `context`.

    ```bash
    LOGBREW_SERVER_API_KEY="$(< "$HOME/.logbrew/quickstart-node.ingest")" \
      node --input-type=module <<'JS'
    import { randomUUID } from "node:crypto";
    import { SdkError } from "@logbrew/sdk";
    import { createLogBrewNodeClient } from "@logbrew/node";

    const client = createLogBrewNodeClient({
      context: {
        schemaVersion: 1,
        resource: { service: { name: "quickstart-node", version: "quickstart@1" } }
      }
    });
    const occurredAt = new Date().toISOString();

    client.release(randomUUID(), occurredAt, {
      version: "quickstart@1",
      metadata: { service: "quickstart-node" }
    });
    client.environment(randomUUID(), occurredAt, { name: "development" });
    client.log(randomUUID(), occurredAt, {
      message: "LogBrew quickstart check",
      level: "info",
      logger: "quickstart-node"
    });

    try {
      const response = await client.shutdown();
      console.log(JSON.stringify({
        ok: true,
        status_code: response.statusCode,
        attempts: response.attempts
      }));
    } catch (error) {
      console.error(JSON.stringify({
        ok: false,
        error: error instanceof SdkError ? error.code : "delivery_failed"
      }));
      process.exitCode = 1;
    }
    JS
    ```

    **Checkpoint:** the script prints `"ok":true` with a `2xx`
    `status_code`. `attempts` is higher than `1` after a retry. A successful
    send is not the last check.

    If delivery fails, the script exits with code `1` and prints a short JSON
    error, such as `{"ok":false,"error":"unauthenticated"}`. It does not print
    the request body or the key.
  </Step>

  <Step title="Read the project doctor report" id="verify-readiness-with-the-project-doctor">
    The CLI uses its saved account access for this read. Do not use the
    project ingest key.

    ```bash
    : "${LOGBREW_PROJECT_ID:?set the project UUID}"

    logbrew doctor --project "$LOGBREW_PROJECT_ID" --json
    ```

    **Checkpoint:** the report has `status: "ready"`. Also read each item in
    `checks`. Exit code `0` does not show that all checks passed. For another
    status, follow `next` and the [CLI reference](/reference/cli).
  </Step>

  <Step title="Read the test log">
    Use the project, release, and environment from the SDK batch.

    ```bash
    logbrew read logs --project "$LOGBREW_PROJECT_ID" \
      --release quickstart@1 \
      --environment development \
      --since 1h \
      --json
    ```

    **Checkpoint:** `LogBrew quickstart check` appears for that project,
    release, and environment. This shows delivery of the test log only.
  </Step>
</Steps>

## <span id="understand-the-test-result">Read the test result</span>

The sample sends three events. Only one is a log. The release and environment
markers give context to the log.

The `console.log` line prints the delivery result to your terminal. The
`client.log` call sends the log to LogBrew. The ingest key selects the
project that receives the log. A CLI `--project` filter does not move events.

This log has no trace context because the sample does not create a request
span. That does not show that the log failed. The CLI read is a snapshot.
Run it again to read later events, or use `logbrew watch logs --json` for a
live stream.

## Common recovery decisions

| Result | Next step |
| --- | --- |
| CLI status is not authenticated | A human runs `logbrew login`. Then run the status command again. |
| The ingest-key file exists | Select an unused path. Do not overwrite an unknown credential. |
| Project creation result is not clear | Run the exact create command again. |
| `unauthenticated` | Examine the project ingest key, not the CLI account credential. A new login does not fix it. |
| `rate_limited` | Wait before you send again. Do not loop or create a new key. |
| `transport_error` or `network_failure` | Examine connectivity. A failed response does not show that the earlier request had no effect. |
| `delivery_failed` | Stop and examine the failure. Do not print secrets or the request body. |
| Doctor `status` is not `ready` | Read `checks` and `next`. Keep the same project. |
| The log read is empty | Compare the project, environment, release, and time range with the sent batch. |

If telemetry is still missing, use the
[first telemetry checks](/guides/troubleshooting#recover-missing-first-telemetry).
If those checks do not help, [report a problem](/guides/report-a-problem).
Do not attach credentials, raw telemetry, customer data, local paths, or
source code.

## Move to your application

- Create the client once in your app's setup code.
- Load the ingest key from your existing secret configuration.
- Use stable service, environment, and release names from your deployment
  configuration. See [Releases](/concepts/releases).
- Write log messages that name the operation and its result, such as
  `Report generation completed`. Keep private values out of the message.
- Keep one sender for each application log to prevent duplicate records.
- Before a production rollout, send one safe event through the real code path
  and read it back.

title: "Quickstart"
description: "Create a first project, send one safe SDK event, verify readiness, and investigate without exposing credentials."
---

This is the shortest supported path to first value with JavaScript or Node.js.
A human handles browser sign-in and the one-time project setup value. A person
or AI agent can complete the remaining steps using stable JSON and fixed scope.

<Note>
  Use `--json` for agent workflows. Keep credentials in protected local
  configuration and pass only variable names between people, tools, and agents.
</Note>

## First project success path

<Steps>
  <Step title="Sign in and confirm account access">
    Install the CLI with the platform command in the [CLI guide](/guides/cli),
    then complete browser sign-in.

    ```bash
    logbrew login
    logbrew status --json
    ```

    **Checkpoint:** status confirms authenticated account access. If an agent
    detects missing auth, it must ask a human to run `logbrew login` and then
    retry status.
  </Step>

  <Step title="Create or select one project">
    Open **Add Project** in LogBrew and create or select the project that will
    own this app's telemetry. Keep its UUID in protected local configuration.

    Copy the one-time project-scoped ingest key shown for SDK setup directly
    into the app's protected configuration. The key is shown once. A human
    should perform this handoff; an agent should work with the configured
    variable name, not the value.

    Never print, paste into a ticket, commit, or retain the value in command
    history. An account access credential is for account and API reads; it is
    not SDK ingest configuration.

    **Checkpoint:** the project is selected and the one-time value is stored.
    This confirms setup material exists, not that telemetry has arrived. See
    [project setup and credential roles](/concepts/projects).
  </Step>

  <Step title="Install the current JavaScript and Node.js SDK path">
    Use the published package names from the current website handoff.

    ```bash
    npm install @logbrew/sdk @logbrew/node
    ```

    Apply the exact generated setup snippet shown by **Add Project**. Do not
    replace its project-scoped configuration with account or session auth.
    [Review the agent-safe SDK handoff](/guides/ai-agents#set-up-sdk-telemetry-from-a-website-handoff)
    when an AI agent is making the code change.
  </Step>

  <Step title="Send one safe first event">
    Run the generated setup snippet with one placeholder-only `info` event.
    Keep `release` and `environment` explicit and reuse those exact values
    during verification.

    The event must not contain credentials, headers, raw request bodies,
    customer data, local paths, or unrelated source. A submitted request is not
    the readiness checkpoint; continue to the project doctor.
  </Step>

  <Step title="Verify readiness with the project doctor">
    Use account authentication for this read. Do not use the project ingest
    value or print the account credential.

    ```bash
    : "${LOGBREW_API_URL:?set LOGBREW_API_URL}"
    : "${LOGBREW_PROJECT_ID:?set the project UUID}"
    : "${LOGBREW_ACCOUNT_BEARER:?set the account access bearer}"

    curl -sS "$LOGBREW_API_URL/api/projects/$LOGBREW_PROJECT_ID/doctor" \
      -H "Authorization: Bearer $LOGBREW_ACCOUNT_BEARER" \
      | jq '{state, setup_status, setup_acknowledged, has_active_ingest_key, first_telemetry_seen_at, next, next_action}'
    ```

    **Checkpoint:** `state: "ready"` with
    `next_action.code: "inspect_recent_telemetry"` and
    `next_action.target: "telemetry_reads"`. For any other state, follow the
    returned typed action through the [project diagnosis
    guide](/concepts/projects#diagnose-project-setup) instead of guessing from
    logs.
  </Step>

  <Step title="Read the event and follow typed issue routing">
    Use the same project, release, and environment that sent the event.

    ```bash
    : "${LOGBREW_RELEASE:?set the event release}"
    : "${LOGBREW_ENVIRONMENT:?set the event environment}"

    logbrew read logs --project "$LOGBREW_PROJECT_ID" \
      --release "$LOGBREW_RELEASE" \
      --environment "$LOGBREW_ENVIRONMENT" \
      --since 1h \
      --json
    ```

    **Checkpoint:** the safe `info` event appears in the fixed scope. If an
    issue is present, start from its authenticated detail response and follow
    only the returned `next_action.code` and `next_action.target`. Use the
    [typed issue investigation workflow](/guides/investigate-an-issue); never
    broaden the query across projects.
  </Step>

  <Step title="Recover safely or report privately">
    Follow the doctor's typed action first. If telemetry is still missing, use
    the ordered [first telemetry checks](/guides/troubleshooting#recover-missing-first-telemetry).

    When those checks cannot recover the path, [create a private support
    ticket](/guides/report-a-problem). Tickets are private to the submitting
    account and LogBrew support, but reports must still omit credentials,
    authorization headers, project IDs, hosts, raw logs or payloads, customer
    data, local paths, and source code. Use only the support guide's strict
    diagnostic allowlist.
  </Step>
</Steps>
